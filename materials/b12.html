    B12 — Security fundamentals: trust, crypto, PKI

    Almost everything people call "a security feature" is one of two questions being answered: who are you? and are you allowed to do this? The machinery around those two questions — passwords, keys, signatures, certificates, permission files — looks enormous from outside and turns out to be small once you have built each piece yourself. That is what this module does. You will run your own certificate authority, issue certificates to yourself, make two programs prove their identities to each other, and then break that arrangement four different ways so that each error message becomes a specific accusation rather than a wall of noise.

    Kubernetes is an unusually good reason to learn this properly, because a cluster is held together by certificates end to end. Every component authenticates to the API server with one. Every kubeconfig is a certificate plus an address. Every "my kubectl suddenly stopped working" is, underneath, one of the four failures you will deliberately cause in the last lesson. People who have never issued a certificate by hand experience this as bad luck; people who have, read the error and know which file to look at.

    Four movements. Framing: the questions that make a security decision answerable — what are you protecting, from whom, and where does control change hands — plus the authentication/authorization split that decides where you go looking when something is refused. Crypto in plain terms: hashing, encoding and encryption told apart for good, the two key models, signatures, and SSH keys as the example already in your hands. PKI hands-on: a CA, a CSR, subject alternative names, chain verification, a real TLS server and mutual TLS — all with openssl, all on one machine. Handling secrets: how a secret leaks on a shared box even when nobody is malicious, and the two kernel layers that stand behind file permissions when everything else has failed.

    Checkpoints16 Hours~5 PrerequisitesB4, B8
    • Threat-model something concrete in one page: name its assets, its plausible actors, and every trust boundary it crosses.
    • Turn "least privilege" and "defense in depth" from slogans into decisions you can check, and measure one with systemd-analyze security.
    • Keep authentication and authorization strictly apart, and route a refusal to the right file on the first try.
    • Tell hashing, encoding and encryption apart on sight, and explain in one sentence why base64 protects nothing.
    • Choose between symmetric and asymmetric keys, and explain why TLS uses both in the same connection.
    • Sign a file and verify it, and say exactly what a valid signature proves and what it does not.
    • Explain SSH key login as a signature challenge, and what ssh-agent trades away for convenience.
    • Create a certificate authority — a key plus a self-signed certificate — and say precisely what holding that key means.
    • Issue a certificate in the two proper steps: a key and a CSR from the subject, a signature from the CA.
    • Get subject alternative names right, and recognise the failure mode of a certificate whose CN is perfect and whose SAN list is wrong.
    • Read a certificate with openssl x509 -text, verify a chain with openssl verify, and find an expiry date in five seconds.
    • Run a TLS server and client with openssl, then require a client certificate so both ends prove identity.
    • Demonstrate how secrets leak through process listings and /proc/PID/environ, and argue for files over environment variables from evidence.
    • Say what seccomp and AppArmor each confine, and inspect one loaded profile.
    • Build mutual TLS between two local processes, each verifying the other against your CA.
    • Break that mTLS four ways and map every error string to one cause without guessing.

    B4 is the real prerequisite: a private key is protected by a file mode and nothing else, so the permission check (B4.5) and the fact that root walks past it entirely (B4.10) are the ground this module stands on. B8 matters because every TLS lab here is an ordinary TCP connection — ss, curl -v and tcpdump (B8.13) are still the tools, and the handshake you are about to read happens right after the three-way handshake you already know (B8.8). Everything runs on the throwaway sandbox VM (B0.1), never on the cluster, and nothing needs installing: openssl, ssh-keygen and aa-status all ship with Ubuntu. You will create a user named mallory, a working directory ~/ca, and a couple of throwaway units; the last lesson tells you how to remove them. Take a snapshot first (B0.9) if you would rather roll back than clean up. One warning worth stating once: the CA you build here is a teaching CA on a disposable VM. Never use these keys, or these one-line commands, for anything real.

    Framing

    B12.1

    Threat modelling in one page: assets, actors, trust boundaries

    Why it matters

    "Is this secure?" is an unanswerable question, and answering it anyway is how people end up with elaborate controls protecting nothing. The answerable version has three parts bolted on: secure for what, against whom, and at which boundary. Threat modelling is just the discipline of writing those three down before you choose a control. It takes fifteen minutes, it needs no tools, and it is the difference between "we enabled TLS" and "we know what TLS did and did not fix here."

    The concept

    Three words carry the whole exercise, and each one is ordinary:

    • Assets — the things that would hurt to lose, leak or have altered. Be specific: not "the server" but "the private key in ~/.ssh/id_ed25519", "the database's contents", "the ability to run commands as root". A list of concrete nouns beats a paragraph of intent.
    • Actors — who might want them, described by their position rather than their motive. "An internet scanner with no account", "a logged-in user on this machine", "a process running as the same user", "someone holding the disk". The position is what determines which controls are even relevant.
    • Trust boundaries — the lines where control changes hands. Every time data or authority crosses from one party to another — user to kernel, one machine to another, your process to a library it loaded, host to container — that crossing is a boundary, and it is where controls belong. Nothing is a "security control" except at a boundary.

    The point of naming boundaries out loud is that once they are on paper, a lot of arguments end. Consider the container runtime socket from B9.18: /run/containerd/containerd.sock is root-owned because whoever can write to it can start a container with any mount and any privilege — that socket is a trust boundary. Draw it once and "just mount the runtime socket into the pod, it's easier" stops sounding like a convenience and starts sounding like what it is: handing the thing on the other side of the boundary everything the thing on this side has.

    A useful habit while modelling: for each control you already have, ask which actor it stops. A file mode of 600 stops another logged-in user. It does not stop root, it does not stop a process running as you, and it does nothing at all once the disk is out of the machine. That is not a criticism of file modes — it is what "against whom" means, and writing it down is how you notice the actor you had not covered.

    asset→who wants it→boundary it crosses→control at that boundary

    Controls chosen in any other order tend to protect the wrong crossing.

    Lab
    1. Pick one concrete asset and look at the only thing currently protecting it. If you have no key yet, make one — you will need it again in B12.7. 
      multipass shell sandbox
ls -l ~/.ssh/id_ed25519 2>/dev/null || ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
stat -c '%n  mode=%a  owner=%U:%G' ~/.ssh/id_ed25519
      /home/ubuntu/.ssh/id_ed25519  mode=600  owner=ubuntu:ubuntu     ← one file mode is the entire control
    2. Introduce a second actor — an ordinary logged-in user with no privileges — and test the boundary the file mode draws. This is the actor 600 exists to stop. 
      sudo adduser --disabled-password --gecos '' mallory
sudo -u mallory cat ~/.ssh/id_ed25519
      cat: /home/ubuntu/.ssh/id_ed25519: Permission denied     ← the control works against this actor
    3. Now test the actor it does not stop. Root does not consult the permission bits at all (B4.10), so anyone who can become root has already crossed this boundary. 
      sudo head -c 40 ~/.ssh/id_ed25519; echo
      -----BEGIN OPENSSH PRIVATE KEY-----      ← root reads it regardless of mode 600
    4. Write the model down. One page, three headings — the artefact is the point, because a model in your head cannot be checked by anyone else. 
      cat > ~/threat-model.md <<'EOF'
# Asset: SSH private key ~/.ssh/id_ed25519
## Actors
- other logged-in user on sandbox      (stopped by: mode 600)
- any process running AS ubuntu        (NOT stopped: same uid, e.g. a bad npm package)
- root / anyone who can sudo           (NOT stopped: root ignores modes)
- holder of the disk image or snapshot (NOT stopped: encrypt the key with a passphrase)
## Trust boundaries crossed
1. disk -> my process        (file permissions)
2. my process -> ssh-agent   (agent holds it decrypted in memory)
3. my machine -> remote host (only a SIGNATURE crosses; the key never does)
EOF
grep -c . ~/threat-model.md
      14        ← the model exists as a file; boundary 3 is the one B12.7 explains
    5. Sanity-check the model against reality: boundary 3 claims the private key never leaves the machine. Confirm what the server actually holds is the public half. 
      ssh-keygen -y -f ~/.ssh/id_ed25519 | cut -c1-40
      ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI       ← this half is what goes into authorized_keys
    Verify

    Without looking at your file, name the three headings and produce one entry under each for a different asset — say, the sudo ability on this VM. Then answer the question that makes a model useful: for each control you listed, which actor does it stop, and which actor walks straight past it? If every control on your page stops the same actor, you have found a real gap — that is defense in depth's absence, and it is the subject of the next lesson.

    Gotchas

    The most common failure is modelling the actor you find interesting rather than the actor you actually have. Elaborate defenses against a remote attacker are routine on machines where the real exposure is a hundred people with sudo and no audit trail. Position, not drama: list who genuinely has a foothold today, and cover those first.

    The second is treating a boundary as a control. Naming /run/containerd/containerd.sock as a trust boundary does not protect it; it tells you that whatever protects it — file mode, group membership, not mounting it into workloads — is load-bearing, and that changes to it are security changes even when the commit message says "convenience". A boundary is where you must decide, not the decision.

    Kubernetes has a small set of boundaries that carry nearly all of its security weight, and they are worth naming now because the rest of the advanced track keeps crossing them. The API server is the boundary between "anyone on the network" and "the cluster's state" — which is why every request through it is authenticated then authorized. The node is the boundary between the control plane and untrusted workloads, which is why a pod that can read the kubelet's credentials or the container runtime socket has effectively escaped. And etcd is the boundary behind everything: direct read access to it is equivalent to reading every Secret in the cluster, because that is literally where they are stored.

    The etcd trust domain and why it is treated as a separate one is W2.5; how a pod's identity reaches the API server at all is W7.4.

    Docs

    There is no man page for threat modelling — the useful searches are the artefacts. man 7 credentials for the identities an actor can hold on a Linux box, and man 2 access for the check that decides a boundary crossing at the filesystem. For the container-shaped boundaries, man 7 namespaces and man 7 capabilities are the two pages that define what "inside" and "outside" mean.

    B12.2

    Least privilege and defense in depth, as decisions you can check

    Why it matters

    These two phrases appear in every security document ever written, which has drained them of meaning. Both are actually testable questions about a specific program: what is the smallest set of permissions under which this still works? and if this one control fails, what is the next one? Asked about a real service, they produce a concrete list of changes — and on a systemd machine you can watch a score move as you make them.

    The concept

    Least privilege means a program holds only the authority it needs, for only as long as it needs it. The trap is that "needs" is usually assumed rather than measured. A web server needs to bind port 80; historically that required root, so web servers ran as root, so a bug in the request parser gave an attacker the whole machine. The privilege that mattered was one narrow thing — bind a port below 1024 — and root was simply the only way anyone knew to ask for it. Linux has had a better answer for years: capabilities (B4.10) split root into a keyring of individually-issued permits, and CAP_NET_BIND_SERVICE is exactly the one permit here.

    Defense in depth means assuming any single control will fail and asking what stands behind it. Not because you expect to be attacked in layers, but because controls fail in ordinary ways: a mode gets changed by a deployment script, a validation is skipped on one code path, a dependency is compromised. The question is never "is this control good enough", it is "what happens the day it isn't".

    Both become concrete on a service. Take a program that must serve on port 80 and read one config file, and walk it down the privilege ladder — running as root, then as an unprivileged user with the one capability it needs, then with the rest of the machine taken away from it. On systemd every rung is a line in a unit file (B11.4): User= drops the identity, AmbientCapabilities= grants the single permit, NoNewPrivileges= forbids regaining anything through a setuid binary (B4.9), ProtectSystem=strict makes the filesystem read-only for it, PrivateTmp= gives it a mount namespace of its own (B6.3). None of those is new machinery — they are B4's and B6's primitives with unit-file names.

    root, everything→own user + one capability→no new privileges→read-only fs, private /tmp

    Least privilege picks the rung; defense in depth is the reason you keep descending after it already works.

    Lab
    1. Write the naive version first — the one that works and gives away everything. It runs as root purely to bind a low port. 
      sudo tee /etc/systemd/system/web.service >/dev/null <<'EOF'
[Unit]
Description=Toy web server
[Service]
ExecStart=/usr/bin/python3 -m http.server 80 --directory /srv/toy
[Install]
WantedBy=multi-user.target
EOF
sudo mkdir -p /srv/toy && echo hi | sudo tee /srv/toy/index.html >/dev/null
sudo systemctl daemon-reload && sudo systemctl start web
curl -s localhost:80; ps -o user,args -C python3 --no-headers | head -1
      hi
root     /usr/bin/python3 -m http.server 80 --directory /srv/toy    ← full root, to bind one port
    2. Measure it before changing anything. systemd-analyze security scores a unit's exposure from 0 (locked down) to 10 (nothing between it and the machine) — a rare case of a security question with a number attached. 
      systemd-analyze security web.service | tail -3
      → Overall exposure level for web.service: 9.6 UNSAFE 😨      ← the naive unit
    3. Apply least privilege: give the service its own identity and exactly one piece of root's authority instead of all of it. 
      sudo useradd --system --no-create-home --shell /usr/sbin/nologin toyweb
sudo mkdir -p /etc/systemd/system/web.service.d
sudo tee /etc/systemd/system/web.service.d/10-drop.conf >/dev/null <<'EOF'
[Service]
User=toyweb
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
EOF
sudo systemctl daemon-reload && sudo systemctl restart web
curl -s localhost:80; ps -o user,args -C python3 --no-headers | head -1
      hi                                                       ← still works
toyweb   /usr/bin/python3 -m http.server 80 ...          ← not root any more
    4. Confirm the permit is real and narrow by reading the process's capability sets straight out of /proc (B4.12) rather than trusting the unit file. 
      pid=$(systemctl show -p MainPID --value web); grep -E 'CapEff|CapBnd' /proc/$pid/status
capsh --decode=$(awk '/CapEff/{print $2}' /proc/$pid/status)
      CapBnd: 0000000000000400
CapEff: 0000000000000400
0x0000000000000400=cap_net_bind_service      ← one permit on the keyring, not the master key
    5. Now add depth: layers that do nothing today and matter the day the program is compromised. Each line takes away something it never needed. 
      sudo tee -a /etc/systemd/system/web.service.d/10-drop.conf >/dev/null <<'EOF'
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ReadOnlyPaths=/srv/toy
EOF
sudo systemctl daemon-reload && sudo systemctl restart web
curl -s localhost:80; systemd-analyze security web.service | tail -1
      hi
→ Overall exposure level for web.service: 2.8 OK 🙂       ← same behaviour, far less reachable
    6. Prove one of the layers actually bites, rather than believing the score. The service can still serve its files and can no longer write anywhere on the system. 
      sudo -u toyweb touch /srv/toy/evidence 2>&1 | head -1
sudo systemctl stop web; sudo rm -rf /etc/systemd/system/web.service /etc/systemd/system/web.service.d
sudo systemctl daemon-reload; echo cleaned
      touch: cannot touch '/srv/toy/evidence': Permission denied
cleaned
    Verify

    State the least-privilege answer for the toy server in one sentence — which single capability it needs and why root was ever involved — and then name three layers you added that do nothing on a healthy day. Check your reasoning with the tool: systemd-analyze security web.service before and after should differ by several points, and the service should behave identically. If a lockdown line breaks the service, that is the useful outcome too; it tells you the program needed something you assumed it didn't.

    Gotchas

    AmbientCapabilities= without CapabilityBoundingSet= is half a job. The ambient set grants the permit; the bounding set is the ceiling on what the process could ever acquire, and leaving it at the default means a setuid binary or a File capability could still hand it more later. Set both, and add NoNewPrivileges=yes so the setuid route is closed outright.

    ProtectSystem=strict makes the entire filesystem read-only for the service, which is exactly what you want and will absolutely break a program that writes a pid file, a cache or a log to disk. The fix is not to weaken it back to full but to name the one path it needs with ReadWritePaths= or StateDirectory= — which is least privilege doing its job by forcing you to enumerate what the program actually writes.

    Finally: a low exposure score is not safety. systemd-analyze security knows about sandboxing options and nothing about your application's bugs, its credentials, or what it is allowed to reach on the network. It is a checklist that happens to have a number, useful for comparing a unit against itself before and after — not a verdict.

    Every line you just wrote has a direct counterpart in a pod's securityContext, because it is the same kernel machinery reached through a different configuration language. User= is runAsUser and runAsNonRoot. AmbientCapabilities=/CapabilityBoundingSet= are capabilities.add and capabilities.drop — and drop: ["ALL"] plus one add is exactly the keyring argument above. NoNewPrivileges= is allowPrivilegeEscalation: false. ProtectSystem=strict is readOnlyRootFilesystem: true, with ReadWritePaths= becoming an emptyDir mounted where the app writes. Kubernetes bundles these into named tiers — the Pod Security Standards privileged, baseline and restricted — and the restricted tier is essentially this lesson's final unit expressed as policy. (Those fields are a CKS topic rather than a CKA one, so the advanced track does not drill them; the machinery is the same regardless of which exam asks about it.)

    Least privilege in its CKA-relevant form is RBAC: the smallest Role that still works, bound as narrowly as possible — W7.6. What actually runs privileged on a node, and why the kubelet and the static pods are in a different position from your workloads, is W1.2.

    Docs

    man 5 systemd.exec is the page for every sandboxing option used here — search it for ProtectSystem, NoNewPrivileges, AmbientCapabilities. man 1 systemd-analyze documents the security verb and how the exposure score is assembled. man 7 capabilities for the permit list and the ambient/bounding set rules, and man 1 capsh for decoding the hex you read out of /proc.

    B12.3

    Authentication vs authorization: two questions, two files

    Why it matters

    When something is refused, there are exactly two possibilities: the system did not believe you are who you claim, or it believed you completely and decided you may not do that. They are fixed in different places by different people, and confusing them is the single most expensive triage mistake in this whole subject — it is why people regenerate certificates for hours when the answer was one line of policy, and vice versa.

    The concept

    Authentication (often abbreviated authn) answers who are you? It ends in an identity or in nothing at all. The evidence can be something you know (a password), something you hold (a private key, a certificate) or something a trusted third party asserts (a signed token). Its failure mode is total: the system has no idea who is asking.

    Authorization (authz) answers may this identity do this particular thing? It starts from an established identity and consults a policy — a file, a table, a set of rules — to reach yes or no. Its failure mode is specific: the system knows exactly who you are and is declining this action.

    The keycard analogy holds all the way through, so use it: authentication is the guard confirming the photo on your ID is you; authorization is whether your card opens that door. Two different systems, two different people to complain to, and — importantly — an authorization failure is proof that authentication succeeded. If you are being told "you may not", the system already knows who you are, so nothing about your credentials needs fixing.

    sudo is the local example, and it separates the two cleanly enough to demonstrate. Your password authenticates you to sudo; /etc/sudoers then authorizes what that identity may run. You can watch the failures happen in order: get the password wrong and you never reach the policy; get it right without a sudoers entry and you are told, in different words, that you are recognised and refused.

    request→authn: who are you?→identity→authz: may you?→allow / deny

    The identity in the middle is the handoff — everything left of it is credentials, everything right of it is policy.

    Lab
    1. Give the mallory user from B12.1 a password so she can attempt to authenticate at all. 
      echo 'mallory:practice-only' | sudo chpasswd
sudo -u mallory whoami
      mallory        ← the identity exists; nothing has been authenticated yet
    2. Watch an authentication failure. Log in as her and run sudo with the wrong password — the request never reaches any policy. 
      su - mallory        # password: practice-only
sudo id             # deliberately type a WRONG password three times
      [sudo] password for mallory:
Sorry, try again.
[sudo] password for mallory:
sudo: 3 incorrect password attempts          ← authn failed: no identity was established
    3. Now authenticate successfully and watch the second question fail. Same command, correct password, completely different message. 
      sudo id             # type the CORRECT password: practice-only
      [sudo] password for mallory:
mallory is not in the sudoers file.  This incident will be reported.
                                        ← authn succeeded; authz refused
    4. Fix it in the right place. The credential was never the problem, so the change goes in the policy — group membership, which /etc/sudoers grants to. 
      exit                                     # back to the ubuntu user
sudo grep -E '^%sudo' /etc/sudoers
sudo usermod -aG sudo mallory
      %sudo   ALL=(ALL:ALL) ALL       ← the policy line: members of group sudo may run anything
    5. Confirm the same credential now passes both stages. Group membership is read at login, so a fresh session is required — the policy changed, the identity did not. 
      su - mallory        # password: practice-only
id -nG; sudo id
      mallory sudo                                      ← identity now carries the group
[sudo] password for mallory:
uid=0(root) gid=0(root) groups=0(root)              ← authenticated, then authorized
    6. Ask sudo to show you the policy for the identity it just authenticated — the closest thing to "print my permissions" a Linux box offers. 
      sudo -l | tail -3; exit
      User mallory may run the following commands on sandbox:
    (ALL : ALL) ALL                                 ← the authz answer, stated in full
    Verify

    Explain out loud, without notes, why "you are not in the sudoers file" is proof that your password was correct. Then do the translation you will use constantly later: given a refusal, say which of the two questions failed and which file you would open. A rejected password, an expired certificate and an unknown signing authority are all the first question; a recognised user without a matching rule is the second. If you cannot tell which one an error is, the error message itself is the thing to read more carefully — the two are almost always worded differently on purpose.

    Gotchas

    Some systems deliberately blur the line to avoid leaking information. A login form that says "invalid username or password" is refusing to tell you which of the two failed, because saying "no such user" would let an attacker enumerate accounts. That is a reasonable design and an annoying one to debug: when a system won't tell you which question failed, the server-side log usually will, and that is where to look rather than at the message you were shown.

    The other trap is fixing the wrong side because the wrong side is easier to change. Regenerating a credential is fast and satisfying; editing a policy needs someone's approval. That asymmetry is exactly why people burn afternoons reissuing certificates for what was, from the first error message, a policy decision. Read the refusal before touching anything.

    This split is the shape of the API server's request pipeline: every request goes through authentication, then authorization, then admission, in that order, and each stage can refuse for its own reasons. The two HTTP status codes tell you which stage spoke. 401 Unauthorized — badly named, it means unauthenticated — says your certificate, token or kubeconfig was not accepted at all, so the fix is in your credentials or the cluster's CA trust. 403 Forbidden says the API server knows precisely who you are, printed your username and groups in the message, and RBAC found no rule permitting the verb on that resource; the fix is a Role and a RoleBinding, and your credentials are fine. Learning to read those two numbers correctly saves more time than any other single habit in cluster troubleshooting.

    The full authn → authz → admission pipeline in order is W1.4; the three credential types the cluster accepts for the first question are W7.1, the authorizer chain that answers the second is W7.5, and kubectl auth can-i — the direct equivalent of sudo -l — is W7.8.

    Docs

    man 8 sudo for the two stages in one program and the -l flag that prints the policy; man 5 sudoers for the rule syntax and the %group form used above. man 8 pam and man 5 pam.conf if you want to see where Linux authentication is actually implemented — PAM is the layer that sudo, login and sshd all delegate the first question to.

    Crypto in plain terms

    B12.4

    Hashing, encoding, encryption — three things that are not each other

    Why it matters

    These three get muddled constantly, and one particular muddle causes real damage: people see base64 and think "encrypted". It is not. It is not even slightly. Getting this straight takes ten minutes with three commands, and it inoculates you against the single most common beginner misreading in the entire Kubernetes ecosystem — that a Secret's base64 value is protected.

    The concept

    Three operations, distinguished by one question: who can reverse it, and with what?

    • Hashing — one way, no key, and nobody can reverse it. A hash function turns any input into a fixed-size fingerprint (sha256sum gives 64 hex characters whether the input is one byte or a gigabyte). Change one bit of the input and roughly half the output bits change, which is what makes it a useful fingerprint. Use it to answer "is this the same as that?" without holding the original: password checking, file integrity, and — as you will see later — the thing that actually gets signed in a signature.
    • Encoding — reversible by anyone, no key involved. Base64 rewrites arbitrary bytes using 64 safe characters so they survive a place that only accepts text: a JSON field, an email body, a YAML file. It is a transport convenience with the security value of writing something backwards. base64 -d undoes it, and there is nothing to know or possess in order to run that command.
    • Encryption — reversible only with a key. Without the key, the output is meaningless; with it, the original comes back exactly. This is the only one of the three that protects a secret's contents, and it always raises the question the other two never do: who has the key, and where is it kept?

    The tell for encoding is that the transformation is fully specified in a public document and needs no secret input. If you can undo it on any machine in the world with a command that takes no key, it was encoding. There is a related third-party habit worth naming: hashes are often stored alongside a random salt, so that two users with the same password do not get the same fingerprint and a precomputed table of common passwords stops being useful. That is why /etc/shadow entries contain a $6$ prefix, a salt and then the hash.

    hash: one way, no key·encode: reversible by anyone·encrypt: reversible with a key

    Only the right-hand one protects anything; the middle one is the one people mistake for it.

    Lab
    1. Run all three on the same string and put the outputs next to each other. Start with hashing — note the fixed length regardless of input. 
      echo -n 'hunter2' | sha256sum
echo -n 'hunter3' | sha256sum
      f52fbd32b2b3b86ff88ef6c490628285f482af15ddcb29541f94bcf526a3f6c7  -
bd50f2c...totally different...9a1c  -        ← one character changed, the whole fingerprint did
    2. Now encode the same string, and immediately undo it. No key was involved in either direction — this is the whole point. 
      echo -n 'hunter2' | base64
echo -n 'aHVudGVyMg==' | base64 -d; echo
      aHVudGVyMg==
hunter2          ← recovered by anyone, anywhere, with no secret at all
    3. Encrypt it properly and see what a keyed transformation looks like. The output is bytes, so it is base64-armoured for display — both operations in one line, which is exactly why people confuse them. 
      echo -n 'hunter2' | openssl enc -aes-256-cbc -pbkdf2 -pass pass:mykey -a
echo 'U2FsdGVkX1+...' | openssl enc -d -aes-256-cbc -pbkdf2 -pass pass:mykey -a
      U2FsdGVkX1+3Qm0Zt7YbVw==8k2Lp9xNc1dRfGh4      ← ciphertext (armoured with base64 for display)
hunter2                                        ← only comes back with -pass pass:mykey
    4. Prove the key is load-bearing: same ciphertext, wrong key, no plaintext. This is the difference between encoding and encryption in one command. 
      echo -n 'hunter2' | openssl enc -aes-256-cbc -pbkdf2 -pass pass:mykey -a > /tmp/ct
openssl enc -d -aes-256-cbc -pbkdf2 -pass pass:WRONG -a -in /tmp/ct
      bad decrypt
40E7...:error:1C800064:Provider routines::bad decrypt        ← no key, no plaintext
    5. Try to reverse a hash the same way and confirm there is no command for it. What people call "cracking" is guessing inputs and comparing fingerprints — which is why a slow, salted password hash matters. 
      sudo grep '^ubuntu:' /etc/shadow | cut -d: -f2 | cut -c1-30
      $6$Xk2p9QmZ$hT4vN...       ← $6$ = SHA-512-crypt, then the salt, then the hash. No key, no reverse.
    6. Do the Kubernetes experiment early, because it is the reason this lesson exists. A Secret's value is stored exactly like this — one command from plaintext. 
      printf 'apiVersion: v1\nkind: Secret\ndata:\n  password: %s\n' "$(echo -n 'hunter2' | base64)" | tee /tmp/secret.yaml
grep password: /tmp/secret.yaml | awk '{print $2}' | base64 -d; echo
        password: aHVudGVyMg==
hunter2          ← that is the entire "protection" a Secret's encoding provides
    Verify

    Answer three questions cold. Which of the three can you undo with no secret whatsoever, and why does that operation exist at all? (Encoding — so arbitrary bytes survive a text-only field.) Why can a password file store hashes safely but never store encrypted passwords comfortably? (A hash needs no key to verify against, so there is no key to protect or leak; an encrypted password requires the key to be present on the machine doing the check, which just moves the secret.) And what does a $6$ prefix in /etc/shadow tell you? (The hash algorithm, followed by a per-user salt, so identical passwords do not produce identical hashes.)

    Gotchas

    The base64-is-security misreading is so common that it deserves stating in its strongest form: if a value is base64 in a config file, a Git repository or a YAML manifest, treat it as if it were written in plain text, because it is. The encoding stops nobody, and it has the unfortunate side effect of looking like protection to a casual reader, which is worse than no protection at all — plaintext at least looks alarming.

    The second trap is reaching for a fast hash where a slow one is required. sha256sum is designed to be fast, which is a virtue for file integrity and a liability for passwords, where speed is exactly what an attacker guessing billions of candidates wants. Password storage uses deliberately slow, salted functions (bcrypt, scrypt, argon2, or SHA-512-crypt with many rounds as in /etc/shadow). Same word, "hash"; entirely different design goal.

    This is the whole answer to "why are Kubernetes Secrets only base64?" They are not encrypted. A Secret object is a ConfigMap whose values happen to be base64-encoded, with slightly more careful default handling — kubectl does not print the values by accident, and they can be mounted as files with tighter permissions. But anyone who can read the Secret object through the API, or read etcd directly, has the value with one base64 -d. Two things change that picture, and both are cluster-level configuration rather than a property of the object: encryption at rest, where the API server encrypts Secret values before writing them to etcd using an EncryptionConfiguration, and RBAC that treats get secrets as the privileged verb it actually is.

    Secrets, base64 and what encryption at rest really does is W3.23; the four ways a pod consumes them is W3.21, and why etcd is its own trust domain is W2.5.

    Docs

    man 1 sha256sum and man 1 base64 for the two simple tools. man 1 openssl-enc for symmetric encryption on the command line, including why -pbkdf2 is not optional when deriving a key from a passphrase. man 5 shadow and man 3 crypt for the password-hash format and its algorithm prefixes.

    B12.5

    Symmetric and asymmetric keys, and why TLS uses both

    Why it matters

    Every secure connection you have ever made used two kinds of key in the same session, for reasons that are practical rather than theoretical. Understanding why is what turns the TLS handshake from a mysterious ritual into an obvious sequence — and it is also what explains why a certificate contains a public key and never a private one.

    The concept

    Symmetric encryption uses one key for both directions: the same secret encrypts and decrypts. It is fast — modern CPUs have AES instructions built in — and it has one crippling problem, the key distribution problem: before you can talk to someone securely, you both need the same secret, and getting it to them is the very thing you cannot do yet.

    Asymmetric encryption uses a mathematically linked pair: a public key you may hand to anyone, and a private key you never disclose to anybody, ever. What one encrypts, only the other can decrypt. That solves distribution outright — publish the public half, and anyone can send you something only you can read, with no prior arrangement. The price is speed: the maths is orders of magnitude slower than symmetric encryption, and RSA can only encrypt a payload smaller than its key size, so encrypting a video stream with it is not merely slow, it is impossible without chopping the stream up.

    So real protocols use both, in the only sensible arrangement: an expensive asymmetric introduction to agree on a cheap symmetric key, then all the actual traffic under that symmetric key. That is the entire architecture of TLS. The certificate exchange and key agreement at the start of the connection exist to establish one temporary session key; from then on the connection is symmetric AES. When you later read a cipher suite like ECDHE-RSA-AES256-GCM-SHA384 in B12.12, you are reading exactly this split: ECDHE agrees the session key, RSA authenticates who you agreed it with, AES256-GCM is the symmetric cipher doing the work, SHA384 is the hash.

    One more thing to fix in your head now, because it decides whether the rest of the module makes sense: a keypair has two uses, and they run in opposite directions. Encrypt with the public key so only the private key can read it — that is confidentiality. Or transform with the private key so anyone with the public key can check it — that is a signature, and it is B12.6. Certificates are entirely about the second use.

    asymmetric handshake→agree one session key→symmetric AES for all traffic

    Expensive introduction, cheap conversation — the shape of every HTTPS connection.

    Lab
    1. Make a working directory for the rest of the module, then generate an RSA keypair. Note that the "private key" file contains both halves — the public one is derived from it. 
      mkdir -p ~/ca && cd ~/ca
openssl genrsa -out demo.key 2048
chmod 600 demo.key
openssl rsa -in demo.key -pubout -out demo.pub
ls -l demo.key demo.pub
      -rw------- 1 ubuntu ubuntu 1704 Jul 25 09:02 demo.key     ← mode 600: this half is the secret
-rw-rw-r-- 1 ubuntu ubuntu  451 Jul 25 09:02 demo.pub      ← this half is meant to be given away
    2. Look inside both. The public file is small and contains only the modulus and exponent; the private file contains those plus the factors that make decryption possible. 
      head -2 demo.pub
openssl rsa -in demo.key -noout -text | head -4
      -----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA5Kj...
Private-Key: (2048 bit, 2 primes)
modulus: 00:e4:a8:...                          ← the modulus is in BOTH files; the primes only here
    3. Use the pair for confidentiality: encrypt with the public key, decrypt with the private one. Anyone holding demo.pub can send you this; only you can open it. 
      echo 'meet at noon' > msg.txt
openssl pkeyutl -encrypt -pubin -inkey demo.pub -in msg.txt -out msg.enc
openssl pkeyutl -decrypt -inkey demo.key -in msg.enc
      meet at noon        ← round-tripped through the pair, with no shared secret arranged in advance
    4. Now hit the size limit that forces the hybrid design. RSA cannot encrypt more than roughly its key size, so a real payload is out of the question. 
      head -c 5000 /dev/urandom > big.bin
openssl pkeyutl -encrypt -pubin -inkey demo.pub -in big.bin -out big.enc
      Public Key operation error
40B7...:error:0200006E:rsa routines::data too large for key size     ← this is why TLS is hybrid
    5. Encrypt the same file symmetrically and time both. The gap is the practical argument, not an aesthetic one. 
      head -c 20M /dev/urandom > huge.bin
time openssl enc -aes-256-cbc -pbkdf2 -pass pass:k -in huge.bin -out huge.enc
      real    0m0.14s        ← 20 MB of AES in a seventh of a second; RSA cannot do this at any size
    6. Confirm the CPU is helping, which is why symmetric encryption is essentially free on modern hardware. 
      grep -o -m1 ' aes ' /proc/cpuinfo && echo 'AES-NI present'
rm -f big.bin big.enc huge.bin huge.enc msg.enc
       aes
AES-NI present         ← hardware AES instructions: the "cheap conversation" half is cheap
    Verify

    Explain in two sentences why TLS uses both key types, naming the specific problem each one solves — distribution for asymmetric, speed and payload size for symmetric. Then answer the question that catches people out: if you hand someone your public key, what can they do with it? (Encrypt something only you can read, and verify signatures you made. They cannot decrypt your traffic, sign as you, or derive the private half.) Check yourself against the file listing: the only file in ~/ca that ever needs mode 600 is the one ending .key.

    Gotchas

    The naming trips everybody at least once. A file called something.key is the private key and must never be copied anywhere casually; a .pub, .crt or .pem certificate contains only the public half and is safe to email, commit and serve over the internet. When you feel unsure which you are holding, openssl rsa -in FILE -noout -text | head -1 says Private-Key or errors — five seconds, and it has saved more than one person from pasting a private key into a ticket.

    The second is assuming key size is the only thing that matters. A 2048-bit RSA key and a 256-bit elliptic-curve key offer comparable strength, because the numbers measure different mathematics — EC keys are dramatically smaller and faster for equivalent security, which is why ed25519 is now the default for SSH and why Kubernetes components increasingly use ECDSA. Do not compare bit counts across algorithms.

    Every component of a cluster holds a keypair, and the split you just built is exactly how they are stored: /etc/kubernetes/pki/ holds .key files (private, mode 600, never leave the node) beside .crt files (public, handed to anyone who connects). The API server presents its public half to every client on every connection; the private half never crosses the network even once. There is one more place the asymmetric pair shows up in a form that surprises people: sa.key and sa.pub, the keypair the controller manager uses to sign ServiceAccount tokens and the API server uses to verify them — no certificate involved, just a raw keypair doing the second use of a pair.

    The layout of /etc/kubernetes/pki, including that odd sa.key/sa.pub couple, is W2.5; how those tokens are issued and rotated is W7.4.

    Docs

    man 1 openssl-genrsa and man 1 openssl-genpkey (the modern, algorithm-agnostic generator) for making keys; man 1 openssl-rsa for inspecting and converting them; man 1 openssl-pkeyutl for the raw encrypt/decrypt operations used above. man 1 openssl-ciphers decodes cipher-suite names like ECDHE-RSA-AES256-GCM-SHA384 piece by piece.

    B12.6

    Signatures: the keypair used backwards

    Why it matters

    A signature is the mechanism behind certificates, SSH logins, signed tokens and package verification — four things that look unrelated until you notice they are one operation. It is also the precise thing a certificate authority does for a living, so the next group of lessons is much easier once this is concrete rather than abstract.

    The concept

    Run the keypair in the other direction. Transform something with your private key, and anyone holding your public key can check that the transformation could only have come from the private half. That check yields two facts at once:

    • Origin — it was produced by whoever holds that private key.
    • Integrity — the data has not changed by a single bit since, because the signature is over the data's hash and any change gives a different hash.

    Mechanically, you do not sign the data itself — you hash it first (B12.4) and sign the hash. That is why signing a 10 GB file is as fast as signing a sentence, and it is why signature commands always name a hash algorithm: openssl dgst -sha256 -sign. The verifier repeats the hash over the data it received, undoes the signature with the public key, and compares. Equal means both facts hold; different means one of them does not, and the tool cannot tell you which.

    Now the essential limitation, which the whole of PKI exists to patch. A valid signature proves the data came from the holder of a specific private key. It says nothing about who that holder is. If an attacker generates their own keypair and signs a message, the signature verifies perfectly against their public key — the maths is not lying, it simply answers a narrower question than you wanted. Verification therefore only means something if you already had good reason to trust the public key you checked against. That "already trusted public key" problem is solved by a certificate authority: someone you trust signs a statement binding a public key to a name, and the trust flows from there.

    data→hash→sign with private key·verify with public key→origin + integrity

    Both facts come from one check; neither of them is "and this person is who they say they are".

    Lab
    1. Sign a file with the private key you already made. The output is opaque bytes, so keep it in its own file. 
      cd ~/ca
echo 'transfer 100 to alice' > order.txt
openssl dgst -sha256 -sign demo.key -out order.sig order.txt
ls -l order.sig
      -rw-rw-r-- 1 ubuntu ubuntu 256 Jul 25 09:14 order.sig      ← 256 bytes = 2048 bits, one RSA block
    2. Verify it with only the public half. This is the operation a recipient performs, and they never need your private key to do it. 
      openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verified OK       ← origin (that private key) and integrity (unchanged) in one word
    3. Change exactly one byte of the data and verify again. Nothing about the signature file changed — the mismatch is entirely in the hash. 
      sed -i 's/alice/bobbb/' order.txt
openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verification failure
40C7...:error:02000068:rsa routines::bad signature          ← integrity broken, caught immediately
    4. Restore the file and confirm verification comes back. The check is exact, not fuzzy: correct data means correct result, every time. 
      sed -i 's/bobbb/alice/' order.txt
openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verified OK
    5. Now demonstrate the limitation that motivates certificates. An impostor generates their own keypair, signs a forged order, and it verifies perfectly — against their public key. 
      openssl genrsa -out impostor.key 2048 2>/dev/null
openssl rsa -in impostor.key -pubout -out impostor.pub 2>/dev/null
echo 'transfer 9000 to mallory' > forged.txt
openssl dgst -sha256 -sign impostor.key -out forged.sig forged.txt
openssl dgst -sha256 -verify impostor.pub -signature forged.sig forged.txt
      Verified OK       ← the maths is fine. The question "whose key is impostor.pub?" is unanswered.
    6. Confirm the forged signature fails against the key you actually trust — which is the only reason step 5 is not a disaster. 
      openssl dgst -sha256 -verify demo.pub -signature forged.sig forged.txt
rm -f impostor.key impostor.pub forged.txt forged.sig
      Verification failure          ← trust was never in the signature; it was in which public key you held
    Verify

    State the two facts a valid signature establishes, and the one fact it does not. Then explain why signing hashes the data first — and what that buys beyond speed (a fixed-size input for a fixed-size operation, and the fact that any change anywhere in the data changes the thing that was signed). Finally, describe step 5 in one sentence to someone else: a signature that verifies against an untrusted public key proves only that somebody, somewhere, holds the matching private key.

    Gotchas

    "Signed" on its own is a meaningless assurance, and marketing uses it that way constantly. The useful question is always signed by a key you had a prior reason to trust? A signed container image, a signed release tarball and a signed token are each worth exactly as much as the answer to that follow-up. This is not pedantry: it is the entire attack that certificate authorities and pinned public keys exist to prevent.

    The second gotcha is the pair of near-identical commands. openssl dgst -sign takes the private key, -verify takes the public one, and passing the wrong file gives a confusing parse error rather than a clear "that is the wrong half". If -verify complains about reading the key, you have almost certainly handed it a private key file.

    Two signature-verification flows run continuously inside a cluster. The first is TLS: when kubectl connects, the API server proves it holds the private key matching the certificate it presented, and kubectl checks that certificate's signature against the cluster CA embedded in your kubeconfig — a signature check over a name binding, which is B12.8's subject. The second is ServiceAccount tokens, which are JWTs: a base64 header and payload (encoding, not encryption — you can read any token's claims with base64 -d) followed by a signature made with sa.key. The API server verifies it with sa.pub, and that verification is the pod's authentication. Both are this lesson's one operation, applied to different data.

    How a pod's token is issued, projected and rotated is W7.4; the CSR API — where you ask the cluster CA to sign a public key you generated — is W7.3.

    Docs

    man 1 openssl-dgst is the page for both halves of this lesson — search it for -sign, -verify and -signature. man 1 openssl-pkeyutl shows the lower-level -sign/-verify operations if you want to see the hash step separated out. man 1 sha256sum remains the plain-text way to see the hash that is actually being signed.

    B12.7

    SSH keys and the agent — the example already in your hands

    Why it matters

    You have been using public-key cryptography every time you log into a machine, and probably without connecting it to anything in the previous three lessons. Making that connection is worth doing deliberately, because SSH is the clearest small example of the whole pattern: a keypair, a signature challenge, a trusted list of public keys, and a cache that trades safety for convenience.

    The concept

    An SSH login with keys works like this. The server has your public key on a line in ~/.ssh/authorized_keys. When you connect, the server sends a challenge, and your client proves it holds the matching private key by signing that challenge (B12.6). The server verifies the signature against the public key on file. Your private key never crosses the network — not encrypted, not at all — which is the property that makes key login strictly better than passwords, where the secret itself is transmitted (inside the encrypted channel, but transmitted).

    Because the private key is a file, it is protected by exactly one thing on disk: its mode. ssh enforces this itself and will flatly refuse to use a key that other users can read — one of the few programs that fails closed on a permission problem rather than warning. A key can additionally be encrypted with a passphrase, which is symmetric encryption (B12.4) wrapped around the private key file: stealing the file then gets you nothing without the passphrase.

    That protection is also an annoyance — a passphrase typed on every connection is a passphrase people remove. ssh-agent is the compromise: a small background process that holds your decrypted private key in memory, so you type the passphrase once per session and every subsequent connection asks the agent to produce signatures on your behalf. The trade-off is worth naming because it recurs everywhere — every credential cache, every token in a pod, every kubeconfig on a laptop makes the same bargain. A decrypted secret is sitting in a running process's memory, reachable by anything that can reach that process: you, root, and any code running as you.

    server: challenge→client signs with private key→server verifies vs authorized_keys→session

    Nothing secret travels; only a signature does.

    Lab
    1. Generate a key with a passphrase, so the agent has something to hold. Ed25519 keys are small, fast, and now the sensible default. 
      cd ~/ca
ssh-keygen -t ed25519 -f ~/.ssh/demo_key -C 'b12 demo' -N 'sandbox-pass'
head -1 ~/.ssh/demo_key
      -----BEGIN OPENSSH PRIVATE KEY-----      ← the file is itself encrypted; the passphrase decrypts it
    2. Authorize it for your own account, so you can log into localhost and watch the exchange. The public half is what goes on the server. 
      cat ~/.ssh/demo_key.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ssh -i ~/.ssh/demo_key -o IdentitiesOnly=yes localhost hostname
      Enter passphrase for key '/home/ubuntu/.ssh/demo_key':
sandbox          ← logged in; the passphrase decrypted the local file, nothing more
    3. Now start an agent and load the key once. From here the passphrase is not asked again — the agent signs each challenge for you. 
      eval "$(ssh-agent -s)"
ssh-add ~/.ssh/demo_key        # passphrase: sandbox-pass
ssh-add -l
      Agent pid 4412
Identity added: /home/ubuntu/.ssh/demo_key (b12 demo)
256 SHA256:9k2Lp... b12 demo (ED25519)        ← the agent is holding it, decrypted, in memory
    4. Connect twice more and note what you are no longer typing. This is the convenience the trade-off buys. 
      ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost 'echo login-1'
ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost 'echo login-2'
      login-1
login-2          ← no prompt: the agent produced both signatures
    5. Look at the boundary the agent creates. It is a Unix socket (B9.17) owned by you, and anything that can reach that socket can sign as you without ever knowing the passphrase. 
      echo "$SSH_AUTH_SOCK"; ls -l "$SSH_AUTH_SOCK"
      /tmp/ssh-XXXX2kPq/agent.4411
srw------- 1 ubuntu ubuntu 0 Jul 25 09:31 /tmp/ssh-XXXX2kPq/agent.4411
                             ↑ mode 600 on a socket is the whole control (B12.1's boundary 2)
    6. Prove that ssh fails closed on permissions — one of the clearest examples of a tool refusing to proceed with a weakened control. 
      chmod 644 ~/.ssh/demo_key
ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost hostname 2>&1 | head -3
      @@@@@ WARNING: UNPROTECTED PRIVATE KEY FILE! @@@@@
Permissions 0644 for '/home/ubuntu/.ssh/demo_key' are too open.
This private key will be ignored.          ← refuses to use it at all
    7. Restore the mode and clean up the agent. The key files stay — B12.16 does not need them, but leaving a demo key authorized is untidy. 
      chmod 600 ~/.ssh/demo_key
ssh-add -D && ssh-agent -k >/dev/null
grep -v 'b12 demo' ~/.ssh/authorized_keys > /tmp/ak && mv /tmp/ak ~/.ssh/authorized_keys; echo cleaned
      All identities removed.
cleaned
    Verify

    Describe an SSH key login as a signature challenge, in one sentence, naming which half of the pair lives where. Then answer two questions about the agent: what does it hold, and what does someone gain by reaching its socket? (A decrypted private key; the ability to sign as you — to log in anywhere that key is authorized — without ever learning the passphrase, for as long as the agent runs.) If you can also say why ssh refuses a mode-644 key rather than warning, you have the lesson.

    Gotchas

    Agent forwarding (ssh -A) deserves a specific warning, because it is the same trade-off pushed one hop further. It exports your agent socket to the machine you log into, so that machine can sign with your key while you are connected — convenient for hopping through a bastion, and it means root on that intermediate machine can use your identity to reach everything you can reach, silently, for the length of the session. Prefer ProxyJump (ssh -J), which tunnels through the bastion without ever exposing the agent to it.

    The second is the passphrase's real scope. It protects the key file at rest and nothing else. Once the agent holds the key, the passphrase is irrelevant to anyone attacking the running system; and a key with no passphrase is simply a plaintext credential on disk, protected by mode 600 alone — which is precisely the situation of most automation credentials, including a kubeconfig.

    A kubeconfig is the same bargain in a different file format, and seeing that is the point of this lesson. ~/.kube/config typically contains client-certificate-data and client-key-data — a certificate and, crucially, a private key, base64-encoded and therefore in plain text (B12.4). It is your identity to the cluster, it has no passphrase, and it is protected by its file mode and nothing else. Copying it to a shared machine, pasting it into a chat, or baking it into an image is the exact equivalent of publishing a passphrase-less SSH private key. Treat it like one: mode 600, never in Git, and rotate it if it ever leaves your machine.

    What is actually inside a kubeconfig, field by field, is W7.2; the certificates kubeadm generates for each identity, and where their keys live, is W2.3.

    Docs

    man 1 ssh-keygen for key generation, passphrase changes (-p) and printing the public half from a private key (-y). man 1 ssh-agent and man 1 ssh-add for the cache and its socket; man 8 sshd, section AUTHORIZED_KEYS FILE FORMAT, for what a line in that file may contain — including the command= and from= restrictions worth knowing. man 5 ssh_config for IdentitiesOnly and ProxyJump.
