    B12 — Security fundamentals: trust, crypto, PKI

    Almost everything people call "a security feature" is one of two questions being answered: who are you? and are you allowed to do this? The machinery around those two questions — passwords, keys, signatures, certificates, permission files — looks enormous from outside and turns out to be small once you have built each piece yourself. That is what this module does. You will run your own certificate authority, issue certificates to yourself, make two programs prove their identities to each other, and then break that arrangement four different ways so that each error message becomes a specific accusation rather than a wall of noise.

    Kubernetes is an unusually good reason to learn this properly, because a cluster is held together by certificates end to end. Every component authenticates to the API server with one. Every kubeconfig is a certificate plus an address. Every "my kubectl suddenly stopped working" is, underneath, one of the four failures you will deliberately cause in the last lesson. People who have never issued a certificate by hand experience this as bad luck; people who have, read the error and know which file to look at.

    Four movements. Framing: the questions that make a security decision answerable — what are you protecting, from whom, and where does control change hands — plus the authentication/authorization split that decides where you go looking when something is refused. Crypto in plain terms: hashing, encoding and encryption told apart for good, the two key models, signatures, and SSH keys as the example already in your hands. PKI hands-on: a CA, a CSR, subject alternative names, chain verification, a real TLS server and mutual TLS — all with openssl, all on one machine. Handling secrets: how a secret leaks on a shared box even when nobody is malicious, and the two kernel layers that stand behind file permissions when everything else has failed.

    • Explain SSH key login as a signature challenge, and what ssh-agent trades away for convenience.
    • Create a certificate authority — a key plus a self-signed certificate — and say precisely what holding that key means.
    • Issue a certificate in the two proper steps: a key and a CSR from the subject, a signature from the CA.

    • Break that mTLS four ways and map every error string to one cause without guessing.

    Framing

    B12.1

    Threat modelling in one page: assets, actors, trust boundaries

    Why it matters

    "Is this secure?" is an unanswerable question, and answering it anyway is how people end up with elaborate controls protecting nothing. The answerable version has three parts bolted on: secure for what, against whom, and at which boundary. Threat modelling is just the discipline of writing those three down before you choose a control. It takes fifteen minutes, it needs no tools, and it is the difference between "we enabled TLS" and "we know what TLS did and did not fix here."

    The concept

    Three words carry the whole exercise, and each one is ordinary:

    • Assets — the things that would hurt to lose, leak or have altered. Be specific: not "the server" but "the private key in ~/.ssh/id_ed25519", "the database's contents", "the ability to run commands as root". A list of concrete nouns beats a paragraph of intent.
    • Actors — who might want them, described by their position rather than their motive. "An internet scanner with no account", "a logged-in user on this machine", "a process running as the same user", "someone holding the disk". The position is what determines which controls are even relevant.
    • Trust boundaries — the lines where control changes hands. Every time data or authority crosses from one party to another — user to kernel, one machine to another, your process to a library it loaded, host to container — that crossing is a boundary, and it is where controls belong. Nothing is a "security control" except at a boundary.

    The point of naming boundaries out loud is that once they are on paper, a lot of arguments end. Consider the container runtime socket from B9.18: /run/containerd/containerd.sock is root-owned because whoever can write to it can start a container with any mount and any privilege — that socket is a trust boundary. Draw it once and "just mount the runtime socket into the pod, it's easier" stops sounding like a convenience and starts sounding like what it is: handing the thing on the other side of the boundary everything the thing on this side has.

    A useful habit while modelling: for each control you already have, ask which actor it stops. A file mode of 600 stops another logged-in user. It does not stop root, it does not stop a process running as you, and it does nothing at all once the disk is out of the machine. That is not a criticism of file modes — it is what "against whom" means, and writing it down is how you notice the actor you had not covered.

    asset→who wants it→boundary it crosses→control at that boundary

    Controls chosen in any other order tend to protect the wrong crossing.

    Lab
    1. Pick one concrete asset and look at the only thing currently protecting it. If you have no key yet, make one — you will need it again in B12.7. 
      multipass shell sandbox
ls -l ~/.ssh/id_ed25519 2>/dev/null || ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
stat -c '%n  mode=%a  owner=%U:%G' ~/.ssh/id_ed25519
      /home/ubuntu/.ssh/id_ed25519  mode=600  owner=ubuntu:ubuntu     ← one file mode is the entire control
    2. Introduce a second actor — an ordinary logged-in user with no privileges — and test the boundary the file mode draws. This is the actor 600 exists to stop. 
      sudo adduser --disabled-password --gecos '' mallory
sudo -u mallory cat ~/.ssh/id_ed25519
      cat: /home/ubuntu/.ssh/id_ed25519: Permission denied     ← the control works against this actor
    3. Now test the actor it does not stop. Root does not consult the permission bits at all (B4.10), so anyone who can become root has already crossed this boundary. 
      sudo head -c 40 ~/.ssh/id_ed25519; echo
      -----BEGIN OPENSSH PRIVATE KEY-----      ← root reads it regardless of mode 600
    4. Write the model down. One page, three headings — the artefact is the point, because a model in your head cannot be checked by anyone else. 
      cat > ~/threat-model.md <<'EOF'
# Asset: SSH private key ~/.ssh/id_ed25519
## Actors
- other logged-in user on sandbox      (stopped by: mode 600)
- any process running AS ubuntu        (NOT stopped: same uid, e.g. a bad npm package)
- root / anyone who can sudo           (NOT stopped: root ignores modes)
- holder of the disk image or snapshot (NOT stopped: encrypt the key with a passphrase)
## Trust boundaries crossed
1. disk -> my process        (file permissions)
2. my process -> ssh-agent   (agent holds it decrypted in memory)
3. my machine -> remote host (only a SIGNATURE crosses; the key never does)
EOF
grep -c . ~/threat-model.md
      14        ← the model exists as a file; boundary 3 is the one B12.7 explains
    5. Sanity-check the model against reality: boundary 3 claims the private key never leaves the machine. Confirm what the server actually holds is the public half. 
      ssh-keygen -y -f ~/.ssh/id_ed25519 | cut -c1-40
      ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI       ← this half is what goes into authorized_keys
    Verify

    Without looking at your file, name the three headings and produce one entry under each for a different asset — say, the sudo ability on this VM. Then answer the question that makes a model useful: for each control you listed, which actor does it stop, and which actor walks straight past it? If every control on your page stops the same actor, you have found a real gap — that is defense in depth's absence, and it is the subject of the next lesson.

    Gotchas

    The most common failure is modelling the actor you find interesting rather than the actor you actually have. Elaborate defenses against a remote attacker are routine on machines where the real exposure is a hundred people with sudo and no audit trail. Position, not drama: list who genuinely has a foothold today, and cover those first.

    The second is treating a boundary as a control. Naming /run/containerd/containerd.sock as a trust boundary does not protect it; it tells you that whatever protects it — file mode, group membership, not mounting it into workloads — is load-bearing, and that changes to it are security changes even when the commit message says "convenience". A boundary is where you must decide, not the decision.

    Kubernetes has a small set of boundaries that carry nearly all of its security weight, and they are worth naming now because the rest of the advanced track keeps crossing them. The API server is the boundary between "anyone on the network" and "the cluster's state" — which is why every request through it is authenticated then authorized. The node is the boundary between the control plane and untrusted workloads, which is why a pod that can read the kubelet's credentials or the container runtime socket has effectively escaped. And etcd is the boundary behind everything: direct read access to it is equivalent to reading every Secret in the cluster, because that is literally where they are stored.

    The etcd trust domain and why it is treated as a separate one is W2.5; how a pod's identity reaches the API server at all is W7.4.

    Docs

    There is no man page for threat modelling — the useful searches are the artefacts. man 7 credentials for the identities an actor can hold on a Linux box, and man 2 access for the check that decides a boundary crossing at the filesystem. For the container-shaped boundaries, man 7 namespaces and man 7 capabilities are the two pages that define what "inside" and "outside" mean.

    B12.2

    Least privilege and defense in depth, as decisions you can check

    Why it matters

    These two phrases appear in every security document ever written, which has drained them of meaning. Both are actually testable questions about a specific program: what is the smallest set of permissions under which this still works? and if this one control fails, what is the next one? Asked about a real service, they produce a concrete list of changes — and on a systemd machine you can watch a score move as you make them.

    The concept

    Least privilege means a program holds only the authority it needs, for only as long as it needs it. The trap is that "needs" is usually assumed rather than measured. A web server needs to bind port 80; historically that required root, so web servers ran as root, so a bug in the request parser gave an attacker the whole machine. The privilege that mattered was one narrow thing — bind a port below 1024 — and root was simply the only way anyone knew to ask for it. Linux has had a better answer for years: capabilities (B4.10) split root into a keyring of individually-issued permits, and CAP_NET_BIND_SERVICE is exactly the one permit here.

    Defense in depth means assuming any single control will fail and asking what stands behind it. Not because you expect to be attacked in layers, but because controls fail in ordinary ways: a mode gets changed by a deployment script, a validation is skipped on one code path, a dependency is compromised. The question is never "is this control good enough", it is "what happens the day it isn't".

    Both become concrete on a service. Take a program that must serve on port 80 and read one config file, and walk it down the privilege ladder — running as root, then as an unprivileged user with the one capability it needs, then with the rest of the machine taken away from it. On systemd every rung is a line in a unit file (B11.4): User= drops the identity, AmbientCapabilities= grants the single permit, NoNewPrivileges= forbids regaining anything through a setuid binary (B4.9), ProtectSystem=strict makes the filesystem read-only for it, PrivateTmp= gives it a mount namespace of its own (B6.6). None of those is new machinery — they are B4's and B6's primitives with unit-file names.

    root, everything→own user + one capability→no new privileges→read-only fs, private /tmp

    Least privilege picks the rung; defense in depth is the reason you keep descending after it already works.

    Lab
    1. Write the naive version first — the one that works and gives away everything. It runs as root purely to bind a low port. 
      sudo tee /etc/systemd/system/web.service >/dev/null <<'EOF'
[Unit]
Description=Toy web server
[Service]
ExecStart=/usr/bin/python3 -m http.server 80 --directory /srv/toy
[Install]
WantedBy=multi-user.target
EOF
sudo mkdir -p /srv/toy && echo hi | sudo tee /srv/toy/index.html >/dev/null
sudo systemctl daemon-reload && sudo systemctl start web
curl -s localhost:80; ps -o user,args -C python3 --no-headers | head -1
      hi
root     /usr/bin/python3 -m http.server 80 --directory /srv/toy    ← full root, to bind one port
    2. Measure it before changing anything. systemd-analyze security scores a unit's exposure from 0 (locked down) to 10 (nothing between it and the machine) — a rare case of a security question with a number attached. 
      systemd-analyze security web.service | tail -3
      → Overall exposure level for web.service: 9.6 UNSAFE 😨      ← the naive unit
    3. Apply least privilege: give the service its own identity and exactly one piece of root's authority instead of all of it. 
      sudo useradd --system --no-create-home --shell /usr/sbin/nologin toyweb
sudo mkdir -p /etc/systemd/system/web.service.d
sudo tee /etc/systemd/system/web.service.d/10-drop.conf >/dev/null <<'EOF'
[Service]
User=toyweb
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
EOF
sudo systemctl daemon-reload && sudo systemctl restart web
curl -s localhost:80; ps -o user,args -C python3 --no-headers | head -1
      hi                                                       ← still works
toyweb   /usr/bin/python3 -m http.server 80 ...          ← not root any more
    4. Confirm the permit is real and narrow by reading the process's capability sets straight out of /proc (B4.12) rather than trusting the unit file. 
      pid=$(systemctl show -p MainPID --value web); grep -E 'CapEff|CapBnd' /proc/$pid/status
capsh --decode=$(awk '/CapEff/{print $2}' /proc/$pid/status)
      CapBnd: 0000000000000400
CapEff: 0000000000000400
0x0000000000000400=cap_net_bind_service      ← one permit on the keyring, not the master key
    5. Now add depth: layers that do nothing today and matter the day the program is compromised. Each line takes away something it never needed. 
      sudo tee -a /etc/systemd/system/web.service.d/10-drop.conf >/dev/null <<'EOF'
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ReadOnlyPaths=/srv/toy
EOF
sudo systemctl daemon-reload && sudo systemctl restart web
curl -s localhost:80; systemd-analyze security web.service | tail -1
      hi
→ Overall exposure level for web.service: 2.8 OK 🙂       ← same behaviour, far less reachable
    6. Prove one of the layers actually bites, rather than believing the score. The service can still serve its files and can no longer write anywhere on the system. 
      sudo -u toyweb touch /srv/toy/evidence 2>&1 | head -1
sudo systemctl stop web; sudo rm -rf /etc/systemd/system/web.service /etc/systemd/system/web.service.d
sudo systemctl daemon-reload; echo cleaned
      touch: cannot touch '/srv/toy/evidence': Permission denied
cleaned
    Verify

    State the least-privilege answer for the toy server in one sentence — which single capability it needs and why root was ever involved — and then name three layers you added that do nothing on a healthy day. Check your reasoning with the tool: systemd-analyze security web.service before and after should differ by several points, and the service should behave identically. If a lockdown line breaks the service, that is the useful outcome too; it tells you the program needed something you assumed it didn't.

    Gotchas

    AmbientCapabilities= without CapabilityBoundingSet= is half a job. The ambient set grants the permit; the bounding set is the ceiling on what the process could ever acquire, and leaving it at the default means a setuid binary or a File capability could still hand it more later. Set both, and add NoNewPrivileges=yes so the setuid route is closed outright.

    ProtectSystem=strict makes the entire filesystem read-only for the service, which is exactly what you want and will absolutely break a program that writes a pid file, a cache or a log to disk. The fix is not to weaken it back to full but to name the one path it needs with ReadWritePaths= or StateDirectory= — which is least privilege doing its job by forcing you to enumerate what the program actually writes.

    Finally: a low exposure score is not safety. systemd-analyze security knows about sandboxing options and nothing about your application's bugs, its credentials, or what it is allowed to reach on the network. It is a checklist that happens to have a number, useful for comparing a unit against itself before and after — not a verdict.

    Every line you just wrote has a direct counterpart in a pod's securityContext, because it is the same kernel machinery reached through a different configuration language. User= is runAsUser and runAsNonRoot. AmbientCapabilities=/CapabilityBoundingSet= are capabilities.add and capabilities.drop — and drop: ["ALL"] plus one add is exactly the keyring argument above. NoNewPrivileges= is allowPrivilegeEscalation: false. ProtectSystem=strict is readOnlyRootFilesystem: true, with ReadWritePaths= becoming an emptyDir mounted where the app writes. Kubernetes bundles these into named tiers — the Pod Security Standards privileged, baseline and restricted — and the restricted tier is essentially this lesson's final unit expressed as policy. (Those fields are a CKS topic rather than a CKA one, so the advanced track does not drill them; the machinery is the same regardless of which exam asks about it.)

    Least privilege in its CKA-relevant form is RBAC: the smallest Role that still works, bound as narrowly as possible — W7.6. What actually runs privileged on a node, and why the kubelet and the static pods are in a different position from your workloads, is W1.2.

    Docs

    man 5 systemd.exec is the page for every sandboxing option used here — search it for ProtectSystem, NoNewPrivileges, AmbientCapabilities. man 1 systemd-analyze documents the security verb and how the exposure score is assembled. man 7 capabilities for the permit list and the ambient/bounding set rules, and man 1 capsh for decoding the hex you read out of /proc.

    B12.3

    Authentication vs authorization: two questions, two files

    Why it matters

    When something is refused, there are exactly two possibilities: the system did not believe you are who you claim, or it believed you completely and decided you may not do that. They are fixed in different places by different people, and confusing them is the single most expensive triage mistake in this whole subject — it is why people regenerate certificates for hours when the answer was one line of policy, and vice versa.

    The concept

    Authentication (often abbreviated authn) answers who are you? It ends in an identity or in nothing at all. The evidence can be something you know (a password), something you hold (a private key, a certificate) or something a trusted third party asserts (a signed token). Its failure mode is total: the system has no idea who is asking.

    Authorization (authz) answers may this identity do this particular thing? It starts from an established identity and consults a policy — a file, a table, a set of rules — to reach yes or no. Its failure mode is specific: the system knows exactly who you are and is declining this action.

    The keycard analogy holds all the way through, so use it: authentication is the guard confirming the photo on your ID is you; authorization is whether your card opens that door. Two different systems, two different people to complain to, and — importantly — an authorization failure is proof that authentication succeeded. If you are being told "you may not", the system already knows who you are, so nothing about your credentials needs fixing.

    sudo is the local example, and it separates the two cleanly enough to demonstrate. Your password authenticates you to sudo; /etc/sudoers then authorizes what that identity may run. You can watch the failures happen in order: get the password wrong and you never reach the policy; get it right without a sudoers entry and you are told, in different words, that you are recognised and refused.

    request→authn: who are you?→identity→authz: may you?→allow / deny

    The identity in the middle is the handoff — everything left of it is credentials, everything right of it is policy.

    Lab
    1. Give the mallory user from B12.1 a password so she can attempt to authenticate at all. 
      echo 'mallory:practice-only' | sudo chpasswd

      sudo id             # type the CORRECT password: practice-only

    4. Fix it in the right place. The credential was never the problem, so the change goes in the policy — group membership, which /etc/sudoers grants to. 
      exit                                     # back to the ubuntu user

    Verify

    Explain out loud, without notes, why "you are not in the sudoers file" is proof that your password was correct. Then do the translation you will use constantly later: given a refusal, say which of the two questions failed and which file you would open. A rejected password, an expired certificate and an unknown signing authority are all the first question; a recognised user without a matching rule is the second. If you cannot tell which one an error is, the error message itself is the thing to read more carefully — the two are almost always worded differently on purpose.

    Gotchas

    Some systems deliberately blur the line to avoid leaking information. A login form that says "invalid username or password" is refusing to tell you which of the two failed, because saying "no such user" would let an attacker enumerate accounts. That is a reasonable design and an annoying one to debug: when a system won't tell you which question failed, the server-side log usually will, and that is where to look rather than at the message you were shown.

    The other trap is fixing the wrong side because the wrong side is easier to change. Regenerating a credential is fast and satisfying; editing a policy needs someone's approval. That asymmetry is exactly why people burn afternoons reissuing certificates for what was, from the first error message, a policy decision. Read the refusal before touching anything.

    This split is the shape of the API server's request pipeline: every request goes through authentication, then authorization, then admission, in that order, and each stage can refuse for its own reasons. The two HTTP status codes tell you which stage spoke. 401 Unauthorized — badly named, it means unauthenticated — says your certificate, token or kubeconfig was not accepted at all, so the fix is in your credentials or the cluster's CA trust. 403 Forbidden says the API server knows precisely who you are, printed your username and groups in the message, and RBAC found no rule permitting the verb on that resource; the fix is a Role and a RoleBinding, and your credentials are fine. Learning to read those two numbers correctly saves more time than any other single habit in cluster troubleshooting.

    The full authn → authz → admission pipeline in order is W1.4; the three credential types the cluster accepts for the first question are W7.1, the authorizer chain that answers the second is W7.5, and kubectl auth can-i — the direct equivalent of sudo -l — is W7.8.

    Docs

    man 8 sudo for the two stages in one program and the -l flag that prints the policy; man 5 sudoers for the rule syntax and the %group form used above. man 8 pam and man 5 pam.conf if you want to see where Linux authentication is actually implemented — PAM is the layer that sudo, login and sshd all delegate the first question to.

    Crypto in plain terms

    B12.4

    Hashing, encoding, encryption — three things that are not each other

    Why it matters

    These three get muddled constantly, and one particular muddle causes real damage: people see base64 and think "encrypted". It is not. It is not even slightly. Getting this straight takes ten minutes with three commands, and it inoculates you against the single most common beginner misreading in the entire Kubernetes ecosystem — that a Secret's base64 value is protected.

    The concept

    Three operations, distinguished by one question: who can reverse it, and with what?

    • Hashing — one way, no key, and nobody can reverse it. A hash function turns any input into a fixed-size fingerprint (sha256sum gives 64 hex characters whether the input is one byte or a gigabyte). Change one bit of the input and roughly half the output bits change, which is what makes it a useful fingerprint. Use it to answer "is this the same as that?" without holding the original: password checking, file integrity, and — as you will see later — the thing that actually gets signed in a signature.
    • Encoding — reversible by anyone, no key involved. Base64 rewrites arbitrary bytes using 64 safe characters so they survive a place that only accepts text: a JSON field, an email body, a YAML file. It is a transport convenience with the security value of writing something backwards. base64 -d undoes it, and there is nothing to know or possess in order to run that command.
    • Encryption — reversible only with a key. Without the key, the output is meaningless; with it, the original comes back exactly. This is the only one of the three that protects a secret's contents, and it always raises the question the other two never do: who has the key, and where is it kept?

    The tell for encoding is that the transformation is fully specified in a public document and needs no secret input. If you can undo it on any machine in the world with a command that takes no key, it was encoding. There is a related third-party habit worth naming: hashes are often stored alongside a random salt, so that two users with the same password do not get the same fingerprint and a precomputed table of common passwords stops being useful. That is why /etc/shadow entries contain a $6$ prefix, a salt and then the hash.

    hash: one way, no key·encode: reversible by anyone·encrypt: reversible with a key

    Only the right-hand one protects anything; the middle one is the one people mistake for it.

    Lab
    1. Run all three on the same string and put the outputs next to each other. Start with hashing — note the fixed length regardless of input. 
      echo -n 'hunter2' | sha256sum
echo -n 'hunter3' | sha256sum
      f52fbd32b2b3b86ff88ef6c490628285f482af15ddcb29541f94bcf526a3f6c7  -
bd50f2c...totally different...9a1c  -        ← one character changed, the whole fingerprint did
    2. Now encode the same string, and immediately undo it. No key was involved in either direction — this is the whole point. 
      echo -n 'hunter2' | base64
echo -n 'aHVudGVyMg==' | base64 -d; echo
      aHVudGVyMg==
hunter2          ← recovered by anyone, anywhere, with no secret at all
    3. Encrypt it properly and see what a keyed transformation looks like. The output is bytes, so it is base64-armoured for display — both operations in one line, which is exactly why people confuse them. 
      echo -n 'hunter2' | openssl enc -aes-256-cbc -pbkdf2 -pass pass:mykey -a
echo 'U2FsdGVkX1+...' | openssl enc -d -aes-256-cbc -pbkdf2 -pass pass:mykey -a
      U2FsdGVkX1+3Qm0Zt7YbVw==8k2Lp9xNc1dRfGh4      ← ciphertext (armoured with base64 for display)
hunter2                                        ← only comes back with -pass pass:mykey
    4. Prove the key is load-bearing: same ciphertext, wrong key, no plaintext. This is the difference between encoding and encryption in one command. 
      echo -n 'hunter2' | openssl enc -aes-256-cbc -pbkdf2 -pass pass:mykey -a > /tmp/ct
openssl enc -d -aes-256-cbc -pbkdf2 -pass pass:WRONG -a -in /tmp/ct
      bad decrypt
40E7...:error:1C800064:Provider routines::bad decrypt        ← no key, no plaintext
    5. Try to reverse a hash the same way and confirm there is no command for it. What people call "cracking" is guessing inputs and comparing fingerprints — which is why a slow, salted password hash matters. 
      sudo grep '^ubuntu:' /etc/shadow | cut -d: -f2 | cut -c1-30
      $6$Xk2p9QmZ$hT4vN...       ← $6$ = SHA-512-crypt, then the salt, then the hash. No key, no reverse.
    6. Do the Kubernetes experiment early, because it is the reason this lesson exists. A Secret's value is stored exactly like this — one command from plaintext. 
      printf 'apiVersion: v1\nkind: Secret\ndata:\n  password: %s\n' "$(echo -n 'hunter2' | base64)" | tee /tmp/secret.yaml
grep password: /tmp/secret.yaml | awk '{print $2}' | base64 -d; echo
        password: aHVudGVyMg==
hunter2          ← that is the entire "protection" a Secret's encoding provides
    Verify

    Answer three questions cold. Which of the three can you undo with no secret whatsoever, and why does that operation exist at all? (Encoding — so arbitrary bytes survive a text-only field.) Why can a password file store hashes safely but never store encrypted passwords comfortably? (A hash needs no key to verify against, so there is no key to protect or leak; an encrypted password requires the key to be present on the machine doing the check, which just moves the secret.) And what does a $6$ prefix in /etc/shadow tell you? (The hash algorithm, followed by a per-user salt, so identical passwords do not produce identical hashes.)

    Gotchas

    The base64-is-security misreading is so common that it deserves stating in its strongest form: if a value is base64 in a config file, a Git repository or a YAML manifest, treat it as if it were written in plain text, because it is. The encoding stops nobody, and it has the unfortunate side effect of looking like protection to a casual reader, which is worse than no protection at all — plaintext at least looks alarming.

    The second trap is reaching for a fast hash where a slow one is required. sha256sum is designed to be fast, which is a virtue for file integrity and a liability for passwords, where speed is exactly what an attacker guessing billions of candidates wants. Password storage uses deliberately slow, salted functions (bcrypt, scrypt, argon2, or SHA-512-crypt with many rounds as in /etc/shadow). Same word, "hash"; entirely different design goal.

    This is the whole answer to "why are Kubernetes Secrets only base64?" They are not encrypted. A Secret object is a ConfigMap whose values happen to be base64-encoded, with slightly more careful default handling — kubectl does not print the values by accident, and they can be mounted as files with tighter permissions. But anyone who can read the Secret object through the API, or read etcd directly, has the value with one base64 -d. Two things change that picture, and both are cluster-level configuration rather than a property of the object: encryption at rest, where the API server encrypts Secret values before writing them to etcd using an EncryptionConfiguration, and RBAC that treats get secrets as the privileged verb it actually is.

    Secrets, base64 and what encryption at rest really does is W3.23; the four ways a pod consumes them is W3.21, and why etcd is its own trust domain is W2.5.

    man 1 sha256sum and man 1 base64 for the two simple tools. man 1 openssl-enc for symmetric encryption on the command line, including why -pbkdf2 is not optional when deriving a key from a passphrase. man 5 shadow and man 3 crypt for the password-hash format and its algorithm prefixes.

    B12.5

    Symmetric and asymmetric keys, and why TLS uses both

    Why it matters

    Every secure connection you have ever made used two kinds of key in the same session, for reasons that are practical rather than theoretical. Understanding why is what turns the TLS handshake from a mysterious ritual into an obvious sequence — and it is also what explains why a certificate contains a public key and never a private one.

    The concept

    Symmetric encryption uses one key for both directions: the same secret encrypts and decrypts. It is fast — modern CPUs have AES instructions built in — and it has one crippling problem, the key distribution problem: before you can talk to someone securely, you both need the same secret, and getting it to them is the very thing you cannot do yet.

    Asymmetric encryption uses a mathematically linked pair: a public key you may hand to anyone, and a private key you never disclose to anybody, ever. What one encrypts, only the other can decrypt. That solves distribution outright — publish the public half, and anyone can send you something only you can read, with no prior arrangement. The price is speed: the maths is orders of magnitude slower than symmetric encryption, and RSA can only encrypt a payload smaller than its key size, so encrypting a video stream with it is not merely slow, it is impossible without chopping the stream up.

    So real protocols use both, in the only sensible arrangement: an expensive asymmetric introduction to agree on a cheap symmetric key, then all the actual traffic under that symmetric key. That is the entire architecture of TLS. The certificate exchange and key agreement at the start of the connection exist to establish one temporary session key; from then on the connection is symmetric AES. When you later read a cipher suite like ECDHE-RSA-AES256-GCM-SHA384 in B12.12, you are reading exactly this split: ECDHE agrees the session key, RSA authenticates who you agreed it with, AES256-GCM is the symmetric cipher doing the work, SHA384 is the hash.

    One more thing to fix in your head now, because it decides whether the rest of the module makes sense: a keypair has two uses, and they run in opposite directions. Encrypt with the public key so only the private key can read it — that is confidentiality. Or transform with the private key so anyone with the public key can check it — that is a signature, and it is B12.6. Certificates are entirely about the second use.

    asymmetric handshake→agree one session key→symmetric AES for all traffic

    Expensive introduction, cheap conversation — the shape of every HTTPS connection.

    Lab
    1. Make a working directory for the rest of the module, then generate an RSA keypair. Note that the "private key" file contains both halves — the public one is derived from it. 
      mkdir -p ~/ca && cd ~/ca
openssl genrsa -out demo.key 2048
chmod 600 demo.key
openssl rsa -in demo.key -pubout -out demo.pub
ls -l demo.key demo.pub
      -rw------- 1 ubuntu ubuntu 1704 Jul 25 09:02 demo.key     ← mode 600: this half is the secret
-rw-rw-r-- 1 ubuntu ubuntu  451 Jul 25 09:02 demo.pub      ← this half is meant to be given away
    2. Look inside both. The public file is small and contains only the modulus and exponent; the private file contains those plus the factors that make decryption possible. 
      head -2 demo.pub
openssl rsa -in demo.key -noout -text | head -4
      -----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA5Kj...
Private-Key: (2048 bit, 2 primes)
modulus: 00:e4:a8:...                          ← the modulus is in BOTH files; the primes only here
    3. Use the pair for confidentiality: encrypt with the public key, decrypt with the private one. Anyone holding demo.pub can send you this; only you can open it. 
      echo 'meet at noon' > msg.txt
openssl pkeyutl -encrypt -pubin -inkey demo.pub -in msg.txt -out msg.enc
openssl pkeyutl -decrypt -inkey demo.key -in msg.enc
      meet at noon        ← round-tripped through the pair, with no shared secret arranged in advance
    4. Now hit the size limit that forces the hybrid design. RSA cannot encrypt more than roughly its key size, so a real payload is out of the question. 
      head -c 5000 /dev/urandom > big.bin
openssl pkeyutl -encrypt -pubin -inkey demo.pub -in big.bin -out big.enc
      Public Key operation error
40B7...:error:0200006E:rsa routines::data too large for key size     ← this is why TLS is hybrid
    5. Encrypt the same file symmetrically and time both. The gap is the practical argument, not an aesthetic one. 
      head -c 20M /dev/urandom > huge.bin
time openssl enc -aes-256-cbc -pbkdf2 -pass pass:k -in huge.bin -out huge.enc
      real    0m0.14s        ← 20 MB of AES in a seventh of a second; RSA cannot do this at any size
    6. Confirm the CPU is helping, which is why symmetric encryption is essentially free on modern hardware. 
      grep -o -m1 ' aes ' /proc/cpuinfo && echo 'AES-NI present'
rm -f big.bin big.enc huge.bin huge.enc msg.enc
       aes
AES-NI present         ← hardware AES instructions: the "cheap conversation" half is cheap
    Verify

    Explain in two sentences why TLS uses both key types, naming the specific problem each one solves — distribution for asymmetric, speed and payload size for symmetric. Then answer the question that catches people out: if you hand someone your public key, what can they do with it? (Encrypt something only you can read, and verify signatures you made. They cannot decrypt your traffic, sign as you, or derive the private half.) Check yourself against the file listing: the only file in ~/ca that ever needs mode 600 is the one ending .key.

    Gotchas

    The naming trips everybody at least once. A file called something.key is the private key and must never be copied anywhere casually; a .pub, .crt or .pem certificate contains only the public half and is safe to email, commit and serve over the internet. When you feel unsure which you are holding, openssl rsa -in FILE -noout -text | head -1 says Private-Key or errors — five seconds, and it has saved more than one person from pasting a private key into a ticket.

    The second is assuming key size is the only thing that matters. A 2048-bit RSA key and a 256-bit elliptic-curve key offer comparable strength, because the numbers measure different mathematics — EC keys are dramatically smaller and faster for equivalent security, which is why ed25519 is now the default for SSH and why Kubernetes components increasingly use ECDSA. Do not compare bit counts across algorithms.

    Every component of a cluster holds a keypair, and the split you just built is exactly how they are stored: /etc/kubernetes/pki/ holds .key files (private, mode 600, never leave the node) beside .crt files (public, handed to anyone who connects). The API server presents its public half to every client on every connection; the private half never crosses the network even once. There is one more place the asymmetric pair shows up in a form that surprises people: sa.key and sa.pub, the keypair the controller manager uses to sign ServiceAccount tokens and the API server uses to verify them — no certificate involved, just a raw keypair doing the second use of a pair.

    The layout of /etc/kubernetes/pki, including that odd sa.key/sa.pub couple, is W2.5; how those tokens are issued and rotated is W7.4.

    man 1 openssl-genrsa and man 1 openssl-genpkey (the modern, algorithm-agnostic generator) for making keys; man 1 openssl-rsa for inspecting and converting them; man 1 openssl-pkeyutl for the raw encrypt/decrypt operations used above. man 1 openssl-ciphers decodes cipher-suite names like ECDHE-RSA-AES256-GCM-SHA384 piece by piece.

    B12.6

    Signatures: the keypair used backwards

    Why it matters

    A signature is the mechanism behind certificates, SSH logins, signed tokens and package verification — four things that look unrelated until you notice they are one operation. It is also the precise thing a certificate authority does for a living, so the next group of lessons is much easier once this is concrete rather than abstract.

    The concept

    Run the keypair in the other direction. Transform something with your private key, and anyone holding your public key can check that the transformation could only have come from the private half. That check yields two facts at once:

    • Origin — it was produced by whoever holds that private key.
    • Integrity — the data has not changed by a single bit since, because the signature is over the data's hash and any change gives a different hash.

    Mechanically, you do not sign the data itself — you hash it first (B12.4) and sign the hash. That is why signing a 10 GB file is as fast as signing a sentence, and it is why signature commands always name a hash algorithm: openssl dgst -sha256 -sign. The verifier repeats the hash over the data it received, undoes the signature with the public key, and compares. Equal means both facts hold; different means one of them does not, and the tool cannot tell you which.

    Now the essential limitation, which the whole of PKI exists to patch. A valid signature proves the data came from the holder of a specific private key. It says nothing about who that holder is. If an attacker generates their own keypair and signs a message, the signature verifies perfectly against their public key — the maths is not lying, it simply answers a narrower question than you wanted. Verification therefore only means something if you already had good reason to trust the public key you checked against. That "already trusted public key" problem is solved by a certificate authority: someone you trust signs a statement binding a public key to a name, and the trust flows from there.

    data→hash→sign with private key·verify with public key→origin + integrity

    Both facts come from one check; neither of them is "and this person is who they say they are".

    Lab
    1. Sign a file with the private key you already made. The output is opaque bytes, so keep it in its own file. 
      cd ~/ca
echo 'transfer 100 to alice' > order.txt
openssl dgst -sha256 -sign demo.key -out order.sig order.txt
ls -l order.sig
      -rw-rw-r-- 1 ubuntu ubuntu 256 Jul 25 09:14 order.sig      ← 256 bytes = 2048 bits, one RSA block
    2. Verify it with only the public half. This is the operation a recipient performs, and they never need your private key to do it. 
      openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verified OK       ← origin (that private key) and integrity (unchanged) in one word
    3. Change exactly one byte of the data and verify again. Nothing about the signature file changed — the mismatch is entirely in the hash. 
      sed -i 's/alice/bobbb/' order.txt
openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verification failure
40C7...:error:02000068:rsa routines::bad signature          ← integrity broken, caught immediately
    4. Restore the file and confirm verification comes back. The check is exact, not fuzzy: correct data means correct result, every time. 
      sed -i 's/bobbb/alice/' order.txt
openssl dgst -sha256 -verify demo.pub -signature order.sig order.txt
      Verified OK
    5. Now demonstrate the limitation that motivates certificates. An impostor generates their own keypair, signs a forged order, and it verifies perfectly — against their public key. 
      openssl genrsa -out impostor.key 2048 2>/dev/null
openssl rsa -in impostor.key -pubout -out impostor.pub 2>/dev/null
echo 'transfer 9000 to mallory' > forged.txt
openssl dgst -sha256 -sign impostor.key -out forged.sig forged.txt
openssl dgst -sha256 -verify impostor.pub -signature forged.sig forged.txt
      Verified OK       ← the maths is fine. The question "whose key is impostor.pub?" is unanswered.
    6. Confirm the forged signature fails against the key you actually trust — which is the only reason step 5 is not a disaster. 
      openssl dgst -sha256 -verify demo.pub -signature forged.sig forged.txt
rm -f impostor.key impostor.pub forged.txt forged.sig
      Verification failure          ← trust was never in the signature; it was in which public key you held
    Verify

    State the two facts a valid signature establishes, and the one fact it does not. Then explain why signing hashes the data first — and what that buys beyond speed (a fixed-size input for a fixed-size operation, and the fact that any change anywhere in the data changes the thing that was signed). Finally, describe step 5 in one sentence to someone else: a signature that verifies against an untrusted public key proves only that somebody, somewhere, holds the matching private key.

    Gotchas

    "Signed" on its own is a meaningless assurance, and marketing uses it that way constantly. The useful question is always signed by a key you had a prior reason to trust? A signed container image, a signed release tarball and a signed token are each worth exactly as much as the answer to that follow-up. This is not pedantry: it is the entire attack that certificate authorities and pinned public keys exist to prevent.

    The second gotcha is the pair of near-identical commands. openssl dgst -sign takes the private key, -verify takes the public one, and passing the wrong file gives a confusing parse error rather than a clear "that is the wrong half". If -verify complains about reading the key, you have almost certainly handed it a private key file.

    Two signature-verification flows run continuously inside a cluster. The first is TLS: when kubectl connects, the API server proves it holds the private key matching the certificate it presented, and kubectl checks that certificate's signature against the cluster CA embedded in your kubeconfig — a signature check over a name binding, which is B12.8's subject. The second is ServiceAccount tokens, which are JWTs: a base64 header and payload (encoding, not encryption — you can read any token's claims with base64 -d) followed by a signature made with sa.key. The API server verifies it with sa.pub, and that verification is the pod's authentication. Both are this lesson's one operation, applied to different data.

    How a pod's token is issued, projected and rotated is W7.4; the CSR API — where you ask the cluster CA to sign a public key you generated — is W7.3.

    Docs

    man 1 openssl-dgst is the page for both halves of this lesson — search it for -sign, -verify and -signature. man 1 openssl-pkeyutl shows the lower-level -sign/-verify operations if you want to see the hash step separated out. man 1 sha256sum remains the plain-text way to see the hash that is actually being signed.

    B12.7

    SSH keys and the agent — the example already in your hands

    Why it matters

    You have been using public-key cryptography every time you log into a machine, and probably without connecting it to anything in the previous three lessons. Making that connection is worth doing deliberately, because SSH is the clearest small example of the whole pattern: a keypair, a signature challenge, a trusted list of public keys, and a cache that trades safety for convenience.

    The concept

    An SSH login with keys works like this. The server has your public key on a line in ~/.ssh/authorized_keys. When you connect, the server sends a challenge, and your client proves it holds the matching private key by signing that challenge (B12.6). The server verifies the signature against the public key on file. Your private key never crosses the network — not encrypted, not at all — which is the property that makes key login strictly better than passwords, where the secret itself is transmitted (inside the encrypted channel, but transmitted).

    Because the private key is a file, it is protected by exactly one thing on disk: its mode. ssh enforces this itself and will flatly refuse to use a key that other users can read — one of the few programs that fails closed on a permission problem rather than warning. A key can additionally be encrypted with a passphrase, which is symmetric encryption (B12.4) wrapped around the private key file: stealing the file then gets you nothing without the passphrase.

    That protection is also an annoyance — a passphrase typed on every connection is a passphrase people remove. ssh-agent is the compromise: a small background process that holds your decrypted private key in memory, so you type the passphrase once per session and every subsequent connection asks the agent to produce signatures on your behalf. The trade-off is worth naming because it recurs everywhere — every credential cache, every token in a pod, every kubeconfig on a laptop makes the same bargain. A decrypted secret is sitting in a running process's memory, reachable by anything that can reach that process: you, root, and any code running as you.

    server: challenge→client signs with private key→server verifies vs authorized_keys→session

    Nothing secret travels; only a signature does.

    Lab
    1. Generate a key with a passphrase, so the agent has something to hold. Ed25519 keys are small, fast, and now the sensible default. 
      cd ~/ca
ssh-keygen -t ed25519 -f ~/.ssh/demo_key -C 'b12 demo' -N 'sandbox-pass'
head -1 ~/.ssh/demo_key
      -----BEGIN OPENSSH PRIVATE KEY-----      ← the file is itself encrypted; the passphrase decrypts it
    2. Authorize it for your own account, so you can log into localhost and watch the exchange. The public half is what goes on the server. 
      cat ~/.ssh/demo_key.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
ssh -i ~/.ssh/demo_key -o IdentitiesOnly=yes localhost hostname
      Enter passphrase for key '/home/ubuntu/.ssh/demo_key':
sandbox          ← logged in; the passphrase decrypted the local file, nothing more
    3. Now start an agent and load the key once. From here the passphrase is not asked again — the agent signs each challenge for you. 
      eval "$(ssh-agent -s)"
ssh-add ~/.ssh/demo_key        # passphrase: sandbox-pass
ssh-add -l
      Agent pid 4412
Identity added: /home/ubuntu/.ssh/demo_key (b12 demo)
256 SHA256:9k2Lp... b12 demo (ED25519)        ← the agent is holding it, decrypted, in memory
    4. Connect twice more and note what you are no longer typing. This is the convenience the trade-off buys. 
      ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost 'echo login-1'
ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost 'echo login-2'
      login-1
login-2          ← no prompt: the agent produced both signatures
    5. Look at the boundary the agent creates. It is a Unix socket (B9.17) owned by you, and anything that can reach that socket can sign as you without ever knowing the passphrase. 
      echo "$SSH_AUTH_SOCK"; ls -l "$SSH_AUTH_SOCK"
      /tmp/ssh-XXXX2kPq/agent.4411
srw------- 1 ubuntu ubuntu 0 Jul 25 09:31 /tmp/ssh-XXXX2kPq/agent.4411
                             ↑ mode 600 on a socket is the whole control (B12.1's boundary 2)
    6. Prove that ssh fails closed on permissions — one of the clearest examples of a tool refusing to proceed with a weakened control. 
      chmod 644 ~/.ssh/demo_key
ssh -o IdentitiesOnly=yes -i ~/.ssh/demo_key localhost hostname 2>&1 | head -3
      @@@@@ WARNING: UNPROTECTED PRIVATE KEY FILE! @@@@@
Permissions 0644 for '/home/ubuntu/.ssh/demo_key' are too open.
This private key will be ignored.          ← refuses to use it at all
    7. Restore the mode and clean up the agent. The key files stay — B12.16 does not need them, but leaving a demo key authorized is untidy. 
      chmod 600 ~/.ssh/demo_key
ssh-add -D && ssh-agent -k >/dev/null
grep -v 'b12 demo' ~/.ssh/authorized_keys > /tmp/ak && mv /tmp/ak ~/.ssh/authorized_keys; echo cleaned
      All identities removed.
cleaned
    Verify

    Describe an SSH key login as a signature challenge, in one sentence, naming which half of the pair lives where. Then answer two questions about the agent: what does it hold, and what does someone gain by reaching its socket? (A decrypted private key; the ability to sign as you — to log in anywhere that key is authorized — without ever learning the passphrase, for as long as the agent runs.) If you can also say why ssh refuses a mode-644 key rather than warning, you have the lesson.

    Gotchas

    Agent forwarding (ssh -A) deserves a specific warning, because it is the same trade-off pushed one hop further. It exports your agent socket to the machine you log into, so that machine can sign with your key while you are connected — convenient for hopping through a bastion, and it means root on that intermediate machine can use your identity to reach everything you can reach, silently, for the length of the session. Prefer ProxyJump (ssh -J), which tunnels through the bastion without ever exposing the agent to it.

    The second is the passphrase's real scope. It protects the key file at rest and nothing else. Once the agent holds the key, the passphrase is irrelevant to anyone attacking the running system; and a key with no passphrase is simply a plaintext credential on disk, protected by mode 600 alone — which is precisely the situation of most automation credentials, including a kubeconfig.

    A kubeconfig is the same bargain in a different file format, and seeing that is the point of this lesson. ~/.kube/config typically contains client-certificate-data and client-key-data — a certificate and, crucially, a private key, base64-encoded and therefore in plain text (B12.4). It is your identity to the cluster, it has no passphrase, and it is protected by its file mode and nothing else. Copying it to a shared machine, pasting it into a chat, or baking it into an image is the exact equivalent of publishing a passphrase-less SSH private key. Treat it like one: mode 600, never in Git, and rotate it if it ever leaves your machine.

    What is actually inside a kubeconfig, field by field, is W7.2; the certificates kubeadm generates for each identity, and where their keys live, is W2.3.

    B12.8

    Become a certificate authority

    Why it matters

    B12.6 ended on a gap: a signature proves someone holds a private key, not who they are. A certificate authority is the whole industry's answer to that gap, and it is far less mysterious than its reputation — it is a keypair plus other people's willingness to trust its signature. Building one takes a single command, and afterwards every certificate error you ever read will be about machinery you have personally assembled.

    The concept

    Use the canonical picture: a certificate is a notarized ID card, and the CA is the notary everyone already trusts. A certificate is a small document saying "this public key belongs to this name", plus validity dates and some usage rules, plus a signature over all of it. Verifying one means checking that signature against the CA's public key — which you must already hold and already trust. The trust does not come from the certificate; it comes from how the CA's own certificate got onto your machine.

    A root CA certificate is self-signed: its subject and issuer are the same name, and it is signed with its own private key. That is not a security property — anyone can self-sign anything, which is why a self-signed certificate presented by a server means nothing. What makes a root CA trustworthy is entirely out-of-band: your operating system ships with a bundle of them in /etc/ssl/certs/, your company puts its internal root there by policy, and in a moment you will pass yours explicitly with -CAfile. Trust is installed, never asserted.

    Two fields make a CA certificate a CA rather than an ordinary one, and clients enforce both. basicConstraints: CA:TRUE says this certificate may sign others; keyUsage: keyCertSign says the key is permitted to do so. A certificate without them is a leaf, and using it to sign is rejected regardless of the maths working.

    Then the part that matters operationally: the CA private key is the most valuable file in the system. Whoever holds it can mint an identity for any name, and everyone trusting that CA will believe it. There is no revocation of that fact in practice — you would have to distribute a new root to every client. This is why ca.key is mode 600, never copied, and on real infrastructure kept offline entirely.

    CA keypair→self-signed CA cert→signs others→clients trust via -CAfile / /etc/ssl/certs

    The arrow that carries trust is the last one, and it is installed by an administrator, not by the network.

    Lab
    1. Create the CA in one command: a new private key and a self-signed certificate over it, valid for ten years. -nodes means the key file is not passphrase-encrypted, which is right for a lab and wrong for anything real. 
      cd ~/ca
openssl req -x509 -newkey rsa:4096 -sha256 -days 3650 -nodes \
  -keyout ca.key -out ca.crt -subj '/CN=B12 Demo CA/O=sandbox'
chmod 600 ca.key; ls -l ca.key ca.crt
      -rw------- 1 ubuntu ubuntu 3272 Jul 25 10:02 ca.key     ← mint-anything power lives in this file
-rw-rw-r-- 1 ubuntu ubuntu 1858 Jul 25 10:02 ca.crt       ← safe to hand to every client
    2. Confirm it is self-signed by reading the two name fields. Identical subject and issuer is the definition — the chain stops here. 
      openssl x509 -in ca.crt -noout -subject -issuer
      subject=CN=B12 Demo CA, O=sandbox
issuer=CN=B12 Demo CA, O=sandbox          ← signed itself: this is a root
    3. Check the two fields that make it usable as a CA at all. Clients read these before they will accept any signature it made. 
      openssl x509 -in ca.crt -noout -ext basicConstraints,keyUsage
      X509v3 Basic Constraints: critical
    CA:TRUE
X509v3 Key Usage: critical
    Digital Signature, Certificate Sign, CRL Sign
    4. Verify it against itself. This is the one case where a certificate validates with only its own file — and it is exactly what "self-signed" means, not a mark of quality. 
      openssl verify -CAfile ca.crt ca.crt
      ca.crt: OK          ← "OK" here means the maths checks out, not that anyone should trust it
    5. See where the system's own trusted roots live, so you know what -CAfile is standing in for. Your CA is not in there, and adding it would be a deliberate administrative act. 
      ls /etc/ssl/certs/*.pem | wc -l
grep -c 'BEGIN CERTIFICATE' /etc/ssl/certs/ca-certificates.crt
      146
146          ← the roots your machine believes by default; every HTTPS check starts from this bundle
    Verify

    Explain, without hedging, what you now hold in ca.key — the ability to issue a certificate for any name that any client trusting ca.crt will accept. Then answer why a self-signed server certificate warns in a browser while a self-signed root is the foundation of all trust: the difference is not the certificate, it is whether that root was installed on the client in advance. Finally, name the two extensions a CA certificate must carry, and say what a client does with a certificate that lacks them.

    Gotchas

    "Self-signed certificate" is used to mean two completely different things and the ambiguity causes real confusion. A self-signed leaf served by a web server is a red flag: nothing vouches for it, and accepting it means accepting whoever is on the other end of the connection today. A self-signed root CA is normal and unavoidable — every trust chain terminates in one — and its safety comes entirely from how it reached your trust store. Same term, opposite implications.

    The second is the illusion of revocation. Certificate revocation lists and OCSP exist, are patchily supported, and are frequently ignored by clients. In practice the defence against a compromised certificate is a short validity period, not revocation — which is why modern public certificates last 90 days and why cluster certificates rotate automatically. If your CA key leaks, revocation will not save you; replacing the root everywhere will.

    kubeadm init runs this exact command on your behalf. It creates /etc/kubernetes/pki/ca.key and ca.crt — a self-signed root for the cluster — and then issues every component certificate from it. Possession of that ca.key is functionally permanent cluster-admin: you can mint a client certificate with CN=whoever and O=system:masters and the API server will believe it, with no RBAC rule able to stop you. That is why the file never leaves the control-plane node, why backing up /etc/kubernetes/pki is backing up the crown jewels, and why a kubeadm cluster actually has more than one CA — the etcd CA and the front-proxy CA are separate roots, so that a compromise in one trust domain does not automatically mint identities in another.

    The three trust domains under /etc/kubernetes/pki, and which certificate belongs to which, is W2.5; what a control-plane rebuild does to them is W2.2.

    Docs

    man 1 openssl-req for the -x509 self-signing mode, -subj and -nodes. man 1 openssl-x509 for reading certificates and the -ext selector used above. man 5 x509v3_config is the page that defines basicConstraints, keyUsage and (next lesson) subjectAltName. man 8 update-ca-certificates for how a root actually gets installed into a machine's trust store.

    B12.9

    Key, CSR, signature: issuing a certificate in two proper steps

    Why it matters

    Issuing a certificate always splits across two parties, and the split is the security property. The subject makes a key and asks; the CA signs. Once you have done it by hand, the Kubernetes CSR API stops looking like a strange bureaucratic detour and starts looking like the only sane way to do it — and you stop being tempted by tutorials that generate a private key on the wrong machine.

    The concept

    A certificate signing request is a small document containing three things: the public key of the requester, the identity they are requesting (subject name, and the SAN list from B12.10), and a self-signature proving the requester holds the matching private key. It does not contain the private key, cannot contain it, and never needs to. The private key is generated on the machine that will use it and stays there for its entire life.

    That is the whole point of the two-step dance. A CSR can be emailed, pasted into a ticket, or posted to an API without exposing anything: the worst an interceptor can do with it is ask for a certificate they cannot use, because they lack the private key it commits to. Any process that sends you a private key — a colleague, a vendor, a script — has already failed, and the certificate should be reissued.

    The CA then does something narrow. It decides whether to believe the requested identity (that decision is policy, not cryptography, and it is where a real CA does all its actual work), and if so signs a certificate binding that public key to that name. The signature is B12.6's operation over the certificate's contents. Note what the CA never learns: the requester's private key. It vouches for a name-to-key binding without ever holding the key it is vouching for.

    subject: keypair→CSR (public key + name + self-sig)→CA signs→certificate back

    Only public material crosses the arrow; the private key never leaves the machine that made it.

    Lab
    1. Generate the server's own key. Think of this as happening on the server, not on the CA — that separation is the lesson. 
      cd ~/ca
openssl genrsa -out server.key 2048
chmod 600 server.key
      (no output — a 2048-bit key file, mode 600, on the machine that will use it)
    2. Create the CSR from that key. Deliberately request only a common name for now; B12.10 will show you why that is not enough. 
      openssl req -new -key server.key -out server.csr -subj '/CN=localhost'
openssl req -in server.csr -noout -subject -verify
      Certificate request self-signature verify OK       ← proves the requester holds the private key
subject=CN=localhost
    3. Prove the CSR carries the public half only, by extracting it and comparing with the public key derived from server.key. Identical output means the CSR commits to this exact keypair and carries nothing secret. 
      openssl req -in server.csr -noout -pubkey | sha256sum
openssl rsa -in server.key -pubout 2>/dev/null | sha256sum
      3f9a1c...c2  -
3f9a1c...c2  -          ← same public key; the CSR is safe to send anywhere
    4. Now act as the CA and sign it. This is the step that requires ca.key — and it is the only step that does. 
      openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 365 -sha256 -out server.crt
openssl x509 -in server.crt -noout -subject -issuer -serial
      Certificate request self-signature ok
subject=CN=localhost
issuer=CN=B12 Demo CA, O=sandbox          ← issued by your CA, not by itself
serial=4A2F1B...                          ← unique per issuance; CAcreateserial started the counter
    5. Verify the chain: does this certificate carry a valid signature from a CA you trust? This is what every TLS client does on every connection. 
      openssl verify -CAfile ca.crt server.crt
      server.crt: OK          ← chain valid. Note this says nothing about the NAME being right (B12.10).
    6. Show the negative case that makes the CA's role concrete: the same certificate against a CA that did not sign it. 
      openssl req -x509 -newkey rsa:2048 -sha256 -days 30 -nodes \
  -keyout other-ca.key -out other-ca.crt -subj '/CN=Other CA' 2>/dev/null
openssl verify -CAfile other-ca.crt server.crt
      C = , CN = localhost
error 20 at 0 depth lookup: unable to get local issuer certificate
                            ← "unknown CA": memorise this string, B12.16 makes you meet it again
    Verify

    Say what a CSR contains and what it deliberately omits, then explain why that omission is the security property rather than an inconvenience. Check your understanding against the files: ls -l ~/ca should show exactly two files with mode 600 so far (ca.key, server.key), and you should be able to say which machine each of them would live on in a real deployment. Finally, note error 20's wording now — unable to get local issuer certificate — because it is the error people most often misread as "the certificate is broken" when it means "I do not trust who signed it".

    Gotchas

    -CAcreateserial creates a ca.srl file that tracks the next serial number. Lose or ignore it and you can issue two certificates with the same serial from the same CA, which some clients and most auditors treat as a serious problem. In a lab it is invisible; the habit worth carrying is that serial uniqueness is the CA's responsibility, not the requester's.

    The second is the one-command shortcut. openssl req -x509 generates a key and a self-signed certificate together, which is right for a root CA and wrong for everything else — it produces a certificate signed by nobody. If a tutorial hands you a single command that emits both tls.key and tls.crt for a server, look closely: you almost certainly want the two-step version, or your clients will need --insecure forever.

    Kubernetes exposes this exact two-step flow as an API. To onboard a human user, you generate a private key and a CSR on their machine, submit the CSR to the cluster as a CertificateSigningRequest object with signerName: kubernetes.io/kube-apiserver-client, and an administrator approves it with kubectl certificate approve. The cluster CA signs it, and the user pulls the certificate back out of the object's status. The private key never touches the cluster, which is precisely why the API is shaped this way — approval is a policy decision about a name, exactly as described above.

    The full CSR onboarding flow, from openssl req to a working kubeconfig, is W7.3; the certificates kubeadm issues for the components themselves are W2.3.

    Docs

    man 1 openssl-req for creating and inspecting CSRs (-new, -verify, -pubkey). man 1 openssl-x509 for the -req signing mode, -CA/-CAkey and -CAcreateserial. man 1 openssl-verify lists every numbered verification error, including error 20 — worth skimming once so the strings are familiar before you meet them under pressure.

    B12.10

    SANs: where most certificate errors actually come from

    Why it matters

    The certificate you signed in the last lesson passes openssl verify and will still be rejected by every modern client. The reason is one missing extension, and it is behind a large fraction of all real-world TLS failures — including the classic one that appears the day someone puts a load balancer in front of a working API server.

    The concept

    Verification has two independent halves, and conflating them is why the error is confusing:

    • Chain validation — is this certificate signed by a CA I trust, and is it within its validity dates? This is what openssl verify -CAfile answers.
    • Name matching — does this certificate actually cover the name I typed? A perfectly valid certificate for example.com must be refused when you asked for bank.com, or the entire system is pointless.

    Name matching reads the subject alternative name extension — the SAN list — and nothing else. Historically it read the subject's common name (CN=localhost), which is why so many people still think of the CN as "the hostname". That has been deprecated for years and is now simply ignored for name matching by browsers, Go's TLS library, curl and openssl alike. A certificate with a perfect CN and no SAN fails everywhere, with an error that mentions neither field clearly.

    A SAN entry is typed. DNS:localhost matches a hostname; IP:127.0.0.1 matches a literal IP address, and — this is the part that catches people — a DNS: entry does not match a connection made to that IP. If a service is reached both by name and by address, both must be listed, separately. Wildcards (DNS:*.svc.cluster.local) match exactly one label, so they cover foo.svc.cluster.local and not foo.bar.svc.cluster.local.

    The practical rule follows directly: enumerate every name and address a client might use to reach this service, and put all of them in the SAN list at issuance time. Not the canonical one — all of them. A certificate cannot be amended later; adding a name means issuing a new certificate.

    chain OK+name in SAN list=connection proceeds

    Two separate checks, two separate failure messages — and only one of them is about trust.

    Lab
    1. Confirm the problem exists. Your server.crt from B12.9 has no SAN extension at all — look for it and find nothing. 
      cd ~/ca
openssl x509 -in server.crt -noout -ext subjectAltName
      No extensions in certificate            ← the CN says localhost; nothing here says it
    2. Watch the two checks disagree. The chain is fine; the name check fails on the same file, with a completely different error. 
      openssl verify -CAfile ca.crt server.crt
openssl verify -CAfile ca.crt -verify_hostname localhost server.crt
      server.crt: OK                                         ← chain validation passes
C = , CN = localhost
error 62 at 0 depth lookup: Hostname mismatch          ← name matching fails: CN is not consulted
    3. Write the extension file the CA will apply when signing. This is where the SAN list, and the leaf-certificate constraints, are declared. 
      cat > san.ext <<'EOF'
basicConstraints = CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:localhost, DNS:sandbox, IP:127.0.0.1
EOF
cat san.ext | tail -1
      subjectAltName = DNS:localhost, DNS:sandbox, IP:127.0.0.1
                 ↑ every name and address a client might use, enumerated at issuance
    4. Reissue from the same CSR and the same key — only the CA's signing step changes. Nothing about the server's private key needs regenerating to fix a SAN. 
      openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 365 -sha256 -extfile san.ext -out server.crt
openssl x509 -in server.crt -noout -ext subjectAltName
      X509v3 Subject Alternative Name:
    DNS:localhost, DNS:sandbox, IP Address:127.0.0.1
    5. Re-run both checks. Chain and name now agree, which is the state every working TLS connection is in. 
      openssl verify -CAfile ca.crt -verify_hostname localhost server.crt
openssl verify -CAfile ca.crt -verify_ip 127.0.0.1 server.crt
      server.crt: OK
server.crt: OK          ← the IP entry is what makes the second one pass; DNS: alone would not
    6. Prove the "add a new name later" failure, because it is the one you will meet in production. A name nobody listed is refused even though nothing about the certificate is broken. 
      openssl verify -CAfile ca.crt -verify_hostname api.internal server.crt
      error 62 at 0 depth lookup: Hostname mismatch
                            ← the load-balancer scenario, in one command
    Verify

    Explain the difference between the two verification halves and give the distinct error each produces — unable to get local issuer certificate for an untrusted signer, Hostname mismatch for a name not in the SAN list. Then answer the two questions that decide most real SAN bugs: does a DNS: entry cover a connection made to the corresponding IP address (no — you need an IP: entry), and can you add a name to an existing certificate (no — you reissue, though the key and CSR can be reused as in step 4).

    Gotchas

    The most expensive habit here is putting a hostname in the CN and assuming it works because it did once. It will pass a casual eyeball review and fail every client, and the error message — Hostname mismatch, or in Go x509: certificate is valid for X, not Y — points at the name rather than at the missing extension, so people re-check the DNS instead of the certificate. When a name-related TLS error appears, print the SAN list first, before anything else.

    The second is -copy_extensions. If you put SANs into the CSR with -addext, openssl x509 -req will silently drop them unless you pass -copy_extensions=copyall — and that flag is genuinely dangerous in a real CA, because it lets a requester ask for any extension including CA:TRUE. The safe pattern is the one used above: the CA decides the extensions with -extfile, the requester only asks.

    The API server's certificate is the longest SAN list most people ever read, and now it is obvious why: it must cover every name and address any client might use to reach it — the node's IP, the cluster IP of the kubernetes service (usually 10.96.0.1), the names kubernetes, kubernetes.default, kubernetes.default.svc and kubernetes.default.svc.cluster.local, plus the node's hostname. Every in-cluster client resolves one of those (B10.4's search list is why the short forms are needed) and each must match.

    This is also the single most common cause of a broken control plane after an infrastructure change: put a load balancer or a new DNS name in front of the API server without adding it to apiServer.certSANs and reissuing, and every client fails with a name mismatch while the server itself looks perfectly healthy. Reading and reissuing those certificates is W2.6, and the kubeadm configuration that sets extra SANs is W2.7.

    Docs

    man 5 x509v3_config is the reference for the extension file written above — search it for subjectAltName, extendedKeyUsage and the DNS:/IP:/URI: prefixes. man 1 openssl-verify documents -verify_hostname, -verify_ip and error 62. man 1 openssl-x509 for -extfile and the -copy_extensions warning.

    B12.11

    Read a certificate, verify a chain, find the expiry in five seconds

    Why it matters

    Certificate expiry is the outage with no deploy behind it: nothing changed, nobody pushed, and at 03:14 the cluster stopped accepting its own kubelets. The only defence is fluency — being able to point openssl at a file or a live port and read the answer without looking anything up. That fluency is five commands, and this lesson drills them.

    The concept

    A certificate is a structured document, and openssl x509 -text prints all of it. The fields worth finding instantly:

    • Subject — who this certificate is about. In client certificates the CN is the username and each O is a group, which is B12.12's subject.
    • Issuer — who signed it. Equal to the subject means self-signed (B12.8).
    • Validity — Not Before and Not After. Both are checked; a clock skewed into the past fails a brand-new certificate just as surely as expiry fails an old one.
    • Subject Alternative Name — the names it actually covers (B12.10).
    • Key Usage / Extended Key Usage — what it may be used for. serverAuth and clientAuth are distinct, and a certificate issued for one is rejected when presented for the other.

    Rather than reading the whole dump every time, use the targeted flags: -subject, -issuer, -dates, -ext subjectAltName, -serial. And learn -checkend, which answers "will this still be valid in N seconds?" with an exit status — the form you can put in a monitoring check, which is where this belongs rather than in someone's calendar.

    Two more skills complete the set. openssl verify -CAfile checks a chain against a trusted root, and openssl s_client -connect host:port pulls a certificate from a live server so you can inspect what is actually being served rather than what is on disk. The two answer different questions, and when they disagree you have found your bug: the file on disk was updated and the process was never restarted.

    on disk: x509 -in filevson the wire: s_client -connect→a disagreement is a missed restart

    Always check the wire when the file looks fine.

    Lab
    1. Read the whole thing once, so the shape is familiar. Then never do this again in a hurry. 
      cd ~/ca
openssl x509 -in server.crt -noout -text | head -14
      Certificate:
    Data:
        Version: 3 (0x2)
        Serial Number: 4a:2f:1b:...
        Signature Algorithm: sha256WithRSAEncryption
        Issuer: CN=B12 Demo CA, O=sandbox
        Validity
            Not Before: Jul 25 10:11:03 2026 GMT
            Not After : Jul 25 10:11:03 2027 GMT
        Subject: CN=localhost
    2. Now the fast version — the four flags worth muscle memory. This is what you actually run during an incident. 
      openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
      subject=CN=localhost
issuer=CN=B12 Demo CA, O=sandbox
notBefore=Jul 25 10:11:03 2026 GMT
notAfter=Jul 25 10:11:03 2027 GMT
X509v3 Subject Alternative Name:
    DNS:localhost, DNS:sandbox, IP Address:127.0.0.1
    3. Turn expiry into a check rather than a reading exercise. -checkend exits 0 if the certificate outlives the window and 1 if it does not — usable in a script or a monitor. 
      openssl x509 -in server.crt -noout -checkend 2592000; echo "exit=$?"
openssl x509 -in server.crt -noout -checkend 99999999; echo "exit=$?"
      Certificate will not expire
exit=0                       ← safe for the next 30 days
Certificate will expire
exit=1                       ← would be expired within ~3.2 years: this is your alert condition
    4. Verify the chain, then break the trust deliberately and read the difference. Both messages are ones you will meet again in B12.16. 
      openssl verify -CAfile ca.crt server.crt
openssl verify -CAfile other-ca.crt server.crt 2>&1 | tail -1
      server.crt: OK
error 20 at 0 depth lookup: unable to get local issuer certificate
    5. Inspect a certificate that is actually being served, using a real public endpoint. This is the command for "what is this server presenting right now". 
      echo | openssl s_client -connect ubuntu.com:443 2>/dev/null \
  | openssl x509 -noout -subject -dates -ext subjectAltName | head -5
      subject=CN=ubuntu.com
notBefore=... GMT
notAfter=... GMT
X509v3 Subject Alternative Name:
    DNS:ubuntu.com, DNS:www.ubuntu.com          ← a real SAN list, read off the wire
    6. Practise the five-second version until it is reflex: one line, one answer, no flags to recall. 
      openssl x509 -in server.crt -noout -enddate
      notAfter=Jul 25 10:11:03 2027 GMT          ← this is the whole skill
    Verify

    Without notes, produce three commands: the expiry date of a certificate file, the SAN list of a certificate being served on a live port, and a check that exits non-zero if a certificate expires within 30 days. Then explain what it means when the file on disk shows a fresh Not After and s_client shows an expired one — the file was renewed and the process still holds the old certificate in memory, so the fix is a restart or a reload, not another renewal.

    Gotchas

    Clock skew produces certificate errors that read like corruption. A machine whose clock is days behind will reject a certificate issued today with certificate is not yet valid, and one whose clock has jumped forward will report expiry on something perfectly current. When a certificate error appears on exactly one machine, check timedatectl before you check anything else — this is a routine cause of a single node failing to join a cluster.

    The second is trusting the file over the connection. Renewal writes a new file; the running process usually mapped the old one at startup and will keep serving it until it is restarted or explicitly reloaded. That is why s_client is the authoritative answer during an incident and the file on disk is only a claim about intent.

    A kubeadm cluster issues component certificates with a one-year lifetime, and this is the reason clusters that are left alone for thirteen months stop working with no change having been made. kubeadm certs check-expiration is exactly this lesson's -enddate loop, run over every file in /etc/kubernetes/pki and every embedded certificate in the control-plane kubeconfigs, and kubeadm certs renew all reissues them — after which the static-pod control plane must actually restart to pick them up, which is the disk-versus-wire distinction biting in the most consequential place it can.

    Inspecting cluster certificates by hand is W2.6; the check-expiration and renewal workflow is W2.7; the kubelet's own client certificate and its automatic rotation — the one certificate that does not need this treatment — is W2.8.

    Docs

    man 1 openssl-x509 for every display flag used here (-subject, -issuer, -dates, -enddate, -serial, -ext, -checkend). man 1 openssl-s_client for pulling a certificate off a live port, including -servername when the server uses SNI to pick between several. man 1 openssl-verify for the numbered errors, and man 1 timedatectl for the clock check the gotcha above depends on.

    B12.12

    Real TLS, then mutual TLS: s_server, s_client and -Verify

    Why it matters

    Everything so far has been files. This is where the files become a connection: a server proving its identity to a client, then — the step that matters for Kubernetes — a client proving its identity right back. Once you have watched a handshake succeed and then fail for a specific reason, the cluster's entire authentication model is something you have already built.

    The concept

    An ordinary TLS connection is one-way authentication. The server presents a certificate; the client checks the chain (B12.9) and the name (B12.10) and, satisfied, proceeds. The server learns nothing about the client — which is right for the public web, where the server has no idea who is visiting and does not need one.

    Mutual TLS (mTLS) adds the mirror image: the server demands a certificate from the client and verifies it against a CA it trusts. Now both ends have proven possession of a private key whose public half is bound, by a trusted signature, to a name. Two consequences follow. First, authentication is finished before a single byte of application data is sent — there is no login request, no token, no password. Second, the identity is in the certificate, so the server can read it straight out of the subject rather than looking anything up.

    That last point is the one to carry forward. In a mutually-authenticated connection, the server extracts the client's identity from the certificate's subject: the CN becomes the username and each O (organization) becomes a group. That convention is not something Kubernetes invented — it is how X.509 client authentication is conventionally mapped — but Kubernetes uses it literally, and knowing it explains kubeconfigs at a glance.

    openssl ships both ends. s_server is a minimal TLS server, s_client a minimal client, and their verification flags are worth reading carefully: on the server, -Verify (capital V) requires a client certificate and fails the connection without one, while -verify (lowercase) merely asks and continues if none arrives. That distinction is the difference between mTLS and a suggestion.

    server cert → client checks+client cert → server checks=both identities proven, before any data

    Mutual TLS is the same check run twice, in opposite directions.

    Lab
    1. Start a TLS server with the certificate you issued. -www makes it answer HTTP requests, so a browser-shaped client can talk to it. 
      cd ~/ca
openssl s_server -accept 4433 -cert server.crt -key server.key -www >/dev/null 2>&1 &
sleep 1; ss -ltnp 2>/dev/null | grep 4433
      LISTEN 0  4096  *:4433  *:*  users:(("openssl",pid=5120,fd=4))     ← a real TLS listener
    2. Connect and read the verification result. The last line of the handshake summary is the one that matters. 
      echo | openssl s_client -connect localhost:4433 -CAfile ca.crt 2>/dev/null \
  | grep -E 'Verify return code|Cipher|Protocol' 
      Protocol  : TLSv1.3
Cipher    : TLS_AES_256_GCM_SHA384          ← symmetric cipher for the conversation (B12.5)
Verify return code: 0 (ok)                  ← chain checked against your CA
    3. See what happens without the CA. The connection still forms — encryption never needed trust — but verification fails, which is what a browser turns into a full-page warning. 
      echo | openssl s_client -connect localhost:4433 2>/dev/null | grep 'Verify return code'
      Verify return code: 21 (unable to verify the first certificate)
                    ← encrypted but unauthenticated: exactly what --insecure buys you
    4. Issue a client certificate. Same two steps as before, with the identity fields that matter for authentication — a username in CN and groups in O. 
      openssl genrsa -out client.key 2048 2>/dev/null; chmod 600 client.key
openssl req -new -key client.key -out client.csr -subj '/CN=alice/O=developers/O=oncall'
printf 'basicConstraints=CA:FALSE\nkeyUsage=critical,digitalSignature\nextendedKeyUsage=clientAuth\n' > client.ext
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 365 -sha256 -extfile client.ext -out client.crt 2>/dev/null
openssl x509 -in client.crt -noout -subject -ext extendedKeyUsage
      subject=CN=alice, O=developers, O=oncall     ← username, then two groups
X509v3 Extended Key Usage:
    TLS Web Client Authentication            ← clientAuth, not serverAuth
    5. Restart the server demanding a client certificate. Capital -Verify is the flag that makes it mandatory. 
      kill %1 2>/dev/null; sleep 1
openssl s_server -accept 4433 -cert server.crt -key server.key \
  -CAfile ca.crt -Verify 1 -www >/dev/null 2>&1 &
sleep 1; echo | openssl s_client -connect localhost:4433 -CAfile ca.crt 2>&1 | tail -2
      40E7...:error:0A000412:SSL routines::sslv3 alert bad certificate
peer did not return a certificate          ← the server refused: no client identity offered
    6. Connect again, this time presenting the client certificate and key. Both ends now verify, and the server prints the identity it read. 
      echo | openssl s_client -connect localhost:4433 -CAfile ca.crt \
  -cert client.crt -key client.key 2>/dev/null | grep -E 'Verify return code|subject='  | head -3
      subject=CN=localhost
Verify return code: 0 (ok)          ← client verified the server; the server verified alice
    7. Stop the server. The certificates stay — B12.15 builds the project on exactly these files. 
      kill %1 2>/dev/null; sleep 1; ss -ltn 2>/dev/null | grep -c 4433
      0          ← listener gone
    Verify

    State what each side proves in a mutual TLS handshake, and where the client's identity comes from once it succeeds. Then check three things you should now be able to produce on demand: the flag that makes a client certificate mandatory rather than optional (-Verify, capital), the verify return code of a successful connection (0 (ok)), and the error a server gives a client that brings no certificate (peer did not return a certificate). If you can also explain why code 21 means the connection was encrypted but worthless, you are ready for the project.

    Gotchas

    Encryption and authentication are separate, and step 3 is the proof. A connection with no verification at all is still encrypted — nobody passively watching the wire can read it — and still completely insecure, because you may be talking to anyone. This is what curl --insecure and kubectl --insecure-skip-tls-verify actually do: they keep the encryption and discard the identity check. Using them to "fix" a certificate error converts a loud problem into a silent one.

    The second is extendedKeyUsage. A certificate marked serverAuth presented as a client certificate is rejected, and the error rarely says so plainly. When a client certificate is refused by a server that trusts the CA and everything looks right, print the EKU — this is a common failure when someone reuses a server certificate for a client identity because both were signed by the same CA.

    You have just built the cluster's authentication model. Every core Kubernetes component authenticates to the API server with a client certificate, and the API server's --client-ca-file is the -CAfile you passed to s_server. The identity mapping is literal: the certificate's CN becomes the username and every O becomes a group. That is why the admin kubeconfig kubeadm writes contains a certificate with O=kubeadm:cluster-admins — a group that a ClusterRoleBinding grants cluster-admin to — and why the kubelet's certificate is CN=system:node:node01, O=system:nodes, which is exactly what the Node authorizer keys off. There is no User object anywhere in Kubernetes; the username is the string in the certificate, which is also why users cannot be deleted, only their certificates left to expire or their bindings removed.

    The three credential types and the "there is no User object" rule are W7.1; which identity is inside each kubeconfig kubeadm writes is W2.3, and the Node authorizer that reads O=system:nodes is W7.5.

    Docs

    man 1 openssl-s_server — read the difference between -verify and -Verify in its own words, plus -CAfile and -www. man 1 openssl-s_client for -cert/-key, -CAfile, -showcerts and the verify return codes. man 1 openssl-verify for what codes 20 and 21 mean, and man 5 x509v3_config for extendedKeyUsage.

    Handling secrets

    B12.13

    How secrets leak: process listings, /proc/PID/environ, and file modes

    Why it matters

    Most secrets are not stolen; they are handed over by ordinary mechanisms working exactly as designed. A password on a command line is public to every user on the machine. An environment variable is copied into every child process. Neither of those requires an attacker to do anything clever, and both are avoidable once you have seen them happen.

    The concept

    There are three common ways to get a secret into a process, and they have very different blast radii.

    • Command-line argument — the worst. A process's arguments live in /proc/PID/cmdline, which is world-readable by design, because that is where ps gets its output. Any user on the machine can read the arguments of any process, no privileges required. Passing --password=hunter2 publishes it.
    • Environment variable — better, and still leaky. /proc/PID/environ is readable only by the process's owner and root, so another unprivileged user cannot read it. But the environment is inherited by every child process, so a secret meant for one program reaches every shell-out, every helper, every crash handler it invokes. Environments are also routinely dumped into crash reports, debug logging and error trackers, which is how secrets end up in a bug database.
    • A file with mode 600 — the best of the three. It is read by the one process that needs it, at the moment it needs it; it is not inherited; it does not appear in any listing; and it can be replaced on disk and re-read without restarting anything. Its weakness is the familiar one: root reads it anyway, and so does anything running as the same user (B12.1).

    Notice that the ranking is about who else ends up holding a copy, not about encryption — none of the three is encrypted. This is a blast-radius argument, and it is the same argument in every context where you will meet it again.

    argv: everyone→environ: you, root, every child→file 600: you, root, on demand

    Same secret, three very different lists of who has it.

    Lab
    1. Publish a secret the easy way, then read it as a completely unprivileged user. No exploit is involved — this is ps doing its job. 
      python3 -c 'import time; time.sleep(300)' --password=hunter2 &
sleep 1; sudo -u mallory ps -eo user,args --no-headers | grep '[p]assword'
      ubuntu   python3 -c import time; time.sleep(300) --password=hunter2
                                                  ← mallory read it with no privileges at all
    2. Confirm where that came from and that the file is world-readable by design, so no permission change can fix it.

    3. Now try the environment variable version, and see the improvement — another user is refused. 
      kill %1; DB_PASSWORD=hunter2 python3 -c 'import time; time.sleep(300)' &

      kill %1 2>/dev/null; pkill -f 'time.sleep(300)'; rm -f ~/db-pass; echo cleaned
      cleaned
    Verify

    Rank the three delivery mechanisms by blast radius and justify each position in one sentence: who can read a command-line argument (everyone), who can read an environment variable (the owner, root, and every descendant process), who can read a mode-600 file (the owner and root, and only when it is opened). Then answer the design question that follows: which of the three can be rotated without restarting the process, and why does that matter operationally?

    Gotchas

    A great many tools still accept --password on the command line, and their own documentation often uses it in the examples. Where a tool offers an alternative — --password-file, a config file, an environment variable, or reading from stdin — take it. Where it does not, be aware that the secret is public to the machine for the lifetime of the process, and that shell history has it too.

    The second, subtler leak is that a secret placed in a file is only as private as everything the file passes through: the editor's swap file, the backup that runs at 02:00, the container image it was baked into, and the Git repository someone committed it to "temporarily". Mode 600 protects the file at that path, not every copy of its contents that exists elsewhere.

    This lesson is the concrete argument behind a recommendation you will meet constantly: mount Secrets as files, not as environment variables. A Secret consumed with env: or envFrom: lands in the container's environment, which means it is inherited by every process the container starts, visible in kubectl exec … env, and frequently swept up by crash reporters and log shippers. Mounted as a volume it is a file in a tmpfs, readable by the process that opens it and nothing else — and, crucially, a mounted Secret updates in place when the Secret object changes, while an environment variable is fixed at container start and can only change by restarting the pod. Same secret, materially different blast radius and materially different rotation story.

    The four ways a pod can consume a Secret or ConfigMap is W3.21; the update-propagation rules that make volumes rotatable and env permanent are W3.22; why the Secret's value itself is only base64 is W3.23.

    man 5 proc is the page for both files — search it for /proc/[pid]/cmdline and /proc/[pid]/environ, including the note that the second is readable only by the owner. man 1 ps for where its output comes from, and man 7 environ for how the environment is inherited across fork and exec (B2.5).

    B12.14

    seccomp and AppArmor: the layers behind the permission check

    Why it matters

    Every control so far has answered "may this identity do this?" — and every one of them is bypassed the moment a process is running as the identity that is allowed. The two kernel layers in this lesson answer a different question: "regardless of who you are, is this program permitted to do this at all?" They are what stands behind the permission check when everything in front of it has already failed.

    The concept

    Standard Linux permissions are discretionary: the owner of a resource decides who may use it, and root may do anything. Mandatory access control is the opposite — a policy set by the administrator constrains a program no matter whose identity it runs under, including root. Ubuntu ships two, working at different levels:

    • seccomp filters system calls (B3.6). A seccomp profile is a list saying which of the ~350 syscalls a process may make; a call outside the list is refused, typically by killing the process with SIGSYS. It is narrow and extremely effective: a web server has no business calling mount, kexec_load or ptrace, and forbidding them removes whole categories of exploit even if the process is compromised.
    • AppArmor confines a program by path: which files it may read or write, which capabilities it may use, whether it may use the network. Profiles live in /etc/apparmor.d/, are attached to an executable's path, and run in one of two modes — enforce (violations blocked) or complain (violations logged only, which is how you develop a profile without breaking the service).

    Both are defense in depth in the exact sense of B12.2: they do nothing on a healthy day. Their value appears at the moment something else has already gone wrong — a parser bug, a compromised dependency, a stolen credential — and the attacker, now running with your service's full identity, tries to do something your service never does. That is when a profile that says "this program never calls mount" stops being paperwork.

    uid/gid check→capability check→seccomp: which syscalls·AppArmor: which paths

    Four gates, and only the last two still apply once an attacker holds a legitimate identity.

    Lab
    1. See what is already confined on this machine. Ubuntu enforces AppArmor profiles out of the box on a surprising number of programs. 
      sudo aa-status | head -6
      apparmor module is loaded.
44 profiles are loaded.

   /usr/bin/man
   /usr/lib/snapd/snap-confine

    2. Read one profile. This is the whole vocabulary: paths, permission letters, capabilities — nothing exotic. 
      sudo grep -E '^\s+(/|capability|network)' /etc/apparmor.d/usr.bin.man | head -6
        capability setuid,
  /usr/bin/man mr,
  /etc/manpath.config r,
  /var/cache/man/** rw,          ← "may read and write here"; anything unlisted is denied
    3. Check which profile a running process is confined by. An unconfined process reports exactly that. 
      cat /proc/self/attr/current; echo

      unconfined                       ← your shell: no AppArmor profile applies
/usr/bin/man (enforce)          ← man, running under its profile
    4. Look at seccomp's status on a normal process. The Seccomp field in /proc/PID/status is 0 (off), 1 (strict) or 2 (a BPF filter is installed). 
      grep -E 'Seccomp' /proc/self/status
      Seccomp:        0          ← no filter: this shell may make any syscall the kernel offers
Seccomp_filters:        0
    5. Install a filter and watch it bite. systemd's SystemCallFilter= is the easiest way to apply seccomp without writing BPF — here, everything except the mount-related calls. 
      sudo systemd-run --pty --quiet -p SystemCallFilter='~@mount' \
  /bin/sh -c 'grep Seccomp: /proc/self/status; mount -t tmpfs none /mnt'
      Seccomp:        2                     ← a BPF filter is installed
sh: line 1: Bad system call           ← SIGSYS: the kernel refused mount(2) outright
    6. Confirm the same command works without the filter, so you know the failure came from seccomp and not from permissions. 
      sudo /bin/sh -c 'mount -t tmpfs none /mnt && echo mounted && umount /mnt'
      mounted          ← same user, same capability, same command — only the filter differed
    Verify

    Say what each layer constrains — seccomp the set of system calls, AppArmor the set of paths, capabilities and network operations available to a named program — and why both are described as mandatory rather than discretionary (the administrator sets them; the program's own identity, root included, cannot override them). Then explain what step 5 proved that step 6 could not have shown alone: the refusal came from the filter, not from a missing permission, and the process was killed rather than given an error.

    Gotchas

    A seccomp violation does not look like a permission error. The default action is SIGSYS, so the process dies and the shell prints Bad system call — no EACCES, no log line from the program itself, nothing pointing at a policy. If a program dies instantly with that message, check Seccomp: in its status and the filter it was started under before you debug the program.

    AppArmor's failure mode is the opposite and just as confusing: a denial is logged to the journal (or dmesg) as apparmor="DENIED" while the program merely sees a file it cannot open, and reports something vague about a missing configuration file. When a service inexplicably cannot read a path that clearly exists with correct permissions, journalctl -k | grep DENIED is the check that ends the investigation in five seconds. This is also why complain mode exists — run the program through its real workload with the profile in complain mode, collect the denials, and only then enforce.

    Kubernetes surfaces both layers in a pod's securityContext, and the important one is chosen for you: seccompProfile: {type: RuntimeDefault} applies the container runtime's own curated filter, which blocks around 40 dangerous syscalls that essentially no workload needs. It is the single highest-value security setting available on a pod and it is off by default for backwards compatibility, which is why the restricted Pod Security Standard requires it. AppArmor is available too, through the appArmorProfile field (an annotation in older versions), pointing at a profile that must already be loaded on the node — which is the operational catch: the profile is a node-level artefact, so a pod that requires one will not start on a node where nobody installed it.

    These are CKS topics rather than CKA ones, so the advanced track does not drill them; what it does cover is where the confinement is applied — the kubelet handing the pod's spec to containerd over CRI, which is W1.20, and what actually runs privileged on a node, W1.2.

    Docs

    man 2 seccomp for the syscall itself and the filter modes; man 5 systemd.exec for SystemCallFilter= and its @-prefixed syscall groups, which are the readable way to use seccomp. man 5 apparmor.d for profile syntax, man 8 aa-status, man 8 aa-complain and man 8 aa-enforce for the mode switches. man 7 capabilities remains the page for the gate immediately before these two.

    Project & drill

    B12.15

    Mini project — mutual TLS between two local processes

    Why it matters

    Assembling the pieces yourself is what converts eleven lessons of vocabulary into something you can reason about under pressure. When you finish this, you will have built — from a private key upwards — the same arrangement that authenticates every component of a Kubernetes cluster to its API server, and you will have proved that an unauthenticated client cannot get in.

    The concept

    The target is two processes on one machine that each refuse to talk to anyone the other CA has not vouched for. You already have every piece: a CA (B12.8), a server certificate with correct SANs (B12.10), a client certificate carrying an identity (B12.12). What is left is to run the server as a real service rather than a foreground command — a systemd unit (B11.3) with its key material referenced by path — and then demonstrate the two outcomes that matter: an authorized client is admitted and its identity is read, and an unauthorized client is refused before any application data flows.

    Success criteria, all of which you should be able to show:

    • The server runs as a systemd unit, is enabled, and survives a restart.
    • A client presenting client.crt/client.key connects, and the server records the subject CN=alice.
    • A client presenting no certificate is refused with peer did not return a certificate.
    • A client presenting a certificate from a different CA is refused, with a different message.
    • The client verifies the server too, and rejects it when given the wrong -CAfile.
    Lab
    1. Put the key material where a service would keep it, with the permissions a service would need. The server reads its own key; nobody else should. 
      cd ~/ca
sudo install -d -m 755 /etc/mtls-demo

-rw-r--r-- 1 root root 1310 server.crt
-rw------- 1 root root 1704 server.key          ← only the key is restricted
    2. Write the unit. Everything security-relevant is on the ExecStart line: the server's own identity, the CA it trusts for clients, and the flag that makes a client certificate mandatory. 
      sudo tee /etc/systemd/system/mtls-demo.service >/dev/null <<'EOF'
[Unit]
Description=B12 mutual-TLS demo server
After=network-online.target
Wants=network-online.target
[Service]

  -cert /etc/mtls-demo/server.crt -key /etc/mtls-demo/server.key \

      echo | openssl s_client -connect localhost:4433 -CAfile ca.crt \

    5. Prove the negative case — a client with no certificate is refused. This is the difference between mTLS and encryption. 
      echo | openssl s_client -connect localhost:4433 -CAfile ca.crt 2>&1 | tail -1
      40E7...:SSL routines::peer did not return a certificate          ← refused at the handshake
    6. Prove the other negative case — a certificate from a CA the server does not trust. Issue one from other-ca and watch it fail differently. 
      openssl genrsa -out rogue.key 2048 2>/dev/null

  -cert rogue.crt -key rogue.key 2>&1 | grep -iE 'alert|unknown ca' | head -2

     ← the name inside the certificate said alice; the signature is what was checked

    Walk the success-criteria list at the top and demonstrate each one. Then answer the question that proves you understand what you built: in step 6 the rogue certificate had the subject CN=alice, exactly like the real one — why was it refused? (Because the identity is not the string in the subject; it is the string in the subject as vouched for by a signature the server trusts. Anyone can write CN=alice; only your CA's key can make the server believe it.) That single sentence is the entire security model of a Kubernetes cluster.

    Gotchas

    If the unit fails to start, read systemctl status mtls-demo before touching the certificates. The two common causes are unrelated to TLS: a stale foreground s_server from B12.12 still holding port 4433 (the log says Address already in use), or a path typo giving 203/EXEC (B11.9). Certificate problems produce handshake errors at connection time, not start-up failures.

    The second is a trap worth meeting here rather than in production: -Verify 1 makes a client certificate mandatory, while -verify 1 makes it optional and lets an anonymous client straight through. If your step-5 test unexpectedly succeeds, you almost certainly typed the lowercase flag — and that same mistake, in a real service, is the difference between an authenticated API and an open one.

    What you have built is a small kube-apiserver, minus the API. The server's -cert/-key is --tls-cert-file/--tls-private-key-file; its -CAfile with -Verify is --client-ca-file, which is precisely what makes client certificates a valid authentication method for the cluster; and the subject the server logged is what the API server turns into a username and groups before RBAC ever sees the request. Your client.crt/client.key pair, base64-encoded into a YAML file with the server's address and ca.crt, is a kubeconfig — there is nothing else in one.

    Read the API server's own flags on a live cluster at W1.5; dissect the kubeconfig those files become at W7.2.

    B12.16

    Debugging drill — break mutual TLS four ways

    Why it matters

    Certificate errors are where people guess, and guessing is expensive: it produces afternoons of regenerating things that were never broken. Each of the four failures below has a distinct message that names its cause precisely, and the point of this drill is to see all four in one sitting so that the strings become diagnostic rather than alarming. You will meet every one again as a kubeconfig failure.

    The concept

    Four independent things must hold for a mutual TLS connection to succeed, and each fails with its own signature:

    • Validity — now is between Not Before and Not After. Fails with certificate has expired (error 10) or certificate is not yet valid (error 9, usually a clock problem).
    • Name — the name the client asked for is in the SAN list. Fails with Hostname mismatch (error 62), or in Go programs x509: certificate is valid for X, not Y.
    • Chain — the certificate is signed by a CA the other end trusts. Fails with unable to get local issuer certificate (error 20) or, on the wire, tlsv1 alert unknown ca.
    • Key pairing — the private key matches the public key in the certificate. Fails at start-up, not at connection time, with key values mismatch.

    That last one is worth its own note because it is the odd one out: a mismatched key never produces a handshake error, because the service refuses to start at all. If a program dies immediately after a certificate change, check the pairing before you check anything else — the one-line test is that the modulus of the certificate and the modulus of the key must be identical.

    expired → error 10·wrong SAN → error 62·unknown CA → error 20 / alert·key mismatch → won't start

    Four checks, four strings; nothing here needs guessing.

    Lab
    1. Fault 1 — expired. Rather than waiting a year, ask openssl to evaluate the certificate at a future moment with -attime. The error is identical to the real thing.

    Verify

    Cover the card and reproduce it: given each of the four faults, name the error string, say whether it appears at start-up or at connection time, and name the one file you would open first. Then answer the discriminating question for each pair that gets confused — expired versus not-yet-valid (check the clock, not the certificate), and unknown CA versus wrong SAN (one is about who signed it and is fixed by the trust store, the other is about what name it covers and is fixed by reissuing).

    Gotchas

    Two of these four are routinely misdiagnosed as each other because both feel like "the certificate is wrong". Unable to get local issuer certificate means the certificate might be perfect and you simply do not have, or did not pass, the CA that signed it — the fix is on the verifying side. Hostname mismatch means the trust is fine and the name is wrong — the fix requires the CA to issue a new certificate. Reissuing for the first, or fiddling with trust stores for the second, is wasted effort in both directions.

    The third trap is --insecure. Every one of these errors can be silenced with curl -k or kubectl --insecure-skip-tls-verify, and the connection will work. What you have done is delete the identity check while keeping the encryption (B12.12) — turning a specific, diagnosable failure into a permanent, invisible exposure. Use it to confirm a diagnosis for ten seconds, never to resolve one.

    All six strings on your card appear verbatim in cluster troubleshooting. Unable to connect to the server: x509: certificate signed by unknown authority is error 20 — your kubeconfig's certificate-authority-data does not match the cluster's current CA, which happens routinely after a cluster is rebuilt. x509: certificate has expired or is not yet valid is error 10, and on a kubeadm cluster it is usually the one-year component certificates asking for kubeadm certs renew all — or a node whose clock has drifted. x509: certificate is valid for 10.96.0.1, kubernetes.default…, not lb.example.com is error 62, the SAN list missing a name someone added in front of the API server. And tls: private key does not match public key in a kubelet or API-server log is the key-pairing failure, which is why the control plane refuses to come up rather than serving badly.

    Certificate inspection on a live cluster is W2.6; expiry and renewal is W2.7; and the systematic "kubectl won't connect" triage that starts from exactly these strings is W6.3.

    B12 recall quiz

    Answer out loud before revealing. If you can name what a signature does and does not prove, and map four TLS error strings to four distinct causes, this module has done its job.

    1. What three things does a threat model name, and why is "is this secure?" unanswerable without them?
      Answer

      Assets (the concrete things worth protecting), actors (who might want them, described by position rather than motive) and trust boundaries (where control changes hands). Without them there is no "against whom", so a control cannot be judged — mode 600 is excellent against another logged-in user and irrelevant against root or against someone holding the disk.

    2. State least privilege and defense in depth as questions rather than slogans.
      Answer

      "What is the smallest set of permissions under which this still works?" and "if this one control fails, what is the next one?" On a systemd machine the first is User= plus a single AmbientCapabilities= entry instead of root; the second is NoNewPrivileges=, ProtectSystem=strict, PrivateTmp= — lines that do nothing on a healthy day.

    3. Why is "you are not in the sudoers file" proof that your password was correct?
      Answer

      Because it is an authorization failure, and authorization only runs on an established identity. Authentication (who are you?) succeeded; policy (may you?) declined. The Kubernetes version is the same fork: 401 means the credential was not accepted at all, 403 means you were recognised perfectly and RBAC said no — and only one of those is fixed by touching certificates.

    4. Hashing, encoding, encryption — which is base64, and what is the consequence for Kubernetes Secrets?
      Answer

      Encoding: reversible by anyone with no key, existing so bytes survive a text field. So a Secret's value is protected by nothing — base64 -d is the whole attack. Values are encrypted at rest only if an EncryptionConfiguration is set up on the API server; otherwise anyone who can read the object or read etcd can read the secret.

    5. Why does TLS use both symmetric and asymmetric cryptography in one connection?
      Answer

      Asymmetric solves key distribution — you can publish a public key and receive something only you can read, with no prior arrangement — but it is slow and cannot encrypt a payload larger than the key. Symmetric is fast and hardware-accelerated but needs a shared key first. So the handshake is asymmetric and exists purely to agree one symmetric session key; everything after is AES. Expensive introduction, cheap conversation.

    6. What does a valid signature prove, and what does it conspicuously not prove?
      Answer

      It proves origin (it was made by the holder of a specific private key) and integrity (the data has not changed since, because the signature is over the data's hash). It proves nothing about who that holder is — an impostor's own signature verifies perfectly against the impostor's own public key. Certificates exist precisely to bind a public key to a name via someone you already trust.

    7. What does ssh-agent hold, and what does reaching its socket get someone?
      Answer

      Your decrypted private key, in the memory of a running process, reachable through a mode-600 Unix socket. Anyone who can reach that socket can have it sign challenges — that is, log in anywhere the key is authorized — without ever learning the passphrase. That is also why ssh -A (agent forwarding) hands the same power to root on every host you hop through, and why ProxyJump is preferable.

    8. What makes a CA certificate a CA, and what exactly does holding ca.key mean?
      Answer

      basicConstraints: CA:TRUE and keyUsage: keyCertSign; clients enforce both. Holding the key means being able to mint a certificate for any name that every client trusting that CA will believe. On a kubeadm cluster that is permanent cluster-admin regardless of RBAC, which is why /etc/kubernetes/pki/ca.key never leaves the control-plane node.

    9. What is in a CSR, what is deliberately absent, and why is the absence the point?
      Answer

      The requester's public key, the identity being requested, and a self-signature proving they hold the matching private key. The private key is absent and never needs to travel — so a CSR can be emailed or posted to an API safely. Anyone who sends you a private key has already broken the model. Kubernetes exposes this as the CertificateSigningRequest object plus kubectl certificate approve.

    10. Your certificate has CN=localhost and no SAN. What happens, and why?
      Answer

      Chain validation passes and name matching fails — Hostname mismatch, error 62. CN-as-hostname has been deprecated for years and is now ignored for matching by browsers, Go, curl and openssl alike; only the subjectAltName list is consulted. And a DNS: entry does not cover a connection made to the corresponding IP; that needs an IP: entry.

    11. The certificate file on disk shows a fresh expiry date and s_client shows an expired one. What happened?
      Answer

      The file was renewed and the process was never restarted — it is still serving the certificate it read at start-up. The wire is authoritative during an incident; the file is only a statement of intent. This is exactly why kubeadm certs renew all must be followed by the static-pod control plane actually restarting.

    12. In mutual TLS, where does the server get the client's identity from?
      Answer

      Straight out of the verified client certificate's subject: the CN becomes the username and each O becomes a group. No lookup, no user database — which is why Kubernetes has no User object, why the admin kubeconfig carries O=kubeadm:cluster-admins, and why the kubelet's certificate is CN=system:node:node01, O=system:nodes.

    13. Rank command-line arguments, environment variables and a mode-600 file by blast radius.
      Answer

      Arguments are worst — /proc/PID/cmdline is world-readable by design, so every user on the box can read them via ps. Environment variables are middling — /proc/PID/environ is owner-only, but the environment is inherited by every child and routinely dumped by crash handlers. A mode-600 file is best: read on demand, not inherited, not listed, and rotatable in place. That is the argument for mounting a Kubernetes Secret as a volume rather than as env:.

    14. What does seccomp constrain, what does AppArmor constrain, and why are both called mandatory?
      Answer

      seccomp filters which system calls a process may make (a violation is SIGSYS — the shell prints Bad system call, not a permission error). AppArmor confines a named program's paths, capabilities and network use. Both are mandatory because the administrator sets the policy and the process's own identity, root included, cannot override it — which is what makes them useful after every identity-based control has already been defeated.

    15. Map four TLS failures to their causes: expired, wrong SAN, unknown CA, mismatched key.
      Answer

      certificate has expired (error 10) — check notAfter and the local clock. Hostname mismatch (62) — the name is not in the SAN list; reissue. unable to get local issuer certificate (20), or tlsv1 alert unknown ca on the wire — the verifying side lacks the right CA file; the certificate may be perfect. key values mismatch — the certificate and key are not a pair, which fails at start-up rather than at connection time; compare the moduli.

    16. Why is --insecure a worse outcome than the error it silences?
      Answer

      Because it removes the identity check while keeping the encryption. The traffic is still unreadable to a passive observer and you now have no idea who is on the other end — a specific, diagnosable failure converted into a permanent, silent exposure. It is a ten-second diagnostic tool, never a fix.
