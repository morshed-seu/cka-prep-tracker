    I7 — Runtime architecture: containerd, shims, snapshotters

    The heaviest module on the track — plan two sittings. Everything above runc and below the kubelet, assembled: who runs, who stays running, what survives a daemon restart, and where each of the three on-disk stores physically is.

    Every module so far handed you one piece. I2 gave you the work order, I3 the contractor who reads it, I4 the flat-pack kit, I5 the warehouse it ships from, I6 the factory that packs it. containerd is the building-services company that employs all of them — and this is the module where the pieces stop being separate. By the end, nothing on a node's container layer is opaque to you, including every object crictl and kubectl politely hide.

    • Explain what survives a containerd restart and why — well enough to convince a sceptical colleague in three sentences.
    • Separate containerd's nouns that people use interchangeably: namespaces, containers, tasks, images, plugins.
    • Navigate all three on-disk stores — content, snapshotter, metadata — and say which can be rebuilt and which cannot.
    • Use leases to stop the garbage collector deleting work you are not finished with.
    • Talk to containerd directly: the socket and what access to it is worth, the gRPC surface, the event stream, and a client of your own.

    I2, I3, I4, I5 — the bundle, the runtime you drive by hand, the image format, and somewhere to pull from. This is the first module that needs all four at once, because containerd is precisely the thing that holds them together.

    The process tree

    I7.1

    Where did runc go, and who is the workload's parent?

    Why it matters

    Everyone who runs containers eventually draws the process tree on a whiteboard, and almost everyone draws it wrong. The wrong picture — containerd as the parent of everything, with runc sitting alongside the workload babysitting it — makes two very common node incidents unexplainable: why restarting containerd does not kill your pods, and why ps on a busy node never shows a single runc. Draw the tree once from a live machine and both stop being mysteries.

    The concept

    In I3.5 you watched runc create return to your prompt while the container stayed up, and you learned why: runc is a contractor. It arrives with the work order, builds the namespaces, pivots the root, hands the job to the workload, and leaves. Nothing about that changes when containerd is driving instead of you. So the question I3 planted — if runc leaves, who holds the door open? — has to have an answer, and the answer is a fourth process that most diagrams omit entirely.

    That process is the shim, containerd-shim-runc-v2. It is the on-site foreman: the contractor finishes and drives away, but somebody has to stay in the building, keep the phone line open and sign for the work. Concretely, the shim holds three things nobody else can:

    • The workload's stdio. Something must be on the other end of the container's stdout pipe, or of its pty for an interactive container. If containerd held that end, stopping containerd would close the pipe under a running workload.
    • The exit status. On Linux only a process's parent can reap it and read its exit code. Whoever is to report "container exited 137" must be the parent — and must still be alive when it happens.
    • The identity of the container while containerd is not running at all.

    Now the part that surprises people. The shim is the workload's parent, but the shim's own parent is PID 1 — systemd — not containerd. containerd starts the shim detached, so it is immediately re-parented to init. That is deliberate, and it is the whole trick: because containerd is never an ancestor of anything that matters, containerd can die, be upgraded and come back without a single workload noticing. You will prove exactly that in I7.3.

    So the lineage of who started whom is containerd → shim → workload, but the live ancestry you see in ps is systemd → shim → workload. Both pictures are true; they answer different questions, and conflating them is what produces the wrong whiteboard drawing.

    containerdstarts, detachedshimfork/execruncexitsworkload

    Read that as a timeline, not as a family tree: only the shim and the workload are still alive by the time you type ps.

    containerd's own runtime-v2 documentation is explicit that containerd does not run the container itself — it talks to something that outlives the call:

    However, containerd itself does not actually directly invoke the runtime to start the container. Instead it expects to invoke the runtime, which will expose a socket - Unix-domain on Unix-like systems, named pipe on Windows - and listen for container commands via ttRPC over that socket.

    and that the shim, not containerd, is what calls runc:

    The shim then invokes the actual runc binary, passing it the container configuration, and the runc binary does the actual work of starting the container.
    containerd runtime v2 — docs/runtime-v2.md
    Lab

      PID=$(sudo ctr task ls | grep '^demo ' | awk '{print $2}')

  54899   54876 sleep           sleep 600

    PID    PPID COMMAND         COMMAND
  54876       1 containerd-shim /usr/local/bin/containerd-shim-runc-v2 -namespace default -id demo -address /run/containerd/containerd.sock

      The workload's parent is the shim, and the shim's parent is 1.

    3. Ask pstree for the same thing, and notice which process is not in the chain. 
      pstree -aps $PID
      systemd,1 --system --deserialize=88
  `-containerd-shim,54876 -namespace default -id demo -address /run/containerd/containerd.sock
      `-sleep,54899 600

      containerd — PID 2805 on this box — appears nowhere in the workload's ancestry.

    4. Check the other direction: does containerd have any shim children at all? 
      pstree -ap $(pgrep -x containerd) | grep -c shim
      0
    5. Now answer I3's question directly. 
      pgrep -a -x runc || echo "no runc process exists"
      no runc process exists

      There is a container running, and there is no runc anywhere on the machine.

    Verify

    You can draw the tree from memory and defend every edge: the workload's parent is a shim; the shim's parent is init; containerd is an ancestor of nothing; and runc is a process that existed for a few milliseconds at creation time and has not existed since.

    Gotchas
    • ctr run -d --rm is rejected outright — ctr: flags --detach and --rm cannot be specified together. --rm means "delete the container when the task exits", which requires ctr to still be attached and watching. Detach and you own the cleanup.
    • "The shim is containerd's child" is the single most common wrong belief here, and it survives because the lineage diagram in every blog post looks like a process tree. Check PPID on a real machine before you argue about it.
    • A missing runc in ps is not evidence that something is wrong. On a node with a hundred pods, seeing zero runc processes is the healthy state. Seeing several stuck ones is the interesting case — that is a container wedged mid-creation, not a container running.
    • --forest will not rescue the wrong mental model. ps -ef --forest shows the same re-parented layout; it just makes it easier to misread, because the shim appears at top level next to other system daemons rather than under containerd.

    This is the tree behind W1.20 — kubelet → containerd → shim → runc, and it is why that arrow diagram must be read as a call chain rather than a ps hierarchy. On a real node the kubelet is a child of systemd, containerd is a child of systemd, and every shim is also a child of systemd — three independent trees, coupled only by sockets. When W6.13 asks you to narrate a node's death timeline, this is the structure that decides what dies in what order.

    Docs: search containerd's docs for runtime-v2 (the shim contract and its flow diagram), and ps(1) for --forest and the ppid output column. On the Kubernetes side, "container runtime interface" is the page that draws the same chain one layer up.

    I7.2

    The shim's directory, which is also the bundle

    Why it matters

    The shim is not just a process — it is a process with a directory, and that directory is where a stuck container's evidence lives. When ctr hangs, when a pod will not terminate, when you need to know what a running container was actually configured with rather than what its manifest claims, this is where you look. It is also the moment the whole track joins up: the shim's working directory turns out to be the OCI bundle you hand-wrote in I2.

    The concept

    Every task gets a directory under /run/containerd/io.containerd.runtime.v2.task/<namespace>/<id>/. The path encodes three things you now know how to read: io.containerd.runtime.v2 is the plugin that owns it (I7.8), the namespace is containerd's own tenancy boundary (I7.5), and the id is the container's name.

    Because it lives under /run, which is a tmpfs, the whole thing evaporates on reboot — correctly, since none of it describes anything that survives a reboot anyway.

    What is inside:

    FileWhat it is for
    config.jsonThe OCI runtime spec — literally the document you wrote by hand in I2.2, generated for you from the image config. ociVersion 1.3.0, the same one runc --version claims.
    rootfs/The mounted root filesystem — the snapshotter's overlay stack, mounted here (I7.11).
    init.pidThe workload's PID as plain text, so state can be rebuilt from disk after containerd restarts.
    bootstrap.jsonThe shim's ttrpc socket address — how containerd finds this shim again.
    logA named pipe the shim writes to and containerd drains into its journal.
    shim-binary-pathWhich shim binary owns this task, so a later delete uses the same one.
    options.jsonRuntime options passed in CreateTaskRequest — {} when you accept every default.
    workA symlink to the task's persistent state under /var/lib/containerd/.

    Two things here have changed and the internet has not caught up. Older guides tell you to cat a file called address to find the shim's socket. On containerd 2.3.3 there is no address file — that information moved into bootstrap.json, which also records the protocol version and names ttrpc explicitly. And the socket itself is no longer an abstract-namespace address: it is a real path under /run/containerd/s/, named by a hash, reached through the s symlink in the task directory.

    On the "one shim per container" question, be careful — the popular phrasing is a simplification of something the shim gets to decide for itself. With ctr, one container does get one shim. Under Kubernetes it is one shim per pod, with the pod's containers grouped underneath, which is why ps on a node shows far fewer shims than containers.

    The grouping is not containerd's rule at all — the documentation hands the decision to the shim:

    containerd does not know or care about whether the shim to container relationship is one-to-one, or one-to-many. It is entirely up to the shim to decide.

    and then names the Kubernetes case exactly:

    In practice, this means that containers launched by Kubernetes, that are part of the same Kubernetes pod, are handled by a single shim, grouping on the io.kubernetes.cri.sandbox-id label set by the CRI plugin.
    containerd runtime v2 — docs/runtime-v2.md

    Gotchas
    • cat or tail on log hangs your terminal. It is a FIFO whose reader is containerd; opening it for reading as a second consumer just blocks. The shim's log output is already in the journal — use journalctl -u containerd instead. This one costs people a full session timeout the first time.
    • There is no address file on containerd 2.x. Any runbook that says cat .../address was written against 1.x. Read bootstrap.json.
    • "One shim per container" is only true outside Kubernetes. If you count shims on a node and compare against container count, expect them to differ by design — that is pod grouping, not a leak.
    • Everything here is on tmpfs. Do not plan to post-mortem a crashed node by reading /run/containerd after a reboot; it is gone. The durable half is the work symlink's target under /var/lib/containerd.

    The pod-grouping rule above is the mechanism behind W1.21 — the pause container: the sandbox is what the shim is grouped around, and the pause process is what holds the pod's namespaces open while individual containers come and go. When W6.2 sends you hunting for logs below kubectl logs, the shim's FIFO into the containerd journal is the rung you are stepping onto.

    Docs: containerd's runtime-v2 doc for the shim lifecycle and the CreateTaskRequest options, and ss(8) for -x (unix sockets) and -p (owning process). For the FIFO behaviour, fifo(7).

    I7.3

    Restart the daemon, keep the containers

    Why it matters

    This is the single most reassuring fact about a Kubernetes node, and the one operators most often refuse to believe until they have watched it: you can restart containerd under running workloads and nothing dies. Not "usually survives", not "restarts quickly" — the workload processes are not signalled at all. Upgrading a container runtime on a production node is a routine operation because of this, and knowing it turns a scary maintenance window into a boring one.

    The concept

    You already have every piece of the explanation from I7.1 and I7.2; this checkpoint just makes you assemble it.

    containerd is not in the workload's ancestry, so killing it orphans nothing. The shim is the parent, the shim is a child of init, and the shim keeps holding the stdio, the pty and the right to reap. Meanwhile everything containerd needs in order to recognise the container again is on disk rather than in memory: the metadata store has the container record (I7.12), the task directory has init.pid, and bootstrap.json has the socket to dial. So a fresh containerd walks the task directories, reconnects to each shim over ttrpc, and rebuilds its view of the world from state it did not create.

    This is the same idea as the reconciliation loop from B13.12, applied to a daemon's own memory: containerd does not remember what is running, it re-derives it. Anything that can be re-derived can be lost safely.

    The three-sentence version for a colleague, which the checkpoint asks you to practise:

    Containerd isn't the parent of your container — a shim process is, and the shim's parent is init. Containerd only talks to that shim over a socket, and it writes down where the socket is, so when it comes back it just reconnects. Nothing ever signalled your process, so there was nothing for it to survive.

    The shim's exit-and-listen dance in the documented flow is exactly what makes this possible — the process that returns the socket address is not the process that keeps it:

    if new, the shim:
    1. creates a new process to listen on a socket for ttRPC commands from containerd
    2. returns the address to that socket to containerd
    3. exits
    containerd runtime v2 — docs/runtime-v2.md
    Lab

    3. Check the workload and the shim.

      ps -o pid,etime,args -p $PID

      Two and a half minutes of continuous uptime across a daemon restart that happened seconds ago.

    Verify

    You have watched containerd's PID change while the workload's PID, start time and elapsed time did not, and you can give the three-sentence explanation without reading it off the page.

    Gotchas
    • This does not extend to killing the shim. The shim is load-bearing in a way containerd is not; kill it and you get the orphan described in I7.18. "The runtime is restartable" is a statement about the daemon only.
    • Events are lost, not queued. If a container exits during the restart window, the exit is delivered when containerd reconnects — but anything watching ctr events (I7.15) simply misses the gap. Clients that assume an unbroken event stream will drift.
    • An upgrade that changes the shim binary does not upgrade running shims. Existing containers keep the old shim — shim-binary-path records which one — until they are recreated. A node can legitimately be running two shim versions at once after an upgrade.
    • Restarting the kubelet is a different question with a different answer, and so is restarting containerd on a node where the kubelet is watching. The kubelet may decide to re-sync pods for its own reasons; that is a Kubernetes-level behaviour layered on top of this Linux-level one.

    This is why runtime upgrades appear in node-maintenance runbooks without a drain step, and it is the fact that makes W6.11's kubelet fault-hunting tractable: when you restart containerd while chasing a fault, you are not adding a second incident. It also sharpens W1.20 — the kubelet's connection to containerd is a gRPC client to a restartable server, so "containerd is down" and "the containers are down" are genuinely independent conditions on a node.

    Docs: systemctl(1) for restart versus reload, and ps(1) for the lstart and etime columns — the two that make "it never restarted" provable rather than asserted.

    I7.4

    Asking the layer below containerd

    Why it matters

    Every layer in this stack keeps its own records, and when they disagree you need to be able to ask each one separately. Being able to query runc directly — underneath containerd, underneath the shim — is what lets you tell "containerd has lost track of a container" apart from "the container is genuinely gone". That distinction is the whole of the orphan drill in I7.18.

    The concept

    In I3.9 you learned that runc keeps its state under a root directory, /run/runc by default, and that --root points it elsewhere. containerd uses that flag: each containerd namespace gets its own runc state directory under /run/containerd/runc/<namespace>. So on this box there is a default tree and a buildkit tree, because I6's builder was a separate tenant.

    The consequence is that you can run runc list against containerd's own state and see containerd's containers — with no daemon involved and no socket to dial. You are reading the same state.json you dissected in I3, written by the same runc, just in a directory containerd chose.

    And now the join that makes the module click. The BUNDLE column of that listing points at /run/containerd/io.containerd.runtime.v2.task/default/demo — the shim's directory from I7.2 is the runc bundle. They were never two things. containerd assembles a bundle in the place the shim will work from, and the shim hands that path to runc exactly as you handed a path to runc by hand in I3.

    ctrgRPCcontainerdttrpcshimargv + bundle pathrunc

    Four interfaces, three of them sockets, and the last one a directory on disk.

    The runtime spec defines the bundle as precisely this pairing of a config and a rootfs in one directory — which is why the shim's working directory can be the bundle without anything special being arranged:

    This bundle is the directory structure that is written to disk or transferred over the network. The bundle contains all the information needed to load and run a container.
    OCI Runtime Specification v1.3.0 — bundle.md

    You can list containerd's containers without containerd, name the flag that makes it possible, and explain why the shim's working directory and the OCI bundle are the same path.

    Gotchas
    • Forgetting --root gives you an empty list, not an error. Plain sudo runc list reads /run/runc, which containerd never writes to, so it truthfully reports nothing. That empty output has convinced more than one person their containers had vanished.
    • The namespace is part of the path. On a Kubernetes node the containers are under /run/containerd/runc/k8s.io, and --root /run/containerd/runc/default will again show you nothing at all. Same trap as ctr -n in I7.5, one layer down.
    • Do not write at this layer. runc delete or runc kill against containerd's root works, and leaves containerd holding a task record for something that no longer exists. Reading is diagnosis; writing is how you manufacture the fault in I7.18.
    • OWNER says root, not the container's user. It is who created the container, not who runs inside it — process.user.uid in config.json is the field you want for that.

    On an exam node this is the deepest rung of W6.2's fallback ladder: when kubectl is unavailable and crictl is also unhappy, runc --root /run/containerd/runc/k8s.io list still answers, because it reads files rather than talking to a daemon. It is also the concrete form of the bundle that W1.23 hints at when it walks you through /var/lib/kubelet.

    Docs: runc --help for --root, and the OCI runtime spec's bundle.md for the two-item definition of a bundle. Then runtime.md's state section for the fields runc state prints.

    I7.5

    The word that has two meanings, and the flag everyone forgets

    Why it matters

    This one checkpoint will save you an hour of confusion on a real node, and it is the single most common way people conclude that a Kubernetes node "has no images". You ssh in, run ctr images ls, get an empty table, and start diagnosing a problem that does not exist — because every pod's image is sitting in a different containerd namespace and ctr defaulted you into the empty one.

    The concept

    Containerd namespaces have nothing to do with Linux namespaces. Same word, unrelated idea, and the collision is unfortunate enough that it is worth saying out loud before anything else. A Linux namespace (B6.1) isolates a process's view of the kernel. A containerd namespace partitions the daemon's own bookkeeping — its containers, its image names, its snapshots — so that several clients can share one daemon without stepping on each other's names.

    The building-services analogy holds: containerd is one company serving the whole building, and a namespace is a client account. Two tenants can each have a container called web and nothing collides, because the account is part of the key.

    In practice you will meet three:

    • default — where ctr and nerdctl put things when you do not say otherwise.
    • k8s.io — where the CRI plugin puts everything the kubelet creates. On a node running Kubernetes, this is the only namespace you care about.
    • buildkit — I6's builder kept its own account, which is why I6.8's nerdctl run on a buildctl-built image decided the image was remote and tried to pull it.

    Now the subtle half, which matters more than the reflex. Namespaces separate names and metadata, not bytes. The content store on disk is one directory with no namespace anywhere in its path, and blobs in it are addressed by digest. So ctr -n fresh content ls genuinely shows zero blobs, while a pull into that namespace writes no new files at all — it only records that this account now references digests already present. You will measure exactly that below.

    That resolves an apparent contradiction from I5.15: a fresh containerd namespace is not a fresh node. If you are trying to reproduce a pull failure by switching namespaces, you are not clearing the cache — you are only clearing the index of it.

    Finally, and importantly: a namespace is not a security boundary. Any client that can reach the socket can name any namespace it likes.

    containerd's own documentation is unusually direct about both halves — the sharing and the non-security:

    Underlying image content is still shared via content addresses but image names and metadata are separate per namespace.
    It is important to note that namespaces, as implemented, is an administrative construct that is not meant to be used as a security feature. It is trivial for clients to switch namespaces.
    containerd Namespaces and Multi-Tenancy — docs/namespaces.md

    Gotchas
    • ctr invents the namespace you name. A typo — -n k8s.oi — produces an empty table and exit 0, not an error. Every "the node has no images" incident starts here.
    • crictl does not have this problem, because it talks CRI and CRI is hard-wired to k8s.io. If crictl images shows images and ctr images ls shows none, you have not found a bug; you have found the flag you forgot.
    • Namespaces are not isolation. Do not use them to separate tenants who should not see each other's containers — anyone with the socket can pass any namespace. The socket is the real boundary, and I7.14 shows what it is worth.
    • Switching namespaces does not give you a clean cache. If you need a genuinely cold pull, remove the blobs (and let the collector run) rather than moving accounts — see I7.13.
    • A namespace cannot be called version, a real reserved-word bug in containerd's API path. Harmless, but it will confuse you for ten minutes if you hit it.

    This is the flag that makes W6.2's log-hunting ladder work at all: everything the kubelet created lives in k8s.io, so ctr -n k8s.io containers ls is the raw view underneath crictl ps. It is also the reason the pods you see in W1.20's chain are invisible to a plain ctr — one flag stands between you and the entire cluster's container layer.

    Docs: containerd's namespaces.md for the multi-tenancy model and the explicit "not a security feature" warning; ctr namespace --help for create/remove/label. On the Kubernetes side, search for "crictl" — its whole reason for existing is that it never lets you pick the wrong namespace.

    I7.6

    A record and a process are not the same object

    Why it matters

    "Container" is used for two different objects, and containerd is the layer where the difference becomes operationally real. Once you can say which of the two you are looking at, a whole class of confusing states stops being confusing: a container that exists but is not running, a stopped thing that still holds disk, and the delete that refuses with an error people find baffling.

    The concept

    In containerd:

    • A container is pure metadata — an OCI spec, an image reference, a snapshot key, some labels. It is a record in the database. Nothing is executing.
    • A task is a running process created from that record. It has a PID. It is the thing the shim is holding.

    The separation is not bureaucracy; it buys something specific. Because the container record already holds the resolved spec and the prepared snapshot, stopping and starting a workload does not re-resolve the image, re-check the registry or re-prepare the filesystem. The expensive work is done once at container-create time, and task start is cheap.

    If that sounds familiar, it should. It is exactly Kubernetes' own split between a container's definition in the pod spec and the instance that carries a restart count. A pod restarting in place is a new task against an unchanged container record, which is why the restart is fast and why the image is not pulled again.

    The state machine has one edge worth knowing precisely, because the tracker's phrasing of it turns out to be over-simplified. Killing a task does not remove it: the task goes to STOPPED and keeps its record and its old PID, so containerd can still be asked for its exit code. From there:

    • Deleting the container while its task is RUNNING fails: cannot delete a non stopped container.
    • Deleting the container while its task is STOPPED succeeds, and takes the task record with it — no separate ctr task rm is required.

    And the leak this sets up, which is the drill in I7.18: delete the task and forget the container, and the container record keeps referencing its snapshot forever. The process is gone, the disk is not. Nothing in ctr task ls will ever show it to you again.

    The distinction is visible in the API surface itself — containerd exposes them as separate gRPC services with separate lifecycles, containerd.services.containers.v1.Containers and containerd.services.tasks.v1.Tasks. The runtime spec draws the same line one layer down, where a container exists in the created state before anything runs:

    created : the runtime has finished the create operation (after the create operation is called), and the container process has neither exited nor executed the user-specified program
    OCI Runtime Specification v1.3.0 — runtime.md
    Lab
    1. Create a container without starting anything, then ask both questions. 
      sudo ctr container create docker.io/library/alpine:3.21 split sleep 300
sudo ctr container ls | grep -E 'CONTAINER|split'
sudo ctr task ls
      CONTAINER   IMAGE                           RUNTIME
split       docker.io/library/alpine:3.21   io.containerd.runc.v2

TASK   PID   STATUS

      The container exists. There is no task, no PID, and no shim.

    2. Start the task and watch a PID appear against the same name. 
      sudo ctr task start -d split
sudo ctr task ls | grep -E 'TASK|split'
      TASK    PID     STATUS
split   57139   RUNNING
    3. Kill the process. The interesting part is what does not disappear. 
      sudo ctr task kill -s SIGKILL split
sudo ctr task ls | grep split
sudo ctr container ls | grep split
      split   57139   STOPPED
split   docker.io/library/alpine:3.21   io.containerd.runc.v2

      The task record survives with its old PID, and the container is untouched.

    4. Now the error. Recreate a running task and try to delete the container underneath it. 
      sudo ctr task start -d split
sudo ctr container rm split
      ctr: cannot delete a non stopped container: {running 0 0001-01-01 00:00:00 +0000 UTC}
    5. Kill it and try again — and notice you do not need ctr task rm at all. 
      sudo ctr task kill -s SIGKILL split; sleep 1
sudo ctr container rm split; echo "exit=$?"
sudo ctr container ls | grep split || echo "container gone"
sudo ctr task ls | grep split || echo "task record gone too"
      exit=0
container gone
task record gone too
    Verify

    Shown a name, you can say whether it refers to a record or a process, predict whether ctr container rm will succeed, and describe the leak that deleting a task without its container produces.

    Gotchas
    • "Delete in the wrong order and read the error" only works while the task is running. A stopped task is removed together with its container in one step, exit 0. If you expected an error and did not get one, your task was already stopped — that is not a version difference.
    • A STOPPED task still lists a PID. That number refers to a process that no longer exists; do not kill it. Compare I3.9, where runc state reports pid: 0 for the same situation — two layers, two conventions, and only one of them is safe to feed to kill.
    • The disk leak is silent by construction. ctr task ls cannot show you a container with no task, so the leaked snapshot is invisible to the command people check. ctr container ls and ctr snapshot ls are the ones that find it.
    • ctr run hides all of this by doing create + start + attach in one call, which is why the distinction stays invisible until the day it matters.

    This is the mechanism under W6.16's CrashLoopBackOff work: kubectl logs --previous and lastState.terminated.exitCode are readable precisely because the stopped task's record — and its exit code — outlive the process. It is also why a pod with a high restart count has not re-pulled its image: the container record, snapshot and all, was never deleted between attempts.

    Docs: ctr container --help and ctr task --help — read them side by side, the verb lists are deliberately different. Then the OCI runtime spec's runtime.md for the four container states, and the Kubernetes API reference for containerStatuses[].lastState.

    I7.7

    An image is a name pointing at one digest

    Why it matters

    Once you have seen that an image is just a name pointing at one digest, three otherwise-puzzling behaviours become obvious at a glance: why ctr images rm can free zero bytes, why two tags for the same image cost one copy, and why a node can be holding an image perfectly well while ctr images ls shows nothing you recognise. This is also the checkpoint where I4 and I5's work stops being an exercise and becomes the thing that is actually on disk.

    The concept

    Strip away the tooling and containerd's image model is one sentence: an image is a name with a target descriptor. The descriptor is a media type, a size and a digest. That is all the image record holds.

    Everything else is reachable by walking from that digest, exactly as pull.py walked it in I5.14: the digest fetches an index, the index names per-platform manifests, a manifest names a config and a list of layers. containerd stores all of those as undifferentiated blobs in the content store — it does not have an "image file" anywhere, because there is no such thing.

    Three consequences follow immediately, and they are the ones that catch people out:

    • Tagging is free. A second name pointing at the same digest adds one row and zero bytes.
    • ctr images rm deletes a name. The blobs stay until nothing references them and the garbage collector runs (I7.13). Deleting an image to free disk and watching df not move is the expected outcome, not a bug.
    • Content can be present without a recognisable name. Everything the kubelet pulls by digest is there by digest; blobs from a build or a half-finished pull have no name at all.

    The join to I4 is worth doing by hand once, and it is the lab below: take the digest out of ctr images ls, pull that blob out of the content store, and find yourself reading the same index JSON your own parser printed — same media type, same 16 entries, same eight unknown/unknown attestation manifests you learned to skip in I4.6.

    One detail to notice in passing, because I7.13 is built on it: the blob listing carries containerd.io/gc.ref.content.* labels. Those are the reference graph, written down. The index blob for a multi-platform image carries one gc.ref label per manifest it points at — sixteen of them for alpine:3.21 — and that is literally how the collector knows the manifests are still wanted.

    containerd stores the relationships as labels because the blobs themselves are opaque to it — the client, not the daemon, understands what an image is:

    an OCI image has a manifest which references a config file and layer tars. These resources are stored in containerd as generic blobs, it is the client that understands the relationships between these blobs and sets them up using labels on the content resources.
    containerd Garbage Collection — docs/garbage-collection.md

    You can go from an image name to its index JSON in two commands without a registry, and you can predict — correctly — that removing an image frees no space until the collector runs.

    Gotchas
    • ctr images rm does not reclaim disk. If you are firefighting a full /var, this command will look like it worked and change nothing. You want I7.13's collector.
    • SIZE in ctr images ls is not disk usage. It is the compressed size from the manifest. What the image actually costs on disk is the unpacked snapshot, which is larger, plus blobs shared with other images, which are not yours alone.
    • The digest in that column is the index digest, not the manifest digest for your platform. If you are matching against something a registry told you, check which of the two you have — I5.4's point about tags, digests and platforms applies here unchanged.
    • ctr content get writes raw bytes to stdout. Pipe it. Doing it to a terminal with a layer digest instead of a manifest digest dumps a gzip stream into your session.

    This is why W6.17's image-failure triage asks you to distinguish "the name did not resolve" from "the bytes are not here": they are separate stores with separate failure modes. It also explains an incident shape from I5.15 — a manifest whose layer blob is missing is invisible on any node that already holds that layer, because the reference and the content are checked in different places.

    Docs: containerd's content-flow.md for how blobs enter the store, and garbage-collection.md for the gc.ref.content label format. Cross-check against the OCI image spec's descriptor.md — the three fields in that image row are precisely a descriptor.

    I7.8

    Sixty-eight plugins in one binary, and a config file that isn't there

    Why it matters

    ctr plugins ls is the fastest triage command on a container host, and almost nobody knows it exists. It tells you, in one screen, which of containerd's ~68 internal components loaded, which were skipped, and which failed — so "containerd is up but nothing works" resolves in seconds instead of a journal-reading session. This checkpoint also settles what containerd's configuration file actually is, which is not what most people assume.

    The concept

    containerd is one binary, but internally it is a registry of plugins that register themselves at start-up and declare dependencies on each other. "Plugin" here almost never means a file you installed — the snapshotters, the differs, the gRPC services and the CRI implementation are all compiled in. What the plugin model buys is ordering (a service starts only after what it needs) and per-component failure (a broken CRI configuration leaves one plugin in error state while the rest of the daemon runs happily).

    That last property is the reason to look. A daemon that is "up" can be missing exactly the piece you need, and the plugin table says which.

    Each plugin has a type and an id. On this box there are 68 of them, and the type histogram is a fair description of what containerd is:

    TypeCountWhat they are
    io.containerd.grpc.v118The API services clients call — containers, tasks, images, content, leases, events.
    io.containerd.service.v18The implementations those gRPC endpoints wrap.
    io.containerd.snapshotter.v17overlayfs, native, btrfs, zfs, devmapper, blockfile, erofs — only two loaded here.
    io.containerd.cri.v12runtime and images — the split that replaced 1.x's single CRI plugin.
    the rest33servers, differs, metrics, tracing, ttrpc, transfer, warnings.

    A skipped plugin is not a broken one. btrfs, zfs and devmapper report skip on this box because the filesystems they need are not present. That is normal and expected on every ordinary node. What you are hunting for is error.

    Now three corrections to what you will read elsewhere, all confirmed on this machine.

    First: the config header is version = 4, not 3. containerd 2.0 moved 2→3 and 2.3 moved 3→4. Any guide — including this repo's own tracker text for this checkpoint — that tells you to confirm version = 3 was written against an earlier 2.x.

    Second: there may be no config file at all. On this box /etc/containerd/ contains only the certs.d directory from I5.13's mirror work — config.toml does not exist. containerd runs entirely on compiled-in defaults, and that is a perfectly normal production configuration. containerd config default prints what it would use; the file, when present, holds overrides only.

    Third: the CRI plugin path is io.containerd.cri.v1.runtime (and …v1.images), not 1.x's io.containerd.grpc.v1.cri. As I5.13 found the hard way, config copied from a 1.7-era post lands under a plugin key nothing reads — and is silently ignored rather than rejected, which is the worst possible failure mode. Note that a plugin named io.containerd.grpc.v1 cri still exists and still reports ok; it is the gRPC endpoint, not the configuration path.

    containerd's plugin documentation frames the whole daemon this way — extensibility through interfaces, with as little as possible done by the daemon itself:

    containerd supports extending its functionality using most of its defined interfaces. This includes using a customized runtime, snapshotter, content store, and even adding gRPC interfaces.

    which is also why so much of what you think of as "containerd behaviour" is really client behaviour — the labels in I7.7, for instance:

    containerd has a smart client architecture, meaning any functionality which is not required by the daemon is done by the client. This includes most high level interactions such as creating a container's specification, interacting with an image registry, or loading an image from tar.
    containerd Plugins — docs/PLUGINS.md

    • skip is fine, error is not. Do not go installing btrfs tooling because a plugin says skip. Filter on error.
    • containerd config default is not your config, and on a box with no config.toml it is also not a file anyone reads. It is a printout of the built-in defaults, useful as a template and as documentation. containerd config dump is the one that shows the merged, effective result.

    Every kubelet-to-container problem passes through io.containerd.cri.v1.runtime, so on a NotReady node from W6.10's ladder this table is the two-second check that says whether CRI even loaded. The SystemdCgroup setting that W1.19 depends on lives under that same key — and if you set it under the 1.x key on a 2.x daemon, the kubelet will simply keep disagreeing with containerd about cgroups while every file looks correct.

    Docs: containerd's PLUGINS.md for the registry model and docs/cri/config.md for the CRI keys. Then containerd config --help — note default versus dump, which answer different questions.
