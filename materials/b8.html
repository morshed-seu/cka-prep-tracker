    B8 — Networking I: the real network

    Almost everything people find hard about "Kubernetes networking" is really ordinary networking they never got to learn slowly. A packet leaving a pod obeys the exact same rules as a packet leaving your laptop: it needs a link to travel on, an address to aim at, a route to choose the door, a firewall that might stop it, and a program at the far end actually listening. This module teaches those five things as a fixed diagnostic ladder — link → address → route → filter → listener — that you climb the same way every single time, on any machine, for the rest of your career. Once the ladder is a reflex, "the network is broken" stops being a feeling and becomes a five-step checklist that ends at the exact rung that's lying to you.

    We build it bottom-up. First layers and addresses: the four-layer model as a bisection tool, MAC addresses and ARP (how a machine finds its neighbour on the wire), CIDR math you can do in your head, and reading your own interfaces. Then routing: how the kernel picks an exit, longest-prefix match, and ip route get — the oracle that tells you the decision instead of making you guess. Then transport: one TCP connection from handshake to teardown, the connection states you'll actually see, UDP, the 4-tuple that lets one port serve thousands, and the difference between a port that's listening and one that's connected. Then observing: reading tcpdump and curl -v without fear, typing an HTTP request by hand, and committing the five-rung ladder to muscle memory. You finish by tracing one real curl end to end and diagnosing three faults by climbing the ladder rather than guessing.

    Checkpoints18 Hours~6 PrerequisitesB1, B3
    • Use the four layers (link, network, transport, application) as a bisection ladder — prove one layer, exonerate everything below it.
    • Explain MAC addresses and ARP, read the neighbour table with ip neigh, and recognise a link-layer answer to an apparent IP problem.
    • Do CIDR math in your head for /8, /16, /24, /26, /30: host count, network, broadcast, usable range.
    • Read ip link and ip addr, distinguish UP from LOWER_UP, and treat addresses as attachable properties, not identities.
    • Read a routing table as ordered rules, apply longest-prefix match, and use ip route get to ask the kernel which route wins.
    • State exactly what ping and traceroute prove — and don't prove — and why "ping works but nothing else does" is a filter, not a paradox.
    • Trace one TCP connection through SYN/SYN-ACK/ACK, data, and FIN teardown, and distinguish refused (instant RST) from filtered (hang).
    • Read the TCP states in ss -tan and know what each accuses — especially CLOSE-WAIT (your bug) vs TIME-WAIT (normal).
    • Contrast UDP with TCP and explain why DNS, VXLAN and metrics agents choose it.
    • Name the 4-tuple that identifies a connection and why one server port serves thousands of clients.
    • Separate listening from established with ss -ltnp/ss -tnp, and read a 127.0.0.1 vs 0.0.0.0 bind.
    • Read a tcpdump line and a curl -v trace as layered probes that name the failing layer.
    • Type an HTTP request by hand through nc and explain why Host: and the blank line matter.
    • Run the five-rung ladder (ip link → ip addr → ip route get → nft list ruleset → ss -ltnp) in order, every time, without improvising.
    • Trace one real curl end to end and diagnose an unreachable host, a wrong netmask, and an MTU black hole by climbing the ladder.

    B1 because you will live inside ip, ss and grep output, slicing and reading it constantly; B3 because a socket is a file descriptor (a listening server is a process holding an fd, which is why ss -ltnp can name the process), and one lab runs strace on curl to watch the syscalls a connection is made of. Everything runs on the throwaway sandbox VM (B0.1), never on the cluster — nothing here is dangerous, but you'll add and remove addresses and flush the ARP cache, so a snapshot (B0.9) keeps a clean baseline. The base image already has iproute2 (ip, ss) and curl; install the observation tools once up front — sudo apt-get install -y tcpdump traceroute bind9-dnsutils ipcalc netcat-openbsd — since net-tools (the old netstat/ifconfig) is deliberately absent on 24.04 and you should learn the modern tools anyway. Your primary interface is called ens3 on a typical Multipass VM; if ip -br link shows a different name, substitute it wherever a lab says ens3.

    Layers and addresses

    B8.1

    The four layers as a decision ladder, not exam trivia

    Why it matters

    The four-layer model gets taught as something to memorise for a test and then forget, which is exactly backwards. Its real value is as a debugging tool: every network question you will ever ask — "why can't this reach that?" — is really "which of four layers is lying to me?", and the layers give you a way to answer it by elimination instead of by guessing. Learn them as a ladder you climb, and network problems stop being mysterious.

    The concept

    Data crossing a network passes through four stacked concerns, each building on the one below. From the bottom:

    • Link — moving bits across one physical segment (a cable, a Wi-Fi cell, a virtual wire). Identities here are MAC addresses. Scope: this wire only.
    • Network — getting a packet between segments, across routers, to anywhere. Identities are IP addresses; the job is routing. Scope: the whole internetwork.
    • Transport — turning "packets to a host" into "a conversation with a program": ports pick which program, and TCP adds reliability (ordering, retransmission) while UDP doesn't. Scope: process-to-process.
    • Application — what the two programs actually say: HTTP, DNS, SSH. Scope: the meaning of the bytes.

    Layering exists so each level can be swapped without disturbing the others — the same TCP runs unchanged over fibre, Wi-Fi, or the virtual veth pair you'll build in B9. But the payoff for you is bisection: because each layer sits on the one below, if you prove a lower layer works, every layer beneath it is exonerated and you never have to think about it again. Can you ping the host (network layer works)? Then the cable and MAC resolution (link) are fine — stop checking them. This is why the troubleshooting ladder in B8.16 is climbed strictly bottom-up, and why "it's DNS" (the application layer) is only a legitimate conclusion after the three layers under DNS have been cleared. Guessing at the top first is the classic time-waster; the model's gift is a fixed order.

    link→network→transport→application· prove low ⇒ exonerate lower
    Lab
    1. See all four layers in one place, each with its own tool, for a single act of loading a web page. Run these and label which layer each answers. 
      multipass shell sandbox

    2. Now feel the bisection. Deliberately ask the wrong layer's question about a working host and a broken one, and watch which layer's tool changes its answer. A host that pings but won't serve HTTP has a working network layer and a failing transport/application layer. 
      ping -c1 example.com          # network layer: does the host answer at all?

    Verify

    Name the four layers bottom to top and the one identity or job each owns. (Link — MAC address, one segment; Network — IP address, routing between segments; Transport — ports + reliability, process to process; Application — the protocol's meaning, e.g. HTTP.) Then: you can ping a host but its web page won't load — which layers have you just proven work, and which is suspect? (Link and network work — ICMP echo made the round trip — so the fault is at transport or application: a closed/filtered port or a dead server, not the wire or the route.)

    Gotchas

    The famous seven-layer OSI model exists too, but for debugging real Linux/Kubernetes networks the four-layer split above (the TCP/IP model) is what maps to your tools — ip for link/network, ss/tcpdump for transport, curl/dig for application. Don't get tangled trying to place things in OSI's presentation/session layers; nobody debugging a pod does. Learn the four that have tools.

    Bisection only works if you actually climb in order and trust a passed rung. The universal mistake is to leap to the most interesting hypothesis ("must be a DNS problem") before clearing the boring layers under it, then spend an hour on DNS when the interface was down the whole time. A wrong guess doesn't just fail — it costs a full investigation. The discipline the layers give you is worth more than any single fact in them: lowest unproven layer first, always.

    This ladder is the entire mental model behind Kubernetes network debugging. When a pod "can't reach a Service," the fix is to walk the same layers: is the pod's veth up (link)? does it have an IP and the right routes (network)? can it open a TCP connection to the Service IP (transport)? is the target actually serving and are there ready endpoints (application)? Every Kubernetes networking chapter — pod networking, Services, DNS, NetworkPolicy — is one of these four layers wearing a Kubernetes costume, and the bisection habit you build here is exactly what the W6 troubleshooting flow formalises one level up.

    The two-rule network model and building a pod network by hand are W4.1–W4.2; the troubleshooting ladder reappears in W6.

For the model itself, any TCP/IP reference; the RFCs are RFC 1122 (host requirements) if you want the source.     B8.2

    The link layer: MAC addresses, ARP, and the neighbour table

    Why it matters

    Before a machine can send a packet to anyone on its local wire, it has to answer a physical question that has nothing to do with IP: "which actual card do I hand these bits to?" The answer is a MAC address, and the way a machine finds it is ARP. This is the bottom rung of the ladder, and skipping it is why people stare at correct-looking IP settings for an hour when the real problem is that two machines can't even find each other on the segment.

    The concept

    Every network interface has a MAC address — a 48-bit hardware address (like 52:54:00:a1:b2:c3) that identifies that one card on its local segment. IP addresses are for getting across the network; MAC addresses are for the final hop across one wire. So when your machine wants to send a packet to another IP on the same subnet, it must first translate that IP into the MAC address of the card that owns it. That translation is ARP (Address Resolution Protocol): the machine broadcasts "who has 192.168.1.1? tell me your MAC" to the entire local segment, and the owner replies with its MAC. The result is cached in the neighbour table (still often called the ARP cache) so it doesn't have to ask again for every packet.

    The one fact that makes this a debugging superpower: ARP is a broadcast to the local segment only — it never routes. Nothing carries an ARP request across a router. This is the physical meaning of "on the same subnet": two machines can ARP for each other only if each believes the other is local. And that's exactly why a wrong netmask makes two correctly-addressed machines invisible to each other — if A's mask says B is on a different subnet, A won't ARP for B at all; it hands the packet to its gateway instead, and the gateway may have no idea what to do with it. So a FAILED or missing neighbour entry is a link-layer answer to what looked like an IP problem. When you learn to read ip neigh, you can see this happen.

    need to send to 192.168.1.1→ ARP broadcast "who has it?" →reply: my MAC is 52:54:…→ cached inip neigh
    Lab
    1. Look at the neighbour table — the MACs your machine has already learned. Each line pairs a local IP with the MAC that answered for it, and a state. 
      multipass shell sandbox
ip neigh show
      10.191.62.1 dev ens3 lladdr 52:54:00:aa:bb:cc REACHABLE
# an IP on our segment (the gateway), its MAC, and a healthy state
    2. Watch ARP happen live. Flush the entry for the gateway, confirm it's gone, then send one ping and watch the table repopulate — that repopulation is an ARP request and reply. 
      GW=$(ip route | awk '/default/{print $3}')       # the gateway IP
sudo ip neigh flush dev ens3                       # forget all learned MACs
ip neigh show | grep "$GW" || echo 'gateway MAC: forgotten'
ping -c1 "$GW" >/dev/null                           # sending forces an ARP
ip neigh show | grep "$GW"                          # learned again
      gateway MAC: forgotten
10.191.62.1 dev ens3 lladdr 52:54:00:aa:bb:cc REACHABLE   ← re-learned by ARP
    3. See the states that accuse. A neighbour that can't be resolved shows FAILED — a link-layer verdict. Ask for a MAC that nobody owns on the segment and watch it fail. 
      ping -c1 -W1 10.191.62.199 >/dev/null 2>&1     # an unused IP on our subnet
ip neigh show 10.191.62.199
      10.191.62.199 dev ens3  FAILED              ← nobody answered ARP: link-layer dead end
    Verify

    What does ARP translate, and why can't an ARP request cross a router? (It translates a local IP address into the MAC address of the card that owns it; ARP is a broadcast scoped to one segment, and routers don't forward broadcasts — so ARP only resolves neighbours on the same subnet.) Then: two machines have correct IPs but one has a wrong netmask and they can't talk — explain in link-layer terms. (The machine with the wrong mask thinks the other is on a different subnet, so it never ARPs for it — it sends to the gateway instead — and the neighbour is never resolved: a link-layer failure caused by an addressing mistake.)

    Gotchas

    Neighbour states look like errors but mostly aren't: STALE just means "we haven't used this entry recently, we'll re-verify on next use" — it's normal and not a problem. The states that actually accuse are FAILED (ARP got no answer — the neighbour isn't there or can't be reached on this segment) and a persistently INCOMPLETE entry (a request went out and nothing has replied yet). Don't chase STALE; do investigate FAILED.

    ARP is IPv4's mechanism; IPv6 does the same job with a different protocol (Neighbour Discovery, using ICMPv6), but ip neigh shows both in the same table, so the tool and the mental model carry over. Also note MAC addresses are only meaningful on the local segment — once a packet crosses a router, the source and destination MACs are rewritten for the next hop while the IP addresses stay the same. That "IP is end-to-end, MAC is hop-by-hop" split is worth holding onto; it's why you can't identify a remote machine by MAC.

    Inside a node, pods reach each other and the outside world through exactly this machinery, just on virtual wires. Each pod's veth (B9) has a MAC, the node's bridge learns those MACs, and a pod ARPs for its gateway (the bridge or the node) before sending — you can watch the same ip neigh table fill on a node. The "wrong netmask ⇒ can't ARP ⇒ silent unreachability" failure has a direct Kubernetes analogue in a misconfigured pod CIDR or node subnet, where pods that look correctly addressed can't resolve each other's MACs across the fabric. Link-layer thinking is the floor under every CNI story in W4.

    Pod veths, MACs, and the node bridge are built by hand in W4.2 and located on a live node in W4.3.

    Docs

    man 8 ip-neighbour for the neighbour table, states, and flush; man 8 ip-link for reading a MAC (link/ether). man 7 arp for the protocol and the kernel's ARP cache behaviour. For the "same subnet = same ARP domain" idea, see the CIDR lesson next (B8.3). In the exam docs, this is assumed under cluster networking — no kubernetes.io page covers ARP directly.

    B8.3

    CIDR math in your head: /8, /16, /24, /26, /30

    Why it matters

    You will do subnet arithmetic constantly in Kubernetes without anyone asking you to "do subnetting" — the pod network is a /16 carved into a /24 per node, the Service range is a separate CIDR, and half of "pods can't reach X" is two ranges overlapping. Being able to look at 10.244.3.0/24 and instantly know its size and boundaries, in your head, is the difference between reasoning about a cluster's addressing and being mystified by it. It's a small skill with an enormous payoff.

    The concept

    An IP address is 32 bits. A CIDR like 10.244.3.0/24 splits those bits with a slash: the number after the slash is how many leading bits are the network part (the neighbourhood), and the rest are the host part (the house number on that street). So /24 means 24 network bits and 8 host bits. From the host-bit count, everything else follows:

    • Addresses in the block = 2(host bits). For /24: 28 = 256 addresses.
    • Usable hosts = that minus 2 — the first address (all host bits 0) is the network address and the last (all host bits 1) is the broadcast address, neither assignable to a machine. For /24: 254 usable.
    • Network address = the block's first address; broadcast = its last; gateway = conventionally the first usable (.1), though that's convention, not law.

    The five masks you'll actually meet, worth knowing cold:

    CIDRHost bitsAddressesUsableExample block → range
    /82416,777,21616,777,21410.0.0.0/8 → 10.0.0.1–10.255.255.254
    /161665,53665,53410.244.0.0/16 → 10.244.0.1–10.244.255.254
    /24825625410.244.3.0/24 → 10.244.3.1–10.244.3.254
    /2666462192.168.1.64/26 → 192.168.1.65–192.168.1.126
    /3024210.0.0.4/30 → 10.0.0.5–10.0.0.6 (point-to-point links)

    The one that trips people is the sub-/24 mask like /26, because the boundaries fall inside the last octet. The trick: a /26 has 64 addresses, so blocks start at multiples of 64 — .0, .64, .128, .192. An address like 192.168.1.64/26 is therefore a network address (start of the .64–.127 block), its broadcast is .127, and its usable range is .65–.126. "Block size = 256 minus the mask's last octet" (256 − 192 = 64) is the fastest mental shortcut.

      ipcalc 10.244.0.0/16 | grep -E 'Hosts|Network'

    Without a tool: how many usable hosts in a /26, and what are the network and broadcast addresses of 192.168.1.64/26? (62 usable; network 192.168.1.64, broadcast 192.168.1.127, usable .65–.126.) Then: why is the usable count always the address count minus 2? (The first address — all host bits zero — is the network identifier and the last — all host bits one — is the broadcast address; neither can be assigned to a host.)

    Gotchas

    The "minus 2" rule is an IPv4-subnet convention, not a universal law, and two modern cases break it. A /31 (RFC 3021) is used for point-to-point links with both addresses usable (no room for a broadcast on a two-host link), and a /32 is a single host route (one address, itself). Kubernetes leans on /32s heavily — a pod IP or a Service ClusterIP often appears as a /32 route. So don't blindly subtract 2 for those; the rule is for ordinary /8–/30 subnets.

    Overlapping CIDRs are the silent killer, and the math is how you catch them. If a cluster's pod CIDR (10.244.0.0/16) overlaps a range that already exists on the physical network, or the pod and Service CIDRs overlap each other, packets get routed to the wrong place with no error message — just mysterious unreachability. When you design or debug cluster networking, the first mental check is always "do any of these ranges overlap?", and you can only answer it if the CIDR arithmetic is instant. Overlap bugs don't announce themselves; you have to see them in the numbers.

    A cluster has three distinct CIDRs and you must keep them straight: the pod CIDR (e.g. 10.244.0.0/16, carved per node into /24s), the Service CIDR (e.g. 10.96.0.0/12, a purely virtual range that exists only as rewrite rules — no machine ever owns a Service IP), and the node network (the real subnet the VMs sit on). Half of cluster-networking debugging is knowing which range an address belongs to and whether any two overlap. The per-node /24 split you verified above is literally how Flannel assigns pod addresses, and reading a route to a pod as a /24 "out this interface" is the routed-CNI datapath in miniature.

    The three CIDRs and exactly where each is configured are W4.4; the virtual Service CIDR shows up as rewrite rules in W4.9.

    Docs

    man 1 ipcalc for the calculator; there's no man page for CIDR itself, but RFC 4632 (CIDR) and RFC 3021 (/31 links) are the sources if you want them. man 8 ip-route shows how prefixes appear in the routing table (next lesson group). In the exam docs, the kubeadm init flags --pod-network-cidr and --service-cidr are where these ranges are set.

    B8.4

    Reading your interfaces: ip link, ip addr, UP vs LOWER_UP

    Why it matters

    The first rung of the ladder is "does the wire even exist and is it working?", and answering it means reading two commands correctly. The subtlety that catches everyone is that there are two different kinds of "up" — one you set and one the hardware reports — and confusing them turns a dead cable into an afternoon of chasing routing ghosts. Getting ip link and ip addr fluent is the foundation everything else in the module stands on.

    The concept

    Two commands answer two questions. ip link is about the interface itself — does it exist, is it administratively enabled, does it see a carrier, what's its MAC. ip addr adds the addresses configured on it. The critical distinction lives in the flags ip link prints:

    • UP is the administrative state — you turned the interface on (ip link set ens3 up). It means "the OS is willing to use this interface."
    • LOWER_UP is the carrier state — the driver sees an actual signal on the wire (a cable is plugged in and live, or the virtual link's peer exists). It means "there is really something to talk to down there."

    You need both. An interface can be UP without LOWER_UP — administratively enabled but with no carrier — and that reads exactly like a routing or address problem until you look at the flags and see the carrier is missing. Reading <BROADCAST,MULTICAST,UP,LOWER_UP> and confirming both are present is how you clear the link rung in one glance.

    The second idea is that an address is a property you attach to an interface, not an identity the card is born with. A single interface can hold several IP addresses at once; you add and remove them freely. This is why ifconfig is not just old but actively misleading here — it predates this model and can't show multiple addresses, network namespaces, or many modern attributes, so on exactly the machines this track builds it lies by omission. Use ip; it tells the truth. Below you attach a second address, use it, and detach it — proving addresses are movable properties.

    Lab
    1. Read the link and its flags. Confirm both UP (admin) and LOWER_UP (carrier) are present — that's the link rung cleared. 
      multipass shell sandbox
ip -br link show            # brief: name, state, MAC
ip link show ens3 | head -1
      lo               UNKNOWN  00:00:00:00:00:00 ...
ens3             UP       52:54:00:12:34:56 ...
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...   ← both ups present
    2. Read the addresses, then attach a second one, ping it locally, and remove it — demonstrating that addresses are attachable properties. 
      ip -br addr show ens3                        # current address(es)
sudo ip addr add 10.191.62.222/24 dev ens3   # attach a second address
ip -br addr show ens3                          # now shows two
ping -c1 10.191.62.222 >/dev/null && echo 'the new address answers'
sudo ip addr del 10.191.62.222/24 dev ens3   # detach it
ip -br addr show ens3                          # back to one
      ens3   UP   10.191.62.10/24
ens3   UP   10.191.62.10/24 10.191.62.222/24     ← two addresses on one card
the new address answers
ens3   UP   10.191.62.10/24                        ← detached cleanly
    3. See the "UP but no carrier" trap safely. Bring an interface administratively down and watch LOWER_UP vanish while the interface still exists — the state that masquerades as a higher-layer fault. (Use loopback so you can't lock yourself out; restore it immediately.) 
      ip link show lo | head -1          # before: UP,LOWER_UP
sudo ip link set lo down
ip link show lo | head -1          # after: neither — the "link" is gone
sudo ip link set lo up             # restore at once
ip link show lo | head -1
      1: lo: <LOOPBACK,UP,LOWER_UP> ...
1: lo: <LOOPBACK> ...              ← down: no UP, no LOWER_UP — link rung fails here
1: lo: <LOOPBACK,UP,LOWER_UP> ...  ← restored
    Verify

    What's the difference between UP and LOWER_UP in ip link output, and why do you need both? (UP is the administrative state you set — the OS will use the interface; LOWER_UP is the carrier — the driver sees a live signal. An interface that's UP without LOWER_UP is enabled but has nothing to talk to, which looks like a higher-layer fault until you check the flags.) Then: what does adding two addresses to one interface prove about the relationship between addresses and cards? (An address is a property attached to an interface, not a fixed identity — one card can hold many, and you add/remove them at will.)

    Gotchas

    Loopback shows state UNKNOWN rather than UP in ip -br link, which looks alarming but is normal — loopback has no carrier concept, so its operational state is reported as unknown even while it works perfectly. Don't read UNKNOWN on lo as a problem. Real interfaces show UP/DOWN; only virtual ones without a carrier notion show UNKNOWN.

    Addresses you add with ip addr add are not persistent — they vanish on reboot, because persistence is a separate concern owned by the network configuration system (netplan/systemd-networkd on 24.04). That's fine and even useful for the throwaway labs here (a reboot resets your experiments), but don't be surprised when a hand-added address disappears; to make one stick you'd edit netplan, which is out of scope for this module. The runtime state (ip) and the persistent config (netplan) are deliberately different layers.

    On a Kubernetes node, ip link and ip addr show a small zoo of interfaces you'll now recognise: the node's real NIC, a CNI bridge (cni0 or similar), a flannel.1 VXLAN device, and one veth per local pod — each a link with its own state and MAC. Reading their flags is the first rung when a node's pods go unreachable. The "multiple addresses on one interface" fact underlies how a node can hold its own IP plus service-related addresses, and the "operational state UNKNOWN is fine for virtual devices" gotcha saves you from false alarms when you inspect veths and bridges, which routinely show UNKNOWN.

    You'll meet cni0, flannel.1, and per-pod veths on a real node in W4.3 and W4.6.

    Routing

    B8.5

    The routing table: ordered rules and longest-prefix match

    Why it matters

    Once a packet's destination isn't on the local wire, the machine has to decide which door to send it out of — that decision is routing, and it's made by a table you can read. The rule that governs it, longest-prefix match, is refreshingly simple once stated plainly, and it's the exact same rule a CNI plugin uses to make pods on different nodes reach each other. Reading a routing table confidently is the second rung of the ladder and the thing that turns "how does traffic get anywhere?" from magic into a lookup.

    The concept

    The routing table is an ordered set of rules, each saying "for destinations in this prefix, send the packet out this interface, optionally via this next-hop router." ip route prints it. Three kinds of entry cover almost everything:

    • On-link (directly connected) routes — for a subnet the machine is physically on, like 10.191.62.0/24 dev ens3. "These are my neighbours; reach them directly (via ARP), no router needed."
    • The default route — default via 10.191.62.1 dev ens3, written as the prefix 0.0.0.0/0 (match anything). "For everything I don't have a more specific rule for, hand it to this gateway."
    • Specific routes — a rule for some other subnet via a particular next hop, e.g. another node's pod CIDR via that node's IP.

    When several rules could match a destination, the kernel uses longest-prefix match: the most specific route wins — the one with the longest prefix (biggest number after the slash) — regardless of the order it's printed in. A /32 (one exact host) beats a /24 beats the /0 default. That's the entire algorithm. And note what routing does not do: it has no idea whether the destination actually exists or will answer. It only decides "out which door, to which next hop." Reachability is somebody else's problem — routing just picks the exit. This is precisely how a CNI plugin works: it doesn't "connect" pods, it adds a route so that packets for another node's pod CIDR leave by the right interface. Routing is door-selection, nothing more.

    dest 10.244.1.5· matches /24 and /0 →longest prefix (/24) wins→ out that door
    Lab
    1. Read your routing table and name each line's type. There's a default, and at least one on-link route for your own subnet. 
      multipass shell sandbox
ip route
      default via 10.191.62.1 dev ens3 proto dhcp ...    ← the default route (0.0.0.0/0)
10.191.62.0/24 dev ens3 proto kernel scope link ...   ← on-link: my own subnet, reach directly
    2. Prove longest-prefix match by adding a more specific route and watching it take precedence over the default without being "first." Add a dummy route for one /32 and a /24, then note the kernel would pick the most specific. 
      # add a specific route (blackhole = a safe no-op target for the demo)

      blackhole 10.244.1.0/24
blackhole 10.244.1.5/32          ← the /32 wins for 10.244.1.5 despite the /24 existing
    3. Clean up the demo routes. 
      sudo ip route del 10.244.1.5/32

ip route | grep -c 10.244.1 || echo 'cleaned'
      cleaned
    Verify

    State longest-prefix match in one sentence, and rank these for destination 10.244.1.5: a /0 default, a /24 route, a /32 route. (The most specific route — longest prefix — wins regardless of print order; ranked: /32 beats /24 beats the /0 default.) Then: does having a route to a destination mean the destination is reachable? (No — routing only chooses which interface and next hop to send toward; it says nothing about whether anything is there or will answer. Reachability is proven at higher layers.)

    Gotchas

    "Ordered set of rules" can mislead: the routing table is printed in an order, but selection is by specificity, not by line order — a more specific route further down still wins. (There's a separate, advanced concept of route metrics to break ties between equally-specific routes, but longest-prefix is the first and dominant rule.) Don't read a routing table top-to-bottom looking for "the first match"; find the most specific match. This is the opposite of how firewall rules work (those are first-match), and mixing up the two models is a common confusion.

    A machine can have a perfect route to a destination and still not reach it, and a missing route produces a very specific symptom: "Network is unreachable" immediately, from the local kernel, before any packet is sent — distinct from a timeout (packet sent, no answer) or "No route to host" (an ARP/link failure). Learn those three failure phrasings apart: Network unreachable = no matching route at all; timeout = routed out but nothing answered; No route to host = routed to the local segment but the neighbour didn't resolve. Each points at a different rung.

    Routed CNI plugins are nothing but routing table entries. In a routed datapath, each node gets a route saying "pod CIDR 10.244.2.0/24 is via node-2's IP," so a packet from a pod here to a pod there is just longest-prefix match choosing the uplink and the right next hop — no tunnels, no magic. Even overlay CNIs like Flannel add on-link routes for the local pod /24 via the bridge. When pods on different nodes can't talk, "is there a route to that node's pod CIDR?" is one of the first questions, and ip route on the node answers it. The "route ≠ reachability" split is why a present route plus a dropped packet points you at the filter rung, not the route rung.

    Per-node pod-CIDR routes and the routed vs overlay datapath are W4.7; building the routes by hand is part of W4.2.

For the algorithm, man 7 rtnetlink covers the kernel routing interface. In the exam docs, routing is assumed under cluster networking; --pod-network-cidr is where the per-node ranges originate.

    B8.6

    ip route get: ask the kernel which route wins

    Why it matters

    Reading a routing table by eye and working out which rule wins for a given destination is error-prone — you can miscount a prefix or miss a more specific route. There's a command that removes all doubt: ip route get asks the kernel to run the actual routing decision for one destination and report exactly what it chose. Making this your reflex — ask, don't guess — is one of the highest-leverage habits in the whole module, because it collapses "which route applies?" into a single authoritative answer.

    The concept

    ip route get <destination> performs a real route lookup — the same one the kernel would do to send a packet there — and prints the outcome: the chosen source address the packet will carry, the interface it will leave by, and the next hop (via ...) if it's going through a gateway. It's not a guess or a simulation of the table; it's the kernel's own decision engine answering for one address. Because it reports the source address too, it also tells you which of your interfaces/addresses the kernel will use as the origin — invaluable when a machine has several and you need to know which one a connection will appear to come from.

    The habit to build: whenever you're about to reason about routing "by hand," run ip route get instead. It's faster and it can't miscount. Compare the output for a public address (which will show via your gateway) with one on your own subnet (which will show direct, no via) and the on-link-vs-routed distinction from B8.5 becomes concrete. This command is the routing rung of the ladder in a single line.

    ip route get 8.8.8.8→ kernel answers:src · dev · via· the exact decision, no guessing
    Lab
    1. Ask the kernel how it would reach a public address. The answer names the source address, the exit interface, and the gateway it goes via. 
      multipass shell sandbox
ip route get 8.8.8.8
      8.8.8.8 via 10.191.62.1 dev ens3 src 10.191.62.10 uid 1000
    cache
# via the gateway (routed), out ens3, appearing to come from 10.191.62.10
    2. Contrast with a destination on your own subnet — no via, because it's on-link (reached directly by ARP, not through a router). 
      MYNET=$(ip -o -4 addr show ens3 | awk '{print $4}')   # e.g. 10.191.62.10/24
ip route get 10.191.62.20
      10.191.62.20 dev ens3 src 10.191.62.10 uid 1000    ← no "via": direct, on-link
    cache
    3. See it resolve a Kubernetes-style pod address against a route you add, proving it picks the specific route. Add a route and query through it. 
      sudo ip route add 10.244.2.0/24 via 10.191.62.1 dev ens3   # pretend node-2's pods
ip route get 10.244.2.7                                       # which route wins?
sudo ip route del 10.244.2.0/24
      10.244.2.7 via 10.191.62.1 dev ens3 src 10.191.62.10   ← chose the /24 we added
    Verify

    What three things does ip route get report, and why is it better than reading ip route by eye? (The source address the packet will use, the exit interface, and the next hop / via if routed — it runs the kernel's actual routing decision for that destination, so it can't miscount a prefix or miss a more specific route.) Then: one ip route get shows via a gateway and another shows no via — what distinguishes them? (No via means the destination is on-link — on a directly-connected subnet, reached via ARP; via means it's routed through a next-hop gateway.)

    Gotchas

    ip route get tells you the routing decision only — it does not send a packet, does not consult firewall rules, and does not prove the destination answers. So a clean ip route get result means "the route rung is fine," not "it works" — the packet could still be dropped by a filter or hit a dead host. Use it to clear the routing rung and move up the ladder, not to declare victory. It's a diagnostic for one specific layer.

    The src address it reports matters more than beginners expect. On a multi-homed machine (several interfaces/addresses), the source address the kernel picks determines which address the far end sees and replies to — and if return routing for that source is broken, you get one-way connectivity that's baffling until you notice the src. When debugging "the request goes out but no reply comes back," check the src in ip route get; an unexpected source address is a classic cause. You can even force one with ip route get <dst> from <src> to test.

    On a node, ip route get <podIP> is the fastest way to answer "how would this node send a packet to that pod?" — it instantly shows whether the packet goes to the local bridge (a pod on this node), out the uplink via another node (routed CNI), or into a tunnel device (overlay). When cross-node pod traffic breaks, ip route get the destination pod IP on the source node tells you whether the route even exists and where it points, in one line, before you touch tcpdump. It's the single most useful routing command in node-level Kubernetes debugging.

    You'll use exactly this reflex when tracing the pod-to-pod datapath in W4.2 and diagnosing broken CNI in W4.8.

    B8.7

    ICMP tools: what ping and traceroute actually prove

    Why it matters

    ping is the first thing everyone reaches for and the most misread tool in networking. It answers a much narrower question than people think, and treating "ping works" or "ping fails" as a verdict on the whole connection is the single most common false conclusion in network debugging. Learning precisely what ping and traceroute prove — and what they can't — turns them from a superstition into two sharp, honest instruments.

    The concept

    Both tools use ICMP (Internet Control Message Protocol), a helper protocol at the network layer that is separate from TCP and UDP. That separateness is the whole lesson:

    • ping sends an ICMP echo request and waits for an echo reply. A reply proves exactly one thing: the host is up and its network stack will answer ICMP, and the path there and back works at the network layer. It proves nothing about whether any actual service (a web server, a database) is running or reachable — those are TCP/UDP on specific ports, a different protocol ping never touches.
    • traceroute reveals the path by a clever trick: it sends packets with deliberately tiny TTL values — first TTL 1, then 2, then 3 — so each successive router along the way is the one that decrements the TTL to zero, drops the packet, and sends back an ICMP "time exceeded" complaint. Collecting those complaints, one per hop, reconstructs the route. So traceroute maps the routers between you and a destination.

    Because ICMP is its own protocol, firewalls treat it independently of TCP and UDP — many networks allow or block ICMP separately from application traffic. This produces the two results that look like paradoxes but aren't: a host that ignores ping but serves traffic perfectly (ICMP filtered, TCP open — extremely common, some networks drop all ping), and a host that answers ping but has every port closed (ICMP open, nothing listening). "Ping works but nothing else does" is therefore not a contradiction — it's a filter or a dead service, and concluding "the network is fine, ping worked" or "the host is down, ping failed" from ICMP alone is the classic mistake. Ping tests the network layer; your service lives at the transport/application layers, and you must test those to know they work.

    ping ok= host answers ICMP (network layer)≠service works (transport/app)
    Lab
    1. Use ping for what it proves — network-layer reachability — and note its silence about services. 
      multipass shell sandbox

      64 bytes from ... time=8.0 ms
64 bytes from ... time=7.9 ms       ← network layer to that host is fine...
# ...but this says nothing about whether port 80 or 443 is open
    2. Demonstrate the false-conclusion trap directly: find something that answers ping but not a given port, or vice versa. Here, a host answers ping while a bogus port is refused/filtered — proving ping ≠ service. 
      ping -c1 example.com >/dev/null && echo 'ping: OK'

      ping: OK                       ← ICMP fine
port 81: no service            ← but this port isn't served — ping told us nothing about it
    3. Map the path with traceroute and watch the TTL trick reveal hops. Each line is a router that complained "time exceeded." 
      traceroute -n example.com | head -6     # -n: no name lookups (faster, honest)
      traceroute to example.com, 30 hops max
 1  10.191.62.1  0.6 ms ...            ← first hop: our gateway (TTL 1 expired here)
 2  192.0.2.1    3.2 ms ...            ← next router (TTL 2)
 3  * * *                              ← a hop that doesn't answer ICMP (common, not an error)
 ...
    Verify

    Exactly what does a successful ping prove, and what does it not prove? (It proves the host is up and answers ICMP echo and the network-layer path works both ways; it proves nothing about whether any TCP/UDP service is running or reachable, because those are different protocols on specific ports.) Then: explain how traceroute discovers each hop. (It sends packets with increasing TTL — 1, 2, 3… — so each successive router decrements the TTL to zero, drops the packet, and returns an ICMP "time exceeded," and collecting those replies reconstructs the path.)

    Gotchas

    * * * lines in traceroute almost never mean a problem — they mean that hop is configured not to send ICMP "time exceeded" replies (very common for security), so traceroute times out waiting for that one router even though traffic passes through it fine. Don't read stars as "the path is broken there"; the connection can complete perfectly with several starred hops. Stars mean "this router is quiet," not "traffic stops here."

    Because ICMP is separately filterable, ping failing is weak evidence — plenty of perfectly reachable hosts (and most cloud load balancers, and many corporate networks) drop ICMP by policy, so "I can't ping it" does not mean "it's down." Always confirm reachability with the actual protocol you care about — a TCP connect to the real port (curl, nc -vz host port) — before concluding a host is unreachable. Ping is a useful positive signal (a reply proves the network layer) and a poor negative one (no reply may just be a filter).

    This is why Kubernetes health checks are TCP or HTTP probes, never ping: liveness/readiness must test the actual service at the transport/application layer, and ICMP would prove nothing about whether the container is serving. It's also why "I can't ping the pod/Service" is a red herring in cluster debugging — Service ClusterIPs are virtual (no host answers ICMP for them at all, they only exist as rewrite rules), and many pods don't respond to ping, so pinging a Service is meaningless. Test the real port with curl/nc from inside a pod instead. The "ping ≠ service" discipline directly prevents the most common wrong turn in W4/W6 network debugging.

    Service ClusterIPs being virtual (unpingable by design) is W4.9; TCP/HTTP probes replace ping in workload health, W3.

    Transport

    B8.8

    One TCP connection, end to end: handshake, data, teardown

    Why it matters

    TCP is the protocol under almost everything you care about — HTTP, SSH, database connections, the Kubernetes API — and watching one connection be born, carry data, and die demystifies all of them at once. The specific payoff is that the shape of a TCP failure tells you what went wrong: a connection refused instantly and one that hangs are two completely different diagnoses, and knowing which is which routes you straight to the cause. Capturing a real connection with tcpdump and naming each packet is the moment transport stops being abstract.

    The concept

    TCP gives you a reliable, ordered byte stream over an unreliable packet network, and it does that with a defined lifecycle you can watch packet by packet:

    • The handshake (three packets): the client sends SYN ("let's talk, here's my starting sequence number"), the server replies SYN-ACK ("okay, and here's mine"), the client sends ACK ("got it"). After these three, the connection is ESTABLISHED and either side may send data. This round-trip is why a new TCP connection always costs at least one there-and-back before any data flows.
    • Data with sequence numbers: every byte is numbered; the receiver ACKs the highest contiguous byte it has, so a lost segment is noticed (a gap in the numbers) and retransmitted. That's the "reliable, ordered" guarantee in action.
    • Teardown: each side sends a FIN when it's done writing, and the other ACKs it — the connection closes in each direction independently. (An abrupt RST is the other ending: "reset, forget this connection now," used for errors and refusals.)

    Here's the diagnostic gold. Because a connection begins with a SYN that must be answered, the failure modes have distinct signatures: a refused connection comes back instantly — the destination host is reachable but nothing is listening on that port, so its kernel immediately sends a RST, and you get "Connection refused" at once. A filtered connection hangs — the SYN vanished into a firewall (or a black hole) and nothing answers, so your side waits and eventually times out. Keep that pair permanently: refused = reached the machine, no one home; timeout = something ate the packet. In Kubernetes those map almost directly to "a Service with no ready endpoints" (refused/reset) versus "a NetworkPolicy or missing route dropping the packet" (timeout).

    SYN →·← SYN-ACK·ACK →= ESTABLISHED · refused=instant RST · filtered=hang
    Lab
    1. Capture a real connection. In one terminal start a capture; in another run curl; then read the handshake and teardown in the capture. 
      multipass shell sandbox

    Gotchas

    In tcpdump's flag notation, [S] is SYN, [S.] is SYN-ACK (the . means ACK is also set), [.] is a bare ACK, [P.] is push+ACK (data), [F.] is FIN+ACK, and [R]/[R.] is RST. The dot tripping people is that . is the ACK flag — so almost every packet after the initial SYN has a dot. Learn to read the bracket at a glance and the whole connection narrates itself. (This notation returns in B8.13.)

    "Connection refused" is genuinely good news when you're hunting reachability: it proves the network path all the way to the host works and the host's kernel is responding — only the service is absent. It's much more informative than a timeout, which leaves you unsure whether the packet even arrived. So when debugging, a refusal narrows the problem to "wrong port / service not started / not listening on that address," while a timeout keeps the whole path (route, firewall, host-down) in play. Prefer the diagnosis that gives you a refusal.

    The refused-vs-timeout split is one of the most useful reflexes in Kubernetes debugging. Curl a Service from a pod and get connection refused → you reached something (the node/kube-proxy rewrote you to an endpoint) but nothing was listening — often a Service whose pods aren't ready, or the wrong targetPort. Get a timeout → a packet is being dropped: a NetworkPolicy denying the traffic, a missing route between nodes, or a black-holed Service IP with no endpoints at all. The TCP handshake you just watched is also literally what a tcpSocket readiness probe performs — it opens a connection and closes it, and the SYN/SYN-ACK/ACK is the "ready" signal.

    B8.9

    TCP states in ss: what CLOSE-WAIT and TIME-WAIT accuse

    Why it matters

    Run ss -tan on any busy machine and you'll see a column of state names — ESTAB, TIME-WAIT, CLOSE-WAIT — and most people ignore them. That's a mistake, because two of those states are precise accusations: a pile of CLOSE-WAIT means your program has a bug, while a pile of TIME-WAIT is completely normal and needs no action. Knowing which states point at your code, which are harmless, and which point at the network saves you from both false alarms and missed real bugs.

    The concept

    A TCP connection moves through a state machine, and ss -tan shows the current state of each. The ones you'll actually see and what each means:

    • LISTEN — a server socket waiting for connections. Not a connection yet; a readiness to accept them.
    • SYN-SENT — a client sent a SYN and is waiting for the SYN-ACK. Stuck here = the handshake isn't completing (filtered, or the server isn't answering).
    • ESTABLISHED (shown ESTAB) — the connection is open and data can flow. The normal working state.
    • CLOSE-WAIT — the peer sent a FIN ("I'm done") and your side hasn't closed its end yet. The connection is waiting for your program to call close(). A few are transient; many, and growing, means your application forgot to close its sockets — the fix is always in your code, never the kernel.
    • TIME-WAIT — the side that closed first holds the connection in this state for ~1–2 minutes after it's fully closed, deliberately, so that any late duplicate packets from the old connection can't be mistaken for a new connection reusing the same 4-tuple. Thousands of these on a busy client are normal and harmless, not a leak.

    The crucial contrast is CLOSE-WAIT vs TIME-WAIT, because they look similar and mean opposite things. CLOSE-WAIT is your fault and accumulates when your code doesn't close sockets it should — a genuine resource leak that eventually exhausts file descriptors. TIME-WAIT is the kernel doing its job correctly on connections you did close, and it clears itself after the timer; trying to "fix" TIME-WAIT is almost always a mistake. Remember it as: CLOSE-WAIT = my bug; TIME-WAIT = working as intended.

    CLOSE-WAIT piling up= your code forgot close() ·fix the app|TIME-WAIT piling up= normal, self-clears
    Lab
    1. Take a census of connection states on the machine. On a quiet VM most are LISTEN and maybe some ESTAB/TIME-WAIT. 
      multipass shell sandbox
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn
           12 LISTEN
      3 ESTAB
      1 TIME-WAIT               ← a recently-closed connection cooling off — normal

      ss -tan state close-wait

      Recv-Q Send-Q  Local Address:Port  Peer Address:Port

    Verify

    You find thousands of CLOSE-WAIT sockets on a server — where is the bug and why? (In the local application: CLOSE-WAIT means the peer sent FIN and your side never called close(), so the sockets leak — the fix is in your code, not the kernel or network.) Then: you find thousands of TIME-WAIT on a busy client — is that a problem? (No — TIME-WAIT is the deliberate ~1–2 minute cooldown the closing side holds so old duplicate packets can't corrupt a new connection on the same 4-tuple; it's normal for a busy client and clears on its own.)

    Gotchas

    People try to "eliminate" TIME-WAIT with sysctls like tcp_tw_reuse or the old, removed tcp_tw_recycle — usually the wrong instinct, and tcp_tw_recycle was deleted from the kernel precisely because it broke connections behind NAT. If you're hitting a real limit from TIME-WAIT (ephemeral port exhaustion on a very busy client), the right fixes are connection pooling/reuse or widening the port range, not disabling the safety timer. Treat TIME-WAIT as correct until proven otherwise.

    ss replaces the old netstat entirely and is faster and namespace-aware — ss -tan (TCP, all, numeric) is the everyday incantation; add p for the owning process (needs privilege) and state <name> to filter. net-tools' netstat isn't even installed on 24.04, and on a machine with network namespaces it couldn't see into them anyway. Build the ss habit; every state-inspection lab in this track and every node-debug in Kubernetes uses it.

    B8.10

    UDP: no handshake, no promises — and why that's useful

    Why it matters

    Not everything wants TCP's reliability, and the protocols that don't — DNS, VXLAN (the tunnel under many Kubernetes overlays), metrics agents — all choose UDP for specific reasons. Understanding UDP's deliberate lack of guarantees explains why "the packet just vanished" is a normal UDP outcome rather than a fault, which in turn explains a whole class of Kubernetes networking behaviour that looks broken but isn't. It's a short lesson with outsized payoff for reading overlay and DNS problems.

    The concept

    UDP (User Datagram Protocol) is TCP's opposite number at the transport layer: it's just addressed datagrams with ports, and nothing else. No handshake (the first packet carries data immediately), no sequence numbers, no acknowledgements, no retransmission, no ordering, no connection state at all. You send a datagram to an IP and port; it arrives, or it doesn't, and UDP neither knows nor cares. If reliability is needed, the application must build it on top.

    That sounds worse than TCP, but the missing machinery is exactly why certain workloads choose it:

    • DNS — a query and its answer each fit in one small packet, and if a query is lost the resolver simply asks again. Paying for a three-packet TCP handshake before every tiny lookup would be absurd overhead; UDP's "just send it" is perfect, and retry-on-loss is cheap at the application level.
    • VXLAN (and other tunnels) — the overlay networks under many CNIs wrap pod packets inside UDP datagrams between nodes. The inner traffic is usually already TCP with its own reliability, so wrapping it in reliable TCP too would be pointless and slow (TCP-in-TCP meltdown); UDP is the right lightweight envelope.
    • Metrics/telemetry (e.g. statsd) — losing an occasional data point is fine, and you never want the metrics path to block the application waiting for acknowledgements.

    So "the packet was silently dropped" is a normal UDP outcome, not a malfunction — the protocol offers no delivery guarantee, by design. This reframes debugging: with UDP you can't infer "it was received" from "I sent it," and there's no connection state to inspect in ss the way TCP has. You verify UDP by checking the application got the datagram (a DNS answer came back, a metric appeared), not by looking for a handshake that never existed.

    Gotchas

    Because UDP keeps no connection state, ss shows only bindings (who's listening), never per-conversation state — so you can't debug UDP by looking for an ESTAB row, and "is the datagram getting there?" is answered with tcpdump on both ends, not with ss. This trips up people who apply TCP habits: there's no connection to inspect, only traffic to capture. For UDP problems, reach for tcpdump first.

    UDP has no built-in flow control, so a fast sender can overwhelm a slow receiver and datagrams get dropped at the socket buffer with no signal to slow down — which is why high-rate UDP (large DNS responses, busy VXLAN) can suffer loss under load that TCP would have paced around. Large DNS answers actually fall back to TCP for this reason (the truncated-response TC flag tells the client "re-ask over TCP"). So UDP's simplicity has real edges; it's the right tool when messages are small and occasional loss is acceptable, and the wrong one when you need bulk reliable delivery.

    Two of Kubernetes' most important paths are UDP, and this lesson explains their quirks. Cluster DNS (CoreDNS) is queried over UDP, so an occasional lost query and retry is normal — and the famous ndots:5 behaviour means one name lookup can fire many UDP queries, which is why DNS load and intermittent resolution failures are a recurring cluster topic. And overlay CNIs like Flannel VXLAN wrap every pod-to-pod packet in UDP between nodes (port 8472), so when cross-node pod traffic fails on an overlay, you're debugging UDP encapsulation — capture the UDP tunnel traffic on the node uplink, not just the inner connection. "Silent drop is normal for UDP" keeps you from misreading these.

    B8.11

    The 4-tuple: what actually identifies a connection

    Why it matters

    "How does one web server on port 443 handle thousands of simultaneous users without the connections getting mixed up?" is a question that seems to have no good answer until you learn what actually names a connection. It's not the port — it's the 4-tuple, and once you see it, a pile of otherwise-mysterious things click into place at once: connection multiplexing, why NAT needs a table, and the hard ceiling on outbound connections that busy gateways hit.

    The concept

    A TCP (or UDP) connection is uniquely identified not by one port but by four values together — the 4-tuple: source IP, source port, destination IP, destination port. The kernel demultiplexes incoming packets by matching all four against its table of open connections. This is the answer to the multiplexing puzzle: a server listening on :443 can hold thousands of connections at once because, although they all share the same destination (the server's IP and port 443), each has a different client half — a different source IP, or at least a different source port. Every client's OS picks an unused ephemeral port (a high-numbered temporary source port) for each outbound connection, so (clientA:51001 → server:443) and (clientA:51002 → server:443) are two distinct connections despite sharing three of the four values.

    Three consequences worth carrying forward:

    • One listening port, many connections — the server side of the tuple is fixed; the variety lives in the client side. This is why "the port is busy" almost never means "we've run out of connections."
    • NAT must keep a table — when a router rewrites addresses (B9), it changes part of the tuple, so it must remember the mapping to un-rewrite every reply against the right original connection. The 4-tuple is what that table is keyed on.
    • Ephemeral ports are a finite ceiling — a single source IP has only ~28,000 ephemeral ports (the default range is 32768–60999). So from one source IP to one destination IP:port, you can have at most ~28,000 simultaneous connections — after that, no free source port, and new connections fail. This is the exact limit busy egress-NAT gateways hit under load and report as baffling intermittent connection failures.

    Gotchas

    The ~28,000 ceiling is per destination IP:port from one source IP, not a global limit — a machine can hold vastly more total connections because different destinations give different tuples. People misremember it as "a server can only handle 28k connections," which is wrong (that's the client-to-one-destination limit). A server listening on one port is bounded by memory and file descriptors, not by 28k, because each connection differs in the client half of the tuple. Keep straight which side of the tuple is the constrained one.

    This ceiling is a real and under-appreciated production failure. A busy egress path where many clients share one NAT source IP (a corporate gateway, or a Kubernetes node doing SNAT for all its pods to one external service) can exhaust the ~28k ephemeral ports to that one destination and start failing new connections while everything looks healthy — plenty of CPU, plenty of memory, "just" no free source ports. The fixes are more source IPs, connection reuse/pooling, or spreading load across destinations. When "connections fail under high load to one service" with no resource pressure, suspect port exhaustion.

    The 4-tuple is the foundation of how Kubernetes Services work. A ClusterIP is virtual — kube-proxy rewrites a connection's destination (the Service IP:port) to a real pod IP:port via DNAT, and conntrack remembers the tuple mapping so replies get un-rewritten correctly (all B9 machinery). Source-port exhaustion is a genuine cluster failure mode: a node SNATs all its pods' egress behind its node IP, so many pods hammering one external service from one node can exhaust ephemeral ports to that destination — a classic "works at low traffic, fails at scale" incident. And the "one listening port, many connections" fact is why a single Service backend pod can serve a whole cluster's worth of clients.

    DNAT rewriting the destination tuple and conntrack tracking it are W4.9–W4.10; you build NAT and see the conntrack table by hand in B9.

    B8.12

    Listening vs established, and the 127.0.0.1 vs 0.0.0.0 bind

    Why it matters

    The fifth and final rung of the ladder is "is anything actually listening, and can I reach it from where I am?" — and it hides one of the most common and frustrating bugs in all of networking: a service that is running and is listening, but on an address you can't reach. The 127.0.0.1-versus-0.0.0.0 distinction is responsible for an enormous share of "the port is open but I can't connect" confusion, in plain Linux and in Kubernetes alike. Reading a bind address correctly is the skill that closes the ladder.

    The concept

    Two different ss queries answer two different questions:

    • ss -ltnp — listening, tcp, numeric, process. "Who is waiting for connections, on which address:port, and which process is it?" This is the listener rung: it proves a server exists and is bound.
    • ss -tnp (no l) — the currently established connections. "Who is actually connected right now?"

    The load-bearing detail is the bind address in the listener's local column, because a socket doesn't just listen on a port — it listens on a specific address:port, and that address controls who can reach it:

    • 127.0.0.1:8080 — bound to loopback only. Reachable solely from the same machine. Any connection attempt from another host never even arrives; the service is invisible off-box no matter how correct everything else is.
    • 0.0.0.0:8080 — bound to all interfaces (the wildcard). Reachable from anywhere that can route to any of the machine's addresses. This is what a service that should accept external traffic must bind.

    So "the port is open but I can't reach it from another machine" is very often not a firewall or a route — it's a service bound to 127.0.0.1 when it needed 0.0.0.0. ss -ltnp shows this instantly: read the local address, and if it's 127.0.0.1 (or ::1 for IPv6), the service is loopback-only by design. This is the fifth rung, and it's the one people skip — they confirm "the process is running" and stop, without checking which address it bound.

    Always pass -p (and use sudo) when you need to know which process owns a listener — without it you see the port but not the culprit, and "what's on port 8080?" is only half-answered. The full triage incantation is sudo ss -ltnp: listening TCP sockets, numeric, with process names. Memorise it; it's the fastest answer to "is anything listening here and what is it?"

    The loopback-bind bug is insidious because every local test passes — you develop and test on the same machine, curl 127.0.0.1 works perfectly, and it only breaks when something external tries to connect. So a service that "works on my machine" but is unreachable from anywhere else is the signature. Also watch for the IPv6 twist: a service on ::1 is loopback-only in IPv6, and [::]:8080 is the IPv6 wildcard — the same distinction, different notation. Read the actual bind address, don't assume.

    This bug is rampant in Kubernetes and now you'll spot it instantly. A container that binds 127.0.0.1 is unreachable from any other pod or through any Service, no matter how perfect the Service and Endpoints are — because the pod's loopback belongs to its own network namespace (B6), so "localhost" inside the container reaches only that container. The fix is always to make the app bind 0.0.0.0. "Service configured correctly but connections refused/time out, and the app logs look fine" very often ends at ss -ltnp inside the pod showing a 127.0.0.1 bind. It's the pod-level version of the exact rung you just learned, and it's the most common self-inflicted Service bug.

    The pod's own loopback living in its network namespace is B6.13; the Service targetPort that must match the container's real bind is W4.14.

    B8.13

    Reading tcpdump without fear

    Why it matters

    tcpdump has a reputation as an expert-only tool, and that reputation costs people dearly, because it's the one instrument that shows you what's actually on the wire rather than what a program claims. When higher-level tools disagree or lie, tcpdump is the ground truth. The skill isn't memorising every option — it's reading one printed line into its meaning and choosing the right interface and filter. Get that, and the scariest tool in networking becomes the one you trust most.

    The concept

    tcpdump captures packets and prints one line each. The options that matter almost every time:

    • -nn — don't resolve hostnames or port names. Always use this: name resolution slows the capture and, worse, generates DNS traffic that pollutes the very capture you're studying (and can hang if DNS is the thing that's broken).
    • -i <iface> — which interface to capture on (or -i any for all). This choice is the deep skill, below.
    • Filters — a mini-language: host 10.0.0.5, port 80, tcp, udp, icmp, combined with and/or/not. tcp port 80 and host example.com captures just that conversation.

    Reading one line: IP 10.191.62.10.44810 > 93.184.x.x.80: Flags [S], seq 12345, length 0 decodes as direction (source 10.191.62.10 port 44810 > destination 93.184.x.x port 80), flags ([S] = SYN, using the same notation as B8.8: [S.] SYN-ACK, [.] ACK, [P.] data, [F.] FIN, [R] reset), and payload size (length 0 = no data, a pure control packet). That single line tells you who spoke to whom, what kind of packet it was, and how much data it carried — the three things you need to narrate a connection.

    The deeper skill is choosing the interface. The same connection looks completely different depending on where you tap it — and in B9, one pod-to-pod connection appears on the veth inside the namespace, again on the node's bridge, and again on the uplink, sometimes NAT-rewritten between them. Capturing at several points and comparing is exactly how you find which hop drops or mangles a packet: the packet present on the veth but absent on the uplink localises the fault to what's between them. Interface choice turns tcpdump from "see packets" into "bisect the datapath."

    IP src.port > dst.port:·Flags [S]· length N — who, what kind, how much

    Gotchas

    Forgetting -nn is the classic self-inflicted wound: tcpdump tries to reverse-resolve every IP and look up every port name, which slows the capture, adds DNS packets you didn't send, and — if you're debugging a DNS problem — can hang the tool on the very lookups that are failing. Use -i any for a quick "is anything happening at all?", then narrow to the real interface to localise a fault.

    On a node, tcpdump is the final arbiter of CNI mysteries. When a pod's traffic vanishes, you capture at each hop of the datapath — the pod's veth peer on the node (tcpdump -nn -i vethXXXX), the CNI bridge (cni0), the overlay device (flannel.1), and the uplink — and the first interface where the packet stops appearing is where the fault lives. The `-nn`-always rule matters doubly in clusters, where the thing you're debugging is often DNS itself. This "capture at each hop and compare" method is the single most powerful CNI-debugging technique, and it's exactly the interface-choice skill you just practised.

    You capture the pod-to-pod datapath at multiple hops when building and breaking the CNI in W4.3 and W4.8.

    B8.14

    curl -v as a layered probe

    Why it matters

    curl -v is a whole diagnostic ladder in one command: it narrates each layer of a web request as it happens — name resolution, TCP connect, TLS handshake, HTTP exchange — so the line it stops on tells you exactly which layer failed. Instead of a vague "the site won't load," you get "it resolved and connected but the TLS handshake failed" — a precise verdict. Learning to read a -v trace is like getting the bisection ladder for free on every HTTP request you make.

    The concept

    Run curl -v <url> and it prints a running commentary, each stage prefixed distinctively (* for curl's own diagnostics, > for the request it sends, < for the response it receives). The stages, in order, map onto the layers you now know:

    • DNS — * Trying 93.184.x.x... is preceded by resolving the name; if it can't resolve, it fails here ("Could not resolve host") and never gets an IP. Application-layer name resolution.
    • TCP connect — * Connected to example.com (93.184.x.x) port 80 means the handshake from B8.8 succeeded. If it fails here (refused/timeout), it's the transport rung.
    • TLS (for https) — * TLS handshake, certificate details; failures here (expired cert, name mismatch, protocol) stop the trace at TLS with connect already proven.
    • HTTP — the > GET / HTTP/1.1 request lines and the < HTTP/1.1 200 OK response. A failure here (a 404, 500, or a hang after connect) is application-layer.

    The diagnostic move is simply read where it stopped. Stopped at "could not resolve" → DNS. Reached "Connected" but no response → the server accepted the TCP connection but isn't answering HTTP (wrong service on the port, or hung app). Stopped at TLS → a certificate/protocol problem with the network path already proven fine. Got < HTTP/1.1 200 → everything worked. Comparing a healthy request with a deliberately broken one (a closed port, an unresolvable name) trains your eye to spot the stopping point instantly.

    resolve→connect→TLS→HTTP· where it stops = the failing layer
    Lab
    1. Read a healthy trace end to end. Note each stage marker: resolve, connect, request (>), response (<). 
      multipass shell sandbox

    Verify

    A curl -v prints * Connected to host (1.2.3.4) port 443 and then hangs with no < response lines — which layers passed and which is suspect? (DNS resolved and the TCP connect succeeded — so link, network, and transport are fine — and the failure is at TLS or the application: the server accepted the connection but isn't completing the handshake/response.) Then: curl -v stops with "Could not resolve host" — which single layer failed, and did any packets to the destination get sent? (DNS/name resolution failed at the application layer; no connection to the destination was even attempted because there was no IP to connect to.)

    Gotchas

    The stream prefixes are easy to misread: * lines are curl talking to you (diagnostics), > lines are what curl sent to the server, and < lines are what the server sent back. If you see plenty of * and > but no <, you spoke and got no answer — a one-sided conversation that localises the problem to the server or the return path. Reading the direction of each line is half the skill.

    curl -v writes its trace to stderr, not stdout, which is why the labs use 2>&1 to see it — a common trip-up when you try to pipe or grep the verbose output and get nothing. Also, for TLS-specific problems, curl -v shows the certificate and protocol details inline; when you need to go deeper (cipher, full chain), openssl s_client -connect host:443 is the next tool, but curl -v resolves the great majority of "why won't this HTTPS endpoint work" questions on its own.

    curl -v from inside a pod is the workhorse of Service and Ingress debugging. Run it against a Service DNS name and the trace tells you the layer: "could not resolve" → cluster DNS/CoreDNS problem; resolved but "connection refused/timed out" → Service has no ready endpoints, or a NetworkPolicy is dropping it, or the app bound loopback; got an HTTP status → the datapath works and you're debugging the application or Ingress routing. For Ingress and TLS, the -v trace shows exactly whether the TLS handshake, host routing, or backend is at fault. It's the same layered-probe reflex, run from the vantage point that matters — inside the cluster.

    Debugging Services and DNS from inside a pod with curl/dig is threaded through W4.18; Ingress with host/path/TLS is W4.19.

    B8.15

    HTTP by hand: typing a request through nc

    Why it matters

    The fastest way to stop being intimidated by HTTP is to type one by hand and watch a real web server answer. HTTP feels like magic hidden inside browsers and libraries; it is in fact just plain text sent over a TCP connection, and proving that to yourself — with no client library between you and the bytes — permanently changes how you read every web problem. It also explains two things that otherwise seem arbitrary: why the Host: header is mandatory and why a stray blank line matters.

    The concept

    An HTTP/1.1 exchange is text with a strict shape. The request is: a request line (GET /path HTTP/1.1), then headers (one per line, Name: value), then a blank line that signals "headers are done," then an optional body. The response mirrors it: a status line (HTTP/1.1 200 OK), headers, a blank line, then the body. That's the whole protocol's skeleton. Because it's just text over TCP, you can produce it by hand with nc (netcat), which opens a raw TCP connection and pipes your keystrokes straight to the server — no HTTP library involved.

    Typing it by hand makes two rules concrete:

    • Host: is mandatory in HTTP/1.1 because one IP address commonly serves many websites (name-based virtual hosting). The server can't know which site you want from the IP alone — the connection landed on a shared address — so the Host: header is how you name the site. Omit it and a modern server returns an error or the wrong site.
    • The blank line ends the headers. HTTP uses an empty line (a bare CRLF) to mark the boundary between headers and body. Send it too early and you truncate your headers; forget it and the server keeps waiting for more headers and never responds. The blank line is load-bearing punctuation.

    Do this once and HTTP is demystified: it's text, framed by lines and a blank line, over the TCP connection from B8.8. Every Kubernetes probe, every apiserver call, every kubectl command is this same exchange (usually with TLS wrapped around it).

    GET / HTTP/1.1·Host: …·(blank line)→ server replies status + headers + body
    Lab
    1. Type an HTTP request by hand through nc. Send the request line, the Host: header, and a blank line, and read the raw response. 
      multipass shell sandbox
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' \
  | nc example.com 80 | head -12
      HTTP/1.1 200 OK                       ← status line
Content-Type: text/html
Content-Length: 1256
...
                                        ← the blank line, then the body:
<!doctype html>
<html> ...                              ← raw HTML, no browser, no library
    2. Prove Host: is mandatory: send a request without it and watch a shared-hosting server reject or misroute it. 
      printf 'GET / HTTP/1.1\r\nConnection: close\r\n\r\n' | nc example.com 80 | head -1
      HTTP/1.1 404 Not Found              ← no Host: → server can't pick the site (may 400/404/wrong site)
    3. Feel the blank-line framing: send headers with no terminating blank line and watch the server hang, waiting for more headers, until it times out. (Ctrl-C to stop.) 
      printf 'GET / HTTP/1.1\r\nHost: example.com\r\n' | nc -w3 example.com 80 | head -1 || echo '(server waited for the blank line, then timed out)'
      (server waited for the blank line, then timed out)   ← headers never terminated
    Verify

    Lay out the shape of an HTTP request and response. (Request: request line GET /path HTTP/1.1, headers, a blank line, optional body. Response: status line HTTP/1.1 200 OK, headers, a blank line, body.) Then: why is Host: mandatory in HTTP/1.1, and what does the blank line do? (One IP serves many sites via name-based virtual hosting, so Host: tells the server which site you want; the blank line marks the end of the headers — without it the server keeps waiting and never responds.)

    Gotchas

    HTTP lines are terminated by \r\n (carriage-return + line-feed, CRLF), not just \n — which is why the labs use printf with explicit \r\n rather than echo. Many servers tolerate bare \n, but the spec requires CRLF and some strict servers or proxies will reject \n-only requests, so when hand-crafting requests, send proper CRLF and you'll never be surprised. The blank line is therefore literally \r\n\r\n (end of the last header, then an empty line).

    nc comes in flavours — the netcat-openbsd build (installed in the prereq) is the common one on Ubuntu; the older GNU/traditional netcat differs in flags (-q, -w behaviour). If a nc invocation behaves oddly, check which implementation you have (nc -h shows it). For scripted request/response testing, curl is more predictable, but nc is unmatched for seeing the raw bytes and for talking to non-HTTP TCP services (SMTP, Redis) the same way — the by-hand skill generalises far beyond HTTP.

    Understanding HTTP as plain text framed by a blank line is what lets you read Kubernetes' HTTP surfaces directly. An httpGet liveness/readiness probe is literally this request sent to your container; the apiserver speaks HTTP/1.1+TLS (you can watch kubectl --v=8 print the raw requests and responses); and Ingress routing decisions are made on the Host: header and path you just learned are mandatory framing. When a probe fails or an Ingress routes to the wrong backend, knowing the request is just a request line + Host: + headers + blank line tells you exactly what to inspect. The "one IP, many sites, chosen by Host:" rule is how host-based Ingress works.

    Host-based routing in Ingress builds directly on the Host: header (W4.19); httpGet probes are this exact request (workloads, W3).

    Docs

    man 1 nc (the netcat-openbsd build: -w timeout, -v, -u for UDP, -z for scan/connect-test). For HTTP itself, RFC 9110 (HTTP semantics) and RFC 9112 (HTTP/1.1 message framing) are the sources, though you rarely need them. In the exam docs, httpGet probe fields and Ingress host/path rules are where this shape appears.

    B8.16

    The five-rung ladder, committed to memory

    Why it matters

    This is the checkpoint the whole module was built to deliver. Everything so far was teaching you the rungs; this lesson assembles them into a fixed routine you run in order, every time, without improvising. The value isn't that any single rung is clever — it's that a fixed order stops you leaping to the exciting hypothesis and wasting an hour, which is the failure mode that separates people who fix networks fast from people who thrash. Write the ladder on a card and it becomes muscle memory.

    The concept

    Five rungs, bottom to top, each with one command that clears it:

    #RungQuestionCommand
    1LinkDoes the interface exist and see carrier?ip link (look for UP,LOWER_UP)
    2AddressDo we have the right IP and mask?ip addr
    3RouteIs there a path to the destination?ip route get <dst>
    4FilterIs a firewall dropping it?nft list ruleset
    5ListenerIs anything listening, on a reachable address?ss -ltnp

    You climb from rung 1 upward, and the discipline is absolute: do not skip, and trust a rung once it passes. If link is down, nothing above matters — fix it first. If the route is missing, don't go inspecting listeners. Each passed rung exonerates everything below it (the bisection from B8.1), so by the time you reach rung 5 you know the lower four are fine and the problem is genuinely "nothing's listening / bound to the wrong address." The ladder converts a vague "the network's broken" into a five-step walk that ends at the exact failing layer, and it's the same routine no matter the machine, the cloud, or the year.

    Why a fixed order beats intuition: guessing feels faster but is reliably slower, because a wrong guess costs a full investigation down a dead end before you're back where you started. The ladder's four boring rungs under your exciting hypothesis take thirty seconds to clear and, often, reveal that the "interesting" theory was wrong and the interface was down the whole time. This is the same discipline as the W6 triage template on the CKA track — one layer lower down.

    1 link→2 address→3 route→4 filter→5 listener
    Lab

(Because each passed rung exonerates everything below it, so the order guarantees you never chase a higher layer while a lower one is broken — and a wrong guess costs a full investigation, making "boring but ordered" reliably faster than "clever but out of order.")

    Gotchas

    The filter rung on 24.04 is nft list ruleset, not iptables -L — the firewall backend is nftables, and while iptables commands still work through a compatibility shim (iptables-nft), nft list ruleset shows the real unified ruleset including rules added by either tool. An empty ruleset means nothing is being filtered (a clean sandbox); on a Kubernetes node this rung is enormous because kube-proxy fills it. Know both tools exist, but read the truth with nft.

    The ladder is necessary but the rungs aren't always sufficient alone — sometimes a problem sits between rungs (an MTU black hole passes link/address/route/filter/listener yet still fails for large packets, the B8.18 drill). The ladder's job is to localise fast and clear the common cases; the rarer faults reveal themselves once the five obvious rungs are proven fine and you know to look at the seams (MTU, DNS, conntrack). Run the ladder first every time; it either finds the fault or tells you it's one of the exotic ones by elimination.

    This ladder is Kubernetes network debugging, one abstraction lower than the tools you'll use. When a pod can't reach a Service, you climb the same five rungs from inside the pod and on the node: link (the pod's veth and the node's interfaces up?), address (pod IP and CIDRs correct?), route (ip route get the destination — does the node know the way?), filter (kube-proxy's and NetworkPolicy's nft rules — is something dropping it?), listener (is the backend pod actually listening on the targetPort, on 0.0.0.0?). The W6 troubleshooting flow is this ladder with Kubernetes objects layered on top; master it here in plain Linux and the cluster version is just new nouns.

    The CKA triage discipline that mirrors this ladder is W6; you apply it to the pod datapath throughout W4.8.

    B8.17

    Mini project — trace a packet, end to end

    Why it matters

    You've learned every stage of a network conversation in isolation; this project makes you assemble them into one continuous story with real evidence under each step. Documenting a single curl from the name lookup to the connection teardown — with actual command output pasted at every stage, no hand-waving between them — is the exercise that fuses the whole module into one mental model. When you can narrate a packet's entire journey and prove each claim, you understand networking rather than merely knowing facts about it.

    The concept

    One curl http://example.com triggers a precise sequence, and each stage has a tool that shows it happening:

    1. Name resolution — turn example.com into an IP (dig).
    2. Route lookup — decide which interface and next hop reach that IP (ip route get).
    3. ARP for the gateway — find the MAC of the next hop on the local segment (ip neigh).
    4. TCP handshake — SYN / SYN-ACK / ACK to establish the connection (tcpdump, ss).
    5. HTTP request and response — the GET and the 200 OK (curl -v or tcpdump).
    6. Teardown — FIN/ACK closing the connection (tcpdump).

    The discipline that makes this worthwhile is no hand-waving between stages: every claim ("then it does ARP") must have output under it proving it happened. This is the same evidence-first habit the debugging drills across B2–B7 trained, applied to a working system rather than a broken one — and doing it on something that works builds the baseline you compare against when something doesn't. The deliverable is a short document with the six stages as headings and real, trimmed output beneath each.

    Lab
    1. Stages 1–3: resolution, route, ARP. Capture the name→IP→route→MAC chain for one destination. 
      multipass shell sandbox
dig +short example.com                          # 1: name → IP
IP=$(dig +short example.com | tail -1)
ip route get "$IP"                               # 2: which route/next-hop wins
GW=$(ip route | awk '/default/{print $3}')
ip neigh show "$GW"                              # 3: the gateway's MAC (ARP result)
      93.184.216.34                                    ← 1: resolved

10.191.62.1 dev ens3 lladdr 52:54:00:aa:bb:cc REACHABLE   ← 3: gateway MAC known

... Flags [S.], ...        ← 4: SYN-ACK        } handshake

    Gotchas

    You may not see ARP happen in stage 3 if the gateway's MAC is already cached (state REACHABLE) — that's normal. But the method is identical — walk the stages, prove each with output, find the stage where reality diverges.     B8.18

    Debugging drill — unreachable host, wrong netmask, MTU black hole

    Why it matters

    Three faults, each solved by climbing the ladder rather than guessing — and the third is the one that humbles experienced people, because every rung passes and it still doesn't work. Reproducing these and naming each from evidence is what converts the module's theory into the reflex that matters: when the network breaks, you don't panic or guess, you climb. The MTU black hole in particular teaches the module's deepest lesson — that a fault can live between the rungs, revealed only once the five obvious checks are proven clean.

    Symptom 1 — an unreachable host, localised by the ladder
    1. A destination won't respond. Don't guess — climb. Run the rungs in order until one fails; that rung is the answer. 
      multipass shell sandbox
DST=10.244.9.9                                   # a destination that won't answer
ip link show ens3 | grep -o 'UP,LOWER_UP'        # 1 link: ok?
ip -br addr show ens3                             # 2 address: ok?
ip route get "$DST" 2>&1                          # 3 route: is there a path?
      UP,LOWER_UP                                       ← 1 ✓
ens3  UP  10.191.62.10/24                          ← 2 ✓
RTNETLINK answers: Network is unreachable       ← 3 ✗: no route — the ladder stops here
    Cause & fix

    The route rung fails: no path to the destination. "Network is unreachable" from ip route get is the kernel saying no matching route at all — the ladder localised it to rung 3 in three commands, without ever touching DNS, the firewall, or the remote host. The fix is to add the missing route (sudo ip route add 10.244.9.0/24 via <gateway>) or fix whatever should have provided it. The reflex to internalise: an unreachable host is diagnosed, not guessed — climb link → address → route and the failing rung names itself. Contrast the three failure phrasings from B8.5: "Network is unreachable" (no route) vs a timeout (routed but no answer) vs "No route to host" (ARP/link failure) — each points at a different rung.

    Symptom 2 — a wrong netmask that breaks only some hosts
    1. The subtlest of the three: a machine reaches some destinations but not others on what looks like the same network. Reproduce by giving an interface too-narrow a mask, then observe selective failure. 
      # give ens3 a /26 when the real subnet is /24 — some hosts now look "remote"
sudo ip addr add 10.191.62.10/26 dev ens3     # wrong, narrower mask (also-present)
# a host inside the /26 (…1–…62) vs one outside it (…70) behave differently
ip route get 10.191.62.40      # inside /26: treated as on-link
ip route get 10.191.62.200     # outside /26: sent to the gateway instead
sudo ip addr del 10.191.62.10/26 dev ens3     # undo
      10.191.62.40 dev ens3 src 10.191.62.10          ← on-link, direct (ARP) — works
10.191.62.200 via 10.191.62.1 dev ens3 ...    ← treated as remote — won't ARP for it directly
    Cause & fix

    A wrong netmask redraws the boundary of "local," so some same-subnet hosts are wrongly treated as remote. With a /26 where the subnet is really /24, the machine believes only .1–.62 are local; for anything above .62 it won't ARP directly (B8.2) — it hands the packet to the gateway, which may have no idea how to deliver it back into the same segment, so those hosts become unreachable while the low ones work fine. The signature is selective unreachability that splits neatly at a power-of-two boundary. The fix is to correct the mask (/24). The reflex: "some hosts on the same LAN work, others don't, and the split is at a round number" ⇒ suspect a netmask, and confirm with ip route get showing some destinations on-link and others going via the gateway. This is why the address rung (B8.16 rung 2) checks the mask, not just the IP.

    Symptom 3 — an MTU black hole (ping works, big transfers hang)
    1. The humbling one: small packets sail through, large ones vanish. ping succeeds, a page half-loads and hangs, and every ladder rung passes. Reproduce by lowering an interface's MTU and sending packets that exceed it with "don't fragment." 
      # small ping: fine
ping -c1 -M do -s 1200 example.com >/dev/null && echo 'small (1200B): OK'
# large packet with Don't-Fragment set, bigger than a constrained path MTU:
ping -c1 -M do -s 2000 example.com 2>&1 | grep -iE 'frag|too long|100% packet loss' | head -1
      small (1200B): OK                               ← small packets pass
ping: local error: message too long          ← large + DF: dropped; a remote hop would do this silently
    2. Diagnose it: the ladder is clean (link/address/route/filter/listener all pass), so the fault is between rungs. The tell is "works small, hangs large." Check the path MTU and interface MTU. 
      ip link show ens3 | grep -o 'mtu [0-9]*'         # this interface's MTU
tracepath example.com | tail -3                   # tracepath reveals where MTU drops on the path
      mtu 1500
 1:  10.191.62.1   0.5ms
     ...  pmtu 1400                                ← a hop caps the packet size: the black hole
 resume: pmtu 1400
    Cause & fix

    An MTU black hole: a hop on the path can't carry full-size packets and drops the big ones without reporting it. Small packets (a ping, a TLS handshake) fit and succeed, so link, address, route, filter, and listener all look perfect — but a bulk transfer sends full 1500-byte packets, a hop with a smaller MTU (a tunnel, a VPN, a misconfigured overlay) drops them, and if the ICMP "fragmentation needed" message that should trigger Path MTU Discovery is itself filtered, the sender never learns and the connection just hangs. The signatures are unmistakable once known: ping works, small requests work, large responses or uploads hang forever. Diagnose with tracepath (shows where pmtu drops) or by testing ping -M do -s <size> at increasing sizes to find the cliff. The fix is to lower the MTU on the sending interface to fit the path (e.g. ip link set ens3 mtu 1400) or fix the hop/allow the ICMP. The lesson: when every rung passes but big transfers fail, suspect MTU — the fault lives in the seams the ladder doesn't directly test.

    Gotchas

    The three faults escalate in subtlety on purpose. The unreachable host fails a rung outright — the ladder catches it immediately. The wrong netmask passes the naive "do I have an IP?" check but fails on the mask, which is why rung 2 is "right IP and mask," not just "an IP." The MTU black hole passes all five rungs and still fails, teaching that the ladder localises the common cases fast and, by clearing them, points you at the exotic seams (MTU, DNS, conntrack) by elimination. A clean ladder plus "small works, large hangs" is itself a diagnosis.

    MTU black holes are notoriously misattributed — because ping and small requests work, people blame the application, the server, or "flaky network," and burn hours. The single fastest discriminator is packet size: if small transfers succeed and large ones hang, it's almost always MTU/fragmentation, full stop. Keep ping -M do -s <size> (don't-fragment at a chosen size) in your kit as the one-line MTU probe; the size where it flips from success to "message too long" is the path MTU.

    All three are real cluster incidents. Missing-route unreachability is a broken or unconfigured CNI — a node with no route to another node's pod CIDR (W4.8). Wrong-netmask selective failure maps to a misconfigured pod CIDR or node subnet where some pods are reachable and others aren't. And the MTU black hole is a famous Kubernetes overlay problem: VXLAN/IPIP encapsulation adds ~50 bytes of header, so if pods use a 1500 MTU over an overlay that can only carry 1450, small requests and TLS handshakes work but large responses hang — the single most misdiagnosed CNI issue, and the reason overlay CNIs set a reduced pod MTU. Recognising "ping works, big transfers hang" as MTU on a cluster will save you days.

    Broken-CNI signatures (including missing routes) are W4.8; the overlay MTU overhead is part of the datapath families in W4.7.

    B8 recall quiz

    Answer out loud before revealing. If you can climb the five-rung ladder from memory and say what each rung's tool proves, this module has done its job.

    1. Name the four layers bottom to top and the identity or job each owns.
      Answer

      Link (MAC address, one segment) → Network (IP address, routing between segments) → Transport (ports + reliability, process to process; TCP vs UDP) → Application (the protocol's meaning, e.g. HTTP/DNS). Each sits on the one below, so proving a lower layer exonerates everything beneath it — which is why you debug bottom-up.

    2. What does ARP translate, why can't it cross a router, and how does that explain a wrong-netmask outage?
      Answer

      ARP translates a local IP into the MAC address of the card that owns it. It's a broadcast scoped to one segment and routers don't forward broadcasts, so it only resolves neighbours on the same subnet. A wrong netmask makes a machine think a same-subnet host is remote, so it never ARPs for it — it sends to the gateway instead — and the neighbour is never resolved: a link-layer failure caused by an addressing mistake.

    3. For 192.168.1.64/26: usable hosts, network address, broadcast, usable range?
      Answer

      62 usable hosts (64 addresses minus network and broadcast). Network 192.168.1.64, broadcast 192.168.1.127, usable range .65–.126. Shortcut: a /26 block is 64 addresses (256 − 192), so blocks start at .0/.64/.128/.192.

    4. What's the difference between UP and LOWER_UP in ip link?
      Answer

      UP is the administrative state (you enabled the interface); LOWER_UP is the carrier (the driver sees a live signal). You need both — an interface UP without LOWER_UP is enabled but has no working link, which masquerades as a higher-layer fault until you read the flags.

    5. State longest-prefix match, and rank a /0, /24, and /32 for one destination.
      Answer

      The most specific route — the one with the longest prefix — wins, regardless of print order. Ranked: /32 beats /24 beats the /0 default. And a route only chooses an exit and next hop; it says nothing about whether the destination actually answers.

    6. What does ip route get 8.8.8.8 report, and why prefer it to reading the table by eye?
      Answer

      It runs the kernel's actual routing decision and reports the source address the packet will use, the exit interface, and the next hop (via) if routed. It can't miscount a prefix or miss a more specific route, so it's the authoritative answer to "which route wins?" — and the src it shows catches multi-homed one-way-connectivity bugs.

    7. Exactly what does a successful ping prove, and what does it not?
      Answer

      It proves the host is up, answers ICMP echo, and the network-layer path works both ways. It proves nothing about whether any TCP/UDP service is running or reachable — those are different protocols on specific ports, separately filterable. "Ping works but nothing else does" is a filter or a dead service, not a paradox; and ping failing is weak evidence since many reachable hosts drop ICMP by policy.

    8. A connection returns "Connection refused" instantly; another hangs and times out. What does each mean?
      Answer

      Refused = you reached the host but nothing is listening on that port, so its kernel sent a RST immediately. Timeout = the SYN was dropped by a filter or black hole and nothing answered — the host may not even have seen it. In Kubernetes: refused ≈ a Service with no ready endpoints / wrong targetPort; timeout ≈ a NetworkPolicy or missing route dropping the packet.

    9. You find thousands of CLOSE-WAIT sockets, and elsewhere thousands of TIME-WAIT. Which is a bug?
      Answer

      CLOSE-WAIT is the bug — the peer sent FIN and your side never called close(), so sockets leak; the fix is in your application code. TIME-WAIT is normal — the deliberate ~1–2 minute cooldown the closing side holds so old duplicate packets can't corrupt a new connection on the same 4-tuple; it clears itself and needs no action.

    10. What four values identify a connection, and where does the ~28,000 ceiling come from?
      Answer

      The 4-tuple: source IP, source port, destination IP, destination port. One server port serves thousands of clients because each differs in the client half of the tuple. The ~28,000 ceiling is per source-IP → one destination IP:port: only the source port varies there, and one IP has ~28,000 ephemeral ports (default range 32768–60999) — exhaust them and new connections to that destination fail. It's the classic egress-NAT-at-scale failure.

    11. A service runs and ss -ltnp shows it on 127.0.0.1:8080, but nobody else can connect. Why, and the fix?
      Answer

      It's bound to loopback, reachable only from the same machine — connections from other hosts never arrive. Bind it to 0.0.0.0 (all interfaces) instead. In Kubernetes this is the most common self-inflicted Service bug: a container that binds 127.0.0.1 is unreachable from any other pod or Service, because the pod's loopback lives in its own network namespace.

    12. Recite the five-rung ladder with a command per rung, and say why order matters.
      Answer

      1 Link — ip link (UP,LOWER_UP); 2 Address — ip addr (right IP + mask); 3 Route — ip route get; 4 Filter — nft list ruleset; 5 Listener — ss -ltnp. Climb in order and trust a passed rung: each one exonerates everything below it, so you never chase a higher layer while a lower one is broken, and a wrong guess costs a full investigation. An MTU black hole is the exception that passes all five — "small works, large hangs" — reminding you faults can live in the seams.
