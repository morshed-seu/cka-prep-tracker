    I9 — CNI: the interface the network speaks

    The smallest contract in the entire ecosystem, and the one that most often gets blamed for outages it merely reported. B9 already built the datapath by hand; this module is the twenty lines of agreement that turned that script into something a runtime can call.

    Six hours here buys something no amount of reading a vendor's docs will: pod networking stops being a black box with a logo on it. By the end you will have written a plugin in bash that containerd calls for a real sandbox, and it will handle three cases the reference plugins get wrong. Along the way this module contradicts several things commonly said about CNI — including two things this repository's own tracker said before the labs were run.

    Checkpoints16 Hours~6 PrerequisitesI8 · B9
    • The contract. Recite it in one sentence, then invoke a real plugin by hand with all six parameters set — doing manually what containerd does at RunPodSandbox. Read the five operations from the spec's own words, and find the one MUST that is violated more than any other sentence in the document.
    • Configuration. Explain what decides which network a node uses — and why the answer is different for libcni and for containerd, because they are two different mechanisms. Build a chain and watch prevResult cross the wire. Drive the whole thing with cnitool, no Kubernetes anywhere.
    • The plugins that ship. Read the reference bridge plugin against your own net-up.sh and find what the contract added. Learn host-local's reservation tree well enough to diagnose a node that has no addresses left and no pods running. Recognise your B9 DNAT rule inside portmap.
    • In a real stack. Name who actually execs the plugin, and prove it. Then measure what the v1.1 additions do on today's plugins rather than what they were designed to do.
    • Project & drill. Ship cni-minibridge, drive it with cnitool, install it as the node's CNI and serve traffic through it. Then plant three faults and read each one from the symptom end.

    I8 (the sandbox is what gets wired) and B9 (veth, bridge, ip_forward, NAT, conntrack, netfilter). Keep net-up.sh open on one side of the screen for most of this module — the project is a rewrite of it.

    Which machine. The sandbox VM, as every intermediate module so far. Every command and every line of output on this page was captured from a live run there against CNI plugins v1.9.1, libcni and cnitool v1.3.0 and containerd 2.3.3 on kernel 6.8.0. Two notes on the toolchain: cnitool is not packaged for Ubuntu 24.04, so it is built from source in I9.8 (one go install); and the plugin binaries were already in /opt/cni/bin from I0's setup.

    A warning about spec versions. The CNI repository's git tags are library releases, not spec versions. The document describing spec 1.1.0 lives in SPEC.md at library tag v1.3.0, and the file at tag v1.1.0 is an older spec that says "CNI defines 4 operations". Every quote on this page is fetched from the v1.3.0 tree.

    The contract

    I9.1

    The whole contract, in one sentence and one command

    Why it matters

    Pod networking has a reputation for being the hardest part of Kubernetes, owned by a vendor whose internals you are not expected to understand. The interface itself is the opposite of that. It is small enough to state in one sentence, and you can verify that sentence with a single command in the next thirty seconds. Everything complicated about cluster networking sits on one side of this interface, and knowing exactly where the line falls is what lets you stop guessing during an outage.

    The concept

    Here is the sentence. The runtime executes a program; it passes configuration as JSON on that program's standard input and parameters in environment variables; it reads a JSON result from the program's standard output. That is CNI. There is no daemon to run, no socket to connect to, no library you must link against, no version-negotiation handshake over a wire.

    A CNI plugin is a file in a directory that the runtime runs like any other command. The calling convention is the one every Unix tool has used since the 1970s: arguments in the environment, input on stdin, output on stdout, a status code to say whether it worked. That is why plugins exist written in Go, Rust, Python and bash without anybody coordinating a client library, and why you will have written one by the end of this module.

    Compare this with CRI, which needed protobuf, gRPC and a generated client on both sides. The difference is not that container runtimes are more complicated than networks. It is that the interaction is different. CRI is a long-lived, bidirectional conversation: the kubelet streams logs, attaches to a TTY, watches for exits, and polls status forever. CNI is a one-shot errand — "attach this thing, tell me its address" — and a one-shot errand needs nothing more than exec. The interface's complexity followed the interaction's shape, not the subject's difficulty. That is the single most useful design lesson in this track.

    The registry's metaphor for it: the electrician is handed a room number and a job, does the work, reports back the socket they fitted, and leaves. Nobody keeps them on staff. If you want somebody on staff — watching the building, re-running wire between floors as tenants move — that is a different role, and I9.13 is where we find out that every real CNI provider hires one.

    The spec states the calling convention in two sentences, and it is worth noticing how little it claims:

    The CNI protocol is based on execution of binaries invoked by the container runtime. CNI defines the protocol between the plugin binary and the runtime.

    The runtime passes parameters to the plugin via environment variables and configuration. It supplies configuration via stdin. The plugin returns a [result](#Section-5-Result-Types) on stdout on success, or an error on stderr if the operation fails. Configuration and results are encoded in JSON.
    CNI spec 1.1.0, § Section 2: Execution Protocol — SPEC.md

    Note the wording "an error on stderr". That sentence is loose, and the spec contradicts it later: § Error requires the error object on stdout, and reserves stderr for "unstructured output such as logs". Every plugin in the field follows the later text, and so must yours — I9.4 is where getting this backwards produces one of the most misleading error messages in Kubernetes.

    Verify

    You can state the contract in one sentence without hedging, and you can demonstrate it with one command. You can also say why CNI is exec-based where CRI is gRPC-based, in terms of the interaction rather than the subject matter.

    Gotchas
    • "Installing a CNI" sounds like installing a service. It is not. There is no unit to enable, nothing to restart, and systemctl status will never tell you anything about it. When someone says the CNI is down, they mean either a file is wrong or a provider's daemon has stopped — and those are different problems with different fixes. I9.13 separates them.
    • The spec's own overview says errors go to stderr, and that is the one place it is wrong. § Error and the STATUS section both put the error object on stdout. Follow those.

    This is the contract behind W4.5 — the CNI contract: exec a binary, JSON in, JSON out. The comparison with a long-lived gRPC API is I8.2 — a gRPC service, on a unix socket, defined by runtime.v1, and the moment a pod's empty network namespace is handed to a plugin is I8.7 — RunPodSandbox triggers CNI ADD, the seam where I9 begins.

    Docs: the spec itself is short enough to read end to end in an hour — containernetworking/cni SPEC.md at v1.3.0. In the exam docs, search for network plugins to find where Kubernetes hands the whole subject to this contract and stops describing it.

    I9.2

    The six parameters — and doing RunPodSandbox's job by hand

    Why it matters

    You are about to attach a network namespace to a bridge, allocate it an address and give it a default route, by typing the same six environment variables containerd sets. After this lesson, "the CNI plugin ran" is not an event you infer from logs — it is something you have done with your own hands, and can do again to test a theory during an incident.

    The concept

    Six environment variables carry everything the runtime tells the plugin about this invocation. Configuration on stdin describes the network; these describe the one attachment.

    ParameterWhat it carriesWhere it comes from in a real pod
    CNI_COMMANDThe operation: ADD, DEL, CHECK, GC, VERSION (and STATUS)What containerd is trying to do
    CNI_CONTAINERIDAn opaque unique string. The plugin's bookkeeping key.The sandbox ID — not any app container
    CNI_NETNSA path to the network namespace file/var/run/netns/cni-<uuid>, bind-mounted before the plugin runs
    CNI_IFNAMEThe name the interface must have inside the namespaceConventionally eth0
    CNI_PATHColon-separated directories to search for other plugin binaries/opt/cni/bin
    CNI_ARGSExtra KEY=VALUE;KEY=VALUE pairsWhere anything Kubernetes-specific is smuggled through

    Notice what is missing. There is no pod name, no namespace, no labels, no service account, no owner reference. CNI knows nothing about Kubernetes and has no vocabulary for it. It is handed an opaque identifier, a path, and a name to use, and that is deliberate — it is why the same plugins work under containerd, CRI-O, Podman and a shell script.

    CNI_NETNS is worth dwelling on. It is a path, not a name and not a PID, because a network namespace is kept alive by something holding a reference to it, and a bind-mounted file is the cheapest such thing. That is B6's mechanism exactly, and I8.7 established the surprising part: for a pod, that bind mount exists before the pause container does, because CNI ADD runs first. The plugin is pointed at a namespace that no process has entered yet — so the familiar claim that the pause container "holds the pod's network namespace" is not what pins it.

    CNI_CONTAINERID is the key everything else is filed under. IPAM reservations are recorded against it; so is the runtime's own cache of the result. This is why a runtime that passes a different ID on DEL than it did on ADD leaks an address on every pod, forever, with no error anywhere — the plugin dutifully looks for a reservation belonging to an ID that never existed, finds none, and reports success.

    And CNI_ARGS is where the tidy story gets a wrinkle that the lab is about to find.

    The spec describes CNI_NETNS in terms of an abstraction, with the namespace path only as an example — because CNI is not Linux-only:

    - `CNI_NETNS`: A reference to the container's "isolation domain". If using network namespaces, then a path to the network namespace (e.g. `/run/netns/[nsname]`)
    CNI spec 1.1.0, § Parameters — SPEC.md

    Verify

    You can name all six parameters and say what each is for, including why CNI_NETNS is a path rather than a PID. You can attach a namespace to a network by hand, and you can read a v1.1.0 result — in particular, what ips[0].interface indexes.

    Gotchas
    • CNI_ARGS is not a free-form bag. The reference plugins fail with code 999 on any key they do not know, so a runtime that wants to pass pod metadata through must send IgnoreUnknown — a convention, not a spec field. If you write a plugin that rejects unknown args without honouring it, you will break under every real runtime.
    • The container ID is the sandbox's, not the app container's. A pod with six containers involves exactly one CNI attachment, filed under the sandbox ID. Looking for a per- container reservation is looking for something that never existed.
    • A successful ADD leaves lo down. The interface plugin does not touch loopback; something else has to. I9.11 is about what happens when nothing does.

    You have just done by hand what W4.2 — build a pod network by hand does inside a cluster, and what W4.3 — find a real pod's veth peer on the node asks you to trace afterwards. The cni-<uuid> path you were pointed at is the one I8.5 dissected; the primitives themselves are B9.2 — a veth pair is a virtual patch cable and B9.3 — a bridge is a virtual switch.

    Docs: the parameter list is § Parameters of SPEC.md; the IgnoreUnknown convention and the capability-args mechanism are in the neighbouring CONVENTIONS.md, which is where anything not in the spec proper gets written down.

    I9.3

    Five operations, and the most-violated MUST in the spec

    Why it matters

    There is one sentence in the CNI specification that gets broken more than any other, and breaking it produces a symptom every Kubernetes operator has seen: a pod stuck in Terminating forever. The sentence is three lines long and it is about DEL. Learning it properly here means recognising that symptom instantly, and never writing the bug yourself.

    The concept

    Take the operation count from the spec's own words rather than from a blog post, because the counting is genuinely awkward. The spec says:

    The operations, as the document itself enumerates them:

    CNI defines 5 operations: `ADD`, `DEL`, `CHECK`, `GC`, and `VERSION`. These are passed to the plugin via the `CNI_COMMAND` environment variable.
    CNI spec 1.1.0, § CNI operations — SPEC.md

    …and then defines STATUS in a section of its own, alongside those five, with its own error codes. So there are five named in the sentence and six you can send. Say it that way; anyone who tells you flatly "CNI has six verbs" is quoting something the spec does not say, and anyone who says four is reading the older document at library tag v1.1.0.

    OperationJobRequiresOutput on success
    ADDCreate or adjust the interfaceCOMMAND, CONTAINERID, NETNS, IFNAMEA result object
    DELRemove it, or undo the modificationCOMMAND, CONTAINERID, IFNAME — NETNS is optionalNothing
    CHECKConfirm the attachment is still as promisedSame as ADD, plus prevResult on stdinNothing
    GCReclaim anything not in the list of live attachmentsCOMMAND, PATHNothing
    STATUSDeclare readiness to serve ADDsNothing but the configNothing
    VERSIONReport supported spec versionsNothing but the configA version object

    Only ADD, DEL, CHECK and VERSION are expected of every plugin; GC and STATUS arrived in 1.1.0 and I9.14 measures how many plugins actually implement them. Note the third column: DEL is the only operation for which CNI_NETNS is optional, and that is not an oversight. It is the spec conceding that teardown routinely happens after the namespace is gone.

    Which brings us to the sentence. A plugin author writes ADD first, tests it, writes DEL, and returns an error when the interface is missing, because "that shouldn't happen." It happens constantly:

    • the runtime's call timed out and it retried, so DEL arrives twice;
    • the node rebooted between ADD and DEL;
    • the sandbox was torn down and the kubelet is reconciling again after a restart;
    • the ADD itself failed halfway, and the runtime is calling DEL to clean up something that was never fully created.

    A DEL that returns an error tells the runtime the teardown failed. The runtime does the correct thing with that information: it retries, with backoff, forever. From the outside that is a pod in Terminating that never leaves, and the plugin's own logs — if it has any — say "interface not found," which reads like a diagnosis rather than the bug it is.

    So the rule for the project, and for any plugin you ever touch: write DEL first, and write it to succeed against an empty world.

    The requirement, and the best-effort principle behind it:

    Plugins MUST accept multiple `DEL` calls for the same (`CNI_CONTAINERID`, `CNI_IFNAME`) pair, and return success if the interface in question, or any modifications added, are missing.
    CNI spec 1.1.0, § DEL — SPEC.md

    And on the runtime's side, the obligation that makes it unavoidable:

    The container runtime must ensure that _add_ is eventually followed by a corresponding _delete_. The only exception is in the event of catastrophic failure, such as node loss. A _delete_ must still be executed even if the _add_ fails.
    CNI spec 1.1.0, § Lifecycle & Ordering

    Verify

    You can quote the operation count the way the spec words it, name which parameters DEL can do without, and explain the causal chain from an erroring DEL to a pod stuck in Terminating. You can also produce four distinct situations in which DEL is called with nothing left to delete.

    Gotchas
    • A silent DEL is a successful DEL. If you are looking for confirmation in the output, there isn't any — check the exit status. Plugins that print "removed interface eth0" on stdout are corrupting the result channel, which is I9.4's fault.
    • Idempotency is not the same as best-effort, and the spec asks for both. Idempotent means the second call succeeds. Best-effort means the first call keeps going after one step fails, cleaning up what it still can, rather than aborting halfway. A plugin that bails on the first missing resource is technically idempotent and still leaves garbage behind — which is exactly the leak I9.9 measures in the reference plugin.
    • "That shouldn't happen" is the whole bug. Every scenario in step 3 is routine. Design DEL for a world where nothing you expect to exist does.

    The Terminating-forever symptom is triaged in W6.11 — the kubelet classics, and a pod whose network teardown fails is one of the cases W4.8 — break the CNI on purpose and read the signatures plants. The idempotency requirement has the same shape as the one I8.11 — teardown, in reverse, and what happens when you get it wrong made about CRI: interfaces that expect to be retried must make retrying safe.

    Docs: read § DEL and § Lifecycle & Ordering of SPEC.md together — the plugin's obligation and the runtime's are two halves of one argument. In the exam docs, search pod termination for the lifecycle the stuck state belongs to.

    Quiz

    1. State the CNI contract in one sentence, without using the words "daemon" or "API".
      Answer

      The runtime executes a program, passing configuration as JSON on its standard input and parameters in environment variables, and reads a JSON result from its standard output. That is the whole of it — no daemon, no socket, no library to link.

    2. How many operations does the spec define, and why is the honest answer awkward?
      Answer

      Its own sentence says "CNI defines 5 operations: ADD, DEL, CHECK, GC, and VERSION", and then it defines STATUS in a section of its own alongside them. So five are named and six can be sent. Anyone saying flatly "six verbs" is quoting something the spec does not say; anyone saying four is reading the older SPEC.md at library tag v1.1.0, since the CNI repo's git tags are library releases rather than spec versions.

    3. A pod is stuck in Terminating and the CNI plugin's log says "interface not found". What is the bug, and in which component?
      Answer

      The bug is in the plugin: its DEL returns an error when the interface is missing, violating the spec's requirement that plugins MUST accept repeated DELs and return success when the resources are already gone. The runtime does the correct thing with an error — retries with backoff, forever — so the plugin's honest-looking message is the fault, not a diagnosis of one.

    4. Which parameters does DEL require, and which one is deliberately optional? Why that one?
      Answer

      CNI_COMMAND, CNI_CONTAINERID and CNI_IFNAME are required; CNI_NETNS is optional. That is the spec conceding that teardown routinely happens after the namespace is gone — a node reboot, a sandbox already destroyed — so a plugin that depends on reading the namespace during DEL cannot be correct.

    5. You add 99-mynetwork.conflist to /etc/cni/net.d alongside 10-flannel.conflist and nothing changes. Why? And what would have changed everything?
      Answer

      Containerd loads maxConfNum configurations — 1 by default — in sorted filename order, so 10-flannel wins and 99- is never read. Naming it 05-mynetwork.conflist would have silently moved every new pod onto your network. Higher numbers do not mean higher precedence; they mean lower.

    6. Does 10-flannel.conflist.orig still act as a live configuration file?
      Answer

      No. libcni matches on the file's final extension, which here is .orig, so the file is never read. .bak and .disabled behave the same way. Renaming within .conflist is what does not help.

    7. Why can't portmap be the first plugin in a chain, and what exactly does it say if it is?
      Answer

      It is a chained plugin: it needs the pod's address, which arrives in prevResult from the interface plugin ahead of it, in order to write a DNAT rule pointing at it. First in the list there is no prevResult, so it fails with must be called as chained plugin — identically whether or not port mappings were supplied, because the fault is its position.

    8. A chained plugin returns a result containing only cniVersion. Nothing errors on ADD. What have you broken?
      Answer

      Everything downstream of it. A chained plugin must pass prevResult through; dropping it means later plugins have no addresses to work with, and the runtime caches that truncated result — so every subsequent CHECK and DEL for the attachment is handed an empty picture too. The failure is silent at the point of the bug and surfaces somewhere else.

    9. A node reports "no IP addresses available" and is running three pods on a /24. Where do you look, and what exactly are you comparing?
      Answer

      ls /var/lib/cni/networks/<network>/, and you compare its count of address files against crictl pods -q | wc -l. Each file is a reservation held regardless of whether its holder exists, and every DEL that did not run leaves one forever. Delete only the entries whose holders are gone — never the directory, or you will hand a live pod's address to a new one.

    10. bridge's DEL returned 0 and the pod's masquerade rule is still in the nat table. Is the plugin buggy?
      Answer

      Not by the letter of the spec, which is what makes it interesting. It learns the container's address by reading the namespace, and the namespace was already gone, so it could not build the rule to delete — and returning success in that situation is exactly what the idempotency MUST demands. The IPAM reservation was released, because that is keyed by container ID. Two of three realistic teardown orders leak this way. The fix, which cni-minibridge implements, is to look the address up in your own store instead.

    11. What is the single observable difference between macvlan and ipvlan, and name one practical consequence.
      Answer

      macvlan gives the container its own MAC address; ipvlan shares the parent interface's MAC byte for byte and splits traffic by IP. Consequences follow from that alone: macvlan is refused by switch port security and by essentially every cloud hypervisor, while ipvlan survives those restrictions but loses L2 features such as broadcast to the container in L3 mode.

    12. Why is loopback mandatory, and what does its absence look like?
      Answer

      A fresh network namespace has a loopback interface that is down, and a successful interface-plugin ADD does not bring it up. Without it, ping 127.0.0.1 inside the pod answers "Network is unreachable" — so the symptom is a failing health check, a sidecar that cannot reach its app, or a client that cannot connect to its own machine. Nothing in it says "networking".

    13. Which component execs the CNI plugin, at what moment, and what does the kubelet learn?
      Answer

      Containerd's CRI plugin, during RunPodSandbox, before any application container exists — the kubelet never execs a plugin. It learns the pod's address as a field in the sandbox status returned over gRPC, which is why kubectl get pod -o wide can show an IP for a pod whose containers have not started.

    14. Draw the line: what does CNI specify, and what is a provider's daemon doing?
      Answer

      CNI attaches one pod on one node to a network and reports its address, then detaches it. Everything else is the provider's: learning each node's pod subnet from the API server, programming routes or VXLAN FDB entries or BGP sessions so nodes reach each other's pods, and enforcing NetworkPolicy. Nothing in the spec concerns node-to-node reachability, which is why datapath families differ wildly while all speaking the same contract.

    15. Your cluster runs CNI plugins v1.9.1. Does GC reclaim leaked IPAM reservations?
      Answer

      No. The spec has the verb, libcni has the runtime half, and not one of the reference plugins registers a GC handler — so CNI_COMMAND=GC with an explicit valid-attachments list, or even an empty one, returns 0 and changes nothing. libcni's other GC phase synthesises DELs from its own result cache, but that cache lives in /var/run and does not survive the reboot that caused the leak. The field repair is still rm.

    16. What does cnitool gc <net> <netns> do to a node with live pods?
      Answer

      Tears them all down. Its source passes nil for the valid-attachments list — "Currently just invoke GC without args, hence all network interface should be GC'ed!" — so libcni treats every cached attachment as stale and synthesises a DEL for each. It means "release everything cached", not "reclaim what leaked".

    17. Sandbox creation fails with failed to unmarshal raw result: invalid character 'm' looking for beginning of value. What is wrong, and did the plugin's work succeed?
      Answer

      A plugin wrote a human-readable line to stdout, which is the result channel — the 'm' is the first character of its message. The fix is >&2. And yes, its actual work almost certainly succeeded: the bridge, veth and address were all created before the unreadable report, so a node suffering this accumulates wired namespaces and reserved addresses for pods that never started.

    18. Why does CNI use exec and JSON where CRI needed gRPC and protobuf?
      Answer

      Because the interaction differs, not the subject. CRI is a long-lived bidirectional conversation — streaming logs, attaching to TTYs, watching for exits, polling status. CNI is a one-shot errand: attach this, report the address. The interface's complexity followed the shape of the interaction, which is the most reusable design lesson in this track.

    • You can state the CNI contract in one sentence and demonstrate it in one command, and say why it is exec-based where CRI is gRPC-based.
    • You have invoked a real plugin by hand with all six parameters, and read a v1.1.0 result field by field — including what ips[].interface indexes.
    • You can quote the operation count the way the spec words it, and you know which single MUST produces pods stuck in Terminating when it is broken.
    • You can read an error object's code and decide whether the runtime should retry, fail fast or skip teardown — and you know two places the reference plugins do not conform.
    • You can say what decides which network a node uses, as two different mechanisms for libcni and for containerd, and which renames disable a conflist.
    • You have watched prevResult cross the wire, and can explain what a chained plugin does and does not receive.
    • You have read the reference bridge plugin against your own net-up.sh and found both what the contract added and where the reference silently leaks.
    • You can diagnose a node with no addresses and nothing running, in one ls, and repair it without breaking a live pod.
    • You can trace hostPort from a pod spec to the exact iptables line you wrote by hand in B9.
    • You know who execs the plugin, what "installing a CNI" consists of, and where CNI's responsibility stops and a provider's begins.
    • You have measured what GC and STATUS actually do on today's plugins, rather than what they were designed to do.
    • You have written a spec-compliant plugin that containerd drives for a real pod serving real traffic — and that fixes three things the reference plugins get wrong.
