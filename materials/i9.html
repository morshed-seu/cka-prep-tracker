    I9 — CNI: the interface the network speaks

    The smallest contract in the entire ecosystem, and the one that most often gets blamed for outages it merely reported. B9 already built the datapath by hand; this module is the twenty lines of agreement that turned that script into something a runtime can call.

    Six hours here buys something no amount of reading a vendor's docs will: pod networking stops being a black box with a logo on it. By the end you will have written a plugin in bash that containerd calls for a real sandbox, and it will handle three cases the reference plugins get wrong. Along the way this module contradicts several things commonly said about CNI — including two things this repository's own tracker said before the labs were run.

    Checkpoints16 Hours~6 PrerequisitesI8 · B9

Read the five operations from the spec's own words, and find the one MUST that is violated more than any other sentence in the document.
    • Configuration. Explain what decides which network a node uses — and why the answer is different for libcni and for containerd, because they are two different mechanisms. Build a chain and watch prevResult cross the wire. Drive the whole thing with cnitool, no Kubernetes anywhere.
    • The plugins that ship. Read the reference bridge plugin against your own net-up.sh and find what the contract added. Learn host-local's reservation tree well enough to diagnose a node that has no addresses left and no pods running. Recognise your B9 DNAT rule inside portmap.
    • In a real stack. Name who actually execs the plugin, and prove it. Then measure what the v1.1 additions do on today's plugins rather than what they were designed to do.
    • Project & drill. Ship cni-minibridge, drive it with cnitool, install it as the node's CNI and serve traffic through it. Then plant three faults and read each one from the symptom end.

    I8 (the sandbox is what gets wired) and B9 (veth, bridge, ip_forward, NAT, conntrack, netfilter). Keep net-up.sh open on one side of the screen for most of this module — the project is a rewrite of it.

Every command and every line of output on this page was captured from a live run there against CNI plugins v1.9.1, libcni and cnitool v1.3.0 and containerd 2.3.3 on kernel 6.8.0.     The contract

    I9.1

    The whole contract, in one sentence and one command

    Why it matters

    Pod networking has a reputation for being the hardest part of Kubernetes, owned by a vendor whose internals you are not expected to understand. The interface itself is the opposite of that. It is small enough to state in one sentence, and you can verify that sentence with a single command in the next thirty seconds. Everything complicated about cluster networking sits on one side of this interface, and knowing exactly where the line falls is what lets you stop guessing during an outage.

    The concept

    Here is the sentence. The runtime executes a program; it passes configuration as JSON on that program's standard input and parameters in environment variables; it reads a JSON result from the program's standard output. That is CNI. There is no daemon to run, no socket to connect to, no library you must link against, no version-negotiation handshake over a wire.

    A CNI plugin is a file in a directory that the runtime runs like any other command. The calling convention is the one every Unix tool has used since the 1970s: arguments in the environment, input on stdin, output on stdout, a status code to say whether it worked. That is why plugins exist written in Go, Rust, Python and bash without anybody coordinating a client library, and why you will have written one by the end of this module.

    Compare this with CRI, which needed protobuf, gRPC and a generated client on both sides. The difference is not that container runtimes are more complicated than networks. It is that the interaction is different. CRI is a long-lived, bidirectional conversation: the kubelet streams logs, attaches to a TTY, watches for exits, and polls status forever. CNI is a one-shot errand — "attach this thing, tell me its address" — and a one-shot errand needs nothing more than exec. The interface's complexity followed the interaction's shape, not the subject's difficulty. That is the single most useful design lesson in this track.

    The registry's metaphor for it: the electrician is handed a room number and a job, does the work, reports back the socket they fitted, and leaves. Nobody keeps them on staff. If you want somebody on staff — watching the building, re-running wire between floors as tenants move — that is a different role, and I9.13 is where we find out that every real CNI provider hires one.

    The spec states the calling convention in two sentences, and it is worth noticing how little it claims:

    The CNI protocol is based on execution of binaries invoked by the container runtime. CNI defines the protocol between the plugin binary and the runtime.

    The runtime passes parameters to the plugin via environment variables and configuration. It supplies configuration via stdin. The plugin returns a [result](#Section-5-Result-Types) on stdout on success, or an error on stderr if the operation fails. Configuration and results are encoded in JSON.
    CNI spec 1.1.0, § Section 2: Execution Protocol — SPEC.md

    Note the wording "an error on stderr". That sentence is loose, and the spec contradicts it later: § Error requires the error object on stdout, and reserves stderr for "unstructured output such as logs". Every plugin in the field follows the later text, and so must yours — I9.4 is where getting this backwards produces one of the most misleading error messages in Kubernetes.

    Gotchas

    I9.2

    The six parameters — and doing RunPodSandbox's job by hand

    Why it matters

    You are about to attach a network namespace to a bridge, allocate it an address and give it a default route, by typing the same six environment variables containerd sets. After this lesson, "the CNI plugin ran" is not an event you infer from logs — it is something you have done with your own hands, and can do again to test a theory during an incident.

    The concept

    Six environment variables carry everything the runtime tells the plugin about this invocation. Configuration on stdin describes the network; these describe the one attachment.

    ParameterWhat it carriesWhere it comes from in a real pod
    CNI_COMMANDThe operation: ADD, DEL, CHECK, GC, VERSION (and STATUS)What containerd is trying to do
    CNI_CONTAINERIDAn opaque unique string. The plugin's bookkeeping key.The sandbox ID — not any app container
    CNI_NETNSA path to the network namespace file/var/run/netns/cni-<uuid>, bind-mounted before the plugin runs
    CNI_IFNAMEThe name the interface must have inside the namespaceConventionally eth0
    CNI_PATHColon-separated directories to search for other plugin binaries/opt/cni/bin
    CNI_ARGSExtra KEY=VALUE;KEY=VALUE pairsWhere anything Kubernetes-specific is smuggled through

    Notice what is missing. There is no pod name, no namespace, no labels, no service account, no owner reference. CNI knows nothing about Kubernetes and has no vocabulary for it. It is handed an opaque identifier, a path, and a name to use, and that is deliberate — it is why the same plugins work under containerd, CRI-O, Podman and a shell script.

    CNI_NETNS is worth dwelling on. It is a path, not a name and not a PID, because a network namespace is kept alive by something holding a reference to it, and a bind-mounted file is the cheapest such thing. That is B6's mechanism exactly, and I8.7 established the surprising part: for a pod, that bind mount exists before the pause container does, because CNI ADD runs first. The plugin is pointed at a namespace that no process has entered yet — so the familiar claim that the pause container "holds the pod's network namespace" is not what pins it.

    CNI_CONTAINERID is the key everything else is filed under. IPAM reservations are recorded against it; so is the runtime's own cache of the result. This is why a runtime that passes a different ID on DEL than it did on ADD leaks an address on every pod, forever, with no error anywhere — the plugin dutifully looks for a reservation belonging to an ID that never existed, finds none, and reports success.

    And CNI_ARGS is where the tidy story gets a wrinkle that the lab is about to find.

    The spec describes CNI_NETNS in terms of an abstraction, with the namespace path only as an example — because CNI is not Linux-only:

    - `CNI_NETNS`: A reference to the container's "isolation domain". If using network namespaces, then a path to the network namespace (e.g. `/run/netns/[nsname]`)
    CNI spec 1.1.0, § Parameters — SPEC.md

    Verify

    You can name all six parameters and say what each is for, including why CNI_NETNS is a path rather than a PID. You can attach a namespace to a network by hand, and you can read a v1.1.0 result — in particular, what ips[0].interface indexes.

    Gotchas
    • CNI_ARGS is not a free-form bag. The reference plugins fail with code 999 on any key they do not know, so a runtime that wants to pass pod metadata through must send IgnoreUnknown — a convention, not a spec field. If you write a plugin that rejects unknown args without honouring it, you will break under every real runtime.
    • The container ID is the sandbox's, not the app container's. A pod with six containers involves exactly one CNI attachment, filed under the sandbox ID. Looking for a per- container reservation is looking for something that never existed.
    • A successful ADD leaves lo down. The interface plugin does not touch loopback; something else has to. I9.11 is about what happens when nothing does.

    You have just done by hand what W4.2 — build a pod network by hand does inside a cluster, and what W4.3 — find a real pod's veth peer on the node asks you to trace afterwards. The cni-<uuid> path you were pointed at is the one I8.5 dissected; the primitives themselves are B9.2 — a veth pair is a virtual patch cable and B9.3 — a bridge is a virtual switch.

    Docs: the parameter list is § Parameters of SPEC.md; the IgnoreUnknown convention and the capability-args mechanism are in the neighbouring CONVENTIONS.md, which is where anything not in the spec proper gets written down.

    I9.3

    Five operations, and the most-violated MUST in the spec

    Why it matters

    There is one sentence in the CNI specification that gets broken more than any other, and breaking it produces a symptom every Kubernetes operator has seen: a pod stuck in Terminating forever. The sentence is three lines long and it is about DEL. Learning it properly here means recognising that symptom instantly, and never writing the bug yourself.

    The concept

    Take the operation count from the spec's own words rather than from a blog post, because the counting is genuinely awkward. The spec says:

    The operations, as the document itself enumerates them:

    CNI defines 5 operations: `ADD`, `DEL`, `CHECK`, `GC`, and `VERSION`. These are passed to the plugin via the `CNI_COMMAND` environment variable.
    CNI spec 1.1.0, § CNI operations — SPEC.md

    …and then defines STATUS in a section of its own, alongside those five, with its own error codes. So there are five named in the sentence and six you can send. Say it that way; anyone who tells you flatly "CNI has six verbs" is quoting something the spec does not say, and anyone who says four is reading the older document at library tag v1.1.0.

    OperationJobRequiresOutput on success
    ADDCreate or adjust the interfaceCOMMAND, CONTAINERID, NETNS, IFNAMEA result object
    DELRemove it, or undo the modificationCOMMAND, CONTAINERID, IFNAME — NETNS is optionalNothing
    CHECKConfirm the attachment is still as promisedSame as ADD, plus prevResult on stdinNothing
    GCReclaim anything not in the list of live attachmentsCOMMAND, PATHNothing
    STATUSDeclare readiness to serve ADDsNothing but the configNothing
    VERSIONReport supported spec versionsNothing but the configA version object

    Only ADD, DEL, CHECK and VERSION are expected of every plugin; GC and STATUS arrived in 1.1.0 and I9.14 measures how many plugins actually implement them. Note the third column: DEL is the only operation for which CNI_NETNS is optional, and that is not an oversight. It is the spec conceding that teardown routinely happens after the namespace is gone.

    Which brings us to the sentence. A plugin author writes ADD first, tests it, writes DEL, and returns an error when the interface is missing, because "that shouldn't happen." It happens constantly:

    • the runtime's call timed out and it retried, so DEL arrives twice;
    • the node rebooted between ADD and DEL;
    • the sandbox was torn down and the kubelet is reconciling again after a restart;
    • the ADD itself failed halfway, and the runtime is calling DEL to clean up something that was never fully created.

    A DEL that returns an error tells the runtime the teardown failed. The runtime does the correct thing with that information: it retries, with backoff, forever. From the outside that is a pod in Terminating that never leaves, and the plugin's own logs — if it has any — say "interface not found," which reads like a diagnosis rather than the bug it is.

    So the rule for the project, and for any plugin you ever touch: write DEL first, and write it to succeed against an empty world.

    The requirement, and the best-effort principle behind it:

    Plugins MUST accept multiple `DEL` calls for the same (`CNI_CONTAINERID`, `CNI_IFNAME`) pair, and return success if the interface in question, or any modifications added, are missing.
    CNI spec 1.1.0, § DEL — SPEC.md

    And on the runtime's side, the obligation that makes it unavoidable:

    The container runtime must ensure that _add_ is eventually followed by a corresponding _delete_. The only exception is in the event of catastrophic failure, such as node loss. A _delete_ must still be executed even if the _add_ fails.
    CNI spec 1.1.0, § Lifecycle & Ordering

    Gotchas
    • A silent DEL is a successful DEL. If you are looking for confirmation in the output, there isn't any — check the exit status. Plugins that print "removed interface eth0" on stdout are corrupting the result channel, which is I9.4's fault.
    • Idempotency is not the same as best-effort, and the spec asks for both. Idempotent means the second call succeeds. Best-effort means the first call keeps going after one step fails, cleaning up what it still can, rather than aborting halfway. A plugin that bails on the first missing resource is technically idempotent and still leaves garbage behind — which is exactly the leak I9.9 measures in the reference plugin.
    • "That shouldn't happen" is the whole bug. Every scenario in step 3 is routine. Design DEL for a world where nothing you expect to exist does.

    The Terminating-forever symptom is triaged in W6.11 — the kubelet classics, and a pod whose network teardown fails is one of the cases W4.8 — break the CNI on purpose and read the signatures plants. The idempotency requirement has the same shape as the one I8.11 — teardown, in reverse, and what happens when you get it wrong made about CRI: interfaces that expect to be retried must make retrying safe.

    Docs: read § DEL and § Lifecycle & Ordering of SPEC.md together — the plugin's obligation and the runtime's are two halves of one argument. In the exam docs, search pod termination for the lifecycle the stuck state belongs to.

    I9.4

    Errors are objects with numbers — and stdout belongs to the result

    Why it matters

    A CNI error is structured data, which is what lets a runtime tell "this plugin cannot speak your version" apart from "the network is broken" and act differently. But that only works if the plugin produces the object instead of printing a sentence. Get this backwards and you generate one of the most disorienting messages in Kubernetes: a JSON parse failure while creating a pod sandbox, which sends the operator to investigate the runtime when the actual bug is a debugging echo in a shell script.

    The concept

    On failure a plugin exits non-zero and writes an object with four fields: cniVersion, a numeric code, a short msg, and an optional longer details. Codes 0–99 are reserved by the spec; 100 and up are the plugin's own.

    CodeMeaningWhat the runtime can do with it
    1Incompatible CNI versionRetry at a lower version, or fail fast with a clear message
    2Unsupported field in the network configurationSurface the offending key to the operator
    3Container unknown or does not existSkip the DEL — there is nothing to clean up
    4Invalid environment variablesA bug in the runtime, not the network
    5I/O failurePossibly transient
    6Failed to decode contentMalformed configuration or result
    7Invalid network configAn operator has to fix a file; retrying is pointless
    11Try again laterRetry — a transient condition the plugin expects to clear
    50 / 51Plugin not available (STATUS only)Stop sending ADDs to this node

    Look at the third column and the value of the scheme becomes obvious. Code 11 means retry; code 7 means stop and page someone. Code 3 means the runtime can skip teardown entirely. A bare exit 1 with a message on stderr collapses all of that into "something went wrong."

    The channel rule follows from this, and it is absolute: stdout is the result channel. Every human-readable word goes to stderr. Not "should mostly" — a single stray line on stdout makes the whole invocation unparseable, because the runtime is reading that stream as JSON and nothing else.

    The error object, and the sentence that settles the channel question the overview muddled in I9.1:

    Plugins should output a JSON object with the following keys if they encounter an error:

    - `cniVersion`: The protocol version in use - "1.1.0"
    - `code`: A numeric error code, see below for reserved codes.
    - `msg`: A short message characterizing the error.
    - `details`: A longer message describing the error.
    CNI spec 1.1.0, § Error — SPEC.md
    In addition, stderr can be used for unstructured output such as logs.

    I9.5

    Two directories the spec never mentions — and what really decides which network wins

    Why it matters

    Everyone learns "configs in /etc/cni/net.d, binaries in /opt/cni/bin, the first file wins." Two of those three claims are conventions rather than requirements, and the third is a simplification that will mislead you at exactly the wrong moment. This lesson replaces the folk rule with the two real mechanisms — which are different for libcni and for containerd — because an operator who believes the folk rule adds a file expecting it to be ignored and silently moves every new pod onto a different network.

    The concept

    Start with what may be the most surprising fact in this module. The CNI specification contains no mention of /etc/cni/net.d, no mention of /opt/cni/bin, and no mention of lexical ordering. Grep the document; there are zero hits. It says a runtime "must be provided a list of paths to search for CNI plugins" and leaves both the search paths and how a configuration is chosen entirely to the runtime.

    So those paths are containerd's configuration, and you can read them from containerd rather than from memory. That is where the decisive setting lives too, and it is not the one people quote.

    Now the two mechanisms, which really are different:

    libcni — the library cnitool, containerd and CRI-O all use — resolves a network by name. Its LoadNetworkConf(dir, name) scans .conflist files only, sorts them, and returns the first whose name field matches what you asked for. Only if no .conflist matched does it fall back to the deprecated single-plugin .conf/.json form. That produces two rules people rarely state:

    • Sort order decides only among files that all carry the name you asked for. A later-sorting file absolutely does win if it is the only one with that name.
    • Every .conflist outranks every .conf, regardless of sort order, because they are two separate passes.

    containerd's CRI plugin does something simpler and stricter: it loads maxConfNum configurations — which defaults to 1 — taking them in sorted order, and uses that one for every pod. It never asks for a network by name, so the name field is irrelevant to the choice. This is where "the first file wins" is true, and maxConfNum: 1 is the setting that makes it true.

    And the extension matters more than the number. libcni matches on the file's final extension, so 10-flannel.conflist.orig has extension .orig and is never read at all. The commonly-repeated warning that a .orig backup is still a live config is wrong — but the underlying fear is right, because a file named 05-cilium.conflist dropped next to 10-flannel.conflist genuinely does take over the node.

    What the spec actually delegates, and how little it constrains:

    Furthermore, the runtime must be provided a list of paths to search for CNI plugins. This must also be provided to plugins during execution via the `CNI_PATH` environment variable.
    CNI spec 1.1.0, § Attachment Parameters — SPEC.md

    That is the whole of it. No directory, no ordering, no file naming. Everything in this lesson below that sentence is implementation behaviour you have to verify per runtime — which is why the lab verifies it.

    I9.6

    Chaining: prevResult on the wire, and why order is not a preference

    Why it matters

    A real node's network configuration is not one plugin, it is four or five in a row. Understanding how they hand work to each other explains why the ecosystem's plugins stay so small, why hostPort is implemented by something that never allocated an address, and why swapping two entries in a list breaks a node in a way the error message describes perfectly — if you know what it is telling you.

    The concept

    A .conflist holds a plugins array, and the runtime executes them in order. The first is an interface plugin: it creates the interface and gets it an address. Each one after it is a chained plugin, and it receives everything the earlier plugins built, as a prevResult object injected into its configuration on stdin.

    That single mechanism is why the plugin set is a set of small tools rather than one large one:

    bridgecreates eth0, gets 10.92.0.2→portmapwrites DNAT to 10.92.0.2→bandwidthshapes that veth→tuningsets sysctls in that namespace

    portmap needs to know the pod's address in order to write a DNAT rule pointing at it, and it gets that address without ever having asked IPAM for anything. bandwidth shapes the interface it is told about. tuning sets sysctls on it. None of them can work first, because none of them creates anything to work on — and that is not a convention or a preference, it is what "chained plugin" means.

    Teardown reverses it. On DEL the runtime walks the array backwards, so the last plugin added is the first undone, and every one of them is handed the final result of the original ADD rather than a partial one. That is why the runtime has to remember the result at all — and it does, in a cache file on disk, which the lab reads.

    Chaining, from the runtime's side:

    2. Derive request configuration from the plugin configuration, with the following parameters:
    - If this is the first plugin in the list, no previous result is provided,
    - For all additional plugins, the previous result is the result of the previous plugins.
    CNI spec 1.1.0, § Adding an attachment — SPEC.md

    And the two rules that govern teardown:

    - The list of plugins is executed in **reverse order**
    - The previous result provided is always the final result of the _add_ operation.
    CNI spec 1.1.0, § Deleting an attachment

    Which forces an obligation on the runtime that is easy to miss, and is the reason a cache exists:

    The runtime must store the result returned by the final plugin persistently, as it is required for _check_ and _delete_ operations.
    CNI spec 1.1.0, § Adding an attachment

    I9.7

    Versions are negotiated per plugin, and the result's shape changes with them

    Why it matters

    The cniVersion in a config file is not documentation and it is not a compatibility declaration about your cluster. It is a request for a particular result format, made independently to each plugin in the chain. Get it wrong in a plugin you write and the result will be parsed, misread, and fail somewhere that blames a different component entirely.

    The concept

    Each plugin advertises the set of spec versions whose results it can produce, via CNI_COMMAND=VERSION. The configuration names one of them. Because the negotiation is per-plugin and per-invocation, a chain can legitimately mix plugins built against different spec generations, as long as each supports the version being asked for. There is no cluster-wide CNI version, and nothing to upgrade in lockstep.

    The differences between generations are small in count and large in consequence:

    VersionResult shapeArrived with
    0.1.0–0.2.0Flat: a single ip4 (and ip6) object. No interface list at all.The original
    0.3.0–0.3.1interfaces + ips + routes, with ips[].interface indexing the arrayThe structure still in use
    0.4.0Same shapeCHECK
    1.0.0Same shape, dns no longer emitted when emptyStability commitment
    1.1.0Same shapeGC, STATUS, and the cniVersions array

    The one real break is between 0.2.0 and 0.3.0: the flat ip4 object was replaced by the interfaces/ips pair, and there is no way to express "which interface" in the older form. libcni converts between the shapes so a modern runtime can still drive an ancient plugin, which is why those versions are still in every plugin's supported list rather than removed.

    1.1.0 also added a second way to state the version: cniVersions, an array of acceptable versions, letting the runtime pick the highest that everything in the chain supports rather than forcing the config author to guess the floor.

    Who chooses, and on what basis:

    CNI runtimes MUST select the highest supported version from the set of network configuration versions given by the `cniVersion` and `cniVersions` fields. Runtimes MAY consider the set of supported plugin versions as reported by the VERSION command when determining available versions.
    CNI spec 1.1.0, § Version considerations — SPEC.md

    Note the asymmetry: consulting the config is a MUST, consulting the plugins is only a MAY. So a runtime is permitted to ask for a version a plugin cannot do and let the plugin refuse — which is precisely what step 3 below demonstrates.

    • Claiming a version you do not implement is worse than claiming a lower one. A plugin that advertises 1.1.0 and emits a 0.3.1-shaped result will be parsed against the wrong schema.     • cniVersions is 1.1.0-only. A conf using it against an older runtime has no cniVersion at all, which is a config error rather than a graceful downgrade. Keep both fields if you need to support both.

    I9.8

    cnitool: a runtime you can drive by hand

    Why it matters

    Debugging a plugin through a Kubernetes pod means a sandbox creation, a kubelet retry backoff, and a hunt through two logs for each attempt. Debugging it through cnitool means one command and a JSON blob on your terminal. This is the tool you will build the project with, and the difference in iteration speed is roughly two orders of magnitude.

    The concept

    cnitool is a thin command-line wrapper over libcni — the same library containerd and CRI-O link against. It finds configurations, orders the chain, injects prevResult, marshals stdin, parses results, and maintains the attachment cache. So "it works under cnitool" is a meaningful statement about spec compliance, not a toy result: the code doing the driving is the production code.

    What it adds on top is a command line: cnitool add|check|del|gc|status <net> <netns>, where <net> is a network name (I9.5's resolution rule) and <netns> is a namespace path. Two environment variables steer it: NETCONFPATH for the config directory — which is how you experiment without touching /etc/cni/net.d — and CNI_PATH for the binaries.

    One behaviour is worth knowing before it confuses you: cnitool derives the container ID deterministically from the namespace path. The same netns always produces the same cnitool-<hex> ID. That is genuinely useful — it means you can run del twice against the same namespace and be testing real idempotency rather than two unrelated attachments — but it also means a leaked reservation from an earlier experiment will collide with your next one on the same namespace, and the error will not mention that.

    It is not packaged for Ubuntu 24.04, so you build it. That is one command and about twenty seconds.

    What you are standing in for when you drive a plugin by hand is a runtime, and the spec constrains one in ways worth knowing before you start hammering the same namespace:

    - The container runtime must not invoke parallel operations for the same container, but is allowed to invoke parallel operations for different containers. This includes across multiple attachments.
    - **Exception**: The runtime must exclusively execute either _gc_ or _add_ and _delete_. The runtime must ensure that no _add_ or _delete_ operations are in progress before executing _gc_, and must wait for _gc_ to complete before issuing new _add_ or _delete_ commands.
    CNI spec 1.1.0, § Lifecycle & Ordering — SPEC.md

    And on CHECK, the rule that makes step 5's failure a diagnosis rather than something to retry:

    - A runtime may assume that a failed `CHECK` means the container is permanently in a misconfigured state.
    CNI spec 1.1.0, § CHECK — Runtime considerations

    I9.9

    bridge, read against your own net-up.sh — and the leak it hides

    Why it matters

    This is the module's thesis made literal. Put the reference bridge plugin next to the bash script you wrote in B9 and the mechanism is the same, step for step. What the plugin adds is the contract — and, it turns out, four pieces of hard-won operational detail your script did not have, plus one bug your script cannot have because it never claimed to be idempotent.

    The concept

    net-up.sh and bridge do the same seven things:

    Stepnet-up.sh (B9.19)bridge plugin
    Create the bridge if absentip link add cni0 type bridgeSame, plus reconciles an existing bridge's settings
    Give it the gateway addressip addr add 10.20.0.1/24Same, when isGateway
    Make a veth pairip link add veth1 type veth peer name eth0Same, host side named from a hash
    Move one end into the namespaceip link set eth0 netns pod1Same, using CNI_NETNS
    Name it, address it, route itThree ip commands in netns execSame, address from the IPAM plugin
    Turn the host into a routersysctl net.ipv4.ip_forward=1Same
    Masquerade egressOne -s 10.20.0.0/24 -o ens3 -j MASQUERADEA per-container chain

    No new mechanism. Not one. The difference is in the last row and in four details the lab measures — and the four are exactly the kind of thing you only write after being paged:

    1. The masquerade rule is per pod, not per subnet. net-up.sh writes one rule covering the whole range, which can only ever be removed all at once. The plugin writes -s 10.90.0.2/32 → CNI-<hash>, and inside that chain it ACCEPTs traffic destined for the pod subnet before masquerading anything, and excludes multicast. Pod-to-pod traffic that leaves the bridge therefore keeps its real source address, where the blanket rule's correctness depended on the -o ens3 qualifier.
    2. hairpin_mode on the bridge port. Without it a frame cannot leave the bridge by the same port it entered, so a pod cannot reach itself through its own Service VIP — a failure that looks like a broken Service and is a bridge setting.
    3. accept_ra=0 on the host-side veth. The host stops accepting IPv6 router advertisements from inside the container. net-up.sh leaves this at 1, meaning a container could advertise itself as the node's IPv6 router.
    4. arp_notify=1 inside the namespace. The interface sends a gratuitous ARP on coming up, so the bridge learns its MAC immediately instead of on first traffic.

    And then there is the thing the plugin gets wrong, which is the most useful part of this lesson. bridge's DEL learns the container's address by reading it out of the network namespace. When the namespace is already gone — a routine situation, per I9.3 — it cannot learn the address, so it cannot construct the rule to delete. It returns success, correctly, because the idempotency MUST requires that. And the masquerade rule stays on the node forever.

    The best-effort principle that makes the leak conformant, and names bridge specifically:

    Plugins should generally complete a `DEL` action without error even if some resources are missing. ... For another example, the `bridge` plugin should delegate the DEL action to the IPAM plugin and clean up its own resources even if the container network namespace and/or container network interface no longer exist.
    CNI spec 1.1.0, § DEL — SPEC.md

    Read the last clause closely: it says the plugin should clean up its own resources in that situation. The measurement below shows it does not manage to, for the one resource whose identity it only knows via the namespace.

    I9.10

    host-local IPAM: a directory of files, and the node that has no addresses left

    Why it matters

    An entire genre of node incident lives in one directory. A node reports that it cannot start pods because there are no IP addresses available — and it has none running. The error message mentions no file, no directory and no plugin state. The evidence is a single ls, and after this lesson you will know which one.

    The concept

    IPAM is a separate plugin, not a feature of the bridge. The ipam block in a configuration names its own type, and the interface plugin delegates to it: bridge execs host-local, passing the same environment parameters along, and uses whatever address comes back. That is why CNI_PATH matters even when your conflist names only one plugin, and why a missing IPAM binary produces an error from a plugin you did not configure.

    The split is a good design. It is also where the accounting lives, and host-local's accounting is about as simple as accounting gets: one file per allocated address, in a directory named after the network, whose filename is the address and whose contents are the holder.

    /var/lib/cni/networks/<network-name>/
├── 10.90.0.2            "<container-id>\r\n<ifname>"
├── 10.90.0.3
├── 10.90.0.4
├── last_reserved_ip.0   the highest address handed out so far
└── lock                 flock target, so concurrent ADDs cannot collide

    There is no TTL, no lease, no heartbeat, no reconciliation against reality, and no coordination beyond that lock file. A file is a reservation, whatever wrote it and whether or not its holder still exists. Every DEL that did not run leaves one behind permanently — and I9.9 just established several routine ways for a DEL not to run, or to run and not finish.

    Two behaviours of the allocator matter for diagnosis. It walks forward from last_reserved_ip.0 and does not backfill released addresses, so the addresses in use are not a contiguous block and a gap does not mean a free address will be reused soon. And last_reserved_ip.0 survives a DEL, so the pointer keeps climbing even as the store empties.

    The spec treats IPAM as a delegated plugin with a defined obligation on teardown, which is exactly why the reservation is released even when the interface cleanup fails:

    Plugins should generally complete a `DEL` action without error even if some resources are missing. For example, an IPAM plugin should generally release an IP allocation and return success even if the container network namespace no longer exists, unless that network namespace is critical for IPAM management.
    CNI spec 1.1.0, § DEL — SPEC.md

    Note what the spec does not do: it never describes where reservations are stored, or in what format. That is entirely host-local's invention, which is why a different IPAM plugin's exhaustion looks nothing like this one's.

    I9.11

    loopback, static, macvlan and ipvlan — the rest of the set in one sitting

    Why it matters

    loopback is the plugin nobody thinks about, and forgetting it produces failures that look like anything except networking — a health check that never passes, a sidecar that cannot reach the app next to it, a database client that cannot connect to its own machine. And macvlan versus ipvlan is a distinction people repeat vaguely; one command settles it permanently.

    The concept

    Four plugins, each answering a different question.

    loopback brings lo up inside the namespace and gives it 127.0.0.1/8 and ::1/128. It is mandatory, and the reason is that a fresh network namespace has a loopback interface that is down — you saw this in I9.2 and again after a successful ADD. An enormous amount of software assumes 127.0.0.1 works unconditionally, because on any real machine it does. Notice also that the runtime calls it as its own attachment with CNI_IFNAME=lo, not as part of the eth0 chain.

    static is an IPAM plugin that takes the address from the configuration instead of a store. No allocation, no reservation file, no state at all — which makes it perfect for a single fixed-address appliance and dangerous everywhere else, because it has no way to know an address is already in use.

    macvlan gives the container its own MAC address on the parent interface's LAN. The container is a peer of the node on the physical network: no bridge, no veth, minimal overhead, and its traffic never traverses the host's IP stack. The catch is that the parent's switch port now sees several MAC addresses, and many switches (port security) and essentially all cloud providers refuse that.

    ipvlan solves that by sharing the parent's MAC and splitting traffic by IP address at layer 3. It survives one-MAC-per-port restrictions, at the cost of L2 features — no broadcast/multicast to the container in L3 mode, and DHCP needs care since every container looks like the same MAC.

    Both put pods directly on the physical network with no encapsulation and no NAT, which is why they turn up in bare-metal, telco and NFV clusters, and almost nowhere else. The single distinguishing fact — own MAC versus shared MAC — is what the lab measures, and it takes one command.

    The spec says nothing about which plugins exist; the plugin set is a separate repository with its own release cycle. What the spec does define is the delegation that makes IPAM a plugin in its own right:

    - **Capability Arguments**: These are also key-value pairs. The key is a string, whereas the value is any JSON-serializable type. The keys and values are defined by [convention](CONVENTIONS.md).
    CNI spec 1.1.0, § Attachment Parameters — SPEC.md

    The practical consequence for this lesson: ipam.type naming another executable is a convention documented outside the spec, and swapping host-local for static or dhcp is a one-word config change precisely because of it.

    Gotchas

    • macvlan on a cloud instance usually fails silently rather than loudly. The interface comes up and the address is assigned; the packets just never arrive, because the hypervisor drops frames from unexpected MACs. Nothing logs it.
    • ipvlan in L3 mode drops broadcast and multicast to the container. Anything relying on discovery protocols, ARP-based failover, or mDNS will behave strangely in ways that look like an application problem.
    • static plus a templating mistake is a duplicate-address outage. Because it has no store, the only thing preventing collisions is whoever wrote the config.

    I9.12

    portmap, bandwidth and tuning — and finding your own B9 rule in a production stack

    Why it matters

    This is the lesson where the black box opens for good. A pod spec's hostPort becomes a capability argument, which becomes an iptables DNAT rule in the node's nat table — and that rule is the one you wrote by hand in B9.16. Not analogous to it. The same rule. Once you have seen that, "how does hostPort work" stops being a question you look up.

    The concept

    Three chained plugins, three different kernel subsystems, one pattern: each is handed the interface and address in prevResult and configures one thing about it.

    PluginWhat it programsWhere the state livesBeginner lesson
    portmapDNAT from a host port to the pod's addressiptables nat tableB9.16
    bandwidthA token-bucket qdisc on the veth, plus an ifb device for the other directiontc, on the host side—
    tuningsysctls, and optionally the MAC/MTU/promisc flags/proc/sys, inside the namespaceB9.6

    portmap is the one with consequences beyond itself. Because the rule it writes lives in the node's nat table and matches on a host port, two pods wanting the same host port on one node cannot both work — the first matching rule wins, and the second pod's rule is never reached. That is why hostPort is a scheduling constraint: the scheduler treats the port as a consumable node resource and refuses to place a second claimant. I8 measured what happens when nothing enforces that — CRI itself does not deduplicate, so two sandboxes each got their rule and the first one won.

    bandwidth has a wrinkle worth knowing: shaping only works on egress from an interface, so limiting traffic into a pod requires redirecting it through an intermediate functional block (ifb) device and shaping that device's egress instead. So one rate limit creates a device you did not ask for, named after the container.

    tuning's sysctls apply inside the network namespace, which means they are per pod and invisible from the host — the same value read in two places gives two answers. That is the whole point, and it is also how a "we set this sysctl and nothing changed" ticket happens.

    Capability arguments are how a runtime passes structured, per-attachment data like a port list. The mechanism is defined by convention rather than in the spec proper:

    Certain flags may be passed as "capability arguments" to plugins. These are also key-value pairs, where the key is a string and the value is any JSON-serializable type. ... To signal that a plugin accepts a capability argument, the plugin configuration must include a `capabilities` key.
    CNI CONVENTIONS.md — CONVENTIONS.md

    That "capabilities": {"portMappings": true} line in every conflist you have seen is the plugin opting in. Without it the runtime will not pass the port list, and the plugin will do nothing while succeeding.

    I9.13

    Who actually execs the plugin — and what "installing a CNI" really is

    Why it matters

    Two questions get answered wrong constantly. "Does the kubelet run the CNI plugin?" — no, and knowing that removes a whole component from your search during an outage. "What does installing a CNI provider consist of?" — a privileged DaemonSet that writes one file and copies some binaries, plus a daemon that stays running to do the part CNI deliberately does not specify. Getting that split straight is the difference between fixing a broken cluster network in five minutes and restarting things hopefully.

    The concept

    containerd's CRI plugin execs the plugin, during RunPodSandbox, before any application container exists. The kubelet never touches /opt/cni/bin. It asks CRI for a sandbox; the runtime creates the network namespace, pins it, runs the CNI chain against it, and returns the resulting pod IP in the sandbox's status. The kubelet learns the pod's address as a field in a gRPC response, which is why kubectl get pod -o wide can show an IP for a pod whose containers have not started.

    That ordering — namespace, then CNI, then pause, then app containers — is I8.7's finding, and it is why the pause container does not "hold" the pod's network namespace. The namespace was pinned and wired before pause existed.

    Now "installing a CNI". Strip the marketing and a provider's DaemonSet does three things on every node:

    1. Copies binaries into /opt/cni/bin from its container image.
    2. Writes a .conflist into /etc/cni/net.d. This is the moment the node's network becomes ready — and, per I9.5, the moment its filename starts deciding things.
    3. Leaves a daemon running, which is doing work CNI has no vocabulary for.

    That third item is the important one, and it is where the honest boundary lies:

    CNI's jobThe provider's daemon's job
    Attach one pod on this node to a network, and report its addressLearn every node's pod subnet from the API server
    Detach it againProgram routes, or VXLAN FDB entries, or BGP sessions, so nodes can reach each other's pods
    —Enforce NetworkPolicy
    —Watch for node additions and removals

    Nothing in the CNI specification concerns node-to-node reachability. That is why the datapath families in W4.7 differ so wildly — overlay, routed, eBPF — while all of them speak the same twenty-line contract. The contract covers the last hop only.

    And it explains the shape of the most common "the cluster network is broken" incident: a node is NotReady with NetworkReady: false because a file is missing, which happens before any daemon has had a chance to misbehave. I8 measured a nasty property of that recovery path — restoring a deleted conf file with mv does not reload it, because containerd watches for filesystem events that mv into place does not generate. Only a content-writing cp works.

    The spec assigns the namespace's creation and cleanup to the runtime, and says nothing whatever about how nodes reach each other:

    - The container runtime must create a new network namespace for the container before invoking any plugins.
    ...
    - The container runtime is responsible for cleanup of the container's network namespace.
    CNI spec 1.1.0, § Lifecycle & Ordering — SPEC.md

    "Before invoking any plugins" is the sentence that settles the pause-container question, and the second bullet is why a plugin that cannot find CNI_NETNS on DEL should not treat that as an error.

    I9.14

    GC and STATUS: what 1.1.0 added, and what today's plugins do with it

    Why it matters

    Both verbs 1.1.0 added exist to delete a class of race by replacing a bad inference with a statement. Both are well designed. And on the plugin set your cluster is almost certainly running, neither does anything at all — which is a more useful thing to know than the design intent, because it means I9.10's field repair is still the field repair.

    The concept

    GC exists because nothing could safely clean up leaked IPAM reservations. The plugin sees one call at a time and cannot know what else should exist; the runtime knows the full set of live attachments but does not own the reservation store. Neither party has enough information alone. GC closes the loop: the runtime hands the plugin cni.dev/valid-attachments — the complete list of (containerID, ifname) pairs that should exist — and everything else is the plugin's to reclaim.

    STATUS exists because runtimes used to infer readiness from a file's existence. A conf file appearing meant "network ready", so nodes went Ready and accepted pods a fraction of a second before their provider's agent had finished programming routes, producing pods with addresses that could not reach anything. STATUS lets the plugin say so itself, with codes 50 ("cannot service ADD") and 51 ("and existing containers may have limited connectivity").

    In libcni, GC is two phases, and confusing them will make the lab's results look like bugs:

    1. libcni synthesises a DEL for every attachment in its own result cache (I9.6's /var/lib/cni/results/) that is not in the valid list. This works against any plugin, including ones predating 1.1.0 — it is just ordinary teardown.
    2. Then it calls CNI_COMMAND=GC on each plugin with the valid-attachments list injected — but only if the conflist's cniVersion is at least 1.1.0.

    Phase one depends on the cache; phase two depends on the plugin. That distinction is the whole lesson, because the cache lives in /var/run — a tmpfs — while reservations live in /var/lib. A reboot destroys the cache and preserves the reservations, which is precisely the situation GC was invented for and precisely the one where phase one has nothing to work from.

    The verb, its input, and the sentence that stops anyone treating it as a shortcut:

    The GC command provides a way for runtimes to specify the expected set of attachments to a network. The network plugin may then remove any resources related to attachments that do not exist in this set.
    - `cni.dev/valid-attachments` (array of objects): The list of **still valid** attachments to this network:
    - `containerID` (string): the value of CNI_CONTAINERID as provided during the CNI ADD operation
    - `ifname` (string): the value of CNI_IFNAME as provided during the CNI ADD operation
    The runtime MUST NOT use GC as a substitute for DEL. Plugins may be unable to clean up some resources from GC that they would have been able to clean up from DEL.
    CNI spec 1.1.0, § GC — SPEC.md

    One implementation detail the spec does not mention and libcni does: it injects the list under two keys, because of a naming mistake in the spec text — cni.dev/valid-attachments and also cni.dev/attachments, with the comment // #1101: spec used incorrect variable name. A plugin should accept either.

    You can explain what bad inference each verb replaces.     Gotchas
    • "CNI 1.1 has GC, so leaked addresses are solved" is false today. The spec has it, libcni has the runtime half, and the plugins do not have the plugin half. Check before relying on it: run CNI_COMMAND=GC against your IPAM plugin with an empty list and see whether anything changes.
    • The result cache is in /var/run and does not survive a reboot; reservations are in /var/lib and do. That asymmetry is why GC's cache-based phase cannot fix the post-reboot case, which is the main case.
    • GC is not a substitute for DEL, and the spec says so explicitly. A runtime that skips teardown intending to sweep later will leak everything a plugin can only clean up when the namespace still exists.
    • A conflist below cniVersion: 1.1.0 cannot be asked for either verb. The refusal is code 1 from skel, before any plugin logic runs.
    • STATUS is advisory and a plugin must not rely on being called. The spec is explicit that other operations arrive regardless of what STATUS said, so it can never be used as an admission gate.

    NetworkReady — the condition STATUS was designed to inform — is the one you read in I8.3 and break in W4.8 — break the CNI on purpose and read the signatures. The wider pattern, replacing an inference with a statement so a race disappears, is B13.12 — the reconciliation loop, and watch versus poll; the accounting that outlives what it accounts for is I9.10, and I7.13 measured containerd's own GC doing this job properly for content.

    Mini project — cni-minibridge, and containerd calling your bash script

    Why it matters

    By the end of this lesson containerd will create a pod sandbox, exec a shell script you wrote, take the IP address that script prints, and serve HTTP traffic to a container through it.     The concept

    labs/intermediate/cni-minibridge is net-up.sh with a contract bolted on. The mechanism is unchanged: a bridge, a veth pair, an address, a route, a masquerade rule. Everything new is protocol.

    The design decisions that matter, each one traceable to a lab earlier in this module:

    DecisionWhy, and where it came from
    Every diagnostic goes to stderr via one log() helperI9.4 — one stray stdout line makes the result unparseable
    Errors are objects built by jq, with the spec's codesI9.4 — and it returns 7 for an unusable config where the reference returns 999
    CNI_COMMAND is validated before stdin is readA missing verb is code 4, not a config error; diagnosing it needs no config
    DEL finds the address in the store, never the namespaceI9.9 — the leak. This is the single most important line in the file
    Reservations are CRLF, in host-local's formatI9.10 — one set of tools then reads both stores
    Every read-modify-write of the store holds flockThe spec requires plugins to handle concurrent execution and lock shared IPAM state
    The masquerade rule is per address, with ! -d $SUBNETI9.9 — per-pod so DEL can remove exactly one, subnet-exempt so pod-to-pod is not NATed
    GC is implementedI9.14 — no reference plugin does, so leaked reservations are still cleaned by hand
    STATUS returns code 50 on an exhausted poolI9.14 — the case those codes exist for, which host-local never reports
    A failed wiring step rolls back its own workI9.4 — otherwise the retry reports "already exists" and hides the real cause

Anything else gets a temporary bind mount into that directory, which is precisely how ip netns and containerd pin a namespace in the first place.

    I9.16

    Debugging drill — three faults that blame the wrong thing

    Why it matters

    Each of these three faults produces a symptom that points somewhere other than its cause. One reports a JSON parsing problem, one reports an address shortage on a node running nothing, and one reports nothing at all — it just quietly changes which network every new pod joins. Plant them, read them from the symptom end, and the next time you meet one in a cluster you will recognise it in seconds.

    The concept

    Work each fault the same way. Write down the symptom exactly as an operator would see it. Then ask the question this module has been training: which side of the contract is this? A malformed result is the plugin's side. An exhausted store is the plugin's state. A wrong config file is the runtime's selection. Those three are diagnosed with three different commands and none of them is systemctl restart.

    The sentence behind fault 3, which the drill will show being violated in the most ordinary way possible:

    - The network configuration should not change between _add_ and _delete_.
    - The network configuration should not change between _attachments_.
    CNI spec 1.1.0, § Lifecycle & Ordering — SPEC.md

    Quiz

    1. State the CNI contract in one sentence, without using the words "daemon" or "API".
      Answer

      The runtime executes a program, passing configuration as JSON on its standard input and parameters in environment variables, and reads a JSON result from its standard output. That is the whole of it — no daemon, no socket, no library to link.

    2. How many operations does the spec define, and why is the honest answer awkward?
      Answer

      Its own sentence says "CNI defines 5 operations: ADD, DEL, CHECK, GC, and VERSION", and then it defines STATUS in a section of its own alongside them. So five are named and six can be sent. Anyone saying flatly "six verbs" is quoting something the spec does not say; anyone saying four is reading the older SPEC.md at library tag v1.1.0, since the CNI repo's git tags are library releases rather than spec versions.

    3. A pod is stuck in Terminating and the CNI plugin's log says "interface not found". What is the bug, and in which component?
      Answer

      The bug is in the plugin: its DEL returns an error when the interface is missing, violating the spec's requirement that plugins MUST accept repeated DELs and return success when the resources are already gone. The runtime does the correct thing with an error — retries with backoff, forever — so the plugin's honest-looking message is the fault, not a diagnosis of one.

    4. Which parameters does DEL require, and which one is deliberately optional? Why that one?
      Answer

      CNI_COMMAND, CNI_CONTAINERID and CNI_IFNAME are required; CNI_NETNS is optional. That is the spec conceding that teardown routinely happens after the namespace is gone — a node reboot, a sandbox already destroyed — so a plugin that depends on reading the namespace during DEL cannot be correct.

    5. You add 99-mynetwork.conflist to /etc/cni/net.d alongside 10-flannel.conflist and nothing changes. Why? And what would have changed everything?
      Answer

      Containerd loads maxConfNum configurations — 1 by default — in sorted filename order, so 10-flannel wins and 99- is never read. Naming it 05-mynetwork.conflist would have silently moved every new pod onto your network. Higher numbers do not mean higher precedence; they mean lower.

    6. Does 10-flannel.conflist.orig still act as a live configuration file?
      Answer

      No. libcni matches on the file's final extension, which here is .orig, so the file is never read. .bak and .disabled behave the same way. Renaming within .conflist is what does not help.

    7. Why can't portmap be the first plugin in a chain, and what exactly does it say if it is?
      Answer

      It is a chained plugin: it needs the pod's address, which arrives in prevResult from the interface plugin ahead of it, in order to write a DNAT rule pointing at it. First in the list there is no prevResult, so it fails with must be called as chained plugin — identically whether or not port mappings were supplied, because the fault is its position.

    8. A chained plugin returns a result containing only cniVersion. Nothing errors on ADD. What have you broken?
      Answer

      Everything downstream of it. A chained plugin must pass prevResult through; dropping it means later plugins have no addresses to work with, and the runtime caches that truncated result — so every subsequent CHECK and DEL for the attachment is handed an empty picture too. The failure is silent at the point of the bug and surfaces somewhere else.

    9. A node reports "no IP addresses available" and is running three pods on a /24. Where do you look, and what exactly are you comparing?
      Answer

      ls /var/lib/cni/networks/<network>/, and you compare its count of address files against crictl pods -q | wc -l. Each file is a reservation held regardless of whether its holder exists, and every DEL that did not run leaves one forever. Delete only the entries whose holders are gone — never the directory, or you will hand a live pod's address to a new one.

    10. bridge's DEL returned 0 and the pod's masquerade rule is still in the nat table. Is the plugin buggy?
      Answer

      Not by the letter of the spec, which is what makes it interesting. It learns the container's address by reading the namespace, and the namespace was already gone, so it could not build the rule to delete — and returning success in that situation is exactly what the idempotency MUST demands. The IPAM reservation was released, because that is keyed by container ID. Two of three realistic teardown orders leak this way. The fix, which cni-minibridge implements, is to look the address up in your own store instead.

    11. What is the single observable difference between macvlan and ipvlan, and name one practical consequence.
      Answer

      macvlan gives the container its own MAC address; ipvlan shares the parent interface's MAC byte for byte and splits traffic by IP. Consequences follow from that alone: macvlan is refused by switch port security and by essentially every cloud hypervisor, while ipvlan survives those restrictions but loses L2 features such as broadcast to the container in L3 mode.

    12. Why is loopback mandatory, and what does its absence look like?
      Answer

      A fresh network namespace has a loopback interface that is down, and a successful interface-plugin ADD does not bring it up. Without it, ping 127.0.0.1 inside the pod answers "Network is unreachable" — so the symptom is a failing health check, a sidecar that cannot reach its app, or a client that cannot connect to its own machine. Nothing in it says "networking".

    13. Which component execs the CNI plugin, at what moment, and what does the kubelet learn?
      Answer

      Containerd's CRI plugin, during RunPodSandbox, before any application container exists — the kubelet never execs a plugin. It learns the pod's address as a field in the sandbox status returned over gRPC, which is why kubectl get pod -o wide can show an IP for a pod whose containers have not started.

    14. Draw the line: what does CNI specify, and what is a provider's daemon doing?
      Answer

      CNI attaches one pod on one node to a network and reports its address, then detaches it. Everything else is the provider's: learning each node's pod subnet from the API server, programming routes or VXLAN FDB entries or BGP sessions so nodes reach each other's pods, and enforcing NetworkPolicy. Nothing in the spec concerns node-to-node reachability, which is why datapath families differ wildly while all speaking the same contract.

    15. Your cluster runs CNI plugins v1.9.1. Does GC reclaim leaked IPAM reservations?
      Answer

      No. The spec has the verb, libcni has the runtime half, and not one of the reference plugins registers a GC handler — so CNI_COMMAND=GC with an explicit valid-attachments list, or even an empty one, returns 0 and changes nothing. libcni's other GC phase synthesises DELs from its own result cache, but that cache lives in /var/run and does not survive the reboot that caused the leak. The field repair is still rm.

    16. What does cnitool gc <net> <netns> do to a node with live pods?
      Answer

      Tears them all down. Its source passes nil for the valid-attachments list — "Currently just invoke GC without args, hence all network interface should be GC'ed!" — so libcni treats every cached attachment as stale and synthesises a DEL for each. It means "release everything cached", not "reclaim what leaked".

    17. Sandbox creation fails with failed to unmarshal raw result: invalid character 'm' looking for beginning of value. What is wrong, and did the plugin's work succeed?
      Answer

      A plugin wrote a human-readable line to stdout, which is the result channel — the 'm' is the first character of its message. The fix is >&2. And yes, its actual work almost certainly succeeded: the bridge, veth and address were all created before the unreadable report, so a node suffering this accumulates wired namespaces and reserved addresses for pods that never started.

    18. Why does CNI use exec and JSON where CRI needed gRPC and protobuf?
      Answer

      Because the interaction differs, not the subject. CRI is a long-lived bidirectional conversation — streaming logs, attaching to TTYs, watching for exits, polling status. CNI is a one-shot errand: attach this, report the address. The interface's complexity followed the shape of the interaction, which is the most reusable design lesson in this track.

    • You can state the CNI contract in one sentence and demonstrate it in one command, and say why it is exec-based where CRI is gRPC-based.
    • You have invoked a real plugin by hand with all six parameters, and read a v1.1.0 result field by field — including what ips[].interface indexes.
    • You can quote the operation count the way the spec words it, and you know which single MUST produces pods stuck in Terminating when it is broken.
    • You can read an error object's code and decide whether the runtime should retry, fail fast or skip teardown — and you know two places the reference plugins do not conform.
    • You can say what decides which network a node uses, as two different mechanisms for libcni and for containerd, and which renames disable a conflist.
    • You have watched prevResult cross the wire, and can explain what a chained plugin does and does not receive.
    • You have read the reference bridge plugin against your own net-up.sh and found both what the contract added and where the reference silently leaks.
    • You can diagnose a node with no addresses and nothing running, in one ls, and repair it without breaking a live pod.
    • You can trace hostPort from a pod spec to the exact iptables line you wrote by hand in B9.
    • You know who execs the plugin, what "installing a CNI" consists of, and where CNI's responsibility stops and a provider's begins.
    • You have measured what GC and STATUS actually do on today's plugins, rather than what they were designed to do.
    • You have written a spec-compliant plugin that containerd drives for a real pod serving real traffic — and that fixes three things the reference plugins get wrong.
