    I12 — Observability of a running runtime

    The short module that makes the other twelve debuggable. One line of application output, traced from write(2) to the file kubectl logs reads; one number, traced from a cgroup file to a dashboard — and the honest limits of both.

    Everything here is the same move: refuse the dashboard and go find the file. A container's logs are a pipe, a FIFO and a text file. Its metrics are six numbers in /sys/fs/cgroup. Its history is an event stream you can tail. Once you have seen each of those with your own eyes, "the monitoring is wrong" stops being a helpless sentence and becomes a question with a location.

    Checkpoints10 Hours~4 PrerequisitesI7 · I8 · B7
    • Logs — follow one line through all four hops, decode the five-field CRI log format including the partial/full split, and find out who owns rotation (on this node: nobody).
    • Metrics — read the cgroup files that are the only source of any container metric, write valid Prometheus exposition by hand, and get the counter/gauge distinction right before it costs you.
    • Events and deeper — answer "did it exit, or was it never started?" from the runtime's event stream, then profile a container from the host by PID without entering it.
    • Project & drill — build a working exporter in fifty lines, then fix logs that stopped appearing and a memory number that grows on its own.

    I7 (the shim owns the stdio) and I8 (the CRI log format and who chose the directory). B7's cgroup files return as the source of every container metric there is.

    Which machine. Everything below ran on the sandbox VM — Ubuntu 24.04.4 LTS, kernel 6.8.0-136-generic, cgroup v2 — with containerd 2.3.3, runc 1.5.1, crictl v1.36.0, nerdctl 2.3.5, Python 3.12.3, perf 6.8.12 and bpftrace v0.20.2. There is no kubelet on this node, which is the point: every question in this module is answerable from the runtime alone.

    Logs

    I12.1

    One line, all four hops: from write(2) to the file on disk

    Why it matters

    When somebody says "the logs are missing", they have described a symptom with at least four possible locations. The application's output travels through a pipe, a shim, a FIFO and a daemon before it becomes a file anyone can read, and every famous logging surprise is a property of exactly one of those hops. You cannot diagnose a chain you have never seen, so this lesson walks the whole thing once with real commands and real process IDs.

    The concept

    Start from the application's point of view, because it is startlingly simple: the workload does not know it is being logged. It writes bytes to file descriptor 1. That is the entire contract. It cannot tell whether fd 1 is a terminal, a file, a socket or a pipe, and nothing in the container gives it a hint.

    In a container, fd 1 is a pipe — a kernel buffer with a write end and a read end, the same object B2 used for shell pipelines. The read end is held by the shim, the small per-container process I7 introduced as the on-site foreman: the one who stays after runc leaves. This is why the shim exists at all. Someone has to be holding the other end of that pipe every moment the container is alive, and it cannot be the daemon, because the daemon has to be restartable.

    Here is the part most descriptions skip, including this repo's own earlier notes. The shim does not write the log file. It writes into a second IPC object — a FIFO, a named pipe that exists as a path on disk — and containerd reads that FIFO and writes the log file. So the chain has four hops and two different kinds of pipe in it:

    workload fd 1→pipe→shim→FIFO→containerd→0.log

    You can prove every arrow, which is what the lab does. The consequence worth carrying away: the timestamp on each line is written by containerd, at the moment it read the bytes — not by the application, and not when the application decided to log. An application with a buffered writer can emit a burst of lines all stamped within the same millisecond, describing events minutes apart. The timestamps are honest about when the runtime saw the bytes and say nothing about when the events happened.

    The CRI does not describe the pipes at all — those are implementation. What it standardises is where the file goes, and it does so in two halves: the sandbox names a directory, and each container names a path relative to it.

    // Path to the directory on the host in which container log files are
    // stored.
    // By default the log of a container going into the LogDirectory will be
    // hooked up to STDOUT and STDERR. However, the LogDirectory may contain
    // binary log files with structured logging data from the individual
    // containers. […]
    // E.g.,
    //     PodSandboxConfig.LogDirectory = `/var/log/pods/<NAMESPACE>_<NAME>_<UID>/`
    //     ContainerConfig.LogPath = `containerName/Instance#.log`
    CRI api.proto, PodSandboxConfig.log_directory — kubernetes/cri-api

    Note what that means: the runtime does not choose the path — its caller does. On a real node the kubelet fills in those two fields, which is why the layout looks like Kubernetes rather than like containerd. Below, we fill them in ourselves and get to pick.

      FIFO=$(sudo find /run/containerd/io.containerd.grpc.v1.cri -name '*-stdout' | head -1)

    5. Hop 4 — the file, and who owns it. This is the step that corrects the folk model. 
      LOG=$(sudo crictl inspect "$CID" | jq -r .status.logPath)

      The shim has zero file descriptors on the log file. containerd writes it. The shim's job is to hold the pipe and survive; the daemon's job is to format and persist.

    6. The payoff — does a containerd restart lose lines? The chain says the shim keeps buffering while the daemon is away. Test it with a numbered sequence so nothing can hide. 
      # container runs: i=0; while :; do i=$((i+1)); echo "seq $i"; sleep 0.2; done
sudo systemctl restart containerd
sleep 5
sudo awk '{print $NF}' "$LOG" > ~/seq.txt

   END{n=0;for(i in w)n++; print "missing lines: " n}' ~/seq.txt
      restart took 0.20s

      The shim survived the restart untouched (I7's finding again), the log file kept the same inode, and containerd reopened it by path and appended. Not one line lost.

    Verify

    You can name all four hops from memory and prove any one of them on a running container with ls -l /proc/<pid>/fd. You can state, without hedging, which process writes the log file — and you know that the shim is not it.

    Gotchas
    • "The shim writes the log" is wrong, and it matters. The shim holds the pipe; containerd formats and writes. If you are looking for the process that has your log file open — to see whether it is stuck, or holding a deleted inode — search containerd's fds, not the shim's.
    • Timestamps are the runtime's, not the application's. They record when containerd read the bytes. A buffered application produces clusters of identical-looking timestamps that have nothing to do with when anything happened. If ordering matters to you, log your own timestamp in the message.
    • The log survives a containerd restart, but the container may not keep running. That is I12.3's subject and it is the sharper half of this story — a chatty container blocks. Do not read "no lines lost" as "no impact".
    • The FIFO path contains a random directory component (io/3004481266/), so never hard-code it. Find it with find, or get the log path from crictl inspect.

    On a real node this whole chain is what sits under one command. kubectl logs asks the apiserver, which proxies to the kubelet, which reads exactly the file you just found — the kubelet is the caller that filled in log_directory and log_path. When kubectl logs fails but the application is clearly running, the advanced track's fallback ladder walks the same hops from the top: W6 · Where logs physically live, and the first moves that precede it in W6 · events, describe, logs, wide.

    Docs: search the CRI proto for log_directory and log_path to see the two-field split; man 7 pipe for why a pipe has a fixed capacity (which is the next lesson's ambush); and crictl inspect's .status.logPath, which is the only supported way to learn where a container's log went.

    I12.2

    The five-field log format, and the split line that breaks log shippers

    Why it matters

    The file containerd writes is not your application's output. It is your application's output wrapped in three fields per line, and one of those fields exists to tell you that the line is incomplete. Log shippers that ignore it deliver your JSON logs chopped into unparseable fragments, and the failure is silent — the shipper is not broken, it is doing exactly what it was told.

    The concept

    Every line in a CRI log file has the same shape: a timestamp, a stream name, a one-character tag, then your bytes.

    RFC3339Nano timestamp·stdout|stderr·P|F·your line

    The stream field comes from which of the two pipes the bytes arrived on, so it is structurally reliable rather than guessed. The tag is the interesting one. F means full: this record is a complete line. P means partial: this record is a fragment, and the line continues in the next record.

    Partial records exist because of a mismatch the pipe cannot resolve. Reading a pipe returns whatever bytes are available, not whole lines — the kernel has no idea what a line is. Meanwhile a log file needs bounded records, or one runaway printf could produce a single line larger than memory. So containerd caps how much it will accumulate before flushing a record, and marks the flushed fragment P to say "not finished". On containerd 2.3.3 that cap is max_container_log_line_size, and its default is 16384 bytes.

    The reassembly rule is simple and worth memorising: a logical line is a run of P records terminated by exactly one F record. Anything that reads the file line-by-line and ignores the tag will emit each 16 KB fragment as if it were a separate log event.

    This format is not in the CRI protobuf — the proto only says where the file goes (I12.1). The format is defined by the code that parses it, on the Kubernetes side, and its own comment is the canonical statement:

    parseCRILog parses logs in CRI log format. CRI Log format example:

    2016-10-06T00:17:09.669794202Z stdout P log content 1
    2016-10-06T00:17:09.669794203Z stderr F log content 2
    Kubernetes cri-client, pkg/logs/logs.go — kubernetes/kubernetes

    Two things follow from the format being defined by the reader rather than by a spec. It is a de-facto contract between two projects, and the example above is the whole of it — there is no field for severity, no field for the container name, and nowhere to put structured data. Everything richer has to live inside your own bytes.

    Lab
    1. Produce all three variants deliberately in one container: a stdout line, a stderr line, and a line long enough to be split.

    Verify

    Given a raw CRI log file you can say how many logical lines it contains without counting records, and you can explain why grep ERROR app.log | wc -l run against a raw CRI file can overcount. You know the default split point is 16384 bytes and where that number is configured.

    Gotchas
    • crictl logs … 2>/dev/null throws away your application's stderr. Use 2>&1 when you want everything in one stream. This bites hardest in scripts, where suppressing tool noise is reflexive.
    • A split line is not an error condition. Nothing logs a warning; the file is valid and every byte is present. The damage happens downstream, in whatever reads it.
    • The split point counts bytes, not characters. A multi-byte UTF-8 character can be cut in half across two records, so a naïve reader can decode a fragment into replacement characters even after reassembling correctly.
    • Raising max_container_log_line_size does not fix a shipper. It moves the threshold; a longer line still splits. Fix the reader, or stop emitting enormous lines.

    The kubelet is the reader that defines this format, so kubectl logs reassembles partial records correctly and interleaves the two streams — which is why kubectl logs output looks nothing like the file on disk. Anything that bypasses the kubelet and reads /var/log/pods directly (most node-level log shippers) has to do the reassembly itself. The advanced track meets those files in W6 · Where logs physically live.

    Docs: the format's definition lives in the cri-client parser rather than in any spec — search for parseCRILog. On the runtime side, search containerd's config for max_container_log_line_size. For the reassembly contract as Kubernetes states it, search the API reference for LogTagPartial.

    I12.3

    Rotation: nobody on this node owns it, and what that costs

    Why it matters

    A container that logs forever writes a file that grows forever. Something has to truncate it, and the surprising answer is that the container runtime does not — not containerd, not runc, not the shim. On the node you are looking at right now, unless a kubelet is running, the answer to "who rotates this?" is nobody. That single fact explains a large share of full-disk incidents, and it explains why kubectl logs sometimes cannot show you what happened an hour ago.

    The concept

    Rotation needs two parties to cooperate, and that is why it is not the runtime's job alone. One party renames or deletes the file. The other party is holding it open and must be told to let go and open a fresh one. If only the first half happens, you get the classic Unix failure that B5 taught: the writer keeps writing into a file that no longer has a name, and every observer looking at the path sees nothing.

    In Kubernetes the two halves are split like this. The kubelet owns rotation — it runs a ContainerLogManager that periodically checks each running container's log size, renames the current file to a timestamped one, compresses older ones to .gz, and deletes the excess. Then it does the second half: it calls the CRI method ReopenContainerLog, and the runtime closes its descriptor and opens the path again. Two defaults are worth memorising because they bound how much history exists at all: containerLogMaxSize is 10Mi and containerLogMaxFiles is 5.

    So on a real node roughly 50 MB of history exists per container, and anything older is gone — not archived, deleted. This is the real reason kubectl logs "loses" history: not a bug, a retention policy you did not know you had. It is also why every serious cluster ships logs off the node.

    Which leads to the design decision this checkpoint asks you to state plainly. A container that writes to a file inside itself has, from the platform's point of view, no logs at all. Nothing collects that file. It is not rotated, so it fills the container's writable layer (I10's copy-up) until the node's disk fills. It is invisible to kubectl logs, to every log shipper, and to the kubelet's own accounting. The contract is fd 1 and fd 2, and there is no second way in.

    The CRI has exactly one method for this, and its comment is unusually explicit about who calls it and when:

    // ReopenContainerLog asks runtime to reopen the stdout/stderr log file
    // for the container. This is often called after the log file has been
    // rotated. If the container is not running, container runtime can choose
    // to either create a new log file and return nil, or return an error.
    // Once it returns error, new container log file MUST NOT be created.
    rpc ReopenContainerLog(ReopenContainerLogRequest) returns (ReopenContainerLogResponse) {}
    CRI api.proto, ReopenContainerLog — kubernetes/cri-api

    Read "asks runtime to" carefully: the runtime is passive here. It never decides to rotate; it waits to be told. The kubelet's own manager states the other half of the bargain in a comment — "rotateLatestLog rotates latest log without compression, so that container can still write and fluentd can finish reading" — which is a designed accommodation for exactly the stale-handle problem in the lab below.

      sudo crictl logs "$CID" 2>&1 | tail -1

    4. The sharper half. I12.1 showed a containerd restart loses no lines. That is true — and it hides something. Stop containerd entirely and watch what happens to a container that logs faster than the pipe can buffer. Each iteration writes 100 KB and then a countable MARK. 
      marks () { sudo grep -c MARK "$LOG"; }
A=$(marks); sleep 5; B=$(marks); echo "up:   $(( (B-A) / 5 )) iterations/s"
sudo systemctl stop containerd
C=$(marks); sleep 12; D=$(marks)
echo "down: $((D-C)) iterations in 12s"
PID=$(sudo cat /sys/fs/cgroup/k8s.io/"$CID"/cgroup.procs | head -1)
sudo ps -o pid,stat,wchan:16,comm --ppid "$PID"
sudo systemctl start containerd; sleep 2
E=$(marks); sleep 5; F=$(marks); echo "up:   $(( (F-E) / 5 )) iterations/s"
      up:   639 iterations/s
down: 0 iterations in 12s
    PID STAT WCHAN            COMMAND

 145262 S    pipe_write       tr
up:   684 iterations/s

      The application did not slow down — it stopped, parked in pipe_write, for as long as containerd was away. The pipe's capacity is 65536 bytes by default; once the shim stops draining and that fills, the next write(2) blocks. Logging is not a side channel. It is backpressure straight into your application's control flow.

    5. Finally, confirm the blocked writes were delayed rather than discarded. 
      sudo grep -o "MARK [0-9]*" "$LOG" | awk '{print $2}' > ~/marks.txt

      first=1 last=11090 count=11090 expected=11090
missing marks: 0  -> delayed, not lost

      Zero of 11,090 lost. Blocking is how the guarantee is bought: the kernel would rather stall your process than drop a line.

    Verify

    You can say who rotates container logs (the kubelet, not the runtime), name the CRI method that makes it safe, and quote the two defaults that decide how much history exists. You can explain, in inode terms, why a renamed log keeps growing while the path shows nothing.

    Gotchas
    • A logrotate rule pointed at /var/log/pods is actively harmful. It performs the first half of a rotation and cannot perform the second, leaving containerd writing to a nameless inode forever. If you must use logrotate here, it needs copytruncate — which has its own race — and even then you are fighting the kubelet.
    • Roughly 50 MB per container is all the history there is (10Mi × 5). A crash loop that logs heavily can push the interesting failure out of retention within minutes.
    • Logging can stall your application. Any consumer downstream of fd 1 — the shim, containerd, or a node agent tailing the file — becomes a dependency of your request path once the pipe fills. Rate-limit your own logging; do not assume the platform absorbs it.
    • Writing logs to a file inside the container is not "logging to disk", it is discarding them. Nothing rotates it, nothing collects it, and it consumes the writable layer until the node's disk fills.
    • crictl logs fails fatally on a missing file rather than returning empty output. In a script, check the exit status — an empty result and an error are different diagnoses.

    This is the mechanism under two everyday observations. "Why can't I see yesterday's logs?" is containerLogMaxSize × containerLogMaxFiles. And "the node's disk filled up" is very often this, which is why the advanced track's disk-pressure and log-location material — W6 · Where logs physically live — is the fallback ladder to walk when kubectl logs has nothing to give you. Note also that kubectl logs --previous reads the previous container instance's file (attempt 0.log vs 1.log from I8), which is a different mechanism from rotation entirely.

    Docs: search the kubelet config reference for containerLogMaxSize and containerLogMaxFiles (and note the newer containerLogMaxWorkers / containerLogMonitorInterval knobs alongside them); search the CRI proto for ReopenContainerLog; and man 7 pipe for the 65536-byte capacity that produced the stall above.

    Metrics

    I12.4

    Every container metric is a cgroup file. There is no other source.

    Why it matters

    Container monitoring looks like a deep stack — Grafana on Prometheus on kube-state-metrics on metrics-server on cAdvisor on the kubelet — and it is easy to assume the numbers come from somewhere sophisticated. They do not. At the bottom of that entire tower are a handful of plain-text files in /sys/fs/cgroup that B7 taught you to cat. Knowing this converts "the dashboard says the pod is using 2 GB" from an assertion into a claim you can check in ten seconds on the node.

    The concept

    A cgroup is a directory (B7's first rule), and the kernel keeps that directory's accounting in files inside it. For a container the interesting ones are few enough to list:

    FileWhat it holdsShape
    memory.currentbytes charged to this cgroup including page cachegauge
    memory.maxthe hard limit, or the literal string maxlimit
    memory.statthe breakdown: anon, file, inactive_file, kernel memory…gauges
    cpu.statusage_usec, plus throttling counterscounters
    cpu.maxquota and period, as two numberslimit
    pids.currentprocesses in the cgroup and its descendantsgauge

    Everything above the kernel is transport and arithmetic. crictl stats reads these files and renames the fields; ctr task metrics reads the same files and keeps the kernel's names; cAdvisor reads them on a timer and adds labels; Prometheus stores what cAdvisor emitted. Nothing in that chain measures anything — the measuring happened in the kernel, at allocation time.

    Finding a container's directory takes one lookup, because the OCI config records it. crictl inspect exposes .info.runtimeSpec.linux.cgroupsPath, and with the cgroupfs driver that value is already a path under /sys/fs/cgroup. (Under the systemd driver it is the slice:prefix:id form from I8 and needs expanding — the mini project handles both.)

    There is no OCI or CRI spec for metrics; the authority is the kernel's own cgroup v2 documentation, and its wording on memory.current is the sentence the rest of this group depends on:

    memory.current
        The total amount of memory currently being used by the cgroup and its descendants.
    Linux Documentation/admin-guide/cgroup-v2.rst — torvalds/linux

    Note what it does not say: it does not say "memory your program allocated". It says memory being used, and the same document defines file as "Amount of memory used to cache filesystem data, including tmpfs and shared memory" — which is charged to the cgroup too. That inclusion is deliberate, correct, and the source of the most misdiagnosed number in container operations (I12.6).

    Lab
    1. Start a container with both a memory limit and a CPU quota, then find its cgroup directory. 
      # container: while :; do :; done   with memory_limit_in_bytes 134217728,
#                                        cpu_quota 20000 / cpu_period 100000
CG=$(sudo crictl inspect "$CID" | jq -r .info.runtimeSpec.linux.cgroupsPath)
echo "cgroupsPath = $CG"
D=/sys/fs/cgroup$CG
      cgroupsPath = /k8s.io/cee11e82b50d15cbda84b2d704877cf5fa32b6e23048370e6843f644f9bc76f4
    2. Read the numbers straight from the kernel. No container tooling is involved in this step at all. 
      for f in memory.current memory.max cpu.max pids.current; do
  printf '%-16s %s\n' "$f" "$(sudo cat "$D/$f")"
done
sudo cat "$D/cpu.stat"
      memory.current   229376
memory.max       134217728
cpu.max          20000 100000
pids.current     1
usage_usec 854747
user_usec 847810
system_usec 6937
nr_periods 42
nr_throttled 42
throttled_usec 3290317

      nr_throttled equals nr_periods: every single enforcement period hit the quota. A spin loop under a 20% cap is throttled 100% of the time, and this is the file that proves it — B7's "slow on an idle box" evidence, now for a real container.

    3. Ask the CRI for the same container's stats and line the two up. 
      sudo crictl stats --output json "$CID" | jq -r '.stats[0] |
  "usageCoreNanoSeconds = \(.cpu.usageCoreNanoSeconds.value)
memory.usageBytes    = \(.memory.usageBytes.value)
memory.rssBytes      = \(.memory.rssBytes.value)"'
echo "kernel usage_usec    = $(sudo awk '/^usage_usec/{print $2}' "$D/cpu.stat")"
echo "kernel memory.current= $(sudo cat "$D/memory.current")"
      usageCoreNanoSeconds = 1088660000
memory.usageBytes    = 229376
memory.rssBytes      = 65536
kernel usage_usec    = 1088660
kernel memory.current= 229376

      Not approximately equal — identical. usageCoreNanoSeconds is usage_usec × 1000, and usageBytes is memory.current byte for byte. The CRI is a unit conversion and a rename.

    4. The other interface, for contrast: ctr task metrics does the same read but keeps the kernel's field names. 
      sudo ctr -n k8s.io task metrics "$CID"
      METRIC                VALUE
pids.current          1
pids.limit            18446744073709551615
cpu.usage_usec        1069549
cpu.nr_throttled      52
cpu.throttled_usec    4089056
memory.usage          229376
memory.usage_limit    134217728
memory.swap_limit     0

      pids.limit of 18446744073709551615 is 2^64 − 1 — how "no limit" looks once the string max has been forced into an unsigned integer. Dashboards that plot "percent of pid limit" against this produce a permanent zero.

    5. Finally, look at what memory.current is actually made of. For a container doing nothing, most of it is not the workload. 
      sudo awk '/^(anon|file|kernel_stack|pagetables|slab) /{print}' "$D/memory.stat"
      anon 65536
file 0
kernel_stack 16384
pagetables 45056
slab 90688

      65,536 bytes of the workload's own memory, and 163,840 bytes of kernel bookkeeping — page tables, kernel stacks, slab objects — charged to the container because the kernel allocated them on its behalf. A container's floor is not zero.

    Verify

    Given any running container you can produce its memory and CPU numbers from /sys/fs/cgroup without using crictl, and then show that crictl stats reports the same values. You can point at the file that proves throttling.

    Gotchas
    • memory.current includes page cache. It is not "how much memory my program is using". This is the whole of I12.6 and half of the debugging drill.
    • memory.max reads as the literal string max when unlimited, and pids.limit comes back as 264−1 through the API. Parse both defensively or your exporter will publish nonsense.
    • The cgroup path depends on the driver. With the systemd driver cgroupsPath is slice:prefix:id, not a filesystem path, and pasting it after /sys/fs/cgroup gives a directory that does not exist — I8's cgroup-driver mismatch showing up as a monitoring bug.
    • A container's cgroup disappears the instant it is deleted, taking its counters with it. There is no historical query here; if you did not sample it, it is gone.

    These files are where the number in kubectl top pod begins. The kubelet reads them, metrics-server scrapes the kubelet, and the HPA divides one of them by your resources.requests to decide whether to scale. Both of those are the advanced track's subject — W3 · metrics-server and the aggregated API and W3 · HPA's control loop and formula. The nr_throttled counter above is also the honest answer to "the pod is slow but CPU usage looks low": it is at its limit, not idle.

    Docs: the kernel's cgroup-v2.rst is the reference for every field name here — search it for memory.stat to see the full breakdown. On the tooling side, crictl stats --output json shows the CRI's field names, and ctr task metrics shows the kernel's.

    Quiz

    1. A container's fd 1 is a pipe. Which process holds the read end, and which process writes the log file on disk?
      Answer

      The shim holds the read end of the pipe. containerd writes the log file — it reads a FIFO the shim writes into, and holds the only file descriptor on 0.log. The shim has none.

    2. A raw CRI log file has 4 records but crictl logs prints 3 lines. What happened?
      Answer

      One logical line exceeded max_container_log_line_size (default 16384) and was written as a P (partial) record followed by an F (full) record. A correct reader joins a run of P records terminated by one F back into a single line.

    3. Why does sudo crictl logs "$CID" 2>/dev/null hide half your application's output?
      Answer

      Because crictl logs replays the stdout/stderr field onto its own stdout and stderr. Redirecting its stderr to /dev/null discards every line the application wrote to stderr.
