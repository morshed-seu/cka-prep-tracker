    I12 — Observability of a running runtime

    The short module that makes the other twelve debuggable. One line of application output, traced from write(2) to the file kubectl logs reads; one number, traced from a cgroup file to a dashboard — and the honest limits of both.

    Everything here is the same move: refuse the dashboard and go find the file. A container's logs are a pipe, a FIFO and a text file. Its metrics are six numbers in /sys/fs/cgroup. Its history is an event stream you can tail. Once you have seen each of those with your own eyes, "the monitoring is wrong" stops being a helpless sentence and becomes a question with a location.

    Checkpoints10 Hours~4 PrerequisitesI7 · I8 · B7
    • Logs — follow one line through all four hops, decode the five-field CRI log format including the partial/full split, and find out who owns rotation (on this node: nobody).
    • Metrics — read the cgroup files that are the only source of any container metric, write valid Prometheus exposition by hand, and get the counter/gauge distinction right before it costs you.
    • Events and deeper — answer "did it exit, or was it never started?" from the runtime's event stream, then profile a container from the host by PID without entering it.
    • Project & drill — build a working exporter in fifty lines, then fix logs that stopped appearing and a memory number that grows on its own.

    I7 (the shim owns the stdio) and I8 (the CRI log format and who chose the directory). B7's cgroup files return as the source of every container metric there is.

    Which machine. Everything below ran on the sandbox VM — Ubuntu 24.04.4 LTS, kernel 6.8.0-136-generic, cgroup v2 — with containerd 2.3.3, runc 1.5.1, crictl v1.36.0, nerdctl 2.3.5, Python 3.12.3, perf 6.8.12 and bpftrace v0.20.2. There is no kubelet on this node, which is the point: every question in this module is answerable from the runtime alone.

    Logs

    I12.1

    One line, all four hops: from write(2) to the file on disk

    Why it matters

    When somebody says "the logs are missing", they have described a symptom with at least four possible locations. The application's output travels through a pipe, a shim, a FIFO and a daemon before it becomes a file anyone can read, and every famous logging surprise is a property of exactly one of those hops. You cannot diagnose a chain you have never seen, so this lesson walks the whole thing once with real commands and real process IDs.

    The concept

    Start from the application's point of view, because it is startlingly simple: the workload does not know it is being logged. It writes bytes to file descriptor 1. That is the entire contract. It cannot tell whether fd 1 is a terminal, a file, a socket or a pipe, and nothing in the container gives it a hint.

    In a container, fd 1 is a pipe — a kernel buffer with a write end and a read end, the same object B2 used for shell pipelines. The read end is held by the shim, the small per-container process I7 introduced as the on-site foreman: the one who stays after runc leaves. This is why the shim exists at all. Someone has to be holding the other end of that pipe every moment the container is alive, and it cannot be the daemon, because the daemon has to be restartable.

    Here is the part most descriptions skip, including this repo's own earlier notes. The shim does not write the log file. It writes into a second IPC object — a FIFO, a named pipe that exists as a path on disk — and containerd reads that FIFO and writes the log file. So the chain has four hops and two different kinds of pipe in it:

    workload fd 1→pipe→shim→FIFO→containerd→0.log

    You can prove every arrow, which is what the lab does. The consequence worth carrying away: the timestamp on each line is written by containerd, at the moment it read the bytes — not by the application, and not when the application decided to log. An application with a buffered writer can emit a burst of lines all stamped within the same millisecond, describing events minutes apart. The timestamps are honest about when the runtime saw the bytes and say nothing about when the events happened.

    The CRI does not describe the pipes at all — those are implementation. What it standardises is where the file goes, and it does so in two halves: the sandbox names a directory, and each container names a path relative to it.

    // Path to the directory on the host in which container log files are
    // stored.
    // By default the log of a container going into the LogDirectory will be
    // hooked up to STDOUT and STDERR. However, the LogDirectory may contain
    // binary log files with structured logging data from the individual
    // containers. […]
    // E.g.,
    //     PodSandboxConfig.LogDirectory = `/var/log/pods/<NAMESPACE>_<NAME>_<UID>/`
    //     ContainerConfig.LogPath = `containerName/Instance#.log`
    CRI api.proto, PodSandboxConfig.log_directory — kubernetes/cri-api

    Note what that means: the runtime does not choose the path — its caller does. On a real node the kubelet fills in those two fields, which is why the layout looks like Kubernetes rather than like containerd. Below, we fill them in ourselves and get to pick.

    Lab
    1. Write a sandbox config that names a log directory, and a container config that names a path inside it and prints a string we can search for. 
      cat > ~/sb.json <<'EOF'
{
  "metadata": { "name": "obs", "uid": "obs-uid", "namespace": "default", "attempt": 0 },
  "log_directory": "/var/log/pods/default_obs_obs-uid",
  "linux": {}
}
EOF
cat > ~/ct.json <<'EOF'
{
  "metadata": { "name": "talker", "attempt": 0 },
  "image": { "image": "docker.io/library/alpine:3.21" },
  "command": [ "/bin/sh", "-c", "echo I-AM-THE-KNOWN-STRING; sleep 300" ],
  "log_path": "talker/0.log"
}
EOF
sudo mkdir -p /var/log/pods/default_obs_obs-uid
POD=$(sudo crictl runp ~/sb.json)
CID=$(sudo crictl create "$POD" ~/ct.json ~/sb.json)
sudo crictl start "$CID"
    2. Hop 1 — the workload's own fds. Ask the CRI for the host PID, then look at what its standard streams actually are. 
      PID=$(sudo crictl inspect "$CID" | jq -r .info.pid)
echo "workload PID on the host = $PID"
sudo ls -l /proc/"$PID"/fd/0 /proc/"$PID"/fd/1 /proc/"$PID"/fd/2
      workload PID on the host = 2256
lrwx------ 1 root root 64 Aug  1 12:28 /proc/2256/fd/0 -> /dev/null
l-wx------ 1 root root 64 Aug  1 12:28 /proc/2256/fd/1 -> pipe:[10973]
l-wx------ 1 root root 64 Aug  1 12:28 /proc/2256/fd/2 -> pipe:[10974]

      stdout and stderr are two different pipes — that separation is physical, and it is why the stream field in the log file can be trusted later. stdin is /dev/null, because nothing is going to type at this container.

    3. Hop 2 — who holds the read end? A pipe has an inode number; search every process's fds for a link to the same one. 
      INO=$(sudo readlink /proc/"$PID"/fd/1 | tr -dc '0-9')
for f in $(sudo find /proc/[0-9]*/fd -lname "pipe:\[$INO\]" 2>/dev/null); do
  p=$(echo "$f" | cut -d/ -f3)
  printf '%-20s pid=%-8s comm=%s\n' "$f" "$p" "$(sudo cat /proc/"$p"/comm)"
done
      /proc/2187/fd/14     pid=2187     comm=containerd-shim
/proc/2256/fd/1      pid=2256     comm=sleep

      Two holders: our workload at the write end, and the shim at the read end. This is I7's claim, made visible.

    4. Hop 3 — the shim writes into a FIFO, and containerd reads it. The FIFO is a real path (note the leading p in its mode — that is what "named pipe" looks like to ls). 
      FIFO=$(sudo find /run/containerd/io.containerd.grpc.v1.cri -name '*-stdout' | head -1)
sudo ls -l "$FIFO"
for f in $(sudo find /proc/[0-9]*/fd -lname "$FIFO" 2>/dev/null); do
  p=$(echo "$f" | cut -d/ -f3)
  printf '%-18s pid=%-7s comm=%-18s mode=%s\n' "$f" "$p" \
    "$(sudo cat /proc/$p/comm)" "$(sudo ls -l "$f" | cut -c1-10)"
done
      prwx------ 1 root root 0 Aug  1 12:28 /run/containerd/io.containerd.grpc.v1.cri/containers/ed6efa44…/io/3004481266/ed6efa44…-stdout
/proc/2187/fd/16   pid=2187   comm=containerd-shim   mode=l-wx------
/proc/2187/fd/19   pid=2187   comm=containerd-shim   mode=lr-x------
/proc/756/fd/25    pid=756    comm=containerd        mode=lr-x------

      Read the mode column, not just the names: the shim holds it write-only on fd 16 (l-wx), containerd holds it read-only on fd 25 (lr-x). That is the direction of flow, stated by the kernel.

    5. Hop 4 — the file, and who owns it. This is the step that corrects the folk model. 
      LOG=$(sudo crictl inspect "$CID" | jq -r .status.logPath)
sudo cat "$LOG"
echo "--- which process has it open?"
sudo find /proc/[0-9]*/fd -lname "$LOG" 2>/dev/null | while read -r f; do
  p=$(echo "$f" | cut -d/ -f3); echo "$f  pid=$p comm=$(sudo cat /proc/"$p"/comm)"
done
      2026-08-01T12:28:09.864985918+06:00 stdout F I-AM-THE-KNOWN-STRING
--- which process has it open?
/proc/756/fd/27  pid=756 comm=containerd

      The shim has zero file descriptors on the log file. containerd writes it. The shim's job is to hold the pipe and survive; the daemon's job is to format and persist.

    6. The payoff — does a containerd restart lose lines? The chain says the shim keeps buffering while the daemon is away. Test it with a numbered sequence so nothing can hide. 
      # container runs: i=0; while :; do i=$((i+1)); echo "seq $i"; sleep 0.2; done
sudo systemctl restart containerd
sleep 5
sudo awk '{print $NF}' "$LOG" > ~/seq.txt
awk -v f="$(head -1 ~/seq.txt)" -v l="$(tail -1 ~/seq.txt)" \
  'BEGIN{for(i=f;i<=l;i++)w[i]=1}{delete w[$1]}
   END{n=0;for(i in w)n++; print "missing lines: " n}' ~/seq.txt
      restart took 0.20s
containerd pid: 39746 -> 39874   (shim pid unchanged)
first=1 last=47 lines=47 expected=47
missing lines: 0

      The shim survived the restart untouched (I7's finding again), the log file kept the same inode, and containerd reopened it by path and appended. Not one line lost.

    Verify

    You can name all four hops from memory and prove any one of them on a running container with ls -l /proc/<pid>/fd. You can state, without hedging, which process writes the log file — and you know that the shim is not it.

    Gotchas
    • "The shim writes the log" is wrong, and it matters. The shim holds the pipe; containerd formats and writes. If you are looking for the process that has your log file open — to see whether it is stuck, or holding a deleted inode — search containerd's fds, not the shim's.
    • Timestamps are the runtime's, not the application's. They record when containerd read the bytes. A buffered application produces clusters of identical-looking timestamps that have nothing to do with when anything happened. If ordering matters to you, log your own timestamp in the message.
    • The log survives a containerd restart, but the container may not keep running. That is I12.3's subject and it is the sharper half of this story — a chatty container blocks. Do not read "no lines lost" as "no impact".
    • The FIFO path contains a random directory component (io/3004481266/), so never hard-code it. Find it with find, or get the log path from crictl inspect.

    On a real node this whole chain is what sits under one command. kubectl logs asks the apiserver, which proxies to the kubelet, which reads exactly the file you just found — the kubelet is the caller that filled in log_directory and log_path. When kubectl logs fails but the application is clearly running, the advanced track's fallback ladder walks the same hops from the top: W6 · Where logs physically live, and the first moves that precede it in W6 · events, describe, logs, wide.

    Docs: search the CRI proto for log_directory and log_path to see the two-field split; man 7 pipe for why a pipe has a fixed capacity (which is the next lesson's ambush); and crictl inspect's .status.logPath, which is the only supported way to learn where a container's log went.

    I12.2

    The five-field log format, and the split line that breaks log shippers

    Why it matters

    The file containerd writes is not your application's output. It is your application's output wrapped in three fields per line, and one of those fields exists to tell you that the line is incomplete. Log shippers that ignore it deliver your JSON logs chopped into unparseable fragments, and the failure is silent — the shipper is not broken, it is doing exactly what it was told.

    The concept

    Every line in a CRI log file has the same shape: a timestamp, a stream name, a one-character tag, then your bytes.

    RFC3339Nano timestamp·stdout|stderr·P|F·your line

    The stream field comes from which of the two pipes the bytes arrived on, so it is structurally reliable rather than guessed. The tag is the interesting one. F means full: this record is a complete line. P means partial: this record is a fragment, and the line continues in the next record.

    Partial records exist because of a mismatch the pipe cannot resolve. Reading a pipe returns whatever bytes are available, not whole lines — the kernel has no idea what a line is. Meanwhile a log file needs bounded records, or one runaway printf could produce a single line larger than memory. So containerd caps how much it will accumulate before flushing a record, and marks the flushed fragment P to say "not finished". On containerd 2.3.3 that cap is max_container_log_line_size, and its default is 16384 bytes.

    The reassembly rule is simple and worth memorising: a logical line is a run of P records terminated by exactly one F record. Anything that reads the file line-by-line and ignores the tag will emit each 16 KB fragment as if it were a separate log event.

    This format is not in the CRI protobuf — the proto only says where the file goes (I12.1). The format is defined by the code that parses it, on the Kubernetes side, and its own comment is the canonical statement:

    parseCRILog parses logs in CRI log format. CRI Log format example:

    2016-10-06T00:17:09.669794202Z stdout P log content 1
    2016-10-06T00:17:09.669794203Z stderr F log content 2
    Kubernetes cri-client, pkg/logs/logs.go — kubernetes/kubernetes

    Two things follow from the format being defined by the reader rather than by a spec. It is a de-facto contract between two projects, and the example above is the whole of it — there is no field for severity, no field for the container name, and nowhere to put structured data. Everything richer has to live inside your own bytes.

    Lab
    1. Produce all three variants deliberately in one container: a stdout line, a stderr line, and a line long enough to be split. 
      cat > ~/ct2.json <<'EOF'
{
  "metadata": { "name": "shouter", "attempt": 0 },
  "image": { "image": "docker.io/library/alpine:3.21" },
  "command": [ "/bin/sh", "-c",
    "echo this-went-to-stdout; echo this-went-to-stderr 1>&2; head -c 20000 /dev/zero | tr '\\0' L; echo; sleep 60" ],
  "log_path": "shouter/0.log"
}
EOF
POD=$(sudo crictl runp ~/sb.json); CID=$(sudo crictl create "$POD" ~/ct2.json ~/sb.json)
sudo crictl start "$CID"; sleep 2
LOG=/var/log/pods/default_obs_obs-uid/shouter/0.log
sudo cut -c1-90 "$LOG" | head -2
      2026-08-01T12:29:24.483101925+06:00 stdout F this-went-to-stdout
2026-08-01T12:29:24.483146165+06:00 stderr F this-went-to-stderr
    2. Now look at the whole file as records rather than as text, printing the stream, the tag and the message length for each. 
      sudo awk '{printf "%-4s stream=%-7s tag=%-3s len(msg)=%d\n", \
  NR, $2, $3, length($0)-length($1)-length($2)-length($3)-3}' "$LOG"
      1    stream=stdout  tag=F   len(msg)=19
2    stream=stderr  tag=F   len(msg)=19
3    stream=stdout  tag=P   len(msg)=16384
4    stream=stdout  tag=F   len(msg)=3616

      One 20,000-byte line became two records: a P of exactly 16384 and an F of 3616. They sum to 20000. That 16384 is max_container_log_line_size, and it is the only log-related knob containerd has apart from a tracing flag:

      containerd config default | grep -i log
        log_trace_id = false
    max_container_log_line_size = 16384
    3. Confirm that a correct reader puts the line back together, and that the timestamp is RFC3339 with nanoseconds and an offset. 
      sudo crictl logs "$CID" 2>&1 | awk '{print NR": len="length($0)" head="substr($0,1,22)}'
sudo awk 'NR==1{print $1}' "$LOG"
      1: len=19 head=this-went-to-stdout
2: len=19 head=this-went-to-stderr
3: len=20000 head=LLLLLLLLLLLLLLLLLLLLLL
2026-08-01T12:29:24.483101925+06:00

      crictl logs reassembled 16384 + 3616 back into one 20,000-byte line. Note the timestamp carries a +06:00 offset — it is the node's local time, not UTC.

    4. The trap worth ten minutes of your life. The stream field is not just metadata that gets printed — crictl logs replays it, sending stdout records to its own stdout and stderr records to its own stderr. 
      echo "--- with 2>/dev/null (crictl's stderr thrown away):"
sudo crictl logs "$CID" 2>/dev/null | cut -c1-30
echo "--- with 2>&1 (both kept):"
sudo crictl logs "$CID" 2>&1 | cut -c1-30
echo "--- only crictl's stderr (1>/dev/null):"
sudo crictl logs "$CID" 1>/dev/null
      --- with 2>/dev/null (crictl's stderr thrown away):
this-went-to-stdout
LLLLLLLLLLLLLLLLLLLLLLLLLLLLLL
--- with 2>&1 (both kept):
this-went-to-stdout
this-went-to-stderr
LLLLLLLLLLLLLLLLLLLLLLLLLLLLLL
--- only crictl's stderr (1>/dev/null):
this-went-to-stderr

      The habitual 2>/dev/null that suppresses a tool's warnings silently discards every stderr line your application wrote — usually the half you were looking for.

    Verify

    Given a raw CRI log file you can say how many logical lines it contains without counting records, and you can explain why grep ERROR app.log | wc -l run against a raw CRI file can overcount. You know the default split point is 16384 bytes and where that number is configured.

    Gotchas
    • crictl logs … 2>/dev/null throws away your application's stderr. Use 2>&1 when you want everything in one stream. This bites hardest in scripts, where suppressing tool noise is reflexive.
    • A split line is not an error condition. Nothing logs a warning; the file is valid and every byte is present. The damage happens downstream, in whatever reads it.
    • The split point counts bytes, not characters. A multi-byte UTF-8 character can be cut in half across two records, so a naïve reader can decode a fragment into replacement characters even after reassembling correctly.
    • Raising max_container_log_line_size does not fix a shipper. It moves the threshold; a longer line still splits. Fix the reader, or stop emitting enormous lines.

    The kubelet is the reader that defines this format, so kubectl logs reassembles partial records correctly and interleaves the two streams — which is why kubectl logs output looks nothing like the file on disk. Anything that bypasses the kubelet and reads /var/log/pods directly (most node-level log shippers) has to do the reassembly itself. The advanced track meets those files in W6 · Where logs physically live.

    Docs: the format's definition lives in the cri-client parser rather than in any spec — search for parseCRILog. On the runtime side, search containerd's config for max_container_log_line_size. For the reassembly contract as Kubernetes states it, search the API reference for LogTagPartial.

    Quiz

    1. A container's fd 1 is a pipe. Which process holds the read end, and which process writes the log file on disk?
      Answer

      The shim holds the read end of the pipe. containerd writes the log file — it reads a FIFO the shim writes into, and holds the only file descriptor on 0.log. The shim has none.

    2. A raw CRI log file has 4 records but crictl logs prints 3 lines. What happened?
      Answer

      One logical line exceeded max_container_log_line_size (default 16384) and was written as a P (partial) record followed by an F (full) record. A correct reader joins a run of P records terminated by one F back into a single line.

    3. Why does sudo crictl logs "$CID" 2>/dev/null hide half your application's output?
      Answer

      Because crictl logs replays the stdout/stderr field onto its own stdout and stderr. Redirecting its stderr to /dev/null discards every line the application wrote to stderr.
