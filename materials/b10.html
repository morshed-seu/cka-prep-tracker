    B10 — Names: DNS and resolution

    "It's always DNS" is the oldest joke in operations, and it is funny for an unflattering reason: DNS is the layer almost nobody sits down and learns. People pick up fragments — /etc/hosts exists, dig prints something, restarting things sometimes helps — and then spend years treating name resolution as weather. This module takes it apart in order and leaves you with no mystery in it. A name becomes an address through a specific chain of software, each link of which you can read, test and break on purpose: the program's call into the C library, the library's list of sources to try, a static file, a configuration file with three kinds of line, a query on the wire, a resolver that walks the internet's tree on your behalf, and a cache that remembers the answer — including, awkwardly, remembering failure.

    We work outward from the program. The client side: who actually resolves (the resolver library, not "DNS"), why ping and dig can honestly disagree, and how the three lines of /etc/resolv.conf turn one short name into a series of queries. The system side: the difference between a resolver that does legwork and a server that holds truth, the root → TLD → authoritative walk you can watch yourself, and the local stub listener Ubuntu 24.04 puts in front of everything. Records and caching: what each record type is for, how to read a dig answer completely rather than squinting at the middle of it, and why TTLs and negative caching make DNS changes feel non-deterministic. Then you run your own resolver, serve your own zone, and resolve it from inside a network namespace you built in B9 — after which Kubernetes' ndots:5 and its four-rung search ladder will read as ordinary configuration you could have written yourself.

    The client side

    B10.1

    Who actually resolves a name: the resolver library and nsswitch.conf

    Why it matters

    When a program wants to talk to example.com, something has to turn that text into an IP address before a single packet can be addressed. Most people call that something "DNS" and stop. It is worth being more precise, because the imprecision is the direct cause of the most confusing symptom in this whole field: ping myhost works, dig myhost finds nothing, and both people in the argument are correct. Once you know exactly which piece of software does the resolving, and how it decides where to look, that symptom stops being a paradox and becomes a one-line diagnosis.

    The concept

    Programs don't speak DNS. A program calls a function in the C library — historically gethostbyname(), today getaddrinfo() — and hands it a name. Everything after that is the library's business. That bundle of library code is called the resolver, and DNS is only one of the places it may look. It might also look in a local file, or ask a local daemon, or use multicast discovery on the LAN. The program never finds out which; it gets an address back and moves on.

    What tells the resolver where to look, and in which order, is a single line in /etc/nsswitch.conf — the name service switch, a table that says "for each kind of lookup, here are the sources to try, left to right." The line that matters here is the one starting hosts:. Each word on it names a plug-in module the library will load and ask, in order, until one of them produces an answer:

    • files — read /etc/hosts, the static local table (B10.2). No network involved at all.
    • dns — do a real DNS query to whichever servers /etc/resolv.conf lists (B10.3). This is the only entry that puts a packet on the wire in the classic way.
    • resolve — hand the question to systemd-resolved over a local socket and let it decide (B10.7), which is how Ubuntu's caching stub gets involved.
    • mdns4_minimal — try multicast DNS on the local link, the .local zeroconf mechanism used to find printers and the like.
    • myhostname — synthesise answers for the machine's own name and localhost, so those work even with no files and no network.

    Between the modules you'll see bracketed actions like [NOTFOUND=return] or [!UNAVAIL=return]. They control what happens on a given result rather than adding a source. [NOTFOUND=return] means "if that module answered definitively, the name does not exist, stop here and report failure — do not try the modules further right." [!UNAVAIL=return] means the opposite emphasis: keep going to the next module only when this one was unavailable (not running), otherwise trust its verdict. These brackets are why order alone doesn't tell you the whole story — a module in the middle of the line can end the search.

    Now the paradox dissolves. ping calls getaddrinfo(), so it walks this whole line and may be answered by /etc/hosts, by mDNS or by systemd-resolved's cache without any DNS query leaving the machine. dig does not use the resolver library at all: it builds a DNS packet itself and sends it straight to a nameserver. They are testing different systems. dig tests the DNS server; getaddrinfo() tests what your application will actually experience. When they disagree, that difference is the finding, not a nuisance.

    program→getaddrinfo()→nsswitch hosts: files → dns→/etc/hostsora DNS query

    The chain a name walks: the program asks the C library, the library consults the switch, and only the dns entry produces a packet.

    Lab
    1. Read the switch line that governs every hostname lookup on this machine. Yours may differ from the output shown — read your line and name the sources in order. 
      multipass shell sandbox
grep '^hosts:' /etc/nsswitch.conf
      hosts:          files mdns4_minimal [NOTFOUND=return] dns
    # some images show plain "files dns", others insert "resolve [!UNAVAIL=return]"
    # in every variant, files comes first and dns is the fallback
    2. Watch the resolver actually walk that line. getent hosts is the command-line front end to exactly the same library call your programs make, so it is the honest test of "what will my application get?" 
      getent hosts localhost        # answered without any network
getent ahosts example.com | head -3   # ahosts shows every address the resolver returns
      127.0.0.1       localhost         ← came from /etc/hosts via the "files" module
23.220.75.232   STREAM example.com   ← came from the "dns" module, over the network
    3. Prove the two tools take different paths. Ask dig for the machine's own hostname — a name that resolves fine through the library — and watch DNS alone come up empty. 
      hostname                                   # this machine's name
getent hosts "$(hostname)"                 # via the resolver library: works
dig +short "$(hostname)"                   # via DNS only: nothing
      sandbox
127.0.1.1       sandbox        ← the library found it in /etc/hosts

    Verify

    Without looking, answer three questions. Which function do ordinary programs call to resolve a name, and which file decides where that function looks? (getaddrinfo() in the C library; /etc/nsswitch.conf's hosts: line.) A colleague says "DNS is broken" because dig myhost returns nothing, yet the application connects fine — who is right? (Both: dig correctly reports there is no DNS record, and the application correctly gets an answer from an earlier source such as /etc/hosts. Nothing is broken; they are testing different systems.) And which of dig or getent hosts tells you what your application will experience? (getent hosts — it uses the same library path the application does.)

    Gotchas

    The trap is reaching for dig as the universal DNS test. It is a superb tool for testing a nameserver and a misleading one for testing an application's resolution, because it skips /etc/hosts, skips nsswitch.conf and skips any local caching daemon. Half of all "but it works from my machine" arguments are one person using dig and the other using the application. The discipline that saves you: when a program can't resolve something, test with getent hosts NAME first (does the program's path work?) and only then with dig NAME (does DNS itself work?). The pair of answers localises the fault immediately — library path works but DNS doesn't means something local is answering; DNS works but the library path doesn't means the switch, or a file, is intercepting.

    The second trap is assuming order is everything on the hosts: line. A bracketed action such as [NOTFOUND=return] can terminate the search in the middle, so a module listed further right may never be consulted even though "the order says it should be." If a lookup fails in a way that makes no sense given the sources you can see, read the brackets, not just the words.

    Inside a pod, this same line is the reason two debugging commands can tell different stories. Pods get a generated /etc/resolv.conf and an /etc/hosts the kubelet writes (including any hostAliases you set), and the application resolves through getaddrinfo() exactly as here — so a name can work for curl and appear absent to dig, or vice versa. When you eventually debug "the app can't reach the Service," the first fork in the road is the one you just learned: is the resolver library's path broken, or is CoreDNS broken?

    The pod's generated resolver configuration is W4.16; the cluster DNS debugging ladder, where this distinction is the first rung, is W4.18.

    Docs

    man 5 nsswitch.conf is the definitive reference for the switch line, including the full action syntax in brackets. man 3 getaddrinfo documents what programs actually call and the shape of what comes back. man 8 nss-resolve explains the resolve module and its interaction with dns; man 8 nss-myhostname covers the synthesised local names. man 1 getent shows how to query any switch database from the shell. No exam-docs page covers this layer — Kubernetes assumes it, which is why it belongs here.

    B10.2

    /etc/hosts: the oldest name database, and proving nothing left the machine

    Why it matters

    Before DNS existed, the entire internet's name-to-address mapping was one file that people copied around. That file still exists on your machine, it is still consulted first, and it still wins over any DNS server on earth. That makes it the fastest way to test "would this work if the name pointed at that IP?" without touching any server — and, when someone has quietly put a line in it, the most invisible cause of "this machine resolves that name differently from every other machine."

    The concept

    /etc/hosts is a plain text file mapping addresses to names: an IP address, whitespace, then one or more names for it. The first field is the address, the rest are aliases; lines starting with # are comments. There is no zone, no server, no TTL and no expiry — it is a static table, read fresh from disk on each lookup, and because files sits first on the hosts: switch line (B10.1), an entry here short-circuits the whole rest of the resolution chain.

    Two properties follow, and both are load-bearing:

    • It is authoritative locally and invisible globally. Only this machine sees it. That's what makes it a perfect test instrument — you can point a production hostname at a test server for one machine, for one afternoon — and what makes a forgotten entry so maddening, because every diagnostic on other machines will disagree with this one and nothing in DNS will explain why.
    • It generates no traffic. A name answered from this file produces zero packets. This is provable, and proving it is the lab: run tcpdump on port 53 and watch a resolution happen in complete silence. That silence is itself a diagnostic — if you are debugging a name and see no DNS query at all, something local answered.

    One nuance worth carrying: on a system running systemd-resolved (B10.7), /etc/hosts may be read by the stub resolver rather than by the files module — resolved parses the file itself and answers from it, with caching. The effect is the same (no query leaves the box, the local mapping wins), but it explains why a tcpdump on the external interface stays quiet even for names you did not put in /etc/hosts: the loopback conversation with the stub is a different capture.

    Lab
    1. Look at the file you already have. Every Linux machine ships with at least loopback and its own hostname here — which is why localhost resolves with the network unplugged. 
      cat /etc/hosts
      127.0.0.1 localhost
127.0.1.1 sandbox          ← the machine's own name, mapped locally
::1 ip6-localhost ip6-loopback  ← the IPv6 equivalents
    2. Add your own mapping. Pick a name that certainly does not exist in DNS, so there is no ambiguity about where the answer came from. 
      echo '192.0.2.10  shop.internal  shop' | sudo tee -a /etc/hosts
getent hosts shop.internal
      192.0.2.10      shop.internal shop     ← resolved instantly, with both names
    3. Now prove no query was sent. Start a capture on all interfaces filtered to DNS traffic, resolve the name in a second shell, and watch nothing appear. Then resolve a real internet name in the same window and watch packets fly — the contrast is the whole lesson. 
      # window 1:
sudo tcpdump -nn -i any port 53
# window 2:
getent hosts shop.internal        # answered from /etc/hosts
getent hosts example.com          # answered by DNS
      listening on any, link-type LINUX_SLL2 ...
    (nothing at all while shop.internal is resolved)
14:02:19.556 IP 127.0.0.1.41290 > 127.0.0.53.53: 4512+ A? example.com. (29)
14:02:19.577 IP 127.0.0.53.53 > 127.0.0.1.41290: 4512 1/0/0 A 23.220.75.232 (45)
    4. Confirm that the file wins even against a name DNS can answer. Map a real domain to an obviously wrong address, resolve it, then remove the line so you don't leave a trap behind. 
      echo '203.0.113.99  example.com' | sudo tee -a /etc/hosts
getent hosts example.com          # the local file overrides the internet
dig +short example.com            # dig ignores /etc/hosts entirely
sudo sed -i '/203.0.113.99/d' /etc/hosts    # clean up
      203.0.113.99    example.com       ← getent: the local file won
23.220.75.232                      ← dig: DNS still says the real address
    Verify

    You should be able to state, and have just witnessed, that a name in /etc/hosts resolves with no packet on the wire, and that it overrides DNS for every program that uses the resolver library. Confirm the residual entry is still working (getent hosts shop.internal returns 192.0.2.10) and that your example.com override is gone (getent hosts example.com now agrees with dig +short example.com). Then explain in one sentence why step 4 produced two different answers from two tools on the same machine.

    Gotchas

    The overriding gotcha is the invisible override. Because this file is consulted before anything else and leaves no trace in any log or capture, an entry someone added months ago will silently defeat every DNS-side investigation you run. When one machine disagrees with all the others about a name, /etc/hosts is the first place to look — before the resolver, before the server, before the zone. It costs one grep and it has ended many long afternoons.

    A milder one: the file has no TTL and no expiry, so nothing ever cleans it up. Test entries survive reboots, image builds and the departure of whoever added them. If you add a line for a temporary purpose — as you just did — remove it when you're finished, or at minimum comment it with a date and reason. And note that dig ignoring the file (step 4) is not a bug: dig is a DNS tool, and /etc/hosts is not DNS.

    Containers have their own /etc/hosts — it is written into the container filesystem at start-up, which is why editing it inside a running pod survives no restart at all. Kubernetes exposes controlled additions to it through a pod's hostAliases field, which is exactly the mechanism you just used by hand: a static name-to-IP mapping consulted before DNS, per pod. And "the container's /etc/hosts has an entry nobody expected" is the containerised version of the invisible override above.

    The generated pod resolver files, including /etc/hosts and hostAliases, are covered in W4.16; the DNS debugging ladder that checks them is W4.18.

    Docs

    man 5 hosts is one page and worth reading end to end — the field order, aliases, and the fact that it is consulted per the switch. man 5 nsswitch.conf for why it is consulted first. man 8 tcpdump for the capture filter used here (-i any, port 53, -nn to keep numbers numeric so the capture doesn't itself trigger lookups). For the systemd-resolved interaction, man 8 systemd-resolved documents that it reads /etc/hosts internally.

    B10.3

    /etc/resolv.conf line by line: nameserver, search, options ndots

    Why it matters

    This file is the entire client-side configuration of DNS on a Unix machine, and it has effectively three kinds of line. Read it fluently and you can predict, before running anything, exactly which queries a given name will produce and in which order. That prediction skill is what turns Kubernetes' famous ndots:5 from folklore into arithmetic — because a pod's version of this file is generated from precisely these same three fields.

    The concept

    When the dns module on the switch line is reached (B10.1), it reads /etc/resolv.conf to learn three things:

    • nameserver IP — who to ask. You may list up to three; they are tried in order, and the second is only consulted when the first fails to answer within a timeout, not when it answers "no such name." That distinction matters enormously: a healthy server saying NXDOMAIN ends the query, so a backup nameserver does not rescue you from a wrong-but-responsive one. Failover here is for a dead server, not a wrong one.
    • search dom1 dom2 … — a list of domains to append to short names. With search example.com corp.example.com, the name web may be tried as web.example.com. then web.corp.example.com.. This is a convenience for typing short names inside an organisation, and it is also the single sneakiest source of "it resolved, but to the wrong host."
    • options ndots:N — the threshold that decides whether a name is treated as short or as complete. If a name contains fewer than N dots, the resolver tries it against the search list first, and only tries it as-typed afterwards. If it contains N or more dots, the name is tried as-typed first. The default is ndots:1, meaning any name with no dots at all (web) gets the search treatment while anything with a dot (example.com) is tried literally first.

    Put those together and the algorithm for one lookup is mechanical. Count the dots in the name. If that count is less than ndots, generate one query per search domain (name + "." + domain), in list order, and only if all of them fail, query the name by itself. If the count is ndots or more, query the name by itself first, and fall back to the search list if that fails. Every query goes to nameserver #1 until it times out.

    Now the Kubernetes number makes sense in advance of ever meeting it. A pod is handed options ndots:5 and a search list of four domains. Any name with fewer than five dots — which is nearly every name a human types, including google.com with its single dot — is tried against all four search domains first, producing four failures before the real query succeeds. That is not a bug and not magic; it is this algorithm, with these two numbers, doing exactly what it says.

    name "web"→dots(0) < ndots(1)?yes →web.example.com.fails →web.

    The dot count decides the order: short names go through the search list first, complete names are tried as-typed first.

    Lab
    1. Read the file as it stands. On Ubuntu 24.04 it is a symlink to a generated file, and it will point at the local stub — both of which are explained in B10.7; for now just read the three kinds of line. 
      ls -l /etc/resolv.conf

    Current Scopes: DNS

      printf '%s\n' "web" "web.corp" "api.web.corp" | \
  awk '{n=gsub(/\./,"."); print $0, "dots="n, (n<1 ? "search first" : "literal first")}'

    4. See the Kubernetes numbers applied to the same arithmetic — with ndots:5, ordinary names flip to the other branch. 
      printf '%s\n' "web" "web.corp" "google.com" "api.web.svc.cluster.local" | \
  awk '{n=gsub(/\./,"."); print $0, "dots="n, (n<5 ? "SEARCH LIST FIRST" : "literal first")}'
      web dots=0 SEARCH LIST FIRST
web.corp dots=1 SEARCH LIST FIRST
google.com dots=1 SEARCH LIST FIRST    ← why external lookups from a pod are slow
api.web.svc.cluster.local dots=4 SEARCH LIST FIRST
    Verify

    Answer these from the rule, not from memory of the output. With search example.com corp.example.com and options ndots:1, how many queries will web produce at most, and in what order? (Up to three: web.example.com., then web.corp.example.com., then web. on its own.) With options ndots:5, how many will google.com produce before the successful one? (One per search domain first — with four search domains, four failures, then the literal query.) And why does adding a second nameserver line not protect you from a nameserver that answers wrongly? (Because a definite answer, including NXDOMAIN, ends the lookup — the second server is only tried when the first fails to respond at all.)

    Gotchas

    The most expensive misunderstanding here is treating multiple nameserver lines as redundancy. They protect against a server that is down, and not at all against a server that is up and wrong: the first server's authoritative-sounding "that name doesn't exist" terminates the search before the second is ever asked. If a resolver is returning bad answers, adding a backup changes nothing; you must fix or remove the bad one.

    The second is forgetting that ndots interacts with the search list to make lookups slower, not just different. Every search-list attempt is a real query with a real round trip and a real timeout budget. A high ndots combined with a long search list means every external name pays for several failures first — which is exactly the well-known Kubernetes DNS performance complaint, and why appending a trailing dot (B10.4) is such an effective fix for hot paths.

    Finally: on this machine the file is a symlink to generated content. Editing it directly appears to work and then silently reverts when something regenerates it — covered properly in B10.7. Resist the urge to vi /etc/resolv.conf until you've read that lesson.

    Every pod gets this exact file, generated by the kubelet: nameserver pointing at the cluster DNS Service address, search carrying <namespace>.svc.cluster.local svc.cluster.local cluster.local (plus any node search domains), and options ndots:5. That search list is what lets one pod reach another Service by bare name — curl http://payments works because payments is tried as payments.<namespace>.svc.cluster.local first. And the ndots:5 that makes external lookups cost four extra queries is the same arithmetic you just did by hand. You can override all three fields per pod with dnsConfig.

    The pod's resolv.conf and the full ndots:5 ladder is W4.16; the record shapes those search domains resolve to are W4.17.

    Docs

    man 5 resolv.conf is the authoritative list of every directive and option, including ndots, timeout, attempts and rotate — read the options section carefully, it is short and it is the whole game. man 1 resolvectl for reading the effective configuration rather than the file. man 5 systemd-resolved.conf for where the values on Ubuntu actually come from.

    B10.4

    Watch a short name fan out into a series of queries — and stop it with a dot

    Why it matters

    The previous lesson gave you the rule on paper. This one makes you watch it happen on the wire, because seeing four queries leave the machine for one name you typed once is the moment the search list stops being abstract. It also hands you the single most useful DNS diagnostic there is: the trailing dot, which takes the search list out of the experiment entirely and tells you in one command whether your problem is the name, the zone, the server — or the search path.

    The concept

    A fully qualified domain name (FQDN) is a name written all the way to the root, and the root is written as a trailing dot: example.com. — with the final dot — is complete, while example.com is, strictly, a name the resolver may still add something to. That trailing dot is not decoration. It is an instruction: this name is complete, ask exactly this, do not consult the search list. Every DNS name on the wire is fully qualified; the search list is purely a client-side convenience that manufactures FQDNs from what you typed.

    So one typed name can become several queries, and the queries are what you can observe. Run a capture on port 53 (B10.2) while resolving a short name with a search list configured, and you see the fan-out in order: name.searchdomain1., then name.searchdomain2., and the literal name. last (assuming the dot count is below ndots). Each of those is a real round trip with a real cost. Add the trailing dot and the capture shows exactly one query.

    The diagnostic power comes from comparing the two. If dig web.example.com. (with the dot) succeeds but web alone fails, the zone and the server are fine and your search line is at fault. If the dotted form also fails, stop looking at the client entirely — the problem is upstream, in the server or the zone. One character splits the search space in half.

    Lab
    1. Give the machine a search domain to work with. Rather than editing the symlinked /etc/resolv.conf (B10.3), set it properly through systemd-resolved so it survives and can be undone cleanly. 
      sudo resolvectl domain ens3 example.com corp.example.com
resolvectl domain ens3
      Link 2 (ens3): example.com corp.example.com     ← two search domains, in order
    2. Capture DNS traffic in one window and resolve a bare, non-existent short name in another. Count the queries and read their order — this is the fan-out, made visible. 
      # window 1:
sudo tcpdump -nn -i any port 53
# window 2:
getent hosts nosuchhost
      IP 127.0.0.1.35112 > 127.0.0.53.53: A? nosuchhost.example.com. (40)
IP 127.0.0.1.35112 > 127.0.0.53.53: A? nosuchhost.corp.example.com. (45)
IP 127.0.0.1.35112 > 127.0.0.53.53: A? nosuchhost. (29)
    ← one typed name, three queries, in search-list order then literal
    3. Now do the same with a trailing dot and watch the search list be skipped entirely. This is the control experiment you will run for the rest of your career. 
      # window 2, with the capture still running:
dig +short nosuchhost.example.com.     # explicitly complete: exactly one query
      IP 127.0.0.1.41903 > 127.0.0.53.53: A? nosuchhost.example.com. (40)
    ← one query only; nothing else was tried
    4. Now watch the ndots threshold pick the other branch. example.org has one dot, and the default ndots is 1 — one is not fewer than one, so this name is tried literally first, succeeds, and the search list is never reached. Same search configuration, one query instead of three, purely because of the dot count. 
      getent hosts example.org        # watch window 1
      IP ... A? example.org. (29)          ← literal first: 1 dot >= ndots 1
    ← it answered, so example.org.example.com. was never asked
    5. Put the search domains back to nothing so later lessons start clean. 
      sudo resolvectl domain ens3 ""
resolvectl domain ens3
      Link 2 (ens3):        ← empty again
    Verify

    With the capture running, you should be able to make the number of queries change on demand: bare short name with two search domains gives three queries; the same name with a trailing dot gives one. State what the trailing dot means (this name is complete — do not append anything) and give the one-line rule for using it as a diagnostic: if it resolves with the dot and fails without it, the fault is in the search path, not in the server or the zone.

    Gotchas

    The dangerous version of the search list is not the slow one, it is the silently successful one. If you ask for db and your search list contains a domain where db happens to exist, you get a perfectly valid answer for a completely different machine — no error, no warning, and every tool reporting success. This is the fault you will practise in B10.13, and the trailing-dot test is what exposes it in seconds: ask for db. and watch the answer change or vanish.

    A second, subtler one: the search list applies to the resolver library, so getent/applications use it and dig mostly does not (dig has its own +search/+nosearch options and defaults to not searching). That is another way the two tools legitimately disagree, and another reason to test with getent when you care about what the application sees. If you want dig to imitate the application, pass +search.

    Finally, note the cost model: every search-list attempt is a round trip and, when a server is slow rather than absent, each one waits out a timeout. A short name with a long search list and an unhealthy first nameserver can take many seconds to fail — which users report as "the app hangs on startup," not as "DNS is misconfigured."

    This is precisely why a pod resolving google.com fires four failing queries first: with ndots:5 and four search domains, google.com (one dot) is treated as a short name and walked through google.com.default.svc.cluster.local, google.com.svc.cluster.local, google.com.cluster.local and any node domain before the literal query succeeds. Writing google.com. with the trailing dot — or setting dnsConfig.options ndots:1 for that pod — collapses all five into one, which is a standard fix for DNS-heavy workloads. It is also the fastest way to prove, inside a broken cluster, that CoreDNS itself is fine and the search path is the problem.

    The full cluster search ladder is walked in W4.16; using it as a debugging step is W4.18.

    The system side

    B10.5

    Two kinds of nameserver: recursive resolvers and authoritative servers

    Why it matters

    "Nameserver" is one word covering two jobs that have almost nothing in common. One does errands: it takes your question, chases the answer across the internet, and keeps a copy. The other holds truth: it owns the records for one slice of the namespace and answers only about that slice. Confusing them produces questions that can't be answered — "why doesn't my authoritative server resolve google.com?" — and, more practically, it is the distinction that makes CoreDNS's role in a cluster comprehensible, because CoreDNS is deliberately both at once.

    The concept

    An authoritative server is the source of truth for a zone — a contiguous chunk of the name tree such as example.com and everything beneath it. Its records were put there deliberately by whoever runs that zone. Ask it about a name in its zone and it answers definitively: here is the address, or that name does not exist, full stop. Ask it about anything outside its zone and, properly configured, it declines — not its business, and it has no idea.

    A recursive resolver holds no truth at all. It is the hotel operator who looks a name up before dialling: you give it a name, and it does the walking — asking the root servers, then the servers they point to, then the servers they point to, until it reaches an authoritative server that can answer (B10.6). Then it hands you the answer and, crucially, keeps a copy for as long as the record's TTL allows (B10.10) so the next person who asks gets it instantly. "Recursive" names the behaviour: it will recurse down the tree on your behalf, rather than replying "not mine, go ask someone else."

    The nameserver line in your /etc/resolv.conf (B10.3) always points at the recursive kind. Your machine is a stub resolver — it asks one question and expects a complete answer; it does no walking itself. That three-tier arrangement (stub → recursive → authoritative) is the shape of essentially every DNS deployment on earth.

    You can see which kind you're talking to in the flags of an answer (B10.9). A recursive resolver sets ra — "recursion available" — meaning it is willing to do the legwork. An authoritative answer carries aa — "authoritative answer" — meaning this server owns the record rather than remembering it. An answer with ra and no aa came from a cache or a chase; an answer with aa came from the horse's mouth.

    your machine (stub)→recursive resolver→root→.com→authoritative for example.com

    Three tiers: you ask one question, the middle tier does all the walking, and only the last tier actually owns the record.

    Lab
    1. Ask your configured resolver a question and look at the flags. This is the recursive path — it will answer about a zone it does not own. 
      dig example.com A | grep -E 'flags:|ANSWER SECTION' -A2
      ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, ...   ← ra = recursion available, no aa
;; ANSWER SECTION:
example.com.  1783  IN  A  23.220.75.232      ← an answer it fetched or cached for you
    2. Now ask an authoritative server the same question directly. Find who is authoritative for the zone, then query one of those servers with @ — and note the different flag. 
      dig +short NS example.com          # who owns this zone?
dig @a.iana-servers.net example.com A | grep -E 'flags:|^example'
      a.iana-servers.net.
b.iana-servers.net.
;; flags: qr aa rd; QUERY: 1, ANSWER: 1, ...   ← aa = authoritative, and no ra
example.com.  86400  IN  A  23.220.75.232       ← note the full, un-decremented TTL
    3. Prove the authoritative server refuses to do errands. Ask it about a zone it does not own — it will not chase the answer for you. 
      dig @a.iana-servers.net wikipedia.org A | grep -E 'status:|flags:|ANSWER:'
      ;; flags: qr; QUERY: 1, ANSWER: 0, AUTHORITY: 0
    ← no ra: recursion is not available here; ANSWER: 0 — not its zone, not its problem
    4. Contrast the two TTLs you just saw. The authoritative answer carried the record's full lifetime; the recursive one carried whatever was left of it (proof it came from a cache — the mechanism you'll pin down in B10.10). 
      dig +short +ttlunits example.com A          # via your resolver: partial TTL
dig +short +ttlunits @a.iana-servers.net example.com A   # authoritative: full TTL
      23.220.75.232        ← +short hides TTLs; re-run without +short to compare them side by side
    Verify

    Explain in one sentence each: what a recursive resolver does that an authoritative server refuses to do (chase an answer through the tree on your behalf, for any zone, and cache the result), and what an authoritative server has that a recursive resolver does not (the actual records for a zone it owns, and the right to say definitively that a name in it does not exist). Then say which kind your /etc/resolv.conf points at (recursive — always) and which flag proves it (ra).

    Gotchas

    An open recursive resolver — one that will do errands for anyone on the internet — is a genuine hazard, not just untidy: attackers use them as amplifiers, sending small forged queries that produce large answers aimed at a victim. That is why the resolver on your machine listens only on loopback, and why running the resolver you build in B10.12 bound to a private address rather than 0.0.0.0 is the correct habit rather than a lab shortcut.

    The subtler gotcha is diagnosing at the wrong tier. If a name fails, asking your configured resolver tells you only that something in the chain failed. Asking the zone's authoritative server directly with dig @server name splits the problem cleanly in half: if the authoritative server answers correctly, the record exists and your resolver or the path to it is at fault; if the authoritative server also says no, the record genuinely isn't there and no amount of cache-flushing will help. Learn to bypass tiers deliberately — it is the fastest halving move in DNS debugging.

    CoreDNS in a cluster plays both roles in one process, which is why its configuration file has two distinct halves. It is authoritative for cluster.local — it owns the records for every Service and pod, generating them from the API rather than a zone file — and it is a recursive forwarder for everything else, passing external names on to the node's upstream resolvers. That dual identity explains the single most common cluster DNS symptom split: internal names failing (its authoritative half or its API watch is broken) versus external names failing (its forwarding half or the upstream is broken). Two different problems, two different fixes, told apart by which kind of name breaks.

    Reading CoreDNS's configuration plugin by plugin, including the kubernetes and forward halves, is W4.15; splitting a failure by internal-versus-external is a rung of the ladder in W4.18.

    Docs

    RFC 1034 §2.4 and §4 define the resolver-versus-name-server split in the original architecture and are surprisingly readable. man 1 dig for the @server syntax and the flag abbreviations (aa, ra, rd, tc). man 5 named.conf (if BIND is installed) shows how a real server is told to be one, the other, or both. For the amplification hazard, search "open resolver" — the operational literature is unanimous.

    B10.6

    The delegation walk: root → TLD → authoritative, watched with dig +trace

    Why it matters

    Nobody, anywhere, holds a list of all the world's domain names. That fact is not a limitation — it is the design, and it is the reason DNS has scaled for forty years without a central database. Watching the walk once, with your own eyes, replaces a vague sense that "DNS is a distributed system" with a concrete picture of a tree where each level knows only who to ask next. It also explains why caching is not an optimisation but a structural necessity, and why a cluster's DNS is arranged the way it is.

    The concept

    The namespace is a tree, read right to left. www.example.com. is: the root (the final dot), then the top-level domain com, then example, then www. Each level is served by different machines, and a level does not know the contents of the levels below it — it knows only who is authoritative for the next level down. Handing off responsibility for a subtree like that is called delegation, and it is recorded as NS records (B10.8) pointing at the servers that take over.

    So a recursive resolver starting from scratch does this, and only this:

    1. Ask one of the thirteen root server addresses (which every resolver ships with, hard-coded — this is the one piece of bootstrap knowledge in the system) for www.example.com.. The root does not know. It replies with a referral: "I don't have that, but here are the servers for com.."
    2. Ask a com. server the same question. It doesn't know either. Another referral: "here are the servers for example.com.."
    3. Ask an example.com. server. This one owns the zone, so it answers authoritatively (the aa flag from B10.5).

    The key idea to internalise is that steps 1 and 2 return referrals, not answers. A referral is a redirection with a list of names and addresses attached — the addresses ride along in the ADDITIONAL section (B10.9) as glue records, so the resolver doesn't have to resolve the nameserver's own name before it can ask it anything, which would be circular. Only the final response is an answer.

    Now the necessity of caching is obvious. If every lookup on the internet started at the root, the thirteen root server clusters would field every query ever made. They don't, because every resolver in the chain remembers the referrals as well as the answers — TLD server lists have TTLs measured in days — so in practice a resolver already knows the com. servers and often the zone's servers too, and a "cold" lookup like the one you're about to watch is rare.

    root (.)referral →com.referral →example.com.answer →23.220.75.232

    Two referrals and one answer: each level knows only who owns the next level down.

    Lab
    1. Run the walk yourself. +trace makes dig stop using your recursive resolver and do the recursion itself, printing every step — which is why the output is long and worth reading top to bottom. 
      dig +trace www.example.com | grep -vE '^;|^$' | head -20
      .            518400  IN  NS  a.root-servers.net.       ← the root's own NS set
com.         172800  IN  NS  a.gtld-servers.net.       ← referral: go ask .com
com.         172800  IN  NS  b.gtld-servers.net.
example.com. 172800  IN  NS  a.iana-servers.net.       ← referral: go ask example.com
example.com. 172800  IN  NS  b.iana-servers.net.
www.example.com. 86400 IN A 23.220.75.232              ← the answer, from the zone itself
    2. Read the server annotations. dig prints which server gave each block — watch the address change at every hop, which is the walk made explicit. 
      dig +trace www.example.com 2>/dev/null | grep 'Received'
      ;; Received 525 bytes from 198.41.0.4#53(a.root-servers.net) in 12 ms   ← the root
;; Received 1170 bytes from 192.5.6.30#53(a.gtld-servers.net) in 20 ms  ← the .com TLD
;; Received 56 bytes from 199.43.135.53#53(a.iana-servers.net) in 8 ms  ← authoritative
    3. Do one hop manually to prove a referral is not an answer. Ask a root server directly for a name it cannot possibly hold, and read what comes back: an empty ANSWER, a populated AUTHORITY. 
      dig @198.41.0.4 www.example.com | grep -E 'status:|ANSWER:|AUTHORITY SECTION' -A3 | head -12
      ;; flags: qr; QUERY: 1, ANSWER: 0, AUTHORITY: 13, ADDITIONAL: 27
;; AUTHORITY SECTION:
com.  172800  IN  NS  a.gtld-servers.net.      ← "not mine — these people handle .com"
com.  172800  IN  NS  b.gtld-servers.net.
    4. See the glue that stops the circularity. The ADDITIONAL section carries the referred servers' addresses, so the resolver can contact them without a second lookup. 
      dig @198.41.0.4 www.example.com | grep -A4 'ADDITIONAL SECTION'
      ;; ADDITIONAL SECTION:
a.gtld-servers.net.  172800  IN  A     192.5.6.30       ← glue: the address rides along
a.gtld-servers.net.  172800  IN  AAAA  2001:503:a83e::2:30
    Verify

    From your own +trace output, name the three servers that were asked and say which one gave an answer rather than a referral. Then explain, without notes, why the root servers are not overwhelmed by the world's DNS traffic (because referrals are cached with long TTLs, so almost no lookup actually starts at the root) and why glue records exist (so a referral to a.gtld-servers.net doesn't require resolving that name first, which would be circular).

    Gotchas

    +trace does not use your configured resolver, which is exactly why it is useful and exactly how it misleads people. It bypasses your nameserver, your cache and your search list entirely and talks to the internet's hierarchy directly. So a +trace that succeeds while ordinary resolution fails does not mean "DNS works" — it means the public hierarchy works while your resolver or its path does not. That is a valuable finding, but only if you know which question you asked. In a private or split-horizon setup (including a Kubernetes cluster) +trace is often useless, because the names you care about do not exist in the public tree at all.

    Second: a +trace run on a machine with no direct outbound access on port 53 — a common corporate or cloud setup where only the local resolver may talk to the internet — will hang or fail even when normal resolution is perfectly healthy. Don't diagnose that as broken DNS. It means the walk is someone else's job, which is the normal arrangement.

    A cluster's names live entirely outside this public tree, which is why cluster.local is a name nobody delegates and no root server has ever heard of. CoreDNS is simply declared authoritative for it inside the cluster, and every pod is pointed at CoreDNS. The delegation walk you just watched is what CoreDNS does on your behalf for external names via its forwarding configuration — usually not by walking the tree itself, but by forwarding to the node's upstream resolvers, which do. Understanding that a private zone is just an assertion made by whichever server your clients are pointed at is the whole conceptual basis for cluster DNS.

    The CoreDNS configuration declaring cluster.local and forwarding the rest is W4.15; the record shapes it serves for that zone are W4.17.

    man 1 dig for +trace, +nssearch and +norecurse (asking a server not to recurse is how you inspect exactly one tier). RFC 1034 §4.3.2 is the resolver algorithm the walk implements, written out step by step.     B10.7

    The local twist: systemd-resolved and the 127.0.0.53 stub

    Why it matters

    On Ubuntu 24.04 your /etc/resolv.conf does not point at a real DNS server. It points at 127.0.0.53 — a small server running on the machine itself, which caches, applies its own rules, and forwards what's left to the actual upstreams. Not knowing this produces two specific confusions that cost people hours: a tcpdump on the network interface that shows nothing during a lookup that plainly worked, and an edit to /etc/resolv.conf that works until, some minutes or one reboot later, it silently reverts. Both are explained by the same daemon.

    The concept

    systemd-resolved is a local resolver service. It listens on the loopback address 127.0.0.53, port 53, and it is what every program on the machine actually talks to when the dns path is taken. It is the hotel operator in the middle: it keeps a cache, it knows which upstream server to use for which domain, and it merges DNS configuration from every source on the machine — DHCP leases, netplan, VPN clients — into one coherent view.

    Three consequences follow directly, and each one is a diagnostic:

    • Cached answers never touch the network. The query goes to loopback, the answer comes back from memory. So tcpdump -i ens3 port 53 — a capture on the uplink — legitimately shows nothing. Capture on -i any or -i lo to see the query at all, and remember that seeing the loopback query but no uplink query means "served from cache," which is itself the answer to "why didn't my DNS change take effect?"
    • /etc/resolv.conf is generated. It is a symlink to /run/systemd/resolve/stub-resolv.conf, a file under /run — a directory that lives in memory and is rebuilt at every boot. Editing the target edits a temporary file; editing through the symlink writes content that anything from a DHCP renewal to a service restart will overwrite. It looks like it worked, which is what makes it a trap. Configure the daemon instead.
    • Per-domain routing. resolved can send different domains to different upstreams. A search domain gets appended to short names as in B10.3; a routing domain, written with a leading ~ (as in ~lab), is not appended to anything — it says "any query ending in lab goes to this server." That single feature is what makes B10.12's project clean: you can hand your private zone to your own resolver without disturbing how the machine resolves everything else.

    You inspect all of this with resolvectl, not by reading files: resolvectl status shows the effective per-link configuration and the real upstreams, resolvectl query NAME resolves through the daemon and tells you where the answer came from (including whether it was a cache hit), and resolvectl statistics shows the cache's hit rate. To change configuration, drop a file into /etc/systemd/resolved.conf.d/ and restart the service — the same drop-in pattern used everywhere in systemd.

    program→127.0.0.53→systemd-resolved (cache + routing)→upstream 192.168.64.1

    Everything local goes through the stub first; only a cache miss produces a packet on the uplink.

    Lab
    1. Confirm the two facts the lesson rests on: the file is a symlink to generated content, and the nameserver in it is loopback. 
      readlink -f /etc/resolv.conf

    You should be able to explain a capture that shows nothing (the answer came from resolved's cache, so no packet reached the uplink) and to state where the real upstream servers are recorded (in resolved's per-link configuration, visible with resolvectl status — not in /etc/resolv.conf, which only ever names the stub). Confirm your drop-in is removed and resolvectl status still reports resolv.conf mode: stub.

    Gotchas

    The classic mistake is hand-editing /etc/resolv.conf. It appears to work immediately — the resolver really does read the new content — and then a DHCP renewal, a netplan apply, a VPN connect or a reboot regenerates the file and your change is gone, usually at the least convenient moment and with no log entry that connects the two events. Whenever you find yourself about to edit it, edit /etc/systemd/resolved.conf.d/*.conf instead and restart the service. (If you genuinely want the file to be static, point the symlink at /run/systemd/resolve/resolv.conf for the real upstreams, or replace it with a plain file and accept that you now own it.)

    The second gotcha is capturing on the wrong interface. tcpdump -i ens3 port 53 will show you upstream traffic only. Every query your programs make goes to 127.0.0.53 over loopback first, so -i any (or -i lo) is what you want when the question is "did my program ask at all?" Getting this wrong produces the false conclusion "the application never even tried to resolve," when in fact it tried and was answered from cache.

    Third: resolvectl flush-caches clears resolved's cache but has no effect on caches inside your application (many runtimes and libraries cache resolutions themselves, sometimes forever) or on any upstream resolver's cache. When a flush "doesn't help," the stale copy is somewhere else — a distinction that matters a lot in B10.11.

    This local-stub arrangement is the reason a node's own /etc/resolv.conf is not simply copied into pods. If it were, every pod would be told to use 127.0.0.53 — an address that, inside the pod's own network namespace (B9.1), reaches nothing at all, because loopback in a namespace is private to that namespace. The kubelet therefore has a flag pointing it at the real upstream list (typically /run/systemd/resolve/resolv.conf) to use when building pod configuration, and the classic symptom of getting this wrong is "external DNS from pods fails while internal names resolve fine." You will meet that exact failure in the advanced track already understanding its cause.

    How a pod's resolver configuration is built, including the upstream-file question, is W4.16; CoreDNS's forwarding of external names to those upstreams is W4.15.

    Records and caching

    B10.8

    The record types, learned by their job: A, AAAA, CNAME, PTR, SRV, TXT, NS

    Why it matters

    DNS is often described as "the phone book of the internet," which undersells it: it is a general key-value store for names, and the value's type says what kind of question you asked. Knowing the handful of types that matter — and specifically what each one is for — turns a wall of dig output into a sentence you can read. It also removes the surprise from several Kubernetes features that are, quite literally, nothing more than one of these record types being served.

    The concept

    Every record is a four-part statement: a name, a TTL (how long it may be cached, B10.10), a class (always IN, for Internet — the others are historical), and a type, followed by type-specific data. You ask for a name and a type; asking for the wrong type gets you an empty answer even though the name exists perfectly well, which is a trap worth meeting early.

    • A — name → one IPv4 address. The workhorse. A name may have several A records, and a resolver typically returns them all; clients pick one, often rotating, which is the oldest form of load balancing there is.
    • AAAA — name → one IPv6 address ("quad-A"). Modern clients ask for both A and AAAA and prefer IPv6 when it works. This is why a broken AAAA record produces the maddening "slow for some users" symptom: they try IPv6 first, wait for it to fail, then fall back.
    • CNAME — canonical name: "this name is an alias for that name." The resolver, on receiving one, restarts the lookup at the target. The rules are strict: a name with a CNAME may have no other records, and therefore the top of a zone (the "apex", e.g. example.com itself) cannot be a CNAME, because it must carry NS and SOA records. That single restriction is why so many hosting providers invent proprietary "ALIAS" records.
    • PTR — address → name, the reverse direction. Reverse lookups don't magically invert the forward tree; they live in a special zone (in-addr.arpa for IPv4) where the address is written backwards. There is no rule that forward and reverse must agree, and often they don't.
    • SRV — service: name → host and port, with priority and weight. This is the only common record that carries a port number, which makes it the right answer for "where is this service, and on which port?" without hard-coding either.
    • TXT — arbitrary text hung on a name. Because anyone who controls a zone can publish text under it, TXT records became the universal proof-of-ownership mechanism (domain verification) and the carrier for mail policy (SPF, DKIM, DMARC).
    • NS — which servers are authoritative for a zone. These are the records that implement delegation (B10.6) — a referral is literally a set of NS records plus their glue.

    Two more you will see and should recognise without needing to use: SOA (start of authority) sits at the top of every zone and carries the zone's serial number and timing parameters, including the negative-caching TTL that B10.11 depends on; and MX routes mail for a domain to named hosts by preference.

    Lab
    1. Ask for the two address types explicitly and see that a name can have both — or only one. 
      dig +noall +answer example.com A
dig +noall +answer example.com AAAA
      example.com.  1795  IN  A     23.220.75.232

      dig +noall +answer example.com TXT

    Match each type to its job without notes: which one carries a port (SRV), which one is an alias that restarts the lookup (CNAME), which one goes from address to name (PTR), which one implements delegation (NS), which one carries proof-of-ownership text (TXT). Then explain what NOERROR with ANSWER: 0 means (the name exists, but has no record of the type you asked for) and why that is different from NXDOMAIN (the name does not exist at all) — a distinction B10.9 makes central.

    Gotchas

    The empty-but-successful answer is the trap that catches everyone once. NOERROR plus zero records does not mean failure and does not mean the name is wrong — it means you asked for a type this name doesn't carry. A tool that only prints the answer section (or dig +short, which prints nothing at all here) makes it look identical to "doesn't exist." Always glance at the status: line before concluding anything.

    The CNAME apex restriction bites in real deployments: you cannot point example.com itself at a load balancer's hostname with a CNAME, because the apex must hold NS and SOA records and a CNAME may not coexist with anything. Providers work around it with non-standard record types, which is why "just CNAME the root domain" is advice that fails.

    Finally, forward and reverse are independent. PTR records live in a zone controlled by whoever owns the address block, not the domain — usually your hosting provider. So a machine can have a perfectly good A record and a PTR that says something unrelated, and software that insists the two match (some mail systems, some old authentication schemes) will reject it for reasons that have nothing to do with your zone.

    Three of these are Kubernetes features wearing their DNS names. A normal Service is an A record for its ClusterIP. A headless Service (one with no ClusterIP) is a set of A records, one per backing pod, so the client sees the individual pods instead of a virtual address. An ExternalName Service is nothing but a CNAME answer — no proxying, no rules, just an alias. And SRV records are how a StatefulSet's members find each other with both address and port, which is what lets a database cluster form itself with no load balancer in the middle. When you meet those features, you will recognise them as record types you already queried by hand.

    Headless Services and per-pod records are W4.13; the full set of record shapes a cluster serves, verified with dig, is W4.17.

    B10.9

    Read a dig answer completely: sections, status, flags, query time

    Why it matters

    Most people read dig output by scanning for an IP address and ignoring everything else. Everything else is where the diagnosis lives. The status field alone tells you whether to go look at the name or at the server — two completely different investigations that present identically to a user as "it doesn't resolve." Reading the whole answer takes ten extra seconds and routinely saves an hour.

    The concept

    A DNS response has four sections, and dig prints them in order:

    • QUESTION — what was actually asked, fully qualified. Read it first, always: it is where you discover that the search list turned your short name into something you did not intend (B10.4).
    • ANSWER — the records that answer the question, including any CNAME hops taken along the way.
    • AUTHORITY — which servers are authoritative. On a failure this usually holds the zone's SOA record, and that SOA is what governs how long the failure is cached (B10.11).
    • ADDITIONAL — extra records the server volunteered, typically the addresses of servers named above (glue, B10.6), plus an OPT pseudo-record carrying EDNS options.

    Above the sections sits the header, and it holds the three things worth memorising:

    • status: — the verdict. NOERROR (the query succeeded; check ANSWER: for whether it succeeded with any records — see B10.8), NXDOMAIN (this name does not exist — the server is healthy and confident), SERVFAIL (the server tried and failed — a broken upstream, a DNSSEC validation failure, an unreachable zone), REFUSED (the server declines to answer you — usually an access-control or wrong-server problem).
    • flags: — qr (this is a response), rd (recursion was desired — you asked for legwork), ra (recursion available — the server does legwork), aa (authoritative answer — from the zone's owner, B10.5), tc (truncated — the answer didn't fit in a UDP packet and should be retried over TCP).
    • Query time — at the bottom, in milliseconds. A sub-millisecond time means a cache served you; tens of milliseconds means a real round trip; thousands means something timed out along the way. This one number is the fastest cache-hit detector you have.

    The status field is a routing decision for your investigation, and it is worth stating flatly: NXDOMAIN is a name problem; SERVFAIL is a server problem. On NXDOMAIN, go check the name and the search path — the server did its job and told you the truth. On SERVFAIL, stop looking at the name entirely and go check the server and its upstreams. Users report both as "it doesn't resolve," and half of all wasted DNS debugging time is spent investigating the wrong one of these two.

    Lab
    1. Read one successful answer completely, top to bottom, naming each part as you go.

    2. Now produce a genuine NXDOMAIN and read what changes. Note that the ANSWER section vanishes and an AUTHORITY section appears carrying the zone's SOA.

      ;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 51002

    3. Compare a cache hit with a cache miss using nothing but the query time. Flush, ask cold, then ask again warm.

    Verify

    Given only a dig header, you should be able to say what to do next. status: NXDOMAIN → the server is fine and the name does not exist; go check the spelling and the search path. status: SERVFAIL → the name may be fine; go check the server and its upstreams. status: NOERROR, ANSWER: 0 → the name exists but has no record of that type. Query time: 0 msec → you were served by a cache, so this tells you nothing about whether the authoritative data changed. Say each of those out loud before moving on.

    Gotchas

    dig +short is convenient and actively dangerous when debugging: it prints the answer records and nothing else, so NXDOMAIN, SERVFAIL, NOERROR-with-no-records and "the answer came from a stale cache" all look identical — an empty line. Use +short in scripts where you already know the shape of the answer; use full output whenever you are actually investigating.

    Second, always read the QUESTION section rather than trusting what you typed. Between the search list and shell quoting, the name that went out is not always the name you meant, and the QUESTION section is the only place the truth is recorded. This is how you catch a search-domain rewrite in one glance instead of ten minutes.

    Third, the SERVER: line at the bottom tells you who actually answered. On this machine it will normally say 127.0.0.53 — the stub — which means the answer may be cached and may be several tiers away from the truth. When an answer looks wrong, re-ask the authoritative server directly (B10.5) and compare; if they differ, you have found a caching problem rather than a data problem.

    Inside a cluster this reading skill is the debugging ladder. A pod that gets NXDOMAIN for payments has a name or namespace or search-path problem — the Service may not exist, or may be in a different namespace than assumed. A pod that gets SERVFAIL has a CoreDNS problem — its pods may be down, its upstream unreachable, or its configuration broken. And a Query time in the thousands points at the resolver being unreachable rather than wrong. Same four statuses, same four conclusions, one layer up.

    The cluster DNS debugging ladder built on exactly these signals is W4.18; the record shapes you'll be reading are W4.17.

    B10.10

    TTL: the contract every cache obeys, watched counting down

    Why it matters

    "I changed the DNS record but it's still going to the old server" is one of the most common and most misunderstood operational complaints, and the explanation is entirely contained in one number attached to every record. Understanding TTL turns DNS changes from a source of anxiety into something you can plan precisely — and, unusually for an operational skill, it lets you predict the exact duration of the confusion.

    The concept

    Every record carries a TTL — time to live — in seconds. It is a statement by the zone's owner: anyone who receives this record may keep using it for this many seconds without asking again. It is not advice and it is not a maximum-age suggestion; it is the contract on which the entire caching layer of DNS is built, and well-behaved resolvers obey it exactly.

    The mechanics are simple and produce an observable signature. When a resolver fetches a record fresh from an authoritative server, it stores the record with the full TTL, say 3600. Every subsequent answer it serves from that cache carries the remaining time: 3598, 3550, 41. When it hits zero the entry is discarded and the next query goes back to the source. So a decreasing TTL across two consecutive queries is direct proof you were served from a cache — and a TTL that resets to its full value means you reached the authoritative server, or that some cache in between refetched.

    The operational consequence is the important part. When you change a record, every resolver that already holds the old value keeps serving it until its copy expires — up to the full TTL, and the clock started whenever that resolver last fetched, which you cannot know. If the TTL is 86400 (a day), some users will see the old address for a day, and there is nothing you can do about it from your end: you cannot reach into other people's caches.

    Which yields the one piece of TTL discipline that matters: lower the TTL before a planned change, not during it. If a record has a 24-hour TTL and you want to move it tomorrow, drop the TTL to 60 seconds today; wait a full old-TTL period for the world's caches to pick up the short value; then make the change, which now propagates in about a minute; then raise the TTL again once you're happy. Doing it the other way around — lowering the TTL at the moment you make the change — accomplishes nothing, because everyone is still holding the long-TTL copy.

    fetch: TTL 3600→+10s: 3590→+3600s: expired→refetch: 3600

    A TTL you watch count down is a cached copy ageing; when it reaches zero the next query goes back to the source.

    Lab

    You should have watched one number decrease and then jump back up. Explain what each event meant (decreasing = a cached copy ageing; jumping back to full = the entry expired and was refetched from the source). Then state the planning rule in your own words: to make a DNS change propagate quickly, lower the TTL at least one old-TTL period before the change, not at the same time — and say why doing it simultaneously has no effect (every existing cache is still holding the long-TTL copy and will not re-ask until it expires).

    Gotchas

    You cannot flush other people's caches. resolvectl flush-caches clears the resolver on this machine and nothing else — not the corporate resolver, not the user's ISP, not the CDN, and not the application's own in-process cache. When a change "hasn't propagated," the honest answer is a duration (the remaining TTL) rather than an action, and the only real lever is the one you had to pull in advance.

    Application-level caching is the layer that breaks the model, and it is worth knowing about because it produces failures that look impossible. Some runtimes and libraries resolve a name once at start-up and hold the address forever, TTL be damned — so the record changes, every resolver in the chain obeys it, and one process keeps talking to the old address until it is restarted. If DNS is provably correct from the same machine and one process still disagrees, suspect the process, not DNS.

    Finally, resist the urge to set every TTL to 30 seconds "just in case." Short TTLs multiply query volume against your authoritative servers and remove the buffer that keeps things resolving during a brief outage — with a long TTL, caches keep serving through a blip; with a 30-second TTL, an authoritative outage becomes a global outage in half a minute. TTL is a trade between agility and resilience, chosen deliberately.

    Cluster DNS answers carry TTLs too — CoreDNS serves records for Services with a short TTL (30 seconds by default) and caches upstream answers according to their own TTLs. That short value is deliberate: a Service's endpoints change whenever pods come and go, so answers must go stale quickly. It is also why the "an application keeps talking to a deleted pod" problem is almost always application-side caching rather than a cluster fault — the cluster's own TTL already expired. When you tune CoreDNS's cache plugin later, you are setting exactly the trade described above.

    The CoreDNS cache plugin and its TTL settings are read in W4.15; how endpoint changes propagate into answers is W4.11.

    B10.11

    Negative caching: failure is remembered too

    Why it matters

    This lesson explains a sentence you have certainly heard and possibly said: "it started working on its own after a few minutes." Nothing works on its own. What happened is that a cached failure expired. Once you know that "no such name" is a cacheable answer with its own timer, a whole class of maddening, apparently-nondeterministic startup problems becomes predictable — and you know exactly which command shortens the wait.

    The concept

    Negative caching is the rule that a resolver may remember "this name does not exist" just as it remembers an address. If it did not, every typo and every probe for a non-existent name would hammer the authoritative servers forever, so the design is necessary. But the consequence is sharp: a name that does not exist yet can keep appearing not to exist after you create it.

    The timer is not the record's TTL — there is no record — so it comes from somewhere else: the SOA record returned in the AUTHORITY section of the NXDOMAIN response (B10.9). The SOA's last field is the minimum field, and modern DNS repurposes it as the negative-caching TTL: how many seconds a resolver may remember this "no." You saw it in B10.9's NXDOMAIN output; typical values are 300 to 3600 seconds. So the length of the confusion is written, in advance, in the zone you are querying — you can look it up rather than guess.

    The classic failure sequence is worth memorising because it recurs at every scale:

    1. Something starts up and resolves a name that does not exist yet — a service that hasn't been created, a peer that hasn't registered.
    2. It gets NXDOMAIN. The local resolver caches that negative answer for the SOA's minimum, say 600 seconds.
    3. The name is created, correctly, thirty seconds later. Everything is now right.
    4. The client keeps failing for the remaining nine and a half minutes, because it is being served a cached "no" — and every diagnostic you run from a different machine says the name resolves fine.

    Two remedies, one technical and one architectural. Technically, resolvectl flush-caches discards the negative entry immediately on this machine. Architecturally — and this is the durable lesson — startup code should re-resolve on retry, not resolve once and give up. A client that retries the connection but reuses a resolution it made at second zero will keep failing through the entire negative-cache window, and will look like a DNS problem when it is a retry-logic problem.

    Explain, without notes, where the negative-cache duration comes from (the minimum field of the SOA record returned in the NXDOMAIN response's AUTHORITY section — not from any record's TTL, since there is no record) and why "it started working on its own" is never actually true (a cached failure expired). Then state the architectural fix in one sentence: retry logic must re-resolve, not reuse a resolution made before the name existed.

    Gotchas

    The signature that identifies this fault is a disagreement between machines: the name resolves perfectly from your laptop and keeps failing on the one box that asked too early. That asymmetry is the tell, and it points at a cache rather than at DNS data. Chasing it in the zone will find nothing wrong, because nothing is wrong — the data is correct and one resolver is holding an expired opinion.

    Flushing is more limited than it looks. resolvectl flush-caches clears this machine's resolver only; an upstream resolver may have its own negative entry, and the application may have cached the failure in its own memory. If a flush doesn't fix it, walk outward — query the upstream directly, then check whether the process has been restarted since.

    And do not "fix" negative caching by disabling it. It exists to keep failures from generating unbounded traffic, and turning it off (or setting the SOA minimum to a few seconds across a zone) trades a bounded, predictable delay for a permanent load problem. The right fix lives in the client's retry behaviour, not in the resolver's memory.

    This is one of the most common "flaky startup" causes in a cluster. A pod that starts before the Service it depends on exists resolves the Service name, gets NXDOMAIN, and — if its client library resolved once — keeps failing after the Service is created, while kubectl and every other pod insist the name works fine. The Kubernetes-native answers are the same two: make the container's retry loop re-resolve each attempt, or express the dependency properly (an init container that waits, or a readiness probe that lets the platform retry for you). Recognising the signature — one pod failing, everything else fine, no configuration wrong — saves you from rebuilding a perfectly healthy DNS setup.

    B10.12

    Mini project — run your own resolver and serve a private zone into a namespace

    Why it matters

    Everything so far has been reading someone else's DNS. Now you become the server. You will run a resolver, invent a zone that exists nowhere on the internet, point a machine at it for that zone only, and then resolve those names from inside a network namespace you built in B9 — watching the query cross your own virtual cable. When you finish, you will have built, in miniature, exactly what CoreDNS is in a cluster: a resolver that is authoritative for a private zone, reachable from inside isolated network namespaces, forwarding everything else upstream. There is no step in that sentence you will not have performed with your own hands.

    The concept

    dnsmasq is a small, single-binary DNS server (and DHCP server, though we ignore that here). It suits this project precisely because it is configured in a few lines and can be both authoritative for a made-up zone and a forwarder for everything else — the dual role from B10.5. The pieces you assemble:

    • A zone that is just an assertion. local=/lab/ tells dnsmasq "you are authoritative for anything ending in lab — never forward those upstream, answer them yourself, and if you don't have the record, say NXDOMAIN." Add host-record= lines and you have a zone. Nobody delegated lab to you and no root server has heard of it; it is real because your clients are pointed at a server that says so — which is exactly the status of cluster.local.
    • Binding without a fight. Port 53 on this machine is already partly taken: systemd-resolved holds 127.0.0.53:53 (B10.7), and the kernel will not let a second process bind the wildcard 0.0.0.0:53 while any specific address on that port is in use. So dnsmasq's default configuration fails to start on Ubuntu, and the fix is not to disable resolved but to be specific: listen-address= plus bind-interfaces makes dnsmasq bind exactly one address. Two servers, two addresses, one port, no conflict.
    • Routing one zone without hijacking the machine. Rather than repointing everything at your new server, you give systemd-resolved a routing domain (B10.7): Domains=~lab with DNS=10.20.0.1 means "queries ending in lab go to that server; everything else carries on as before." This is split-horizon DNS in two lines, and it is the same idea a cluster applies when it points pods at CoreDNS for cluster.local and lets CoreDNS forward the rest.
    • A namespace's own resolver configuration. ip netns exec has a feature made for exactly this: if /etc/netns/<name>/resolv.conf exists, it is bind-mounted over /etc/resolv.conf for commands run in that namespace. So a namespace can have its own nameserver and its own search list while sharing the rest of the filesystem — which is, structurally, what a pod gets.

    You will reuse net-up.sh from B9.19 for the network: a bridge cni0 at 10.20.0.1 and namespaces pod1 (10.20.0.2) and pod2 (10.20.0.3). The bridge address is what dnsmasq will listen on, which makes it reachable from the namespaces and from the host, and from nowhere else.

    pod1 (10.20.0.2)→ veth →cni0 10.20.0.1→dnsmasq: authoritative for .lab→ else →upstream

    A private zone served on the bridge address, reachable from inside the namespaces and from the host — CoreDNS in miniature.

sudo ~/net-up.sh 2                      # from B9.19: cni0 at 10.20.0.1, pod1/pod2

      cni0  UP  10.20.0.1/24          ← the address the resolver will live on
  pod1 = 10.20.0.2

    2. Write the zone. Four lines of configuration make dnsmasq authoritative for lab, give it two records, bind it to one address so it cannot collide with resolved, and set a cacheable TTL so B10.10's countdown works on your own records. 
      sudo tee /etc/dnsmasq.d/lab.conf >/dev/null <<'EOF'
listen-address=10.20.0.1
bind-interfaces
local=/lab/
local-ttl=300
host-record=web.lab,10.20.0.2
host-record=db.lab,10.20.0.3
host-record=web.prod.lab,10.20.0.2
host-record=web.dev.lab,10.20.0.3

EOF

systemctl is-active dnsmasq; sudo ss -ulnp | grep ':53'
      active

UNCONN 0 0 127.0.0.53%lo:53 0.0.0.0:* users:(("systemd-resolve",...))     ← resolved, untouched
    3. Query it directly, bypassing every resolver on the machine. This proves the server itself is right before any client configuration is involved — the tier-splitting habit from B10.5. 
      dig @10.20.0.1 +noall +answer web.lab A

      web.lab.  300  IN  A  10.20.0.2       ← your record, your TTL
;; status: NXDOMAIN                   ← authoritative "no": local=/lab/ never forwards
    4. Point the host at it for .lab only, using a drop-in rather than editing /etc/resolv.conf (B10.7). Everything else must keep resolving normally — check that too. 
      sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/50-lab.conf >/dev/null <<'EOF'

      web.lab: 10.20.0.2                            ← routed to your server

example.com: 23.220.75.232                     ← everything else untouched

      sudo mkdir -p /etc/netns/pod1
printf 'nameserver 10.20.0.1\nsearch lab\n' | sudo tee /etc/netns/pod1/resolv.conf
sudo ip netns exec pod1 cat /etc/resolv.conf        # the bind-mounted version
sudo ip netns exec pod1 getent hosts web.lab

      # window 1:
sudo tcpdump -nn -i veth1 port 53
# window 2:
sudo ip netns exec pod1 dig +short web.lab

    7. Read your server's own log. log-queries makes dnsmasq narrate every question it is asked and where the answer came from — the same visibility CoreDNS's log plugin gives you. 
      sudo journalctl -u dnsmasq -n 6 --no-pager
      dnsmasq[3412]: query[A] web.lab from 10.20.0.2       ← the namespace asked
dnsmasq[3412]: config web.lab is 10.20.0.2                ← answered from your config
    Verify

    Four things should now be true, and each has a one-command check. Your server answers authoritatively for its zone (dig @10.20.0.1 web.lab returns a record; dig @10.20.0.1 nothing.lab returns NXDOMAIN rather than forwarding). The host resolves .lab through it without changing anything else (resolvectl query web.lab works and resolvectl query example.com still works). The namespace has its own resolver configuration (sudo ip netns exec pod1 cat /etc/resolv.conf differs from the host's). And the query genuinely traverses the veth (your tcpdump showed 10.20.0.2 > 10.20.0.1.53). Then answer the concept question: what makes lab a real zone? (Nothing but the fact that the clients are pointed at a server that claims it — exactly the status of cluster.local.)

    Gotchas

    If dnsmasq refuses to start, read the journal before changing anything: the overwhelmingly likely cause is the port-53 collision described above, and it appears as a bind failure. The fix is listen-address= plus bind-interfaces, which you already have — but note that bind-interfaces binds at start-up, so if cni0 does not exist yet, dnsmasq will fail with "cannot assign requested address." Run net-up.sh first, then restart dnsmasq. The general shape of this problem — a daemon that must be started after the interface it binds — recurs constantly.

    Do not solve the collision by disabling systemd-resolved or setting DNSStubListener=no. It is the frequently-recommended answer online and it is the wrong lesson: it removes the machine's cache and its per-domain routing to fix a problem that a one-line bind address solves. Coexistence is both easy and the correct model — and it is the model a cluster uses, where CoreDNS and the node's own resolver both exist and each has a defined scope.

    Keep /etc/netns/pod1/resolv.conf in mind as a general tool. It is bind-mounted only for processes started via ip netns exec, so a process that entered the namespace some other way (nsenter, a container runtime) will see the host's file instead. If a namespace mysteriously uses the wrong nameserver, check how the process got into the namespace before doubting the file.

    Finally, leave this setup running — B10.13 breaks exactly this rig three ways, and the cleanup instructions are at the end of that lesson.

    You have just built CoreDNS's job description. In a cluster: a DNS server runs as pods, is authoritative for a private zone (cluster.local) that nobody delegated and no root server knows, forwards everything else to upstream resolvers, and is reachable from inside every pod's network namespace at a fixed address written into that pod's own generated /etc/resolv.conf — with a search list that lets short names work. Every clause of that maps onto a step you just performed. The one thing your version lacks is automation: CoreDNS generates its records by watching the API for Services and pods instead of reading host-record= lines, which is the only substantive difference between your lab zone and a cluster's.

    CoreDNS's configuration, read plugin by plugin — kubernetes for the authoritative half, forward for the rest, cache for the TTLs — is W4.15; the per-pod resolver file you just imitated with /etc/netns/ is W4.16.

    B10.13

    Debugging drill — a wrong nameserver, a search-path rewrite, a stale cache

    Why it matters

    Three faults, and the discipline is to name each from its symptom before you look at any configuration. They are chosen because they fail in three completely different ways: the first fails loudly and slowly, the second does not fail at all (it succeeds, wrongly), and the third fails while every piece of configuration on the machine is correct. Learn to tell them apart by their signature and DNS stops being weather. Each runs against the rig you built in B10.12.

    Symptom 1 — everything fails, slowly (a wrong nameserver)
    1. Point the namespace at a nameserver that does not exist, then observe: every name fails, each attempt takes seconds rather than milliseconds, and nothing distinguishes one name from another. 
      multipass shell sandbox
printf 'nameserver 192.0.2.53\nsearch lab\n' | sudo tee /etc/netns/pod1/resolv.conf   # plant the fault
time sudo ip netns exec pod1 getent hosts web.lab; echo "exit=$?"
time sudo ip netns exec pod1 getent hosts example.com; echo "exit=$?"
      exit=2   (real ~5.0s)      ← the lab name fails, after a long wait
exit=2   (real ~5.0s)      ← the external name fails identically
    ← nothing resolves, everything is slow, all names behave the same
    Cause & fix

    The configured nameserver is unreachable, so every query waits out its timeout and fails. The signature is the uniformity plus the duration: a name problem affects some names, a server problem affects all of them, and an unreachable server (as opposed to a wrong one) adds seconds of timeout to each attempt. Confirm in two moves — dig @10.20.0.1 web.lab succeeds, proving the data and the server are fine, while dig web.lab through the configured resolver hangs; and a tcpdump -nn -i any port 53 shows queries leaving for 192.0.2.53 with no reply ever coming back. On a real system the same evidence appears as SERVFAIL or connection timed out; no servers could be reached. Fix by putting the right nameserver back: printf 'nameserver 10.20.0.1\nsearch lab\n' | sudo tee /etc/netns/pod1/resolv.conf. The reflex: if every name fails and each failure is slow, stop looking at names and go look at the nameserver.

    Symptom 2 — it resolves, to the wrong host (a search-path rewrite)
    1. Give the namespace two search domains in an order nobody double-checked, then ask for a short name. It resolves — instantly, successfully, with no error anywhere — to the wrong machine. 
      printf 'nameserver 10.20.0.1\nsearch dev.lab prod.lab\n' | sudo tee /etc/netns/pod1/resolv.conf
sudo ip netns exec pod1 getent hosts web          # you meant web.prod.lab (10.20.0.2)
sudo ip netns exec pod1 dig +short web.prod.lab.  # the trailing-dot control (B10.4)
      10.20.0.3       web        ← succeeded — but that is web.dev.lab, not prod
10.20.0.2                  ← the name you meant resolves correctly when fully qualified
    Cause & fix

    The search list completed the short name against the first domain that had a match, which was not the one intended. This is the nastiest of the three precisely because nothing reports an error: the lookup succeeds, the address is valid, a host answers, and every monitoring check goes green while traffic goes to the wrong environment. The tell is that the fully-qualified form (with the trailing dot) gives a different answer from the short form — which is the one-command diagnosis from B10.4, and worth running reflexively whenever an answer is surprising rather than absent. Confirm with a capture: tcpdump -nn -i veth1 port 53 shows the QUESTION as web.dev.lab., not web., which is the resolver telling you exactly what it did. Fix by ordering the search list deliberately (search prod.lab dev.lab) or, better, by using fully-qualified names in configuration and leaving short names to humans. The reflex: when a name resolves to something surprising, read the QUESTION section — the name you asked is not always the name you typed.

    Symptom 3 — the resolver and the source disagree (a stale cached record)
    1. Move a record at the source while a client is holding a cached copy. Every piece of configuration is now correct, and the client is still wrong — the DNS analogue of B9's stale conntrack entry. 
      resolvectl query web.lab | head -1                     # host caches it: 10.20.0.2, TTL 300
sudo sed -i 's/^host-record=web.lab,.*/host-record=web.lab,10.20.0.9/' /etc/dnsmasq.d/lab.conf
sudo systemctl restart dnsmasq                         # the source now says .9
dig @10.20.0.1 +short web.lab                          # ask the source directly
resolvectl query web.lab | head -1                     # ask the resolver
      web.lab: 10.20.0.2                 ← cached before the change
10.20.0.9                          ← the source: correct, updated
web.lab: 10.20.0.2                 ← the resolver: still serving the old answer
    Cause & fix

    A cached record is being served until its TTL expires, so the resolver and the authoritative source disagree while both are behaving correctly. The signature is precisely that disagreement: dig @<source> gives the new answer and the ordinary path gives the old one, with a Query time: 0 msec on the stale answer proving it came from memory (B10.9). Nothing is misconfigured — this is the system honouring the TTL contract from B10.10. Fix on this machine with sudo resolvectl flush-caches, then re-query and watch it agree; the general fix is to have lowered the TTL before the change, because you cannot flush anyone else's cache. The reflex: when the resolver and the source disagree, you have a caching problem, not a data problem — check the query time and flush before you touch a single record. This is the same lesson as B9's stale conntrack entry in a different layer: correct configuration plus remembered state equals wrong behaviour.

    Gotchas

    The three faults escalate in how hard they are to notice, which is the real point of the ordering. The first announces itself — everything is broken and slow, and someone will file a ticket within a minute. The second announces nothing at all; it succeeds, and it can run in production for months routing a fraction of traffic to the wrong environment until someone notices data in the wrong database. The third announces itself only as a disagreement between two machines, which is easy to dismiss as "must be a fluke, it works from here." Ranked by how much damage they can do before discovery, the order is exactly reversed from how loudly they fail.

    Each has a one-command discriminator, and they are worth keeping together as a kit. Everything fails, slowly → suspect the nameserver; discriminate with dig @<server> to bypass it. It resolves to the wrong thing → suspect the search path; discriminate with a trailing dot. Two machines disagree → suspect a cache; discriminate with Query time and a flush. Three symptoms, three commands, and between them they cover the large majority of real resolution incidents.

    Restore the rig before you leave: put the good record back and flush, so nothing here surprises you later.

    sudo sed -i 's/^host-record=web.lab,.*/host-record=web.lab,10.20.0.2/' /etc/dnsmasq.d/lab.conf
sudo systemctl restart dnsmasq
printf 'nameserver 10.20.0.1\nsearch lab\n' | sudo tee /etc/netns/pod1/resolv.conf
sudo resolvectl flush-caches
resolvectl query web.lab | head -1
    web.lab: 10.20.0.2        ← back to a known-good state

    All three are everyday cluster incidents wearing cluster clothes. A wrong or unreachable nameserver is a pod whose dnsPolicy or dnsConfig points it somewhere useless, or CoreDNS pods that are down — everything fails, slowly, for that pod only. A search-path rewrite is a bare Service name resolving in the wrong namespace because the pod's namespace search domain matched first, which sends traffic to a same-named Service in a different environment with no error anywhere. And the resolver-versus-source disagreement is a stale cached answer, which is why kubectl get svc showing the right endpoint while a pod talks to the wrong one is a caching question rather than a Kubernetes question. You now have the by-hand version of all three signatures.

    The cluster DNS debug ladder that formalises these discriminators is W4.18; the pod resolver settings that cause the first two are W4.16.

    B10 recall quiz

    Answer out loud before revealing. If you can explain why a pod fires four failing queries before resolving google.com, and why a name can keep failing for ten minutes after it starts existing, this module has done its job.

    1. Which piece of software actually turns a hostname into an address for an ordinary program, and which file tells it where to look?
      Answer

      The C library's resolver, entered through getaddrinfo(). /etc/nsswitch.conf's hosts: line lists the sources in order — typically files (read /etc/hosts) before dns (query a nameserver), sometimes with resolve (hand it to systemd-resolved) or mdns4_minimal in between. DNS is only one of several possible sources, which is why "the resolver" and "DNS" are not synonyms.

    2. ping myhost works and dig myhost returns nothing. Who is wrong?
      Answer

      Neither. ping goes through the resolver library and may be answered by /etc/hosts, mDNS or a local cache with no DNS query ever leaving the machine; dig builds a DNS packet itself and asks a nameserver directly, correctly reporting that no DNS record exists. Test with getent hosts NAME when you want to know what the application will get, and dig when you want to know what DNS says.

    3. You have search example.com corp.example.com and options ndots:1. How many queries does the name web produce, and in what order?
      Answer

      Up to three: web.example.com., then web.corp.example.com., then the literal web. — because web has zero dots, which is fewer than ndots:1, so the search list is tried first. Each attempt is a real round trip. Writing web. with a trailing dot produces exactly one query.

    4. Why does a pod with ndots:5 fire four failing queries before resolving google.com?
      Answer

      google.com has one dot, which is fewer than five, so it counts as a "short" name and is walked through every search domain first — google.com.default.svc.cluster.local, google.com.svc.cluster.local, google.com.cluster.local, plus any node domain — before the literal query finally succeeds. It is the plain dot-counting rule with a high threshold, not a bug. A trailing dot or dnsConfig with ndots:1 collapses it to one query.

    5. What is the difference between a recursive resolver and an authoritative server, and which flag proves which you're talking to?
      Answer

      A recursive resolver holds no records; it chases an answer through the tree on your behalf and caches it, for any zone — it sets ra (recursion available). An authoritative server holds the actual records for one zone and answers only about that zone, definitively — it sets aa (authoritative answer). Your /etc/resolv.conf always points at the recursive kind. CoreDNS is deliberately both: authoritative for cluster.local, a forwarder for everything else.

    6. In a dig +trace, what do the root and TLD servers actually return, and why are glue records needed?
      Answer

      Referrals, not answers: a set of NS records saying "not mine — these servers handle the next level down." Only the final, authoritative server returns an ANSWER section. Glue records are the referred nameservers' addresses, shipped in the ADDITIONAL section, so the resolver doesn't have to resolve a.gtld-servers.net before it can ask it anything — which would be circular.

    7. On Ubuntu 24.04, your /etc/resolv.conf says nameserver 127.0.0.53. What is that, and where are the real upstreams?
      Answer

      It's systemd-resolved's local stub listener — a caching, per-domain-routing resolver running on this machine. The real upstreams are in resolved's per-link configuration, visible with resolvectl status, and never appear in /etc/resolv.conf (which is a generated symlink into /run, so hand-editing it silently reverts). Two consequences: a capture on the uplink shows nothing for a cache hit, and configuration belongs in /etc/systemd/resolved.conf.d/.

    8. Which record type carries a port number, and which one is an alias that restarts the lookup?
      Answer

      SRV carries priority, weight, port and target — the only common record with a port, which is how StatefulSet members find each other. CNAME is the alias: the resolver receives it and restarts the lookup at the target. A CNAME may not coexist with other records, which is why a zone apex can never be one — and why an ExternalName Service, which is just a CNAME answer, behaves the way it does.

    9. status: NOERROR with ANSWER: 0. What happened, and how is it different from NXDOMAIN?
      Answer

      The name exists but has no record of the type you asked for — a successful query with an empty answer. NXDOMAIN means the name itself does not exist at all. Both look identical through dig +short (a blank line), which is why you read the status: line before concluding anything. And the routing rule: NXDOMAIN sends you to check the name and search path; SERVFAIL sends you to check the server and its upstreams.

    10. You query a name twice and the TTL goes from 3600 to 3590. What does that prove, and what would a jump back to 3600 mean?
      Answer

      A decreasing TTL proves you were served from a cache — you are watching a stored copy age. A jump back to the full value means the entry expired and was refetched from the source (or that you asked the authoritative server directly, which never counts down because it isn't caching). Corollary: to make a change propagate quickly, lower the TTL at least one old-TTL period before the change; doing both at once accomplishes nothing.

    11. A name starts failing before it exists, is then created correctly, and keeps failing on one machine for another nine minutes. Why, and where does the nine minutes come from?
      Answer

      Negative caching: the resolver cached the NXDOMAIN. The duration comes from the minimum field of the SOA record returned in the AUTHORITY section of that failure — not from any record's TTL, since there is no record. resolvectl flush-caches clears it on that machine; the durable fix is client-side, making retry logic re-resolve each attempt rather than reuse a resolution made before the name existed.

    12. What makes lab — or cluster.local — a real zone, given that no root server has heard of either?
      Answer

      Nothing but a server asserting it and clients being pointed at that server. In your project, local=/lab/ told dnsmasq to answer for lab authoritatively and never forward, and a routing domain (Domains=~lab) sent those queries there while everything else carried on upstream. A cluster does exactly this: CoreDNS is declared authoritative for cluster.local, every pod's generated resolv.conf points at it, and external names are forwarded on. Private zones are assertions, not delegations.

    • Use getent hosts to test what an application will experience and dig to test what DNS says — and know which question each answers.
    • Use /etc/hosts deliberately, prove with tcpdump that it puts nothing on the wire, and check it first when one machine disagrees with all the others.
    • Read /etc/resolv.conf line by line and predict, by counting dots against ndots, exactly which queries a given name will generate and in what order.
    • Explain ndots:5 and a cluster's four-domain search ladder as arithmetic rather than folklore, including why external lookups from a pod cost four extra queries.
    • Stop a search-list fan-out on demand with a trailing dot, and use that as the one-command test that separates a search-path fault from a server or zone fault.
    • Tell a recursive resolver from an authoritative server by the ra and aa flags, and halve any DNS problem by asking the authoritative server directly with dig @server.
    • Walk the root → TLD → authoritative delegation with dig +trace, read referrals and glue, and explain why caching is structural rather than an optimisation.
    • Explain the 127.0.0.53 stub, find the real upstreams with resolvectl status, capture on the right interface, and configure resolution with a drop-in instead of editing a generated file.
    • Use routing domains (~zone) to hand one zone to one server without disturbing how the machine resolves anything else.
    • Say what each record type is for — A, AAAA, CNAME, PTR, SRV, TXT, NS, SOA — and recognise Services, headless Services and ExternalName as three of them.
