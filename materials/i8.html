    I8 — CRI: the interface the kubelet speaks

    The first of the three contracts Kubernetes drives a node through. By the end you can say exactly what the kubelet asks for, in what order, and what comes back — and you will have implemented enough of the server side to make crictl believe you are a container runtime.

    Every module so far has been about a thing Kubernetes uses. This one is about a thing Kubernetes defines. CRI is the first of three interfaces — CRI, CNI, CSI — where the Kubernetes project stopped implementing and started specifying, and the shape it chose has consequences you can see from a node's shell: why a pod has a pause container, why an app container shares an IP but not a filesystem, why a broken network plugin produces pods with no logs at all, and why kubectl exec can fail against a host that appears nowhere in your kubeconfig. By the end you will have driven a whole pod through the interface by hand, and then implemented the other side of it.

    Checkpoints16 Hours~7 PrerequisitesI7
    • Why and what. Say what CRI replaced, state the contract in one sentence, and name its two services — then verify every clause of that sentence on a running node.
    • The sandbox model. Create a pod without Kubernetes, read the pause container off /proc, and find the single config field that makes containers in a pod share a network namespace.
    • The call sequence. Drive one pod's whole lifecycle in the kubelet's own order, including the two exec paths, in-place resource updates, and teardown.
    • Operating it. Make crictl a reflex, decode a raw CRI log file, and read the runtime's CRI configuration — including the cgroup driver, which is the single most common node misconfiguration in the field.
    • Project & drill. Write a CRI server in Python that crictl drives end to end, then diagnose three faults that all present as "the node is broken".

    I7 — CRI is a plugin inside the containerd you just took apart, so every call below lands on machinery you can already inspect from underneath.

    Which machine. Everything below ran on the single intermediate VM, sandbox (Ubuntu 24.04, kernel 6.8.0), with containerd 2.3.3, runc 1.5.1, crictl v1.36.0 and CNI plugins v1.9.1. There is no Kubernetes on it and no kubelet — which is the point: every call in this module is one you make yourself. Where a real kubelet would behave differently, that is said explicitly rather than glossed.

    Why and what

    I8.1

    What CRI replaced, and what its removal actually broke

    Why it matters

    Kubernetes has to start containers, but Kubernetes does not start containers. Something else does, and the kubelet asks it to. CRI — the Container Runtime Interface — is the shape of that asking. Knowing why it exists in that shape explains most of what the rest of this module makes you look at, and it settles an argument the internet got badly wrong in 2021.

    The concept

    Before CRI, the kubelet contained the code for talking to each container runtime. Not a plugin, not a library it loaded at runtime — code compiled into the kubelet binary, one branch per runtime. Docker support lived in the kubelet. rkt support lived in the kubelet. If you wanted your runtime supported, you opened a pull request against Kubernetes and waited.

    Three things follow from that arrangement, and all three are bad. Every runtime's bugs became kubelet bugs, because the buggy code shipped inside the kubelet. Every runtime's release cadence became Kubernetes' release cadence, because a fix could only reach users in a Kubernetes release. And the set of supported runtimes was decided by whoever had commit rights to one repository.

    CRI inverts all three. The kubelet ships one client — a generated gRPC stub — and anyone may write a server. A runtime bug is now the runtime's bug, fixed on the runtime's schedule, in a package you upgrade on its own. The kubelet does not know or care what is on the other end of the socket as long as it answers runtime.v1.

    dockershim was the last survivor of the old arrangement: the in-tree adapter that let the kubelet drive the Docker daemon, kept alive for years after CRI existed because so many clusters used it. It was removed in Kubernetes v1.24, and it is worth being precise about what that did, because the coverage at the time was not.

    • Images built with Docker were never affected. A docker build produces an OCI image — I4's subject, byte-for-byte the same artifact any other builder produces. Nothing about running it changed.
    • Using Docker on your laptop was never affected. The removal was about what runs on a node.
    • What broke was nodes whose container runtime was the Docker daemon. The fix was almost always to point the kubelet at containerd — which the Docker daemon had been using underneath the whole time. In most cases the same containerd, already installed, already running, already holding the same containers.

    That last point is the one worth carrying: the migration was mostly a change of address, not a change of machinery. The containerd you took apart in I7 is what Docker was driving all along.

    Lab
    1. Confirm the shape on your own box. There is no Docker here, no kubelet, and yet a full CRI runtime is listening — because CRI support is a property of containerd, not of Kubernetes. 
      which docker dockerd || echo "no docker on this machine"
sudo crictl version
      no docker on this machine
Version:  0.1.0
RuntimeName:  containerd
RuntimeVersion:  v2.3.3
RuntimeApiVersion:  v1
    2. Note what those four lines are. Version is the version of the response message, not of anything you installed. RuntimeName and RuntimeVersion are the server's, and they move on containerd's release schedule. RuntimeApiVersion is the contract, and it has been v1 since Kubernetes 1.23 — which is precisely the property that made removing dockershim survivable.
    Verify

    You can explain, in one paragraph and without hedging, what dockershim's removal cost a real cluster, and name two things people believed it broke that it did not.

    Gotchas
    • "Kubernetes deprecated Docker" is a sentence that means nothing. Kubernetes removed a shim that let the kubelet drive the Docker daemon. It did not deprecate the image format (that is OCI, I4), the build tool (that is I6), or the registry protocol (that is I5). If someone tells you their Dockerfiles stopped working in v1.24, that is not what happened.
    • The compatibility rule is asymmetric. An older kubelet against a newer runtime is generally fine — the runtime implements everything the kubelet knows how to ask for. A newer kubelet against an older runtime is the combination that bites, because the kubelet may send fields the runtime never implemented and will silently ignore. Upgrade the runtime first, then the kubelet.

    The advanced track walks the same path from the top down: W1.20 — Understand CRI: kubelet → containerd → shim → runc is the picture this module fills in from underneath, and W1.19 — the kubelet's syncLoop and its three pod sources is the loop that issues every call you are about to make by hand.

    Docs: the contract itself is a file, not a web page — search for cri-api on GitHub and read pkg/apis/runtime/v1/api.proto. For the dockershim history, kubernetes.io's "Don't Panic: Kubernetes and Docker" blog post is still the clearest statement of what did and did not change.

    I8.2

    A gRPC service, on a unix socket, defined by runtime.v1

    Why it matters

    Nine words describe the whole interface: a gRPC service, on a unix socket, defined by runtime.v1. Each clause is checkable on a running node in one command, and each one has an operational consequence. Learning to verify the sentence clause by clause is what turns "the runtime is broken" into a specific question with a specific answer.

    The concept

    gRPC is a remote-procedure-call system: you define messages and methods in a .proto file, a code generator turns that into client and server stubs, and calls travel as protobuf — a compact binary encoding — over HTTP/2. The important word is generated. The contract is not prose that two teams interpret; it is a machine-readable file both sides compile against. That is why CRI has stayed stable for years while the kubelet and containerd changed underneath it, and it is why you will be able to write a working CRI server in I8.15 without reading a single page of documentation about wire formats.

    A unix socket rather than a TCP port means the trust boundary is filesystem permissions. There is no authentication in CRI — none, at any layer. The socket is srw-rw---- root:root, and that file mode is the entire access control, exactly as I7.14 found for containerd's own API. Anyone who can write to it can run any container, as root, with any bind mount, on that node.

    And runtime.v1 is the protobuf package name — the versioned namespace the messages live in. It has been v1 throughout, and the compatibility promise attached to it is what makes a kubelet and a runtime upgradeable independently.

    One detail on this box is worth pausing over: crictl and ctr use the same socket. They are not two daemons; they are two gRPC services registered on one listener. ctr speaks containerd's own native API (I7's subject), crictl speaks CRI, and both arrive at /run/containerd/containerd.sock. That is why an I7 finding — that the socket is root on the node — transfers here unchanged, and why "containerd is up" and "CRI is working" are two different claims.

    The contract's own words for the services it defines:

    // Runtime service defines the public APIs for remote container runtimes
    service RuntimeService {
    Kubernetes cri-api, runtime.v1 — pkg/apis/runtime/v1/api.proto
    Lab
    1. Find the socket the kubelet would use, and read its mode. This is the whole security model. 
      ls -l /run/containerd/containerd.sock
cat /etc/crictl.yaml
      srw-rw---- 1 root root 0 Jul 30 12:55 /run/containerd/containerd.sock
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
timeout: 10

      The timeout: 10 matters more than it looks — you will meet it in I8.4, where a cold node's first pod takes longer than ten seconds and the resulting error names nothing useful.

    2. Confirm the API version, and notice that client and server are different projects at different versions. 
      crictl --version
sudo crictl version
      crictl version v1.36.0
Version:  0.1.0
RuntimeName:  containerd
RuntimeVersion:  v2.3.3
RuntimeApiVersion:  v1

      crictl 1.36 is versioned with Kubernetes; containerd 2.3.3 is not. Neither knows the other's version number, and neither needs to.

    3. Prove the "one socket, two services" claim by asking the same file a question in containerd's native dialect and then in CRI's. 
      sudo ctr version | head -2
sudo crictl version | head -2
      Client:
  Version:  v2.3.3
Version:  0.1.0
RuntimeName:  containerd
    Verify

    You can state the contract in one sentence and point at the evidence for each clause: the socket file and its mode, the v1 in crictl version, and the fact that the client and server carry unrelated version numbers.

    Gotchas
    • Write access to the CRI socket is root on the node, with no audit trail. There is no user, no token, no per-call authorisation — the socket mode is all of it. A pod that mounts this socket has escaped, which is the same warning as I7.14 and worth repeating because CRI adds a second path to the same door.
    • "containerd is running" does not mean "CRI is answering". The CRI plugin can fail to load while the daemon stays up — you will make exactly that happen in I8.14. Check the service, not the process.
    • crictl's default timeout is 10 s and it is a client-side timeout. When it fires, the server is still working; you get DeadlineExceeded and the server gets a cancelled context. The real cause is in the runtime's log, not in crictl's output.

    The kubelet is told this endpoint with --container-runtime-endpoint, which you can see on any node's kubelet command line — W1.2 — how each component actually runs on the node shows where to look. The unix-socket-as-trust-boundary idea was built by hand in B9.18 — talk over a socket, and why containerd.sock is root.

    Docs: in the exam docs, search container runtimes for the endpoint flags and the socket paths for containerd and CRI-O. For the contract itself, the cri-api repository's api.proto is the only authoritative source.

    I8.3

    Two services, not one — and why images are separate

    Why it matters

    CRI is usually drawn as one box. It is two: RuntimeService and ImageService. That split is not bookkeeping — it halves your search space during an incident, because "images pull but nothing starts" and "containers start but images fail" are failures of two different services with two different dependency sets.

    The concept

    RuntimeService owns everything about running things: sandboxes, containers, exec, attach, port-forward, logs, stats, and the runtime's own health. ImageService owns everything about images: pull, list, status, remove, and filesystem usage.

    They are separate because they can genuinely be provided by different components, and the kubelet supports exactly that — --image-service-endpoint is a distinct flag from the runtime endpoint. But the more useful reason is the line the split draws. The image half is the half that talks to the network. It needs registry credentials, it is where pull secrets and digest pinning and registry mirrors live (all of I5), and it is subject to rate limits and DNS and TLS. The runtime half never opens a socket to the internet. When a node misbehaves, deciding which half you are looking at eliminates the other half's entire failure surface.

    On containerd 2.x the split is not a diagram — it is two plugins with two IDs, plus a third that registers both on the gRPC listener. You can see all three in the plugin table, which after I7.8 you already know is the honest source of truth on a machine with no config file.

    The proto defines them as two services in one file:

    // ImageService defines the public APIs for managing images.
    service ImageService {
    Kubernetes cri-api, runtime.v1 — pkg/apis/runtime/v1/api.proto
    Lab
    1. Find the two services as two plugins. The third row is the gRPC registration that puts both on the socket. 
      sudo ctr plugins ls | awk 'NR==1 || /cri/'
      TYPE                                      ID                       PLATFORMS      STATUS
io.containerd.cri.v1                      images                   -              ok
io.containerd.cri.v1                      runtime                  linux/amd64    ok
io.containerd.grpc.v1                     cri                      -              ok

      Note the platform column: the image plugin is platform-agnostic (it can hold an arm64 image on an amd64 node — I4.8's subject), while the runtime plugin is bound to linux/amd64, because running is where the architecture finally has to match.

    2. Query each service from the client side. 
      sudo crictl ps        # RuntimeService.ListContainers
sudo crictl images    # ImageService.ListImages
      CONTAINER   IMAGE   CREATED   STATE   NAME   ATTEMPT   POD ID   POD   NAMESPACE

IMAGE                      TAG      IMAGE ID        SIZE
docker.io/library/alpine   3.21     2607caa980584   3.66MB
registry.k8s.io/pause      3.10     873ed75102791   320kB
registry.k8s.io/pause      3.10.2   4a83b15d3ecfe   321kB
    3. Ask the ImageService for its own filesystem accounting — a call the RuntimeService has no equivalent of, and the one the kubelet uses to decide the node has DiskPressure. 
      sudo crictl imagefsinfo | jq -c '.status.imageFilesystems[]'
      {"fsId":{"mountpoint":"/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs"},
 "inodesUsed":{"value":"525"},"timestamp":"1785399743051488965","usedBytes":{"value":"9986048"}}

      The mountpoint is the snapshotter directory, not the content store. I7.12 measured why that is the number that matters: unpacked layers ran about three times the compressed size, so the snapshotter is what fills a node, and crictl images systematically understates it.

    4. Ask the runtime for its health. This is Status(), the call the kubelet polls to decide whether the node can accept pods at all. 
      sudo crictl info | jq -c '.status.conditions[]'
      {"message":"","reason":"","status":true,"type":"RuntimeReady"}
{"message":"","reason":"","status":true,"type":"NetworkReady"}
{"message":"","reason":"","status":true,"type":"ContainerdHasNoDeprecationWarnings"}

      Two of those three are in the spec; the third is containerd's own. NetworkReady is the one you will break deliberately in I8.7, and it is the condition behind a large share of real NotReady nodes.

    Verify

    Given a symptom — "every pod on this node is stuck pulling" versus "images are all present but nothing starts" — you can name which of the two services to investigate and, for the image half, list the external dependencies that the runtime half does not have.

    Gotchas
    • crictl imagefsinfo reports the snapshotter, not the images. A node whose crictl images total looks modest can still be out of disk, because that total is compressed sizes and the snapshotter holds them unpacked. Believe imagefsinfo and df, not the image list.
    • The two endpoints usually point at the same socket, so people forget they are separable. They still fail separately: a registry outage takes the ImageService down while the RuntimeService keeps every running container alive, which is exactly why existing pods survive a registry outage and new ones do not.

    The image half is where W6.17 — image failures: ErrImagePull, ImagePullBackOff, and the three root causes lives; the runtime half is W6.11 — the kubelet classics. The snapshotter-versus-content-store distinction behind imagefsinfo was measured in I7.12 — the third store, and the only one with no upstream.

    Docs: search the exam docs for node-pressure eviction to see how imagefsinfo feeds DiskPressure, and for images to find the pull-policy and pull-secret behaviour that lives entirely on the ImageService side.
