    I8 — CRI: the interface the kubelet speaks

    The first of the three contracts Kubernetes drives a node through. By the end you can say exactly what the kubelet asks for, in what order, and what comes back — and you will have implemented enough of the server side to make crictl believe you are a container runtime.

    Every module so far has been about a thing Kubernetes uses. This one is about a thing Kubernetes defines. CRI is the first of three interfaces — CRI, CNI, CSI — where the Kubernetes project stopped implementing and started specifying, and the shape it chose has consequences you can see from a node's shell: why a pod has a pause container, why an app container shares an IP but not a filesystem, why a broken network plugin produces pods with no logs at all, and why kubectl exec can fail against a host that appears nowhere in your kubeconfig. By the end you will have driven a whole pod through the interface by hand, and then implemented the other side of it.

    Checkpoints16 Hours~7 PrerequisitesI7
    • Why and what. Say what CRI replaced, state the contract in one sentence, and name its two services — then verify every clause of that sentence on a running node.
    • The sandbox model. Create a pod without Kubernetes, read the pause container off /proc, and find the single config field that makes containers in a pod share a network namespace.
    • The call sequence. Drive one pod's whole lifecycle in the kubelet's own order, including the two exec paths, in-place resource updates, and teardown.
    • Operating it. Make crictl a reflex, decode a raw CRI log file, and read the runtime's CRI configuration — including the cgroup driver, which is the single most common node misconfiguration in the field.
    • Project & drill. Write a CRI server in Python that crictl drives end to end, then diagnose three faults that all present as "the node is broken".

    I7 — CRI is a plugin inside the containerd you just took apart, so every call below lands on machinery you can already inspect from underneath.

    Which machine. Everything below ran on the single intermediate VM, sandbox (Ubuntu 24.04, kernel 6.8.0), with containerd 2.3.3, runc 1.5.1, crictl v1.36.0 and CNI plugins v1.9.1. There is no Kubernetes on it and no kubelet — which is the point: every call in this module is one you make yourself. Where a real kubelet would behave differently, that is said explicitly rather than glossed.

    Why and what

    I8.1

    What CRI replaced, and what its removal actually broke

    Why it matters

    Kubernetes has to start containers, but Kubernetes does not start containers. Something else does, and the kubelet asks it to. CRI — the Container Runtime Interface — is the shape of that asking. Knowing why it exists in that shape explains most of what the rest of this module makes you look at, and it settles an argument the internet got badly wrong in 2021.

    The concept

    Before CRI, the kubelet contained the code for talking to each container runtime. Not a plugin, not a library it loaded at runtime — code compiled into the kubelet binary, one branch per runtime. Docker support lived in the kubelet. rkt support lived in the kubelet. If you wanted your runtime supported, you opened a pull request against Kubernetes and waited.

    Three things follow from that arrangement, and all three are bad. Every runtime's bugs became kubelet bugs, because the buggy code shipped inside the kubelet. Every runtime's release cadence became Kubernetes' release cadence, because a fix could only reach users in a Kubernetes release. And the set of supported runtimes was decided by whoever had commit rights to one repository.

    CRI inverts all three. The kubelet ships one client — a generated gRPC stub — and anyone may write a server. A runtime bug is now the runtime's bug, fixed on the runtime's schedule, in a package you upgrade on its own. The kubelet does not know or care what is on the other end of the socket as long as it answers runtime.v1.

    dockershim was the last survivor of the old arrangement: the in-tree adapter that let the kubelet drive the Docker daemon, kept alive for years after CRI existed because so many clusters used it. It was removed in Kubernetes v1.24, and it is worth being precise about what that did, because the coverage at the time was not.

    • Images built with Docker were never affected. A docker build produces an OCI image — I4's subject, byte-for-byte the same artifact any other builder produces. Nothing about running it changed.
    • Using Docker on your laptop was never affected. The removal was about what runs on a node.
    • What broke was nodes whose container runtime was the Docker daemon. The fix was almost always to point the kubelet at containerd — which the Docker daemon had been using underneath the whole time. In most cases the same containerd, already installed, already running, already holding the same containers.

    That last point is the one worth carrying: the migration was mostly a change of address, not a change of machinery. The containerd you took apart in I7 is what Docker was driving all along.

    The contract's identity is three lines at the top of one file. This is what replaced "open a pull request against the kubelet":

    package runtime.v1;
    option go_package = "k8s.io/cri-api/pkg/apis/runtime/v1";

    Gotchas
    • "Kubernetes deprecated Docker" is a sentence that means nothing. Kubernetes removed a shim that let the kubelet drive the Docker daemon. It did not deprecate the image format (that is OCI, I4), the build tool (that is I6), or the registry protocol (that is I5). If someone tells you their Dockerfiles stopped working in v1.24, that is not what happened.
    • The compatibility rule is asymmetric. An older kubelet against a newer runtime is generally fine — the runtime implements everything the kubelet knows how to ask for. A newer kubelet against an older runtime is the combination that bites, because the kubelet may send fields the runtime never implemented and will silently ignore. Upgrade the runtime first, then the kubelet.

    I8.2

    A gRPC service, on a unix socket, defined by runtime.v1

    Why it matters

    Nine words describe the whole interface: a gRPC service, on a unix socket, defined by runtime.v1. Each clause is checkable on a running node in one command, and each one has an operational consequence. Learning to verify the sentence clause by clause is what turns "the runtime is broken" into a specific question with a specific answer.

    The concept

    gRPC is a remote-procedure-call system: you define messages and methods in a .proto file, a code generator turns that into client and server stubs, and calls travel as protobuf — a compact binary encoding — over HTTP/2. The important word is generated. The contract is not prose that two teams interpret; it is a machine-readable file both sides compile against. That is why CRI has stayed stable for years while the kubelet and containerd changed underneath it, and it is why you will be able to write a working CRI server in I8.15 without reading a single page of documentation about wire formats.

    A unix socket rather than a TCP port means the trust boundary is filesystem permissions. There is no authentication in CRI — none, at any layer. The socket is srw-rw---- root:root, and that file mode is the entire access control, exactly as I7.14 found for containerd's own API. Anyone who can write to it can run any container, as root, with any bind mount, on that node.

    And runtime.v1 is the protobuf package name — the versioned namespace the messages live in. It has been v1 throughout, and the compatibility promise attached to it is what makes a kubelet and a runtime upgradeable independently.

    One detail on this box is worth pausing over: crictl and ctr use the same socket. They are not two daemons; they are two gRPC services registered on one listener. ctr speaks containerd's own native API (I7's subject), crictl speaks CRI, and both arrive at /run/containerd/containerd.sock. That is why an I7 finding — that the socket is root on the node — transfers here unchanged, and why "containerd is up" and "CRI is working" are two different claims.

    Gotchas
    • Write access to the CRI socket is root on the node, with no audit trail. There is no user, no token, no per-call authorisation — the socket mode is all of it. A pod that mounts this socket has escaped, which is the same warning as I7.14 and worth repeating because CRI adds a second path to the same door.
    • "containerd is running" does not mean "CRI is answering". The CRI plugin can fail to load while the daemon stays up — you will make exactly that happen in I8.14. Check the service, not the process.
    • crictl's default timeout is 10 s and it is a client-side timeout. When it fires, the server is still working; you get DeadlineExceeded and the server gets a cancelled context. The real cause is in the runtime's log, not in crictl's output.

    The kubelet is told this endpoint with --container-runtime-endpoint, which you can see on any node's kubelet command line — W1.2 — how each component actually runs on the node shows where to look. The unix-socket-as-trust-boundary idea was built by hand in B9.18 — talk over a socket, and why containerd.sock is root.

    I8.3

    Two services, not one — and why images are separate

    Why it matters

    CRI is usually drawn as one box. It is two: RuntimeService and ImageService. That split is not bookkeeping — it halves your search space during an incident, because "images pull but nothing starts" and "containers start but images fail" are failures of two different services with two different dependency sets.

    The concept

    RuntimeService owns everything about running things: sandboxes, containers, exec, attach, port-forward, logs, stats, and the runtime's own health. ImageService owns everything about images: pull, list, status, remove, and filesystem usage.

    They are separate because they can genuinely be provided by different components, and the kubelet supports exactly that — --image-service-endpoint is a distinct flag from the runtime endpoint. But the more useful reason is the line the split draws. The image half is the half that talks to the network. It needs registry credentials, it is where pull secrets and digest pinning and registry mirrors live (all of I5), and it is subject to rate limits and DNS and TLS. The runtime half never opens a socket to the internet. When a node misbehaves, deciding which half you are looking at eliminates the other half's entire failure surface.

    On containerd 2.x the split is not a diagram — it is two plugins with two IDs, plus a third that registers both on the gRPC listener. You can see all three in the plugin table, which after I7.8 you already know is the honest source of truth on a machine with no config file.

    The sandbox model

    I8.4

    Create a pod without Kubernetes, and meet the pause container

    Why it matters

    A pod is not a kernel object. Linux has no idea what one is. A pod is a container that does nothing, plus other containers that borrow its namespaces — and you can build one by hand, in three commands, with no Kubernetes anywhere. Doing it once permanently removes the mystery from a lot of pod behaviour.

    The concept

    The interface calls it a sandbox: the room rented, numbered and wired before any guest checks in. RunPodSandbox is the call that rents it, and what it actually produces is an ordinary container running a program called pause whose entire job is to exist.

    Why must something exist? Because of ordering and lifetime. A namespace is destroyed when the last process in it exits unless something pins it (B6.3's lesson, that a namespace is a file you can hold open). The pod's network and IPC namespaces must be created before the first app container starts, must survive every app container dying and being replaced, and must be the last thing torn down. "A process that does nothing, for as long as the pod lives" is precisely the right tool, and its source is a few dozen lines: set up signal handling, reap orphaned children, block forever.

    You will see that "block forever" literally. The kernel's own record of what the pause process is doing names the syscall.

    There is one refinement the folklore misses, and it is visible on this box. On containerd the network namespace is not held by pause at all. It is created and bind-mount pinned under /var/run/netns/ before the pause container exists, because CNI has to run against it first (that is I8.7's seam). Pause genuinely holds the IPC and UTS namespaces via /proc/<pid>/ns/…, and the netns is pinned by a file. Both mechanisms are B6's; only one of them is the pause container.

    I8.5

    The one field that explains "containers in a pod share a network namespace"

    Why it matters

    Sidecars reach each other on localhost. They cannot see each other's files. They cannot see each other's processes — usually. All of that is famous pod behaviour, and all of it is one array in the generated OCI config, with a path on some entries and not others. Once you have seen it, pod semantics stop being a Kubernetes feature and become a consequence.

    The concept

    I2.7 taught the runtime spec's linux.namespaces array and the rule that governs it: an entry with a path means join this existing namespace, and an entry without one means unshare a new one. B6 taught that a namespace is identified by an inode you can read through /proc/<pid>/ns/. Put the two together and the CRI plugin's job for an app container is almost trivial: look up the sandbox's PID, and write /proc/<that pid>/ns/net into the container's config.

    The default split is: net, IPC and UTS joined; mount and cgroup private. Shared network means one IP, one loopback, one port space — which is why two containers in a pod cannot both bind :80, and why one can curl the other on 127.0.0.1. Shared UTS means one hostname. Private mount namespace means each container keeps its own filesystem view, which is why a sidecar cannot read the app's files unless a volume is explicitly shared into both.

    PID is the interesting one, because it is configurable and because the switch is on the container config, not the pod config — a detail that is easy to get backwards. In Kubernetes you write shareProcessNamespace: true at pod level; the kubelet translates that into namespace_options.pid = POD on each container's CRI request. Setting it on the sandbox config alone does nothing, as the lab below demonstrates.

    The enum that decides it, with the spec's own examples:

    enum NamespaceMode {
        // A POD namespace is common to all containers in a pod.
        // For example, a container with a PID namespace of POD expects to view
        // all of the processes in all of the containers in the pod.
        POD = 0;
        // A CONTAINER namespace is restricted to a single container.
        // For example, a container with a PID namespace of CONTAINER expects to
        // view only the processes in that container.
        CONTAINER = 1;
        // A NODE namespace is the namespace of the Kubernetes node.
        // For example, a container with a PID namespace of NODE expects to view
        // all of the processes on the host running the kubelet.
        NODE = 2;

    I8.6

    Reading a sandbox config field by field, and finding what each one became

    Why it matters

    Several classic Kubernetes mysteries — why every pod has the same nameserver regardless of its base image, why an external DNS lookup takes five failed queries first, where kubectl logs reads from — are not Kubernetes behaviour at all. They are fields in the sandbox config, and each one leaves a trace on disk you can go and look at.

    The concept

    The sandbox config is where the kubelet tells the runtime everything about the pod that is not a container. Four fields are worth following all the way to their consequences.

    dns_config becomes a resolv.conf that the runtime writes, in its own directory, and bind-mounts over whatever the image had. This is the answer to "why does every pod resolve through the cluster DNS service even though my base image never heard of it" — nothing in the image is consulted. It is also where options ndots:5 comes from, and B10.4 already showed you what that costs: a name with fewer than five dots is tried against every search-domain suffix first, so api.example.com becomes four failed queries and then a successful one.

    log_directory, combined with each container's log_path, decides where the container's stdout and stderr are written. The kubelet chooses the value; the runtime creates the file. This is the whole reason kubectl logs works, and I8.13 dissects the format.

    port_mappings — the hostPort feature — becomes iptables DNAT rules installed by the CNI portmap plugin, which is B9.16 done by machine.

    linux.cgroup_parent is the directory (or systemd slice) under which the runtime places the pod's cgroups. It is how the kubelet keeps a QoS hierarchy, and it is one half of the cgroup-driver disagreement in I8.14.

    I8.7

    RunPodSandbox triggers CNI ADD — the seam where I9 begins

    Why it matters

    "Pod stuck in ContainerCreating, no logs, error mentions the network" is one of the most common failure shapes in Kubernetes, and it has one structural explanation: networking is attached to the sandbox, and the sandbox is created before any application container exists. There is nothing to log because nothing was started.

    The concept

    Inside RunPodSandbox, the runtime creates a network namespace, pins it as a file, and invokes the CNI plugin chain with ADD — handing it that namespace path and expecting an IP back. Only if that succeeds does it start the pause container. The IP belongs to the sandbox's network namespace, not to any container, which is why a pod keeps its address across container restarts and loses it when the sandbox is recreated.

    Everything downstream follows from the ordering. If CNI cannot run, the sandbox never becomes ready; if the sandbox never becomes ready, no container is ever created; if no container is created, kubectl logs has nothing to read and kubectl describe is your only evidence. It also explains why the reverse order matters at teardown (I8.11): the CNI DEL that releases the IP is bound to sandbox teardown, so skipping it leaks addresses.

    containerd exposes its CNI state in two places worth knowing: the NetworkReady condition from Status(), and a lastCNILoadStatus string that says why the config failed to load. Between them they name the fault precisely.

    The proto says nothing about CNI — that is I9's specification. What it does say is whose IP it is, and the answer explains why the address survives container restarts:

    The call sequence

    I8.8

    Four verbs: pull, runp, create, start

    Why it matters

    One pod becomes four calls, always in the same order. Memorising them is not trivia — it is a diagnostic tool. Each call has a different set of things that can go wrong, so knowing which call failed tells you which third of the problem space to search, before you have read a single log line.

    The concept

    The sequence is PullImage → RunPodSandbox → CreateContainer → StartContainer, followed by ListContainers and ContainerStatus polling for as long as the pod lives.

    But it is not a script. The kubelet is a reconciler — B13's loop, and W1.19's syncLoop — that compares the pod spec it has been given against what the runtime reports and issues whichever calls close the gap. That is why the same sequence handles a container that crashed (create and start it again), a sandbox that disappeared (make a new one, and accept a new IP), and a pod that has not changed at all (issue nothing). The order is a consequence of dependencies, not of a program counter.

    The dependency chain reads as a fault-isolation table:

    What existsWhat failedWhere to look
    nothing at allRunPodSandboxCNI, or the sandbox image (I8.7, I8.4)
    a sandbox, no containerPullImage or CreateContainer registry and credentials (I5), or the container config

    I8.9

    ExecSync and Exec: two paths, and the one that leaves gRPC

    Why it matters

    kubectl exec can fail with an error naming a host and port that appear nowhere in your kubeconfig. Liveness probes can wedge a node's runtime. Both are explained by one design decision: interactive exec does not travel over the kubelet's gRPC connection at all.

    The concept

    gRPC is a poor fit for an interactive terminal. A terminal session is long-lived, bidirectional, and carries out-of-band events like window resizes; gRPC streams can do it, but badly, and the kubelet would become a proxy for every byte. So CRI splits the problem in two.

    ExecSync is the simple case: run a command, wait, return stdout, stderr and the exit code in one response. This is the probe path — every exec liveness and readiness probe in your cluster is an ExecSync call. It is synchronous by definition, which is why a heavyweight probe with a generous timeout can occupy runtime resources and, at scale, make a node sluggish in a way that names no workload.

    Exec is the streaming case, and it does something unusual: it does not stream. It returns a URL. The runtime hosts a small HTTP server — the streaming server — generates a single-use URL for this exec session, and returns it. The API server is then redirected to that URL and the terminal traffic flows directly between them. Attach and PortForward work the same way.

    Two consequences follow. First, the streaming endpoint is a separate network path with separate reachability and authentication concerns from the rest of the API — which is why kubectl exec can fail while everything else works, with an error naming an address you have never configured. Second, PortForward is a tunnel into the sandbox's network namespace: it works for a pod with no Service at all, and it therefore tells you exactly nothing about whether Service routing is healthy.

    The two calls, one line apart in the proto, and the word that distinguishes them:

    // ExecSync runs a command in a container synchronously.
    rpc ExecSync(ExecSyncRequest) returns (ExecSyncResponse) {}
    // Exec prepares a streaming endpoint to execute a command in the container.
    rpc Exec(ExecRequest) returns (ExecResponse) {}

    I8.10

    UpdateContainerResources, and what in-place pod resize really does

    Why it matters

    In-place pod resize went GA in Kubernetes v1.35, the version this track targets. Underneath the feature gate and the API machinery there is one CRI call, and what it does is write into the container's cgroup v2 files — which is B7's lab, driven by an API. Watching it happen makes the feature's limits obvious rather than mysterious.

    The concept

    UpdateContainerResources changes a running container's limits without recreating it. The runtime writes the new values into memory.max, cpu.max, cpu.weight and friends, and the kernel applies them to a process that never noticed.

    The asymmetry between growing and shrinking is not a Kubernetes quirk; it is how cgroups work. Growing a limit is always safe — the cgroup's current usage is already below the new ceiling by definition. Shrinking a memory limit below current usage is a kill. The kernel is asked to make usage fit under a smaller number; it reclaims what it can, and if it cannot reclaim enough, it invokes the OOM killer inside that cgroup. CPU has no equivalent hazard — a smaller quota just throttles.

    Kubernetes' own contract acknowledges this. Since v1.33 the CRI contract specifies that runtimes must not deliberately restart a container to apply a resize, and must return an error if a restart would be required. Note what that does and does not promise: the runtime will not restart your container. The kernel may still kill it, and the call will have returned success first.

    There is one more thing worth checking here, because I3.8 found the opposite for bare runc: does anything on disk record the change?

    The call's contract, verbatim — note "transactionally", which is the runtime's promise, not the kernel's:

    // UpdateContainerResources updates ContainerConfig of the container synchronously.
    // If runtime fails to transactionally update the requested resources, an error is returned.
    Kubernetes cri-api, runtime.v1 — pkg/apis/runtime/v1/api.proto

    • The bundle's config.json is stale after an update. Read the value from crictl inspect, not from the file on disk — a habit worth forming, because the file is the more obvious place to look and it is wrong.

    I8.11

    Teardown, in reverse, and what happens when you get it wrong

    Why it matters

    Deletion runs creation backwards, and the rule to keep is one sentence: the sandbox is created first and destroyed last. Getting it wrong leaks IP addresses, which is a node-level outage that arrives hours later as "this node refuses new pods" with no obvious cause.

    The concept

    The correct order is: stop each container, remove each container, stop the sandbox, remove the sandbox. The reason is ownership. The sandbox owns the network namespace, so tearing it down while containers are still joined to it would strand them in a namespace that is going away. And the CNI DEL — the call that returns the pod's IP to the IPAM pool — is bound to sandbox teardown, so the sandbox must outlive everything that used its network.

    This is also why a terminating pod's terminationGracePeriodSeconds is spent on containers: the grace period is the timeout on StopContainer, and the sandbox is removed only after every container has gone.

    The proto is unusually explicit about the idempotency requirements here, and about who forcibly terminates what.

    Both teardown calls, verbatim — note that both are required to be idempotent, and that RemovePodSandbox is permitted to forcibly kill containers:

    // RemovePodSandbox removes the sandbox. If there are any running containers
    // in the sandbox, they must be forcibly terminated and removed.
    // This call is idempotent, and must not return an error if the sandbox has
    // already been removed.
    rpc RemovePodSandbox(RemovePodSandboxRequest) returns (RemovePodSandboxResponse) {}
    Kubernetes cri-api, runtime.v1 — pkg/apis/runtime/v1/api.proto
    Lab

  \"ab4b4d921a5df79db10787b73e9415dd68e197dcea76b7b2b8a6d6ffbe955aac\"

    Gotchas
    • Leaked IPAM reservations are a delayed, node-level outage. Each skipped CNI DEL holds one address in the host-local IPAM store forever. Nothing complains until the subnet is full, at which point every new pod on that node fails to get an IP and the pods holding the addresses no longer exist. This is I9's third fault, and it is real.
    • The grace period is spent on containers, not on the sandbox. A pod that takes forever to terminate is a container ignoring SIGTERM. The sandbox teardown is fast.
    • Both teardown calls must be idempotent, so a "successful" delete proves nothing. Calling StopPodSandbox on an already-stopped sandbox returns success by design. Verify with crictl pods, not with the exit status.

    I8.12

    crictl as a reflex, and the things kubectl cannot show you

    Why it matters

    kubectl shows you the cluster's intent and the kubelet's summary of reality. crictl shows you the node's reality, with no API server in the path. When the API server is unreachable, when a node is NotReady, or when a pod's status summarises something that has already happened three times, crictl still answers. That is why it belongs in your CKA toolkit and not merely in your vocabulary.

    The concept

    The verb set is small and worth having in muscle memory: pods, ps -a, inspect, inspectp, logs, exec, imagefsinfo, stats. Most map one-to-one onto CRI calls, which is why the output shapes look like protobuf messages rather than like kubectl.

    Two things crictl sees that kubectl cannot. First, containers the kubelet has already replaced — crictl ps -a lists the corpses, with their exit codes, their timestamps and their log files intact, after kubectl has moved on to describing the replacement. Second, objects with no API representation at all: a sandbox created outside Kubernetes, or one left behind by a kubelet that died mid-teardown.

    The trap is the reverse direction. crictl talks to a runtime. It knows nothing about scheduling, admission, controllers, or the objects that caused what you are looking at. "Why is there no pod here" is never a crictl question.

    One mechanism is worth understanding properly, because it explains a filename, a column, and an error message all at once. CRI reserves a unique name per container built from <container>_<pod>_<namespace>_<uid>_<attempt>. The attempt field is what a restart increments — and it is the same number that appears in the log filename 0.log, 1.log, and the same number kubectl shows you as RESTARTS. One mechanism, three faces.

    I8.13

    Decoding a raw CRI log file

    Why it matters

    The workload calls write(2) on file descriptor 1. It has no idea it is being logged, no idea what a timestamp is, and no idea a pod exists. Everything kubectl logs shows you was invented on the way out — and the format it was invented in is four fields you can read with awk on a node where kubectl is unavailable.

    The concept

    Each line in a CRI log file is: an RFC 3339 timestamp, the stream name (stdout or stderr), a P/F tag, and the line itself, space-separated.

    The timestamp is the runtime's, taken when it read the bytes off the pipe — not the application's. If your app also prints its own timestamps, you will see two, and they will disagree by the pipe latency. The stream field is why kubectl logs can interleave stdout and stderr correctly even though the container wrote to two separate pipes.

    The P/F tag is the interesting one. P means partial, F means full — the end of a logical line. A single application line longer than the runtime's maximum arrives as several P records followed by one F, and it is the consumer's job to reassemble them. This exists because the runtime must bound its own memory: it cannot buffer an unbounded line before writing.

    Knowing who writes this format explains one hard rule: a container that logs to a file inside itself effectively has no logs. Nothing is reading that file. The pipeline starts at fd 1 and fd 2, and anything that does not go there does not exist as far as Kubernetes is concerned.

    The container half of the log path, with the spec's own example — Instance# is the attempt number, which is the whole story of 0.log and 1.log:

    // Path relative to PodSandboxConfig.LogDirectory for container to store
    // the log (STDOUT and STDERR) on the host.
    // E.g.,
    //     PodSandboxConfig.LogDirectory = `/var/log/pods/<NAMESPACE>_<NAME>_<UID>/`
    //     ContainerConfig.LogPath = `containerName/Instance#.log`
    Kubernetes cri-api, runtime.v1 — pkg/apis/runtime/v1/api.proto
    Lab
    1. Run a container that prints a short stdout line, a short stderr line, and one 20,000-byte line, then read the raw file.

    Gotchas

    • The timestamp is the runtime's, in the node's timezone. Correlating it with application-emitted timestamps means accounting for both an offset and a small delay.
    • Logs to a file inside the container do not exist. No amount of Kubernetes configuration recovers them; the application must write to stdout or stderr, or you need a sidecar that reads the file and does.
    • /var/log/containers/ is the kubelet's, /var/log/pods/ is the runtime's. When only the symlinks are stale or missing, suspect the kubelet, not the runtime.

    I8.14

    The CRI config: sandbox image, runtime handlers, and the cgroup driver

    Why it matters

    Three settings in the runtime's CRI configuration cause a disproportionate share of real node failures. One of them — the cgroup driver — is not a preference at all. It is a claim about who owns the cgroup tree, and when the kubelet and the runtime disagree, both succeed at their own half and the node quietly makes eviction decisions about a tree nothing is charged to.

    The concept

    Start with an honest observation: this box has no /etc/containerd/config.toml at all, and CRI works perfectly. That was I7.8's finding and it holds here — the file is optional, and the live values come from the API. Read the config from the runtime, not from a file that may not exist.

    The sandbox image is declared as a pinned image, which is one declaration doing two jobs: it names the pause image, and pinning is what stops image garbage collection from evicting the one image without which no pod can start.

    The runtimes map is a set of named handlers. Each key becomes a value you can name in a Kubernetes RuntimeClass, which is how a cluster offers gVisor or Kata alongside runc on the same node.

    And the cgroup driver. With SystemdCgroup = false (the upstream default) the runtime creates cgroup directories itself, and a container's cgroup path is a plain filesystem path.     Quiz

    1. State the CRI contract in one sentence, then name one operational consequence of each clause.
      Answer

      A gRPC service, on a unix socket, defined by runtime.v1. gRPC: the contract is a generated .proto, which is why the two sides upgrade independently. Unix socket: the trust boundary is the file mode, so write access is root on the node with no audit trail. runtime.v1: a stable versioned namespace, which is what made removing dockershim survivable.

    2. What did the dockershim removal actually break, and name two things people believed it broke that it did not.
      Answer

      It broke nodes whose container runtime was the Docker daemon; the fix was almost always pointing the kubelet at containerd, which Docker had been using underneath anyway. It did not break images built with Docker (they are OCI images) and it did not affect Docker on a developer machine.

    3. Why must a pod have a container that does nothing?
      Answer

      Because a namespace is destroyed when the last process in it exits unless something pins it, and the pod's namespaces must exist before the first app container starts, survive app containers coming and going, and die last. On this box /pause was one thread, 624 kB resident, blocked in __do_sys_pause.

    4. Which of the pod's namespaces does the pause container actually hold on containerd, and which one does it not?
      Answer

      It holds IPC and UTS (and PID, when sharing is on) via /proc/<pid>/ns/. It does not hold the network namespace: that is created and bind-mount pinned at /var/run/netns/cni-<uuid> before pause exists, because CNI ADD has to run against it first. The sandbox's own config joins it by path.

    5. Where does the switch for shareProcessNamespace live in the CRI request, and what happens if you put it in the other place?
      Answer

      On the container config's linux.security_context.namespace_options.pid. Setting it on the sandbox config alone has no effect on app containers and produces no warning. With POD the app's PID 1 is the pause process; with CONTAINER it is the app itself.

    6. A pod is stuck in ContainerCreating, the event mentions the network, and kubectl logs says the container is not found. Why are there no logs?
      Answer

      Because CNI ADD happens inside RunPodSandbox, before any container is created. The failure is at sandbox creation, so no container was ever started and there is nothing to log. crictl ps -a is empty for that pod.

    7. You restored a deleted CNI config file with mv and the node is still NetworkReady=false ten minutes later. What happened, and what fixes it?
      Answer

      containerd's config watcher fired on the rename out and reloaded to nothing; the rename in produced no event, and neither did touch. A content write does — cp the file's contents into place, or restart containerd. Check crictl info | jq -r .lastCNILoadStatus.

    8. Name the four calls for one pod, and say what each failure point implies.
      Answer

      PullImage → RunPodSandbox → CreateContainer → StartContainer. Nothing at all means the sandbox failed: CNI or the sandbox image. A sandbox with no container means the image or the container config. A container that starts and exits means the workload.

    9. Which exec path does a liveness probe use, and how would you prove which one a given command took?
      Answer

      ExecSync. Prove it by watching connections to the runtime's streaming server: the streaming Exec opens a TCP connection to 127.0.0.1:<stream port>, ExecSync opens none. Note that crictl exec defaults to streaming; -s selects ExecSync.

    10. You call UpdateContainerResources to shrink a memory limit and it returns success. Is the container safe?
      Answer

      No. If the new limit is below current usage, the kernel reclaims what it can and OOM-kills what it cannot — measured here as exit 137, reason OOMKilled, two seconds after a successful call. The v1.33+ contract says the runtime must not restart the container to resize; it says nothing about the kernel.

    11. Decode this log record: 2026-07-30T14:00:46.508944247+06:00 stdout P xxxx…. Whose timestamp is it, and what does P mean?
      Answer

      The runtime's, taken when it read the bytes off the pipe, in the node's local offset. P is a partial record: the application line exceeded maxContainerLogLineSize (16384 here) and continues in the next record, ending with an F. A consumer must reassemble them.

    12. Why does crictl ps sometimes print unknown in the POD column?
      Answer

      Because the pod name comes from io.kubernetes.pod.* labels the kubelet sets on each container, not from anything in CRI's message structure. A container created by hand has empty labels and no pod name.

    13. What is the relationship between metadata.attempt, the file 1.log, and the RESTARTS column?
      Answer

      They are the same number. CRI reserves the name <container>_<pod>_<ns>_<uid>_<attempt>, so a restart must increment attempt; that value becomes the log filename and is what kubectl reports as the restart count.

    14. The kubelet says systemd and the runtime says cgroupfs. What is the symptom, and what is the evidence?
      Answer

      No error at all — both halves succeed. Pods run, limits are enforced, and the kubelet's accounting reads a tree nothing is charged to, so evictions and restarts happen for no visible reason. The evidence is two trees on disk: /sys/fs/cgroup/kubepods.slice/… exists while /sys/fs/cgroup/kubepods/… does not, or the reverse.

    15. crictl ps fails with dial unix /run/containerd/containerd.sock: connect: no such file or directory. Name the two possible causes and the one command that separates them.
      Answer
