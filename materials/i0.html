    I0 — Your build box

    This track takes apart software that other people wrote: containerd, runc, the CNI plugins, a registry. Taking software apart means stopping it mid-flight, editing its configuration to something wrong on purpose, and occasionally leaving it in a state where nothing starts. So the first module builds a second machine for that — buildbox — and then installs every component of the container stack on it at a version you chose and wrote down.

    The version part is not bookkeeping. For the rest of this track, "my output doesn't match the lesson's" is nearly always a version answer, and the fastest way to settle it is a table you can print in one command. That table is this module's mini project.

    Checkpoints8 Hours~2 Prerequisitesthe beginner track, or equivalent
    • Stand up and snapshot a second throwaway VM, and say why it is neither the beginner sandbox nor a cluster node.
    • Create the Python environment this track's programs run in, and explain the error you get without it.
    • Bootstrap the two beginner-track artefacts — a bash container runtime and a hand-built pod network — and confirm both actually run.
    • Install containerd, runc and the CNI plugins from the projects' own releases rather than from apt, and say why that matters on Ubuntu 24.04.
    • Draw the map of which binary owns which layer, from the kubelet down to the workload process.
    • Read an OCI specification: RFC 2119 keywords, how the documents are laid out, and how to find the sentence that settles an argument.
    • Print the whole toolchain's versions and config paths in one command, and fail loudly when something is missing.

    The Beginner track, or equivalent fluency with namespaces, cgroups v2, overlayfs and Linux networking — this track never re-teaches those, it only extends them. If you skipped it, you can still start here: the two artefacts the track argues about ship in labs/intermediate/seed/ and I0.3 installs them for you.

    On your host you need room for a second VM: 4 vCPU, 8 GB RAM and 40 GB of disk while it is running. Unlike the beginner sandbox, this machine needs working internet — pulling real images from real registries is the subject matter of I4–I6, not a setup step.

    The box

    I0.1

    Launch buildbox, and know why it is a third machine

    Why it matters

    You almost certainly already have virtual machines from the other two tracks — a sandbox from B0.4, and possibly a three-node cluster from W0.5. It is tempting to reuse one. Doing so is the single most likely way to lose an afternoon in this track, and the reasons are worth stating before you type anything, because each of them is really a fact about what containers do to a machine.

    The concept

    Three reasons, in order of how badly each one bites.

    • Not the beginner sandbox. That machine is 2 vCPU / 4 GB / 20 GB, which is fine for unshare-and-cgroup experiments and not fine for pulling and unpacking real images: a handful of ordinary base images plus a local registry plus a BuildKit cache will fill 20 GB, and image builds are the one thing in this track that genuinely wants cores. Its clean snapshot is also a beginner-track asset you may still want intact.
    • Not the CKA lab's cp/node01/node02. These labs stop containerd, rewrite its configuration, restart it, point crictl at it, and in I9 replace the CNI configuration on disk. Every one of those actions breaks a running Kubernetes node — that node's kubelet is talking to the same containerd through the same socket. The advanced track depends on that cluster staying up.
    • It needs internet, and the beginner sandbox deliberately did not. B0 built a machine that could work entirely offline, because a beginner-track lab that fails because DNS is down teaches nothing. Here, the network is the subject: an image is something you fetch from a registry over HTTPS, and I5 spends a whole module doing that by hand with curl.

    One more habit carried straight from B0: name the Ubuntu release by number. multipass launch lts is a moving alias — as of July 2026 it resolves to Ubuntu 26.04, not 24.04 — and the failure is silent, because the VM boots and every command exists and only the details disagree with the pasted output in these lessons.

    The snapshot reflex matters more here than it did in the beginner track, not less. There, you broke things you had built yourself and could rebuild. Here you will break containerd's configuration, and the difference between a five-second restore and an hour of reading someone else's TOML is entirely down to whether you took the snapshot first.

    launch→install toolchain→snapshot clean→wreck freely→restore
    Lab

    multipass list --snapshots shows blank on buildbox; inside the VM lsb_release -cs prints noble, nproc prints 4, and stat -fc %T /sys/fs/cgroup prints cgroup2fs. If you kept the beginner track's snapshot.sh/restore.sh from B0.9, they already take an instance name — snapshot.sh buildbox works today with no edits.

    Gotchas

    If multipass launch fails for lack of memory, remember that the beginner sandbox and the three CKA VMs are probably still running and holding their own allocations. multipass stop sandbox cp node01 node02 frees them; nothing in this track needs them running at the same time as buildbox.

    A freshly launched VM keeps working for a minute or two after it prints Launched — cloud-init is still finishing first-boot setup and holds apt's lock while it does. If the next lesson's apt complains it cannot get a lock, wait it out with cloud-init status --wait rather than killing the lock holder.

    You will take a second snapshot at the end of this module, once the toolchain is installed. Keep both: blank is the floor you fall back to if an install goes wrong, and clean (I0.8) is the one you will actually use between modules.

    Everything you install on this box over the next hour is what the advanced track's W0.6 — install containerd + kubeadm/kubelet/kubectl by hand installs on every node of a cluster, minus the Kubernetes parts. A node is a machine with exactly this stack on it plus a kubelet; kubeadm adds no container machinery of its own.

    The snapshot habit is the same one W0.8 asks for on the cluster VMs, and for the same reason: the fastest fix for a control plane you broke while learning is not a repair, it is a restore.

    Docs

    multipass help launch, multipass help snapshot, multipass help restore. Inside the VM, man 1 stat (note that -f asks about the filesystem) and man 7 cgroups, which is the primary source you will be arguing with in I1.

    I0.2

    The Python environment, and the error you get without it

    Why it matters

    Several modules of this track ask you to write a program rather than run one: an image parser in I4, a registry client in I5, a toy CRI server in I8, a CNI plugin in I9. Those are written in Python 3, and on Ubuntu 24.04 installing a Python library the obvious way fails with an error message that looks like a bug and is not. Meeting it deliberately now, with an explanation, costs two minutes; meeting it in the middle of I5 costs your concentration.

    The concept

    A virtual environment (a "venv") is a directory containing its own python3, its own pip, and its own site-packages folder. Activating one puts that directory first on your PATH, so python3 means the copy in the venv and every library you install lands inside it. Deleting the directory uninstalls everything you ever put in it. Nothing is global; nothing is shared.

    Ubuntu insists on this, and the mechanism has a name. PEP 668 lets a distribution mark its Python installation as externally managed — meaning "apt owns the packages here, do not let pip write into them". The marker is a real file you can look at:

    cat /usr/lib/python3.12/EXTERNALLY-MANAGED
    [externally-managed]
Error=To install Python packages system-wide, try apt install
 python3-xyz, where xyz is the package you are trying to
 install. ...

    The reason is not tidiness. On Ubuntu, real system tools are written in Python — cloud-init, parts of the installer, apt's own helpers — and they import libraries that apt installed at specific versions. A pip install that upgrades one of those libraries system-wide can leave the machine unable to finish a boot or complete a package operation. The escape hatch --break-system-packages exists and is named honestly. Use the venv.

    One thing a venv does not do: it does not isolate you from the kernel, from files, or from anything else. It is a PATH trick and a directory, not a container. That distinction is worth holding onto for the whole track — you are about to spend fourteen modules on the machinery that does provide real isolation, and "virtual environment" is a name that invites the confusion.

    Lab
    1. Install the venv module and — so you can see the failure — pip itself, which the cloud image does not ship. 
      sudo apt update
sudo apt install -y python3-venv python3-pip jq tree
    2. Reproduce the error on purpose. Do not skip this: the point is to recognise it instantly the next time it appears, in someone else's terminal, in a bug report. 
      pip install requests
      error: externally-managed-environment

    3. Create the track's environment. Every Python lab from here on assumes this exact path, so that a lesson can say "activate the venv" without repeating itself. 
      python3 -m venv ~/.venv-intermediate

    4. Confirm the activation actually changed which interpreter you are running, then install something into it. 
      which python3

      echo 'source ~/.venv-intermediate/bin/activate' >> ~/.bashrc
    Verify

    Open a fresh shell (exit, then multipass shell buildbox). The prompt is prefixed with (.venv-intermediate), which python3 points inside your home directory, and python3 -c 'import requests' prints nothing and exits 0.

    Gotchas

    sudo python3 … does not use your venv. sudo resets the environment, so the root shell gets /usr/bin/python3 and none of your installed libraries — which produces a baffling ModuleNotFoundError for a module you can see is installed. When a lab genuinely needs both root and the venv, spell out the interpreter: sudo ~/.venv-intermediate/bin/python3 script.py.

    Do not be tempted by --break-system-packages "just this once on a throwaway VM". It works, and then two modules later you restore a snapshot, forget you used it, and cannot reproduce your own result. The venv costs one line in .bashrc.

    No direct counterpart — this is toolchain hygiene, not a Kubernetes mechanism. It earns its place because the same instinct shows up one level up: a container image exists largely so that an application's dependencies are pinned somewhere that cannot collide with the host's.

    Keep the comparison in mind when you reach W3.16 — requests vs limits and, later here, I4's layer model: a venv isolates a search path, an image isolates a filesystem, and a container isolates kernel resources. Three different strengths of the same word.

    Docs

    PEP 668 for the marker file and why distributions wanted it; man 1 python3; python3 -m venv --help. The Python packaging guide's "Installing packages using pip and virtual environments" is the canonical how-to.

    I0.3

    Seed the two artefacts this whole track argues about

    Why it matters

    This track's thesis is that the container ecosystem added remarkably little mechanism — it added contracts. That claim is only interesting if you are holding the mechanism in your hands while someone shows you the contract. The two scripts you install now are that mechanism: a container runtime in about eighty lines of bash, and a pod network in about forty. Every module from here compares a real component against one of them.

    The concept

    Look at what you are holding before anyone calls it primitive.

    minibox.sh — the assembled form of what B14.1–B14.4 build one layer at a time — mounts an overlay filesystem (a stack of read-only directories with one writable layer on top, exactly the shape a container image has), unshares five namespaces so the process gets its own mounts, process list, hostname, IPC and network, writes CPU, memory and PID limits into a cgroup, pivot_roots so the host filesystem becomes unreachable, drops four capabilities, and execs your command. Then it wires a veth pair into a bridge on the host, gives the inside end an address and a default route, and adds a NAT rule so it can reach the internet.

    That is a container runtime. It is not a toy version of one; it is one. What it lacks is not machinery but agreement: there is no file another program could read to learn what this container is, no name by which a second tool could find it, no defined way to ask it to stop, and no way to hand the same description to a different implementation and get the same container. It has no bugs a specification would have caught, because it has no specification.

    net-up.sh — the beginner track's B9.19 mini project — is the same story for networking: it creates N network namespaces on one bridge, allocates each an address, routes between them, and masquerades their egress. That is a pod network: IP address management, the wiring, and the egress path. What it lacks is a calling convention, which is precisely and only what CNI adds.

    One correction ships with the seed copy, and it is worth reading because it is a genuine ordering bug that the specification-free version invites. unshare(2) and pivot_root(2) both require CAP_SYS_ADMIN. A runtime that drops that capability before it isolates the process fails with EPERM having isolated nothing. So the rule is isolate, then disarm — and because pivot_root has by then made the host's /usr unreachable, the seed script has to copy capsh and its shared libraries into the rootfs to be able to drop anything at all. runc needs no such trick: it is a single process that unshares, pivots, drops and execs, so its own code is still in memory at the moment it gives up privilege. Keep that in mind; I3 is that lesson.

    Lab
    1. Copy both scripts onto the box. They live in this site's repository under labs/intermediate/seed/; from your host, multipass transfer is the direct route (if your Multipass is a snap and cannot read your temp directory, pipe them instead, as the second line shows). 
      multipass transfer labs/intermediate/seed/minibox.sh buildbox:/home/ubuntu/minibox.sh
multipass exec buildbox -- bash -c 'cat > ~/net-up.sh' < labs/intermediate/seed/net-up.sh
multipass exec buildbox -- chmod +x /home/ubuntu/minibox.sh /home/ubuntu/net-up.sh
    2. Inside the VM, install the two packages the scripts need. busybox-static is a single binary containing several hundred small Unix tools — it is what makes a 5 MB root filesystem possible without a package manager. 
      sudo apt install -y busybox-static libcap2-bin iptables
    3. Build the root filesystem. This is B14.1 as a function: it creates the overlay's lower directories, installs busybox's applets as symlinks, writes a three-line /etc, and copies capsh in. 
      sudo ~/minibox.sh --init
      rootfs ready: 271 applets in /srv/minibox/lower-base/bin
    4. Run something inside it. Read the output line by line — every one of them is a namespace or a cgroup doing its job. 
      sudo ~/minibox.sh /bin/sh -c 'id; hostname; ls /; ip -br addr; ping -c1 -W3 10.88.0.1'
      uid=0(root) gid=0 groups=0

      sudo ~/minibox.sh /bin/sh -c '/bin/capsh --print | head -2; ping -c1 -W3 8.8.8.8 | tail -2'
      Current: =ep cap_net_admin,cap_sys_module,cap_sys_admin,cap_sys_time-ep

    6. Now the network script. up 2 creates two namespaces on one bridge; give it a second before testing, because the first packet has to wait for ARP. 
      sudo ~/net-up.sh up 2
      bridge cni0 = 10.20.0.1/24, egress via ens3
  pod1 = 10.20.0.2
  pod2 = 10.20.0.3
      sudo ip netns exec pod1 ping -c2 -W2 10.20.0.3 | tail -2
sudo ip netns exec pod1 ping -c1 -W3 8.8.8.8 | tail -2
      2 packets transmitted, 2 received, 0% packet loss
1 packets transmitted, 1 received, 0% packet loss
    7. Tear both down. Leaving them up costs you a bridge and a NAT rule that will confuse a later module. 
      sudo ~/net-up.sh down
sudo ~/minibox.sh --clean
    Verify

    Both scripts ran without an error and both cleaned up: ip netns list is empty, ip link show cni0 and ip link show mb0 both report does not exist, and ls /srv/minibox reports no such directory. You should be able to say, out loud, which line of minibox.sh creates the isolation and which creates the filesystem.

    Gotchas

    Both scripts carry a wrong-box guard: they refuse to run if /etc/kubernetes exists. That is not paranoia — minibox.sh writes a MASQUERADE rule and net-up.sh flips net.ipv4.ip_forward, and doing either on a cluster node produces a networking failure that is genuinely hard to trace back to its cause. If the guard fires, you are on the wrong machine; do not edit it out.

    If minibox.sh reports unshare failed: Operation not permitted while you are root, you are running a copy with the pre-correction ordering (capabilities dropped before unshare). Re-copy from labs/intermediate/seed/. I1.4 explains the other cause of that message, which applies when you are not root: Ubuntu 24.04 gates unprivileged user namespaces behind AppArmor.

    --clean deliberately leaves the NAT rule for 10.88.0.0/24 in place and says so. Removing a MASQUERADE rule you did not add is a good way to break something else on a shared machine; on buildbox you can flush it yourself with sudo iptables -t nat -F POSTROUTING.

    minibox.sh is a pod with one container in it, and net-up.sh is that pod's network. Put them beside W1.20 — understand CRI: kubelet → containerd → shim → runc and the chain becomes concrete: everything in that lesson exists to turn a YAML object into the sequence of syscalls your two scripts make by hand.

    The clearest single mapping is W1.21 — meet the pause container. A pod's namespaces have to be created and held open by something before any application container joins them; in minibox.sh that something is the backgrounded unshare whose PID the script wires the veth into. Kubernetes calls the equivalent the sandbox, and I8 is where you create one directly.

    Docs

    Read the two scripts themselves — they are commented line by line and are the shortest primary source in this track. Then man 7 namespaces, man 2 pivot_root, man 8 ip-netns, man 1 capsh, and man 5 overlayfs (or the kernel's Documentation/filesystems/overlayfs.rst) for the lowerdir/upperdir/workdir triple.
