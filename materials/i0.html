    I0 — Your build box

    This track takes apart software that other people wrote: containerd, runc, the CNI plugins, a registry. Taking software apart means stopping it mid-flight, editing its configuration to something wrong on purpose, and occasionally leaving it in a state where nothing starts. So the first module builds a second machine for that — buildbox — and then installs every component of the container stack on it at a version you chose and wrote down.

    The version part is not bookkeeping. For the rest of this track, "my output doesn't match the lesson's" is nearly always a version answer, and the fastest way to settle it is a table you can print in one command. That table is this module's mini project.

    Checkpoints8 Hours~2 Prerequisitesthe beginner track, or equivalent
    • Stand up and snapshot a second throwaway VM, and say why it is neither the beginner sandbox nor a cluster node.
    • Create the Python environment this track's programs run in, and explain the error you get without it.
    • Bootstrap the two beginner-track artefacts — a bash container runtime and a hand-built pod network — and confirm both actually run.
    • Install containerd, runc and the CNI plugins from the projects' own releases rather than from apt, and say why that matters on Ubuntu 24.04.
    • Draw the map of which binary owns which layer, from the kubelet down to the workload process.
    • Read an OCI specification: RFC 2119 keywords, how the documents are laid out, and how to find the sentence that settles an argument.
    • Print the whole toolchain's versions and config paths in one command, and fail loudly when something is missing.

    The Beginner track, or equivalent fluency with namespaces, cgroups v2, overlayfs and Linux networking — this track never re-teaches those, it only extends them. If you skipped it, you can still start here: the two artefacts the track argues about ship in labs/intermediate/seed/ and I0.3 installs them for you.

    On your host you need room for a second VM: 4 vCPU, 8 GB RAM and 40 GB of disk while it is running. Unlike the beginner sandbox, this machine needs working internet — pulling real images from real registries is the subject matter of I4–I6, not a setup step.

    The box

    I0.1

    Launch buildbox, and know why it is a third machine

    Why it matters

    You almost certainly already have virtual machines from the other two tracks — a sandbox from B0.4, and possibly a three-node cluster from W0.5. It is tempting to reuse one. Doing so is the single most likely way to lose an afternoon in this track, and the reasons are worth stating before you type anything, because each of them is really a fact about what containers do to a machine.

    The concept

    Three reasons, in order of how badly each one bites.

    • Not the beginner sandbox. That machine is 2 vCPU / 4 GB / 20 GB, which is fine for unshare-and-cgroup experiments and not fine for pulling and unpacking real images: a handful of ordinary base images plus a local registry plus a BuildKit cache will fill 20 GB, and image builds are the one thing in this track that genuinely wants cores. Its clean snapshot is also a beginner-track asset you may still want intact.
    • Not the CKA lab's cp/node01/node02. These labs stop containerd, rewrite its configuration, restart it, point crictl at it, and in I9 replace the CNI configuration on disk. Every one of those actions breaks a running Kubernetes node — that node's kubelet is talking to the same containerd through the same socket. The advanced track depends on that cluster staying up.
    • It needs internet, and the beginner sandbox deliberately did not. B0 built a machine that could work entirely offline, because a beginner-track lab that fails because DNS is down teaches nothing. Here, the network is the subject: an image is something you fetch from a registry over HTTPS, and I5 spends a whole module doing that by hand with curl.

    One more habit carried straight from B0: name the Ubuntu release by number. multipass launch lts is a moving alias — as of July 2026 it resolves to Ubuntu 26.04, not 24.04 — and the failure is silent, because the VM boots and every command exists and only the details disagree with the pasted output in these lessons.

    The snapshot reflex matters more here than it did in the beginner track, not less. There, you broke things you had built yourself and could rebuild. Here you will break containerd's configuration, and the difference between a five-second restore and an hour of reading someone else's TOML is entirely down to whether you took the snapshot first.

    launch→install toolchain→snapshot clean→wreck freely→restore

    Gotchas

    If multipass launch fails for lack of memory, remember that the beginner sandbox and the three CKA VMs are probably still running and holding their own allocations. multipass stop sandbox cp node01 node02 frees them; nothing in this track needs them running at the same time as buildbox.

    A freshly launched VM keeps working for a minute or two after it prints Launched — cloud-init is still finishing first-boot setup and holds apt's lock while it does. If the next lesson's apt complains it cannot get a lock, wait it out with cloud-init status --wait rather than killing the lock holder.

    You will take a second snapshot at the end of this module, once the toolchain is installed. Keep both: blank is the floor you fall back to if an install goes wrong, and clean (I0.8) is the one you will actually use between modules.

    Everything you install on this box over the next hour is what the advanced track's W0.6 — install containerd + kubeadm/kubelet/kubectl by hand installs on every node of a cluster, minus the Kubernetes parts. A node is a machine with exactly this stack on it plus a kubelet; kubeadm adds no container machinery of its own.

    The snapshot habit is the same one W0.8 asks for on the cluster VMs, and for the same reason: the fastest fix for a control plane you broke while learning is not a repair, it is a restore.

    Docs

    multipass help launch, multipass help snapshot, multipass help restore. Inside the VM, man 1 stat (note that -f asks about the filesystem) and man 7 cgroups, which is the primary source you will be arguing with in I1.

    I0.2

    The Python environment, and the error you get without it

    Why it matters

    Several modules of this track ask you to write a program rather than run one: an image parser in I4, a registry client in I5, a toy CRI server in I8, a CNI plugin in I9. Those are written in Python 3, and on Ubuntu 24.04 installing a Python library the obvious way fails with an error message that looks like a bug and is not. Meeting it deliberately now, with an explanation, costs two minutes; meeting it in the middle of I5 costs your concentration.

    The concept

    A virtual environment (a "venv") is a directory containing its own python3, its own pip, and its own site-packages folder. Activating one puts that directory first on your PATH, so python3 means the copy in the venv and every library you install lands inside it. Deleting the directory uninstalls everything you ever put in it. Nothing is global; nothing is shared.

    Ubuntu insists on this, and the mechanism has a name. PEP 668 lets a distribution mark its Python installation as externally managed — meaning "apt owns the packages here, do not let pip write into them". The marker is a real file you can look at:

    cat /usr/lib/python3.12/EXTERNALLY-MANAGED
    [externally-managed]
Error=To install Python packages system-wide, try apt install
 python3-xyz, where xyz is the package you are trying to
 install. ...

    The reason is not tidiness. On Ubuntu, real system tools are written in Python — cloud-init, parts of the installer, apt's own helpers — and they import libraries that apt installed at specific versions. A pip install that upgrades one of those libraries system-wide can leave the machine unable to finish a boot or complete a package operation. The escape hatch --break-system-packages exists and is named honestly. Use the venv.

    One thing a venv does not do: it does not isolate you from the kernel, from files, or from anything else. It is a PATH trick and a directory, not a container. That distinction is worth holding onto for the whole track — you are about to spend fourteen modules on the machinery that does provide real isolation, and "virtual environment" is a name that invites the confusion.

    Lab

    Open a fresh shell (exit, then multipass shell buildbox). The prompt is prefixed with (.venv-intermediate), which python3 points inside your home directory, and python3 -c 'import requests' prints nothing and exits 0.

    Gotchas

    sudo python3 … does not use your venv. sudo resets the environment, so the root shell gets /usr/bin/python3 and none of your installed libraries — which produces a baffling ModuleNotFoundError for a module you can see is installed. When a lab genuinely needs both root and the venv, spell out the interpreter: sudo ~/.venv-intermediate/bin/python3 script.py.

    Do not be tempted by --break-system-packages "just this once on a throwaway VM". It works, and then two modules later you restore a snapshot, forget you used it, and cannot reproduce your own result. The venv costs one line in .bashrc.

    No direct counterpart — this is toolchain hygiene, not a Kubernetes mechanism. It earns its place because the same instinct shows up one level up: a container image exists largely so that an application's dependencies are pinned somewhere that cannot collide with the host's.

    Keep the comparison in mind when you reach W3.16 — requests vs limits and, later here, I4's layer model: a venv isolates a search path, an image isolates a filesystem, and a container isolates kernel resources. Three different strengths of the same word.

    Docs

    PEP 668 for the marker file and why distributions wanted it; man 1 python3; python3 -m venv --help. The Python packaging guide's "Installing packages using pip and virtual environments" is the canonical how-to.

    I0.3

    Seed the two artefacts this whole track argues about

    Why it matters

    This track's thesis is that the container ecosystem added remarkably little mechanism — it added contracts. That claim is only interesting if you are holding the mechanism in your hands while someone shows you the contract. The two scripts you install now are that mechanism: a container runtime in about eighty lines of bash, and a pod network in about forty. Every module from here compares a real component against one of them.

    The concept

    Look at what you are holding before anyone calls it primitive.

    minibox.sh — the assembled form of what B14.1–B14.4 build one layer at a time — mounts an overlay filesystem (a stack of read-only directories with one writable layer on top, exactly the shape a container image has), unshares five namespaces so the process gets its own mounts, process list, hostname, IPC and network, writes CPU, memory and PID limits into a cgroup, pivot_roots so the host filesystem becomes unreachable, drops four capabilities, and execs your command. Then it wires a veth pair into a bridge on the host, gives the inside end an address and a default route, and adds a NAT rule so it can reach the internet.

    That is a container runtime. It is not a toy version of one; it is one. What it lacks is not machinery but agreement: there is no file another program could read to learn what this container is, no name by which a second tool could find it, no defined way to ask it to stop, and no way to hand the same description to a different implementation and get the same container. It has no bugs a specification would have caught, because it has no specification.

    net-up.sh — the beginner track's B9.19 mini project — is the same story for networking: it creates N network namespaces on one bridge, allocates each an address, routes between them, and masquerades their egress. That is a pod network: IP address management, the wiring, and the egress path. What it lacks is a calling convention, which is precisely and only what CNI adds.

    the unshare/pivot_root/exec sequencerunc and the runtime lifecycleI3

    copying a rootfs onto the box by handOCI distribution-spec (a registry)I5

    One correction ships with the seed copy, and it is worth reading because it is a genuine ordering bug that the specification-free version invites. unshare(2) and pivot_root(2) both require CAP_SYS_ADMIN. A runtime that drops that capability before it isolates the process fails with EPERM having isolated nothing. So the rule is isolate, then disarm — and because pivot_root has by then made the host's /usr unreachable, the seed script has to copy capsh and its shared libraries into the rootfs to be able to drop anything at all. runc needs no such trick: it is a single process that unshares, pivots, drops and execs, so its own code is still in memory at the moment it gives up privilege. Keep that in mind; I3 is that lesson.

    Gotchas

    Both scripts carry a wrong-box guard: they refuse to run if /etc/kubernetes exists. That is not paranoia — minibox.sh writes a MASQUERADE rule and net-up.sh flips net.ipv4.ip_forward, and doing either on a cluster node produces a networking failure that is genuinely hard to trace back to its cause. If the guard fires, you are on the wrong machine; do not edit it out.

    If minibox.sh reports unshare failed: Operation not permitted while you are root, you are running a copy with the pre-correction ordering (capabilities dropped before unshare). Re-copy from labs/intermediate/seed/. I1.4 explains the other cause of that message, which applies when you are not root: Ubuntu 24.04 gates unprivileged user namespaces behind AppArmor.

    --clean deliberately leaves the NAT rule for 10.88.0.0/24 in place and says so. Removing a MASQUERADE rule you did not add is a good way to break something else on a shared machine; on buildbox you can flush it yourself with sudo iptables -t nat -F POSTROUTING.

    minibox.sh is a pod with one container in it, and net-up.sh is that pod's network. Put them beside W1.20 — understand CRI: kubelet → containerd → shim → runc and the chain becomes concrete: everything in that lesson exists to turn a YAML object into the sequence of syscalls your two scripts make by hand.

    The clearest single mapping is W1.21 — meet the pause container. A pod's namespaces have to be created and held open by something before any application container joins them; in minibox.sh that something is the backgrounded unshare whose PID the script wires the veth into. Kubernetes calls the equivalent the sandbox, and I8 is where you create one directly.

    Docs

    Read the two scripts themselves — they are commented line by line and are the shortest primary source in this track. Then man 7 namespaces, man 2 pivot_root, man 8 ip-netns, man 1 capsh, and man 5 overlayfs (or the kernel's Documentation/filesystems/overlayfs.rst) for the lowerdir/upperdir/workdir triple.

    The toolchain

    I0.4

    Install the runtime layer from the projects' own releases

    Why it matters

    sudo apt install containerd works and would be wrong here. Ubuntu 24.04 packages the 1.7 line, which predates almost everything this track teaches about configuring containerd: the config file's version number, the names of its plugins, and where the CRI implementation lives inside it all changed in 2.0 and again since. Learning 1.7's layout and then meeting 2.x on a real node is the worst of both worlds.

    The concept

    Three binaries, three separate projects, three separate release cadences — and one of the recurring confusions in this ecosystem is that people say "containerd" when they mean all three.

    • containerd is a long-running daemon. It holds a content store of image layers, a metadata database, and the bookkeeping for every container on the machine, and it exposes all of that over a unix socket. In the track's analogy it is the building-services company: it does not lay bricks itself, it dispatches people who do.
    • runc is not a daemon. It is a program you run once, which reads a directory containing a root filesystem and a config.json, creates the namespaces and cgroups that file describes, execs your process, and — in the normal case — leaves. The contractor: it shows up with the work order, does exactly what is written on it, and goes home.
    • The CNI plugins are a directory of small standalone binaries (bridge, host-local, portmap, loopback…), each of which does one networking job when executed with JSON on standard input. There is no daemon and no library; the interface is the process boundary itself.

    Everything gets an explicit version, and this is the habit rather than the detail. Every one of those three projects now ships minor releases on a several-month cadence, so "latest" means something different depending on the month you read this; pinning is what makes an output you paste into a bug report reproducible by the person reading it. Versions this page was authored against, verified 2026-07-27:

    ComponentVersion hereWhere it goesWhy not apt
    containerd2.3.3/usr/local/binnoble ships 1.7.28 — pre-2.0 config and plugin layout
    runcv1.5.1/usr/local/sbintracks containerd's release matrix, not the distro's

    The install paths are not arbitrary either. /opt/cni/bin is the directory every CRI implementation looks in by default, and /usr/local is the conventional home for software you installed outside the package manager — keeping it out of /usr/bin means a later apt operation can never quietly replace it.

    Gotchas

    The config version number is a moving target and the single most common source of stale advice about containerd. 2.0 moved from version = 2 to version = 3 and renamed the CRI plugin; 2.3 moved again to version = 4. Old configs are migrated in memory at every startup and keep working, which is exactly why people do not notice they are following a guide for a layout that no longer exists. Two rules keep you out of trouble: generate a fresh config with containerd config default rather than copying one from a blog, and use containerd config migrate to convert an old file rather than editing it by hand.

    Note there is also a plugins.'io.containerd.grpc.v1.cri' section in the default output. That is the compatibility shell for the old single CRI plugin, which 2.x split into the separate …cri.v1.images and …cri.v1.runtime plugins you saw above. Configuring the old path and wondering why nothing changed is a rite of passage; I7 and I8 come back to it.

    runc lands in /usr/local/sbin, which is on root's PATH but not always on an ordinary user's. That is deliberate — runc does essentially nothing useful unprivileged — but it means runc --version may report command not found until you use sudo or add the directory to your PATH.

    This is precisely what W0.6 — install containerd + kubeadm/kubelet/kubectl by hand does on every node, in the same order and from the same tarballs. It is worth noticing how little of that lesson is Kubernetes: three quarters of a node's container machinery is installed before kubeadm is mentioned.

    The /opt/cni/bin directory is the one W0.7 — kubeadm init, install a CNI, join both workers fills when you apply a Flannel or Calico manifest: those manifests are mostly a DaemonSet whose job is to drop a binary into that directory and a JSON file into /etc/cni/net.d. I9 is where that stops being magic.

    Docs

    The containerd getting-started guide is the source these steps follow; docs/cri/config.md in the same repository is the configuration reference. containerd config default and containerd config migrate are the two commands to remember. For runc, the repository's README and man 8 runc.

    I0.5

    Install the client layer, and draw the map of who owns which layer

    Why it matters

    You are about to have four different command-line tools on this machine that can all show you "containers", and they will disagree. That is not a bug and it is the classic beginner error in this ecosystem: ctr, crictl and nerdctl cut into the same chain at different heights, so each shows a different, correct, partial view. Ten minutes drawing the map now saves you the "but my container isn't there" hour later.

    The concept

    The chain, in one line: kubelet → (CRI) → containerd → (shim) → runc → your process, with images arriving from a registry over HTTP and the network attached by a CNI plugin executed as a subprocess. Every arrow in that sentence is a module of this track.

    Read it top to bottom: each layer knows less than the one above. The kubelet knows about pods; containerd knows about containers and images but not pods; runc knows about neither — it knows about a directory and a JSON file.

    The four clients, and what each one can and cannot see:

    ToolSpeaksSeesBlind to
    ctrcontainerd's own native APIeverything containerd holds, in every namespacepods; it has no concept of one
    crictlCRI — the same interface the kubelet usespod sandboxes and the containers inside themanything created outside CRI (e.g. by ctr)
    nerdctlcontainerd, with a Docker-shaped CLIwhat you created with nerdctl; builds, composeCRI's pods, unless you ask for that namespace
    runcnothing — no client/server at allbundles on disk that it started itselfimages, registries, networks, containerd

    The word namespace is overloaded here and it catches everyone once. containerd has its own notion of a namespace — a top-level partition of its metadata store, so that two tools can use the same daemon without seeing each other's objects. It has nothing to do with Linux kernel namespaces, and nothing to do with Kubernetes Namespaces. The kubelet's containers live in containerd's k8s.io namespace; ctr defaults to default. That one fact explains most of "my container isn't there".

    skopeo joins the list for a different reason: it talks to registries and never to a runtime at all. It can inspect and copy images between a registry, a local directory and a tarball without any daemon running, which makes it the right tool for I4 and I5 precisely because it removes containerd from the picture.

    Lab
    1. Install the client layer. crictl comes from cri-tools, whose version tracks the Kubernetes CRI API version; nerdctl's full bundle also carries BuildKit, which I6 needs. 
      CRICTL_VER=v1.36.0

    4. Draw the map. On paper, not in a file — the point is to produce it from memory, and you will be asked to redraw it at the end of I7 and compare the two.       An empty list is correct on a fresh daemon — namespaces are created on first use. After I7 pulls an image with ctr you will see default; after I8 creates a sandbox with crictl you will see k8s.io too, holding a completely separate set of objects.

    Verify

    All four clients report a version, and crictl reaches the daemon without a warning about the endpoint:

    Gotchas

    crictl's own Version: 0.1.0 line in crictl version is the CRI API version, not the tool's — the tool's is what crictl --version prints. Two different numbers with almost the same command; read the labels.

    Almost everything here needs root, because it all ends at a unix socket owned by root (/run/containerd/containerd.sock) or at a syscall that requires privilege. If a command mysteriously reports "connection refused" or "permission denied", try it under sudo before debugging anything else. Rootless operation is real and is I1 and I11's subject; it is not the default.

    A version mismatch between crictl and your Kubernetes version is tolerated but not silent — cri-tools follows the Kubernetes minor version, and using a much older crictl against a newer runtime can hide fields that were added in between. Pin it to the Kubernetes version you care about; for this track that is v1.35 or newer.

    crictl is the tool the advanced track reaches for when kubectl has stopped being useful. W6.2 — where logs physically live is that ladder written down: when the API server is down, or the kubelet cannot start a pod at all, you go to the node and ask the runtime directly.

    The same distinction explains a whole class of exam-relevant failures. W6.17 — image failures: ErrImagePull, ImagePullBackOff is a kubelet-level symptom whose cause is always one layer down, in exactly the registry conversation you will hold by hand in I5.

    Docs

    cri-tools' crictl guide — the closest thing to a manual it has; crictl --help and ctr --help (note ctr's help is organised by object: ctr images, ctr containers, ctr tasks). man 1 skopeo and man 1 skopeo-inspect.     I0.6

    First contact with each tool — and no more than that

    Why it matters

    Four commands, chosen because each one leaks a fact about the architecture that the rest of the track spends modules unpacking. The instruction that matters most in this lesson is the one telling you to stop: run them, notice the one thing each reveals, and resist trying to understand the output. Nothing here is a prerequisite for the next lesson; all of it is a prerequisite for recognising the same output later and thinking "I have seen this".

    The concept

    What to notice, in advance, so you actually see it:

    • ctr version prints a client version and a server version, separately. That is your first sight of the daemon architecture — ctr is a thin client over a unix socket and the thing that holds your containers is a long-lived process elsewhere. It has a surprising consequence that I7 makes you prove: killing the daemon does not kill the containers, because the daemon is not their parent. A per-container shim is.
    • crictl info reports readiness as a set of conditions, and one of them will be false. The runtime is ready; the network is not, because no CNI configuration exists on this box yet. That single false condition is the most common reason a real node sits in NotReady, and you are seeing it in its purest form: nothing is broken, something is merely absent.
    • nerdctl info answers in Docker's vocabulary — storage driver, logging driver, cgroup driver — over a daemon that is not Docker. Those names are a compatibility surface, and knowing they are a translation rather than the underlying truth stops you looking for a "storage driver" setting in containerd's config.
    • runc spec writes a config.json and needs no daemon, no image and no network. Open it and you will recognise most of it from minibox.sh: a root filesystem path, a process to exec, a list of namespaces, a set of capabilities, a few mounts. That recognition is the thesis of this track, so let it land before I2 formalises it.

    Gotchas

    runc spec writes config.json into the current directory and overwrites an existing one without asking. Always run it in a directory you made for the purpose. It also does not create the rootfs/ directory the config refers to — the bundle it generates is deliberately incomplete, which is why running runc run on it immediately fails. That is I3's first lab, not a mistake here.

    Do not read the whole config.json yet, and especially do not start editing it. It is 2.5 KB and about a dozen concepts, several of which (masked paths, rlimits, the seccomp default, the device allow-list) are only sensible after I1. Reading it cold is the reliable way to conclude that the OCI spec is impenetrable, when it is actually one of the shortest specifications you will ever be asked to know.

    The ociVersion field you just read is the first thing the runtime specification requires of any bundle:

    ociVersion (string, REQUIRED) MUST be in SemVer v2.0.0 format and specifies the version of the Open Container Initiative Runtime Specification with which the bundle complies.

    So runc writing 1.3.0 is not runc's own version (which is 1.5.1) — it is runc declaring which edition of the standard this file conforms to. Two different numbers that both look like a version of "the container thing", and telling them apart is worth doing once, now.

On a real node, this exact message is what the kubelet reports upward as container runtime network not ready: cni plugin not initialized — and it is the number-one cause of a freshly-kubeadm inited control plane sitting in NotReady until a CNI is applied.

    See W0.7 — kubeadm init, install a CNI, join both workers, where installing the CNI is what flips it, and W6.11 — the NotReady ladder, end to end for the diagnosis path. You have now seen the bottom rung of that ladder before ever meeting the top of it.

    man 8 runc and man 8 runc-spec; ctr --help; crictl info --help. The runtime-spec's config.md is the field-by-field reference for the file you just generated — bookmark it, do not read it yet.

    How to read a spec

    I0.7

    RFC 2119, the shape of the OCI documents, and finding the sentence that settles it

    Why it matters

    This is the reading skill the whole track depends on, and it is genuinely a skill rather than a fact. Most arguments about container behaviour — does a runtime have to do X, is it safe to rely on Y, whose bug is this — are settled by a single sentence in a Markdown file that takes under a minute to find. The people who seem to know this ecosystem cold are, very often, just people who have read the specs and know their table of contents.

    The concept

    Specifications are written in a small controlled vocabulary defined by RFC 2119, and every OCI document opens by saying so. The words are not English intensifiers; they are conformance requirements with precise consequences:

    KeywordMeansWhat it implies for you
    MUST / REQUIRED / SHALLabsolute requirementan implementation that does not is non-conforming; you may rely on it, and file a bug when it fails
    MUST NOT / SHALL NOTabsolute prohibitionif you see it happen, that is a bug, not a feature to depend on
    SHOULD / RECOMMENDEDdo it unless you have a stated reason not tomost implementations do it; a few deliberately do not, and they are still conforming
    MAY / OPTIONALgenuinely optionalthis is where portability bugs live — code that assumes it happens is broken on the runtime that doesn't

    Two habits follow, and they pay off immediately.

    First: MAY is a warning label. When a specification says a runtime MAY do something, two conforming implementations can differ, and any code you write that assumes one of them is quietly non-portable. Most cross-runtime bugs — works on containerd, fails on CRI-O; works with runc, fails with crun — live under a MAY.

    Second: "the specification is silent on this" is a real and frequent answer, and often the most useful one. The runtime specification says nothing whatsoever about images, registries, networking, logging, or how containers are named. Every one of those silences is a later module of this track, because each was filled in later by a different standard or by no standard at all. Recognising that a behaviour is unspecified is more useful than guessing which implementation's behaviour is the standard one.

    The OCI documents are short and their layout is regular. The runtime specification is a handful of Markdown files in one repository, split by concern, and knowing which file answers which kind of question is most of the skill:

    FileAnswers
    spec.mdthe introduction, and the RFC 2119 statement itself
    bundle.mdwhat a "bundle" is: a directory containing config.json and a root filesystem
    config.mdevery field of config.json, platform-independent — the file you will open most
    config-linux.mdthe Linux-only parts: namespaces, cgroups, devices, seccomp, sysctls
    runtime.mdthe lifecycle: what create, start, kill, delete and state must do
    features.mdhow a runtime advertises what it supports (this is how you avoid relying on a MAY)
    glossary.mdthe definitions the other files use precisely

    The image and distribution specifications have the same shape in their own repositories, and CNI's is a single SPEC.md. You will meet all of them.

    Lab
    1. Clone the specification you will use most. It is small — a few hundred kilobytes — and having it locally means you can grep it, which is the whole trick. 
      cd ~ && git clone --depth 1 --branch v1.3.0 \
  https://github.com/opencontainers/runtime-spec.git
ls ~/runtime-spec/*.md
      bundle.md  config-linux.md  config.md  features.md  glossary.md
principles.md  runtime.md  spec.md  ...
    2. Read the conformance sentence itself, so you know it is really there rather than taking this lesson's word for it. 
      grep -A2 'key words' ~/runtime-spec/spec.md
      The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
"OPTIONAL" are to be interpreted as described in [RFC 2119][rfc2119].
    3. Now the timed exercise. In under a minute, find the sentence that says whether process is required in a config.json. Try it before reading on. 
      grep -n '^\*\* `process` \|`process` (object' ~/runtime-spec/config.md
      **`process`** (object, OPTIONAL) specifies the container process.

      Stopping there gets you the wrong answer, which is why this is the exercise. Read the next sentence:

      grep -A1 '`process` (object' ~/runtime-spec/config.md
      **`process`** (object, OPTIONAL) specifies the container process.
This property is REQUIRED when [`start`](runtime.md#start) is called.
    4. Sit with what that means, because it is the shape of most specification answers. process is optional in the document but required in practice for any bundle you intend to run — which is how a runtime can legitimately accept a config.json with no process, let you create the container, and only then fail at start. "Optional" and "you can leave it out" are not the same claim.
    5. Practise the same move on a question with a different answer: is root required? 
      grep -B1 -A3 'On all other platforms, this field is REQUIRED' ~/runtime-spec/config.md
      On Windows, for Windows Server Containers, this field is REQUIRED.
For [Hyper-V Containers](config-windows.md#hyperv), this field MUST NOT be set.
On all other platforms, this field is REQUIRED.

      Three different answers depending on platform, in three consecutive sentences. This is why "I read that a container must have a root filesystem" is a claim that needs a platform attached to it.

    6. Finally, prove a silence. Search the entire runtime specification for the words that are not in it. 
      grep -ril 'registry\|image manifest\|CNI' ~/runtime-spec/*.md | wc -l
      0

      Zero files. The document that defines what a container is has nothing to say about where its filesystem came from or how it reaches the network. Those are separate standards — I4, I5 and I9 — and the separation is deliberate design, not an oversight.

    Verify

    Answer these three without looking, then check: (1) If a spec says a runtime MAY do something, can you rely on it? No — that is precisely where implementations differ. (2) Is process required in config.json? Optional in the document, required before start. (3) Which OCI document tells you what runc delete must do? runtime.md, the lifecycle file — not config.md.

    Gotchas

    Read the version of the specification your tools implement, not main. GitHub shows you the default branch, which contains unreleased changes; the tag matters. runc --version printed spec: 1.3.0 in I0.6, which is why the clone above pins v1.3.0. Answering a question from main and then finding your runtime disagrees is a very ordinary way to lose an hour.

    Do not confuse the three OCI specifications, which version independently and answer different questions: runtime-spec (v1.3.0) says what a container is and how to run one; image-spec (v1.1.1) says what an image is on disk; distribution-spec (v1.1.1) says how a registry serves them over HTTP. A question about digests belongs to the second, not the first.

    Beware, too, of reading a normative document as a tutorial. Specifications are written for implementers and say nothing about why you would want a feature or how to use it well. When a spec answers "what is allowed" and you needed "what should I do", the spec is not the wrong document — you asked the wrong question of it.

    Every OCI document inherits its vocabulary from one sentence:

    The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" are to be interpreted as described in RFC 2119.
    OCI Runtime Specification v1.3.0 — spec.md; the identical statement opens the image and distribution specifications, and the CNI specification.

    And the exercise's answer, in full, showing why the parenthesis alone is not the answer:

    process (object, OPTIONAL) specifies the container process. This property is REQUIRED when start is called.
    OCI Runtime Specification v1.3.0 — config.md § Process

    Kubernetes has the same skill under a different name, and it is the highest-value habit in the CKA exam: kubectl explain reads the API schema out of your live cluster and tells you whether a field is required, what type it is, and what it defaults to — with no browser and no guessing about which version's fields you are looking at. W0.11 — kubectl explain drills it.

    The instinct is identical to the one you just practised: the authoritative answer is already on the machine in front of you, in a document with a stable structure, and finding it is faster and more accurate than asking the internet. The difference is only that Kubernetes ships its schema inside the API server, while OCI ships its in a Git repository.

    Docs

    RFC 2119 itself is one page — read it once, today. Then the four specifications you will use: runtime-spec, image-spec, distribution-spec, and CNI's SPEC.md. Clone each at the tag your tools implement, and grep rather than browse.

    I0.8

    toolcheck.sh — every version and every config path, in one table

    Why it matters

    For the next thirteen modules, the most common thing that will go wrong is not a mistake in your command — it is a difference between your box and the one these lessons were written on. A different containerd minor, a config file you edited three modules ago and forgot, a venv you did not activate. Every one of those is invisible until you look, and looking takes one command if you build it now.

    The second reason is more subtle and more valuable: writing this script forces you to answer, for each component, where does it read its configuration from? That question has a non-obvious answer for at least three of them, and knowing it is worth more than the script.

    The concept

    Four design decisions, each of which recurs every time you write a small operational tool.

    • Report everything, then fail once. The obvious implementation exits at the first missing tool, which tells you the least useful possible thing: one problem at a time. Instead the script counts failures, prints the whole table, and exits non-zero at the end. A tool that stops at the first error turns one broken install into five runs.
    • Distinguish "missing" from "not configured". A component can be installed and have no configuration file, which is normal — containerd runs happily on its compiled-in defaults with no /etc/containerd/config.toml at all. So the table marks a config path + if the file exists and - if it does not, and neither is a failure. Only a missing binary is.
    • Print the environment's facts, not just the tools'. Three lines at the bottom answer questions that are not about any one binary: which runtime-spec version your runc implements, whether this box is cgroup v2, and whether the daemon is actually running. Those are the three things most likely to explain a mismatch that the version table alone cannot.
    • Do not use set -e here. This is the rare script where you want it off: its entire job is to run commands that might fail and report on them. set -uo pipefail keeps the useful halves — unset variables are still errors, and a failure mid-pipeline is still noticed.

    The config paths themselves are the part worth memorising, because several are not where you would guess:

    ComponentReads its config fromNote
    containerd/etc/containerd/config.tomloptional; absent means compiled-in defaults, which is the state you are in now
    runc— nothing —every input arrives as the bundle's config.json; there is no global config, by design
    crictl/etc/crictl.yamlabsent means it probes well-known socket paths and warns
    nerdctl~/.config/nerdctl/nerdctl.tomlper-user, unlike the rest
    CNI/etc/cni/net.d/ (plus /opt/cni/bin)a directory, read in lexical order; containerd created it empty at startup
    skopeo/etc/containers/registries.confshared with podman/buildah — the "containers" family, not the containerd one

    That runc row is the interesting one. A component with no configuration file is a component whose entire behaviour is a function of its inputs, which is exactly what makes it replaceable — and replaceability is the point of a specification. Hold that thought for I3.

    Lab
    1. Write the script on buildbox, in your home directory. 
      cat > ~/toolcheck.sh <<'EOF'
#!/usr/bin/env bash
# toolcheck — one table of what this box actually has, and where each component
# reads its configuration from. Run it at the top of every module.
set -uo pipefail

missing=0

row() {                                   # row <name> <version-cmd> <config-path>
  local name=$1 vercmd=$2 conf=$3 ver mark=' '
  if ! ver=$(eval "$vercmd" 2>/dev/null) || [ -z "$ver" ]; then
    ver=MISSING; missing=$((missing + 1))
  fi
  [ -n "$conf" ] && { [ -e "$conf" ] && mark='+' || mark='-'; }
  printf '%-11s %-16s %s %s\n' "$name" "$ver" "$mark" "${conf:-—}"
}

printf '%-11s %-16s %s %s\n' COMPONENT VERSION ' ' CONFIG
printf '%-11s %-16s %s %s\n' ----------- ---------------- - ------

row containerd "containerd --version | awk '{print \$3}'" /etc/containerd/config.toml
row runc       "runc --version | awk 'NR==1{print \$3}'" ''
row crictl     "crictl --version | awk '{print \$3}'" /etc/crictl.yaml
row nerdctl    "nerdctl --version | awk '{print \$3}'" "$HOME/.config/nerdctl/nerdctl.toml"
row skopeo     "skopeo --version | awk '{print \$3}'" /etc/containers/registries.conf
row cni        "ls /opt/cni/bin/bridge >/dev/null && echo installed" /etc/cni/net.d
row jq         "jq --version | sed 's/jq-//'" ''
row python3    "python3 -V | awk '{print \$2}'" "$HOME/.venv-intermediate/bin/activate"

echo
echo "runtime-spec implemented: $(runc --version 2>/dev/null | awk '/^spec:/{print $2}')"
echo "cgroup hierarchy:         $(stat -fc %T /sys/fs/cgroup)"
echo "containerd service:       $(systemctl is-active containerd 2>/dev/null)"

if [ "$missing" -gt 0 ]; then
  echo
  echo "FAIL: $missing component(s) missing" >&2
  exit 1
fi
echo
echo "OK: toolchain complete"

    Gotchas

    The eval in row() deserves a word, because eval is usually a mistake. Here every string passed to it is a literal written in this file — no user input reaches it — which is the only condition under which it is defensible. It is used because each tool prints its version in a slightly different shape and the alternative is eight near-identical functions. If you extend the script, keep that invariant: the version command is always a literal.

    Re-run this after every snapshot restore, and especially after any module that changes containerd's configuration. The failure mode it catches is not "I forgot to install something" — it is "I restored a snapshot from before I installed something", which produces a much more confusing symptom because the tool was there ten minutes ago.

    If you later add a component (BuildKit in I6, cosign and a scanner in I11), add its row here at the same time. A check that is one module out of date is worse than no check, because you will trust it.

    Node-level version drift is a real Kubernetes failure class, and this script is its miniature. A cluster's nodes can run different container runtime versions, and kubectl get nodes -o wide prints each node's CONTAINER-RUNTIME column for exactly this reason — it is the first thing to compare when one node behaves differently from the others.

    The formal version of the same concern is W2.12 — memorize the version skew rules, which governs how far apart the control plane and the kubelets may drift. Same instinct at a different altitude: write the versions down, and check them before you debug anything else.

    man 1 bash — the Parameter Expansion section for ${conf:-—}, The Set Builtin for -uo pipefail, and SHELL BUILTIN COMMANDS for eval and local. man 1 printf for the field-width syntax. man 1 systemctl for is-active, which is designed to be read by scripts rather than people.

    I0 recall quiz

    Answer out loud before revealing. These are all setup questions, which makes them easy to skip and expensive to get wrong — every one of them is a mismatch you would otherwise debug in a later module.

    1. Why a third VM? Give the three separate reasons, not one.
      Answer

      Size: the beginner sandbox is 2 vCPU / 4 GB / 20 GB, which image builds and a local registry will exhaust. Blast radius: these labs stop and reconfigure containerd, which would break the CKA lab's nodes, whose kubelets use that same daemon. Internet: unlike sandbox, buildbox must reach real registries, because that conversation is the subject matter of I4–I6.

    2. What is PEP 668, and why is --break-system-packages a bad habit even on a throwaway VM?
      Answer

      PEP 668 lets a distribution mark its Python as externally managed — the marker is /usr/lib/python3.12/EXTERNALLY-MANAGED — so pip refuses to write into packages that apt owns. Real Ubuntu system tools are written in Python, and a pip upgrade of a shared library can break boot or package operations. On a throwaway box the flag works, and then you restore a snapshot, forget you used it, and cannot reproduce your own result.

    3. minibox.sh is a container runtime. Name three things it lacks that are not mechanisms.
      Answer

      A written description another program could read or generate (that is config.json); a name or ID by which a second tool could find the container; and a defined lifecycle — an agreed way to ask it to create, start, stop or delete. All three are agreements, not machinery. It also has no image format, no registry and no network calling convention.

    4. Why must a runtime isolate before it drops capabilities, and what does that cost a shell-script runtime?
      Answer

      unshare(2) and pivot_root(2) both need CAP_SYS_ADMIN; drop it first and the runtime fails with EPERM having isolated nothing. Because pivot_root then makes the host's /usr unreachable, a bash runtime has to ship capsh and its libraries inside the rootfs to drop anything. runc is one process that unshares, pivots, drops and execs, so its own code is still in memory when it gives up privilege.

    5. Why install containerd from a tarball instead of apt on Ubuntu 24.04?
      Answer

      Noble ships the 1.7 line, which predates the configuration layout this track teaches: 2.0 moved the config to version = 3 and split the CRI plugin into io.containerd.cri.v1.runtime and io.containerd.cri.v1.images; 2.3 moved the config again to version = 4. Learning 1.7's layout and then meeting 2.x on a real node is the worst of both.

    6. ctr, crictl and nerdctl can all list containers on the same box and disagree. Why?
      Answer

      They cut into the same chain at different heights and, crucially, look in different containerd namespaces — containerd's own metadata partitions, unrelated to Linux or Kubernetes namespaces. crictl speaks CRI and sees pod sandboxes in the k8s.io namespace; ctr speaks containerd's native API and defaults to default; nerdctl is a Docker-shaped face on the same daemon. A container created by one is invisible to the others unless you name the namespace.

    7. Which of those tools would you use to ask "does this image tag exist and what is its digest", and why is it none of the above?
      Answer

      skopeo. It talks to registries over HTTP and needs no runtime, no daemon and nothing pulled locally — which makes it the right tool precisely because it takes containerd out of the picture. I4 and I5 lean on it heavily.

    8. Your fresh containerd reports NetworkReady: false. Is something broken?
      Answer

      No — something is absent. There is no CNI configuration in /etc/cni/net.d yet, so the runtime correctly reports it cannot attach a pod to a network. This is the purest form of the most common cause of a node stuck in NotReady after kubeadm init: the cluster is fine, the CNI has simply not been installed.

    9. runc --version prints 1.5.1 and spec: 1.3.0. What are those two numbers?
      Answer

      The first is runc's own release version. The second is the version of the OCI runtime specification it implements — the same number that appears as ociVersion in a generated config.json. They move independently: a bundle declares which edition of the standard it complies with, not which runtime wrote it.

    10. In RFC 2119 terms, where do portability bugs live, and why?
      Answer

      Under MAY / OPTIONAL. If a spec says a runtime may do something, two conforming implementations can differ — so code that assumes the behaviour happens is broken on the one that doesn't, and neither implementation has a bug. features.md exists so a runtime can advertise which optional things it actually supports.

    11. Is process required in a config.json?
      Answer

      Both answers are right, which is the lesson. The spec says "process (object, OPTIONAL)" and then, in the very next sentence, "This property is REQUIRED when start is called." So a runtime may accept and create a bundle without it, and must fail at start. Reading the parenthesis alone gets you the wrong answer.

    12. The OCI runtime specification says nothing about images, registries or networking. Is that a gap?
      Answer

      No — it is deliberate separation. Those are three other standards (image-spec, distribution-spec, CNI) that version independently, which is what lets you swap a registry without touching your runtime. "The spec is silent on this" is a real and frequent answer, and recognising it beats guessing which implementation's behaviour is the standard one.

    13. Why does toolcheck.sh not exit at the first missing tool, and why does it not use set -e?
      Answer

      Because a tool that stops at the first error turns one broken install into five runs — it counts failures, prints the whole table, and exits non-zero at the end. set -e is off for the same reason: the script's entire job is to run commands that may fail and report on them. set -uo pipefail keeps the useful halves.

    14. Which component in the table has no configuration file at all, and why is that significant?
      Answer

      runc. Every input it takes arrives as the bundle's config.json, so its behaviour is a pure function of its inputs — which is exactly what makes it replaceable by any other conforming runtime. A component with no hidden state is the practical payoff of having a specification.
