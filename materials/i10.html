    I10 — Container storage: volumes, snapshots, the CSI shape

    The third contract, and the one with the least mystery in it: a volume at the runtime layer is a bind mount plus some bookkeeping. Get that sentence properly earned and Kubernetes storage becomes a naming and orchestration layer over mechanics you already have.

    Storage is where Kubernetes vocabulary is thickest — PersistentVolume, PersistentVolumeClaim, StorageClass, provisioner, attacher, stage, publish — and where the machinery underneath is thinnest. Nearly all of it reduces to three things you have already built: a directory, mount(2), and a program keeping a record of which is which. This module spends its five hours proving that, ending with a real CSI driver you drive by hand over its socket, and a hundred-line volume manager of your own.

    Checkpoints12 Hours~5 PrerequisitesI7 · B5

    • Add a volume by hand — one entry in config.json's mounts array — and tell a bind, a tmpfs and a real block device apart by how each one fails.
    • Work mount propagation in both directions, and explain from the mount table alone why mountPropagation: HostToContainer exists.
    • Drive a real CSI driver over its socket: Identity, Controller, Node, and the four calls that matter.
    • Explain stage versus publish well enough to predict which component failed from the symptom.

    A container's three storages

    I10.1

    Three storages, and only one of them is a volume

    Why it matters

    Nearly every storage question in Kubernetes is really one question wearing a disguise: which of the three storages is this? A container has exactly three, they behave completely differently, and confusing them produces the two most baffling incidents on the list — a pod with no volumes filling a node's disk, and data that vanishes on a restart nobody ordered.

    The concept

    Every running container reads and writes through three separate things stacked into one apparent filesystem.

    The image layers. Read-only, shared between every container started from that image, owned by the snapshotter. Ten pods from one image cost one copy on the node, and every byte is re-fetchable from a registry at any time. This is B5's overlayfs lowerdir stack, and I7.11 is where you last saw the directories.

    The writable layer. One per container, private to it, unshared. It is the overlay's upperdir — every file the container creates or modifies lands here. It is counted against the node's ephemeral storage, it is destroyed with the container, and it is recoverable from nowhere at all. No registry has a copy, because it never came from one.

    Mounts from outside. Anything the runtime was told to mount into the container from elsewhere: a host directory, a tmpfs, a real block device. This is the only category whose lifetime is independent of the container, and everything a pod spec calls a volume is one of these.

    Hold on to that last sentence. emptyDir, hostPath, a ConfigMap projection, a PVC backed by a cloud disk — at the runtime layer these are all the third category, differing only in who created the directory and what they put in it before the mount happened.

    image layersshared, re-fetchablewritable layerprivate, gone with the containeroutside mountsindependent lifetime

    It is worth noticing what the runtime spec does not say. There are no layers in it, no sharing, no snapshotter — the root filesystem is one directory, and everything about layering is an invention of the layer above.

    **`root`** (object, OPTIONAL) specifies the container's root filesystem.
    […]
    * **`path`** (string, REQUIRED) Specifies the path to the root filesystem for the container.
    […] The value SHOULD be the conventional `rootfs`.

    A directory MUST exist at the path declared by the field.
    OCI Runtime Specification v1.3.0 — config.md § Root

    For any running container you can now name its three storages, print the two snapshotter paths from a single command, and say without hesitating which one survives ctr container rm, which one survives a node rebuild, and which one exists only because someone asked for it in a spec.

    Gotchas
    • The content store is a fourth thing, not one of the three. It holds compressed blobs as pulled; the snapshotter holds them unpacked and mountable. Both live under /var/lib/containerd and neither is a volume. Deleting an image frees the first; only deleting containers frees the second.
    • "Shared" means shared bytes, not a shared directory. The lowerdir is one path on disk that many containers mount simultaneously. Nothing is copied per container until something writes — which is I10.3.
    • The numbers move under you. du on a live snapshot tree races with running containers. Take the measurement twice if it matters.

    A pod's volumes: list is the third category, exclusively. W5.1 walks the ephemeral kinds — emptyDir, hostPath, ConfigMap and Secret projections — and W5.2 shows where the kubelet puts them on the node, under /var/lib/kubelet/pods/<uid>/volumes/. Neither of the other two storages is nameable in a pod spec at all: you influence the image layers by choosing an image, and the writable layer only through ephemeral-storage limits.

    I10.2

    The pod with no volumes that fills the node

    Why it matters

    A pod with no volumes, no PVCs and a perfectly modest memory limit can fill a node's disk and get itself — and its innocent neighbours — evicted. Nothing limits how much a container writes into its own root filesystem unless somebody set an ephemeral-storage limit, and almost nobody does. The usual culprit is not application data but a log file written inside the container, which the CRI also cannot show you through kubectl logs. Worst of both worlds, from one mistake.

    The concept

    The writable layer is an ordinary directory on the node's filesystem. There is no quota on it, no reservation, and no accounting the container can see. df inside the container reports the host's filesystem, because that is genuinely what it is writing to. So a container that writes 300 MB writes 300 MB of the node's disk, and it does so through a path with no gate on it.

    What makes this hard to diagnose is that the accounting is split. The kubelet learns about disk usage through the CRI, and — as the lab shows — the CRI reports only the containers it created. A node whose disk is full of snapshots made by ctr, or by a build in another containerd namespace, will report a comfortable few megabytes while du screams.

    The CRI splits its answer in two, and the split is exactly the distinction this lesson turns on: images are shared and re-fetchable, container writable layers are not.

    // ImageFsInfo returns information of the filesystem that is used to store images.
    rpc ImageFsInfo(ImageFsInfoRequest) returns (ImageFsInfoResponse) {}
    Kubernetes CRI, runtime.v1 — api.proto; the response carries image_filesystems and container_filesystems separately

    You can state where a container's writes physically land, produce the file from the host with one ls, show the number the kubelet would evict on, and explain why that number can disagree with du by two orders of magnitude on a busy node.

    Gotchas
    • crictl imagefsinfo nests its answer under .status. A jq filter of .imageFilesystems[0] silently yields null, which reads like an empty node rather than a wrong query. This cost a round while writing this page.
    • A container made with ctr is invisible to CRI accounting even in the k8s.io namespace. Writing 300 MB through ctr moved imagefsinfo by exactly zero bytes; the same write through crictl moved it by 314 MB. The CRI reports on what it created, not on what is in the namespace.
    • Deletion is asynchronous. Check once, immediately after container rm, and the upperdir is still on disk — it went away at +800 ms here. A monitoring check written that way reports a leak that does not exist.
    • Container filesystem stats are windowed. crictl stats right after a write shows the old value. The twelve-second sleep in the lab is not decoration.

    This is the mechanism under node disk pressure and the ephemeral-storage request and limit. W5.1 specifies emptyDir, which lands on this same filesystem and is charged the same way. The fix for the logging case is not a bigger disk: it is not writing logs to a file inside the container, so that both this problem and the kubectl logs one disappear together.

    Docs: in the Kubernetes docs, search node-pressure eviction and local ephemeral storage; for the runtime side, crictl stats and crictl imagefsinfo in the cri-tools documentation.

    I10.3

    Shared until you write: copy-up and its price

    Why it matters

    Two facts that sound unrelated have the same cause. Starting a hundred pods from one image is nearly free. Opening a two-gigabyte file inside a container for writing is not — it costs two gigabytes before a single byte changes. Both fall out of one rule you already met in B5.14, and being able to derive them rather than remember them is the point of this checkpoint.

    The concept

    Every container from an image mounts the same read-only lowerdir stack and gets its own empty upperdir. Reads fall through the stack until a layer has the file, so unmodified files are read straight from the shared copy — one set of bytes on disk, however many containers.

    Writes are where it changes. Overlayfs cannot modify a file in a read-only lower layer, so the first write to any such file triggers a copy-up: the kernel copies the file in its entirety into that container's upperdir, then applies the write to the copy. The cost is proportional to the file's size, not to the size of the change. Appending one byte to a four-megabyte library copies four megabytes.

    This is why a container that opens a large data file read-write pays for it at open time, in disk and in latency, and why the same container reading that file pays nothing. It is also why "the image is only 200 MB" tells you nothing about what the container will cost on the node.

    Copy-up is kernel behaviour, not a container standard — no OCI document mentions it. The authority is the overlayfs documentation, and it is explicit that the copy precedes the change.

    When a file in the lower filesystem is accessed in a way that requires write-access, such as opening for write access, changing some metadata etc., the file is first copied from the lower filesystem to the upper filesystem (copy_up).
    […]
    The copy_up may turn out to be unnecessary, for example if the file is opened for read-write but the data is not modified.
    Linux kernel documentation — filesystems/overlayfs.rst

    Gotchas
    • Copy-up is triggered by intent, not by change. Opening for write is enough; so is chmod or touch. A process that opens a large file read-write and writes nothing still pays in full.

    • Sharing is per layer, not per image. Two images built on the same base share the base's snapshots and nothing above. This is why rebasing images onto a common parent is a real disk optimisation on a busy node.

    This is the whole reason a node can run many pods of one image cheaply, and it sets the honest cost model for emptyDir versus writing into the container filesystem — see W5.1. It is also why databases and anything else that rewrites large files in place belong on a volume (W5.3) rather than in the container's own filesystem: on a volume there is no lower layer, so there is no copy-up.

    Volumes at runtime level

    I10.4

    A volume is one entry in the mounts array

    Why it matters

    The word "volume" suggests an object — something created, tracked, owned. At the runtime layer there is no such object. There is an array in a JSON file and a directory somebody manages. Once you have added one by hand, the entire Kubernetes storage stack reads as elaborate bookkeeping around a field you can type yourself.

    The concept

    The runtime spec's mounts array is a list of mount(2) arguments — source, destination, type, options — that the runtime executes inside the container's mount namespace after pivot_root. That is the whole mechanism. Everything the ecosystem calls a volume is built on it:

    • a Docker named volume is a directory under /var/lib/docker/volumes plus a name in a database;
    • a Kubernetes emptyDir is a directory under /var/lib/kubelet/pods/<uid>/volumes/ that the kubelet creates and deletes;
    • a PVC-backed volume is the same again, with a CSI driver having mounted something there first.

    The orchestration around each of those is elaborate and genuinely valuable — it is what makes a volume follow a pod across nodes, survive a reschedule, and be requested declaratively. The runtime-level primitive it all lands on is one line of JSON.

    The spec is unusually blunt here: it does not define volume semantics at all, it defers to the mount(2) man page and specifies only the ordering.

    **`mounts`** (array of objects, OPTIONAL) specifies additional mounts beyond [`root`](#root).
    The runtime MUST mount entries in the listed order.
    For Linux, the parameters are as documented in [mount(2)][mount.2] system call man page.
    OCI Runtime Specification v1.3.0 — config.md § Mounts

    "In the listed order" is load-bearing: mounts that nest inside one another only work one way round, and a runtime is required to respect what you wrote rather than sort it for you.

    Gotchas
    • Order matters and the runtime will not fix it. The spec says entries are mounted in the order listed. Mount /data/inner before /data and the first one disappears under the second.
    • rbind and bind are not the same. rbind brings along mounts nested under the source; plain bind brings only the top one, so a volume containing another mount arrives mysteriously empty at that sub-path.
    • A bind mount has no size of its own. It is the host filesystem, so df inside the container reports the host's free space and no limit applies — the subject of I10.5.

    W5.2 walks the kubelet's side of exactly this: every pod volume becomes a directory under /var/lib/kubelet/pods/<uid>/volumes/, and the container's generated config.json gets one mounts entry per volumeMounts entry. The subPath field, which surprises people by being resolved on the node rather than by the storage system, is nothing more than a longer source in that JSON.

    I10.5

    Three things you can mount, told apart by how they fail

    Why it matters

    A bind, a tmpfs and a real filesystem on a block device all arrive as a directory inside the container and look identical to the application. They are not remotely identical, and the cleanest way to tell them apart is to fill each one until something breaks. One of them gets your container OOM-killed with a message about memory and no mention of storage anywhere.

    The concept

    A bind is part of the host's filesystem, so it has no size of its own. df inside the container reports the host's free space, and nothing enforces a limit — which is why size limits on ordinary bind mounts are so awkward, and why the mini project in I10.11 reaches for a loop image to get one.

    A tmpfs is memory pretending to be a filesystem. The pages are page cache, and — this is the part that catches people — they are charged to the cgroup of the process that wrote them. So filling a tmpfs mounted into a container consumes that container's memory limit. Fill it past the limit and the kernel's OOM killer ends the process, reporting a memory problem, because from the kernel's point of view it is one. B7's OOM lesson (B7.9) arriving from an unexpected direction.

    A real filesystem on a block device is the only one of the three with genuine quota semantics: its own superblock, its own free-space accounting, its own ENOSPC. Fill it and the write fails, the process handles it or does not, and nothing gets killed.

    bindfills the nodetmpfsOOM-kills the containerblock deviceENOSPC, container lives

    The spec allows all three through the same field — the difference is entirely in type and options, which it hands to mount(2) without interpretation.

    * **`type`** (string, OPTIONAL) The type of the filesystem to be mounted.
    * Linux: filesystem types supported by the kernel as listed in /proc/filesystems (e.g., "minix", "ext2", "ext3", "jfs", "xfs", "reiserfs", "msdos", "proc", "nfs", "iso9660"). For bind mounts (when `options` include either `bind` or `rbind`), the type is a dummy, often "none" (not listed in /proc/filesystems).
    OCI Runtime Specification v1.3.0 — config.md § Mounts

    I10.6

    Mount propagation, and why HostToContainer exists

    Why it matters

    B5.12 taught propagation as kernel mechanics. Here is what it is for. A CSI node plugin runs as a pod and mounts a volume into a host path; the workload pod must see that mount appear inside a directory it already has mounted. Under the wrong propagation that is impossible, and the symptom is uniquely maddening: an empty directory where a filesystem plainly is mounted, one namespace over.

    The concept

    A mount is not a fact about a path, it is a fact about a path in a mount namespace. Propagation settings decide whether a mount event crosses between namespaces, and there are three that matter:

    • private — nothing crosses, in either direction.
    • slave — mounts made on the host appear inside the container; mounts made inside stay inside. One-way, downhill.
    • shared — events cross both ways; a mount made inside the container appears on the host.

    Kubernetes exposes exactly these as mountPropagation: None (rprivate), HostToContainer (rslave) and Bidirectional (rshared). Bidirectional requires a privileged container, for the reason the lab makes visible: a container that can create mounts on the host can mount things the node's administrator did not agree to.

    One subtlety decides whether any of this works: the host-side path must itself be a shared mount point. Propagation happens between peers in a peer group, and a plain directory is not in one. This is why a node's kubelet directory is deliberately made shared, and why a CSI driver's manifest asks for Bidirectional on /var/lib/kubelet.

    The runtime spec carries propagation twice — per mount, in options, and once for the whole root filesystem. The second one is the field people miss, and the lab shows it deciding the outcome.

    **`rootfsPropagation`** (string, OPTIONAL) sets the rootfs's mount propagation.
    Its value is either `shared`, `slave`, `private` or `unbindable`.
    It's worth noting that a peer group is defined as a group of VFS mounts that propagate events to each other.
    […]
    * **`private`**: the rootfs mount doesn't receive mount propagation events from the host and further mounts in nested containers will be isolated from the host and from the rootfs (even if the nested container `rootfsPropagation` option is shared).
    OCI Runtime Specification v1.3.0 — config-linux.md § Rootfs Mount Propagation

    Gotchas
    • The host path must already be a shared mount point. A plain directory has no peer group, so nothing propagates and every test says "no" — with no error to explain it.

    The CSI shape

    I10.7

    Why there is an interface here at all

    Why it matters

    By now this story should be predictable, and that is the point of asking it a third time. You have watched the same thing happen to runtimes (CRI) and to networking (CNI). Storage went the same way for the same reason, and once you can see the pattern you can predict where the next interface will appear.

    The concept

    Storage drivers used to live in tree: the code that talked to AWS EBS, GCE PD, Ceph, NFS and a dozen others was inside the Kubernetes repository. Every vendor's bug was a Kubernetes bug, every vendor's fix waited for a Kubernetes release, and every vendor's credentials-handling code ran in the controller manager. Adding support for a new storage system meant getting a pull request merged into Kubernetes.

    CSI replaced that with a contract. A driver is now a separate program speaking a versioned gRPC API; Kubernetes ships a client and some generic controllers, and the vendor ships everything that knows about their storage. The in-tree plugins were migrated behind the same interface and removed.

    Here is the two-sentence version worth remembering: CSI replaced vendor code living inside Kubernetes with a versioned gRPC contract that vendor code implements from outside. That made storage support a matter of installing a driver rather than upgrading Kubernetes — and made every storage system's bugs its own again.

    Notice the shape each interface took, because the shape follows the interaction rather than the subject:

    InterfaceInteraction it supportsShape it took
    CNIone short action per sandbox, then donean exec'd binary, JSON on stdin
    CRIlong-lived, stateful, error-heavygRPC on a unix socket
    CSIlong-lived, stateful, error-heavy, and partly off-nodegRPC on a unix socket, split into three services

    All three are versioned contracts with their own release cycles, and Kubernetes ships a client for each. Once you see that, "how do I add X to Kubernetes" almost always answers itself: find which interface already covers it.

    CSI does not mention Kubernetes in its definitions at all. It speaks of a "CO" — a Container Orchestration system — and Kubernetes is merely one. That abstraction is the whole point of the exercise.

    | Volume | A unit of storage that will be made available inside of a CO-managed container, via the CSI. |
    | CO | Container Orchestration system, communicates with Plugins using CSI service RPCs. |
    | Plugin | Aka “plugin implementation”, a gRPC endpoint that implements the CSI Services. |
    Container Storage Interface v1.13.0 — spec.md § Terminology

    I10.8

    Three services, and the four calls that matter

    Why it matters

    The three-way split is not organisational tidiness — it is a diagnostic map. Learn which service a call belongs to and half of CSI debugging becomes arithmetic: a volume stuck with no PersistentVolume is a Controller problem, a pod stuck ContainerCreating on one node is a Node problem, and those two live in different pods with different logs.

    The concept

    The split is by where the work must run, not by what it does.

    • Identity — who are you, are you healthy, what do you support. Three calls. Every other component asks these first.
    • Controller — cluster-wide operations that talk to a storage API somewhere: create a volume, delete it, attach it to a node. These can run anywhere in the cluster, because they are API calls to a SAN or a cloud provider.
    • Node — operations that perform mount(2), and therefore must run on the machine where the pod will run.

    That is exactly why a CSI driver ships as two workloads: a Deployment for the Controller half and a DaemonSet for the Node half. And it is why the four calls that matter sort the way they do:

    CreateVolumeControllerControllerPublishVolumeControllerNodeStageVolumeNodeNodePublishVolumeNode

    • An unset Probe readiness means ready. The field is a wrapper type precisely so that "not answered" and "answered false" are different. Treating them the same restarts healthy drivers.
    • Capability enums have gaps, and drivers advertise numbers your spec version does not define. Measured here on the reference driver, not a hypothetical. Never call Name() on an unvalidated enum value.
    • A call the driver did not advertise is a call it never receives. The CO checks capabilities and skips; if a driver forgets to advertise STAGE_UNSTAGE_VOLUME, staging is silently not attempted rather than failing loudly.

    W5.11 is this same architecture named from the Kubernetes side, and W5.12 traces one mount end to end on a node — the two paths from the last lab step are exactly what it finds. The Controller/Node split is also why W5.9's WaitForFirstConsumer exists: for topology-constrained storage, the Controller cannot sensibly create the volume until the scheduler has chosen the node.

    Docs: the CSI spec's RPC Interface section — the service definitions and the volume lifecycle diagram; and the kubernetes-csi site's Developing CSI Drivers.

    I10.9

    Stage versus publish: once per node, once per pod

    Why it matters

    This is the distinction people skip, and skipping it costs them the answer to a question that surprises everyone: how can a ReadWriteOnce volume serve three pods at once? Get stage and publish straight and that stops being a puzzle and becomes a consequence.

    The concept

    There are two Node-side mount operations, and they exist because some of the work is expensive and must not be repeated.

    NodeStageVolume happens once per node. It does the costly things: format the filesystem if it has never been formatted, run fsck, attach the device, apply an fsGroup ownership change — then mounts the result at a global staging path, keyed by volume.

    NodePublishVolume happens once per pod. It bind-mounts from the staging path into that pod's own directory. This is cheap, because everything expensive already happened.

    Now the surprise resolves itself. ReadWriteOnce means the volume can be staged on one node. On that node, any number of pods can be published from the same staging mount — which is why several pods on one node can share an RWO volume while a pod on a second node cannot get it at all. The access mode was always a statement about nodes, not pods.

    attach + format + fsck + chownNodeStageVolume, once/…/globalmountNodePublishVolume, per pod/…/pods/<uid>/…/mount

    The spec makes the ordering a requirement on the CO, not a suggestion, and makes re-staging a no-op rather than an error.

    The CO MUST guarantee that this RPC is called and returns a success before any `NodePublishVolume` is called for the given volume on the given node.
    […]
    If the volume corresponding to the `volume_id` is already staged to the `staging_target_path`, and is identical to the specified `volume_capability` the Plugin MUST reply `0 OK`.
    Container Storage Interface v1.13.0 — spec.md § NodeStageVolume
    Lab
    1. Try to collapse the two steps. Publish a freshly created volume without staging it first, exactly as a CO with a bug would. 
      sudo … csi-probe.py provision i10-order-a
sudo … csi-probe.py publish "$V1" pod-1111
      gRPC FAILED_PRECONDITION: volume "9ea9941c-…" must be staged before publishing
mounts created: 0

      The driver enforces what the spec requires of the caller. Nothing was mounted, and the error names the cause precisely.

    2. Do it properly: stage once, publish twice, for two different pods. 
      sudo … csi-probe.py stage   "$VOL"
sudo … csi-probe.py publish "$VOL" pod-aaaa1111

findmnt -no TARGET,SOURCE | grep -E "globalmount|kubernetes.io~csi"
      /var/lib/kubelet/pods/pod-aaaa1111/volumes/kubernetes.io~csi/pvc-aece9ac8/mount   /dev/sda1[/var/lib/i10-csi-data/aece9ac8-…]

      Two pod mounts, one source. Each appears twice in the full table — the shared-subtree duplication from I10.6, now on a real driver.

    3. Confirm they are the same bytes, which is the entire promise of a shared volume. 
      echo "written through pod-aaaa1111" | sudo tee $A/hello.txt

      And there is the last piece of demystification: the "volume" this driver provisions is a directory named after a UUID. Everything above it — the staging mount, the two pod mounts, the PV object, the PVC — is naming and bookkeeping around that directory.

    4. Now try to unstage while pods still hold it. This is what happens when a CO gets teardown ordering wrong. 
      sudo … csi-probe.py unstage "$V1"
      NodeUnstageVolume  INTERNAL: volume "9ea9941c-…" is still published at
  ["/var/lib/kubelet/pods/pod-1111/…/mount" "/var/lib/kubelet/pods/pod-2222/…/mount"] on node "sandbox"
      sudo … csi-probe.py unpublish "$V1" pod-2222

      NodeUnpublishVolume  ok
NodeUnstageVolume    INTERNAL: volume "9ea9941c-…" is still published at
  ["/var/lib/kubelet/pods/pod-1111/…/mount"] on node "sandbox"
      sudo … csi-probe.py unpublish "$V1" pod-1111
sudo … csi-probe.py unstage   "$V1"
      NodeUnpublishVolume  ok

mounts left: 0

      Staging is refcounted by publications, and the driver refuses until the last one is gone. This is the mechanism behind a volume that will not detach because one pod on one node is still terminating.

    5. Finally, the failure that is not refused. Delete the volume while a pod still has it published. 
      sudo … csi-probe.py delete "$V2"    # ControllerUnpublishVolume + DeleteVolume
      before: 2 pod mount(s)
ControllerUnpublishVolume  ok
DeleteVolume               ok
after:  2 pod mount(s), and the volume is gone
what the mount now points at:
  /var/lib/kubelet/pods/pod-3333/…/mount   /dev/sda1[/var/lib/i10-csi-data/9f56707a-…//deleted]
and the tidy-up that is now nobody's job:
NodeUnpublishVolume  NOT_FOUND: volume id 9f56707a-… does not exist in the volumes list

      //deleted is the kernel's marker for a mount whose source directory has been unlinked. The mount is still there, the data is not, and the call that would clean it up now refuses because the driver has forgotten the volume. This is why PersistentVolumes carry finalizers — something must hold the delete until the node side is finished.

    6. The other expensive-once operation is fsGroup. Measure it, because "it is slow on large volumes" is not a number. 
      sudo find "$STAGE" -type f | wc -l

      50000 files

  warm: 0.18 s
one stat() on the top directory:  0.00 s
      …  # the same operation on ten times the files

      Half a million small files cost 5.74 seconds of pod start-up, on local ext4 with nothing else happening. That is the cost fsGroupChangePolicy: OnRootMismatch avoids by doing the single stat instead — and it is charged once per node when done at stage time, rather than once per pod.

    Verify

    You can explain why several pods on one node can share a ReadWriteOnce volume and a pod on a second node cannot, predict the error class for publishing before staging and unstaging before unpublishing, and give a measured figure for what a recursive fsGroup chown costs.

    Gotchas
    • The chown figure depends entirely on the backing store. 5.74 s for 500,000 files is local ext4. On network-backed storage each operation is a round trip, which is where the "minutes" in the folklore comes from. Quoting one number for both is how this gets argued about.
    • DeleteVolume does not check whether the volume is mounted. Measured: it succeeded with two live pod mounts, which then pointed at //deleted and could no longer be unpublished. Ordering is the caller's responsibility, and finalizers are how Kubernetes discharges it.
    • Staging is refcounted, unstaging is not idempotent in the way you might hope. The driver returns INTERNAL — not a nice typed error — while publications remain, and the message body is where the actual paths are.
    • Not every driver stages. If STAGE_UNSTAGE_VOLUME is not advertised, the CO goes straight to publish and there is no global mount at all. Looking for globalmount on such a node and finding nothing is not a fault.

    W5.6 is where access modes are established as node-level guarantees — this checkpoint is the mechanism underneath that claim. W5.12 traces the two paths on a real node, and they are the same two you produced by hand. The fsGroup measurement is the justification for fsGroupChangePolicy, which sits in a pod's securityContext — a field the advanced track deliberately does not cover, so this page is where it is explained.

    Docs: the CSI spec's NodeStageVolume and NodePublishVolume sections, including their error tables; and in the Kubernetes docs, access modes and configure a security context for a pod for fsGroupChangePolicy.

    I10.10

    The sidecars: controllers that translate objects into gRPC

    Why it matters

    A CSI driver's pod usually has four or five containers in it, and only one of them is the vendor's. Knowing what the others do turns "the volume is stuck" from a vendor-support question into a question with a shape: which loop stopped turning?

    The concept

    The vendor writes one thing: a gRPC server that knows their storage. Everything Kubernetes-shaped — watching objects, respecting finalizers, retrying with backoff, leader-electing between replicas — is done by generic sidecar containers that the project maintains, running next to the driver in the same pod and talking to it over the same socket you used in I10.8.

    Each sidecar is an ordinary controller in the B13 sense: watch an object, compare desired to actual, act, record. The only unusual part is that "act" means a gRPC call instead of another API write.

    SidecarWatchesCalls
    external-provisionerPersistentVolumeClaimCreateVolume, DeleteVolume
    external-attacherVolumeAttachmentControllerPublishVolume, ControllerUnpublishVolume
    external-resizerPersistentVolumeClaim (size changes)ControllerExpandVolume
    external-snapshotterVolumeSnapshot, VolumeSnapshotContentCreateSnapshot, DeleteSnapshot
    node-driver-registrarnothing — it makes no API calls at allGetPluginInfo, then registers with the kubelet over a socket
    livenessprobenothingProbe, exposed as an HTTP health endpoint

    The registrar is the one worth pausing on, because it is commonly described incorrectly. It does not watch Node objects and it needs no RBAC: it asks the driver its name, then creates a registration socket that the kubelet's plugin watcher notices. That is the whole mechanism by which a node learns a driver exists.

    Nobody publishes on the node's behalf. NodeStageVolume and NodePublishVolume are called by the kubelet itself — there is no sidecar for them, which is why those two calls appear in kubelet logs and the others do not.

    The registrar's own documentation is blunt about the thing most summaries get wrong:

    The node-driver-registrar does not interact with the Kubernetes API, so no RBAC rules are needed.
    kubernetes-csi/node-driver-registrar — README
    Lab
    1. Map each call you made in I10.8 and I10.9 onto the component that would have made it on a real cluster. This is the checkpoint's actual work; csi-probe.py prints the answer beside each call so you can check yourself. 
      CreateVolume            <- external-provisioner, reacting to a PVC
ControllerPublishVolume <- external-attacher, reacting to a VolumeAttachment
NodeStageVolume         <- the kubelet, on the node the pod was scheduled to
NodePublishVolume       <- the kubelet, once per pod
    2. Look at the two sockets involved, because the distinction explains a whole class of "driver not found" problems. The driver creates one; the registrar creates the other. 
      sudo ls -l /var/lib/i10-csi/                      # the driver's own socket
ls /var/lib/kubelet/plugins_registry/ 2>/dev/null || echo "  (no registry dir — no kubelet on this box)"
      srwxr-xr-x 1 root root 0 Jul 31 08:53 csi.sock
  (no registry dir — no kubelet on this box)

      On a real node there would be a second socket, /var/lib/kubelet/plugins_registry/<drivername>-reg.sock, created by the registrar. The kubelet watches that directory; a driver whose registrar failed is running, healthy, answering gRPC — and invisible.

    3. Confirm the division of labour from the other end: ask the driver for the identity information the registrar would ask for, and note that it is the whole conversation. 
      sudo CSI_PB_DIR=$HOME/csi ~/.venv-intermediate/bin/python ~/csi-probe.py identity | head -2
      GetPluginInfo         name=hostpath.csi.k8s.io version=v1.18.0
GetPluginCapabilities service: CONTROLLER_SERVICE

      The registrar takes that name and reports it to the kubelet along with the driver's socket path. Everything after that is the kubelet calling the Node service directly.

    Verify

    Given a stuck volume you can name the loop to inspect: PVC Pending with no PV means external-provisioner; a VolumeAttachment that never becomes attached means external-attacher; a pod stuck ContainerCreating with a mount error means the kubelet and the Node service; and a driver that seems entirely absent from a node means the registrar.

    Gotchas
    • The registrar is widely described as watching Node objects. It does not. The summary page for the sidecars is vague enough to invite that reading; the component's own README says it makes no API calls and needs no RBAC. Checked while writing this page, because the first source said otherwise.
    • There is no sidecar for the Node service's mount calls. The kubelet makes them. Looking for an external-mounter in a driver's pod is looking for something that does not exist.
    • Sidecars are versioned separately from the driver and from the spec. Three independent version streams in one pod, which is why compatibility matrices exist for CSI drivers at all.
    • Leader election is per sidecar. Two replicas of a controller Deployment do not split the work; one is elected and the other waits, so "the provisioner is running" is not the same as "the provisioner is the leader".

    This is W5.11 from the other side, and the two descriptions should now be recognisably the same system. It is also B13's reconciliation loop with a translator bolted on — every sidecar is watch, compare, act, and the acting happens to be a gRPC call. When a volume is stuck, the productive first question is which of those loops stopped turning, not what the vendor's driver logged.

    Docs: the kubernetes-csi site's CSI Sidecar Containers page and each sidecar's own README; in the Kubernetes docs, CSIDriver and VolumeAttachment in the API reference.

    I10.11

    Mini project — volman.py, a volume manager in two hundred lines

    Why it matters

    Every claim this module has made is testable by writing the thing. A volume manager that creates named volumes, enforces a size limit, attaches them to containers and survives container deletion is about two hundred lines — and writing it is what turns "a volume is a bind mount plus bookkeeping" from a slogan into something you have proven.

    What you are building

    volman.py keeps volumes under /var/lib/volman: an ext4 image per volume for a real size limit, a JSON file for the bookkeeping, and one function per CSI call. The verbs are deliberately named after the contract from I10.8, so the program is also a restatement of it:

    volman verbstands in fordoes
    createCreateVolume (Controller)truncate + mkfs.ext4 on an image file
    stageNodeStageVolume (Node)loop-mount it once, at a global path
    attachNodePublishVolume (Node)add one entry to a bundle's config.json
    detachNodeUnpublishVolumeremove that entry
    unstageNodeUnstageVolumeunmount the global mount
    rmDeleteVolume (Controller)delete the image — refusing while referenced

    The one place it deliberately does better than the reference driver is rm: I10.9 showed DeleteVolume destroying a volume out from under two live mounts, so volman rm refuses while anything still holds it.

    Lab
    1. Create a volume. Nothing is mounted and no container exists — this is a Controller operation and could have happened on another machine entirely. 
      sudo python3 volman.py create appdata --size 32M
sudo python3 volman.py ls
      created appdata (32M) -> /var/lib/volman/images/appdata.img
NAME         SIZE   USED     STAGED                             PUBLISHED
appdata      32M    -        -                                  0
    2. Attach it to a container. Staging happens automatically first, exactly as the kubelet would do it. 
      sudo python3 volman.py attach appdata ~/i10/a --dest /data
sudo jq -c '.mounts[-1]' ~/i10/a/config.json
      staged appdata at /var/lib/volman/mnt/appdata
attached appdata -> /data in /home/ubuntu/i10/a/config.json
{"destination":"/data","type":"bind","source":"/var/lib/volman/mnt/appdata","options":["rbind","rw"]}

      That last line is I10.4's mounts entry, written by a program instead of by hand. There is nothing else to a volume.

    3. Run the container and write to it. The size the container sees is the loop device's, not the host's. 
      cd ~/i10/a && sudo runc run boxa
      /dev/loop1               26.0M     24.0K     23.7M   0% /data
total 20
-rw-r--r--    1 root     root            21 Jul 31 03:01 ledger.txt
drwx------    2 root     root         16384 Jul 31 03:01 lost+found

      lost+found is a nice tell: this is a real ext4 filesystem, not a directory pretending to be one.

    4. Destroy the container completely — delete its bundle, rootfs and all — and check the volume. 
      sudo runc delete -f boxa && sudo rm -rf ~/i10/a
sudo runc list
sudo python3 volman.py ls
      ID          PID         STATUS      BUNDLE      CREATED     OWNER
NAME         SIZE   USED     STAGED                             PUBLISHED
appdata      32M    28K      /var/lib/volman/mnt/appdata        1

      No containers exist. The volume does, with the data in it.

    5. The payoff: a second, entirely unrelated container mounts the same volume at a different path and reads the first one's data. 
      sudo python3 volman.py attach appdata ~/i10/b --dest /shared
cd ~/i10/b && sudo runc run boxb
      container A was here

      That is the whole value proposition of a volume, demonstrated end to end in about a hundred lines of Python and two mount calls.

    6. Check the size limit is real rather than advisory, by overrunning it. 
      …  # dd if=/dev/zero of=/shared/fill bs=1M count=100
      26533888 bytes (25.3MB) copied, 0.030787 seconds, 821.9MB/s
/dev/loop1               26.0M     25.3M         0 100% /shared

      The write stopped at the filesystem boundary. This is why the project uses a loop image rather than a plain directory: it is the only way to give a bind mount a size that means something.

    7. Try to delete it while it is in use. 
      sudo python3 volman.py rm appdata
      volman: appdata is still published to ['/home/ubuntu/i10/a', '/home/ubuntu/i10/b']
    8. Now the interesting failure, which happened by accident the first time this ran and was kept. Bundle a was deleted from disk in step 4 without ever being detached, so the volume is pinned by a reference to a container that no longer exists. 
      sudo python3 volman.py detach appdata ~/i10/b
sudo python3 volman.py unstage appdata
sudo jq -c '.appdata.published' /var/lib/volman/volumes.json
ls -d ~/i10/a
      detached appdata from /home/ubuntu/i10/b
volman: appdata is still published to ['/home/ubuntu/i10/a']
["/home/ubuntu/i10/a"]
ls: cannot access '/home/ubuntu/i10/a': No such file or directory

      A PersistentVolumeClaim stuck Terminating on a finalizer, in miniature: the bookkeeping holds a reference the world no longer contains, and the delete blocks until somebody removes it. That is not a bug in the design — it is the design working, and it is exactly why kubectl patch-ing finalizers off a PVC is such a dangerous habit.

    9. Drop the stale reference and finish the teardown in spec order. 
      sudo python3 volman.py detach appdata ~/i10/a
sudo python3 volman.py unstage appdata
sudo python3 volman.py rm appdata
sudo python3 volman.py ls
      detached appdata from /home/ubuntu/i10/a
unstaged appdata
deleted appdata
no volumes
    Verify

    Your volume manager creates a volume with a size that is enforced, attaches it to two containers in turn, survives the complete destruction of the first, refuses to delete a volume in use, and tears down cleanly leaving no mounts and no image file. If you wrote it yourself, check that stage is idempotent — running it twice must do no work the second time, because the spec requires that of NodeStageVolume.

    Gotchas
    • Write the state file atomically. volman.py writes to a temporary file and os.replaces it. A volume manager interrupted mid-write with a truncated JSON file has lost every volume it manages — and this is precisely why containerd's metadata store is the one with no upstream to rebuild from.
    • os.path.ismount is the check, not the state file. Trusting your own record of "staged" across a reboot means trying to bind from a path with nothing mounted at it, which succeeds and gives the container an empty directory.
    • Refuse, do not clean up. It is tempting to make rm unmount and detach automatically. The reference driver's willingness to delete a mounted volume is the failure in I10.9; refusing is the better contract.

    You have now built, at small scale, what a StorageClass plus a provisioner plus the kubelet do together (W5.8, W5.10). The volumes.json file is etcd's job; the published list is what finalizers protect; stage and attach are the two calls the kubelet makes. Nothing in the Kubernetes storage stack is a different kind of thing from this — there is simply a great deal more of it, distributed, and with an API in front.

    Docs: man 8 losetup and man 8 mkfs.ext4; the CSI spec's volume lifecycle diagram, to check your verb ordering against.

    I10.12

    Debugging drill — the empty directory and the uid from nowhere

    Why it matters

    Both faults below produce symptoms that point away from the cause. One shows an empty directory where a filesystem is unquestionably mounted; the other refuses a write on behalf of a user that appears in no /etc/passwd on either side. Neither is guessable — both are readable, from evidence you now know how to collect.

    Fault 1 — the storage is mounted and the container sees nothing
    1. The setup is the CSI arrangement in miniature: a volume bound into a container, and then a "node plugin" (here, the host) mounting the real storage underneath that path afterwards. 
      sudo mount --bind ~/i10-drill ~/i10-drill && sudo mount --make-rshared ~/i10-drill
#  … container started with the volume mounted rprivate  …
sudo mount -t tmpfs tmpfs ~/i10-drill/data
echo "the-real-data" | sudo tee ~/i10-drill/data/payload.txt
    2. The host is completely satisfied that the data is there. 
      ls -l ~/i10-drill/data
      -rw-r--r-- 1 root root 14 Jul 31 09:03 payload.txt
    3. The application disagrees. 
      sudo runc exec drillbox sh -c 'ls -la /vol/data; df -h /vol/data | tail -1'
      total 8
drwxrwxr-x    2 1000     1000          4096 Jul 31 03:03 .
drwxrwxr-x    3 1000     1000          4096 Jul 31 03:03 ..
/dev/sda1                18.3G      8.9G      9.4G  48% /

      An empty directory, and — the giveaway — df reports the root filesystem rather than a tmpfs. The container is not looking at a broken mount; it is looking at the directory that existed before anything was mounted over it.

    4. Collect the evidence that names the fault: the same filter against both mount tables. 
      grep " $HOME/i10-drill/data " /proc/self/mountinfo
sudo runc exec drillbox sh -c 'grep " /vol/data " /proc/self/mountinfo || echo "  (no such mount in this namespace)"'
sudo runc exec drillbox sh -c 'grep " /vol " /proc/self/mountinfo | sed "s/ - .*//"'
      256 93 0:52 / /home/ubuntu/i10-drill/data rw,relatime shared:261 - tmpfs tmpfs rw,inode64
  (no such mount in this namespace)
440 417 8:1 /home/ubuntu/i10-drill /vol rw,relatime            ← no propagation tag at all
      Diagnosis

      The mount exists on the host and does not exist in the container's mount namespace, so it is not a storage problem at all — the mount event never propagated. The container's /vol line carries neither shared: nor master:, which is rprivate: nothing crosses in either direction. The fix is mountPropagation: HostToContainer (rslave), after which the same line reads master:1 and the tmpfs appears inside. This is precisely why CSI node plugins need propagation configured on the kubelet directory, and the fault is only visible by comparing the two mount tables — every single-sided view looks correct.

    5. The reverse case is the same mechanism and is worth reproducing too: with rprivate, a mount made inside the container is invisible on the host. That version bites when a container is expected to expose something to the node, and the diagnosis is identical.
    Fault 2 — permission denied, on a uid that exists nowhere
    1. The volume, from the host's point of view, belongs to a perfectly ordinary numeric owner. 
      ls -ln ~/i10-drill2
getent passwd 5000 || echo "no - it is only a number here"
      -rw-rw-r-- 1 5000 5000 11 Jul 31 09:08 app.conf
no - it is only a number here
    2. The container runs in a user namespace, as a hardened workload does. Watch what it sees. 
      unshare --user --map-users=0:100000:65536 --map-groups=0:100000:65536 -- \
  sh -c 'cat /proc/self/uid_map; ls -ln ~/i10-drill2; ls -l ~/i10-drill2;
         touch ~/i10-drill2/write-test; cat ~/i10-drill2/app.conf'
               0     100000      65536
-rw-rw-r-- 1 65534 65534 11 Jul 31 09:08 app.conf
-rw-rw-r-- 1 nobody nogroup 11 Jul 31 09:08 app.conf
touch: cannot touch '/home/ubuntu/i10-drill2/write-test': Permission denied
app config
      Diagnosis

      The container maps container uids 0–65535 onto host uids 100000–165535. The file's owner, host uid 5000, is outside that map, so it has no representation inside the namespace at all and the kernel substitutes the overflow uid — 65534, displayed as nobody. The number appears in no /etc/passwd on either side: on the host 5000 is unnamed, and inside, 65534 is a placeholder meaning "unmappable", not a user. Reading still works because the file is world-readable; writing does not, because ownership cannot match. The fixes are the ones Kubernetes offers — fsGroup to chown the volume into a range the container can use (with the cost measured in I10.9), a matching runAsUser, or an idmapped mount so the kernel translates ownership at the mount rather than on disk.

      cat /proc/sys/kernel/overflowuid  →  65534
    3. Contrast, and a note on this machine: mapping yourself to root inside a namespace is refused here, while the subuid-backed path above works. 
      unshare --user --map-root-user -- id
      unshare: write failed /proc/self/uid_map: Operation not permitted

      Two different mechanisms: --map-users goes through the setuid helper newuidmap and is authorised by /etc/subuid; --map-root-user writes uid_map directly. On Ubuntu 24.04 the second is blocked in this configuration — the same class of unexplained EPERM as I1.4's AppArmor wall, and worth recognising before it is mistaken for a storage fault.

    Verify

    For fault 1 you can produce, in two commands, the evidence that a mount exists on the host and not in the container, and name the propagation setting that caused it. For fault 2 you can explain where 65534 comes from without looking it up, and name three different fixes with their costs.

    Gotchas
    • Neither fault produces a useful error message. Fault 1 produces no error at all — an empty directory is not an error condition. Fault 2's message names a path, not the mapping that caused it.
    • Both faults look like the storage system failed. Both are entirely local to the node, and neither would be improved by anything the storage vendor could do.
    • A nobody-owned file is a symptom with exactly one cause family. An unmapped id — from a user namespace, or from NFS squashing. It is never corruption, and chowning it on the host without changing the map does not help.

    Fault 1 is the classic CSI-driver-on-a-misconfigured-node incident and connects straight to W5.12's mount trace. Fault 2 is what a securityContext with runAsUser or a user-namespaced pod meets when it is handed a volume that was written by something else — the reason fsGroup exists, and the reason it is applied at stage time rather than per pod.

    Docs: man 7 user_namespaces, sections on uid_map and the overflow ids; man 8 mount on shared subtrees; in the Kubernetes docs, fsGroup, fsGroupChangePolicy and user namespaces for pods.

    Quiz

    1. A pod has no volumes, no PVC, and a 256 MiB memory limit. It fills the node's disk. Where did the bytes go, and which of the three storages is that?
      Answer

      Into its writable layer — the overlay upperdir, one per container, private and unlimited unless ephemeral-storage limits are set. It is destroyed with the container and recoverable from nowhere, which is why the usual cause (a log file written inside the container) loses the logs as well as filling the node.

    2. A container appends one byte to a 4 MB file that came from its image. How much does its writable layer grow, and why?
      Answer

      By the whole 4 MB — measured here as 12 bytes to 4,498,781. Overlayfs cannot modify a file in a read-only lower layer, so the first write triggers a copy-up of the entire file before the change is applied. The cost is the file's size, never the change's.

    3. Why does crictl imagefsinfo sometimes report a few megabytes on a node whose snapshotter directory holds gigabytes?
      Answer

      Because it counts only what the CRI created. Snapshots made by ctr, or in another containerd namespace such as buildkit, are on the same filesystem and invisible to it — measured here as 9,986,048 bytes reported against 2.3 GB on disk. The kubelet's eviction input has the same blind spot.

    4. What is a volume, at the runtime layer, in one sentence?
      Answer

      One entry in config.json's mounts array — source, destination, type, options, handed to mount(2) — plus a directory that somebody else manages. A stock bundle has seven mounts, all kernel plumbing; a volume is the eighth.

    5. A container writing into an emptyDir: {medium: Memory} is killed with exit 137 and a dmesg line about a memory cgroup. Nothing allocated that much memory. Explain.
      Answer

      A tmpfs is memory. Its pages are charged to the cgroup of the process that wrote them, so filling it consumes the container's memory limit and the OOM killer ends the process. The tmpfs will happily advertise half of RAM in df — 1.9 GB here against a 128 MiB limit — because the filesystem and the cgroup know nothing about each other.

    6. Why can that same OOM kill show up as exit status 0?
      Answer

      If the write is in a shell pipeline, the exit status is the last command's. Measured: identical writes gave 137 unpiped and 0 piped into tail. In Kubernetes that means no OOMKilled reason and no restart under restartPolicy: OnFailure.

    7. Reading a mountinfo line for a volume inside a container, how do you tell which mountPropagation produced it?
      Answer

      No tag means rprivate (None); master:N means rslave (HostToContainer); shared:N with N matching the host's peer group means rshared (Bidirectional). Beware shared:246 master:1 — that is a slave that shares only with itself, which is what you get when the mount asks for rshared but rootfsPropagation is left at slave.

    8. Sort these into services and order them: NodePublishVolume, CreateVolume, NodeStageVolume, ControllerPublishVolume.
      Answer

      CreateVolume (Controller) → ControllerPublishVolume (Controller) → NodeStageVolume (Node) → NodePublishVolume (Node). The spec's state machine names the states between them: CREATED, NODE_READY, PUBLISHED. Controller calls run anywhere; Node calls must run on the pod's node, because they perform mount(2).

    9. Three pods on one node share a ReadWriteOnce volume happily, and a fourth pod on another node cannot get it. Why is that consistent?
      Answer

      Because the access mode is about nodes. The volume is staged once per node — the expensive step — and published once per pod as a cheap bind mount off that staging path. Any number of pods can be published on the node where it is staged; a second node would require a second stage, which RWO forbids.

    10. A PVC is stuck Pending with no PersistentVolume. A different pod is stuck ContainerCreating with a mount error on one node. Which component do you read for each?
      Answer

      The first is the Controller side — external-provisioner calling CreateVolume, running in the driver's Deployment. The second is the Node side — the kubelet calling NodeStageVolume/NodePublishVolume against the driver's DaemonSet pod on that node. Different pods, different logs, and the split is by where the work must run.

    11. Which sidecar makes the mount calls?
      Answer

      None. The kubelet calls the Node service itself. node-driver-registrar only tells the kubelet the driver exists — and it makes no Kubernetes API calls at all, needing no RBAC; it registers over a socket under /var/lib/kubelet/plugins_registry/.

    12. A pod shows an empty directory where a CSI volume should be, and the node shows the filesystem correctly mounted at the same path. What do you check, and with what?
      Answer

      Mount propagation, by grepping the same path in both /proc/self/mountinfo tables — the host's and the container's. If the mount exists in one and not the other, no storage component failed; the mount event did not cross the namespace boundary. The container's line for the parent volume will carry no propagation tag.

    13. A volume's files show as owned by nobody inside a container and writes fail. What is the one cause family?
      Answer

      An unmapped id. The owning uid falls outside the container's user-namespace map, so the kernel substitutes the overflow uid, 65534. It is never corruption. Fixes: fsGroup (a recursive chown, measured at 5.74 s per 500,000 files on local ext4), a matching runAsUser, or an idmapped mount.

    14. Why is it dangerous to remove a PersistentVolume's finalizer to unstick a delete?
      Answer

      Because DeleteVolume does not check whether the volume is still mounted anywhere — measured here, it destroyed a volume with two live pod mounts, which then pointed at //deleted and could no longer be unpublished, since the driver had forgotten the volume. The finalizer is the thing holding the delete until the node side has finished; removing it is removing the check.
