    I10 — Container storage: volumes, snapshots, the CSI shape

    The third contract, and the one with the least mystery in it: a volume at the runtime layer is a bind mount plus some bookkeeping. Get that sentence properly earned and Kubernetes storage becomes a naming and orchestration layer over mechanics you already have.

    Storage is where Kubernetes vocabulary is thickest — PersistentVolume, PersistentVolumeClaim, StorageClass, provisioner, attacher, stage, publish — and where the machinery underneath is thinnest. Nearly all of it reduces to three things you have already built: a directory, mount(2), and a program keeping a record of which is which. This module spends its five hours proving that, ending with a real CSI driver you drive by hand over its socket, and a hundred-line volume manager of your own.

    Checkpoints12 Hours~5 PrerequisitesI7 · B5
    • Name a container's three storages, find each one physically on the node, and say which survives what.
    • Add a volume by hand — one entry in config.json's mounts array — and tell a bind, a tmpfs and a real block device apart by how each one fails.
    • Work mount propagation in both directions, and explain from the mount table alone why mountPropagation: HostToContainer exists.
    • Drive a real CSI driver over its socket: Identity, Controller, Node, and the four calls that matter.
    • Explain stage versus publish well enough to predict which component failed from the symptom.

    I7 (snapshots and where the writable layer lives) and B5 (VFS, mounts, overlayfs, propagation, loop devices — you will reuse that module's disk.img trick).

    Which machine. Everything below ran on sandbox, the Ubuntu 24.04 VM carrying the intermediate toolchain: kernel 6.8.0-136-generic, containerd 2.3.3, runc 1.5.1, crictl v1.36.0, plus registry.k8s.io/sig-storage/hostpathplugin:v1.18.0 and the CSI spec at v1.13.0 for the second half.     A container's three storages

    I10.1

    Three storages, and only one of them is a volume

    Why it matters

    Nearly every storage question in Kubernetes is really one question wearing a disguise: which of the three storages is this? A container has exactly three, they behave completely differently, and confusing them produces the two most baffling incidents on the list — a pod with no volumes filling a node's disk, and data that vanishes on a restart nobody ordered.

    The concept

    Every running container reads and writes through three separate things stacked into one apparent filesystem.

    The image layers. Read-only, shared between every container started from that image, owned by the snapshotter. Ten pods from one image cost one copy on the node, and every byte is re-fetchable from a registry at any time. This is B5's overlayfs lowerdir stack, and I7.11 is where you last saw the directories.

    The writable layer. One per container, private to it, unshared. It is the overlay's upperdir — every file the container creates or modifies lands here. It is counted against the node's ephemeral storage, it is destroyed with the container, and it is recoverable from nowhere at all. No registry has a copy, because it never came from one.

    Mounts from outside. Anything the runtime was told to mount into the container from elsewhere: a host directory, a tmpfs, a real block device. This is the only category whose lifetime is independent of the container, and everything a pod spec calls a volume is one of these.

    Hold on to that last sentence. emptyDir, hostPath, a ConfigMap projection, a PVC backed by a cloud disk — at the runtime layer these are all the third category, differing only in who created the directory and what they put in it before the mount happened.

    image layersshared, re-fetchablewritable layerprivate, gone with the containeroutside mountsindependent lifetime

    It is worth noticing what the runtime spec does not say. There are no layers in it, no sharing, no snapshotter — the root filesystem is one directory, and everything about layering is an invention of the layer above.

    **`root`** (object, OPTIONAL) specifies the container's root filesystem.
    […]
    * **`path`** (string, REQUIRED) Specifies the path to the root filesystem for the container.
    […] The value SHOULD be the conventional `rootfs`.

    A directory MUST exist at the path declared by the field.
    OCI Runtime Specification v1.3.0 — config.md § Root

    Verify

    For any running container you can now name its three storages, print the two snapshotter paths from a single command, and say without hesitating which one survives ctr container rm, which one survives a node rebuild, and which one exists only because someone asked for it in a spec.

    Gotchas
    • The content store is a fourth thing, not one of the three. It holds compressed blobs as pulled; the snapshotter holds them unpacked and mountable. Both live under /var/lib/containerd and neither is a volume. Deleting an image frees the first; only deleting containers frees the second.
    • "Shared" means shared bytes, not a shared directory. The lowerdir is one path on disk that many containers mount simultaneously. Nothing is copied per container until something writes — which is I10.3.
    • The numbers move under you. du on a live snapshot tree races with running containers. Take the measurement twice if it matters.

    A pod's volumes: list is the third category, exclusively. W5.1 walks the ephemeral kinds — emptyDir, hostPath, ConfigMap and Secret projections — and W5.2 shows where the kubelet puts them on the node, under /var/lib/kubelet/pods/<uid>/volumes/. Neither of the other two storages is nameable in a pod spec at all: you influence the image layers by choosing an image, and the writable layer only through ephemeral-storage limits.

    Docs: search the OCI runtime spec for root and readonly; the containerd docs for snapshotters; and in the Kubernetes docs, ephemeral storage under node-pressure eviction.

    I10.2

    The pod with no volumes that fills the node

    Why it matters

    A pod with no volumes, no PVCs and a perfectly modest memory limit can fill a node's disk and get itself — and its innocent neighbours — evicted. Nothing limits how much a container writes into its own root filesystem unless somebody set an ephemeral-storage limit, and almost nobody does. The usual culprit is not application data but a log file written inside the container, which the CRI also cannot show you through kubectl logs. Worst of both worlds, from one mistake.

    The concept

    The writable layer is an ordinary directory on the node's filesystem. There is no quota on it, no reservation, and no accounting the container can see. df inside the container reports the host's filesystem, because that is genuinely what it is writing to. So a container that writes 300 MB writes 300 MB of the node's disk, and it does so through a path with no gate on it.

    What makes this hard to diagnose is that the accounting is split. The kubelet learns about disk usage through the CRI, and — as the lab shows — the CRI reports only the containers it created. A node whose disk is full of snapshots made by ctr, or by a build in another containerd namespace, will report a comfortable few megabytes while du screams.

    The CRI splits its answer in two, and the split is exactly the distinction this lesson turns on: images are shared and re-fetchable, container writable layers are not.

    // ImageFsInfo returns information of the filesystem that is used to store images.
    rpc ImageFsInfo(ImageFsInfoRequest) returns (ImageFsInfoResponse) {}
    Kubernetes CRI, runtime.v1 — api.proto; the response carries image_filesystems and container_filesystems separately
    Lab

      sudo ctr -n k8s.io container rm i10b

  if sudo test -d "$UP"; then echo "  +$((i*200))ms  still there"; else echo "  +$((i*200))ms  GONE"; break; fi

    You can state where a container's writes physically land, produce the file from the host with one ls, show the number the kubelet would evict on, and explain why that number can disagree with du by two orders of magnitude on a busy node.

    Gotchas
    • crictl imagefsinfo nests its answer under .status. A jq filter of .imageFilesystems[0] silently yields null, which reads like an empty node rather than a wrong query. This cost a round while writing this page.
    • A container made with ctr is invisible to CRI accounting even in the k8s.io namespace. Writing 300 MB through ctr moved imagefsinfo by exactly zero bytes; the same write through crictl moved it by 314 MB. The CRI reports on what it created, not on what is in the namespace.
    • Deletion is asynchronous. Check once, immediately after container rm, and the upperdir is still on disk — it went away at +800 ms here. A monitoring check written that way reports a leak that does not exist.
    • Container filesystem stats are windowed. crictl stats right after a write shows the old value. The twelve-second sleep in the lab is not decoration.

    This is the mechanism under node disk pressure and the ephemeral-storage request and limit. W6.12 reads DiskPressure from the node's side, and W6.2 is where logs physically live — the other half of the logging mistake. W5.1 specifies emptyDir, which lands on this same filesystem and is charged the same way. The fix for the logging case is not a bigger disk: it is not writing logs to a file inside the container, so that both this problem and the kubectl logs one disappear together.

    Docs: in the Kubernetes docs, search node-pressure eviction and local ephemeral storage; for the runtime side, crictl stats and crictl imagefsinfo in the cri-tools documentation.

    I10.3

    Shared until you write: copy-up and its price

    Why it matters

    Two facts that sound unrelated have the same cause. Starting a hundred pods from one image is nearly free. Opening a two-gigabyte file inside a container for writing is not — it costs two gigabytes before a single byte changes. Both fall out of one rule you already met in B5.14, and being able to derive them rather than remember them is the point of this checkpoint.

    The concept

    Every container from an image mounts the same read-only lowerdir stack and gets its own empty upperdir. Reads fall through the stack until a layer has the file, so unmodified files are read straight from the shared copy — one set of bytes on disk, however many containers.

    Writes are where it changes. Overlayfs cannot modify a file in a read-only lower layer, so the first write to any such file triggers a copy-up: the kernel copies the file in its entirety into that container's upperdir, then applies the write to the copy. The cost is proportional to the file's size, not to the size of the change. Appending one byte to a four-megabyte library copies four megabytes.

    This is why a container that opens a large data file read-write pays for it at open time, in disk and in latency, and why the same container reading that file pays nothing. It is also why "the image is only 200 MB" tells you nothing about what the container will cost on the node.

    Copy-up is kernel behaviour, not a container standard — no OCI document mentions it. The authority is the overlayfs documentation, and it is explicit that the copy precedes the change.

    When a file in the lower filesystem is accessed in a way that requires write-access, such as opening for write access, changing some metadata etc., the file is first copied from the lower filesystem to the upper filesystem (copy_up).
    […]
    The copy_up may turn out to be unnecessary, for example if the file is opened for read-write but the data is not modified.
    Linux kernel documentation — filesystems/overlayfs.rst

    You can explain from the copy-up rule — not from memory — why a hundred pods from one image cost one copy of it, why c1's one-byte append cost 4,498,769 bytes, and why the answer would have been the same had the file been a gigabyte.

    Gotchas
    • Copy-up is triggered by intent, not by change. Opening for write is enough; so is chmod or touch. A process that opens a large file read-write and writes nothing still pays in full.
    • Alpine's busybox find does not accept -size +1M. Combined with 2>/dev/null it fails silently and hands you an empty variable — which is precisely how the first attempt at this lab produced a plausible-looking wrong answer. Select from the host side.
    • Sharing is per layer, not per image. Two images built on the same base share the base's snapshots and nothing above. This is why rebasing images onto a common parent is a real disk optimisation on a busy node.

    This is the whole reason a node can run many pods of one image cheaply, and it sets the honest cost model for emptyDir versus writing into the container filesystem — see W5.1. It is also why databases and anything else that rewrites large files in place belong on a volume (W5.3) rather than in the container's own filesystem: on a volume there is no lower layer, so there is no copy-up.

    Docs: the kernel's overlayfs documentation, sections Non-directories and Multiple lower layers; and B5.14, where you did this by hand with three directories.

    Volumes at runtime level

    I10.4

    A volume is one entry in the mounts array

    Why it matters

    The word "volume" suggests an object — something created, tracked, owned. At the runtime layer there is no such object. There is an array in a JSON file and a directory somebody manages. Once you have added one by hand, the entire Kubernetes storage stack reads as elaborate bookkeeping around a field you can type yourself.

    The concept

    The runtime spec's mounts array is a list of mount(2) arguments — source, destination, type, options — that the runtime executes inside the container's mount namespace after pivot_root. That is the whole mechanism. Everything the ecosystem calls a volume is built on it:

    • a Docker named volume is a directory under /var/lib/docker/volumes plus a name in a database;
    • a Kubernetes emptyDir is a directory under /var/lib/kubelet/pods/<uid>/volumes/ that the kubelet creates and deletes;
    • a PVC-backed volume is the same again, with a CSI driver having mounted something there first.

    The orchestration around each of those is elaborate and genuinely valuable — it is what makes a volume follow a pod across nodes, survive a reschedule, and be requested declaratively. The runtime-level primitive it all lands on is one line of JSON.

    The spec is unusually blunt here: it does not define volume semantics at all, it defers to the mount(2) man page and specifies only the ordering.

    **`mounts`** (array of objects, OPTIONAL) specifies additional mounts beyond [`root`](#root).
    The runtime MUST mount entries in the listed order.
    For Linux, the parameters are as documented in [mount(2)][mount.2] system call man page.
    OCI Runtime Specification v1.3.0 — config.md § Mounts

    "In the listed order" is load-bearing: mounts that nest inside one another only work one way round, and a runtime is required to respect what you wrote rather than sort it for you.

    Lab
    1. Build a bundle the I2.3 way and look at what a container gets before anyone adds a volume. 
      mkdir -p ~/i10/vol/rootfs && cd ~/i10/vol

      Seven mounts, every one of them kernel plumbing. None of them is storage in any sense a user would recognise.

      mkdir -p ~/i10-vol

    3. Add the eighth mount. This is the entire feature. 
      jq --arg src "$HOME/i10-vol" \
  '.mounts += [{"destination":"/data","type":"bind","source":$src,"options":["rbind","rw"]}]' \
  config.json > config.new && sudo mv config.new config.json

  "type": "bind",

    4. Run it. The container reads what was there, appends, and reports how the kernel sees the mount. 
      sudo runc run volbox
      data that outlives containers

      The mountinfo line is worth reading slowly: inside the container, /data is a subtree of the host's ext4 root filesystem on /dev/sda1. There is no volume driver, no indirection, and nothing that would look different to the kernel from any other bind mount.

    5. Delete the container and check what survived. 
      sudo runc list

      ID          PID         STATUS      BUNDLE      CREATED     OWNER

      No containers exist. The data does, including the line written by PID 1 inside the one that is gone. That gap — between the lifetime of the container and the lifetime of the bytes — is the only thing a volume actually provides.

    Verify

    You can add a volume to a container without any tool that knows the word "volume", and you can point at the exact JSON that makes emptyDir, hostPath and a PVC mount identical from the runtime's point of view.

    Gotchas
    • Order matters and the runtime will not fix it. The spec says entries are mounted in the order listed. Mount /data/inner before /data and the first one disappears under the second.
    • rbind and bind are not the same. rbind brings along mounts nested under the source; plain bind brings only the top one, so a volume containing another mount arrives mysteriously empty at that sub-path.
    • A bind mount has no size of its own. It is the host filesystem, so df inside the container reports the host's free space and no limit applies — the subject of I10.5.

    W5.2 walks the kubelet's side of exactly this: every pod volume becomes a directory under /var/lib/kubelet/pods/<uid>/volumes/, and the container's generated config.json gets one mounts entry per volumeMounts entry. The subPath field, which surprises people by being resolved on the node rather than by the storage system, is nothing more than a longer source in that JSON.

    Docs: the OCI runtime spec's Mounts section and man 2 mount; in the Kubernetes docs, volumes and volumeMounts under the pod spec reference.

    I10.5

    Three things you can mount, told apart by how they fail

    Why it matters

    A bind, a tmpfs and a real filesystem on a block device all arrive as a directory inside the container and look identical to the application. They are not remotely identical, and the cleanest way to tell them apart is to fill each one until something breaks. One of them gets your container OOM-killed with a message about memory and no mention of storage anywhere.

    The concept

    A bind is part of the host's filesystem, so it has no size of its own. df inside the container reports the host's free space, and nothing enforces a limit — which is why size limits on ordinary bind mounts are so awkward, and why the mini project in I10.11 reaches for a loop image to get one.

    A tmpfs is memory pretending to be a filesystem. The pages are page cache, and — this is the part that catches people — they are charged to the cgroup of the process that wrote them. So filling a tmpfs mounted into a container consumes that container's memory limit. Fill it past the limit and the kernel's OOM killer ends the process, reporting a memory problem, because from the kernel's point of view it is one. B7's OOM lesson (B7.9) arriving from an unexpected direction.

    A real filesystem on a block device is the only one of the three with genuine quota semantics: its own superblock, its own free-space accounting, its own ENOSPC. Fill it and the write fails, the process handles it or does not, and nothing gets killed.

    bindfills the nodetmpfsOOM-kills the containerblock deviceENOSPC, container lives

    The spec allows all three through the same field — the difference is entirely in type and options, which it hands to mount(2) without interpretation.

    * **`type`** (string, OPTIONAL) The type of the filesystem to be mounted.
    * Linux: filesystem types supported by the kernel as listed in /proc/filesystems (e.g., "minix", "ext2", "ext3", "jfs", "xfs", "reiserfs", "msdos", "proc", "nfs", "iso9660"). For bind mounts (when `options` include either `bind` or `rbind`), the type is a dummy, often "none" (not listed in /proc/filesystems).
    OCI Runtime Specification v1.3.0 — config.md § Mounts

    Gotchas
    • A tmpfs's advertised size is not the limit that will kill you. Without size=, Linux offers half of RAM — 1.9 GB here — while the cgroup limit was 128 MiB. Both numbers are real; only one is enforced against the container.

    • Root in a container cannot necessarily write to a bind mount. Adding that one capability changed nothing else and made the write succeed. This is B4.10 arriving as a storage bug, and it is half of the drill in I10.12.
    • Appending to an existing root-owned file still works in that situation, because the check is on the directory for creation and on the file for writing. A volume that appears writable for one file and not for another is this, not corruption.

The block-device case is what a real CSI-provisioned volume gives you, and the reason a PVC has a size that means something.

    I10.6

    Mount propagation, and why HostToContainer exists

    Why it matters

    B5.12 taught propagation as kernel mechanics. Here is what it is for. A CSI node plugin runs as a pod and mounts a volume into a host path; the workload pod must see that mount appear inside a directory it already has mounted. Under the wrong propagation that is impossible, and the symptom is uniquely maddening: an empty directory where a filesystem plainly is mounted, one namespace over.

    The concept

    A mount is not a fact about a path, it is a fact about a path in a mount namespace. Propagation settings decide whether a mount event crosses between namespaces, and there are three that matter:

    • private — nothing crosses, in either direction.
    • slave — mounts made on the host appear inside the container; mounts made inside stay inside. One-way, downhill.
    • shared — events cross both ways; a mount made inside the container appears on the host.

    Kubernetes exposes exactly these as mountPropagation: None (rprivate), HostToContainer (rslave) and Bidirectional (rshared). Bidirectional requires a privileged container, for the reason the lab makes visible: a container that can create mounts on the host can mount things the node's administrator did not agree to.

    One subtlety decides whether any of this works: the host-side path must itself be a shared mount point. Propagation happens between peers in a peer group, and a plain directory is not in one. This is why a node's kubelet directory is deliberately made shared, and why a CSI driver's manifest asks for Bidirectional on /var/lib/kubelet.

    The runtime spec carries propagation twice — per mount, in options, and once for the whole root filesystem. The second one is the field people miss, and the lab shows it deciding the outcome.

    **`rootfsPropagation`** (string, OPTIONAL) sets the rootfs's mount propagation.
    Its value is either `shared`, `slave`, `private` or `unbindable`.
    It's worth noting that a peer group is defined as a group of VFS mounts that propagate events to each other.
    […]
    * **`private`**: the rootfs mount doesn't receive mount propagation events from the host and further mounts in nested containers will be isolated from the host and from the rootfs (even if the nested container `rootfsPropagation` option is shared).
    OCI Runtime Specification v1.3.0 — config-linux.md § Rootfs Mount Propagation

    Verify

    Shown a mountinfo line, you can say which Kubernetes mountPropagation value produced it by reading the shared: and master: tags, and you can explain why a driver that needs Bidirectional must also be privileged.

    Gotchas
    • The host path must already be a shared mount point. A plain directory has no peer group, so nothing propagates and every test says "no" — with no error to explain it.
    • A bare runc bundle's default is not Kubernetes' default. With no propagation option at all, the volume came out master:1 — a slave, i.e. host-to-container propagation working. Kubernetes' default is None, which explicitly asks for rprivate. Do not test the default and conclude anything about a pod.
    • rootfsPropagation overrules the per-mount option. Asking for rshared on the mount while the rootfs is slave gives you shared:N master:1, which looks shared and behaves like a slave.
    • A mount that escapes onto the host outlives the container. That is the actual risk behind requiring privileged for Bidirectional: nothing unmounts it when the pod goes away.

    This is the whole content of the mountPropagation field, and it is why CSI node plugins are deployed as privileged DaemonSets with Bidirectional on the kubelet directory — see the architecture in W5.11 and the end-to-end mount trace in W5.12. When a pod shows an empty directory where a CSI volume should be, propagation is the first thing to check on the node, before anything about the storage system.

    Docs: the kernel's sharedsubtree documentation; man 8 mount under Shared subtree operations; and in the Kubernetes docs, mountPropagation in the volumeMounts reference.

    The CSI shape

    I10.7

    Why there is an interface here at all

    Why it matters

    By now this story should be predictable, and that is the point of asking it a third time. You have watched the same thing happen to runtimes (CRI) and to networking (CNI). Storage went the same way for the same reason, and once you can see the pattern you can predict where the next interface will appear.

    The concept

    Storage drivers used to live in tree: the code that talked to AWS EBS, GCE PD, Ceph, NFS and a dozen others was inside the Kubernetes repository. Every vendor's bug was a Kubernetes bug, every vendor's fix waited for a Kubernetes release, and every vendor's credentials-handling code ran in the controller manager. Adding support for a new storage system meant getting a pull request merged into Kubernetes.

    CSI replaced that with a contract. A driver is now a separate program speaking a versioned gRPC API; Kubernetes ships a client and some generic controllers, and the vendor ships everything that knows about their storage. The in-tree plugins were migrated behind the same interface and removed.

    Here is the two-sentence version worth remembering: CSI replaced vendor code living inside Kubernetes with a versioned gRPC contract that vendor code implements from outside. That made storage support a matter of installing a driver rather than upgrading Kubernetes — and made every storage system's bugs its own again.

    Notice the shape each interface took, because the shape follows the interaction rather than the subject:

    InterfaceInteraction it supportsShape it took
    CNIone short action per sandbox, then donean exec'd binary, JSON on stdin
    CRIlong-lived, stateful, error-heavygRPC on a unix socket
    CSIlong-lived, stateful, error-heavy, and partly off-nodegRPC on a unix socket, split into three services

    All three are versioned contracts with their own release cycles, and Kubernetes ships a client for each. Once you see that, "how do I add X to Kubernetes" almost always answers itself: find which interface already covers it.

    CSI does not mention Kubernetes in its definitions at all. It speaks of a "CO" — a Container Orchestration system — and Kubernetes is merely one. That abstraction is the whole point of the exercise.

    | Volume | A unit of storage that will be made available inside of a CO-managed container, via the CSI. |
    | CO | Container Orchestration system, communicates with Plugins using CSI service RPCs. |
    | Plugin | Aka “plugin implementation”, a gRPC endpoint that implements the CSI Services. |
    Container Storage Interface v1.13.0 — spec.md § Terminology

    I10.8

    Three services, and the four calls that matter

    Why it matters

    The three-way split is not organisational tidiness — it is a diagnostic map. Learn which service a call belongs to and half of CSI debugging becomes arithmetic: a volume stuck with no PersistentVolume is a Controller problem, a pod stuck ContainerCreating on one node is a Node problem, and those two live in different pods with different logs.

    The concept

    The split is by where the work must run, not by what it does.

    • Identity — who are you, are you healthy, what do you support. Three calls. Every other component asks these first.
    • Controller — cluster-wide operations that talk to a storage API somewhere: create a volume, delete it, attach it to a node. These can run anywhere in the cluster, because they are API calls to a SAN or a cloud provider.
    • Node — operations that perform mount(2), and therefore must run on the machine where the pod will run.

    That is exactly why a CSI driver ships as two workloads: a Deployment for the Controller half and a DaemonSet for the Node half. And it is why the four calls that matter sort the way they do:

    CreateVolumeControllerControllerPublishVolumeControllerNodeStageVolumeNodeNodePublishVolumeNode

    The spec draws the same sequence as a state machine, and it is worth committing to memory because every stuck volume is stuck between two of these boxes.

       CreateVolume +------------+ DeleteVolume
 +------------->|  CREATED   +--------------+
 |              +---+----^---+              |
 |       Controller |    | Controller       v
+++         Publish |    | Unpublish       +++
|X|          Volume |    | Volume          | |
+-+             +---v----+---+             +-+
                | NODE_READY |
                +---+----^---+
               Node |    | Node
            Publish |    | Unpublish
             Volume |    | Volume
                +---v----+---+
                | PUBLISHED  |

    • An unset Probe readiness means ready. The field is a wrapper type precisely so that "not answered" and "answered false" are different. Treating them the same restarts healthy drivers.
    • Capability enums have gaps, and drivers advertise numbers your spec version does not define. Measured here on the reference driver, not a hypothetical. Never call Name() on an unvalidated enum value.
    • A call the driver did not advertise is a call it never receives. The CO checks capabilities and skips; if a driver forgets to advertise STAGE_UNSTAGE_VOLUME, staging is silently not attempted rather than failing loudly.

    W5.11 is this same architecture named from the Kubernetes side, and W5.12 traces one mount end to end on a node — the two paths from the last lab step are exactly what it finds. The Controller/Node split is also why W5.9's WaitForFirstConsumer exists: for topology-constrained storage, the Controller cannot sensibly create the volume until the scheduler has chosen the node.
