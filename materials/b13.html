    B13 — Distributed systems fundamentals

    Every module so far has happened inside one machine. One kernel, one process table, one clock, one filesystem — and one enormous simplification you have been enjoying without noticing: when you call something, it either runs or it does not, and you always find out which. Add a second machine and that guarantee disappears. A request can arrive, be executed perfectly, and have its reply lost on the way back, and the caller has no way to tell that apart from a request that never arrived at all. Almost everything strange about distributed systems grows out of that one sentence.

    If one hotel has been the machine all along, this module is the city: many buildings, no shared switchboard, messages carried between them by runners who sometimes do not come back. You cannot ask "did they get it?" without sending another runner, who may also not come back. So instead of certainty, distributed systems are built out of a small set of compromises — retry, but make the operation safe to repeat; guess at failure with a timeout, and accept that you will sometimes be wrong; require a majority to agree, so two halves of a split can never both act.

    Kubernetes is a very large answer to exactly these problems, which is why this module is the last conceptual one before the capstone. Every piece of it that seems arbitrary at first — why etcd wants three members and never four, why controllers loop forever instead of doing things once, why a node goes NotReady forty seconds after it stops speaking rather than instantly, why kubectl apply can be run ten times without harm — is one of the compromises below, chosen deliberately. Four movements: what changes when there are two machines, state and agreement (replication, consistency, quorum, consensus), the patterns every distributed system converges on, and then a project where you build a controller and a quorum simulation of your own.

    Checkpoints15 Hours~5 PrerequisitesB2, B8, B11

    B2 is the working prerequisite: the reconciler you build supervises real processes, so fork/exec (B2.5), signals (B2.8) and the hand-written supervisor (B2.17) are all directly reused — this module is that supervisor's idea, generalised. B8 matters because the failures here are network failures: a dropped packet, a timeout, a connection that hangs rather than refuses (B8.9), and you will drop traffic deliberately with the packet-filtering tools from B9.11. B11 is how the reconciler graduates from a script into a service (B11.3). Everything runs on the throwaway sandbox VM (B0.1) — this module needs no second machine, because every distributed behaviour here is simulated with processes, files and firewall rules on one box, which is exactly enough to make the mechanisms visible. Nothing needs installing beyond what B8/B9 already added (netcat-openbsd for the partial-failure lab); python3, iptables and timedatectl ship with the system. One lesson deliberately moves the clock backwards, so take a snapshot first (B0.9) if that makes you nervous — the lab puts it back.

    What changes

    B13.1

    Why anyone accepts a second machine at all

    Why it matters

    Distribution is expensive. It brings failure modes that do not exist on one box, it makes debugging harder, and it forces every design decision through questions nobody had to ask before. Knowing the three reasons people pay that price is what lets you tell a system that needed distributing from one that was distributed out of habit — and it explains why a Kubernetes cluster is shaped the way it is.

    The concept

    There are exactly three reasons, and they are worth being able to name:

    • Scale — the work does not fit on one machine. Not "would be faster spread out", but genuinely does not fit: more requests than one box can serve, more data than one disk holds, more CPU than one socket provides. This is the reason people assume is primary and it is often the least common of the three.
    • Availability — the service must survive losing a machine. One machine has a failure probability that no amount of good engineering removes: disks die, kernels panic, someone unplugs the wrong cable, the datacentre loses power. If the service must keep answering through that, there must be another machine already running.
    • Blast radius — one failure should not take everything. Separating workloads onto different machines means a memory leak in one does not evict the other, and a bad deploy takes down one replica rather than the service.

    The availability reason has arithmetic behind it, and the arithmetic is the argument. If one machine is available 99% of the time, two independent machines are both down only 0.01% of the time — 99.99% availability, four hours of downtime a year instead of three and a half days. That word independent is doing enormous work, and it is where real systems fail: two machines in the same rack share a power feed, two replicas on the same node share a kernel, and two datacentres on the same fibre path share a backhoe. Redundancy only multiplies when the failures do not correlate — which is exactly what a Kubernetes anti-affinity rule exists to enforce.

    Note also what distribution costs you in exchange, so the trade is honest: every call that used to be a function call is now a network request that can fail slowly (B13.2); state that used to be a variable now needs replication and agreement (B13.8); and a system that used to have one clock now has none (B13.3). The rest of this module is that bill, itemised.

    scale·availability·blast radius→and the bill: partial failure, no clock, agreement

    Three reasons to say yes; the rest of the module is what you pay.

    Name the three reasons without looking, and for each, name a system you know that has it as its primary reason.     Gotchas

    The commonest mistake is distributing for scale that does not exist. A single modern machine handles a genuinely enormous amount of work — tens of thousands of requests per second, terabytes of disk, dozens of cores — and a distributed version of a system that fits on one box is usually slower, harder to debug and less available, because it has more parts that can fail and a network between them. "We might need to scale someday" is not one of the three reasons.

    The second is treating redundancy as automatically independent. Two replicas scheduled onto the same node, two nodes in the same rack, two zones on the same power grid: each pair fails together, so the arithmetic above quietly does not apply. Every real availability incident with a surprised post-mortem has a correlated failure in it somewhere, and the correlation was usually invisible on the architecture diagram.

    All three reasons are visible in the shape of a cluster. Scale is why a Deployment has a replica count and why nodes are added rather than enlarged. Availability is why the control plane can be run with three or five control-plane nodes rather than one, and why losing a worker is a scheduling event rather than an outage. Blast radius is why pods have resource limits (B7's cgroups, wearing a Kubernetes name), why namespaces exist, and why the scheduler can be told to spread replicas across nodes and zones instead of packing them together — the anti-affinity rule is the "make the failures independent" precondition, written as configuration.

    The two high-availability control-plane topologies, and what the load balancer in front of them is for, is W2.11; spreading replicas so their failures stay independent is W3.13.

    Docs

    This lesson is arithmetic and judgement rather than tooling, so the useful pages are the measuring ones: man 1 nproc, man 1 free and man 1 df for the ceiling, man 1 xargs (the -P flag) for the parallelism demo, and man 1 systemd-detect-virt for what your "independent" machines are actually running on. man 5 systemd.resource-control for the blast-radius controls from B7.11.

    B13.2

    Partial failure: the one fact everything else follows from

    Why it matters

    This is the defining difference between one machine and many, and nearly every other idea in this module is a response to it. On one machine, a function call runs or it does not, and you always know which. Across a network there is a third outcome that has no local equivalent: it might have worked, and you cannot find out. Once you have seen that outcome with your own eyes, retries, idempotency, timeouts and consensus all stop being abstractions.

    The concept

    Send a request to another machine and get no reply. At least four things could have happened:

    • The request never arrived — it was dropped on the way out.
    • It arrived, and the machine died before doing anything.
    • It arrived, was executed completely, and the reply was lost on the way back.
    • It arrived and is still being processed, slowly, and the reply is coming.

    From the caller's position these are identical. There is no observation you can make, and no timeout you can set, that distinguishes them — because the only way to ask "did you get it?" is to send another message, which is subject to exactly the same uncertainty. This is not an engineering shortfall to be fixed with a better protocol; it is a property of communicating over a channel that can lose things.

    Everything follows. Because you cannot know, you must retry — and because a retry may be a second execution of something that already succeeded, the operation must be safe to repeat, which is idempotency (B13.10). Because you cannot wait forever, you need a timeout — and a timeout is a guess, so you will sometimes declare a healthy peer dead (B13.13). Because two nodes may disagree about who is alive, you need a way to agree that a minority cannot override (B13.8). Four ideas, one cause.

    There is a related asymmetry worth naming: the distinction between failed and slow is undecidable. A peer that is merely overloaded looks exactly like a peer that is dead, and this is why every failure detector in every distributed system is, formally, a heuristic that can be wrong.

    no reply→never arrived?·done, reply lost?·still running?→indistinguishable

    The caller cannot tell these apart — so the system must be designed as if all of them are true.

    Lab
    1. Build a "server" that receives a request, records that it did the work, and never replies. This is the executed-but-reply-lost case, made concrete. 
      cd ~ && : > work.log
while true; do nc -l -p 9000 >> work.log; echo "--- executed at $(date +%T)" >> work.log; done &
sleep 1; ss -ltn | grep 9000
      LISTEN 0  1  *:9000  *:*          ← listening; it will read a request and answer nothing
    2. Send a request as a client with a timeout. From the client's seat, this is a failure — it got nothing back. 
      curl -s --max-time 3 http://localhost:9000/charge-card ; echo "curl exit=$?"
      curl exit=28          ← 28 = timeout. The client knows only that no answer came.
    3. Now look at the server's side of the same event. The work was done — the client's conclusion of "it failed" is simply wrong. 
      grep -c 'charge-card' work.log; tail -2 work.log
      1
GET /charge-card HTTP/1.1
--- executed at 09:14:22          ← the card WAS charged. The caller has no way to know.
    4. Produce the other case — a request that genuinely never arrives — and compare what the client sees. Drop the traffic before it reaches the listener (B9.12). 
      sudo iptables -I INPUT -p tcp --dport 9000 -j DROP

grep -c 'charge-card' work.log
      curl exit=28          ← identical symptom, identical exit code
1                      ← but this time nothing was executed: still 1 from step 3
    5. Put the two side by side. Same client observation, opposite server reality — this is partial failure in one screen. 
      echo "case A (reply lost)  : client=timeout(28)  server=executed"
echo "case B (never arrived): client=timeout(28)  server=did nothing"
      case A (reply lost)  : client=timeout(28)  server=executed

                       ↑ identical           ↑ the only place the truth exists
    6. Show the third case too — slow, not dead — because this is the one that makes every timeout a guess. 
      sudo iptables -D INPUT -p tcp --dport 9000 -j DROP
curl -s --max-time 1 http://localhost:9000/slow; echo "client gave up: exit=$?"
sleep 2; tail -1 work.log

--- executed at 09:15:40          ← the server was working the whole time; the client was wrong
    7. Clean up the listener and the log. 
      kill %1 2>/dev/null; pkill -f 'nc -l -p 9000'; rm -f ~/work.log; echo cleaned
      cleaned
    Verify

    List the four things that could have happened when a request gets no reply, and say why no timeout value distinguishes them. Then derive the three consequences out loud, in order: you must retry (because you cannot know), so operations must be safe to repeat; you must time out (because you cannot wait forever), so you will sometimes be wrong about who is dead; and you must have a rule for agreeing when peers disagree. If you can point at your own work.log as evidence for the first one, the lesson has landed.

    Gotchas

    The most dangerous instinct here is to design as though "the request failed" is a fact you were given. It is a conclusion the client drew, and it is wrong roughly as often as the reply-lost case occurs. Payment systems, order systems and provisioning systems all learn this the same way: a client that retries a non-idempotent operation after a timeout charges the card twice, and the logs on both sides look completely reasonable.

    The second is expecting error codes to disambiguate. A connection refused (B8.9) genuinely tells you nothing was executed — that one is informative. But a timeout, a reset mid-response, and a connection that hangs and then dies are all silent about what the far side did. Treat "I received a definite error before the request was processed" and "I received nothing" as two completely different situations, because only the first is actually safe to retry blindly.

    The API server is unusually honest about this problem, and its answer is worth knowing. Every write goes through the same uncertainty — kubectl apply may time out after the object was created — which is precisely why the API is declarative and its operations are idempotent: applying the same manifest again is defined to be harmless, so the retry is safe by construction. For the operations that genuinely cannot be made idempotent, Kubernetes uses optimistic concurrency instead: every object carries a resourceVersion, and an update that names a stale one is rejected with a conflict rather than silently overwriting someone else's change.

    The end-to-end path a write actually takes, and where it can fail on each hop, is W1.3; what still works when etcd itself stops answering — the largest partial failure a cluster can have — is W6.8.

    Docs

    man 1 curl for --max-time and the exit-code table (28 is timeout, 7 is connection refused — the distinction the gotcha rests on). man 1 nc for the throwaway listener. man 8 iptables for the DROP rule that manufactures a lost request; man 7 tcp for what the kernel does while a client waits, and why a dropped SYN produces a long hang rather than an error.

    B13.3

    There is no shared clock

    Why it matters

    "Which of these two events happened first?" is a question you have answered with timestamps your whole career, and across machines it is not reliably answerable that way. Clocks differ, drift apart and occasionally jump backwards when something corrects them. Knowing this is what stops you from debugging a distributed system by sorting two machines' logs together and believing the result.

    The concept

    Every machine has its own clock, and no two agree exactly. Three separate problems stack up:

    • Offset — two clocks read different times right now, typically by milliseconds, sometimes by much more.
    • Drift — they run at slightly different rates, so the offset grows on its own. A cheap oscillator can drift seconds per day.
    • Jumps — when a time daemon corrects the clock it may step it, and a step can go backwards. Time on a machine is not guaranteed to be monotonic.

    That last one is the killer, because it breaks the assumption underneath timestamp ordering. If a clock steps back by two seconds, an event that genuinely happened later can carry an earlier timestamp than one that happened before it — on the same machine, never mind across two.

    Linux offers a way out for measuring durations: two different clocks. CLOCK_REALTIME is wall-clock time, which can be stepped by NTP and by an administrator. CLOCK_MONOTONIC only ever moves forward at a steady rate since boot, and is immune to steps. Rule of thumb worth internalising: use the wall clock only for displaying times to humans; use the monotonic clock for every timeout, deadline and duration. Code that measures an interval with the wall clock will one day measure a negative one.

    For ordering events across machines, neither clock helps, so distributed systems stop using time altogether and use a logical counter instead: a number that increases with every change, whose only meaning is "this came after that". Kubernetes uses this pervasively — etcd's revision, and the resourceVersion on every object, are counters, not times. They can be compared within one cluster and are meaningless anywhere else, which is why you cannot compare a resourceVersion between two clusters, or reason about how long ago a revision was.

    wall clock: display only·monotonic: durations·logical counter: ordering across machines

    Three clocks for three jobs; using the first one for the other two is the classic bug.

    Gotchas

    Measuring a duration with the wall clock is the bug this lesson exists to prevent. Code that records time.time() at the start and end of an operation will, eventually, compute a negative elapsed time or a sixty-second one for something instantaneous — and it will do it rarely enough to be blamed on anything else. Every language has a monotonic clock; use it for every deadline, retry interval and timeout.

    The second is a certificate-shaped one you have already met: clock skew produces errors that look like corruption. A machine whose clock is behind rejects freshly-issued certificates as not yet valid (B12.11), and a node whose clock is far ahead can invalidate tokens the moment it receives them. When exactly one machine in a cluster misbehaves in an inexplicable, security-flavoured way, check timedatectl before anything else.

    Kubernetes avoids wall-clock ordering wherever correctness depends on it. Every object carries a resourceVersion, which is etcd's revision counter — a monotonically increasing integer with no relationship to time. Watches resume from a resourceVersion rather than from a timestamp, which is why a controller that reconnects does not miss changes and does not need the two machines' clocks to agree. The creationTimestamp you see in an object is for humans; nothing in the system orders events with it.

    etcd's revision model — how those counters work, and what compaction does to old ones — is W1.10; where objects actually live under those revisions is W1.8. And the clock-skew certificate failure is W2.6.

    Docs

    man 1 timedatectl for the sync status and timesync-status output. man 2 clock_gettime is the page that defines CLOCK_REALTIME versus CLOCK_MONOTONIC — the whole lesson in one man page. man 5 systemd-timesyncd.conf for what disciplines the clock on Ubuntu, and man 7 time for the general model.

    B13.4

    The eight fallacies, and a latency ladder you have measured yourself

    Why it matters

    The eight fallacies are a checklist of assumptions that feel obviously true, are quietly built into most code, and are all false. Reading them is mildly interesting; matching each one to a failure you personally caused in B8–B10 is what makes them stick. The latency ladder is the numeric half of the same lesson: an intuition for what things cost, so "just call the service again" gets priced correctly.

    The concept

    The list, formulated at Sun Microsystems, is eight assumptions that every distributed system eventually violates:

    • The network is reliable — packets are dropped, links flap, and a message sent is not a message received (B13.2).
    • Latency is zero — a call across a datacentre is roughly a hundred thousand times slower than a local function call, and one across the world is a million.
    • Bandwidth is infinite — it is shared, finite, and the thing your backup job saturates at 02:00.
    • The network is secure — anyone on the path can read and modify unless you did the work in B12.12.
    • Topology doesn't change — pods move, IPs are reused, nodes are replaced. This is why you resolve names instead of caching addresses (B10.11).
    • There is one administrator — the firewall rule you did not know about was added by someone you have not met.
    • Transport cost is zero — serialising, encrypting and copying data costs CPU on both ends, and the wire itself costs money.
    • The network is homogeneous — different MTUs, different hardware, different behaviour, which is exactly the black hole from B8.18.

    The latency ladder gives the second fallacy a number. Orders of magnitude are what matter, not exact figures: a memory reference is ~100 nanoseconds, an SSD read ~100 microseconds (1,000×), a round trip within a datacentre ~0.5 milliseconds (5,000×), a round trip across a continent ~50–100 milliseconds. The practical consequence is that the number of round trips dominates almost everything else. One request that fetches everything beats ten that each fetch a piece, regardless of how fast the far end is, because the round trips do not overlap.

    memory ~100 ns→SSD ~100 µs→same-DC RTT ~0.5 ms→cross-continent ~50 ms

    Each step is roughly a thousand times the last — which is why round trips, not bytes, are the thing to count.

    Gotchas

    The fallacies are seductive because each one is almost true in a lab. On a single machine with loopback networking, the network really is reliable, latency really is negligible, and topology really does not change — so code written and tested there encodes all eight assumptions without anyone noticing. They surface for the first time in production, together, usually during an incident. This is the argument for testing with deliberate failure injection rather than only in the happy environment.

    The second is misreading averages. A mean latency of 11 ms with a tail at 900 ms is a completely different system from a flat 11 ms, and the tail is what your users and your timeouts actually experience. When you have a choice, look at the 99th percentile; a distributed system with many components is dominated by its slowest ones, because a request that touches ten services meets ten chances to hit a tail.

    The latency ladder explains one of the most confusing Kubernetes performance symptoms there is: a slow API server whose real cause is a slow disk. etcd commits every write to disk on a majority of members before acknowledging it (B13.9), so etcd's write latency is bounded by fdatasync on the slowest member of the quorum. Put etcd on a spinning disk or a throttled network volume and every object creation in the cluster pays that cost — the symptom presents as "kubectl is slow", several layers above the actual fault.

    Checking etcd's health, including the latency metrics that make this visible, is W1.13; the wider "the API server is slow or unavailable" ladder is W6.5.

    Docs

    The fallacies have no man page — they are a list worth keeping. For the measurements: man 1 dd (especially iflag=direct, which is what makes it a device measurement rather than a page-cache one), man 8 ping for round-trip statistics, and man 1 curl with -w '%{time_total}' for per-request timing. man 7 tcp explains why the first request to a new connection costs more than the ones after it.
