    B13 — Distributed systems fundamentals

    Every module so far has happened inside one machine. One kernel, one process table, one clock, one filesystem — and one enormous simplification you have been enjoying without noticing: when you call something, it either runs or it does not, and you always find out which. Add a second machine and that guarantee disappears. A request can arrive, be executed perfectly, and have its reply lost on the way back, and the caller has no way to tell that apart from a request that never arrived at all. Almost everything strange about distributed systems grows out of that one sentence.

    If one hotel has been the machine all along, this module is the city: many buildings, no shared switchboard, messages carried between them by runners who sometimes do not come back. You cannot ask "did they get it?" without sending another runner, who may also not come back. So instead of certainty, distributed systems are built out of a small set of compromises — retry, but make the operation safe to repeat; guess at failure with a timeout, and accept that you will sometimes be wrong; require a majority to agree, so two halves of a split can never both act.

    Kubernetes is a very large answer to exactly these problems, which is why this module is the last conceptual one before the capstone. Every piece of it that seems arbitrary at first — why etcd wants three members and never four, why controllers loop forever instead of doing things once, why a node goes NotReady forty seconds after it stops speaking rather than instantly, why kubectl apply can be run ten times without harm — is one of the compromises below, chosen deliberately. Four movements: what changes when there are two machines, state and agreement (replication, consistency, quorum, consensus), the patterns every distributed system converges on, and then a project where you build a controller and a quorum simulation of your own.

    Checkpoints15 Hours~5 PrerequisitesB2, B8, B11

    B2 is the working prerequisite: the reconciler you build supervises real processes, so fork/exec (B2.5), signals (B2.8) and the hand-written supervisor (B2.17) are all directly reused — this module is that supervisor's idea, generalised. B8 matters because the failures here are network failures: a dropped packet, a timeout, a connection that hangs rather than refuses (B8.9), and you will drop traffic deliberately with the packet-filtering tools from B9.11. B11 is how the reconciler graduates from a script into a service (B11.3). Everything runs on the throwaway sandbox VM (B0.1) — this module needs no second machine, because every distributed behaviour here is simulated with processes, files and firewall rules on one box, which is exactly enough to make the mechanisms visible. Nothing needs installing beyond what B8/B9 already added (netcat-openbsd for the partial-failure lab); python3, iptables and timedatectl ship with the system. One lesson deliberately moves the clock backwards, so take a snapshot first (B0.9) if that makes you nervous — the lab puts it back.

    What changes

    B13.1

    Why anyone accepts a second machine at all

    Why it matters

    Distribution is expensive. It brings failure modes that do not exist on one box, it makes debugging harder, and it forces every design decision through questions nobody had to ask before. Knowing the three reasons people pay that price is what lets you tell a system that needed distributing from one that was distributed out of habit — and it explains why a Kubernetes cluster is shaped the way it is.

    The concept

    There are exactly three reasons, and they are worth being able to name:

    • Scale — the work does not fit on one machine. Not "would be faster spread out", but genuinely does not fit: more requests than one box can serve, more data than one disk holds, more CPU than one socket provides. This is the reason people assume is primary and it is often the least common of the three.
    • Availability — the service must survive losing a machine. One machine has a failure probability that no amount of good engineering removes: disks die, kernels panic, someone unplugs the wrong cable, the datacentre loses power. If the service must keep answering through that, there must be another machine already running.
    • Blast radius — one failure should not take everything. Separating workloads onto different machines means a memory leak in one does not evict the other, and a bad deploy takes down one replica rather than the service.

    The availability reason has arithmetic behind it, and the arithmetic is the argument. If one machine is available 99% of the time, two independent machines are both down only 0.01% of the time — 99.99% availability, four hours of downtime a year instead of three and a half days. That word independent is doing enormous work, and it is where real systems fail: two machines in the same rack share a power feed, two replicas on the same node share a kernel, and two datacentres on the same fibre path share a backhoe. Redundancy only multiplies when the failures do not correlate — which is exactly what a Kubernetes anti-affinity rule exists to enforce.

    Note also what distribution costs you in exchange, so the trade is honest: every call that used to be a function call is now a network request that can fail slowly (B13.2); state that used to be a variable now needs replication and agreement (B13.8); and a system that used to have one clock now has none (B13.3). The rest of this module is that bill, itemised.

    scale·availability·blast radius→and the bill: partial failure, no clock, agreement

    Three reasons to say yes; the rest of the module is what you pay.

    Name the three reasons without looking, and for each, name a system you know that has it as its primary reason.     Gotchas

    The commonest mistake is distributing for scale that does not exist. A single modern machine handles a genuinely enormous amount of work — tens of thousands of requests per second, terabytes of disk, dozens of cores — and a distributed version of a system that fits on one box is usually slower, harder to debug and less available, because it has more parts that can fail and a network between them. "We might need to scale someday" is not one of the three reasons.

    The second is treating redundancy as automatically independent. Two replicas scheduled onto the same node, two nodes in the same rack, two zones on the same power grid: each pair fails together, so the arithmetic above quietly does not apply. Every real availability incident with a surprised post-mortem has a correlated failure in it somewhere, and the correlation was usually invisible on the architecture diagram.

    All three reasons are visible in the shape of a cluster. Scale is why a Deployment has a replica count and why nodes are added rather than enlarged. Availability is why the control plane can be run with three or five control-plane nodes rather than one, and why losing a worker is a scheduling event rather than an outage. Blast radius is why pods have resource limits (B7's cgroups, wearing a Kubernetes name), why namespaces exist, and why the scheduler can be told to spread replicas across nodes and zones instead of packing them together — the anti-affinity rule is the "make the failures independent" precondition, written as configuration.

    The two high-availability control-plane topologies, and what the load balancer in front of them is for, is W2.11; spreading replicas so their failures stay independent is W3.13.

    Docs

    This lesson is arithmetic and judgement rather than tooling, so the useful pages are the measuring ones: man 1 nproc, man 1 free and man 1 df for the ceiling, man 1 xargs (the -P flag) for the parallelism demo, and man 1 systemd-detect-virt for what your "independent" machines are actually running on. man 5 systemd.resource-control for the blast-radius controls from B7.11.

    B13.2

    Partial failure: the one fact everything else follows from

    Why it matters

    This is the defining difference between one machine and many, and nearly every other idea in this module is a response to it. On one machine, a function call runs or it does not, and you always know which. Across a network there is a third outcome that has no local equivalent: it might have worked, and you cannot find out. Once you have seen that outcome with your own eyes, retries, idempotency, timeouts and consensus all stop being abstractions.

    The concept

    Send a request to another machine and get no reply. At least four things could have happened:

    • The request never arrived — it was dropped on the way out.
    • It arrived, and the machine died before doing anything.
    • It arrived, was executed completely, and the reply was lost on the way back.
    • It arrived and is still being processed, slowly, and the reply is coming.

    From the caller's position these are identical. There is no observation you can make, and no timeout you can set, that distinguishes them — because the only way to ask "did you get it?" is to send another message, which is subject to exactly the same uncertainty. This is not an engineering shortfall to be fixed with a better protocol; it is a property of communicating over a channel that can lose things.

    Everything follows. Because you cannot know, you must retry — and because a retry may be a second execution of something that already succeeded, the operation must be safe to repeat, which is idempotency (B13.10). Because you cannot wait forever, you need a timeout — and a timeout is a guess, so you will sometimes declare a healthy peer dead (B13.13). Because two nodes may disagree about who is alive, you need a way to agree that a minority cannot override (B13.8). Four ideas, one cause.

    There is a related asymmetry worth naming: the distinction between failed and slow is undecidable. A peer that is merely overloaded looks exactly like a peer that is dead, and this is why every failure detector in every distributed system is, formally, a heuristic that can be wrong.

    no reply→never arrived?·done, reply lost?·still running?→indistinguishable

    The caller cannot tell these apart — so the system must be designed as if all of them are true.

    Lab
    1. Build a "server" that receives a request, records that it did the work, and never replies. This is the executed-but-reply-lost case, made concrete. 
      cd ~ && : > work.log
while true; do nc -l -p 9000 >> work.log; echo "--- executed at $(date +%T)" >> work.log; done &
sleep 1; ss -ltn | grep 9000
      LISTEN 0  1  *:9000  *:*          ← listening; it will read a request and answer nothing
    2. Send a request as a client with a timeout. From the client's seat, this is a failure — it got nothing back. 
      curl -s --max-time 3 http://localhost:9000/charge-card ; echo "curl exit=$?"
      curl exit=28          ← 28 = timeout. The client knows only that no answer came.
    3. Now look at the server's side of the same event. The work was done — the client's conclusion of "it failed" is simply wrong. 
      grep -c 'charge-card' work.log; tail -2 work.log
      1
GET /charge-card HTTP/1.1
--- executed at 09:14:22          ← the card WAS charged. The caller has no way to know.
    4. Produce the other case — a request that genuinely never arrives — and compare what the client sees. Drop the traffic before it reaches the listener (B9.12). 
      sudo iptables -I INPUT -p tcp --dport 9000 -j DROP

grep -c 'charge-card' work.log
      curl exit=28          ← identical symptom, identical exit code
1                      ← but this time nothing was executed: still 1 from step 3
    5. Put the two side by side. Same client observation, opposite server reality — this is partial failure in one screen. 
      echo "case A (reply lost)  : client=timeout(28)  server=executed"
echo "case B (never arrived): client=timeout(28)  server=did nothing"
      case A (reply lost)  : client=timeout(28)  server=executed

                       ↑ identical           ↑ the only place the truth exists
    6. Show the third case too — slow, not dead — because this is the one that makes every timeout a guess. 
      sudo iptables -D INPUT -p tcp --dport 9000 -j DROP
curl -s --max-time 1 http://localhost:9000/slow; echo "client gave up: exit=$?"
sleep 2; tail -1 work.log

--- executed at 09:15:40          ← the server was working the whole time; the client was wrong
    7. Clean up the listener and the log. 
      kill %1 2>/dev/null; pkill -f 'nc -l -p 9000'; rm -f ~/work.log; echo cleaned
      cleaned
    Verify

    List the four things that could have happened when a request gets no reply, and say why no timeout value distinguishes them. Then derive the three consequences out loud, in order: you must retry (because you cannot know), so operations must be safe to repeat; you must time out (because you cannot wait forever), so you will sometimes be wrong about who is dead; and you must have a rule for agreeing when peers disagree. If you can point at your own work.log as evidence for the first one, the lesson has landed.

    Gotchas

    The most dangerous instinct here is to design as though "the request failed" is a fact you were given. It is a conclusion the client drew, and it is wrong roughly as often as the reply-lost case occurs. Payment systems, order systems and provisioning systems all learn this the same way: a client that retries a non-idempotent operation after a timeout charges the card twice, and the logs on both sides look completely reasonable.

    The second is expecting error codes to disambiguate. A connection refused (B8.9) genuinely tells you nothing was executed — that one is informative. But a timeout, a reset mid-response, and a connection that hangs and then dies are all silent about what the far side did. Treat "I received a definite error before the request was processed" and "I received nothing" as two completely different situations, because only the first is actually safe to retry blindly.

    The API server is unusually honest about this problem, and its answer is worth knowing. Every write goes through the same uncertainty — kubectl apply may time out after the object was created — which is precisely why the API is declarative and its operations are idempotent: applying the same manifest again is defined to be harmless, so the retry is safe by construction. For the operations that genuinely cannot be made idempotent, Kubernetes uses optimistic concurrency instead: every object carries a resourceVersion, and an update that names a stale one is rejected with a conflict rather than silently overwriting someone else's change.

    The end-to-end path a write actually takes, and where it can fail on each hop, is W1.3; what still works when etcd itself stops answering — the largest partial failure a cluster can have — is W6.8.

    Docs

    man 1 curl for --max-time and the exit-code table (28 is timeout, 7 is connection refused — the distinction the gotcha rests on). man 1 nc for the throwaway listener. man 8 iptables for the DROP rule that manufactures a lost request; man 7 tcp for what the kernel does while a client waits, and why a dropped SYN produces a long hang rather than an error.

    B13.3

    There is no shared clock

    Why it matters

    "Which of these two events happened first?" is a question you have answered with timestamps your whole career, and across machines it is not reliably answerable that way. Clocks differ, drift apart and occasionally jump backwards when something corrects them. Knowing this is what stops you from debugging a distributed system by sorting two machines' logs together and believing the result.

    The concept

    Every machine has its own clock, and no two agree exactly. Three separate problems stack up:

    • Offset — two clocks read different times right now, typically by milliseconds, sometimes by much more.
    • Drift — they run at slightly different rates, so the offset grows on its own. A cheap oscillator can drift seconds per day.
    • Jumps — when a time daemon corrects the clock it may step it, and a step can go backwards. Time on a machine is not guaranteed to be monotonic.

    That last one is the killer, because it breaks the assumption underneath timestamp ordering. If a clock steps back by two seconds, an event that genuinely happened later can carry an earlier timestamp than one that happened before it — on the same machine, never mind across two.

    Linux offers a way out for measuring durations: two different clocks. CLOCK_REALTIME is wall-clock time, which can be stepped by NTP and by an administrator. CLOCK_MONOTONIC only ever moves forward at a steady rate since boot, and is immune to steps. Rule of thumb worth internalising: use the wall clock only for displaying times to humans; use the monotonic clock for every timeout, deadline and duration. Code that measures an interval with the wall clock will one day measure a negative one.

    For ordering events across machines, neither clock helps, so distributed systems stop using time altogether and use a logical counter instead: a number that increases with every change, whose only meaning is "this came after that". Kubernetes uses this pervasively — etcd's revision, and the resourceVersion on every object, are counters, not times. They can be compared within one cluster and are meaningless anywhere else, which is why you cannot compare a resourceVersion between two clusters, or reason about how long ago a revision was.

    wall clock: display only·monotonic: durations·logical counter: ordering across machines

    Three clocks for three jobs; using the first one for the other two is the classic bug.

    Gotchas

    Measuring a duration with the wall clock is the bug this lesson exists to prevent. Code that records time.time() at the start and end of an operation will, eventually, compute a negative elapsed time or a sixty-second one for something instantaneous — and it will do it rarely enough to be blamed on anything else. Every language has a monotonic clock; use it for every deadline, retry interval and timeout.

    The second is a certificate-shaped one you have already met: clock skew produces errors that look like corruption. A machine whose clock is behind rejects freshly-issued certificates as not yet valid (B12.11), and a node whose clock is far ahead can invalidate tokens the moment it receives them. When exactly one machine in a cluster misbehaves in an inexplicable, security-flavoured way, check timedatectl before anything else.

    Kubernetes avoids wall-clock ordering wherever correctness depends on it. Every object carries a resourceVersion, which is etcd's revision counter — a monotonically increasing integer with no relationship to time. Watches resume from a resourceVersion rather than from a timestamp, which is why a controller that reconnects does not miss changes and does not need the two machines' clocks to agree. The creationTimestamp you see in an object is for humans; nothing in the system orders events with it.

    etcd's revision model — how those counters work, and what compaction does to old ones — is W1.10; where objects actually live under those revisions is W1.8. And the clock-skew certificate failure is W2.6.

    Docs

    man 1 timedatectl for the sync status and timesync-status output. man 2 clock_gettime is the page that defines CLOCK_REALTIME versus CLOCK_MONOTONIC — the whole lesson in one man page. man 5 systemd-timesyncd.conf for what disciplines the clock on Ubuntu, and man 7 time for the general model.

    B13.4

    The eight fallacies, and a latency ladder you have measured yourself

    Why it matters

    The eight fallacies are a checklist of assumptions that feel obviously true, are quietly built into most code, and are all false. Reading them is mildly interesting; matching each one to a failure you personally caused in B8–B10 is what makes them stick. The latency ladder is the numeric half of the same lesson: an intuition for what things cost, so "just call the service again" gets priced correctly.

    The concept

    The list, formulated at Sun Microsystems, is eight assumptions that every distributed system eventually violates:

    • The network is reliable — packets are dropped, links flap, and a message sent is not a message received (B13.2).
    • Latency is zero — a call across a datacentre is roughly a hundred thousand times slower than a local function call, and one across the world is a million.
    • Bandwidth is infinite — it is shared, finite, and the thing your backup job saturates at 02:00.
    • The network is secure — anyone on the path can read and modify unless you did the work in B12.12.
    • Topology doesn't change — pods move, IPs are reused, nodes are replaced. This is why you resolve names instead of caching addresses (B10.11).
    • There is one administrator — the firewall rule you did not know about was added by someone you have not met.
    • Transport cost is zero — serialising, encrypting and copying data costs CPU on both ends, and the wire itself costs money.
    • The network is homogeneous — different MTUs, different hardware, different behaviour, which is exactly the black hole from B8.18.

    The latency ladder gives the second fallacy a number. Orders of magnitude are what matter, not exact figures: a memory reference is ~100 nanoseconds, an SSD read ~100 microseconds (1,000×), a round trip within a datacentre ~0.5 milliseconds (5,000×), a round trip across a continent ~50–100 milliseconds. The practical consequence is that the number of round trips dominates almost everything else. One request that fetches everything beats ten that each fetch a piece, regardless of how fast the far end is, because the round trips do not overlap.

    memory ~100 ns→SSD ~100 µs→same-DC RTT ~0.5 ms→cross-continent ~50 ms

    Each step is roughly a thousand times the last — which is why round trips, not bytes, are the thing to count.

    Gotchas

    The fallacies are seductive because each one is almost true in a lab. On a single machine with loopback networking, the network really is reliable, latency really is negligible, and topology really does not change — so code written and tested there encodes all eight assumptions without anyone noticing. They surface for the first time in production, together, usually during an incident. This is the argument for testing with deliberate failure injection rather than only in the happy environment.

    The second is misreading averages. A mean latency of 11 ms with a tail at 900 ms is a completely different system from a flat 11 ms, and the tail is what your users and your timeouts actually experience. When you have a choice, look at the 99th percentile; a distributed system with many components is dominated by its slowest ones, because a request that touches ten services meets ten chances to hit a tail.

    The latency ladder explains one of the most confusing Kubernetes performance symptoms there is: a slow API server whose real cause is a slow disk. etcd commits every write to disk on a majority of members before acknowledging it (B13.9), so etcd's write latency is bounded by fdatasync on the slowest member of the quorum. Put etcd on a spinning disk or a throttled network volume and every object creation in the cluster pays that cost — the symptom presents as "kubectl is slow", several layers above the actual fault.

    Checking etcd's health, including the latency metrics that make this visible, is W1.13; the wider "the API server is slow or unavailable" ladder is W6.5.

    State and agreement

    B13.5

    Stateless and stateful, and why only one of them is easy

    Why it matters

    Almost every "just add another replica" story works beautifully or destroys data, and which one you get is decided entirely by this distinction. It is also the reason Kubernetes has two different objects for running copies of a program, and choosing the wrong one is a data-loss bug rather than a matter of taste.

    The concept

    A stateless service keeps nothing between requests that matters. Every instance is interchangeable: any copy can serve any request, a dead one can be replaced by a fresh one that knows nothing, and scaling is a matter of starting more. It is not that a stateless service has no data — it usually has plenty — but the data lives somewhere else, and the instance is a pure function of its inputs.

    A stateful service owns data that must survive its own restart. That single fact drags in three hard problems at once: the data must be durable (survive a crash), it must be findable (a replacement instance needs the same data, not a blank disk), and it must not be corrupted by two writers at the same time. The last one is the sharp edge, because it fails silently. Two processes doing read-modify-write on the same value will lose updates, and neither will report an error.

    The strategy every real system uses is to push state to the edges: make as much of the system stateless as possible, and concentrate the state in a small number of components that are designed for it — a database, a replicated log, etcd. Those components then take on replication (B13.6), consistency (B13.7) and agreement (B13.9), which is precisely why the rest of this module is about them.

    stateless: any copy will dovsstateful: this copy owns something→durable · findable · one writer

    Push the state into as few places as you can; everything else becomes replaceable.

    Lab
    1. Run a stateless service and prove instances are interchangeable. Kill one, start another, and nothing was lost because nothing was held. 
      mkdir -p ~/dist && cd ~/dist

    2. Now make something stateful — a counter that lives in a file — and see that a replacement instance needs the data, not just the program. 
      echo 0 > counter

    3. Break it the way two writers break it. Run the same read-modify-write loop twice, concurrently, 500 increments each. 
      echo 0 > counter

    4. See exactly where it went wrong. The gap between reading and writing is where the other writer slipped in — this is the lost-update problem in three commands. 
      echo "writer A reads 41 ─┐"; echo "writer B reads 41 ─┤ both compute 42"; echo "both write 42     ─┘ one increment vanished"

      echo 0 > counter

  flock counter.lock bash -c 'n=$(cat counter); echo $((n+1)) > counter'

    Verify

    Define both terms in one sentence each, without using the word "state" in the definition — a stateless instance can be replaced by any identical copy at any moment; a stateful one owns data that must outlive it. Then explain the step-3 result: why did 1000 increments produce 612, and why was there no error message? Finally, name the two ways to fix it and what each costs (a lock serialises and therefore slows; an atomic operation avoids the gap entirely but limits what you can express).

    Gotchas

    Silent corruption is the point to take away. Step 3 produced a wrong number with no failure, no exception and no log line — every command "succeeded". Concurrency bugs on shared state do not announce themselves, which is why they are found weeks later by someone reconciling totals, and why "it worked when I tested it" is not evidence of anything: with one writer, the bug is invisible.

    The second trap is believing a service is stateless because it has no database. In-memory session data, an upload directory, a local cache that clients depend on, a lock file — each of these makes an instance non-interchangeable, and each one turns a routine restart into a user-visible failure. The test is not "does it have a database", it is "if I kill this instance right now and start a fresh one, does anyone notice?"

    This is the entire reason Kubernetes has both Deployments and StatefulSets. Deployment pods are treated as interchangeable: they get random name suffixes, start in any order, and a replacement is simply another copy. StatefulSet pods get stable identity — db-0, db-1, in that order — a stable network name, and their own persistent volume that follows the ordinal rather than the pod. That is the machinery for "findable data" and "this copy owns something", expressed as an API object. Choosing a Deployment for something stateful usually appears to work: the pods run, the service answers, and the data corruption or loss shows up on the first rescheduling event.

    The full workload zoo, including when a StatefulSet is the right answer, is W3.10; why StatefulSets and DaemonSets roll differently from Deployments is W3.9.

    Docs

    man 1 flock for the serialising fix in step 5 — the same advisory-lock mechanism from B2.12. man 2 open for O_EXCL and man 2 rename for the atomic-replace pattern (write to temp, rename over), which is how most programs update a file safely without a lock at all. man 7 pipe if you want the other classic answer: hand the state to a single owner and talk to it.

    B13.6

    Leader/follower replication, and what "behind" costs

    Why it matters

    Replication is how stateful services survive losing a machine, and the leader/follower arrangement is by far the most common shape. Its behaviour under normal conditions is easy; what matters is knowing precisely what a follower being behind means for a reader, and what happens in the seconds after a leader dies. Both are measurable, and both explain Kubernetes behaviour you will otherwise find surprising.

    The concept

    One member is the leader (also called primary): it is the only member that accepts writes. Every write is applied there and then shipped to the followers, which apply the same changes in the same order. Followers can serve reads, which is often why the arrangement is chosen — read capacity scales with members even though write capacity does not.

    Two properties fall straight out of that design:

    • Replication lag. A follower is always at least a little behind — the time for the change to travel and be applied. A read from a follower is a read of the recent past. Usually that is milliseconds and nobody notices; under load or across a slow link it can be seconds, and then a user who writes a value and immediately reads it back sees the old one. This is the "I saved it and it didn't save" bug, and it is not a bug in the write path at all.
    • A failover window. When the leader dies, everything it had accepted but not yet shipped is gone. The remaining members promote one of themselves, and whatever the new leader never received simply did not happen — from the outside, acknowledged writes vanish. Systems that cannot tolerate that use synchronous replication instead: the leader does not acknowledge a write until a follower has it, which closes the window and adds a round trip to every write.

    So there is a knob, and it has exactly the shape you would expect: asynchronous replication is fast and can lose recent writes; synchronous replication is slower and does not. Consensus systems like etcd sit at the strict end — a write is not acknowledged until a majority has it on disk (B13.9) — which is why they are correct through a leader failure and why their write latency is bounded by the slowest member of that majority.

    client→leader (writes)→follower (reads, behind)·lag = staleness · unshipped = loss window

    Reads from a follower are reads of the past; how far past is the number that matters.

    Lab
    1. Set up a leader and a follower as two files, with a replicator process copying one to the other on an interval. The interval is the lag, made explicit. 
      cd ~/dist; echo 0 > leader.db; echo 0 > follower.db

      replicator pid 6412          ← ships the leader's state to the follower every 2 s
    2. Write to the leader and immediately read from the follower. This is the read-your-own-write failure, reproduced on demand. 
      echo 42 > leader.db

      leader:   42
follower: 0          ← the write happened, and the follower has not heard about it yet
    3. Wait out the lag and read again. Nothing was broken — the follower was simply in the past. 
      sleep 2.5; echo "follower: $(cat follower.db)"
      follower: 42          ← caught up. "Eventually" is a real technical term (B13.7).
    4. Measure the lag rather than assuming it. Write a timestamped value and time how long it takes to appear on the follower. 
      date +%s.%N > leader.db

      replication lag: 1.31 s          ← a real number; this is what a follower read is behind by
    5. Now kill the leader mid-flight and see the loss window. Writes accepted after the last replication cycle are gone. 
      echo 100 > leader.db; echo 101 > leader.db; echo 102 > leader.db   # accepted by the leader

rm -f leader.db                                                    # its disk is gone with it

      promoted follower now holds: 42          ← three acknowledged writes vanished
    6. Do it the synchronous way and watch the window close — at the cost of a slower write. 
      echo 42 > leader.db

      real    0m0.004s
leader=103 follower=103          ← no window: the write was not "done" until both had it
    Verify

    Explain, without notes, what a follower read gives you and why that is not a bug. Then quantify the two costs: what does replication lag cost a user (a read of the recent past, most visibly right after their own write), and what does asynchronous replication cost during a failover (every write the leader accepted but had not shipped)? Finally, state the trade in one sentence — synchronous replication closes the loss window by adding a round trip to every write — and say which end of that trade etcd sits at.

    Gotchas

    Read-your-own-writes is the failure that gets misdiagnosed most often, because the symptom appears in the read path while the cause is in the replication topology. A user updates their profile, the write goes to the leader, the subsequent page load is served by a follower that has not caught up, and the application appears to have ignored the save. Nothing in the write path is faulty; the fix is to route reads that follow a write to the leader, or to wait for the follower to reach the write's position.

    The second trap is treating a follower's health as a green light. A follower that is up, connected and answering can still be minutes behind, and monitoring that checks liveness rather than lag will report everything as fine while readers get stale data. Lag is a separate metric and it is the one that matters — a replica that is up but hours behind is not a replica, it is a slow backup.

    etcd is a leader/follower system with the strict settings: one member is the leader, all writes go through it, and a write is not acknowledged until a majority of members have persisted it. That is why a Kubernetes control plane survives losing an etcd member without losing acknowledged data — there is no unshipped-writes window, because "acknowledged" is defined as "a majority already has it". The price is exactly the one this lesson predicts: every write costs a round trip to the slowest member of the majority, plus a disk sync, which is why etcd is so sensitive to disk and network latency (B13.4).

    Raft — the algorithm that turns leader/follower replication into something safe through a leader failure — is W1.9; the revision counter that orders those replicated entries is W1.10.

    Docs

    No single man page covers replication, so read the mechanisms instead: man 2 fsync and man 2 fdatasync for what "durably stored" costs on the leader, man 1 rsync for the shape of an incremental ship-the-difference protocol, and man 5 systemd.timer if you want the replicator loop from step 1 running as a real unit rather than a background shell (B11.2).

    B13.7

    Strong and eventual consistency, and CAP as a real choice

    Why it matters

    CAP is the most-quoted and least-usefully-understood idea in distributed systems, usually rendered as "pick two of three", which is not what it says. Stated properly it is a decision you make at a specific moment — when the network splits — and Kubernetes makes that decision differently in different components, on purpose. Knowing which is which explains why kubectl get can show you something out of date and be working perfectly.

    The concept

    Two consistency models, in plain words:

    • Strong consistency — every read returns the most recent write. To promise that, a read must be answered by someone who is certain they are current, which means waiting or coordinating. You pay in latency and in availability during trouble.
    • Eventual consistency — reads may return stale data for a while, and if writes stop, all replicas converge on the same value. You gain speed and the ability to keep answering when parts of the system cannot talk, and you accept that a reader may see the past (B13.6's lag, promoted to a design decision).

    CAP is the statement that makes the choice unavoidable. Its useful form: when a network partition happens — when some members cannot reach others — a system must choose between refusing to answer (staying consistent) and answering with possibly-stale data (staying available). It cannot do both, because the only way to be certain you are current is to hear from the others, and by assumption you cannot. When there is no partition there is no trade-off, which is why "pick two of three" misleads: partitions are not optional, so the real choice is only ever between the other two, and only during the partition.

    Kubernetes makes both choices deliberately, in different layers. etcd chooses consistency: lose quorum and writes stop rather than risk two halves diverging (B13.8). The controllers around it are eventually consistent by design: each works from a local cache that may be a moment out of date, acts on what it sees, and corrects itself on the next pass (B13.12). The combination is deliberate — one component that must never be wrong, surrounded by many that are allowed to be briefly out of date because they will re-check.

    partition happens→refuse to answer (consistent)oranswer possibly-stale (available)

    The choice only exists during a partition — and it is a choice, not a failure.

    Lab
    1. Rebuild the leader/follower pair with a heartbeat, so a reader can tell whether its data is fresh. The heartbeat is what makes the choice possible at all. 
      cd ~/dist; echo 42 > leader.db; cp leader.db follower.db; date +%s > follower.sync
( while true; do cp leader.db follower.db; date +%s > follower.sync; sleep 1; done ) &
sleep 2; echo "last sync $(( $(date +%s) - $(cat follower.sync) ))s ago"
      last sync 0s ago          ← the follower knows how current it is; that is the whole trick
    2. Write a reader that implements both policies, choosing between them with a flag. Twelve lines, and it is the entire CAP decision. 
      cat > read.sh <<'EOF'

age=$(( $(date +%s) - $(cat follower.sync) ))
if [ "$mode" = strong ] && [ "$age" -gt "$max_age" ]; then
  echo "REFUSED: data is ${age}s old, cannot guarantee freshness"; exit 1
fi
echo "value=$(cat follower.db)  (age ${age}s)"
EOF
chmod +x read.sh; ./read.sh strong; ./read.sh eventual
      value=42  (age 0s)

    3. Now partition the system — stop the replication and let the follower fall behind while the leader keeps taking writes. 
      kill %1 2>/dev/null; echo 99 > leader.db; sleep 4

      leader has: 99

    4. Ask both policies the same question during the partition. This is the trade-off, executing. 
      ./read.sh strong; ./read.sh eventual

    5. Heal the partition and watch convergence — the "eventual" in eventual consistency, arriving. 
      ( while true; do cp leader.db follower.db; date +%s > follower.sync; sleep 1; done ) &

    State CAP in its useful form — during a partition, choose between refusing to answer and answering with possibly-stale data — and explain why "pick two of three" is a misleading summary. Then place both Kubernetes layers on that spectrum and justify each: etcd must never let two halves diverge, because the cluster's entire state lives there; controllers may safely act on stale data because their actions are re-evaluated on the next pass and are idempotent, so a mistake made from a stale view is corrected rather than compounded.

    Gotchas

    "Eventually consistent" is often heard as "unreliable", and it is not. It is a precise promise: if writes stop, all replicas converge on the same value. What it does not promise is when, and that is where systems get into trouble — an eventual-consistency design with no bound on staleness, and no way for a reader to learn the age of what it is reading, gives you no way to distinguish "slightly behind" from "broken and stuck since Tuesday". Step 1's heartbeat exists for exactly this reason: expose the age, so someone can decide.

    The second is assuming strong consistency is simply the better choice when you can afford it. It costs availability at precisely the worst moment — during a partition, the consistent system stops answering, which for a user is indistinguishable from an outage. Whether that is right depends entirely on the data: a bank balance should refuse rather than lie, a cached product listing should absolutely keep serving.

    This is why a Kubernetes cluster degrades the way it does when etcd loses quorum: reads keep working from the API server's caches, and writes fail. That is consistency being chosen on your behalf — the cluster would rather stop accepting changes than let two partitions both accept them and diverge. Meanwhile the eventual-consistency half explains an everyday observation: kubectl get pods can show a pod that has already terminated, because the answer came from a watch cache that is a moment behind, and the next controller pass reconciles the difference. Neither is a fault; they are two deliberate settings in one system.

    What exactly still works when etcd stops answering is W6.8; the controller pattern that makes eventual consistency safe — informer, queue, reconcile — is W1.16.

    Docs

    CAP is a theorem rather than a tool, so the reading is conceptual: Brewer's original formulation, and Kleppmann's "Please stop calling databases CP or AP" for why the labels are less useful than the specific behaviour. Locally, man 2 fsync and man 7 tcp are still the mechanisms underneath — durability on one node, and the channel that partitions.

    B13.8

    Quorum arithmetic: why 3 and 5, and never 4

    Why it matters

    This is the arithmetic behind every "how many members should this cluster have?" decision, and it takes two minutes to learn permanently. It also explains, exactly, why losing two of three control-plane nodes turns a Kubernetes cluster read-only rather than merely slower — a behaviour that looks like a bug until you have done the sum.

    The concept

    A quorum is the minimum number of members that must agree before the group may act. Use the canonical picture: a small committee that can only make decisions with a strict majority present. For N members, a majority is floor(N/2) + 1, and the number of failures the group tolerates is N − quorum.

    The reason it must be a majority, rather than any fixed number, is the property that makes the whole scheme work: two disjoint groups cannot both contain a majority. If the network splits the cluster in two, at most one side can have more than half the members, so at most one side can act. That single fact is what prevents two halves of a partitioned cluster from both accepting writes and diverging — the failure mode called split brain (B13.9).

    Now the odd-numbers result, which follows directly. With 3 members, quorum is 2, so 1 failure is tolerated. With 4 members, quorum is 3, so still only 1 failure is tolerated — you added a machine, added its failure probability to the pool, added its latency to every commit, and gained nothing. Even member counts always tie with the odd number below them. This is why real deployments are 3, 5 or 7, and why 5 is the usual practical ceiling: past that, the coordination cost of every write grows faster than the fault tolerance you are buying.

    One subtlety worth carrying: losing quorum is not data loss and not corruption. The remaining members still hold the data and can usually still serve reads; what they refuse to do is accept changes, because they cannot prove they are not the minority side of a split. Recovery is a matter of bringing members back, not of restoring from backup.

    N members→quorum = ⌊N/2⌋+1→tolerates N−quorum failures→only one side of a split can act

    One formula, and everything about cluster sizing follows from it.

    Lab

    Gotchas

    The most consequential misreading is treating "lost quorum" as "lost data". It is neither corruption nor loss: the surviving members hold everything, and the cluster is deliberately refusing to change state because it cannot prove it is the majority side. Reaching for a snapshot restore in that situation is how a recoverable incident becomes a real one — the correct move is almost always to bring a member back.

    The second is adding a member to "improve availability" without doing the arithmetic. Going from 3 to 4 adds no fault tolerance, adds a machine that can fail, and makes every write wait for one more acknowledgement. Adding members also slows the cluster in a way people find surprising, because commit latency is set by the slowest member of the required majority — so a 7-member cluster with one sluggish disk is slower than a 3-member cluster with good ones.

    This is why kubeadm's high-availability guidance is three or five control-plane nodes, and why nobody runs four. Each control-plane node carries an etcd member, so the etcd quorum and the control-plane count are the same number. Lose one of three and everything continues normally. Lose two of three and etcd refuses writes: the API server can still serve reads from etcd, so kubectl get keeps working, but every create, update and delete fails — and because controllers cannot write either, nothing self-heals. That is the read-only cluster people find so alarming, and it is the arithmetic above doing exactly what it was designed to do.

    B13.9

    Consensus, Raft, and what split brain would cost

    Why it matters

    Consensus is how a group of machines agrees on a single sequence of events despite failures, and Raft is the algorithm nearly everything you will touch uses — etcd above all, which means the entire Kubernetes control plane rests on it. You do not need to implement it, but being able to narrate a leader failure without notes is the difference between reading an etcd incident and guessing at one.

    The concept

    The problem: several machines must agree on an ordered log of changes, such that everyone applies the same changes in the same order, even though members crash and messages are lost. Raft solves it with three parts, and each is simple on its own.

    • Leader election. Time is divided into numbered terms. A member that has not heard from a leader for a randomised timeout becomes a candidate, increments the term, votes for itself and asks the others for votes. Each member votes at most once per term, so a candidate needs a majority (B13.8) to win. The randomised timeout matters: it makes simultaneous candidacies rare, so elections usually resolve in one round.
    • Log replication. The leader is the only member that accepts writes. It appends each change to its log and ships it to the followers, which append it in the same position.
    • Commit. An entry is committed once a majority of members have stored it. Only then is it applied and acknowledged to the client. That definition is the safety guarantee: a committed entry survives any minority failing, because a majority already holds it.

    What this prevents is split brain — two members both believing they lead, both accepting writes, and the data diverging into two irreconcilable histories. Two defences stack. Quorum makes it impossible for both sides of a partition to elect a leader, because both cannot hold a majority. And terms make a stale leader harmless: an old leader that was cut off and never learned about the election still thinks it leads, but its messages carry an outdated term number, so every member rejects them — and on seeing the newer term, it stands down. That last step is fencing: the deposed leader is actively prevented from continuing, rather than trusted to notice it should stop.

    One consequence worth carrying into operations: because a commit requires a majority to have stored the entry — durably, on disk — Raft's write latency is bounded by the slowest member of that majority. A single slow disk in a five-member cluster does not slow one member down; it slows every write in the whole system.

    election (term + majority)→replication (leader appends, ships)→commit (majority stored)

    Three parts; the third one is where the safety guarantee actually lives.

    1. Write a small Raft-shaped election simulator. It is not Raft — no logs, no persistence — but the election rule is the real one. 
      cd ~/dist; cat > election.py <<'EOF'
import sys, random
members = {1: 'up', 2: 'up', 3: 'up'}          # id -> up | down
term = 0

def elect(reachable):
    """One election round among the reachable, live members."""
    global term
    term += 1
    live = [m for m in reachable if members[m] == 'up']
    needed = len(members) // 2 + 1              # majority of ALL members, not of the live ones
    if len(live) >= needed:
        leader = random.choice(live)
        print(f'term {term}: {len(live)}/{len(members)} reachable, need {needed} -> LEADER = member {leader}')
        return leader
    print(f'term {term}: {len(live)}/{len(members)} reachable, need {needed} -> NO LEADER (minority)')
    return None

leader = elect([1, 2, 3])
print('--- leader crashes ---')
members[leader] = 'down'
elect([1, 2, 3])
print('--- network splits 2 | 1 ---')
for m in members: members[m] = 'up'
elect([1, 2]); elect([3])

    Gotchas

    The most common misconception is that the leader is a performance bottleneck to be worked around. It is not there for performance, it is there to impose an order — a single member deciding the sequence is what makes agreement tractable at all. Directing writes elsewhere does not distribute load; it produces a system with no defined order, which is the problem consensus exists to solve.

    The second is underestimating what "committed" costs. An entry is committed when a majority has it on disk, which means an fsync on each of those members before the client hears anything. This is why consensus systems are so unusually sensitive to disk latency, and why the standard advice is to give etcd its own fast disk: a shared or throttled volume turns every single object creation in the cluster into a slow operation, and the symptom appears several layers away as a sluggish API server.

    This is etcd, and therefore the foundation everything else stands on. Every object you have ever created in Kubernetes is a committed entry in a replicated Raft log — the Deployment, the Secret, the Lease that says a node is alive. The properties transfer directly: the control plane survives losing a minority of etcd members with no data loss; it refuses writes when it cannot assemble a majority (B13.8); and its write performance is bounded by fsync on the slowest member of the majority, which is why "the API server got slow" so often ends at a disk.
