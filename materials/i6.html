    I6 — Building images

    A Dockerfile is two things at once: a sequence of layer-producing operations, and a cache-key function. Learn to read it as both — then build an image with no Dockerfile and no Docker, which is the only way to be certain you understood it.

    This module is where images stop being something a tool produces for you. Four of the corrections in it are to beliefs almost everyone holds — that WORKDIR is free, that the whole build context is uploaded, that a comment busts the cache, that rm reclaims space — and every one of them is settled here by measurement rather than assertion. By the last checkpoint you will have built an image with no Dockerfile, no builder and no daemon, using nothing but tar, jq and sha256sum, which is the only way to be certain the format holds no more mysteries.

    • Doing it properly. Write a multi-stage build and use --target to debug the builder stage; use BuildKit's DAG, cache mounts and secret mounts, and find a --build-arg token sitting in plain text in an image's history; build a multi-platform image and pay the emulation bill knowingly.

    • Reading images others built. Use history as the audit trail it is, attribute an image's bulk to the instruction that caused it, and recover a credential from a layer that its author believed was deleted.

    Semantics

    I6.1

    Two kinds of instruction, and the one that fools everybody

    Why it matters

    A Dockerfile looks like a shell script, which is exactly why people misread it. It is not a script — it is a list of steps, where each step either changes the filesystem (and so becomes a layer you will store, push and download forever) or merely writes a note in the image's config (and so costs nothing at all). Sorting your instructions into those two piles is the single skill that turns build behaviour from mysterious into predictable, and almost every "why is my image 800 MB" and "why does my CI take nine minutes" question is answered by it.

    The concept

    You already have the machinery for this. From I4.9, a layer is a tar file of changes. From I4.13, the image config is a JSON document of pre-declared defaults. A build walks your instructions in order and, for each one, does one of two things:

    • Produce a layer. The step runs against a snapshot of the filesystem so far, and whatever changed is packed into a new tar. That tar gets a digest, a diff_id, and a slot in rootfs.diff_ids. RUN, COPY and ADD all work this way.
    • Amend the config. The step touches no files; it just sets a field — Env, Cmd, User, Labels. Nothing is stored, nothing is pushed, and the image's layer count does not move. ENV, CMD, ENTRYPOINT, USER, LABEL and EXPOSE all work this way.

    Both kinds still get a line in the config's history array, which is what makes the split visible: a config-amending step is marked empty_layer: true, and a layer-producing step is not. So the arithmetic from I4.13 holds on every image ever built — history entries minus empty ones equals the number of layers — and you can audit any image's build by reading two fields.

    That is why an image with thirty instructions may have only five layers, and why re-ordering your ENV and LABEL lines is free while moving a COPY is not: only the layer-producing steps change the filesystem, and therefore only they change the chain ID (I4.12) that every subsequent step's cache key is built on.

    And now the part that catches everyone, including the author of this module's own checkpoint list. WORKDIR produces a layer. It has to: it creates the directory if it is missing, and creating a directory is a filesystem change. So the neat "config-amending" bucket that every tutorial puts WORKDIR in is wrong, and the lab below proves it in two lines of jq.

    It is stranger than that. WORKDIR takes a layer slot even when the directory already exists and nothing changes — the step still goes through the snapshot path, the snapshot still gets diffed, and the diff comes out empty. What lands in rootfs.diff_ids is then the empty layer: 1024 zero bytes, diff_id sha256:5f70bf18a086…, compressing to a 32-byte blob. If you have read many image configs you have seen that digest before; now you know where it comes from.

    So the reliable rule is not a list of instruction names to memorise. It is a question about mechanism: does this step go through the filesystem-snapshot path? If yes it consumes a diff_id, possibly an empty one. If no, it is empty_layer: true. Ask the mechanism, not the tutorial.

    The spec never lists which Dockerfile instructions make layers — it could not, since it knows nothing about Dockerfiles. It defines the test instead, and the test is about filesystem diffs, not instruction names. That is precisely why WORKDIR falls on the side it does.

    empty_layer boolean, OPTIONAL

    This field is used to mark if the history item created a filesystem diff.
    It is set to true if this history item doesn't correspond to an actual layer in the rootfs section (for example, Dockerfile's ENV command results in no change to the filesystem).
    OCI image-spec v1.1.1 — config.md § Properties

    Worth noticing: the spec's own worked example of a config has exactly two diff_ids, and the second one is sha256:5f70bf18a086007016e948b04aed3b82103a36bea41755b6cddfaf10ace3c6ef — the same empty layer your WORKDIR is about to produce.

    Verify

    Handed any Dockerfile, you can predict its image's layer count before building, and check your prediction with two jq expressions. You can state the mechanism-level rule — does the step go through the snapshot path — rather than reciting a list. And you can recognise sha256:5f70bf18a086… and its 32-byte compressed form as the empty layer, wherever they turn up.

    Gotchas
    • WORKDIR is on the expensive side of the split, and nearly every tutorial says otherwise. The cost is small — an empty layer, or a one-directory layer — but it is a real slot in rootfs.diff_ids, and it means moving a WORKDIR line invalidates the cache for everything below it, exactly like moving a COPY. If you have ever seen a "harmless" reshuffle trigger a full rebuild, this is a strong candidate.
    • "Empty layer" and empty_layer: true are different things, and the collision is unfortunate. The 1024-zero-byte layer is a layer with a digest and a slot; empty_layer: true means there is no layer at all. An image can therefore have empty layers and no empty-layer history entries, or the reverse.
    • The step numbers in the build log count vertices, not lines. [2/4] for a nine-line Dockerfile is not the builder skipping your work — it is the builder telling you five of your lines are free. Reading that counter is a fast sanity check on your own classification.
    • history is written by whichever tool built the image, and it is free-form text. The created_by strings above end in # buildkit because BuildKit wrote them; another builder writes something else, and a hand-assembled image (I6.9) may have no history at all. Treat it as a strong hint, never as proof — a point that returns in I6.10.

    This split is why W3.21 exists at all. Everything on the config-amending side — ENV, CMD, USER, EXPOSE — is a default baked into the image, and every one of those defaults can be overridden by the pod spec without rebuilding anything: env, command/args, securityContext.runAsUser. Anything on the layer-producing side cannot be, because it is bytes in a tar in a registry. That is the real dividing line behind "configuration belongs in a ConfigMap, not in the image", and the reason W3.23 insists a Secret is a runtime object: a secret written by a RUN is a layer, and layers are not configurable, they are shipped.

    Docs: config.md § Properties for rootfs.diff_ids, history and empty_layer — the only normative text in play here. For the instruction semantics themselves, search the Docker docs for "Dockerfile reference", remembering it is a reference and not a standard. On the Kubernetes side, search for "define a command and arguments for a container" to see which of these fields a pod spec can override.

    I6.2

    The build context, and the folklore about it that is now wrong

    Why it matters

    When you type docker build ., that trailing dot is not decoration — it names the build context, the set of files the builder is allowed to reach. Understanding what actually crosses from your directory into the builder is how you explain a build that takes six seconds before running a single instruction, and it is how credentials end up in public images. Both stories are in this checkpoint, and one of them has changed since the advice you have probably read.

    The concept

    The builder is a separate program from the client, often on a separate machine, and it cannot see your disk. So before anything runs, the client has to hand over the files. The old Docker daemon did that the blunt way: it tarred up the whole directory and uploaded it. That is where the standard warning comes from — the entire context is transferred whether you reference it or not, so a stray .env or a 2 GB .git costs you on every build.

    On BuildKit, that is no longer true, and the lab below measures it. BuildKit runs the transfer as a session between client and builder and moves files on demand: it resolves your Dockerfile into a graph first, sees which paths the graph actually references, and pulls only those across. A 100 MB file sitting beside your Dockerfile that nothing copies is transferred as zero bytes. Repeating the old warning as fact is one of the most widespread pieces of stale container advice, and it matters because it teaches people to fear the wrong thing.

    What is still completely true is the consequence, and it has simply moved one step along. The transfer is driven by what the graph references — so the risk is not "having files in the directory", it is writing an instruction that references all of them. And there is exactly one such instruction, it is extremely common, and it is COPY . .. The moment you write it, every byte in that directory is both transferred and baked into a layer that will be pushed to a registry: the .env with your cloud credentials, the .git directory containing the history where you already removed a key once, the private key someone left in the tree. From I4.1, that layer is content-addressed and immutable, and from I6.4, deleting the file later does not remove it.

    So .dockerignore deserves a better framing than the performance tweak it is usually sold as. It is a secrecy control — the list of things you are declaring your build has no business seeing, enforced at the point where files cross the boundary rather than left to the discipline of everyone who ever edits the Dockerfile. Read it the way you would read a firewall rule, not a cache hint. The speed improvement is real and it is the lesser half.

    One detail about how it is enforced, because it explains the numbers in the lab. .dockerignore is applied by the client while it builds the file list, before the transfer decision — so an ignored file is not "sent and then discarded", it is never a candidate. That is also why the exclusion works even for COPY . .: by the time the graph asks for everything, "everything" already has your exclusions taken out of it.

    There is no OCI spec for the build context — the specs cover the image, the runtime and the registry, and stop at the door of how the image is produced. This is the first checkpoint in the intermediate track where the honest answer is no standard governs this, and it is worth sitting with, because it explains the ecosystem you are looking at: builds are where the tools differ most, precisely because nobody wrote a contract for them.

    The closest thing to normative text is BuildKit's own documentation of the syntax, which is a de-facto standard by adoption rather than a specification. Treat its behaviour as observed, not guaranteed — which is exactly why this checkpoint measures instead of asserting.

    You can state what determines the size of a context transfer (the instructions, not the directory), demonstrate it with two builds differing by one line, and explain why .dockerignore is a secrecy control rather than a cache hint.     Gotchas
    • The old advice is not malicious, it is dated — check which builder you are on before repeating either version. The classic Docker daemon really did tar the whole directory. If you are on a CI image pinned to an ancient Docker, or building with something that shells out to the legacy builder, the 101 MB transfer is back. --progress=plain and the context vertex tell you which world you are in, in one build.
    • .dockerignore does not protect you from a RUN that fetches a secret itself. It governs what crosses from your directory, nothing more. A RUN curl that pulls a token into a layer is untouched by it — that is what I6.6's secret mount is for.
    • .dockerignore itself lands in the image when you COPY . . — you can see it in the last listing above. Harmless, but a good reminder that the file is an instruction to the client, not a magic invisible marker.
    • Excluding a path from the context does not remove it from your Git history, and images built before you added the file are unaffected. If a credential was ever in a pushed layer, .dockerignore is the fix going forward and rotation is the fix for what already happened. I6.11 is where that becomes uncomfortably concrete.
    • A missing .dockerignore and an empty one are the same thing, but a typo is not. The file has its own pattern syntax, close to but not identical to .gitignore; an exclusion that silently fails to match looks exactly like a working one until you check the transferred byte count. Check the byte count.

    Kubernetes never sees your build context — but it pays for it. Every byte a careless COPY . . adds is a byte the kubelet's image pull moves on every node that schedules the pod, which is a large share of the cold-start latency people blame on the scheduler; W6.17's slow and failing pulls are frequently a 900 MB image that should have been 90 MB. The secrecy half lands on W3.23: a credential swept into a layer by COPY . . defeats every protection Kubernetes offers a Secret, because it was never a Secret — it is image content, replicated to every node that runs the workload and to every mirror that caches it.

    I6.3

    Deriving the cache key by experiment

    Why it matters

    Build caching is the difference between a nine-minute CI run and a nine-second one, and almost nobody can state the rule it follows. The result is cargo-cult Dockerfiles: instructions shuffled by superstition, --no-cache added because "the cache was being weird". The rule is small and you can derive it from seven builds. Do that once and you will never guess again — and you will be able to read a slow build log and name the offending line.

    The concept

    Every step in a build gets a cache key. Before running the step, the builder computes that key and looks for a previous result with the same one; if it finds it, the step is skipped and its stored output is reused, which the log reports as CACHED. The key is built from two things:

    • What this step is — the parsed instruction, not the raw source line.
    • What it is built on — the identity of the filesystem it starts from, which is the chain ID from I4.12, i.e. a hash over every layer beneath it in order.

    That second half is why the cache is a chain, not a set. A step's key contains its parent's identity, so once any step misses, every step after it has a different parent and therefore a different key and therefore misses too — however unrelated its own instruction is. There is no such thing as a cache hit below a cache miss. Internalise that one sentence and the ordering rule becomes obvious rather than memorised.

    For COPY and ADD there is a third input: the content of the files being copied, hashed. Not their timestamps, not their names — the bytes. So a COPY of an unchanged file hits the cache even if you have touched, moved or rewritten it in place with identical content, and misses the moment a single byte differs.

    Now put those three facts together and the most valuable ordering rule in the ecosystem falls out with no memorisation at all. Copy your dependency manifest, install dependencies, then copy your source. The install step's key depends on the manifest's content and nothing else, so editing application code leaves it hit and skips the slowest step in the build. Do it the other way — COPY . . above the install — and the copy's key contains the hash of your source, so a one-character edit misses, and the chain rule makes the install below it miss too. Every commit reinstalls the world. That is the single most common cause of slow CI, and it is this module's first drill fault (I6.13).

    Two things the lab will show that the folklore gets wrong. Comments do not affect the cache key — the key is computed from the parsed graph, and a comment never becomes a node in it, so you can annotate a Dockerfile freely. And touch does not bust a COPY, because content is hashed rather than mtime; that was true of older builders and is a real behavioural difference, not a myth about nothing.

    Again, no OCI spec — caching is entirely a builder concern, and the OCI specs deliberately describe only the artefact, not its production. But the spec does explain, at unusual length for a standards document, why the second input to a cache key has to be a hash of the whole stack rather than of the layer immediately below. Read it as the argument that a single layer digest cannot identify the filesystem a step starts from:

    Let's say we have layers A, B, C, ordered from bottom to top, where A is the base and C is the top. Defining | as a binary application operator, the root filesystem may be A|B|C. While it is implied that C is only useful when applied to A|B, the identifier C is insufficient to identify this result […]

    This means that if an attacker can define x, relying on C provides no guarantee that the layers were applied in any order.

    The ChainID addresses this problem by being defined as a compound hash.
    OCI image-spec v1.1.1 — config.md § Layer ChainID

    So the chain ID of I4.12 exists to answer exactly the question a cache key needs answered — which stack am I standing on? — and the cache key is a construction on top of it. The cache key is not in any spec; the identity it depends on is, and this is why.

    Gotchas
    • The cache lives in the builder, not in your image. A fresh CI runner starts with nothing, so a Dockerfile perfectly ordered for your laptop can still rebuild everything in CI. That is what registry-backed cache export exists for, and it is why "it's fast locally" is not evidence about your pipeline.
    • RUN keys do not know what the command did. RUN apt-get update has one key forever, so a cached layer can contain a six-month-old package index while the instruction looks current — the classic stale-apt-cache trap, and the reason update and install belong in the same RUN.     • Content hashing includes file mode and ownership, not just bytes. A chmod +x on a copied file is a cache miss even though the content is identical — correct, since the layer really is different, but surprising if you were told "content only".
    • A comment being free is not a licence to reorder freely. Adding a comment is invisible; moving an instruction is not, and I6.1 is the reminder that WORKDIR counts as an instruction for this purpose.
    • --no-cache is a diagnostic, not a fix. If you need it routinely, some step's key does not capture something it depends on — a fetch from a mutable URL, a floating tag, a clock. Find that step; disabling the cache everywhere hides it and costs you the whole build every time.

    Nothing in Kubernetes reads a build cache — but the ordering rule this checkpoint derives is the same shape as the layer-sharing that makes image pulls cheap on a node. Because a chain ID identifies a whole stack, two images built from a shared prefix share those blobs in the node's content store, so the second pull moves only the layers below the divergence point; a Dockerfile ordered manifest-first produces exactly that shared prefix across your whole fleet, and one ordered COPY . .-first gives every build a unique chain from the second layer down. That is the difference between a rollout where most nodes fetch a few megabytes and one where they all fetch the world — the practical face of W6.17's pull-time troubles, and part of why W3.2's init containers are usually pinned to a base the cluster already has.

    I6.4

    Deleting a file makes the image bigger

    Why it matters

    This is I4.11's whiteout lesson arriving as a bill, and it is the checkpoint that changes how you write Dockerfiles for good. The instinct that a RUN rm reclaims space is completely wrong, in a way that costs real money in bandwidth and real minutes in pull time — and, far worse, in a way that means a secret you deleted is still shipped to everyone who pulls your image.

    The concept

    A layer is a diff, and diffs only add. Once a layer is written it is content-addressed (I4.1) and therefore frozen: its digest is its bytes, so nothing later in the build can reach back and remove anything from it. When a later step deletes a file, all it can do is record the deletion — a .wh.<name> entry in the new layer, exactly the encoding you took apart in I4.11.

    So a RUN rm of a 100 MB file does not make the image 100 MB smaller. It makes it slightly larger: the 100 MB is still there in the earlier layer, plus a new layer holding the whiteout. What changes is only what you see at runtime, because the overlay filesystem — the same one you built by hand in B5.15 — reads the whiteout and hides the file from the merged view. Hidden, not gone. Every node that pulls the image still downloads all 100 MB of it.

    The fix is to never let the bytes become a sealed layer in the first place, which means doing the create and the delete inside one step, chained with &&. Then the snapshot taken at the end of that step never contained the file, so the diff never mentions it, and there is nothing to whiten out. This is the whole reason real Dockerfiles chain apt-get update && apt-get install && rm -rf /var/lib/apt/lists/* into one unreadable line: it is not style, it is the only way the cleanup does anything.

    Notice the tension with I6.3, because it is a genuine trade-off and not a solved problem. Chaining reduces size and reduces the number of cache checkpoints; splitting steps gives finer caching and permanent bloat. There is no setting that gives you both — which is why I6.5's multi-stage builds matter so much: they let you be as wasteful as you like in a stage whose layers are then discarded wholesale rather than whitened out.

    And then the part that is not about size at all. Because the bytes are in a pushed, content-addressed blob, a credential written in one step and deleted in the next is in the image — fetchable with curl and tar by anyone who can pull it, with no running container and no exploit involved. I6.11 is where you go and do it. That is why build-time secrets need the mechanism in I6.6 rather than the discipline of remembering to delete.

    The spec is explicit that a whiteout is an instruction to the reader, not a modification of anything. Note the last sentence in particular: it tells the consumer to remove the file from the extracted result, and says nothing about the layer that contains it, because the layer is immutable by construction.

    Once a whiteout is applied, the whiteout itself MUST also be hidden.
    Whiteout files MUST only apply to resources in lower/parent layers.
    Files that are present in the same layer as a whiteout file can only be hidden by whiteout files in subsequent layers.
    OCI image-spec v1.1.1 — layer.md § Whiteouts

    Gotchas
    • The tool's SIZE column and what crosses the wire are different numbers, and both are honest. nerdctl images showed 113.4 MB (uncompressed, as unpacked on disk) while the manifest sums to 108.5 MB (compressed, as transferred). Compare like with like, and prefer the manifest when the question is "what does a pull cost".
    • There is no way to shrink a layer after the fact. Not rm, not truncate, not a later chmod 000. The only options are to not create the bytes in that step (chaining), to not keep the layer at all (I6.5), or to rebuild the image. Squashing tools exist and work by rebuilding, which is worth knowing so you recognise what they are actually doing.
    • Chaining trades size for cache granularity, and sometimes the trade is wrong. A single 400-line RUN is one cache entry: change anything in it and the whole thing reruns. Chain what must be cleaned up together; split what genuinely caches independently.
    • "We removed it in the next layer" and "we deleted the tag" are both non-answers to a leaked secret. The blob is content-addressed and may still be fetchable by digest even after the tag is gone, and any mirror or node that replicated it kept a copy — I5.3 and I5.11 are why. The only correct response is to treat it as disclosed and rotate.
    • A whiteout can hide a file the reader is entitled to see. The spec's rule that whiteouts apply only to lower layers is what stops a producer from claiming to delete something in its own layer — useful to know when you are reading someone else's image and wondering whether a listing is complete.

    Every byte of that 108.5 MB is moved by the kubelet on every node the pod is scheduled to, on every pull that misses the node's content store. A DaemonSet across fifty nodes turns a careless RUN rm into fifty times the waste, and it is a routine contributor to the slow pulls and pull timeouts that present as W6.17's ErrImagePull and ImagePullBackOff under a cold cache or a rate limit (I5.6). The security half aims at W3.23: a Secret in Kubernetes is at least a named object with RBAC on it and encryption-at-rest available, whereas a credential baked into a layer has no access control at all beyond "can pull this image" — which, for a public base image or a shared internal registry, is close to everyone.

    Doing it properly

    I6.5

    Multi-stage: throwing a whole filesystem away

    Why it matters

    I6.4 left you with an unsatisfying choice: chain everything into one giant RUN and lose your cache granularity, or split it up and ship the garbage. Multi-stage builds dissolve that choice. You get to be as wasteful as you like — install a 250 MB toolchain, unpack sources, leave caches lying around — in a stage whose layers are then discarded entirely rather than whitened out. This is the single largest, cheapest improvement available to most real Dockerfiles, and it is one keyword.

    The concept

    A Dockerfile may contain more than one FROM. Each FROM starts a new stage with its own filesystem, and a stage can be named with AS name. COPY --from=name /path /dest then reaches into a previous stage's finished filesystem and copies a file out of it, exactly as COPY reaches into your build context.

    Here is the part that matters, and it is a stronger claim than "delete it afterwards": only the last stage becomes the image. The earlier stages' layers are never referenced by the final manifest, so they are never in rootfs.diff_ids, never pushed and never pulled. Compare that with I6.4, where the 100 MB stayed in a blob anyone could fetch. Here the compiler, the headers, the package index, the source tree and any credential you used along the way were never in a layer of the resulting image at all. There is nothing to extract, because there is nothing there.

    The canonical shape is compile-then-copy: a first stage with the whole toolchain that produces one artefact, and a final stage on a minimal base that copies just that artefact in. The lab below does it with a C program and a static binary, because that makes the arithmetic brutal — 261.9 MB against 8.6 MB for byte-identical behaviour. In a Go or Rust project the ratio is often larger still.

    Two properties fall out that are worth noticing separately. First, stages need not be used: an unreferenced stage is simply not built (I6.6 shows why — the DAG prunes it). Second, and much more useful than most people realise, --target lets you build any stage as an image in its own right. When a compile fails only inside the build, you do not need a second Dockerfile or a hand-assembled debug container: --target build gives you an image of the builder stage, with the toolchain and the sources exactly as the failing step saw them, and you can open a shell in it. This is the underused half of the feature.

    The one real cost is to auditability, and it is worth knowing before you rely on it. Because the earlier stages are not in the image, they are also not in the image's history — the lab shows the final image's history mentioning a bare COPY /hello /usr/local/bin/hello, with the --from=build stripped and no hint that a compiler ever existed. Excellent for not leaking; awkward when the question is "what produced this binary?", which is the gap I6.10 runs into and that provenance attestations exist to fill.

    There is no such thing as a build stage in the OCI specs, and the definition of an image is the reason. An image is its filesystem changes and its execution parameters — and nothing else. There is no third field for "how this was produced", which is precisely why the discarded stages leave no trace, for good and for ill.

    An OCI Image is an ordered collection of root filesystem changes and the corresponding execution parameters for use within a container runtime.

    • COPY --from copies files, not behaviour. That trade-off is the reason W6.3's ephemeral debug containers exist.
    • Stage names are not namespaces. Two stages both named build, or a stage referenced before it is defined, fail in ways whose error messages point at the COPY rather than at the naming. Name stages for what they produce.
    • Multi-stage hides the build from history, which cuts both ways. Nothing in the final image records the compiler version, the source revision or the flags used, so I6.10's audit trail is thinner for exactly the images that are best built. If you need that record, it has to be added deliberately — a LABEL, or the provenance attestations of I6.7's tooling.
    • An unused stage costs nothing, but an unused stage that fails also costs nothing — until someone references it. A broken stage nothing copies from will sit undetected in your Dockerfile indefinitely, because it is never built.

    This is the checkpoint that makes the difference on a real cluster, and the mechanism is I5.3's: image size is pull time, pull time is pod start time, and pod start time is what a rollout, a scale-up under load and a node replacement all wait on. A 90 MB image against a 3.7 MB one is the difference between an autoscaler that reacts in seconds and one that reacts in minutes. The security half aims squarely at what W3.23 is about: a build-time credential in a discarded stage is genuinely not in the shipped artefact, which is a claim you can defend, unlike "we deleted it in the next layer". And the smaller the final base, the more W6.3's kubectl debug becomes your only way in — plan for that before the incident, not during it.

    Docs: No spec covers stages — search the Docker docs for "multi-stage builds" and "build target". On the Kubernetes side, search for "ephemeral containers", which is what you will need once your final stage stops shipping a shell.

    I6.6

    BuildKit: a graph, two mounts, and one leak

    Why it matters

    Everything you have measured so far — the lazy context transfer, the vertex numbers that do not match your line numbers, the cache that survives across builds — comes from one design decision: BuildKit treats a build as a graph to be solved, not a script to be run. Once you see the graph, three features stop looking like unrelated flags and become obvious consequences of it. And one long-standing bad habit becomes indefensible, because you will read a live credential out of an image in one line.

    The concept

    BuildKit parses your Dockerfile into a DAG of operations, where each node's inputs are other nodes. From there, three behaviours follow with no extra machinery:

    • Independent branches run concurrently. Two stages that do not depend on each other have no edge between them, so nothing orders them, so they run at once. The lab measures two 6-second stages completing in 7.7 seconds.
    • Branches nothing needs are never built. Solving a graph means computing what the requested output depends on; a stage nobody copies from is not in that set. --target is just naming a different output node.
    • Steps are addressed by content, not position. Which is I6.3's cache key, now visibly the same idea: a node's identity is its operation plus its inputs' identities.

    The two mounts follow from the same model. A RUN step's output is the filesystem diff it produces — so if you want a directory that the step can read and write but that is not part of that diff, you attach it as a mount rather than putting it in the tree:

    • --mount=type=cache,target=/path — a persistent directory shared across builds, contributing nothing to any layer. This is what finally made pip, npm and apt caches safe to keep: previously your choice was to delete the cache (slow builds) or ship it (fat images).
    • --mount=type=secret,id=name — a file present at /run/secrets/name for the duration of one RUN, and in no layer afterwards. The step can read the real credential; the image contains no trace of it.

    Which brings us to the leak, and it is worth being precise about why it is not a bug. --build-arg was never a secret mechanism. Build args are recorded in the image config's history, in plain text, because history's job is to record what produced each layer — the spec says created_by is "The command which created the layer", and the value of an ARG is part of that command. So a token passed as a build arg is published with the image, readable by anyone who can pull it.

    The lab shows it is worse than the usual warning suggests, in two ways. The token appears twice — once as its own ARG NAME=value entry and once inlined into the RUN entry as RUN |1 NAME=value /bin/sh -c …. And the image's only layer is the 32-byte empty blob from I6.1, because the RUN wrote nothing to disk — so a secret scanner that unpacks layer tars finds absolutely nothing. The credential is pure metadata, and metadata is exactly where nobody looks.

    The spec does not warn you about build args, because from its point of view nothing is wrong: a field defined to hold the command that created a layer is holding the command that created a layer. The leak is a misuse of a working feature, which is why it cannot be fixed and had to be replaced.

    Gotchas
    • --no-cache destroys cache mounts. Measured above: four accumulated lines became one, permanently. Reach for it to diagnose a suspected stale-cache problem, not as a routine "make it clean" flag, or your dependency caches never survive.
    • Cache mounts are shared by target path unless you say otherwise. Two projects both mounting /root/.cache/pip use the same cache — usually fine and occasionally the source of a baffling cross-project interaction. id= is how you separate them; sharing=locked is how you stop two concurrent builds corrupting one.
    • A secret mount protects the layer, not the command's output. If your RUN prints the secret, it is in the build log, and build logs are frequently more widely readable than images — CI systems keep them, forward them, and put them behind weaker access control. Redirect, do not echo.
    • ARG is not ENV, and neither is a secret. An ARG leaks through history; an ENV leaks through history and sits in the config where it is handed to the process at runtime and shows up in /proc/PID/environ — which is B12.13, arriving in a new place.
    • Deleting the tag does not unpublish the token. The config blob is content-addressed and may remain fetchable by digest, and I5.11's cross-repo mounts and any mirror mean copies exist elsewhere. A leaked build arg is a rotation, not a cleanup.
    • Cache mounts live in the builder, so they are invisible to your Dockerfile's correctness. A build that only succeeds because something is in the cache mount fails on a fresh builder — the same class of bug as this module's second drill fault (I6.13).

    The leak is the sharp end for Kubernetes. A registry credential, cloud key or Git token passed as a build arg is published to everyone who can pull the image — which, for an internal registry, is typically every node and every workload in the cluster, since W3.21's imagePullSecrets grant pull access, not per-image access. No amount of care with the Secret objects in W3.23 helps, because the credential never was a Secret; it is image metadata, replicated wherever the image goes. Note too that the history you just read is the same field I6.10 uses as an audit trail — which is the honest summary of this checkpoint: history is a feature, and treating it as private is the mistake.

    I6.7

    Multi-platform: what an index costs and what it buys

    Why it matters

    Half your colleagues are on ARM laptops and most of your nodes are x86, or the other way round, and exec format error is the ugliest way to discover which. I4.8 showed you what a multi-platform image is from the outside; this checkpoint has you produce one, and — more usefully — measure honestly what it costs, because the answer is neither "nothing" nor "don't bother".

    The concept

    One --platform=linux/amd64,linux/arm64 and the builder solves the graph once per platform, then publishes an image index: a small JSON document listing one manifest per platform, each tagged with its platform object. From I4.3, that index is the extra hop at the top of the graph, and from I5.4 it is what a client resolves a tag to before choosing a manifest. The payoff is exactly one thing, and it is real: a single image reference that works on both architectures, so nobody has to think about -arm64 tag suffixes ever again.

    The cost is where honesty is required. Building for a foreign architecture means running foreign binaries, and unless you have a real machine of that architecture, they run under QEMU user-mode emulation — a translation layer registered with the kernel through binfmt_misc, so that executing an aarch64 binary transparently invokes the emulator instead of failing. It is genuinely transparent; it is also slower, and how much slower depends entirely on what the step does. The lab measures two cases on the same machine and gets 1.6× for one and 4.1× for another, which is why quoting a single multiplier is not useful.

    The case that matters is the one that does not appear as a multiplier at all. When this module's labs tried to apk add build-base — a 250 MB toolchain install that takes about twenty seconds natively — inside an emulated arm64 stage, it did not complete in 520 seconds, and the run was abandoned. That is the shape of the real problem: it is not that emulated builds are some tidy factor slower, it is that a step which was comfortably fast becomes effectively unbounded, and CI times out rather than reporting a slowdown.

    Which sets up the decision. If your foreign stage only copies in an artefact built natively — the multi-stage pattern from I6.5, with a Go or Rust cross-compile in a native stage — emulation costs almost nothing, because almost nothing foreign runs. If your foreign stage compiles or installs packages, you want a real builder per architecture and the results combined into one index, which is what projects with heavy builds end up doing. Both routes produce the identical artefact; the index does not record how it was made.

    One last thing worth checking rather than assuming, because it caught this repo out in I4.8: an index's entries are not all images. Docker Hub's alpine:3.21 carries 16 entries for 8 architectures, the extra 8 being attestation manifests marked platform: unknown/unknown. The index you build below has exactly 2 entries and no attestations, because nothing here asked for them — so "count the entries and divide by the platforms" is a habit that works on your own images and misleads on everyone else's.

    The platform object is the whole mechanism — it is what makes an entry selectable. Two details in the normative text pay off directly: the property is only SHOULD be present, so an entry may legally have none (which is how attestation manifests get away with unknown/unknown), and architecture and variant are separate fields, so arm64 plus v8 never concatenates into a string like "arm64v8".

    Building without Docker

    I6.8

    Under the friendly tool: frontend, exporter, and where the result lands

    Why it matters

    nerdctl build and docker build present a build as one atomic thing: Dockerfile in, image in your local image list, done. That framing hides two decisions that turn out to matter enormously — who parses the Dockerfile, and where the result is written — and it is the reason people are surprised that BuildKit can build an image on a machine with no container runtime at all. Driving buildctl once makes both decisions explicit, and one of them will explain a "but I just built it" failure you have already met.

    The concept

    BuildKit does not natively understand Dockerfiles. Its own language is LLB, the graph from I6.6, and everything in front of and behind that graph is pluggable:

    • A frontend turns some build definition into LLB. The Dockerfile frontend is called dockerfile.v0, and — this is the part that surprises people — it is itself distributed as a container image, which is why a Dockerfile can start with # syntax=docker/dockerfile:1 and get parser features newer than your builder.
    • An exporter decides what happens to the solved result: write it into a container runtime's image store, write an OCI layout to a tarball, push it straight to a registry, or just dump the resulting filesystem into a directory with no image involved at all.

    That decomposition is why alternative build definitions exist, and why the same builder can produce an image on a machine with no runtime — which is exactly what you want in CI, where "build and push" should not require a daemon that can start containers. It is also why I6.9 is possible at all: if the exporter is the only thing that knows about images, then producing an image is just writing files in the right shape.

    The lab below builds one Dockerfile four ways and gets the same manifest digest every time — sha256:05f3b7aaf28e… from nerdctl build, from buildctl with the image exporter, and from the OCI-tarball exporter. That is the strongest possible statement that nerdctl build is a thin client over the same buildkitd: same graph, same bytes, three destinations.

    And then the detail worth the whole checkpoint. The two tools wrote that identical image into different containerd namespaces — nerdctl into default, buildctl into buildkit — so nerdctl run could not find the buildctl-built image and tried to pull it from a registry instead. The image existed, on the same machine, in the same content store, under a name that resolved to nothing. If you remember one thing from this checkpoint, make it that: "the image is not there" and "the image is not in the namespace you are looking in" produce the same error message. It is the same class of confusion as I5.13's two non-interchangeable config_path settings, and for the same underlying reason.

    No spec governs builders, frontends or exporters — but the OCI image layout is a spec, and it is what the oci exporter emits. That is the seam that makes the pluggability useful: an exporter that writes a standard layout produces something every other tool can read without knowing what built it.

    You can build a Dockerfile with buildctl from first principles, naming the frontend and the exporter explicitly, and you can send one build to a runtime, a directory, a tarball or a registry without changing the Dockerfile.     Gotchas
    • "Image not found" from nerdctl may mean "not in this namespace", and the error will talk about the network instead. It falls through to a pull, so what you see is a DNS or connection failure against a registry — pointing you at exactly the wrong subsystem. Check ctr -n buildkit images ls before you debug your mirror.
    • --local context=. and --local dockerfile=. are two separate mounts, and forgetting the second is the usual first error. They are separate because they genuinely can differ — a Dockerfile from one place and a context from another is a normal thing to want, and nerdctl's single . hides that they were ever distinct.
    • The Dockerfile frontend is a container image, so parsing can be newer than your builder. That is what # syntax=docker/dockerfile:1 selects, and it means a Dockerfile using a new feature can work on an old buildkitd — and that a build can fail because the frontend image could not be pulled, which looks nothing like a syntax error.
    • type=local exports the filesystem of the final stage, not an image, and it drops the config entirely. No Cmd, no Env, no layer boundaries — just files. If you export a whole base image this way you get every file merged flat, which is rarely what you wanted.
    • Same digest is not the same reproducibility claim. These four builds matched because they ran the same graph on the same machine minutes apart; a build with a timestamp, a network fetch or a package index in it will not match itself tomorrow. Reproducible builds are a separate discipline, and SOURCE_DATE_EPOCH is where it starts.

    This is the checkpoint that explains how images get built inside a cluster without the thing everybody rightly refuses: mounting the node's container socket into a pod. If a build needs no runtime — only a frontend, a solver and an exporter that writes to a registry — then a build pod needs no access to the node's containerd at all, which is why Kaniko, Buildah and BuildKit-as-a-pod exist and why W7.9's ServiceAccount-scoped credentials are enough for a CI job. The namespace confusion has a Kubernetes cousin too: containerd's namespaces are why I5.13 insists that ctr proving a pull works proves nothing about the kubelet, which uses the k8s.io namespace and a different config path entirely.

    I6.9

    An image by hand: tar, sha256sum and curl

    Why it matters

    This is the checkpoint where images stop being a black box permanently. You are going to produce a working container image — one a real runtime pulls and runs — using no builder, no daemon, no Docker and no privileged operation of any kind. Four shell tools. When it runs, you will have proved to yourself that everything in I4, I5 and I6 was not an abstraction over something deeper: that was the deeper thing.

    The concept

    Look at what an image actually requires, from I4.3: a layer (a tar file), a config (a JSON document), a manifest (a JSON document pointing at both by digest), and optionally an index. Then look at what I5.9 says publishing requires: PUT the blobs, then PUT the manifest.

    There is no privileged operation anywhere in that list. No namespaces, no mounts, no cgroups, no daemon, no root. Because — and this is the sentence worth carrying out of the module — building an image is not running a container. It is writing tar files and JSON documents and computing hashes. Running a container needs the kernel machinery of B6, B7 and I2; producing the artefact that will later be run needs none of it.

    That realisation is what the entire unprivileged, daemonless build ecosystem stands on. Kaniko, Buildah in rootless mode, ko, apko, Nix's container output, Bazel's rules — none of them are clever workarounds for a missing daemon. They are the straightforward consequence of noticing that the format has no privileged requirements. It is also why building images inside a Kubernetes cluster without mounting the node's container socket is possible at all, which is the practical thing this checkpoint buys you.

    There is exactly one step that genuinely does need a container: executing a RUN instruction, because that means running someone's code against a filesystem. Everything else — FROM, COPY, ENV, CMD, computing layers, writing the config, pushing — is file manipulation. That single exception is what the mini project in I6.12 hands to runc, and it is why tinybuild.py can be a short program rather than a build system.

    One practical note before you start. The image below has no base layer at all — one layer, containing one statically linked binary. That is deliberate: a static binary needs no loader, no libc and no /etc, so the smallest correct image really is one file, and nothing distracts from the format. It is also, exactly, what FROM scratch means.

    Two requirements make the hand-built config valid, and they are the only ones you must not get wrong. diff_ids holds the hashes of the uncompressed layers while the manifest's descriptors hold the digests of what was actually transferred — I4.10's two hashes, now something you have to compute separately rather than merely observe.

    rootfs object, REQUIRED

    The rootfs key references the layer content addresses used by the image. This makes the image config hash depend on the filesystem hash.

      An array of layer content hashes (DiffIDs), in order from first to last.

    You have pushed a working image built with no builder, and a real runtime ran it. You can state which single Dockerfile instruction genuinely needs container machinery and why the others do not, and you can explain what Kaniko and Buildah-rootless are actually exploiting.

    Gotchas
    • The two hashes are not interchangeable and swapping them fails late. Put the compressed digest in diff_ids and the push succeeds, the manifest validates, and the pull fails when the client decompresses a layer and gets a hash the config did not promise. Both documents are well-formed; the error arrives at the consumer.
    • gzip without -n embeds a timestamp, so your layer digest changes every time you build the same bytes. Harmless here, fatal to any caching or reproducibility claim, and a common source of "why did the digest change when nothing changed".
    • registry:2's upload Location is absolute and already has a query string. Prefixing your registry URL yields a malformed URL, and appending ?digest= instead of &digest= yields an equally confusing failure. The spec permits either form of Location, so a client must handle both — the kind of detail I5.10's hand-rolled upload exists to teach.
    • No index means no platform negotiation, and no client will warn you. This image is amd64 because its config says so; run it on arm64 and you get exec format error, exactly I6.7's failure. Adding an index is one more small JSON document.
    • A dynamically linked binary in a one-layer image fails in a way that looks like the binary is missing. The kernel cannot find the loader, so you get "no such file or directory" for a file that is demonstrably there. This is the single most common FROM scratch mistake, and the reason step 1 checks for statically linked.
    • history is optional and yours is a fiction. "tar, jq and sha256sum" is a perfectly legal created_by. Keep that in mind for I6.10: an image's audit trail is whatever its producer chose to write.

    The kubelet cannot tell the difference. It resolves your tag, fetches the manifest, pulls the blobs, verifies the digests and hands the result to containerd exactly as for an image from Docker Hub — because the contract is the artefact, not the process, which is the thesis of this whole track. Practically, this is the checkpoint that unblocks in-cluster builds: a pod that needs no privilege, no container socket and no daemon to produce images is a pod you can actually run under a reasonable policy, and it only needs registry credentials of the kind W7.9 wires to a ServiceAccount. It should also mildly alarm you: anyone who can push to a repository can publish an image whose history claims anything at all, which is the gap that image signing and provenance attestations exist to close, and why W3.6's advice to pin a digest is worth more than trusting a tag.

    Reading images others built

    I6.10

    Reading someone else's build: attributing bytes to instructions

    Why it matters

    Most images you deal with, you did not build. When one of them is 400 MB and slowing every rollout, "it's a big image" is not actionable — "57% of it is one apt-get install in the base image's Dockerfile" is. This checkpoint turns history into that answer, using nothing but skopeo and jq against a registry, with no pull at all. It is also where you learn precisely how much to trust what you read.

    The concept

    You already know the two fields. The manifest's layers array holds each layer's compressed size, in order. The config's history array holds one entry per build step, in order, each with created, created_by and possibly empty_layer. And from I6.1, the non-empty history entries correspond one-to-one, in order, with the layers.

    So the join is mechanical: filter history to the entries without empty_layer, zip that list against layers by position, and you have bytes attributed to build steps. Sort descending and the first line usually explains the whole image. That is the entire technique, it is about six lines of jq, and it works on any image in any registry because both documents are just JSON you can fetch.

    Two caveats, and they are not footnotes — they are the reason this is a starting point for investigation rather than an answer.

    First, created_by is free-form text written by whichever tool produced the image. Not a specification, not validated, not necessarily a Dockerfile instruction at all. The lab makes this vivid: one of python:3.13's seven layers reports created_by of # debian.sh --arch 'amd64' out/ 'trixie' '@1783900800', which is Debian's own rootfs build script and nothing to do with any Dockerfile. Meanwhile I6.9's hand-built image happily claims it was created by "tar, jq and sha256sum", because nothing stops it. Treat created_by as a strong hint from a cooperative producer, never as evidence.

    Second, history can be absent or useless. It is an OPTIONAL field. A squashed image, a hand-assembled one, or anything from a builder that does not bother has no usable trail — and, as I6.5 showed, a multi-stage build legitimately erases the build stage from the record, so the best-built images often have the thinnest history. Both facts are why SBOMs and provenance attestations exist: they are the same idea done deliberately, signed, and with a schema, instead of inferred from a text field.

    There is a third thing worth knowing, and it is the reason this works without a pull. Manifests and configs are small — hundreds of bytes to a few kilobytes — while layers are hundreds of megabytes. Fetching the two documents costs essentially nothing, and from I5.3 you know that resolving and reading a manifest does not move a rate-limit counter the way pulling does. You can audit an image far more cheaply than you can download it.

    Everything this technique relies on is normative, and so is its central weakness. The ordering guarantees are firm; the content of created_by is described in six words and constrained by nothing.

    history array of objects, OPTIONAL

    Describes the history of each layer.
    The array is ordered from first to last.

    - created_by string, OPTIONAL
      The command which created the layer.
    OCI image-spec v1.1.1 — config.md § Properties

    Note that history is OPTIONAL and its ordering is guaranteed, while created_by is OPTIONAL and its content is unconstrained. That asymmetry is exactly what makes the positional join reliable and the attribution advisory.

    I6.11

    Finding a secret somebody believed they had deleted

    Why it matters

    Everything in this module now converges on one exercise. You are going to build an image the way a competent, careful engineer builds one when they need a deploy key during the build — copy it in, use it, delete it, verify it is gone — and then recover that key from the published image with two commands. Not to be clever: because the fix for this class of mistake depends entirely on understanding that it is not a mistake in the deletion, and the only way to believe that is to do it.

    The concept

    There is no new mechanism here. I6.4 established that a later layer cannot remove bytes from an earlier one; it can only add a whiteout. I4.1 established that layers are content-addressed and therefore immutable. I5.2 established that a blob URL is fetchable by anyone permitted to pull the repository. Put those three together and the conclusion is unavoidable: a file written in one build step and deleted in a later one is in the published image, readable by anyone who can pull it.

    What makes it worth its own checkpoint is how little the attack needs. Not root, not an exploit, not a running container, not even a full pull — curl for one blob and tar to list it. The verification the author performed was real and honest: ls says the file is gone, find / returns nothing, because the overlay filesystem is faithfully applying the whiteout exactly as B5.15 taught. The runtime view is correct. The runtime view is not the artefact.

    And there are two independent leak channels, which matters because they need different defences and different searches:

    • Layer contents — a file that was in the tree when a step's snapshot was taken. Found by unpacking layer tars. Defended against by never letting the bytes into a sealed layer: a secret mount (I6.6), or a discarded stage (I6.5).
    • Config metadata — a build arg or an ENV, sitting in history. Found by reading one small JSON document, as in I6.6. Invisible to any scanner that only unpacks layers, because the filesystem genuinely contains nothing.

    So the response, when this happens to you, is fixed and there is no negotiating with it. Treat the credential as disclosed and rotate it. "We removed it in the next layer" describes the bug rather than a fix. "We deleted the tag" does not help either: the blob is content-addressed and may remain fetchable by digest, and per I5.11 and I5.3 any mirror, node or downstream repository that replicated it kept its own copy. You cannot recall bytes you published.

    The spec spells out that whiteouts are a directive to the party applying the layers, and that they never touch the layer holding the file. Read the last clause as a security property: the file is not deleted, its presence is hidden from the extracted result. Anyone who reads the archive instead of the result is unaffected.

    • Two channels, two searches. Layer tars for file contents, the config's history for build args and ENV. Checking only one is the most common gap in a home-grown scanner, and the metadata channel is the one that leaves no filesystem evidence at all.
    • Deleting the tag does not unpublish the blob.     • Rotation is the fix, and it is not optional. The credential was disclosed at push time to everyone with pull access. Rebuilding the image correctly is necessary and does nothing about the copies already out there.
    • Public base images are a much larger surface than you think. "Anyone who can pull" for a public image means anyone at all, and the same technique works on every image on every public registry. That is a reason to assume disclosure quickly, and a reason to be careful what you go looking for in other people's images.
    • Git history is a separate leak with the same shape. If the key was ever committed, .dockerignore (I6.2) and a rebuilt image do not touch it. Rotate once, fix both.

    This is the sharpest possible argument for why W3.23's Secrets have to be a runtime object rather than something baked in. A Kubernetes Secret is at least a named API object with RBAC on it, an audit log, and encryption at rest available; a credential in a layer has no access control finer than "can pull this image", which — via the imagePullSecrets of W3.21 — is typically every node in the cluster and every workload that can read a pull secret. Note as well that the node's content store keeps those layers after the pod is gone, so a leaked key persists on disk across every node that ever ran the workload, which is a far wider blast radius than the Secret machinery would ever have given it.

    I6.12

    Mini project — tinybuild.py, a builder in 440 lines

    Why it matters

    I6.9 assembled one image by hand, once, with a fixed layer. This project turns that into a program: read a Dockerfile, execute its steps, and produce an image. It is the checkpoint where the three specs stop being separate subjects — you will use the runtime spec to execute a RUN, the image spec to write what it produced, and the distribution spec to publish it, in one file, and see how small the glue between them actually is.

    What to build

    labs/intermediate/tinybuild.py is the finished version to read after you have attempted your own. It supports five instructions and nothing more:

    InstructionWhat it doesWhich spec
    FROM ref | scratchpull the base and extract its layers in orderdistribution + image

    ENV k=vamend the configimage

    Four design decisions are worth making deliberately, because each one is a checkpoint from this module arriving as code:

    • Reuse pull.py for FROM, unchanged. It already resolves references, authenticates, verifies every digest and writes an OCI layout. Call it by swapping sys.argv rather than refactoring it — I5.14's deliverable stays exactly as it shipped, which is the whole benefit of having written it.
    • Compute diffs by comparing filesystem trees. Snapshot the metadata of every path before a step and after it; changed paths go into the tar, vanished paths become .wh. entries. This is what containerd's own walking differ does, which is why — as I4.11 discovered by measurement — a replaced directory yields one .wh.<child> per former child rather than an opaque marker. Both encodings are legal; be honest about which yours emits.
    • Hand RUN to runc, and nothing else. Write an I2 bundle, point root.path at the working rootfs, set process.args, run it. That single call is the only privileged operation in the program — everything else is tar files, JSON and HTTP.
    • Push blobs first, manifest last. I5.9's order is not a convention, it is the consistency model: a manifest that references a missing blob is a broken image that no client can repair.

    Two traps this module already paid for, now encoded as two lines: gzip must be given mtime=0 or the header timestamp changes the layer digest for identical bytes (I6.9), and registry:2's upload Location is absolute with a query string already attached, so the digest is appended with & and the registry root must not be prefixed.

    Gotchas
    • A metadata-only differ is not a content differ, and this one is metadata-only. A step that rewrites a file with identical bytes but a new mtime produces a layer here, where a COPY cache key (I6.3) would have hit. Real differs make the same trade for the same reason — walking a tree is cheap, hashing every file is not.
    • Applying whiteouts on extraction is not optional. Extract a base image's layers as plain tars and any file its upper layers deleted comes back. The spec's whiteout rules are consumer obligations, and skipping them silently corrupts your rootfs.
    • Order the tar's parent directories yourself. A tar entry for app/note whose parent app/ is absent extracts unpredictably. Collect every ancestor of every changed path — that is where the surprising +2 changed comes from.
    • Numeric owners only. Without them the tar records your machine's user names, which means the layer digest depends on the builder's /etc/passwd. Correct-looking, unreproducible, and hard to spot later.
    • runc delete before and after, always. A leftover container record makes the next build fail with "already exists", and per I3.9 that record lives in a state directory which can outlast the container it describes.
    • This is a teaching builder, not a build system. No cache, no parallelism, no multi-stage, no ARG. That is the point — the gap between it and BuildKit is caching and scheduling, not understanding of the format.

Turn it round for the security lesson: since anyone who can push can publish an image whose history claims anything at all, pinning a digest as in W3.6 is worth strictly more than trusting a tag and a plausible-looking build trail.

    I6.13

    Debugging drill — the slow pipeline and the image that only works at home

    Why it matters

    Two faults, both extremely common, and neither announces itself. The first makes every build slow while the build log looks entirely normal. The second produces a green build and a broken image, which is the worse failure because nothing anywhere reports an error. Both are diagnosed from artefacts you now know how to read, and the second one's signature is a digest you have already memorised.

    Fault 1 — the pipeline that reinstalls the world on every commit

    Symptom. CI takes the same time on a one-character README change as on a dependency bump. Nobody can reproduce it locally "because it's fast the second time".

    Stage 1 — where exactly do you look?

    At the CACHED markers, and at the first step that lost one. Comparing the two logs: WORKDIR is still CACHED, COPY . . is not, and everything below it is not either. That is the whole diagnosis available from the log alone — the first miss is the cause and the rest are consequences of the chain rule from I6.3. Note what you do not need: no timing instrumentation, no cache statistics. Just which line stopped saying CACHED.

    Stage 2 — why did that step miss, when the requirements file did not change?

    Because COPY . .'s cache key includes the content of everything it copies, and src/app.py is inside .. The install step below it did not miss on its own instruction — its instruction text is identical — it missed because its parent changed. A cache miss cannot have hits below it, so putting a volatile input above the expensive step guarantees the expensive step reruns for every commit. The install is not slow; it is being asked to run when it did not need to.

    Copy only the dependency manifest, install, and copy the source afterwards. The install's key then depends on requirements.txt alone.

Two caveats before you celebrate in a real pipeline: the cache lives in the builder, so a fresh CI runner still pays for everything unless you export cache to a registry; and remember from I6.1 that WORKDIR is a layer-producing step, so moving it has the same invalidating effect as moving a COPY.

    Fault 2 — the image that runs on the machine that built it

    Symptom. Works on the developer's laptop. CI builds it green, and it crashes in the cluster. No error anywhere in the build.

    1. Reproduce the developer's side. app.conf exists locally and was never committed — which is a normal state for a config file. 
      mkdir -p ~/i6/d2 && cd ~/i6/d2
echo "listen_port = 8080" > app.conf
echo "print(1)" > main.py
cat > Dockerfile <<'EOF'
FROM alpine:3.21
COPY . /src/
RUN cp /src/app.conf /etc/app.conf 2>/dev/null || true
RUN rm -rf /src
CMD ["sh","-c","cat /etc/app.conf"]
EOF
sudo nerdctl build --no-cache -q -t i6/d2:dev .
sudo nerdctl run --rm i6/d2:dev
      listen_port = 8080
    2. Now reproduce CI, where the file is not in the context because it is not in the repository. 
      echo "app.conf" > .dockerignore
sudo nerdctl build --no-cache -q -t i6/d2:ci .
sudo nerdctl run --rm i6/d2:ci
      sha256:6d1b93f0485804ab1ec53d7c4c172e8ea6bf5e41b29dadf6509341c022478308

cat: can't open '/etc/app.conf': No such file or directory

      The build printed a digest and exited 0. The failure is deferred to whoever runs the image.

    Stage 1 — the build succeeded. What is the first thing to compare?

    The two images' layers, not their behaviour. You have a working image and a broken one from the same Dockerfile, which is the ideal debugging position: diff the artefacts. Pull each manifest and list the layer sizes. Resist starting with nerdctl run … sh — the runtime view is what I6.11 just taught you not to trust, and here it will only tell you the file is missing, which you already know.

    Stage 2 — read the layer sizes 
    for t in dev ci; do
  M=$(sudo ctr -n default images ls name==docker.io/i6/d2:$t | awk 'NR==2{print $3}')
  echo "--- i6/d2:$t"
  sudo ctr -n default content get "$M" | jq -r '.layers[] | "      \(.size)  \(.digest[0:26])"'
done

      3646875  sha256:897d797d2723cf0e318
      313  sha256:1b2680a982310a7273b
      154  sha256:3e938fcc04564db4ea7

--- i6/d2:ci
      3646875  sha256:897d797d2723cf0e318

      73  sha256:68739a056a6e973756a

    There it is, and you know that digest by heart: sha256:4f4fb700ef54… is the empty layer from I6.1. The third step — the cp — produced 154 bytes on the developer's machine and nothing at all in CI. An empty layer where a step was supposed to produce something is a readable signature, and it points at the exact instruction.

    Stage 3 — the cause and the fix

    The cause is || true. It converts "the file I need is missing" into "this step succeeded", so the build cannot fail and the error surfaces hours later as a crash somewhere else. The 2>/dev/null makes it worse by hiding the message that would have named the file.

    The immediate fix is to delete both and let the build fail where the mistake is:

    RUN cp /src/app.conf /etc/app.conf

    The real fix is architectural, and it is the same conclusion I6.2 reached from the other direction: a config file that differs per environment does not belong in the image at all. Baking it in means one image per environment and a build that depends on the builder's working directory; a ConfigMap means one image everywhere and the value supplied at run time, which is exactly what W3.21 is for. Two general lessons worth writing down: never let a build step swallow a failure, and if an image behaves differently depending on where it was built, compare layer digests before you compare behaviour.

    Verify

    You can find the cause of a slow pipeline from a build log by locating the first lost CACHED, and fix it by reordering. You can diagnose a green build that produces a broken image by comparing layer digests between a working and a failing image, and you recognise the empty-layer digest as the signature of a step that did nothing.

    Gotchas
    • "It's fast locally" is not evidence. Both faults hide behind a warm cache and a complete context. Reproduce with the constraints CI actually has — a fresh builder, and only committed files.
    • The first cache miss is the cause; every miss below it is a consequence. Reading the log bottom-up leads you to the expensive step and away from the reason it ran.
    • || true and 2>/dev/null in a RUN are how green builds produce broken images. If a step may legitimately do nothing, say so with a test that fails loudly when the assumption breaks — not by discarding the exit status.
    • The empty-layer digest is a diagnostic, not a curiosity. sha256:4f4fb700ef54… compressed, sha256:5f70bf18a086… as a diff_id. Seeing either where a step should have produced output tells you which instruction silently did nothing.

    Fault 2 is the honest origin of a large share of "it works in staging, not in production" incidents, and it is why W6.16's CrashLoopBackOff investigation so often ends in the build rather than the cluster: the pod is doing exactly what the image tells it to, and the image is missing a file nobody noticed was missing. The structural answer is W3.21 — one image, configuration supplied per environment — and the reason it is worth the ceremony is that a ConfigMap that is absent fails visibly at pod start, whereas a file that is absent from a layer fails whenever the code happens to read it.

    Quiz

    1. A Dockerfile has nine instructions: FROM, ENV, LABEL, WORKDIR, RUN, COPY, USER, EXPOSE, CMD. How many layers does the resulting image have, and how many history entries?
      Answer

      Four layers — the base, WORKDIR, RUN and COPY — and ten history entries, because alpine contributes two of its own. WORKDIR is the one people get wrong: it goes through the filesystem-snapshot path, so it consumes a diff_id slot and is never marked empty_layer. The check is always the same arithmetic: history entries minus empty ones equals layers, so 10 − 6 = 4.

    2. You point WORKDIR at /tmp, which already exists in the base image. Does that produce a layer, and if so what is in it?
      Answer

      Yes — and this is the sharper version of the same trap. The step still takes a slot; the diff simply comes out empty, so the slot holds the empty layer: 1024 zero bytes (two tar terminator blocks), diff_id sha256:5f70bf18a086…, compressing to the 32-byte blob sha256:4f4fb700ef54…. Two such steps dedupe to one blob, because content addressing does not care that they came from different instructions.

    3. Your build directory holds a 100 MB file that no instruction references. Your Dockerfile says COPY app.txt /app.txt. How much does the context transfer cost?
      Answer

      38 bytes, measured. BuildKit resolves the graph first and transfers only the paths the graph references, so the 100 MB file is never sent. The widely repeated claim that "the whole context is uploaded" was true of the old Docker daemon, which tarred the directory up front, and is false here. Change one line to COPY . /src/ and the same directory transfers 104.89 MB — the cost is a property of your instructions, not of your directory.

    4. So if the context is transferred lazily, why is .dockerignore still a security control rather than just a speed tweak?
      Answer

      Because COPY . . is extremely common and it widens the graph's reference to everything — at which point a .env or a private key is both transferred and baked into a layer that gets pushed to a registry, where I6.11's two commands recover it. .dockerignore is enforced while the client builds its file list, upstream of what the graph can ask for, so the exclusion holds even for COPY . .. Read it like a firewall rule.

    5. Name the three inputs to a step's cache key, and explain why a cache miss can never have a hit below it.
      Answer

      The parsed instruction, the identity of the filesystem it starts from (the chain ID of I4.12), and — for COPY/ADD — the content of the files being copied. Because each key contains the parent's identity, one miss changes every descendant's parent and therefore every descendant's key. That single fact is the whole justification for copying your dependency manifest before your source, rather than a rule to memorise.

    6. Which of these break the cache: adding a comment, editing an uncopied file in the context, touching a copied file, chmod +x on a copied file?
      Answer

      Only the last. Comments never become graph vertices, so they are invisible. A file nothing references is in no key. touch does not matter because content is hashed rather than mtime — that was different on older builders, so it is a real behavioural change and not a myth. chmod +x does bust it, because mode is part of what a layer records.

    7. A RUN downloads a 100 MB file and the next RUN deletes it. What does the image cost, and where is the file?
      Answer

      Measured: 108,536,725 bytes in three layers, against 3,646,907 in two when the same work is chained with && — a factor of thirty. The file is still in the second layer, entirely intact, and the third layer is 77 bytes holding one .wh.big.bin entry. Two curl-and-tar commands recover all 104,857,600 bytes from the registry, which is why this is a disclosure problem and not only a size problem.

    8. Why is a multi-stage build a categorically stronger guarantee than deleting a secret in a later step?
      Answer

      Because the discarded stage's layers are never referenced by the final manifest — they are not in rootfs.diff_ids, never pushed, never pullable. There is nothing to extract because there is nothing there, whereas a whiteout only hides bytes that remain fetchable. Measured on the same program: 261.9 MB single-stage against 8.598 MB multi-stage. The cost is auditability: the final image's created_by reads COPY /hello /usr/local/bin/hello with the --from=build stripped, so nothing records that a compiler was ever involved.

    9. You pass a token as --build-arg and the RUN writes nothing to disk. Is the token in the image?
      Answer

      Yes, twice, and in the one place nobody scans. The only added layer is the 32-byte empty blob, so the filesystem genuinely contains nothing — but history holds both ARG GITHUB_TOKEN=ghp_… and, inlined into the RUN entry, RUN |1 GITHUB_TOKEN=ghp_… /bin/sh -c …. One curl and one jq against the registry prints it. This is not a bug: created_by is specified as "the command which created the layer", and the arg is part of that command — which is exactly why the secret mount had to be invented.

    10. What does --no-cache do to a --mount=type=cache directory?
      Answer

      It empties it, permanently. Measured: four accumulated lines dropped to one, and the next ordinary build saw two rather than five — destroyed, not shadowed. So the common habit of adding --no-cache "to get a clean build" also throws away every package cache in the Dockerfile. Related surprise: cache mounts are keyed by their target path by default, so two unrelated projects mounting /root/.cache/pip share one cache unless you give them an explicit id=.

    11. How much slower is an emulated arm64 build than a native amd64 one?
      Answer

      There is no single number, and insisting on one is the mistake. On one machine, one build, identical steps: 4.1× for an interpreter-bound loop (0.8 s against 3.3 s) and 1.6× for a hashing step. The case that matters is not a multiple at all — an emulated apk add build-base did not finish in 520 seconds where the native install takes about twenty. The real failure mode is a job timeout, not a slowdown, which is why the good strategy is to compile natively and COPY --from the artefact so almost no foreign code runs.

    12. You build with buildctl, then nerdctl run the image and get a connection-refused error against a registry. What happened?
      Answer

      The image is on the machine, in a different containerd namespace — nerdctl uses default, buildkitd's containerd worker writes to buildkit. Not finding it locally, nerdctl concluded it was remote and tried to pull it, so the error names your mirror instead of the real problem. "Not there" and "not in the namespace you are looking in" are indistinguishable from the message; ctr -n buildkit images ls settles it. Same trap as I5.13's two non-interchangeable config_path settings.

    13. Which single Dockerfile instruction genuinely needs container machinery, and why does that matter?
      Answer

      RUN, because it executes someone's code against a filesystem. FROM, COPY, ENV, CMD, computing layers, writing the config and pushing are all just tar files, JSON and HTTP — no namespaces, no mounts, no daemon, no root. That is why I6.9 can build a working image with four shell tools, why Kaniko and rootless Buildah exist, and why building images inside a cluster without mounting the node's container socket is possible at all.

    14. An image works on the machine that built it and fails everywhere else, and the build exited 0. Where do you look first?
      Answer

      At the two images' layer sizes, not at their behaviour — you have a working and a failing artefact from one Dockerfile, which is the ideal position. In the drill the failing image's third layer is sha256:4f4fb700ef54…, the empty layer, where the working one has 154 bytes: the step produced nothing. An empty layer where a step should have produced output is a readable signature that names the guilty instruction. The cause was || true converting "the file is missing" into "this step succeeded".

    15. You need to know which layer makes a 412 MB public image big. What do you download?
      Answer

      Two small JSON documents — the manifest for layer sizes and the config for history — and no layers at all. Filter history to entries without empty_layer, zip against layers by position, sort descending. On python:3.13 that identifies one apt-get install holding 236,258,363 of 412,660,988 bytes. Check the correspondence first (12 entries − 5 empty = 7 layers), and remember created_by is unvalidated free-form text: one of those layers reports # debian.sh --arch 'amd64' …, which is not a Dockerfile instruction at all.

    • You sort instructions into layer-producing and config-amending by asking whether the step goes through the snapshot path, so WORKDIR no longer surprises you, and you check any image's classification with two jq expressions.
    • You can say what a build context actually transfers and demonstrate it with two builds differing by one line, and you treat .dockerignore as a secrecy control rather than a cache hint.
    • You derived the cache key rather than memorising rules, so the copy-manifest-then-install ordering is a consequence you can re-derive, and you can name the offending line in a slow build log.
    • You price a RUN rm before writing it, and you reach for a discarded stage or a secret mount instead of trusting a deletion.
    • You build multi-platform images knowing what emulation costs for your workload, and you recognise exec format error as a missing index.
    • You can drive buildkitd directly, send one build to a runtime, a directory, a tarball or a registry, and diagnose "I built it but the tool cannot find it" as a namespace question.
    • You have built a working image with tar, sha256sum and curl, and written a program that does it from a Dockerfile — so unprivileged in-cluster builders are no longer mysterious.
    • You can audit any image in any registry for its bulk and for two independent kinds of leaked credential, and you know that "we deleted it in the next layer" is a description of the bug.
