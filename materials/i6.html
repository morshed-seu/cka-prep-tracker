    I6 — Building images

    A Dockerfile is two things at once: a sequence of layer-producing operations, and a cache-key function. Learn to read it as both — then build an image with no Dockerfile and no Docker, which is the only way to be certain you understood it.

    This module is where images stop being something a tool produces for you. Four of the corrections in it are to beliefs almost everyone holds — that WORKDIR is free, that the whole build context is uploaded, that a comment busts the cache, that rm reclaims space — and every one of them is settled here by measurement rather than assertion. By the last checkpoint you will have built an image with no Dockerfile, no builder and no daemon, using nothing but tar, jq and sha256sum, which is the only way to be certain the format holds no more mysteries.

    Checkpoints13 Hours~5 PrerequisitesI4, I5
    • Semantics. Sort any instruction into layer-producing or config-amending by asking about mechanism rather than reciting a list; say what a build context actually transfers and why .dockerignore is a secrecy control; derive the cache key from seven builds and predict which edit stops the cache hitting; and price the layer that a RUN rm adds instead of removing.
    • Doing it properly. Write a multi-stage build and use --target to debug the builder stage; use BuildKit's DAG, cache mounts and secret mounts, and find a --build-arg token sitting in plain text in an image's history; build a multi-platform image and pay the emulation bill knowingly.
    • Building without Docker. Drive buildkitd through buildctl to see the frontend and exporter the friendly tools hide; then assemble a working image entirely by hand, with no builder in the picture at all.
    • Reading images others built. Use history as the audit trail it is, attribute an image's bulk to the instruction that caused it, and recover a credential from a layer that its author believed was deleted.

    I4 (layers, digests, chain IDs) and I5 (you need somewhere to push to — the local registry:2 from I5.9).

    Semantics

    I6.1

    Two kinds of instruction, and the one that fools everybody

    Why it matters

    A Dockerfile looks like a shell script, which is exactly why people misread it. It is not a script — it is a list of steps, where each step either changes the filesystem (and so becomes a layer you will store, push and download forever) or merely writes a note in the image's config (and so costs nothing at all). Sorting your instructions into those two piles is the single skill that turns build behaviour from mysterious into predictable, and almost every "why is my image 800 MB" and "why does my CI take nine minutes" question is answered by it.

    The concept

    You already have the machinery for this. From I4.9, a layer is a tar file of changes. From I4.13, the image config is a JSON document of pre-declared defaults. A build walks your instructions in order and, for each one, does one of two things:

    • Produce a layer. The step runs against a snapshot of the filesystem so far, and whatever changed is packed into a new tar. That tar gets a digest, a diff_id, and a slot in rootfs.diff_ids. RUN, COPY and ADD all work this way.
    • Amend the config. The step touches no files; it just sets a field — Env, Cmd, User, Labels. Nothing is stored, nothing is pushed, and the image's layer count does not move. ENV, CMD, ENTRYPOINT, USER, LABEL and EXPOSE all work this way.

    Both kinds still get a line in the config's history array, which is what makes the split visible: a config-amending step is marked empty_layer: true, and a layer-producing step is not. So the arithmetic from I4.13 holds on every image ever built — history entries minus empty ones equals the number of layers — and you can audit any image's build by reading two fields.

    That is why an image with thirty instructions may have only five layers, and why re-ordering your ENV and LABEL lines is free while moving a COPY is not: only the layer-producing steps change the filesystem, and therefore only they change the chain ID (I4.12) that every subsequent step's cache key is built on.

    And now the part that catches everyone, including the author of this module's own checkpoint list. WORKDIR produces a layer. It has to: it creates the directory if it is missing, and creating a directory is a filesystem change. So the neat "config-amending" bucket that every tutorial puts WORKDIR in is wrong, and the lab below proves it in two lines of jq.

    It is stranger than that. WORKDIR takes a layer slot even when the directory already exists and nothing changes — the step still goes through the snapshot path, the snapshot still gets diffed, and the diff comes out empty. What lands in rootfs.diff_ids is then the empty layer: 1024 zero bytes, diff_id sha256:5f70bf18a086…, compressing to a 32-byte blob. If you have read many image configs you have seen that digest before; now you know where it comes from.

    So the reliable rule is not a list of instruction names to memorise. It is a question about mechanism: does this step go through the filesystem-snapshot path? If yes it consumes a diff_id, possibly an empty one. If no, it is empty_layer: true. Ask the mechanism, not the tutorial.

    The spec never lists which Dockerfile instructions make layers — it could not, since it knows nothing about Dockerfiles. It defines the test instead, and the test is about filesystem diffs, not instruction names. That is precisely why WORKDIR falls on the side it does.

    empty_layer boolean, OPTIONAL

    This field is used to mark if the history item created a filesystem diff.
    It is set to true if this history item doesn't correspond to an actual layer in the rootfs section (for example, Dockerfile's ENV command results in no change to the filesystem).
    OCI image-spec v1.1.1 — config.md § Properties

    Worth noticing: the spec's own worked example of a config has exactly two diff_ids, and the second one is sha256:5f70bf18a086007016e948b04aed3b82103a36bea41755b6cddfaf10ace3c6ef — the same empty layer your WORKDIR is about to produce.

      Ten history entries for nine instructions, because alpine:3.21 brought two of its own along. Four layers, so six entries must be empty.

      Six EMPTY, four LAYER, and 10 − 6 = 4 matches n_layers exactly. ENV, LABEL, USER, EXPOSE and both CMDs were free. WORKDIR was not.

      Note that WORKDIR did both jobs: it set WorkingDir and made a layer. It is the only instruction here that appears on both sides of the split.

      One tar entry, one directory, no files. Small — but a real layer, with a real digest, that every node pulling this image will fetch.

      mkdir -p ~/i6/wd && cd ~/i6/wd
printf 'FROM alpine:3.21\nWORKDIR /tmp\nWORKDIR /etc\n' > Dockerfile

      Both still LAYER. Nothing was created, nothing changed, and two layer slots were consumed anyway.

      1024 zero bytes — two 512-byte tar terminator blocks and nothing else — hashing to the empty diff_id, gzipping to the 32-byte blob. Three digests you will now recognise on sight.

    Verify

    Handed any Dockerfile, you can predict its image's layer count before building, and check your prediction with two jq expressions. You can state the mechanism-level rule — does the step go through the snapshot path — rather than reciting a list. And you can recognise sha256:5f70bf18a086… and its 32-byte compressed form as the empty layer, wherever they turn up.

    Gotchas
    • WORKDIR is on the expensive side of the split, and nearly every tutorial says otherwise. The cost is small — an empty layer, or a one-directory layer — but it is a real slot in rootfs.diff_ids, and it means moving a WORKDIR line invalidates the cache for everything below it, exactly like moving a COPY. If you have ever seen a "harmless" reshuffle trigger a full rebuild, this is a strong candidate.
    • "Empty layer" and empty_layer: true are different things, and the collision is unfortunate. The 1024-zero-byte layer is a layer with a digest and a slot; empty_layer: true means there is no layer at all. An image can therefore have empty layers and no empty-layer history entries, or the reverse.
    • The step numbers in the build log count vertices, not lines. [2/4] for a nine-line Dockerfile is not the builder skipping your work — it is the builder telling you five of your lines are free. Reading that counter is a fast sanity check on your own classification.
    • history is written by whichever tool built the image, and it is free-form text. The created_by strings above end in # buildkit because BuildKit wrote them; another builder writes something else, and a hand-assembled image (I6.9) may have no history at all. Treat it as a strong hint, never as proof — a point that returns in I6.10.

    This split is why W3.21 exists at all. Everything on the config-amending side — ENV, CMD, USER, EXPOSE — is a default baked into the image, and every one of those defaults can be overridden by the pod spec without rebuilding anything: env, command/args, securityContext.runAsUser. Anything on the layer-producing side cannot be, because it is bytes in a tar in a registry. That is the real dividing line behind "configuration belongs in a ConfigMap, not in the image", and the reason W3.23 insists a Secret is a runtime object: a secret written by a RUN is a layer, and layers are not configurable, they are shipped.

    Docs: config.md § Properties for rootfs.diff_ids, history and empty_layer — the only normative text in play here. For the instruction semantics themselves, search the Docker docs for "Dockerfile reference", remembering it is a reference and not a standard. On the Kubernetes side, search for "define a command and arguments for a container" to see which of these fields a pod spec can override.

    I6.2

    The build context, and the folklore about it that is now wrong

    Why it matters

    When you type docker build ., that trailing dot is not decoration — it names the build context, the set of files the builder is allowed to reach. Understanding what actually crosses from your directory into the builder is how you explain a build that takes six seconds before running a single instruction, and it is how credentials end up in public images. Both stories are in this checkpoint, and one of them has changed since the advice you have probably read.

    The concept

    The builder is a separate program from the client, often on a separate machine, and it cannot see your disk. So before anything runs, the client has to hand over the files. The old Docker daemon did that the blunt way: it tarred up the whole directory and uploaded it. That is where the standard warning comes from — the entire context is transferred whether you reference it or not, so a stray .env or a 2 GB .git costs you on every build.

    On BuildKit, that is no longer true, and the lab below measures it. BuildKit runs the transfer as a session between client and builder and moves files on demand: it resolves your Dockerfile into a graph first, sees which paths the graph actually references, and pulls only those across. A 100 MB file sitting beside your Dockerfile that nothing copies is transferred as zero bytes. Repeating the old warning as fact is one of the most widespread pieces of stale container advice, and it matters because it teaches people to fear the wrong thing.

    What is still completely true is the consequence, and it has simply moved one step along. The transfer is driven by what the graph references — so the risk is not "having files in the directory", it is writing an instruction that references all of them. And there is exactly one such instruction, it is extremely common, and it is COPY . .. The moment you write it, every byte in that directory is both transferred and baked into a layer that will be pushed to a registry: the .env with your cloud credentials, the .git directory containing the history where you already removed a key once, the private key someone left in the tree. From I4.1, that layer is content-addressed and immutable, and from I6.4, deleting the file later does not remove it.

    So .dockerignore deserves a better framing than the performance tweak it is usually sold as. It is a secrecy control — the list of things you are declaring your build has no business seeing, enforced at the point where files cross the boundary rather than left to the discipline of everyone who ever edits the Dockerfile. Read it the way you would read a firewall rule, not a cache hint. The speed improvement is real and it is the lesser half.

    One detail about how it is enforced, because it explains the numbers in the lab. .dockerignore is applied by the client while it builds the file list, before the transfer decision — so an ignored file is not "sent and then discarded", it is never a candidate. That is also why the exclusion works even for COPY . .: by the time the graph asks for everything, "everything" already has your exclusions taken out of it.

    There is no OCI spec for the build context — the specs cover the image, the runtime and the registry, and stop at the door of how the image is produced. This is the first checkpoint in the intermediate track where the honest answer is no standard governs this, and it is worth sitting with, because it explains the ecosystem you are looking at: builds are where the tools differ most, precisely because nobody wrote a contract for them.

    The closest thing to normative text is BuildKit's own documentation of the syntax, which is a de-facto standard by adoption rather than a specification. Treat its behaviour as observed, not guaranteed — which is exactly why this checkpoint measures instead of asserting.

    No OCI spec applies — see moby/buildkit § .dockerignore and the Dockerfile reference

    Verify

    You can state what determines the size of a context transfer (the instructions, not the directory), demonstrate it with two builds differing by one line, and explain why .dockerignore is a secrecy control rather than a cache hint. You can also correct the stale version of this advice when you meet it, and say precisely which builder it was true of.

    Gotchas
    • The old advice is not malicious, it is dated — check which builder you are on before repeating either version. The classic Docker daemon really did tar the whole directory. If you are on a CI image pinned to an ancient Docker, or building with something that shells out to the legacy builder, the 101 MB transfer is back. --progress=plain and the context vertex tell you which world you are in, in one build.
    • .dockerignore does not protect you from a RUN that fetches a secret itself. It governs what crosses from your directory, nothing more. A RUN curl that pulls a token into a layer is untouched by it — that is what I6.6's secret mount is for.
    • .dockerignore itself lands in the image when you COPY . . — you can see it in the last listing above. Harmless, but a good reminder that the file is an instruction to the client, not a magic invisible marker.
    • Excluding a path from the context does not remove it from your Git history, and images built before you added the file are unaffected. If a credential was ever in a pushed layer, .dockerignore is the fix going forward and rotation is the fix for what already happened. I6.11 is where that becomes uncomfortably concrete.
    • A missing .dockerignore and an empty one are the same thing, but a typo is not. The file has its own pattern syntax, close to but not identical to .gitignore; an exclusion that silently fails to match looks exactly like a working one until you check the transferred byte count. Check the byte count.

    Kubernetes never sees your build context — but it pays for it. Every byte a careless COPY . . adds is a byte the kubelet's image pull moves on every node that schedules the pod, which is a large share of the cold-start latency people blame on the scheduler; W6.17's slow and failing pulls are frequently a 900 MB image that should have been 90 MB. The secrecy half lands on W3.23: a credential swept into a layer by COPY . . defeats every protection Kubernetes offers a Secret, because it was never a Secret — it is image content, replicated to every node that runs the workload and to every mirror that caches it.

    Docs: No OCI spec covers this — search the Docker docs for "build context" and ".dockerignore file", and BuildKit's repo for the session-based transfer if you want the mechanism. On the Kubernetes side, search for "pre-pulled images" and "image pull policy", which is where image size stops being your problem and becomes the node's.

    I6.3

    Deriving the cache key by experiment

    Why it matters

    Build caching is the difference between a nine-minute CI run and a nine-second one, and almost nobody can state the rule it follows. The result is cargo-cult Dockerfiles: instructions shuffled by superstition, --no-cache added because "the cache was being weird". The rule is small and you can derive it from seven builds. Do that once and you will never guess again — and you will be able to read a slow build log and name the offending line.

    The concept

    Every step in a build gets a cache key. Before running the step, the builder computes that key and looks for a previous result with the same one; if it finds it, the step is skipped and its stored output is reused, which the log reports as CACHED. The key is built from two things:

    • What this step is — the parsed instruction, not the raw source line.
    • What it is built on — the identity of the filesystem it starts from, which is the chain ID from I4.12, i.e. a hash over every layer beneath it in order.

    That second half is why the cache is a chain, not a set. A step's key contains its parent's identity, so once any step misses, every step after it has a different parent and therefore a different key and therefore misses too — however unrelated its own instruction is. There is no such thing as a cache hit below a cache miss. Internalise that one sentence and the ordering rule becomes obvious rather than memorised.

    For COPY and ADD there is a third input: the content of the files being copied, hashed. Not their timestamps, not their names — the bytes. So a COPY of an unchanged file hits the cache even if you have touched, moved or rewritten it in place with identical content, and misses the moment a single byte differs.

    Now put those three facts together and the most valuable ordering rule in the ecosystem falls out with no memorisation at all. Copy your dependency manifest, install dependencies, then copy your source. The install step's key depends on the manifest's content and nothing else, so editing application code leaves it hit and skips the slowest step in the build. Do it the other way — COPY . . above the install — and the copy's key contains the hash of your source, so a one-character edit misses, and the chain rule makes the install below it miss too. Every commit reinstalls the world. That is the single most common cause of slow CI, and it is this module's first drill fault (I6.13).

    Two things the lab will show that the folklore gets wrong. Comments do not affect the cache key — the key is computed from the parsed graph, and a comment never becomes a node in it, so you can annotate a Dockerfile freely. And touch does not bust a COPY, because content is hashed rather than mtime; that was true of older builders and is a real behavioural difference, not a myth about nothing.

    Again, no OCI spec — caching is entirely a builder concern, and the OCI specs deliberately describe only the artefact, not its production. But the spec does explain, at unusual length for a standards document, why the second input to a cache key has to be a hash of the whole stack rather than of the layer immediately below. Read it as the argument that a single layer digest cannot identify the filesystem a step starts from:

    Let's say we have layers A, B, C, ordered from bottom to top, where A is the base and C is the top. Defining | as a binary application operator, the root filesystem may be A|B|C. While it is implied that C is only useful when applied to A|B, the identifier C is insufficient to identify this result […]

    This means that if an attacker can define x, relying on C provides no guarantee that the layers were applied in any order.

    The ChainID addresses this problem by being defined as a compound hash.
    OCI image-spec v1.1.1 — config.md § Layer ChainID

    So the chain ID of I4.12 exists to answer exactly the question a cache key needs answered — which stack am I standing on? — and the cache key is a construction on top of it. The cache key is not in any spec; the identity it depends on is, and this is why.

    Lab
    1. Build the smallest Dockerfile that has the ordering rule in it: a manifest, an install that depends on the manifest, and source copied afterwards. 
      mkdir -p ~/i6/cache && cd ~/i6/cache
echo "flask==3.0.0" > requirements.txt
echo "print(1)" > src.py
echo "notes" > README.md
cat > Dockerfile <<'EOF'
FROM alpine:3.21
COPY requirements.txt /app/
RUN echo "installed from $(cat /app/requirements.txt)" > /app/installed
COPY src.py /app/
EOF

      FROM is already cached — the base image was pulled earlier. The other three ran.

#6 CACHED

      All three still hit. Comments are invisible to the cache, because the key is computed from the parsed graph and a comment never becomes a node in it. Annotate freely.

      All hit — and this is I6.2's lesson from the other side. A file nothing references is not in any cache key any more than it is in the transfer.

    6. Change 3 — touch a copied file without changing a byte of it. Older builders considered the mtime; this one hashes content.

      Still all cached: content, not mtime. And notice the ordering — #6 is now the RUN that is [3/4] in the Dockerfile, printed before the COPY that is [2/4]. The #n are graph vertices and the [n/4] are source lines, and they need not agree. You have just seen the DAG of I6.6 three checkpoints early.

    7. Change 4 — edit the source file, which is copied last. This is the every-commit case, and the whole point of the ordering. 
      echo "print(2)" >> src.py
show
      #6 [2/4] COPY requirements.txt /app/
#6 CACHED
#7 [3/4] RUN echo "installed from $(cat /app/requirements.txt)" > /app/installed
#7 CACHED
#8 [4/4] COPY src.py /app/

      The manifest copy and the install both hit; only the final copy reran. In a real project that is the difference between re-resolving every dependency and doing nothing at all.

    8. Change 5 — edit the manifest, which is copied first. Watch the chain rule take out everything below it. 
      echo "requests==2.32.0" >> requirements.txt
show
      #5 [1/4] FROM docker.io/library/alpine:3.21@sha256:48b0309ca019d8...
#5 CACHED
#6 [2/4] COPY requirements.txt /app/
#7 [3/4] RUN echo "installed from $(cat /app/requirements.txt)" > /app/installed
#8 [4/4] COPY src.py /app/

      Three misses from one edit. The COPY missed on content; the RUN missed because its parent changed, not because its instruction did; the final COPY missed for the same reason, even though src.py is untouched. That is the chain, and it is the correct behaviour — a dependency change really may change what the install produces.

    Verify

    You can state the cache key's three inputs from memory, explain why a cache miss cannot have hits below it, and justify the copy-manifest-then-install-then-copy-source ordering as a consequence rather than a rule to remember. Shown a build log where an install step reran, you can name the line that caused it.

    Gotchas
    • The cache lives in the builder, not in your image. A fresh CI runner starts with nothing, so a Dockerfile perfectly ordered for your laptop can still rebuild everything in CI. That is what registry-backed cache export exists for, and it is why "it's fast locally" is not evidence about your pipeline.
    • RUN keys do not know what the command did. RUN apt-get update has one key forever, so a cached layer can contain a six-month-old package index while the instruction looks current — the classic stale-apt-cache trap, and the reason update and install belong in the same RUN. The cache is honest about instruction text and knows nothing about the internet.
    • Content hashing includes file mode and ownership, not just bytes. A chmod +x on a copied file is a cache miss even though the content is identical — correct, since the layer really is different, but surprising if you were told "content only".
    • A comment being free is not a licence to reorder freely. Adding a comment is invisible; moving an instruction is not, and I6.1 is the reminder that WORKDIR counts as an instruction for this purpose.
    • --no-cache is a diagnostic, not a fix. If you need it routinely, some step's key does not capture something it depends on — a fetch from a mutable URL, a floating tag, a clock. Find that step; disabling the cache everywhere hides it and costs you the whole build every time.

    Nothing in Kubernetes reads a build cache — but the ordering rule this checkpoint derives is the same shape as the layer-sharing that makes image pulls cheap on a node. Because a chain ID identifies a whole stack, two images built from a shared prefix share those blobs in the node's content store, so the second pull moves only the layers below the divergence point; a Dockerfile ordered manifest-first produces exactly that shared prefix across your whole fleet, and one ordered COPY . .-first gives every build a unique chain from the second layer down. That is the difference between a rollout where most nodes fetch a few megabytes and one where they all fetch the world — the practical face of W6.17's pull-time troubles, and part of why W3.2's init containers are usually pinned to a base the cluster already has.

    Docs: No spec governs caching — search the Docker docs for "cache invalidation" and "optimizing builds with cache", and BuildKit's docs for "cache backends" when you need the cache to survive a fresh CI runner. layer.md § Applying Changesets is the ordering guarantee everything here is built on.

    I6.4

    Deleting a file makes the image bigger

    Why it matters

    This is I4.11's whiteout lesson arriving as a bill, and it is the checkpoint that changes how you write Dockerfiles for good. The instinct that a RUN rm reclaims space is completely wrong, in a way that costs real money in bandwidth and real minutes in pull time — and, far worse, in a way that means a secret you deleted is still shipped to everyone who pulls your image.

    The concept

    A layer is a diff, and diffs only add. Once a layer is written it is content-addressed (I4.1) and therefore frozen: its digest is its bytes, so nothing later in the build can reach back and remove anything from it. When a later step deletes a file, all it can do is record the deletion — a .wh.<name> entry in the new layer, exactly the encoding you took apart in I4.11.

    So a RUN rm of a 100 MB file does not make the image 100 MB smaller. It makes it slightly larger: the 100 MB is still there in the earlier layer, plus a new layer holding the whiteout. What changes is only what you see at runtime, because the overlay filesystem — the same one you built by hand in B5.15 — reads the whiteout and hides the file from the merged view. Hidden, not gone. Every node that pulls the image still downloads all 100 MB of it.

    The fix is to never let the bytes become a sealed layer in the first place, which means doing the create and the delete inside one step, chained with &&. Then the snapshot taken at the end of that step never contained the file, so the diff never mentions it, and there is nothing to whiten out. This is the whole reason real Dockerfiles chain apt-get update && apt-get install && rm -rf /var/lib/apt/lists/* into one unreadable line: it is not style, it is the only way the cleanup does anything.

    Notice the tension with I6.3, because it is a genuine trade-off and not a solved problem. Chaining reduces size and reduces the number of cache checkpoints; splitting steps gives finer caching and permanent bloat. There is no setting that gives you both — which is why I6.5's multi-stage builds matter so much: they let you be as wasteful as you like in a stage whose layers are then discarded wholesale rather than whitened out.

    And then the part that is not about size at all. Because the bytes are in a pushed, content-addressed blob, a credential written in one step and deleted in the next is in the image — fetchable with curl and tar by anyone who can pull it, with no running container and no exploit involved. I6.11 is where you go and do it. That is why build-time secrets need the mechanism in I6.6 rather than the discipline of remembering to delete.

    The spec is explicit that a whiteout is an instruction to the reader, not a modification of anything. Note the last sentence in particular: it tells the consumer to remove the file from the extracted result, and says nothing about the layer that contains it, because the layer is immutable by construction.

    Once a whiteout is applied, the whiteout itself MUST also be hidden.
    Whiteout files MUST only apply to resources in lower/parent layers.
    Files that are present in the same layer as a whiteout file can only be hidden by whiteout files in subsequent layers.
    OCI image-spec v1.1.1 — layer.md § Whiteouts

    Verify

    You can explain why RUN rm increases image size, predict the layer count and rough size of both variants before building, identify a whiteout entry in a layer listing on sight, and recover a "deleted" file from a registry with curl and tar. You can also state the trade-off chaining costs you in cache granularity, rather than treating it as free.

    Gotchas
    • The tool's SIZE column and what crosses the wire are different numbers, and both are honest. nerdctl images showed 113.4 MB (uncompressed, as unpacked on disk) while the manifest sums to 108.5 MB (compressed, as transferred). Compare like with like, and prefer the manifest when the question is "what does a pull cost".
    • There is no way to shrink a layer after the fact. Not rm, not truncate, not a later chmod 000. The only options are to not create the bytes in that step (chaining), to not keep the layer at all (I6.5), or to rebuild the image. Squashing tools exist and work by rebuilding, which is worth knowing so you recognise what they are actually doing.
    • Chaining trades size for cache granularity, and sometimes the trade is wrong. A single 400-line RUN is one cache entry: change anything in it and the whole thing reruns. Chain what must be cleaned up together; split what genuinely caches independently.
    • "We removed it in the next layer" and "we deleted the tag" are both non-answers to a leaked secret. The blob is content-addressed and may still be fetchable by digest even after the tag is gone, and any mirror or node that replicated it kept a copy — I5.3 and I5.11 are why. The only correct response is to treat it as disclosed and rotate.
    • A whiteout can hide a file the reader is entitled to see. The spec's rule that whiteouts apply only to lower layers is what stops a producer from claiming to delete something in its own layer — useful to know when you are reading someone else's image and wondering whether a listing is complete.

    Every byte of that 108.5 MB is moved by the kubelet on every node the pod is scheduled to, on every pull that misses the node's content store. A DaemonSet across fifty nodes turns a careless RUN rm into fifty times the waste, and it is a routine contributor to the slow pulls and pull timeouts that present as W6.17's ErrImagePull and ImagePullBackOff under a cold cache or a rate limit (I5.6). The security half aims at W3.23: a Secret in Kubernetes is at least a named object with RBAC on it and encryption-at-rest available, whereas a credential baked into a layer has no access control at all beyond "can pull this image" — which, for a public base image or a shared internal registry, is close to everyone.

Search the Docker docs for "minimize the number of layers", and note as you read it that the size argument and the caching argument point in opposite directions. On the Kubernetes side, search for "images" and "image pull policy" for what the node does with the bytes you produced.
