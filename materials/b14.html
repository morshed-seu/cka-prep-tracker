    B14 — Capstone: build minibox, then the gauntlet

    There is nothing new in this module. Every mechanism you are about to use has its own lesson behind it, and the only thing left is assembly — which turns out to be the part that changes how you see all of it. You will write one script that puts a process on its own filesystem, in its own namespaces, inside its own resource limits, with a reduced set of privileges, on its own network with a working name resolver, supervised by systemd and logging to the journal. That script is about 150 lines of bash, and it is, honestly, a container runtime.

    That is the point of the whole track stated as an artefact. A container is not a technology you install; it is a process with five kernel features switched on around it. Once you have switched them on by hand, "the pod won't start" stops being one opaque failure and becomes a question about which of six specific layers is unhappy — which is exactly what the second half of this module drills, with eight planted faults and a clock.

    Three parts. The capstone: minibox, built one layer at a time, each layer verified before the next goes on. The gauntlet: eight faults, one per layer, then a written post-mortem of your own triage order, then a second run to watch a routine beat improvisation. The assessment: a written self-test, a timed practical set, and an honest readiness checklist for what comes next.

    Checkpoints10 Hours~6 PrerequisitesAll of B0–B13

    Capstone — minibox, one layer at a time

    B14.1

    Layer 1 — the filesystem: stacked layers and one writable top

    Why it matters

    Before a container can have its own processes it needs its own files, and the way that is done is the single most surprising thing about container images: they are not disk images. They are directories, stacked. Building the stack by hand is what makes "image layer", "copy-on-write" and "the container's writable layer is thrown away" concrete rather than vocabulary.

    The concept

    Use the picture from B5.13: a stack of transparent sheets. You read through the whole stack, and you write only on the top one. overlayfs makes that literal with four directories — one or more lowerdirs (read-only, leftmost wins), an upperdir (writable), a workdir (overlayfs's scratch space, must be empty and on the same filesystem as the upper), and a merged mountpoint where the union appears.

    Two behaviours matter for what comes later. Copy-up: the first time you write to a file that lives in a lower layer, the whole file is copied into the upper layer and modified there — so the lower layer is never touched, and a large file's first write is expensive. Whiteouts: deleting a file that exists below does not remove it; it creates a marker in the upper layer that hides it. Both are why several containers can share one read-only image safely, and why a container's changes vanish when its upper directory is discarded.

    lower1 (base)+lower0 (config)+upper (writable)=merged

    Read through the stack, write only on top — the whole of container storage in one sentence.

    Name the four directories overlayfs needs and what each is for, and state the ordering rule for multiple lower directories. Then explain steps 4–6 in image terms: which directory is the image (shared, read-only, reused by every container), which is the container (writable, per-instance, discarded on removal), and what docker commit would have to do to turn the second back into the first.     Gotchas

    The workdir must be empty and on the same filesystem as the upperdir, and overlayfs will refuse the mount rather than explain why if either is wrong. If mount returns "invalid argument" with everything apparently correct, check those two things first — it is nearly always one of them, and the error message never says so.

    The second is copy-up cost. Writing one byte to a 2 GB file in a lower layer copies the entire 2 GB into the upper layer first. Containers that write into large image files behave inexplicably slowly on their first write and normally afterwards, and this is the reason — it is also why databases in containers are given a volume rather than being left on the overlay.

    You have just built a container image's storage model. On a Kubernetes node, containerd assembles exactly this for every container: the image's layers become the lowerdir list (shared read-only between every pod using that image, which is why the tenth pod from an image starts far faster than the first), and a fresh upperdir becomes the container's writable layer. That writable layer is why a pod's filesystem changes disappear on restart, why ephemeral-storage is a schedulable resource, and why writing large amounts of data inside a container without a volume eventually triggers node disk pressure.

    How the kubelet and containerd divide this work is W1.20; where the images and layers physically live on a node is W1.23; and volumes as the answer to "do not write into the overlay" is W5.1.

    B14.2

    Layer 2 — isolation: five namespaces, pivot_root and a fresh /proc

    Why it matters

    This is the layer where the thing stops looking like a directory and starts looking like a container. When ps inside your process shows one process — itself, as PID 1 — and nothing else on the machine, you are looking at the whole illusion, produced by five flags and a mount.

    The concept

    Five namespaces (B6.2), each hiding one kind of thing: mnt (its own mount table, so it can have its own root), pid (its own process numbering, so it becomes PID 1 and cannot see the host's processes), uts (its own hostname), ipc (its own shared-memory world) and net (its own interfaces, routes and ports — for now, completely empty, which B14.4 fixes).

    Then the root change. chroot moves the apparent root but leaves the old root reachable, which is why it is not a security boundary. pivot_root swaps the mount namespace's root for a new one and gives you the old root at a path you can then unmount — after which the host filesystem is genuinely unreachable, not merely out of sight. It has four preconditions (B6.11): you must be in your own mount namespace, the new root must be a mount point, it must not be shared, and the old-root directory must live under the new root. Every EINVAL from pivot_root is one of those four.

    Finally the step everyone forgets: mount a fresh /proc inside. A PID namespace changes process numbering, but ps reads /proc, so without a new procfs the "isolated" process cheerfully lists every process on the host. That mismatch is the clearest possible demonstration that isolation is not one switch.

    unshare 5 namespaces→pivot_root into merged→umount old root→mount -t proc

    Four steps, in that order; skipping the last one is the classic bug.

    Lab
    1. Start minibox.sh with the isolation step. The self-re-exec via _MINIBOX_STAGE is what lets one script be both the launcher and the thing that runs inside. 
      cat > ~/minibox.sh <<'EOF'
#!/usr/bin/env bash
# minibox — a container runtime in bash. Layers: fs, isolation, limits, network.
set -euo pipefail
ROOT=/srv/minibox
NAME=${NAME:-minibox}

mount_rootfs() {
  mountpoint -q "$ROOT/merged" && return 0
  rm -rf "$ROOT/upper" "$ROOT/work"; install -d -m 755 "$ROOT/upper" "$ROOT/work"
  mount -t overlay minibox-overlay \
    -o "lowerdir=$ROOT/lower-conf:$ROOT/lower-base,upperdir=$ROOT/upper,workdir=$ROOT/work" \
    "$ROOT/merged"
}

enter_rootfs() {                     # runs INSIDE the new namespaces
  mount --make-rprivate /
  mount --bind "$ROOT/merged" "$ROOT/merged"      # new root must be a mount point
  install -d "$ROOT/merged/.oldroot"
  cd "$ROOT/merged"
  pivot_root . .oldroot
  cd /
  umount -l /.oldroot && rmdir /.oldroot          # the host filesystem is now unreachable
  mount -t proc proc /proc                        # the step everyone forgets
  hostname "$NAME"
}

if [ "${_MINIBOX_STAGE:-}" = "inside" ]; then
  enter_rootfs
  exec "${@:-/bin/sh}"
fi

[ "$(id -u)" -eq 0 ] || { echo "run with sudo" >&2; exit 1; }
mount_rootfs
_MINIBOX_STAGE=inside exec unshare --mount --pid --uts --ipc --net --fork \
  "$0" "$@"
EOF

    Name the five namespaces and what each hides. Then explain the two things people get wrong here: why chroot is not a security boundary and pivot_root is (the old root is unmounted, so there is no path back to it), and why a PID namespace alone does not change what ps prints (it reads /proc, which must be remounted inside). Finally, list pivot_root's four preconditions from memory — every EINVAL it returns is one of them.

    Gotchas

    mount --make-rprivate / before anything else is not optional. systemd makes all mounts shared by default (B5.12), and a shared mount propagates your container's mounts back out to the host — which both breaks pivot_root's preconditions and, worse, silently modifies the host's mount table. Forget it and you will find mystery mounts on the host after the container exits.

    The second is the PID-1 duty this process has now inherited (B11.1). Your /bin/sh is PID 1 inside, which means the kernel will not deliver SIGTERM to it without a handler, and it must reap orphans. That is why a real runtime either uses a tiny init like tini or requires the application to handle signals — and why some containers take exactly the full grace period to stop.

    A pod is a group of containers that share some of these namespaces and not others, and now you can say precisely which. Containers in a pod share the net namespace — which is why they reach each other on localhost and why they cannot both bind port 8080 — plus ipc and, optionally, pid (shareProcessNamespace: true). Each keeps its own mnt namespace, which is why they have separate filesystems and need a shared volume to exchange files. The namespace that holds the pod's network is created and held open by the pause container, which does nothing but exist so that the namespace outlives any individual container restarting inside it.

    The pause container and what it is actually for is W1.21; the CRI path from kubelet to containerd to runc that performs these calls is W1.20.

    Docs

    man 1 unshare for the flags used here — note --fork, which is required for --pid to affect the child rather than nothing. man 2 pivot_root for the four preconditions and the exact EINVAL conditions; man 7 pid_namespaces for the PID-1 rules; man 7 mount_namespaces for propagation and why --make-rprivate matters.

    B14.3

    Layer 3 — limits and privilege: a cgroup and a smaller keyring

    Why it matters

    Namespaces hide; they do not limit. The process you built in B14.2 cannot see the host, and it can still consume every core and all the memory on it, and it is still running as root with every capability. This layer is where a hidden process becomes a contained one, and it is exactly the difference between "it works on my machine" and "it is safe to run next to other people's workloads".

    The concept

    Two independent mechanisms, both from earlier modules.

    Resource limits come from cgroup v2 (B7): a directory under /sys/fs/cgroup is a cgroup, writing a PID into its cgroup.procs moves that process (and everything it later forks) into it, and the control files set the caps. cpu.max is a hard ceiling expressed as quota period in microseconds — 50000 100000 means half a core, enforced even when the machine is idle. memory.max is a hard limit whose enforcement is the OOM killer: exceed it and the kernel sends SIGKILL, which the process cannot catch, so its own logs will never explain what happened.

    Privilege comes from capabilities (B4.10): root is not one flag but a keyring of about forty individually-grantable permits. A container that never configures interfaces does not need CAP_NET_ADMIN; one that never mounts anything does not need CAP_SYS_ADMIN. Dropping the bounding set removes them permanently for that process and everything it spawns, so a compromise inside the container cannot pick them back up. Add --no-new-privs and the setuid escape hatch closes too (B4.9).

    namespaces hide·cgroups limit·capabilities restrict→a container

    Three orthogonal mechanisms; a container is all three at once, and nothing else.

    Gotchas

    Order matters when joining a cgroup: write the PID before the process forks the workload, because cgroup.procs moves one process, and children inherit membership only from the moment they are created. Move the parent first and everything below it is caged; move it after and the workers you already started are outside the cage, running unlimited, while the tidy-looking parent sits inside it.

    The second is dropping capabilities you actually need and then blaming the wrong layer. If minibox suddenly cannot bring up its own interface in B14.4, that is this lesson's --drop=cap_net_admin doing its job — the fix is to configure the network from outside the namespace, which is exactly what a real runtime does, rather than to hand the capability back.

    Both mechanisms appear directly in a pod spec. resources.requests and resources.limits become the cgroup you just wrote by hand — a CPU limit is cpu.max, a memory limit is memory.max, and a CPU request is cpu.weight, which is why requests only matter under contention while limits bite on an idle node. The QoS class a pod lands in is derived from which of those it sets, and it decides who the kernel kills first under pressure. securityContext.capabilities.drop is the keyring, and allowPrivilegeEscalation: false is --no-new-privs. Exit code 137 on a pod means the same thing it meant above, one layer up.

    Requests versus limits, and which is bookkeeping versus enforcement, is W3.16; QoS classes and what they buy at OOM time is W3.17; node-pressure eviction is W3.18.

    B14.4

    Layer 4 — network, names and supervision: minibox, finished

    Why it matters

    An isolated, limited process with no network is not much use. This layer gives it an address, a route out, a name resolver and a supervisor — and when it is done you will have a script that does everything a container runtime does, which is the point at which you can say exactly what the real ones add.

    The concept

    The network namespace from B14.2 starts with nothing: one loopback interface, down, no routes, no ports. Filling it is four steps you already know from B9.8, done from outside the namespace because the process inside no longer has CAP_NET_ADMIN:

    1. A veth pair — a virtual patch cable. One end goes into the container's namespace, the other is plugged into a bridge on the host.
    2. An address and a route inside: an IP on the subnet, and a default route via the bridge.
    3. NAT egress: a MASQUERADE rule so replies to the private address find their way back, plus ip_forward on the host.
    4. A resolver: a /etc/resolv.conf inside the container pointing at something that will actually answer (B10.3).

    Then supervision. Wrapping the script in a systemd unit (B11.3) gives you restart policy, boot enablement, journald logging and a cgroup for free — and makes the last comparison honest, because that is roughly the relationship between a kubelet and the containers it runs.

    Now the comparison worth carrying into the next track. What a real stack adds is standardisation, not mechanism: an image format and a registry instead of directories you assembled by hand; the OCI runtime spec instead of your argument parsing; a CRI so a kubelet can drive it; and a CNI plugin contract instead of your networking script. None of them replace what is underneath — every one of them ends up making the same calls you just made.

    veth + bridge→address + route→NAT→resolv.conf→systemd unit

    Four network steps and a supervisor; that is the whole remaining gap.

    Gotchas

    Configure the network from outside the namespace, not inside it. Your printf 'nameserver …' is the kubelet writing /etc/resolv.conf from the pod's dnsPolicy, pointing at the cluster's DNS service instead of a public resolver.

    The debugging gauntlet

    B14.5

    Run 1 — eight faults, one per layer, 45 minutes

    Why it matters

    Building something correct and repairing something broken are different skills, and only the second one is tested by an exam or an incident. Eight faults, one in each layer you have just assembled, is the smallest set that forces you to locate a fault before fixing it — which is the habit the whole track has been building toward.

    The concept

    Eight scripts in labs/beginner/, each planting exactly one fault, each with the same contract as the CKA track's drills: a banner, a typed confirmation, a wrong-box guard that refuses to run anywhere but the sandbox VM, a backup of whatever it is about to change, and a mission statement that never names the fault. One per layer:

    • permission — a service account can no longer read its own file (B4.6).
    • cgroup — a healthy service starts failing without its program changing (B7.8).
    • mount — files vanish from a directory without being deleted (B5.11).
    • route — a namespace reaches its own subnet and nothing beyond (B8.5).
    • iptables — a healthy service becomes unreachable (B9.12).
    • DNS — a correctly-spelled name stops resolving (B10.1).
    • systemd unit — a unit refuses to start and its program logs nothing (B11.9).
    • certificate — a TLS service keeps serving and clients stop trusting it (B12.10).

    The rule that makes this worth doing: five real minutes on a fault before you open a hint. The reveals below are staged — symptom, hint, full fix — so you can take exactly as much as you need. Taking the fix straight away converts a debugging exercise into a reading exercise, and the thing being trained here is the search, not the answer.

    Staged reveals

    One group per fault. Open Stage 1 only to confirm you are seeing the right symptom, Stage 2 after five real minutes of your own work, and Stage 3 when you want the answer.

    b14-permission-01 — the permission layer

    Stage 1 · Expected symptom

    sudo -u gauntlet cat /srv/gauntlet/data/config.txt gives Permission denied. The file itself is mode 644, owned by root, and world-readable — so the file's own permissions look completely correct, which is the point.

    Stage 2 · Hint

    Reading a file requires more than permission on the file: every directory on the path must grant execute (traverse) to the user doing the reading. Walk the path from / downward with namei -l /srv/gauntlet/data/config.txt and look at each component's mode rather than the last one.

    Stage 3 · Full fix

    namei -l shows /srv/gauntlet at drwxr-x--- — no x for "other", so the gauntlet user cannot traverse into it. Fix with sudo chmod o+x /srv/gauntlet (or chmod 755). Fingerprint: file mode is fine, access still denied → check the whole path, not the file (B4.6's traverse ladder).

    b14-cgroup-01 — the resource-limit layer

    Stage 1 · Expected symptom

    gauntlet-worker.service cycles through activating (auto-restart) and failed. journalctl -u gauntlet-worker shows the restarts but nothing from the program — no traceback, no error, no last words.

    Stage 2 · Hint

    A program that is killed rather than exiting cannot log why: SIGKILL is uncatchable. So read the exit status rather than the logs — systemctl show -p ExecMainStatus -p Result gauntlet-worker — and then ask who does the killing.

    Stage 3 · Full fix

    Result=oom-kill and status 137 (128+9). systemctl cat gauntlet-worker shows a drop-in setting MemoryMax=16M against a program that allocates 64 MiB. Remove /etc/systemd/system/gauntlet-worker.service.d/10-gauntlet.conf, daemon-reload, restart. Fingerprint: exit 137 + silent log → look outside the program (B7.8).

    b14-mount-01 — the filesystem layer

    Stage 1 · Expected symptom

    /srv/gauntlet/data is empty. No deletion happened, the parent directory's timestamps look ordinary, and free disk space did not change.

    Stage 2 · Hint

    A directory can be covered rather than emptied — a mount hides whatever was underneath without touching it. Ask the kernel what is mounted where: findmnt /srv/gauntlet/data or mountpoint /srv/gauntlet/data.

    Stage 3 · Full fix

    findmnt shows a tmpfs mounted at /srv/gauntlet/data. sudo umount /srv/gauntlet/data and the three files reappear untouched. Fingerprint: files gone, nothing deleted, space unchanged → something is mounted over them (B5.11).

    b14-route-01 — the routing layer

    Stage 1 · Expected symptom

    From inside gauntlet-ns, pinging 10.77.0.1 works and pinging the VM's own primary address times out. The interface is up, the address is correct, and nothing is refused — it simply never arrives.

    Stage 2 · Hint

    Local subnet works, everything else does not: that is rung three of the ladder (B8.16) — link and address passed, routing did not. Ask the kernel which route it would use rather than reading the table: ip netns exec gauntlet-ns ip route get <target>.

    Stage 3 · Full fix

    ip route get reports via 10.77.0.99 — a gateway that does not exist. Replace it: sudo ip netns exec gauntlet-ns ip route replace default via 10.77.0.1. Fingerprint: subnet fine, off-subnet dead → the default route, and ip route get is the one command that says so (B8.6).

    b14-iptables-01 — the packet-filter layer

    Stage 1 · Expected symptom

    gauntlet-web.service is active, ss -ltnp shows it listening on 8082, and curl --max-time 3 http://127.0.0.1:8082/ hangs until the timeout rather than being refused.

    Stage 2 · Hint

    The distinction is the whole diagnosis: a refused connection means nothing is listening; a hang means the packets are being dropped in flight. Rung four of the ladder — read the ruleset, and read the counters, not just the rules: sudo iptables -L INPUT -n -v --line-numbers.

    Stage 3 · Full fix

    A DROP rule at the top of INPUT matching tcp dpt:8082, with a climbing packet counter. Delete that rule only — sudo iptables -D INPUT -p tcp --dport 8082 -j DROP — rather than flushing the table. Fingerprint: listener healthy + client hangs → filter, and the counter proves which rule (B9.14).

    b14-dns-01 — the name-resolution layer

    Stage 1 · Expected symptom

    getent hosts gauntlet.svc returns nothing and curl http://gauntlet.svc:8082/ fails to resolve — while grep gauntlet.svc /etc/hosts shows the entry sitting there, correct and readable.

    Stage 2 · Hint

    /etc/hosts is not consulted by magic: the resolver reads /etc/nsswitch.conf to decide which sources to try, in order, for hosts: lookups. Compare that line with a system you have not broken.

    Stage 3 · Full fix

    The hosts: line in /etc/nsswitch.conf has lost its files source, so /etc/hosts is never read. Restore it (hosts: files mdns4_minimal [NOTFOUND=return] dns, matching the backup in /root/.b14-fault-backups/). Fingerprint: dig and ping disagree, or a hosts entry is ignored → nsswitch, not DNS (B10.1).

    b14-systemd-01 — the service-management layer

    Stage 1 · Expected symptom

    gauntlet-api.service is failed, and journalctl -u gauntlet-api contains systemd's own restart messages and nothing else at all — no output from the program, not even a startup line.

    Stage 2 · Hint

    No program output means the program never ran. systemctl status names the stage that failed in its Process: line — read the code after status= and look it up rather than guessing (B11.9).

    Stage 3 · Full fix

    status=203/EXEC — systemd could not execute the command at all. systemctl cat gauntlet-api shows a drop-in that clears ExecStart= and repoints it at /usr/local/bin/gauntlet-api, which does not exist. Delete the drop-in, daemon-reload, restart. Fingerprint: 203/EXEC → path, execute bit or interpreter; never the program's own bug.

    b14-cert-01 — the TLS layer

    Stage 1 · Expected symptom

    gauntlet-tls.service is active and serving; curl --cacert …/ca.crt https://localhost:8443/ fails with a certificate error mentioning the host name. --insecure would work, which tells you the transport is fine and the identity check is not.

    Stage 2 · Hint

    Verification has two independent halves: is it signed by a CA I trust, and does it cover the name I asked for? Decide which one failed before touching anything — then print the certificate the server is actually serving: openssl s_client -connect localhost:8443 2>/dev/null | openssl x509 -noout -issuer -ext subjectAltName.

    Stage 3 · Full fix

    The issuer is still the Gauntlet CA — the chain is fine — but the SAN list reads DNS:gauntlet-internal, with no localhost and no 127.0.0.1. Reissue from the CSR and the CA key already in /srv/gauntlet/tls with subjectAltName=DNS:localhost,IP:127.0.0.1, then restart the unit. Fingerprint: chain OK, name rejected → the SAN list, fixed by reissuing, never by editing trust (B12.10).

    Gotchas

    The expensive habit this drill exposes is fixing before locating.     B14.6

    Post-mortem your own triage, and write the checklist

    Why it matters

    Speed on the CKA and speed in a real incident come from having an order, not from knowing more commands. Almost every minute you lost in run 1 will turn out to be a skipped rung or a guess made before evidence — and the reason to write it down is that you cannot fix a habit you have not named. This one page is the real deliverable of the module.

    The concept

    A post-mortem here has three columns and no blame. For each fault: what did you check first, what did it cost, and which single command would have found it fastest. That third column is the one that becomes your checklist, because it is the difference between knowing a tool and knowing when to reach for it.

    Two patterns show up in nearly everyone's first run. The first is fixing before locating — editing the thing that looks broken rather than establishing which layer the fault is in. The second is trusting a claim instead of testing it: believing a service is unreachable because a client failed, rather than checking whether it is listening. Both are cured by the same discipline, which is to make the next command answer a question rather than attempt a repair.

    Your checklist should be ordered by cost of checking, cheapest first, so the early rungs are one-command questions that rule out whole layers. A useful skeleton, which you should rewrite in your own words rather than copy: is the thing running (systemctl is-active, ps) → is it listening (ss -ltnp) → can I reach it locally (curl 127.0.0.1) → does the name resolve (getent hosts) → is the path routable (ip route get) → is anything dropping it (iptables -L -n -v) → what does its own log say (journalctl -u) → what does its exit status say (systemctl show -p).

    B14 recall quiz

    Answer out loud before revealing. If you can answer the first question in one sentence and defend every clause, the track has done its job.

    1. What is a container, in kernel terms?
      Answer

      A process, running on an overlay filesystem, in its own mount/PID/UTS/IPC/network namespaces, inside a cgroup that caps its CPU and memory, with a reduced capability set, attached to a bridge by a veth pair. Nothing else — there is no container object in the kernel, only those features switched on around an ordinary process.

    2. Name the four directories overlayfs needs, and say which one is the image and which is the container.
      Answer

      lowerdir (one or more, read-only, leftmost wins) — the image's layers, shared by every container using them. upperdir — the container's writable layer, discarded when it is removed. workdir — overlayfs's scratch space, must be empty and on the same filesystem as upper. merged — the mountpoint where the union appears.

    3. Why is chroot not a security boundary, and what does pivot_root add?
      Answer

      chroot changes what / resolves to but leaves the old root mounted and reachable, so a sufficiently privileged process can walk back out. pivot_root swaps the mount namespace's root and puts the old one at a path you then unmount — after which there is genuinely no path back. Its four preconditions: your own mount namespace, the new root is a mount point, it is not shared, and the old-root directory is under the new root.

    4. You ran a shell in a new PID namespace and ps lists the entire host. What happened?
      Answer

      You did not mount a fresh /proc inside. The PID namespace changed process numbering, but ps reads procfs, and the host's procfs still describes the host. unshare --mount-proc (or mount -t proc proc /proc after the pivot) fixes it — and this is the single most common "my container isn't isolated" confusion.

    5. Namespaces or cgroups: which one stops a container using every core, and which one stops it seeing the host's processes?
      Answer

      Namespaces hide; cgroups limit. The PID namespace stops it seeing host processes; cpu.max in its cgroup stops it using every core. They are completely independent — a process can be perfectly isolated and still consume the whole machine, which is exactly what B14.2 produced before B14.3 fixed it.

    6. Why does minibox configure the container's network from outside the namespace?
      Answer

      Because the process inside dropped CAP_NET_ADMIN, so every ip command it runs fails. The privileged parent configures the namespace by PID instead — which is exactly what a CNI plugin does when the kubelet hands it a pod's network-namespace path, and why workloads never need the capability at all.

    7. What does a real container stack add on top of what you built?
      Answer

      Standardisation, not mechanism: an image format and a registry instead of directories you assembled by hand; the OCI runtime spec instead of your own arguments; a CRI so a kubelet can drive it; and a CNI plugin contract instead of your networking function. Every one of them ends up making the same kernel calls you made.

    8. A file is mode 644 and a user still gets Permission denied. What is the one command?
      Answer

      namei -l /path/to/file — it prints every component of the path with its mode, and the fault is almost always a missing execute (traverse) bit on a parent directory. Reading a file requires x on every directory leading to it, and the file's own mode says nothing about that.

    9. A service exits with 137 and its log is empty. Where do you look, and what will you find?
      Answer

      Outside the program — it was killed, not stopped, and SIGKILL cannot be caught, so it never got to log anything. systemctl show -p Result says oom-kill, memory.events shows oom_kill incrementing, and the kernel log names the process. The cause is memory.max, wherever it was set.

    10. A client hangs until timeout instead of being refused. What does that distinction tell you?
      Answer

      Refused means the packet reached the host and nothing was listening — an RST came back. Hanging means the SYN is being dropped, so the fault is a filter, a route or a black hole, not the service. In the gauntlet this is the difference between the iptables fault and a stopped unit, and it is one curl --max-time away.

    11. getent hosts name fails while the entry is right there in /etc/hosts. Which file explains it?
      Answer

      /etc/nsswitch.conf — its hosts: line decides which sources the resolver consults and in what order, and removing files means /etc/hosts is never read. This is also why ping and dig can disagree: ping uses the resolver library, dig talks straight to a DNS server.

    12. status=203/EXEC. What failed, and what will the program's logs contain?
      Answer

      systemd could not execute the command at all — a wrong path, a missing execute bit, or a missing interpreter. The program's logs contain nothing, because the program never ran; that absence is the diagnostic. Check the path before you check anything else.

    13. A TLS client fails while the server is healthy and the CA is trusted. What is the fault, and what is the fix?
      Answer

      Name matching, not chain validation — the certificate's SAN list does not cover the name the client asked for (Hostname mismatch, error 62). The fix is to reissue the certificate with the right subjectAltName; it is never to edit the trust store, and never --insecure, which deletes the identity check while keeping the encryption.

    14. Why is the triage checklist ordered by cost of checking rather than by likelihood?
      Answer

      Because a one-second check that rules out a whole layer is worth running even when you are fairly sure it will pass — the expensive checks are still available afterwards, and the cheap ones narrow the search first. Ordering by likelihood means starting with the check you find most interesting, which is what cost the minutes in run 1.

    15. What does the second gauntlet run actually prove, and what does it not?
      Answer

      It proves that having an order beats improvising — the search was the slow part, and the fixes never were. It does not prove you can diagnose something you have not seen, because you knew the faults, so the run exercised recall as well as routine. The wider claim needs a fault someone else plants, or the same gauntlet a month later.
