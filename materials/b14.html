    B14 — Capstone: build minibox, then the gauntlet

    There is nothing new in this module. Every mechanism you are about to use has its own lesson behind it, and the only thing left is assembly — which turns out to be the part that changes how you see all of it. You will write one script that puts a process on its own filesystem, in its own namespaces, inside its own resource limits, with a reduced set of privileges, on its own network with a working name resolver, supervised by systemd and logging to the journal. That script is about 150 lines of bash, and it is, honestly, a container runtime.

    That is the point of the whole track stated as an artefact. A container is not a technology you install; it is a process with five kernel features switched on around it. Once you have switched them on by hand, "the pod won't start" stops being one opaque failure and becomes a question about which of six specific layers is unhappy — which is exactly what the second half of this module drills, with eight planted faults and a clock.

    Three parts. The capstone: minibox, built one layer at a time, each layer verified before the next goes on. The gauntlet: eight faults, one per layer, then a written post-mortem of your own triage order, then a second run to watch a routine beat improvisation. The assessment: a written self-test, a timed practical set, and an honest readiness checklist for what comes next.

    Checkpoints10 Hours~6 PrerequisitesAll of B0–B13
    • Assemble a root filesystem from stacked read-only layers plus one writable layer, and prove the lower layers are never modified.
    • Run a process in its own mount, PID, UTS, IPC and network namespaces, pivoted into that filesystem with its own /proc.
    • Put that process in a cgroup with CPU and memory caps, and strip the capabilities it does not need — then prove both bite.
    • Give it a network: a veth pair to a bridge, an address, a route, NAT egress and a resolver that works.
    • Wrap the whole thing in a systemd unit that supervises it and sends its output to the journal.
    • Explain, layer by layer, what a real container runtime adds on top of what you built — and what it does not replace.
    • Diagnose eight planted faults across eight layers inside 45 minutes, using evidence rather than guesses.
    • Write your own triage checklist from your own post-mortem, and beat your first time with it.
    • Score a written self-test spanning B0–B13, and re-read the module behind every wrong answer.
    • Pass a timed practical set against a 66% line, and confirm the readiness checklist for the Intermediate track.

    All of B0–B13. If any module still has unticked checkpoints, finish it first — the capstone assumes every layer is already familiar, and debugging two unfamiliar layers at once is how people conclude they are bad at this. Everything runs on the throwaway sandbox VM (B0.1), and this module both breaks and rebuilds it repeatedly, so take a snapshot before you start (B0.9) — the gauntlet plants eight faults on purpose. One package is needed for the capstone's root filesystem (busybox-static); the gauntlet scripts install nothing. The specific lessons this module assembles: overlayfs (B5.13), namespaces and pivot_root (B6.11), cgroup v2 limits (B7.6), capabilities (B4.10), veth/bridge/NAT (B9.8), resolver configuration (B10.3) and units (B11.3).

    Capstone — minibox, one layer at a time

    B14.1

    Layer 1 — the filesystem: stacked layers and one writable top

    Why it matters

    Before a container can have its own processes it needs its own files, and the way that is done is the single most surprising thing about container images: they are not disk images. They are directories, stacked. Building the stack by hand is what makes "image layer", "copy-on-write" and "the container's writable layer is thrown away" concrete rather than vocabulary.

    The concept

    Use the picture from B5.13: a stack of transparent sheets. You read through the whole stack, and you write only on the top one. overlayfs makes that literal with four directories — one or more lowerdirs (read-only, leftmost wins), an upperdir (writable), a workdir (overlayfs's scratch space, must be empty and on the same filesystem as the upper), and a merged mountpoint where the union appears.

    Two behaviours matter for what comes later. Copy-up: the first time you write to a file that lives in a lower layer, the whole file is copied into the upper layer and modified there — so the lower layer is never touched, and a large file's first write is expensive. Whiteouts: deleting a file that exists below does not remove it; it creates a marker in the upper layer that hides it. Both are why several containers can share one read-only image safely, and why a container's changes vanish when its upper directory is discarded.

    lower1 (base)+lower0 (config)+upper (writable)=merged

    Read through the stack, write only on top — the whole of container storage in one sentence.

    Verify

    Name the four directories overlayfs needs and what each is for, and state the ordering rule for multiple lower directories. Then explain steps 4–6 in image terms: which directory is the image (shared, read-only, reused by every container), which is the container (writable, per-instance, discarded on removal), and what docker commit would have to do to turn the second back into the first. If you can also say why the whiteout is a character device rather than a deleted file, you have the layer.

    Gotchas

    The workdir must be empty and on the same filesystem as the upperdir, and overlayfs will refuse the mount rather than explain why if either is wrong. If mount returns "invalid argument" with everything apparently correct, check those two things first — it is nearly always one of them, and the error message never says so.

    The second is copy-up cost. Writing one byte to a 2 GB file in a lower layer copies the entire 2 GB into the upper layer first. Containers that write into large image files behave inexplicably slowly on their first write and normally afterwards, and this is the reason — it is also why databases in containers are given a volume rather than being left on the overlay.

    You have just built a container image's storage model. On a Kubernetes node, containerd assembles exactly this for every container: the image's layers become the lowerdir list (shared read-only between every pod using that image, which is why the tenth pod from an image starts far faster than the first), and a fresh upperdir becomes the container's writable layer. That writable layer is why a pod's filesystem changes disappear on restart, why ephemeral-storage is a schedulable resource, and why writing large amounts of data inside a container without a volume eventually triggers node disk pressure.

    How the kubelet and containerd divide this work is W1.20; where the images and layers physically live on a node is W1.23; and volumes as the answer to "do not write into the overlay" is W5.1.

    Docs

    man 8 mount for the overlay options, and the kernel's own Documentation/filesystems/overlayfs.rst for the authoritative description of copy-up, whiteouts and the workdir rules. man 1 findmnt to confirm what is actually mounted where; man 1 busybox for the userland used above.

    B14.2

    Layer 2 — isolation: five namespaces, pivot_root and a fresh /proc

    Why it matters

    This is the layer where the thing stops looking like a directory and starts looking like a container. When ps inside your process shows one process — itself, as PID 1 — and nothing else on the machine, you are looking at the whole illusion, produced by five flags and a mount.

    The concept

    Five namespaces (B6.2), each hiding one kind of thing: mnt (its own mount table, so it can have its own root), pid (its own process numbering, so it becomes PID 1 and cannot see the host's processes), uts (its own hostname), ipc (its own shared-memory world) and net (its own interfaces, routes and ports — for now, completely empty, which B14.4 fixes).

    Then the root change. chroot moves the apparent root but leaves the old root reachable, which is why it is not a security boundary. pivot_root swaps the mount namespace's root for a new one and gives you the old root at a path you can then unmount — after which the host filesystem is genuinely unreachable, not merely out of sight. It has four preconditions (B6.11): you must be in your own mount namespace, the new root must be a mount point, it must not be shared, and the old-root directory must live under the new root. Every EINVAL from pivot_root is one of those four.

    Finally the step everyone forgets: mount a fresh /proc inside. A PID namespace changes process numbering, but ps reads /proc, so without a new procfs the "isolated" process cheerfully lists every process on the host. That mismatch is the clearest possible demonstration that isolation is not one switch.

    unshare 5 namespaces→pivot_root into merged→umount old root→mount -t proc

    Four steps, in that order; skipping the last one is the classic bug.

    Lab
    1. Start minibox.sh with the isolation step. The self-re-exec via _MINIBOX_STAGE is what lets one script be both the launcher and the thing that runs inside. 
      cat > ~/minibox.sh <<'EOF'
#!/usr/bin/env bash
# minibox — a container runtime in bash. Layers: fs, isolation, limits, network.
set -euo pipefail
ROOT=/srv/minibox
NAME=${NAME:-minibox}

mount_rootfs() {
  mountpoint -q "$ROOT/merged" && return 0
  rm -rf "$ROOT/upper" "$ROOT/work"; install -d -m 755 "$ROOT/upper" "$ROOT/work"
  mount -t overlay minibox-overlay \
    -o "lowerdir=$ROOT/lower-conf:$ROOT/lower-base,upperdir=$ROOT/upper,workdir=$ROOT/work" \
    "$ROOT/merged"
}

enter_rootfs() {                     # runs INSIDE the new namespaces
  mount --make-rprivate /
  mount --bind "$ROOT/merged" "$ROOT/merged"      # new root must be a mount point
  install -d "$ROOT/merged/.oldroot"
  cd "$ROOT/merged"
  pivot_root . .oldroot
  cd /
  umount -l /.oldroot && rmdir /.oldroot          # the host filesystem is now unreachable
  mount -t proc proc /proc                        # the step everyone forgets
  hostname "$NAME"
}

if [ "${_MINIBOX_STAGE:-}" = "inside" ]; then
  enter_rootfs
  exec "${@:-/bin/sh}"
fi

[ "$(id -u)" -eq 0 ] || { echo "run with sudo" >&2; exit 1; }
mount_rootfs
_MINIBOX_STAGE=inside exec unshare --mount --pid --uts --ipc --net --fork \
  "$0" "$@"
EOF
chmod +x ~/minibox.sh; bash -n ~/minibox.sh && echo "syntax ok"
      syntax ok

      sudo unshare --pid --fork --mount --uts /bin/sh -c 'ps -ef | wc -l'

    Verify

    Name the five namespaces and what each hides. Then explain the two things people get wrong here: why chroot is not a security boundary and pivot_root is (the old root is unmounted, so there is no path back to it), and why a PID namespace alone does not change what ps prints (it reads /proc, which must be remounted inside). Finally, list pivot_root's four preconditions from memory — every EINVAL it returns is one of them.

    Gotchas

    mount --make-rprivate / before anything else is not optional. systemd makes all mounts shared by default (B5.12), and a shared mount propagates your container's mounts back out to the host — which both breaks pivot_root's preconditions and, worse, silently modifies the host's mount table. Forget it and you will find mystery mounts on the host after the container exits.

    The second is the PID-1 duty this process has now inherited (B11.1). Your /bin/sh is PID 1 inside, which means the kernel will not deliver SIGTERM to it without a handler, and it must reap orphans. That is why a real runtime either uses a tiny init like tini or requires the application to handle signals — and why some containers take exactly the full grace period to stop.

    A pod is a group of containers that share some of these namespaces and not others, and now you can say precisely which. Containers in a pod share the net namespace — which is why they reach each other on localhost and why they cannot both bind port 8080 — plus ipc and, optionally, pid (shareProcessNamespace: true). Each keeps its own mnt namespace, which is why they have separate filesystems and need a shared volume to exchange files. The namespace that holds the pod's network is created and held open by the pause container, which does nothing but exist so that the namespace outlives any individual container restarting inside it.

    The pause container and what it is actually for is W1.21; the CRI path from kubelet to containerd to runc that performs these calls is W1.20.

    Docs

    man 1 unshare for the flags used here — note --fork, which is required for --pid to affect the child rather than nothing. man 2 pivot_root for the four preconditions and the exact EINVAL conditions; man 7 pid_namespaces for the PID-1 rules; man 7 mount_namespaces for propagation and why --make-rprivate matters.

    B14.3

    Layer 3 — limits and privilege: a cgroup and a smaller keyring

    Why it matters

    Namespaces hide; they do not limit. The process you built in B14.2 cannot see the host, and it can still consume every core and all the memory on it, and it is still running as root with every capability. This layer is where a hidden process becomes a contained one, and it is exactly the difference between "it works on my machine" and "it is safe to run next to other people's workloads".

    The concept

    Two independent mechanisms, both from earlier modules.

    Resource limits come from cgroup v2 (B7): a directory under /sys/fs/cgroup is a cgroup, writing a PID into its cgroup.procs moves that process (and everything it later forks) into it, and the control files set the caps. cpu.max is a hard ceiling expressed as quota period in microseconds — 50000 100000 means half a core, enforced even when the machine is idle. memory.max is a hard limit whose enforcement is the OOM killer: exceed it and the kernel sends SIGKILL, which the process cannot catch, so its own logs will never explain what happened.

    Privilege comes from capabilities (B4.10): root is not one flag but a keyring of about forty individually-grantable permits. A container that never configures interfaces does not need CAP_NET_ADMIN; one that never mounts anything does not need CAP_SYS_ADMIN. Dropping the bounding set removes them permanently for that process and everything it spawns, so a compromise inside the container cannot pick them back up. Add --no-new-privs and the setuid escape hatch closes too (B4.9).

    namespaces hide·cgroups limit·capabilities restrict→a container

    Three orthogonal mechanisms; a container is all three at once, and nothing else.

    Lab

    State the one-line difference between namespaces and cgroups, and give the exact evidence trio for an OOM kill: exit code 137, oom_kill in memory.events, and a kernel message — with nothing at all in the application's own log, because SIGKILL cannot be caught. Then explain why dropping the bounding set matters more than dropping the effective one, and what --no-new-privs adds on top.

    Gotchas

    Order matters when joining a cgroup: write the PID before the process forks the workload, because cgroup.procs moves one process, and children inherit membership only from the moment they are created. Move the parent first and everything below it is caged; move it after and the workers you already started are outside the cage, running unlimited, while the tidy-looking parent sits inside it.

    The second is dropping capabilities you actually need and then blaming the wrong layer. If minibox suddenly cannot bring up its own interface in B14.4, that is this lesson's --drop=cap_net_admin doing its job — the fix is to configure the network from outside the namespace, which is exactly what a real runtime does, rather than to hand the capability back.

    Both mechanisms appear directly in a pod spec. resources.requests and resources.limits become the cgroup you just wrote by hand — a CPU limit is cpu.max, a memory limit is memory.max, and a CPU request is cpu.weight, which is why requests only matter under contention while limits bite on an idle node. The QoS class a pod lands in is derived from which of those it sets, and it decides who the kernel kills first under pressure. securityContext.capabilities.drop is the keyring, and allowPrivilegeEscalation: false is --no-new-privs. Exit code 137 on a pod means the same thing it meant above, one layer up.

    Requests versus limits, and which is bookkeeping versus enforcement, is W3.16; QoS classes and what they buy at OOM time is W3.17; node-pressure eviction is W3.18.

    Docs

    The kernel's Documentation/admin-guide/cgroup-v2.rst is the reference for cpu.max, memory.max, cpu.stat and memory.events. man 7 capabilities for the permit list and the bounding set; man 1 capsh for --drop and --no-new-privs; man 2 prctl for PR_SET_NO_NEW_PRIVS itself.

    B14.4

    Layer 4 — network, names and supervision: minibox, finished

    Why it matters

    An isolated, limited process with no network is not much use. This layer gives it an address, a route out, a name resolver and a supervisor — and when it is done you will have a script that does everything a container runtime does, which is the point at which you can say exactly what the real ones add.

    The concept

    The network namespace from B14.2 starts with nothing: one loopback interface, down, no routes, no ports. Filling it is four steps you already know from B9.8, done from outside the namespace because the process inside no longer has CAP_NET_ADMIN:

    1. A veth pair — a virtual patch cable. One end goes into the container's namespace, the other is plugged into a bridge on the host.
    2. An address and a route inside: an IP on the subnet, and a default route via the bridge.
    3. NAT egress: a MASQUERADE rule so replies to the private address find their way back, plus ip_forward on the host.
    4. A resolver: a /etc/resolv.conf inside the container pointing at something that will actually answer (B10.3).

    Then supervision. Wrapping the script in a systemd unit (B11.3) gives you restart policy, boot enablement, journald logging and a cgroup for free — and makes the last comparison honest, because that is roughly the relationship between a kubelet and the containers it runs.

    Now the comparison worth carrying into the next track. What a real stack adds is standardisation, not mechanism: an image format and a registry instead of directories you assembled by hand; the OCI runtime spec instead of your argument parsing; a CRI so a kubelet can drive it; and a CNI plugin contract instead of your networking script. None of them replace what is underneath — every one of them ends up making the same calls you just made.

    veth + bridge→address + route→NAT→resolv.conf→systemd unit

    Four network steps and a supervisor; that is the whole remaining gap.

    Lab
    1. Add the networking function to minibox.sh. It runs on the host, against the child's PID, which is how every runtime does it. 
      python3 - <<'PY'

    Gotchas

    Configure the network from outside the namespace, not inside it. The process inside dropped CAP_NET_ADMIN in B14.3, so every ip command it runs will fail — and the temptation to hand the capability back is exactly the wrong lesson. Real runtimes do it the way setup_net does: the privileged parent (or a CNI plugin) configures the namespace by PID, and the workload never has the permit at all.

    The second is cleanup. Namespaces, veth interfaces, bridges, NAT rules, cgroup directories and overlay mounts all outlive a crashed script, and a few failed runs leave a machine littered with mbv* interfaces and duplicate MASQUERADE rules (B9.19 made exactly this mistake). Deleting the veth removes both ends and the namespace disappears with its last process, but the NAT rule and the cgroup directory need removing explicitly — which is why real runtimes track state on disk rather than trusting a script to unwind.

    Compare your four network steps with what happens when a pod starts on a node. The kubelet asks containerd to create the sandbox; containerd (through runc) creates the namespaces and starts the pause container to hold the network namespace open; then the kubelet calls a CNI plugin, handing it the namespace path — and the plugin does precisely what setup_net does: create a veth pair, put one end in the namespace, attach the other to a bridge (or an overlay interface), assign an address from its IPAM range, and add a route. Your printf 'nameserver …' is the kubelet writing /etc/resolv.conf from the pod's dnsPolicy, pointing at the cluster's DNS service instead of a public resolver.

    The CNI contract and how a pod actually gets its address is W4.5; the kubelet-to-containerd path that drives all of it is W1.20; and the pod DNS configuration your resolv.conf line stands in for is W4.16.
