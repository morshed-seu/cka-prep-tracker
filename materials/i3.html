    I3 — runc internals

    I2 told you what a container is: a directory with a config.json in it, and a specification saying what any runtime must do when handed one. This module is about the runtime doing it. Not the abstract "a runtime applies the config" of the last module — the actual sequence of system calls, in order, with the reasons each one has to come where it does.

    The centre of the module is a surprise that catches nearly everyone. runc does not stay running. It builds the container and then exits, leaving your workload re-parented to PID 1 with nobody watching it. That is not a bug and it is not laziness; it is a deliberate design choice, and it is the reason an entire category of software — shims — exists at all. By the end of this module you will have written one, in about sixty lines of Python, and you will understand exactly what job you were filling.

    Along the way you will trace the three-process dance that makes a container, read the private environment-variable handshake the two halves of runc use to talk to each other, find the file that a daemonless runtime uses as its memory, and hand-build the exact invocation pattern that CNI will standardise in I9.

    Creation, step by step

    I3.1

    The runtime runs a second copy of itself

    Why it matters

    There is a puzzle hidden in every container runtime, and it is worth stating before you see the answer. A runtime has to put your program inside a set of brand-new namespaces. But unshare() changes the namespaces of the process that calls it — so if runc called unshare directly, runc itself would end up inside the container it was building. It would be trapped in the thing it made. Every runtime has to solve this, and watching runc solve it explains a process tree that otherwise looks bizarre.

    The concept

    The answer is that runc splits itself in two. The copy you invoked stays outside and stays in charge; it spawns a second copy of the runc binary, told to run as runc init, and that copy is the one that gets buried under namespaces, mounts and capability drops until nothing of it is left but your program. In the track's analogy: the contractor does not move into the building. They send an apprentice in, brick up the door behind them, and the apprentice becomes the tenant.

    Even that is a simplification. runc actually uses three processes, and they have names in runc's own debug output — stage 0, stage 1 and stage 2 — belonging to a C routine called nsexec that runs before Go's runtime even starts. The reason for the third one is precise and worth internalising, because it is a property of the kernel and not of runc: unshare(CLONE_NEWPID) does not move the caller into the new PID namespace. It only arranges that the caller's next children are born in it. So stage 1 unshares, and then must clone() once more to produce stage 2 — the process that is actually PID 1 inside. There is no way to skip that step.

    stage 0
    runc init    →stage 1
    unshares    →stage 2
    PID 1 inside    →your program

    One more detail hides in the execve you are about to see, and it is a security fix with a CVE behind it. runc does not re-execute itself by path — it re-executes a file descriptor. If it ran /usr/local/sbin/runc by name, a malicious container image could arrange for that path to resolve to something else by the time it was used, and get its own code run with the host's privileges. Instead runc makes a sealed, read-only clone of its own binary and execs the fd; the container never gets a path it could tamper with.

    Notice what the specification has to say about any of this:

    This operation MUST create a new container. All of the properties configured in config.json except for process MUST be applied.
    OCI Runtime Specification v1.3.0 — runtime.md, "Create"

    That is the whole requirement. Three processes, nsexec, stage numbering, sealed binaries — none of it is specified, and none of it has to be. The spec constrains the observable result; everything on this page is runc's private business, which is exactly why crun can reach the same result with completely different code. Remember that when something here surprises you: you are reading an implementation, not a standard.

    Lab
    1. Trace the creation with strace, restricted to the handful of calls that actually build a container. One warning first, because it will bite you: strace -f waits for every process it follows, and runc create deliberately leaves one alive. So strace will not return on its own — wrap it in timeout. 
      cd ~/i3/box
sudo timeout -s KILL 25 strace -f -o /tmp/s1.trace \
  -e trace=clone,clone3,unshare,setns,mount,pivot_root,execve \
  runc create s1 < /dev/null
sudo runc list
      Killed
ID   PID     STATUS     BUNDLE                CREATED
s1   31593   created    /home/ubuntu/i3/box   2026-07-27T14:02:45Z

      Killed is strace being timed out, not a failure — the container was created successfully, which is what runc list confirms.

    2. Find the re-execution. This is the single most important line in the trace. 
      sudo grep -E 'execve|unshare' /tmp/s1.trace
      31583 execve("/usr/local/sbin/runc", ["runc", "create", "s1"], … ) = 0
31591 execve("/proc/self/fd/6", ["runc", "init"], 0xc0000a80c0 /* 7 vars */) = 0
31592 unshare(CLONE_NEWNS|CLONE_NEWCGROUP|CLONE_NEWUTS|CLONE_NEWIPC|CLONE_NEWPID|CLONE_NEWNET) = 0

      Three things at once. The binary re-executed itself as runc init; it did so from /proc/self/fd/6 rather than from a path; and all six namespaces are unshared in a single call by a different process from the one that exec'd.

    3. Read the process tree out of the trace. Follow the PIDs, not the order of lines. 
      sudo grep -E 'clone\(child_stack|unshare' /tmp/s1.trace
      31583 clone(…, flags=CLONE_VM|CLONE_PIDFD|CLONE_VFORK|SIGCHLD)   = 31591
31591 clone(child_stack=…, flags=CLONE_PARENT|SIGCHLD)          = 31592
31592 unshare(CLONE_NEWNS|…|CLONE_NEWPID|CLONE_NEWNET)           = 0
31592 clone(child_stack=…, flags=CLONE_PARENT|SIGCHLD)          = 31593

      31583 is the runc create you typed. 31591 is stage 0, the re-exec'd runc init. 31592 is stage 1, which does the unsharing. 31593 is stage 2 — the container's PID 1, and the number runc list reported. Note CLONE_PARENT on both clones: each new stage is made a sibling rather than a child, so that when the intermediate stages exit, stage 2 is left parented to the original runc rather than orphaned mid-setup.

    4. Now get runc to narrate the same thing in its own words. This is far easier to read than the trace, and it is the tool to reach for when something goes wrong. 
      sudo runc delete --force s1
sudo setsid runc --debug create s1 < /dev/null > /tmp/dbg.out 2>&1
sudo grep -E 'exeseal|nsexec-[012]' /tmp/dbg.out | head -14
      msg="runc exeseal: using overlayfs for sealed /proc/self/exe"
msg="runc exeseal: using /proc/self/exe clone"
msg="nsexec-0[33659]: ~> nsexec stage-0"
msg="nsexec-0[33659]: spawn stage-1"
msg="nsexec-1[33660]: ~> nsexec stage-1"
msg="nsexec-1[33660]: unshare remaining namespaces"
msg="nsexec-1[33660]: spawn stage-2"
msg="nsexec-1[33660]: request stage-0 to forward stage-2 pid (33661)"
msg="nsexec-2[1]: ~> nsexec stage-2"

      Two payoffs. exeseal is the sealed-binary machinery from the concept above, telling you which of its three methods it managed to use. And look at stage 2's bracketed PID: 1. It is already reporting its own PID from inside the new namespace, so you can see the exact line at which the container's inside and outside stop agreeing about numbers.

    5. Confirm the sealed binary is a real, unnameable copy rather than the file on disk. 
      P=$(sudo runc state s1 | jq -r .pid)
sudo readlink /proc/$P/fd/6
sudo stat -Lc 'dev=%d ino=%i size=%s' /proc/$P/fd/6
sudo stat -c  'dev=%d ino=%i size=%s' /usr/local/sbin/runc
      /runc
dev=53    ino=8443 size=11437312
dev=2049  ino=8443 size=11437312

      Same inode and same size — it is unmistakably runc — but on a different device, because it is being served from an overlay mount that exists only for this purpose. The name /runc resolves to nothing the container can reach.

    Verify

    You can point at the exact execve line where one process became two, name all three stages by PID from the trace, and say — without looking it up — why stage 1 could not simply have become the container itself.

    Gotchas
    • strace -f on runc create hangs, and it is not a mistake. The whole point of create is that it leaves a process alive and waiting. strace has nothing to report and will not exit; always use timeout. This trips people up badly the first time, because "the trace hung" reads like "the runtime hung".
    • You will not see the container's own program exec'd in this trace — no /bin/sleep, nothing from process.args. That is not strace losing it. create genuinely stops before that point, which is I3.5's subject.
    • runc init is not a command you run. If you find it in a process list it is a container mid-setup, or one parked between create and start. Typing it yourself gets you an error about a missing init pipe, because it is only meaningful with the handshake I3.2 covers.
    • The exeseal method varies by machine. Overlayfs is preferred, memfd_create is next, and a temporary file is the last resort — the debug log names which one it took. If you are on a box with vm.memfd_noexec=2 or no overlayfs, expect a different line there and do not read it as a fault.

    The three-stage dance is invisible from Kubernetes, but its consequence is not. When a pod is stuck and crictl inspect shows a container created but not running, the process you would find on the node is exactly the stage-2 runc init above, waiting. And the sealed-binary machinery is the fix for CVE-2019-5736, a container-escape that worked precisely by overwriting the runtime binary through /proc/self/exe — worth knowing when a scanner flags a node's runc version. Where the runtime sits in the stack is W1.20, kubelet → containerd → shim → runc.

    Docs: runc's nsexec.c — the C source for all three stages, unusually well commented; man 2 unshare for the CLONE_NEWPID caveat, which the man page states explicitly and almost everyone misses.

    I3.2

    The private handshake between the two halves

    Why it matters

    Once you know a runtime splits itself in two, an obvious question follows: how does the half that stays outside tell the half that is being buried what to do? It cannot use command-line arguments — you saw the exec, and the arguments were just runc init, nothing more. It cannot use a config file, because the inside half is about to lose access to the filesystem the config lives on. The answer is a small, private, entirely undocumented protocol, and reading it turns the runtime from a black box into a program.

    The concept

    The channel is set up before the exec, using the two things that survive it: open file descriptors and environment variables. File descriptors stay open across execve unless explicitly marked close-on-exec, so the outer half opens the pipes it needs, and then uses environment variables to tell the inner half which numbers they landed on. That is all the _LIBCONTAINER_* variables are: a directory of fd numbers.

    The leading underscore is a convention meaning "internal, do not depend on this". These names are not in any specification, they are not in runc's man pages, and they can change between releases. They are still worth knowing, because they appear in every strace of every container start on earth.

    variablewhat is on the other end
    _LIBCONTAINER_INITPIPEThe main channel — a socketpair, not a pipe, because the protocol needs to pass file descriptors as well as bytes. The outer half writes the bootstrap message down it.
    _LIBCONTAINER_SYNCPIPEThe step-by-step synchronisation channel used after bootstrap, so each side can block until the other has finished a stage.
    _LIBCONTAINER_LOGPIPEHow the inner half gets log lines out. Without it, errors raised after the mount namespace is swapped would have nowhere to go.
    _LIBCONTAINER_FIFOFDAn open fd on exec.fifo — the thing that makes create stop before running your program. I3.5's subject, and the single most load-bearing fd here.
    _LIBCONTAINER_INITTYPEstandard for a new container, setns for runc exec joining an existing one. One binary, two jobs.

    The bootstrap message itself is netlink-formatted — the same length-type-value encoding the kernel uses for ip commands, reused here purely as a convenient binary format between two userspace processes. It carries the namespaces to create or join, the UID/GID mappings, and the OOM score. It has to be a binary message rather than JSON because it is parsed by nsexec's C code, which runs before Go exists in the process.

    The specification describes exactly one thing a runtime must communicate, and it is not any of this:

    pid (int, REQUIRED when status is created or running on Linux) is the ID of the container process.
    OCI Runtime Specification v1.3.0 — runtime.md, "State"

    Everything in this lesson is beneath that line. The spec cares that a PID comes out; how the runtime's halves negotiated it is left entirely alone. This is a good habit to build now: when you meet a runtime behaviour, ask first whether it is required, permitted, or merely what this one does — the three have very different implications when you are debugging a mixed cluster.

    Lab
    1. strace does not print environments by default. Add -v and you get the whole handshake in one line. 
      sudo runc delete --force s2 2>/dev/null
sudo timeout -s KILL 25 strace -f -v -s 200 -o /tmp/s2.trace \
  -e trace=execve runc create s2 < /dev/null
sudo grep 'runc", "init' /tmp/s2.trace
      31851 execve("/proc/self/fd/6", ["runc", "init"], ["GOMAXPROCS=",
  "_LIBCONTAINER_INITPIPE=3", "_LIBCONTAINER_SYNCPIPE=4",
  "_LIBCONTAINER_LOGPIPE=5",  "_LIBCONTAINER_LOGLEVEL=4",
  "_LIBCONTAINER_FIFOFD=7",   "_LIBCONTAINER_INITTYPE=standard"]) = 0

      Seven variables, and the container's own environment is not among them — process.env from the config is delivered later, over the init pipe, not through this exec.

    2. Verify the numbers are real by looking at the surviving process's open files. Every variable above should point at something you can identify. 
      P=$(sudo runc state s2 | jq -r .pid)
sudo ls -l /proc/$P/fd
      0 -> /dev/null
1 -> /tmp/s2.out
2 -> /tmp/s2.out
3 -> socket:[114982]

      fd 3 is a socket:, confirming the init pipe is a socketpair rather than an ordinary pipe — which is what lets it carry file descriptors. And there is exec.fifo, on the fd number the handshake announced. Hold that thought until I3.5.

    3. Confirm the claim about INITTYPE by watching what a second kind of init looks like. Leave the container running and exec into it. 
      sudo runc start s2
sudo timeout -s KILL 15 strace -f -v -s 120 -o /tmp/s3.trace \
  -e trace=execve runc exec s2 /bin/true
sudo grep -o '_LIBCONTAINER_INITTYPE=[a-z]*' /tmp/s3.trace | sort -u
      _LIBCONTAINER_INITTYPE=setns

      The same binary, re-exec'd the same way, told by one environment variable to join namespaces instead of creating them. That is the whole difference between starting a container and kubectl exec-ing into one.

    Verify

    You can name what is on the other end of every _LIBCONTAINER_* fd, explain from evidence why the init pipe must be a socket rather than a pipe, and say what changes between INITTYPE=standard and INITTYPE=setns.

    Gotchas
    • Without -v, strace hides all of this. The default output shows 0xc0000a80c0 /* 7 vars */ and moves on. People conclude the exec carries no information and go looking for a config file that does not exist.
    • Do not build anything on these variable names. They are private, they have changed before, and the older write-ups you will find describe a slightly different set (_LIBCONTAINER_STATEDIR and _LIBCONTAINER_CONSOLE appear in material written against runc 1.0 and are simply absent in 1.5.1). Read them as diagnostics, never as an interface.
    • An fd number in the environment is meaningless outside that process. _LIBCONTAINER_INITPIPE=3 is only true for the one child it was exported to. Reading it from anywhere else and opening fd 3 gets you something unrelated.

    You will see these variables again the first time you strace a stuck pod on a node, and their presence is diagnostic: a runc init process holding _LIBCONTAINER_FIFOFD is a container that was created and never started, which usually means the thing that should have called start — the shim, or the CNI plugin ahead of it — is what is actually wedged. That is a very different investigation from "the application won't boot", and it is the practical payoff for reading a handshake nobody documents. Pod-startup failure modes are catalogued in W6.16.

    Docs: man 2 execve on which file descriptors survive an exec (the FD_CLOEXEC rule this whole design rests on); man 7 netlink for the message format the bootstrap data borrows; and runc's message_linux.go for the bootstrap message's actual fields.

    I3.3

    The order of operations, verified in /proc

    Why it matters

    A container is not created by one action but by a sequence of them, and the sequence is fixed. Knowing it converts a large class of mysterious failures into obvious ones: if you know that mounts happen after the namespaces and before the capability drop, then "my mount failed with EPERM" and "my mount succeeded but the file isn't there" become questions with different answers. This lesson establishes the sequence and — more usefully — teaches you to confirm it yourself rather than trusting a list.

    The concept

    The order, as runc performs it:

    namespaces→cgroup→mounts→pivot_root→capabilities→seccomp→execve

    Each of these leaves a trace somewhere in /proc/<pid>/ that you can read from outside, which is what makes the sequence checkable rather than folklore:

    stepwhere it becomes visible
    namespaces/proc/<pid>/ns/* — inode numbers differing from the host's
    cgroup/proc/<pid>/cgroup, and the pid appearing in that cgroup's cgroup.procs
    mounts + pivot_root/proc/<pid>/mountinfo — the entry whose mount point is /
    capabilitiesCapBnd, CapEff and CapPrm in /proc/<pid>/status
    seccompSeccomp and Seccomp_filters in the same file
    execve/proc/<pid>/cmdline — your program's name replacing runc init

    There is one very convenient property of runc create that makes this easy to check: it performs every step except the last, and then stops. So a created-but-not-started container is a container frozen one instruction before your program begins — you can walk down the table above at your leisure and find all six earlier steps already done.

    The stopping point is not runc being helpful; it is required:

    All of the properties configured in config.json except for process MUST be applied. process.args MUST NOT be applied until triggered by the start operation. The remaining process properties MAY be applied by this operation.
    OCI Runtime Specification v1.3.0 — runtime.md, "Create"

    Read the last sentence carefully, because it is the source of a real portability trap. process.args is pinned to start, but everything else under process — capabilities, rlimits, the user — is MAY. runc applies them at create, as the lab below shows. A different runtime is entitled to defer them, and any tool that inspects a created container to see what it will be allowed to do is depending on behaviour the spec does not promise.

    Lab
    1. Create without starting, and walk the table. Every line below reads a different piece of evidence for a different step. 
      cd ~/i3/box
sudo runc delete --force s5 2>/dev/null
sudo setsid runc create s5 < /dev/null > /tmp/s5.out 2>&1
P=$(sudo runc state s5 | jq -r .pid)

printf 'namespaces : '; sudo readlink /proc/$P/ns/pid
printf 'cgroup     : '; sudo cat /proc/$P/cgroup
printf 'rootfs     : '; sudo awk '$5=="/" {print $4}' /proc/$P/mountinfo
printf 'caps       : '; sudo awk '/^CapBnd/{print $2}' /proc/$P/status
printf 'seccomp    : '; sudo awk '/^Seccomp:/{print $2}' /proc/$P/status
printf 'program    : '; sudo tr '\0' ' ' < /proc/$P/cmdline; echo
      namespaces : pid:[4026532406]
cgroup     : 0::/user.slice/user-1000.slice/s5
rootfs     : /home/ubuntu/i3/box/rootfs
caps       : 0000000020000420
seccomp    : 0
program    : runc init

      Five of six steps are already visible. A private PID namespace exists, a cgroup has been made and joined, the bundle's rootfs is mounted as this process's /, and the capability set has already been cut down. Seccomp: 0 only because the default runc spec config has no seccomp section — add one and this reads 2. The last line is the giveaway: the program is still runc init.

    2. Decode that capability mask rather than squinting at hex. 
      capsh --decode=0000000020000420
      0x0000000020000420=cap_kill,cap_net_bind_service,cap_audit_write

      Three capabilities — the default runc spec set from I2.4. Crucially CAP_SYS_ADMIN is gone, and it is CAP_SYS_ADMIN that mount and pivot_root require. The mounts you just confirmed in mountinfo could not have been made by a process holding only this set, which is direct evidence that the drop came after the mounting.

    3. Now trigger the last step and watch exactly one thing change. 
      sudo runc start s5
sleep 0.3
printf 'program    : '; sudo tr '\0' ' ' < /proc/$P/cmdline; echo
printf 'namespaces : '; sudo readlink /proc/$P/ns/pid
sudo runc list
      program    : sleep 1000
namespaces : pid:[4026532406]     # unchanged
ID   PID     STATUS     BUNDLE                CREATED
s5   33759   running    /home/ubuntu/i3/box   2026-07-27T…

      Same PID, same namespace inode, different program. That is execve doing what execve does — replacing the program inside an existing process, keeping everything the process already held. It is the cleanest possible demonstration that all the container's isolation was built around a process before your code ever ran in it.

    4. Prove the capability claim from the other direction: ask the running container to mount something. 
      sudo runc exec s5 /bin/sh -c 'mount -t tmpfs none /mnt; echo rc=$?'
      mount: permission denied (are you root?)
rc=1

      It is uid 0 and it still cannot mount, because the bounding set has no CAP_SYS_ADMIN. Root inside a container is exactly the capabilities it was left holding and nothing more — the point B4 made with capsh, now enforced by a runtime.

    Verify

    You can recite the seven steps, name the file in /proc that proves each one, and demonstrate on a live container that create completes six of them.

    Gotchas
    • Seccomp: 0 does not mean seccomp failed. The stock runc spec output has no linux.seccomp section at all, so there is nothing to install. Container runtimes higher up the stack add one — which is why a container run through ctr or a kubelet shows Seccomp: 2 here and a hand-built bundle does not.
    • The cgroup path depends on who invoked runc. Run as a normal user's sudo, the container landed under /user.slice/user-1000.slice/; run from a system service it lands elsewhere. Do not memorise the path, read it.
    • /proc/<pid>/mountinfo shows the host's view of the paths, so the root entry names the bundle directory rather than /. That is correct and often confusing — you are reading a container's mounts through a host process's eyes.
    • Do not infer ordering from a single snapshot. Everything above was already true when you looked. The evidence for the order is the capability argument in step 2 — a step that cannot have happened after the drop must have happened before it — not the fact that all six are visible at once.

    This sequence is why securityContext settings that look equivalent behave differently. A volume mounted into a pod is applied during the mount phase, by the runtime, holding full privilege — so it succeeds regardless of how thoroughly you strip the container's capabilities. But anything the application tries to mount at runtime, including the surprisingly common case of a process wanting to remount /proc, runs after the drop and fails. The advanced track has no dedicated securityContext lesson; the closest material is W7.1 on the authorisation model and W3.16 on how pod-level settings reach the runtime.

    Docs: man 5 proc for status, mountinfo and ns/ — the three files this lesson lives in; man 7 capabilities for what CAP_SYS_ADMIN actually gates, which is a longer list than anyone expects.

    I3.4

    Why the order is forced, not chosen

    Why it matters

    I3.3 gave you a sequence. A sequence you have merely memorised is fragile — you will misremember it under pressure, and you will have no way to check. This lesson gives you the rule the sequence follows, and a rule can be re-derived. It is one sentence long, and once you have it you can work out the correct position of a step you have never seen before, including steps in runtimes that do not exist yet.

    The concept

    Here is the rule:

    Every step in container setup removes a power. So each step must run after everything that still needs the power it removes.

    Container creation is a one-way descent. It begins with a process holding everything — full root, all capabilities, unrestricted syscalls, the host's whole filesystem — and it ends with a process holding almost nothing. Each step is a door closing behind you. Which means the sequence is not a design decision at all; it is forced by a dependency graph, and there is essentially only one valid ordering.

    Work the two swaps the checkpoint asks for and you will see the rule bite twice.

    Swap one: seccomp before mounts. A seccomp profile is a filter on system calls. Container profiles routinely block mount, umount2, pivot_root and the whole family of namespace calls — those are exactly the syscalls you do not want a compromised container making. But the setup process needs every one of them; it has a dozen mounts to perform and a root to pivot into. Install the filter first and the runtime immediately blocks itself. The failure is spectacular and completely self-inflicted: the container fails to create, with an EPERM from a syscall the runtime made against a filter the runtime installed on itself.

    Swap two: capabilities before pivot_root. pivot_root(2) requires CAP_SYS_ADMIN in the mount namespace's owning user namespace. You verified in I3.3 that the container's bounding set is three capabilities and CAP_SYS_ADMIN is not one of them. Drop first and the pivot returns EPERM — the container would be left running your program on the host's root filesystem, if the runtime were careless enough to continue. Which is why the ordering matters as a security property and not merely a functional one: get it wrong and the failure mode is not "container does not start", it is "container starts, unisolated".

    The same rule places execve unarguably last. Your program is the one participant that must never hold any of the powers being removed, so everything happens before it and nothing after. And it places seccomp immediately before execve, second-to-last, for the same reason capabilities come late: it is the most aggressive restriction, so it goes on at the last possible moment.

    One genuine subtlety, and the exception that proves the rule: seccomp is installed after capabilities rather than before, even though both are "restrictions". The reason is NoNewPrivs. Installing a seccomp filter as an unprivileged process requires the no_new_privs bit, and setting that bit is itself irreversible — so it has to come after any step that might have needed to gain privilege. The ordering rule still holds; you just have to count no_new_privs as a power being removed too.

    The specification is deliberately silent about ordering — with exactly one exception, and it is instructive:

    The createRuntime hooks MUST be called as part of the create operation after the runtime environment has been created (according to the configuration in config.json) but before the pivot_root or any equivalent operation has been executed. […] The createContainer hooks MUST be called after the createRuntime hooks.
    OCI Runtime Specification v1.3.0 — config.md, "POSIX-platform Hooks"

    The spec pins the ordering only where a third party can observe it. Hooks are other people's code, so the spec must promise them a position — and note it does so by naming the one landmark that matters, pivot_root, rather than by describing the sequence. The rest of the order is unmentioned because nobody outside the runtime can tell, and, as the argument above shows, because there is only one way to do it anyway. I3.11 puts a hook in that window and makes it do real work.

    Lab
    1. This lesson is reasoning, not a patch to runc — but the premises are checkable, and you should check them rather than take them on faith. Start with the capability requirement for pivot_root, using a bare shell and no runtime at all.

    Verify

    State the rule in one sentence without looking. Then, given a hypothetical new setup step — say, "apply a Landlock filesystem policy" — place it correctly in the sequence and justify the placement from the rule alone.

    Gotchas
    • "Restrictions last" is a good heuristic, not the rule. It fails on pivot_root, which is not a restriction at all yet must precede the capability drop. Use the dependency form — after everything that needs what it removes — and it never fails.
    • Cgroup placement is the one step with genuine flexibility. Joining a cgroup does not remove a power the later steps need, so runtimes differ on exactly when they do it, and both CLONE_INTO_CGROUP and a post-hoc write to cgroup.procs are legitimate. If a memory limit appears to be enforced slightly later than you expected, this is why.
    • Do not reason about ordering from an strace of a multithreaded runtime. Go's scheduler interleaves threads and the trace lines will not be in causal order. The --debug narration from I3.1 is sequenced correctly; the raw trace is not.

    This is the rule behind a Kubernetes behaviour that reads as inconsistent until you know it. allowPrivilegeEscalation: false sets no_new_privs, and because that bit is irreversible and set before execve, a setuid binary in the image simply stops working — with no error mentioning Kubernetes, the pod spec, or privileges. Likewise an init container that needs to mount something must be privileged, not merely capability-granted, because it runs as a normal container after the runtime has already descended. The general shape — configuration applied by the runtime at creation, invisible afterwards — is W3.16.

    Docs: man 2 pivot_root for its exact capability requirement; man 2 prctl under PR_SET_NO_NEW_PRIVS for the irreversibility argument; and the moby default seccomp profile, which is the one containerd ships and the one to search when a syscall is mysteriously blocked.

    Living with a runtime that exits

    I3.5

    The runtime does not stay: foreground, detached, and who the parent becomes

    Why it matters

    This is the fact the whole module turns on, and it is worth being blunt about it: after runc run --detach returns, there is no runc process anywhere on the machine. Your container is running, and nothing is supervising it. Nobody is waiting to hear its exit code. Nobody will notice when it dies. If that sounds like a serious gap in a container platform — it is, and filling it is a job with a name. Understanding why runc refuses to fill it is what makes a shim make sense instead of looking like accidental complexity.

    The concept

    runc is a daemonless runtime. It is a command-line program that does a piece of work and exits, in the tradition of mkdir or mount — not a service that lives alongside what it made. In the track's analogy the contractor finishes the building and drives away; if you want somebody on site afterwards, that is a different person with a different job.

    There are two modes, and the difference between them is not cosmetic:

    • runc run <id> — foreground. runc creates the container, starts it, and then simply waits. It stays as the container's parent for the container's entire life, holds its stdio, and finally exits with the container's own exit code.
    • runc run --detach <id> — detached. runc creates the container, starts it, and returns immediately with exit code 0. Exit code 0 here means "I successfully started something", not "your program succeeded" — it cannot mean that, because your program has barely begun.

    When runc exits in detached mode, the container's init process is orphaned, and the kernel does what it always does with orphans: re-parents them to PID 1 — or, on a systemd machine, to the nearest ancestor that has marked itself a subreaper. You verified this mechanism in B2 with ordinary processes; here it happens to something you are supposed to be managing.

    Now list what is lost along with that parent, because this list is the specification for a shim:

    lost when runc exitswhy it matters
    The exit codeOnly a process's parent can reap it and read its status. systemd reaps the orphan and discards the number. "Did it exit 0 or 137?" becomes unanswerable.
    stdout and stderrThe container inherited runc's file descriptors. Once runc is gone, whatever those pointed at is where logs go — with nobody to rotate, tag or forward them.
    A signal pathThere is no process to send SIGTERM to that would forward it. You can still runc kill, but that requires the state directory and a runc binary, not a pipe to a supervisor.
    The moment of deathNobody is in wait(), so nothing learns that the container exited except by polling.

    Why not just keep runc running, then? Because a foreground runc has to stay alive for the container's whole life, and that ties the container's fate to a process that was never designed to be long-lived. Upgrade the runtime and every running container's supervisor is the old binary. A daemonless runtime is easier to reason about, easier to replace, and easier to make correct — and the supervision problem is handed to something whose only job is supervision.

    Here is the interesting part. Search the runtime specification for a requirement about the runtime process's lifetime and you will find nothing at all — no MUST, no SHOULD, not a mention. The spec defines create, start, kill, delete and state as operations with observable effects, and is completely silent on whether the program implementing them sticks around.

    This operation MUST run the user-specified program as specified by process.
    OCI Runtime Specification v1.3.0 — runtime.md, "Start" — the entire requirement

    So "the runtime exits" is runc's design decision, not a rule you can rely on across runtimes. It happens to be near-universal — crun, youki and runsc all do the same — but a conformant runtime that stayed resident would break nothing. When you hear "OCI runtimes are daemonless", that is a description of the field, not a clause in the standard.

    You can state what is running after runc run --detach returns, name the four things lost when runc exits, and explain why rc=0 from a detached run tells you nothing about your program.

    Gotchas
    • --detach's exit code is about the launch, not the workload. Scripts that treat runc run --detach && echo success as meaning the container is healthy are testing that the container was created. It may have exited a millisecond later.
    • Foreground runc holds your terminal's file descriptors. Close the terminal and the container's stdio disappears with it; a container writing to a closed pipe gets SIGPIPE. This is why every real launcher detaches and hands stdio to something durable.
    • The re-parent target is not always PID 1. Anything that called prctl(PR_SET_CHILD_SUBREAPER) claims orphans below it first — and that is exactly the trick a shim uses. If you see a detached container parented to something other than PID 1, you have found a subreaper.
    • Do not run runc from a shell you will close while testing, foreground or not. Use setsid as the labs do; otherwise your experiment ends when your SSH session does.

    This lesson is the direct answer to "why is there a containerd-shim-runc-v2 process for every pod on my node?" Each one exists to be the parent runc refused to be: it holds the container's stdio, sits in wait() to catch the exit code, survives containerd restarts so a containerd upgrade does not kill every pod, and reports the status upward. The Exit Code: 137 in kubectl describe pod travelled from the kernel, through a shim's wait(), to containerd, to the kubelet, to the API server. Remove the shim and that field is permanently empty. The stack is W1.20; the exit codes are W6.16. I7 takes the real shim apart and puts it beside the one you write in I3.13.

    Docs: man 2 prctl under PR_SET_CHILD_SUBREAPER, the mechanism that lets a shim claim orphans; man 2 wait on why only a parent can read an exit status — the constraint the entire shim design exists to satisfy.

    I3.6

    --pid-file, and the race a supervisor loses without it

    Why it matters

    If runc exits and leaves you a container, the very first thing you need is its PID — you cannot signal it, inspect it, or wait for it otherwise. There is an obvious way to get that number and a correct way, and they differ. The obvious one works every time you test it by hand and fails in production, which is the worst possible combination. This lesson makes it fail on demand so you never write it.

    The concept

    The naive approach is to ask afterwards: run the container, then call runc state <id> and read the pid field. The problem is the word afterwards. Between runc exiting and your query landing, time passes — and in that gap the container may already have finished. Once its init process is gone there is no PID to report, and the answer you wanted no longer exists.

    --pid-file <path> closes the gap by moving the reporting to the only moment when the answer is certainly available: runc writes the PID to that file before it exits, while it still has the container in hand. Your supervisor reads a file that was written by the process that knew.

    This is a specific instance of a general rule worth carrying: when you need a fact about a transient thing, arrange for the fact to be recorded by whoever held it, not queried by whoever wants it. The same reasoning is why pid files exist at all, why CLONE_PIDFD was added to the kernel, and why the shim you write in I3.13 takes the PID from a file rather than looking it up.

    Note that --pid-file does not solve everything. There remains a smaller race in the other direction: PIDs are recycled, so a PID you read from a file may later refer to a different process entirely. runc guards against that in its own state by recording the process's start time alongside its PID — I3.9 shows the field. A number alone is never a safe handle to a process.

    The spec makes the PID available, but only conditionally — and the condition is precisely the one this lesson is about:

    pid (int, REQUIRED when status is created or running on Linux, OPTIONAL on other platforms) is the ID of the container process.
    OCI Runtime Specification v1.3.0 — runtime.md, "State"

    Read the parenthesis as a warning rather than a detail. The PID is required to be present only while the container is created or running. For a stopped container the runtime owes you nothing, and runc takes that literally — you are about to watch it return 0. --pid-file is not a spec feature at all; it is runc's answer to a gap the spec leaves open by design.

    Lab
    1. Build a bundle whose container exits the instant it starts. This is not a contrived edge case — it is every short-lived job, every misconfigured command, and every crash on startup.

Everything between the kubelet and runc is built to avoid exactly the lookup you just watched fail. The shim takes the PID from a file at creation and holds a handle to the process for its whole life, so a container that exits in three milliseconds still has its status recorded by something that was already waiting. When you meet a very-short-lived container in Kubernetes and still get a clean Exit Code in W6.16's output, this is the machinery you are being handed for free.

    I3.7

    The console socket: passing a terminal through a hole in the wall

    Why it matters

    Ask for a terminal in a detached container and runc refuses outright. The error is precise and, until you know the mechanism, completely opaque: cannot allocate tty if runc will detach without setting console socket. Behind that sentence is one of the most elegant pieces of plumbing in the whole runtime — and it is a direct, practical application of the file-descriptor passing you did by hand in B9. This is where that lesson pays off.

    The concept

    Start with why there is a problem at all. A pseudo-terminal comes in two halves. The slave (/dev/pts/N) goes to the program that thinks it is talking to a terminal — the container's shell. The master is the other end, held by whoever is driving that terminal. For an interactive container the slave belongs inside and the master must belong outside.

    runc creates the pty. But in detached mode runc is about to exit — so it cannot be the one holding the master. It has to hand it to you. And a master pty is not something you can hand over by name: the file descriptor is the terminal, and re-opening /dev/pts/ptmx by path gets you a different pty, not the same one.

    The kernel does provide a way to move an open file descriptor between unrelated processes: SCM_RIGHTS over a unix-domain socket. It is a genuine hole in the process boundary — the receiving process ends up with a real descriptor to the same open file, with its own number. That is the mechanism B9 built by hand, and the console socket is precisely it: you create and listen on a unix socket, you pass its path to runc, and runc connects to it and sends the pty master through.

    you: listen()→runc: connect()→SCM_RIGHTS
    pty master fd    →you hold the terminal→runc exits

    The direction is worth dwelling on because it is the opposite of most people's guess. runc does not open a socket for you to connect to — you are the server and the runtime is the client. That inversion is deliberate: it means the terminal's owner is whoever was already listening, so there is no window in which the master exists but nobody responsible holds it.

    Along with the descriptor, runc sends a small ordinary payload: the pty's name. It is not needed to use the terminal — you already have the fd — but it makes debugging output legible.

    The specification asks for the terminal and says nothing about how it is delivered:

    terminal (bool, OPTIONAL) specifies whether a terminal is attached to the process, defaults to false.
    OCI Runtime Specification v1.3.0 — config.md, "Process"

    That is the whole field. The surrounding text goes on to say that on Linux a pseudoterminal pair is allocated and the slave is duplicated onto the process's standard streams — and then simply does not mention the master. Where the master goes is left to the runtime, because the spec has no concept of a caller to hand it to. --console-socket is runc's invention filling that silence, and containerd's shim uses it exactly as you are about to.

    Lab
    1. First, meet the error, so the rest of the lesson has something to fix. Make a bundle that asks for a terminal. 
      cd ~/i3

  config.json > /tmp/c.json && sudo cp /tmp/c.json config.json

      runc is telling you it has a master pty it cannot keep and cannot give away. Give it somewhere to send it.

    2. Write the receiver. The interesting part is four lines long — recvmsg with space for ancillary data, then pulling the descriptor out of the SCM_RIGHTS control message. 
      cat > ~/i3/getconsole.py <<'PY'
import array, os, socket, sys
path = sys.argv[1]
srv = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
srv.bind(path); srv.listen(1)
print("listening", flush=True)
conn, _ = srv.accept()
msg, anc, _, _ = conn.recvmsg(4096, socket.CMSG_SPACE(4))
fds = array.array("i")
for level, typ, data in anc:
    if typ == socket.SCM_RIGHTS:
        fds.frombytes(data[:len(data) - (len(data) % 4)])
master = fds[0]
print("payload   =", msg, flush=True)
print("master fd =", master, flush=True)
print("readlink  =", os.readlink(f"/proc/self/fd/{master}"), flush=True)
print("isatty    =", os.isatty(master), flush=True)
os.write(master, b"echo HELLO-FROM-THE-MASTER-FD\n")
import time; time.sleep(1)
print("read back =", os.read(master, 400), flush=True)
PY

      Read that last line carefully, because it contains the whole proof. Your write went into the master; the container's shell received it as keyboard input, echoed it back (the first copy), executed it (HELLO-FROM-THE-MASTER-FD), and printed a fresh prompt. The \r\n line endings are the terminal discipline doing its job — a pipe would give you bare \n. And \x1b[6n is the shell asking the terminal where the cursor is, which is a question a program only bothers to ask something it believes is a real terminal.

    4. Confirm the descriptor genuinely crossed a process boundary, rather than being inherited. 
      sudo pgrep -af 'runc.*t1' || echo '(no runc process for t1)'

      (no runc process for t1)
t1   34876   running   /home/ubuntu/i3/tty   2026-07-27T14:24:20Z

      Note this only works if your receiver is still holding the descriptor — the container's shell dies with its terminal, so a receiver that exits takes the container with it. runc, meanwhile, is gone and the terminal still works. The fd in your Python process is not a copy of anything runc still holds — it is the master, now owned by an unrelated program that was never runc's child.

    Verify

    You can explain who listens and who connects, name what travels in the ancillary data versus the ordinary payload, and point at the two pieces of evidence in the read-back that prove a real terminal rather than a pipe.

    Gotchas
    • The listener must be running first. runc connects during create and fails immediately if nothing is listening. Starting them in the wrong order gives a connection-refused error that reads like a permissions problem.
    • recvmsg without CMSG_SPACE silently drops the descriptor. If you allocate no ancillary buffer, the kernel discards the fd and closes it — you get the payload, no error, and no terminal. This is the single most common bug when writing one of these by hand.
    • The socket path is not cleaned up. A leftover socket file makes the next bind() fail with "address already in use"; rm -f it first, as the lab does.
    • socat is often suggested for this and cannot do it. socat relays bytes; it has no way to accept an SCM_RIGHTS descriptor and adopt it. You need something that calls recvmsg — a few lines of Python, or runc's own recvtty helper.
    • Terminal mode is not free. With a pty, stdout and stderr are merged onto one stream and line endings become \r\n. Log collectors that assume separated streams get confused, which is why non-interactive containers should leave terminal: false.

    This is the mechanism behind kubectl exec -it and the tty: true field in a pod spec. The chain is longer — your terminal, the API server, the kubelet's streaming endpoint, the CRI runtime, the shim — but the last hop is exactly what you just built: a console socket, and a pty master passed over it by SCM_RIGHTS. It also explains a puzzle people hit constantly: a pod with tty: true whose logs arrive with stdout and stderr interleaved and \r characters everywhere. That is not Kubernetes mangling the output; that is a terminal doing what terminals do, three layers down. kubectl exec's path through the stack is W1.20.

    Docs: man 7 unix under SCM_RIGHTS — the authoritative description of descriptor passing, including the truncation behaviour behind the CMSG_SPACE gotcha; man 4 pts and man 3 posix_openpt for the master/slave split; runc's recvtty, the reference receiver in Go.

    I3.8

    The rest of the surface: exec, ps, events, update

    Why it matters

    Four commands remain, and each one is the ancestor of something you already use in Kubernetes. runc exec is kubectl exec. runc events --stats is what metrics-server ultimately reads. runc update is the machinery behind in-place pod resizing, which went GA in v1.35. Meeting them at this level means that when the Kubernetes version misbehaves you know what it was asking for underneath.

    The concept

    runc exec starts a second process inside an existing container. Mechanically it is the same binary doing the same re-exec you traced in I3.1, with one environment variable changed: _LIBCONTAINER_INITTYPE=setns instead of standard. Where the standard path calls unshare to make namespaces, the setns path calls setns to join existing ones. One program, two directions.

    The natural question is which namespaces it joins, and the answer for runc is refreshingly simple: all of them. You will verify inode-by-inode below that an exec'd process is in the container's mount, PID, network, UTS, IPC and cgroup namespaces, and in its cgroup. What it does not inherit is the container's process configuration from config.json — the exec'd process gets its own capabilities, its own environment and its own working directory, defaulting to values that are not necessarily the ones your container was started with. That mismatch is the source of the most confusing exec bugs: a shell that can do things the application cannot, or the reverse.

    runc ps lists the processes in the container's cgroup. Note the implementation detail, because it explains the output: it reads the cgroup's cgroup.procs and then shells out to the host's ps with those PIDs. So the numbers you see are host PIDs, not the container's own view.

    runc events --stats takes a one-shot resource snapshot and prints it as JSON — CPU time, memory, pids, and block I/O, read straight out of the cgroup files you drove by hand in B7. Without --stats the same command streams events instead, blocking until something happens.

    runc update changes resource limits on a running container. This is the one that surprises people: cgroup limits are not fixed at creation, because a cgroup is a live kernel object and writing a new number into cpu.max takes effect immediately. There is an important catch, though, and the lab makes you look at it — update changes the kernel's state and nothing else. Not the bundle, not runc's own saved state.

    Of these four, the specification defines exactly none — and this time the evidence is an absence rather than a sentence. Here is every operation heading in the spec's "Operations" section, in full:

    Query State · Create · Start · Kill · Delete
    OCI Runtime Specification v1.3.0 — runtime.md, "Operations" — the complete list

    That is the whole standard surface. exec, ps, events, update, pause and resume appear nowhere in the document. Five operations are standardised; everything in this lesson is runc going beyond the contract. It matters practically: a CRI implementation cannot assume any runtime offers update, which is why in-place pod resize took so long to stabilise and why it is negotiated through CRI's own UpdateContainerResources call rather than assumed.

    Gotchas
    • runc update is invisible to everything but the kernel. It is not in the bundle and not in state.json, so it does not survive a recreate and leaves no audit trail. Treat it as a live intervention, never as configuration.
    • runc exec does not inherit the container's process block. Capabilities, environment and working directory come from the exec's own arguments and defaults. A shell that behaves differently from your application is usually this, not a broken image.
    • An exec'd process shares the container's memory limit. A debugging session that loads a large file can OOM-kill the workload you were debugging. This is a real way to turn an investigation into an outage.
    • events without --stats blocks. It streams OOM notifications and waits for them; typed casually into a terminal it looks like a hang.
    • The cgroup path is not stable across environments. /user.slice/user-1000.slice/s5 is what you get from a user's sudo; read it from state.json's cgroup_paths rather than assuming.

    Every one of these has a Kubernetes descendant. runc exec's namespace-joining is why kubectl exec sees the pod's network and filesystem — and its separate process config is why kubectl exec sometimes has capabilities the application does not. events --stats is the bottom of the metrics pipeline that ends in kubectl top. And update is the primitive behind in-place pod resize, GA in v1.35: changing a running pod's resources reaches the node as CRI's UpdateContainerResources, which lands as exactly the cgroup write you just made. The gotcha above has a Kubernetes twin worth remembering — because the change is only in the kernel, a container restart returns it to the value in the pod spec, which is the correct behaviour and still catches people out. Requests and limits are W3.16; the CRI call itself is I8's material.

    Docs: runc exec --help and runc update --help for the flags this lesson skips (notably --resources -, which reads a whole JSON resources block from stdin); the kernel's cgroup v2 documentation for cpu.max's two-number format.

    State on disk

    I3.9

    Where a daemonless runtime keeps its memory

    Why it matters

    Here is a puzzle that follows directly from I3.5. If runc exits after every command, how does the next runc command know anything? You type runc kill mycontainer and a brand-new process, with no memory of anything, has to work out what mycontainer is. There is no daemon holding that knowledge. So it must be on disk — and finding out exactly what is written there tells you what a container really consists of when nobody is looking at it.

    The concept

    Every runc invocation is amnesiac, so runc keeps its entire memory in one directory: /run/runc/<id>/, containing a single file, state.json. That is the whole database. runc list is a directory listing; runc state is a file read; runc kill reads the PID out of the file and calls kill(2). There is no other bookkeeping anywhere.

    /run is a tmpfs — memory, not disk — which means the whole thing evaporates on reboot. That is intentional and correct: every container it described died with the reboot too, so records of them would be lies.

    The file has eight top-level keys, and three of them repay careful reading:

    keywhat it is, and why it is there
    init_process_pidThe container's PID on the host. The obvious one.
    init_process_startThe start time of that process, in clock ticks since boot — field 22 of /proc/<pid>/stat. This is the guard against PID reuse, and it is the most interesting field in the file.
    namespace_pathsPaths of the form /proc/<pid>/ns/net — the namespaces named by where they can be found, not by identity.
    cgroup_pathsAbsolute paths under /sys/fs/cgroup, so delete knows what to remove and update knows what to write.
    configThe configuration — but not your config.json. It is libcontainer's internal translation of it, with different key names.

    The init_process_start field deserves the attention because it solves a real problem elegantly. PIDs are recycled. If runc stored only the number, then a container that died could have its PID reassigned to your database, and runc kill mycontainer would kill your database. Storing the start time alongside makes the pair unforgeable: no other process can have both that PID and that exact boot-relative start tick. Any tool that holds a PID across time and does not do this has the bug.

    And now the question the checkpoint asks: when nothing is running, what is a container? Look at what is in the file and what is not. namespace_paths point through the process — kill it and every one of those paths 404s. The cgroup is a real kernel object but an empty one. The rootfs mounts live in a mount namespace that ceases to exist with its last member. So the honest answer is: a container is a name, a record, and a process — and when the process is gone, what remains is the name and the record. That is precisely why the lifecycle has a stopped state that still requires delete, and precisely why the next lesson's fault exists.

    The spec requires the information to be obtainable and says nothing about storing it:

    This operation MUST generate an error if it is not provided the ID of a container. Attempting to query a container that does not exist MUST generate an error. This operation MUST return the state of a container as specified in the State section.
    OCI Runtime Specification v1.3.0 — runtime.md, "Query State"

    A daemon-based runtime could answer that query from memory and write nothing to disk at all. runc must write, because runc does not persist — the state directory is the direct consequence of the design choice in I3.5. The two facts are the same fact seen from different ends, and noticing that is most of what it means to understand a daemonless runtime.

    Gotchas
    • /run/runc is only root's copy.     • Do not edit state.json. It is an internal serialisation with no compatibility promise, and runc reads it expecting itself to have written it. The supported way to change a running container is runc update.
    • The state directory is tmpfs. Nothing here survives a reboot, which is correct — but it also means a filesystem-level backup of a node captures no container state at all.
    • cgroup_paths has an empty-string key. That "" is a cgroup v1 leftover, where the map was keyed by controller. On v2 there is one unified path and the key means nothing. Do not write a parser that expects a controller name there.

    /run/runc is the bottom of a stack of exactly this pattern. containerd keeps its own metadata in a bolt database under /var/lib/containerd; the kubelet keeps a pod checkpoint under /var/lib/kubelet/pods; etcd keeps the cluster's copy. Each layer records what the layer below cannot be asked. When those records disagree — a pod the API server believes is running, on a node where runc list shows nothing — you are looking at a reconciliation problem, and knowing which layer stores what is how you decide which one is lying. The reconciliation model is W0.6; node-level state is W6.4.

    I3.10

    container with given ID already exists, on purpose

    Why it matters

    This error is a rite of passage, and the reason it is worth manufacturing deliberately is that the obvious fix is the wrong one. Faced with "already exists" when nothing exists, almost everyone reaches for rm -rf on the state directory. It works — the next create succeeds, the incident closes — and it quietly leaves something behind. Doing it both ways once, on purpose, is how you learn to prefer the correct one under pressure.

    The concept

    The error is a direct consequence of I3.9. A container's identity lives in /run/runc/<id>/, and creating a container means creating that directory. If it already exists, runc refuses — because the alternative is silently adopting or clobbering something that might be a live container.

    The interesting case is when the directory outlives the container. That happens whenever a container's process dies without anybody calling delete: a SIGKILL, an OOM kill, a supervisor that crashed between killing and cleaning up, or a node that lost power mid-operation. In every case the record says a container exists and the reality says otherwise, and runc believes the record.

    Two ways to resolve it, and they are not equivalent:

    • runc delete --force <id> — the correct fix. runc kills anything still alive, removes the cgroup, unmounts what needs unmounting, and then removes the state directory. It knows what it created because state.json told it.
    • rm -rf /run/runc/<id> — the tempting fix. It removes the record of what to clean up without doing any cleaning. The next create succeeds, so it looks like it worked. But the cgroup directory is still there, with no record anywhere that it exists or who made it.

    Reach for the destructive one habitually and you get a slow leak: cgroup directories accumulating in /sys/fs/cgroup, one per incident, each one a live kernel object holding memory. It is a small leak per container and a real one on a node that has been restarting things for months.

    Both halves of this behaviour are required:

    If the ID provided is not unique across all containers within the scope of the runtime, or is not valid in any other way, the implementation MUST generate an error and a new container MUST NOT be created. […] Deleting a container MUST delete the resources that were created during the create step. Note that resources associated with the container, but not created by this container, MUST NOT be deleted. Once a container is deleted its ID MAY be used by a subsequent container.
    OCI Runtime Specification v1.3.0 — runtime.md, "Create" and "Delete"

    The refusal is a MUST, so the error is conformant behaviour rather than runc being fussy. And read the delete clause as a job description: delete the resources that were created during the create step. That is exactly the job rm -rf does not do — it destroys the only record of what those resources were.

    Gotchas
    • The bad fix succeeds, which is why it spreads. Nothing about the outcome tells you it was wrong; you have to know to check /sys/fs/cgroup. Treat "the workaround worked" as the weakest possible evidence that it was correct.

The chain is the same one you just built by hand — something killed a container without a clean delete, the runtime's state directory survived, and the next attempt to create by the same ID is refused. The kubelet retries forever, because retrying is not the fix. The real fix is at the layer that owns the stale record, which is why the operational advice is to clean up through crictl rm rather than by deleting directories — crictl is the tool that knows what to remove, in exactly the way runc delete does and rm -rf does not. The pod-lifecycle failure catalogue is W6.16; crictl itself is I8.

    Beyond the basics

    I3.11

    Hooks in anger: networking a container from outside it

    Why it matters

    In I2.13 you worked out, from evidence, where each hook runs. This lesson spends that knowledge: you are going to make a hook do the single most important job hooks are actually used for. When you are finished you will have hand-built the invocation pattern that CNI standardises — and I9 will feel like meeting something you already designed.

    The concept

    Recall the problem the runtime cannot solve alone. A container's network namespace is empty except for a down lo. Something has to put an interface in it, address it, and route it. But that something cannot be the container — the container has no privilege and, by the time it runs, no host tooling. And it cannot be the runtime, because the runtime has no opinion about your network. So it must be a third party, running at a very specific moment: after the namespace exists, and before the workload starts.

    That moment is the createRuntime hook, and I2 already established what it looks like from the inside: it runs on the host, in the host's namespaces, with the host's filesystem and the runtime's full privileges. Which is exactly what you need — host tooling in hand, and a container namespace to reach into.

    The handoff is deliberately minimal. The runtime writes the container's state JSON on the hook's stdin — the same document runc state prints — and the hook takes one field from it: the PID. A PID is a complete address for a namespace, because /proc/<pid>/ns/net is a path you can hand to nsenter or ip link set … netns. That is the entire interface: here is a process; its namespaces are yours to configure.

    runc: namespaces made→state JSON
    on stdin    →hook: veth + addr + route→runc: pivot_root, exec

    Everything the hook does, you already did by hand in B9 — create a veth pair, put one end on a bridge, move the other into a namespace, address it, add a default route. Nothing new is happening at the kernel level. What is new is who decides when: the runtime, at a guaranteed point in the lifecycle, from a declaration inside the bundle rather than from a script somebody has to remember to run.

    That is the whole idea CNI generalises. A CNI plugin is this hook with the interface written down: instead of the runtime's state JSON on stdin it gets a CNI config on stdin plus CNI_* environment variables, and instead of exiting quietly it prints a result. Same moment, same privilege, same namespace-by-PID handle — standardised so that any runtime can call any plugin.

    The spec defines the stdin contract exactly:

    The state of the container MUST be passed to hooks over stdin so that they may do work appropriate to the current state of the container.
    OCI Runtime Specification v1.3.0 — config.md, "POSIX-platform Hooks"

    Note what is not promised. There is no schema for what a hook may do, no way to return data to the runtime, and no notion of a plugin. A hook is an executable with a JSON document on stdin and an exit code — and that thinness is why CNI had to exist. If you want a plugin to tell the runtime which IP it assigned, hooks give you nowhere to put the answer.

    I3.12

    Checkpoint and restore, without needing it

    Why it matters

    This is the one lesson in the module you are unlikely to use, and it is here for two reasons. First, it appears in runc --help, so you should know what it is rather than wondering. Second, and more usefully, understanding why it is rarely used teaches you something durable about what a process actually consists of — because the list of things that make a process hard to freeze is the list of things that make it a process at all.

    The concept

    Checkpoint/restore means freezing a running process tree, writing everything about it to disk, and later reconstructing it so it continues from that exact instruction. Not restarting it — continuing it. Open files still open, memory contents intact, the program unaware anything happened.

    runc does not implement this itself. It shells out to CRIU ("Checkpoint/Restore In Userspace"), a separate project, and runc checkpoint is a thin wrapper. CRIU walks /proc for everything it can learn about the processes, uses specialised kernel interfaces for the things it cannot, and writes a directory of image files.

    What has to be captured is more than you would guess: every memory page of every process, the register state of every thread, all open file descriptors and their offsets, the process tree's parent/child structure, pending signals, timers, and network sockets with their in-kernel buffers.

    Now the important part — the reason it is rare. You do not have to take anybody's word for it, because runc checkpoint --help confesses. Read the flag list as a list of things that do not work by default:

    flagwhat its existence admits
    --tcp-establishedOpen TCP connections are not handled unless you ask. The peer at the other end never agreed to be paused, and its kernel is still counting timeouts.
    --ext-unix-skUnix sockets to anything outside the container are a problem, because the other end is not part of the checkpoint.
    --file-locksFile locks, "for safety" — a lock is a relationship with the kernel that another process may be waiting on.
    --link-remapDeleted-but-still-open files need reconstructing, because the path is gone but the inode is in use.
    --shell-jobA process attached to a terminal needs the terminal back — and it may not exist any more.

    The pattern is one idea: a process is not self-contained. It is a bundle of relationships with the kernel, the filesystem, and other machines — and a checkpoint can only capture the process's half of each. Everything on that list is a relationship whose other end did not get checkpointed. That is why checkpoint/restore works beautifully for a compute job with a big array in memory, and poorly for anything holding a connection.

    Requirements, briefly: CRIU installed on the node (it is not in Ubuntu 24.04's repositories, as the lab shows), a kernel with the interfaces CRIU needs, and CAP_SYS_ADMIN — plus, for anything containerised, matching kernel and CPU features on the restore host.

    Neither operation is in the specification. The Operations section, in full, is Query State, Create, Start, Kill, Delete — checkpoint and restore appear nowhere, in the same way exec and update did not in I3.8.

    This is the practical consequence of that gap: because the OCI does not define checkpointing, Kubernetes could not simply expose "the runtime's checkpoint operation". It had to define its own kubelet endpoint, and its behaviour depends on which runtime is underneath. A feature built on an unstandardised operation inherits the runtime's variability — which is a large part of why the Kubernetes feature has stayed in beta for several releases.

    Lab
    1. Ask runc to checkpoint the container from I3.11 and read the error carefully.

    3. Read the confession. This is the lesson's real lab: the flag list, understood as a list of limitations. 
      sudo runc checkpoint --help | grep -E '^   --'
         --image-path value       path for saving criu image files

    Gotchas
    • Checkpoint images contain all of the container's memory. Every secret, token and key the process had loaded is in that tar, in plaintext, on disk. Treat a checkpoint as the most sensitive artefact your cluster can produce — this is the main security caveat in Kubernetes' own documentation for the feature.
    • Restore is not portable. A different kernel version, or a CPU lacking an instruction set the checkpointed process was using, will fail the restore or corrupt it. Checkpoints are not backups.
    • runc checkpoint stops the container by default. Use --leave-running if you meant to take a snapshot rather than move it, or you will have paused production to look at it.
    • A missing CRIU looks like a runc bug. The error names an executable, not a feature, so it reads as a broken installation. It is neither — it is a component nobody installed.

    The Kubernetes feature built on this is forensic container checkpointing, via the kubelet's checkpoint API: POST /checkpoint/{namespace}/{pod}/{container}, which writes a tar archive to /var/lib/kubelet/checkpoints/. It went alpha in v1.25, reached beta and enabled-by-default in v1.30, and is still beta — the long stay is itself the lesson about building on an unstandardised runtime operation. Note the framing: forensic. The archive is meant to be moved to a sandbox and analysed, so a compromised container can be examined without leaving it running in production. Live migration of pods is not what the feature is for, and Kubernetes does not offer it — pods are designed to be replaceable, which is why the reconciliation model (W0.6) never needs to move one.

    Docs: the kubelet checkpoint API reference for the endpoint, the output path and the security caveat; CRIU's own "What cannot be checkpointed", which is the definitive version of the flag table above.

    I3.13

    Mini project — microshim.py

    Why it matters

    I3.5 left you with a problem: runc exits, your container is orphaned, and its exit code is thrown away by PID 1. This project fixes that in about sixty lines. When you are done you will have written a shim — a real one, doing the real job — and in I7 you will put it beside containerd-shim-runc-v2 and ask what is missing. That comparison is far more useful when the thing on your side of it is yours.

    The concept

    The shim's job is to be the parent runc refuses to be. Four responsibilities:

    1. Claim the container as a child, so its exit status comes to you.
    2. Create and start it, taking the PID from a pid file rather than a query (I3.6).
    3. Forward termination signals to the container's PID 1, so SIGTERM to the shim means "shut the container down".
    4. Wait, report the exit code, and clean up with runc delete — cgroup included (I3.10).

    The first one is the interesting one, because there is a trap in it. runc creates the container as its child, then exits — so the container is never your child at all, and os.wait() would return immediately with "no children". You cannot wait for a process that is not yours.

    The kernel's answer is prctl(PR_SET_CHILD_SUBREAPER, 1). A process that sets this flag becomes the collection point for orphans in its subtree: when an intermediate process dies, its children re-parent to the nearest marked ancestor instead of to PID 1. So the shim sets the flag, runs runc, runc exits — and the container lands on the shim rather than on init. This is exactly what the real shim does, and it is the single most important line in the file.

    shim: subreaper=1→runc create+start→runc exits→container re-parents
    to the shim    →shim waits

    One design decision worth stating: the shim uses create and start as two calls rather than run --detach. It costs nothing here, and it leaves the window open where a CNI plugin would go — which is precisely why the real shim does the same.

    Lab
    1. Write it. The comments mark the four responsibilities. 
      cat > ~/i3/microshim.py <<'PY'
#!/usr/bin/env python3
"""microshim.py — be the parent runc refuses to be.

Usage: microshim.py <container-id> <bundle-dir>
"""
import ctypes, os, signal, subprocess, sys

PR_SET_CHILD_SUBREAPER = 36
cid, bundle = sys.argv[1], sys.argv[2]
pidfile = f"/run/{cid}.pid"

# 1. Claim orphans. Without this the container re-parents to PID 1 when runc
#    exits, and PID 1 reaps it -- taking the exit code with it.
libc = ctypes.CDLL("libc.so.6", use_errno=True)
if libc.prctl(PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0) != 0:
    raise OSError(ctypes.get_errno(), "PR_SET_CHILD_SUBREAPER failed")

# 2. Create and start the container detached. runc exits; we inherit it.
subprocess.run(["runc", "create", "--pid-file", pidfile, "--bundle", bundle, cid],
               check=True)
pid = int(open(pidfile).read().strip())
print(f"[shim] container init pid={pid}", flush=True)
subprocess.run(["runc", "start", cid], check=True)

# 3. Forward termination signals to the container's PID 1.
def forward(signum, _frame):
    print(f"[shim] forwarding {signal.Signals(signum).name} to {pid}", flush=True)
    try:
        os.kill(pid, signum)
    except ProcessLookupError:
        pass
signal.signal(signal.SIGTERM, forward)
signal.signal(signal.SIGINT, forward)

# 4. Wait for it. As subreaper we get the real wait status, not a guess.
status = 0
while True:
    try:
        reaped, status = os.wait()
    except ChildProcessError:
        break
    except InterruptedError:
        continue
    if reaped == pid:
        break

if os.WIFSIGNALED(status):
    sig = os.WTERMSIG(status)
    code = 128 + sig
    print(f"[shim] container killed by {signal.Signals(sig).name}, exit={code}", flush=True)
else:
    code = os.WEXITSTATUS(status)
    print(f"[shim] container exited, exit={code}", flush=True)

# 5. Clean up the way runc delete does -- cgroup included.
subprocess.run(["runc", "delete", cid], check=False)
os.unlink(pidfile)
sys.exit(code)

    Gotchas
    • Without the prctl call the shim silently does nothing useful. os.wait() raises ChildProcessError immediately, the loop breaks, and the shim exits reporting 0 while the container runs on happily. Comment out that line once and watch it happen — it is a much better lesson than reading about it.
    • A subreaper collects all orphans below it, not just yours. The wait loop must check which PID it reaped, which is what if reaped == pid is for. Drop the check and the shim exits when any unrelated grandchild dies.
    • SIGKILL cannot be forwarded. signal.signal(signal.SIGKILL, …) raises, and a SIGKILLed shim runs no cleanup at all. That is I3.14's second fault, and it is why real shims are designed to be restartable rather than assumed reliable.
    • Signals to PID 1 of a namespace need a handler. The container traps TERM deliberately — without the trap, the kernel drops the signal and the container ignores your shutdown entirely. That is I2's lesson and the most common cause of a pod burning its full termination grace period.
    • This shim holds no stdio. The container inherited the shim's, so its output lands wherever the shim's went. A real shim owns a pty or a fifo pair and serves logs on request — one of several gaps I7 catalogues.

    What you wrote is a recognisable subset of containerd-shim-runc-v2, the process you will find one of per pod on every node. The real one adds: a ttRPC API so containerd can drive it after a restart, log handling, an exit-event stream, the ability to host several containers in one pod sandbox, and — crucially — it survives containerd restarting, which is why upgrading containerd does not kill running pods. That last property is the reason the shim is a separate process rather than a goroutine inside containerd, and it is worth carrying into I7. The stack is W1.20; graceful termination, which is your signal-forwarding path seen from Kubernetes, is W3.5.

    I3.14

    Debugging drill — two faults

    Why it matters

    Both faults below are the runtime-level ancestors of Kubernetes symptoms you will meet, and both are the kind that produce no error message. Nothing crashes, nothing logs, and the system reports success. Learning to recognise them here — where there are four moving parts instead of forty — is what makes them recognisable later.

    Fault 1 — "it starts and immediately exits 0"

    Plant it. A bundle whose args point at a shell, with no terminal and no stdin.

    cd ~/i3
sudo cp -a box drill1
sudo jq '.process.args = ["/bin/sh"] | .process.terminal = false' \
  drill1/config.json > /tmp/c.json && sudo cp /tmp/c.json drill1/config.json

    rc=0  pid-file=37049
d1   0   stopped   /home/ubuntu/i3/drill1   2026-07-27T14:36:33Z   root

    The symptom. Everything reports success. runc exits 0, the pid file has a real PID, and the container is already stopped. There is no error anywhere — because nothing went wrong.

    Run it under your shim and you get the one extra fact that solves it:

    sudo runc delete --force d1; sudo rm -f /run/d1.pid
sudo python3 ~/i3/microshim.py d1 ~/i3/drill1 < /dev/null
    [shim] container init pid=37189
[shim] container exited, exit=0
    Hint 1 — what is not wrong

    Exit code 0 means the program ran and chose to finish. This is not a crash, not a missing binary (that gives executable file not found), not a permissions problem, and not the runtime. Something inside completed its work in microseconds and had nothing further to do. Ask what /bin/sh does when it is started with nothing to run.

    Hint 2 — what is on stdin

    An interactive shell reads commands from stdin. With terminal: false there is no pty, and the lab redirected stdin from /dev/null, so the very first read returns end-of-file. A shell that reaches EOF exits — successfully, because reaching the end of its input is a normal way to finish. Confirm it outside any container: /bin/sh < /dev/null; echo $?.

    Solution

    The container is doing exactly what it was told. args: ["/bin/sh"] asks for an interactive shell; it gets no terminal and an empty stdin, reads EOF, and exits 0.

    Two fixes, and the right one depends on intent:

    # If you meant it to do work: give it work.
sudo jq '.process.args = ["/bin/sh","-c","echo I-AM-ALIVE; sleep 2"]' \
  drill1/config.json > /tmp/c.json && sudo cp /tmp/c.json drill1/config.json
sudo runc delete --force d1; sudo rm -f /run/d1.pid
sudo python3 ~/i3/microshim.py d1 ~/i3/drill1 < /dev/null
    [shim] container init pid=37231
I-AM-ALIVE
[shim] container exited, exit=0

    If you meant it to be interactive, the fix is a terminal — process.terminal: true and a console socket (I3.7). Either way, the diagnosis is the same: exit 0 with no output means the process finished normally, so ask what "finished" meant to it.

    This is CrashLoopBackOff on a container that never crashed. A pod whose command is a shell, or an image whose ENTRYPOINT expects arguments it did not get, exits 0 immediately; the default restartPolicy: Always restarts it; it exits again; and the backoff timer climbs. The tell is Last State: Terminated, Exit Code: 0 — a crash loop with a successful exit code in it is always this fault, never a crash. See W6.16.

    Fault 2 — a shim that was SIGKILLed

    Plant it. Start a container under the shim, then kill the shim in the one way it cannot defend against.

    sudo runc delete --force d2 2>/dev/null; sudo rm -f /run/d2.pid
sudo setsid python3 ~/i3/microshim.py d2 ~/i3/shimbox > /tmp/d2.out 2>&1 &
sleep 2

    [shim] container init pid=37332
container up                          # note: no exit line
d2   37332   running   /home/ubuntu/i3/shimbox   2026-07-27T14:38:31Z   root

    The symptom. Now try to start it again by the same ID — which is what any supervisor would do.

    sudo runc create --bundle ~/i3/shimbox d2
    level=error msg="runc create failed: container with given ID already exists"
    Hint 1 — is it stale, or is it real?

    Do not assume "already exists" means a leftover record. Check first: sudo runc state d2 | jq -c '{status,pid}'. If the status is running and that PID exists, the container is genuinely alive and the message is telling the truth. Something else died.

    Hint 2 — who is the orphan's parent?

    sudo ps -o pid,ppid,comm -p <pid>. The parent is PID 1. The shim set itself as a subreaper, but a subreaper that dies stops collecting — so the container re-parented a second time, to init. Nothing is supervising it, and nothing will ever report its exit code.

    Solution

    SIGKILL cannot be caught, so the shim never reached step 5 and never ran runc delete. The container outlived its supervisor. This is different from I3.10's fault, where the container died and the record survived — here the record and the container are both real, and the supervisor is the thing that is gone. That distinction decides the repair:

    sudo runc state d2 | jq -c '{status,pid}'     # is it actually alive?
sudo ps -o pid,ppid,comm -p 37332              # who parents it now?
sudo runc delete d2                            # will refuse — and should
sudo runc delete --force d2                    # the correct repair
    {"status":"running","pid":37332}
    PID    PPID COMMAND
  37332       1 sh
level=error msg="cannot delete container d2 that is not stopped: running"
# --force: succeeds, kills the orphan, removes the cgroup

    Note that plain runc delete refusing is correct behaviour and useful information — it is the runtime telling you your diagnosis was wrong. Reaching straight for --force would have killed a running workload without ever learning that it was running.

    Verify the repair reached everything:

    sudo runc list | grep d2 || echo '(gone)'
