    I5 — Registries

    A registry is an HTTP server with two namespaces — blobs by digest, manifests by tag or digest — and once you have pulled an image using nothing but curl, ImagePullBackOff stops being a Kubernetes mystery and becomes a status code you can read.

    I4 gave you an image sitting in a directory. This module is about the four hours of its life before that — how it travelled. The answer is smaller than you expect: a registry is an HTTP server with two kinds of URL, and by the end of the second group you will have pulled a complete image using curl, jq and sha256sum, with no container tooling anywhere in the path.

    Checkpoints15 Hours~6 PrerequisitesI4
    • Read the two endpoint families off any registry URL, and say which one is mutable and why that asymmetry is the whole design.
    • Complete the token dance by hand and pull a full image — index, manifest, config, every layer — with curl alone, verifying each digest as it lands.
    • Push blobs monolithically and in chunks, explain why the manifest goes last, and make a 30 MB "upload" take no bytes at all.
    • Point containerd at a mirror with hosts.toml, and diagnose the four common pull failures from their status codes rather than from Kubernetes' summary of them.

    I4 — you must already be able to walk an image graph and verify a digest. Authored against OCI distribution-spec v1.1.1. This module needs working internet.

    Which machine. Every capture below is from the sandbox VM (Ubuntu 24.04, kernel 6.8.0) running curl 8.5.0, jq 1.7, skopeo 1.13.3, containerd 2.3.3, nerdctl 2.3.5 and registry:2, against Docker Hub and against a local registry on localhost:5000.     The API

    I5.1

    The handshake: one URL that answers "are you a registry?"

    Why it matters

    Before you can debug a registry you have to be sure you are talking to one. That sounds trivial until the day a pull fails against an internal host and the question "is the registry broken, or is something in front of it?" costs an hour. There is exactly one request that answers it, and the answer arrives in the status code alone.

    The concept

    Every registry that implements the distribution spec serves its entire API under the path prefix /v2/, and the bare endpoint /v2/ is the version handshake. The version lives in the path rather than in a header, which is a small decision with a pleasant consequence: a client discovers whether a server speaks the protocol with one request and nothing to negotiate.

    The part that surprises people is what a healthy Docker Hub returns: 401 Unauthorized, not 200. That is not a failure. The endpoint exists, the server answered, and the WWW-Authenticate header it sent back is the server telling you exactly where to go and get a token. On this API, 401 is frequently the first line of a successful conversation — internalise that now and half of the confusion in this module never arises.

    The genuinely bad answer is 404. A 404 at /v2/ means whatever answered does not know it is supposed to be a registry — usually a reverse proxy, ingress rule or load balancer that is routing your request somewhere else entirely. Distinguishing "needs auth" from "is not a registry" is the entire job of this one request, and it takes a second.

    The spec defines this endpoint for exactly one purpose, and is careful to say that authentication is somebody else's business.

    To check whether or not the registry implements this specification, perform a GET request to the following endpoint: /v2/.

    If the response is 200 OK, then the registry implements this specification.

    This endpoint MAY be used for authentication/authorization purposes, but this is out of the purview of this specification.
    OCI distribution-spec v1.1.1 — spec.md § Determining Support
    Lab
    1. Ask Docker Hub the question. Read the status line first and the headers second — everything you need for the next three checkpoints is in this one response. 
      curl -si https://registry-1.docker.io/v2/ | head -9

      curl -si http://localhost:5000/v2/ | head -6

{}
    3. And the answer that means "you are not talking to a registry". Note the give-away: content-type: text/html and a server header that belongs to something else. 
      curl -si https://example.com/v2/ | head -4
      HTTP/2 404
date: Tue, 28 Jul 2026 11:31:58 GMT
content-type: text/html
server: cloudflare
    Verify

    Given a hostname, you can say in one request whether it is a registry, and if so whether it wants a token. You can also explain to a colleague why the 401 they screenshotted is not the bug they think it is.

    Gotchas
    • The trailing slash is required. /v2 and /v2/ are different paths, and some registries answer only the second. When a handshake mysteriously 404s, check that first.
    • A JSON error body means the registry answered; a plain-text one means something else did. The {"errors":[...]} envelope is part of the spec, so its presence tells you the request reached a registry handler. A bare 404 page not found in plain text — you will see one in I5.2 — means the request was rejected before any registry code ran.
    • docker-distribution-api-version is not a reliable signal. The spec calls the Docker-era headers OPTIONAL and says clients SHOULD NOT depend on them. Read the status code.

    When a node reports ErrImagePull against an internal registry (W6.17), this is the first command to run from that node — not from your laptop. It separates "the registry is unreachable or misrouted" from "the credentials in the imagePullSecret are wrong", and those two have completely different fixes. Kubernetes never shows you this layer; you have to go and look.

    Docs: the exam will not ask you to curl a registry, but it will ask you to fix a pod that cannot pull. Search the Kubernetes docs for "images" and read the private-registry section; the spec side is spec.md § Determining Support.

    I5.2

    Two endpoint families, one of them mutable

    Why it matters

    The distribution API is small enough to hold in your head — but only once you notice that every URL in it belongs to one of two families, and that the difference between them explains why registry mirrors are easy, why caching is safe, and where every interesting attack is aimed.

    The concept

    There are two:

    • /v2/<name>/blobs/<digest> — content, addressed by its own hash. The reference here must be a digest. Because of I4.1, this URL is immutable by construction: the name is computed from the bytes, so the same URL can never legitimately return different content.
    • /v2/<name>/manifests/<reference> — metadata, where the reference may be a digest or a tag. And that is the whole difference. A tag is a name somebody assigned, so it can be moved.

    So the entire mutable surface of a registry is one mapping: tag → digest. Everything else is content-addressed and therefore frozen.

    Follow the consequences, because they are not obvious and they matter. Blobs can be cached forever with no invalidation logic — there is nothing to invalidate. They can be served by any mirror, any CDN, any USB stick, because the client verifies them itself and never has to trust the source (I4.1 again, now doing real work). Registry caching, normally a subtle problem, becomes almost trivially correct.

    And all the difficulty concentrates in one place. The tag endpoint is the only thing that needs consistency guarantees, the only thing worth protecting with authorisation, and the only thing an attacker gains anything by tampering with — because moving :latest to point at their digest is the whole attack, and no amount of digest verification downstream will notice, since the bytes really do match the digest they were promised. That is precisely the gap I11's signing story is built to close.

    The spec's own definitions draw the line in one sentence each. Note that "blob" is defined by how it is addressed, and "manifest" by what it points at.

    Blob: the binary form of content that is stored by a registry, addressable by a digest

    Manifest: a JSON document uploaded via the manifests endpoint. A manifest may reference other manifests and blobs in a repository via descriptors.

    Tag: a custom, human-readable pointer to a manifest. A manifest digest may have zero, one, or many tags referencing it.
    OCI distribution-spec v1.1.1 — spec.md § Definitions
    Lab
    1. Fetch one manifest twice — once by tag, once by the digest that tag resolves to. Same document, two names, and only one of them can ever change. (The token dance on line 2 is I5.5; take it on trust for now.) 
      REG=https://registry-1.docker.io; REPO=library/alpine

echo "resolved  -> $D"

    2. Now try to use a tag where the spec demands a digest. The blob endpoint has no tags to offer. 
      curl -s -w "\nstatus: %{http_code}\n" -H "Authorization: Bearer $TOKEN" \
     $REG/v2/$REPO/blobs/3.21
      404 page not found

status: 404

      Look closely at that body: plain text, no {"errors":[...]} envelope. The request never reached a registry handler at all, because 3.21 failed to parse as a digest. That distinction — JSON error versus bare text — is a diagnostic you will reuse.

    Verify

    Shown any registry URL, you can say instantly whether what it names can change, and therefore whether it is safe to cache forever. You can also say where in this API an attacker would aim.

    Gotchas
    • "Immutable" is a property of the naming, not a promise from the server. A hostile registry can absolutely return the wrong bytes for a blob URL. What content addressing gives you is the ability to detect that in one line of code — which is why every client in this module recomputes the digest, and why I5.7's step 4 is not ceremony.
    • A digest may carry many tags, or none. Deleting a tag does not delete an image, and an image referenced only by digest is perfectly normal — that is exactly what a pinned pod spec produces.
    • The repository name has a strict grammar. Lowercase only, and the spec's regex forbids the uppercase letters people reach for first. An unexpected 400 on push is often a capital letter in a repository name.

    This asymmetry is the real argument for image: app@sha256:… over image: app:v2 in a deployment. A tag is a mutable pointer that someone else controls; a digest is not. It is the same distinction W3.6 makes when a rollout's identity has to be pinned to something that cannot shift underneath it, and it is why W6.17's "but it worked yesterday" pulls are so often a moved tag rather than a broken registry.

    Docs: spec.md § Definitions and § Pulling manifests for the grammar of <name> and <reference>. On the Kubernetes side, search for "image pull policy" — the tag/digest distinction drives its whole behaviour.

    I5.3

    HEAD: how a node asks "has this tag moved?"

    Why it matters

    imagePullPolicy: Always has a reputation for being expensive, and the reputation is wrong. Understanding the one HTTP request behind it fixes that misconception, explains why the policy nonetheless breaks disconnected clusters, and — as a bonus you can measure — shows you which registry requests cost you rate-limit budget and which are free.

    The concept

    A HEAD request returns a response's headers with no body. On a manifest URL, the header that matters is Docker-Content-Digest: the digest the reference currently resolves to. So a node holding a cached image can ask the only question it actually has — has this tag moved since I pulled it? — by comparing one string, having transferred nothing.

    That reframes the policy. Always does not mean "always re-download". It means "always re-resolve". The kubelet HEADs the manifest, compares the returned digest against what its content store already holds, and if they match it pulls not one byte. The cost of the policy is one cheap round trip per container start, not a transfer.

    Which also explains the failure that makes it painful in the wrong environment. If the registry is unreachable, the resolve fails — and the pod fails with it, even though a perfectly good image is sitting on local disk. Nothing was needed from the network except a string comparison, and the pod dies anyway. That is why disconnected and air-gapped clusters run IfNotPresent, and it is the single most common reason a cluster that survived a Docker Hub outage sat next to one that did not.

    The spec gives HEAD its own section, and — importantly — makes the digest header a SHOULD, not a MUST. A client cannot assume it is there.

    In order to verify that a repository contains a given manifest or blob, make a HEAD request to a URL in the following form: […]

    A HEAD request to an existing blob or manifest URL MUST return 200 OK.
    A successful response SHOULD contain the digest of the uploaded blob in the header Docker-Content-Digest.
    A successful response SHOULD contain the size in bytes of the uploaded blob in the header Content-Length.
    OCI distribution-spec v1.1.1 — spec.md § Checking if content exists in the registry

    You can explain imagePullPolicy: Always in terms of one HTTP request, say what it costs, and say exactly which environment it breaks and why.

    Gotchas
    • Docker-Content-Digest is a SHOULD, and its name is a historical accident. The spec calls the Docker-era headers OPTIONAL. A client that cannot get the header falls back to a GET and hashes the body itself — which is why "HEAD is free" is a property of Docker Hub's implementation, not a guarantee of the protocol.
    • The digest depends on your Accept header. HEAD the same tag asking for different media types and you can get different digests back, because you are asking about different documents. I5.4 is entirely about this.
    • "Re-resolve" still needs the registry. The cheapness of Always is about bytes, not about availability. One unreachable registry and every Always pod on the node stops starting.

    This is the mechanism under W1.20's account of who does the pulling on a node, and the reason W6.17 recommends IfNotPresent for clusters that must survive a registry outage. Note the Kubernetes default that catches people: a pod whose image has no tag, or the tag :latest, gets Always whether you asked for it or not.

    Docs: search the Kubernetes docs for "image pull policy" — the defaulting rule for :latest is the exam-relevant part. Spec side: spec.md § Checking if content exists.

    I5.4

    Content negotiation, and the 404 that is really a wrong header

    Why it matters

    One tag can be several different documents depending on what you say you accept, and a registry is entitled to answer "I have nothing that matches" with a 404. That is how you get MANIFEST_UNKNOWN for an image you are looking at in the web UI — the fourth fault in this module's drill, and a genuinely nasty half-hour if you have never met it.

    The concept

    The Accept header lists the media types your client can parse. Four matter here, in two matched pairs: the OCI image index and the Docker manifest list (multi-platform, a list of manifests); and the OCI image manifest and the Docker v2 schema 2 manifest (one platform, config plus layers). I4.6 established that OCI and Docker forms differ in three media-type strings and an annotations block, and in nothing else that moves bytes.

    What a registry does with your Accept header, however, is not uniform, and this is where the lesson has to be careful. The spec says the client SHOULD send one and the server indicates what it returned in Content-Type. It does not require conversion, and it does not require an error. Measured on the two registries in front of us in 2026, the behaviours are strikingly different:

    • Docker Hub ignores it. Ask for the single-platform Docker v2s2 type and you still get the OCI index back. It returns what is stored, and lets your client cope.
    • registry:2 honours it strictly. Ask for a type it does not hold and you get 404 MANIFEST_UNKNOWN — for an image that is definitely there. Send no Accept at all and you get the same 404, because the default is the ancient schema 1 type and modern images are not stored that way.

    There is a third behaviour, and it is the strangest: asked for a type it does not hold, registry:2 may down-convert to Docker schema 1 — a signed legacy format — and hand you a document with a completely different digest from the image you asked about. You did not get an error, you got a different image identity. If anything downstream compares that digest against a pinned one, it will disagree, and nothing in the exchange says why.

    The practical upshot is a rule: always send an explicit Accept listing all four types. Never rely on a server default. Every curl in the rest of this module does exactly that.

    Note how much room the spec leaves here — SHOULD throughout, and no requirement to convert or to refuse.

    The client SHOULD include an Accept header indicating which manifest content types it supports.
    In a successful response, the Content-Type header will indicate the type of the returned manifest.
    […]
    If the manifest has a mediaType field, clients SHOULD reject unless the mediaType field's value matches the type specified by the Content-Type header.
    OCI distribution-spec v1.1.1 — spec.md § Pulling manifests

    Gotchas
    • Registries genuinely differ here, so do not generalise from one. Docker Hub ignored every Accept we sent; registry:2 enforced it strictly. Both are conformant — the spec says SHOULD. Test against the registry you actually use.
    • A schema-1 fallback is a silent identity change. You asked about a tag and got a different digest, with a 200 and no warning. Any pinning or signature check downstream will now disagree with you and will not say why.
    • The 16 entries are not 16 images. Eight are attestation manifests, as I4.5 found. Any platform selection must skip them — I5.7 does it explicitly.

    Kubernetes never exposes this layer: whatever the negotiation did, the kubelet reports ErrImagePull with the registry's message flattened into an event (W6.17). When the message is manifest unknown for an image you can see in the registry UI, the wrong-Accept path is the explanation people take longest to find — and the fastest test is one curl from the node with an explicit four-type header.

    Docs: spec.md § Pulling manifests, plus the spec's own content-negotiation.md. On the Kubernetes side there is nothing to read — that is rather the point of this checkpoint.
