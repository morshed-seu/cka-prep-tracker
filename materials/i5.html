    I5 — Registries

    A registry is an HTTP server with two namespaces — blobs by digest, manifests by tag or digest — and once you have pulled an image using nothing but curl, ImagePullBackOff stops being a Kubernetes mystery and becomes a status code you can read.

    I4 gave you an image sitting in a directory. This module is about the four hours of its life before that — how it travelled. The answer is smaller than you expect: a registry is an HTTP server with two kinds of URL, and by the end of the second group you will have pulled a complete image using curl, jq and sha256sum, with no container tooling anywhere in the path.

    Checkpoints15 Hours~6 PrerequisitesI4
    • Read the two endpoint families off any registry URL, and say which one is mutable and why that asymmetry is the whole design.
    • Complete the token dance by hand and pull a full image — index, manifest, config, every layer — with curl alone, verifying each digest as it lands.
    • Push blobs monolithically and in chunks, explain why the manifest goes last, and make a 30 MB "upload" take no bytes at all.
    • Point containerd at a mirror with hosts.toml, and diagnose the four common pull failures from their status codes rather than from Kubernetes' summary of them.

    The API

    I5.1

    The handshake: one URL that answers "are you a registry?"

    Why it matters

    Before you can debug a registry you have to be sure you are talking to one. That sounds trivial until the day a pull fails against an internal host and the question "is the registry broken, or is something in front of it?" costs an hour. There is exactly one request that answers it, and the answer arrives in the status code alone.

    The concept

    Every registry that implements the distribution spec serves its entire API under the path prefix /v2/, and the bare endpoint /v2/ is the version handshake. The version lives in the path rather than in a header, which is a small decision with a pleasant consequence: a client discovers whether a server speaks the protocol with one request and nothing to negotiate.

    The part that surprises people is what a healthy Docker Hub returns: 401 Unauthorized, not 200. That is not a failure. The endpoint exists, the server answered, and the WWW-Authenticate header it sent back is the server telling you exactly where to go and get a token. On this API, 401 is frequently the first line of a successful conversation — internalise that now and half of the confusion in this module never arises.

    The genuinely bad answer is 404. A 404 at /v2/ means whatever answered does not know it is supposed to be a registry — usually a reverse proxy, ingress rule or load balancer that is routing your request somewhere else entirely. Distinguishing "needs auth" from "is not a registry" is the entire job of this one request, and it takes a second.

    The spec defines this endpoint for exactly one purpose, and is careful to say that authentication is somebody else's business.

    To check whether or not the registry implements this specification, perform a GET request to the following endpoint: /v2/.

    If the response is 200 OK, then the registry implements this specification.

    This endpoint MAY be used for authentication/authorization purposes, but this is out of the purview of this specification.

    Given a hostname, you can say in one request whether it is a registry, and if so whether it wants a token. You can also explain to a colleague why the 401 they screenshotted is not the bug they think it is.

    Gotchas
    • The trailing slash is required. /v2 and /v2/ are different paths, and some registries answer only the second. When a handshake mysteriously 404s, check that first.
    • A JSON error body means the registry answered; a plain-text one means something else did. The {"errors":[...]} envelope is part of the spec, so its presence tells you the request reached a registry handler. A bare 404 page not found in plain text — you will see one in I5.2 — means the request was rejected before any registry code ran.
    • docker-distribution-api-version is not a reliable signal. The spec calls the Docker-era headers OPTIONAL and says clients SHOULD NOT depend on them. Read the status code.

    When a node reports ErrImagePull against an internal registry (W6.17), this is the first command to run from that node — not from your laptop. It separates "the registry is unreachable or misrouted" from "the credentials in the imagePullSecret are wrong", and those two have completely different fixes. Kubernetes never shows you this layer; you have to go and look.

    Docs: the exam will not ask you to curl a registry, but it will ask you to fix a pod that cannot pull. Search the Kubernetes docs for "images" and read the private-registry section; the spec side is spec.md § Determining Support.

    I5.2

    Two endpoint families, one of them mutable

    Why it matters

    The distribution API is small enough to hold in your head — but only once you notice that every URL in it belongs to one of two families, and that the difference between them explains why registry mirrors are easy, why caching is safe, and where every interesting attack is aimed.

    The concept

    There are two:

    • /v2/<name>/blobs/<digest> — content, addressed by its own hash. The reference here must be a digest. Because of I4.1, this URL is immutable by construction: the name is computed from the bytes, so the same URL can never legitimately return different content.
    • /v2/<name>/manifests/<reference> — metadata, where the reference may be a digest or a tag. And that is the whole difference. A tag is a name somebody assigned, so it can be moved.

    So the entire mutable surface of a registry is one mapping: tag → digest. Everything else is content-addressed and therefore frozen.

    Follow the consequences, because they are not obvious and they matter. Blobs can be cached forever with no invalidation logic — there is nothing to invalidate. They can be served by any mirror, any CDN, any USB stick, because the client verifies them itself and never has to trust the source (I4.1 again, now doing real work). Registry caching, normally a subtle problem, becomes almost trivially correct.

    And all the difficulty concentrates in one place. The tag endpoint is the only thing that needs consistency guarantees, the only thing worth protecting with authorisation, and the only thing an attacker gains anything by tampering with — because moving :latest to point at their digest is the whole attack, and no amount of digest verification downstream will notice, since the bytes really do match the digest they were promised. That is precisely the gap I11's signing story is built to close.

    The spec's own definitions draw the line in one sentence each. Note that "blob" is defined by how it is addressed, and "manifest" by what it points at.

    Blob: the binary form of content that is stored by a registry, addressable by a digest

    Manifest: a JSON document uploaded via the manifests endpoint. A manifest may reference other manifests and blobs in a repository via descriptors.

    Tag: a custom, human-readable pointer to a manifest. A manifest digest may have zero, one, or many tags referencing it.
    OCI distribution-spec v1.1.1 — spec.md § Definitions

    Gotchas
    • "Immutable" is a property of the naming, not a promise from the server. A hostile registry can absolutely return the wrong bytes for a blob URL. What content addressing gives you is the ability to detect that in one line of code — which is why every client in this module recomputes the digest, and why I5.7's step 4 is not ceremony.
    • A digest may carry many tags, or none. Deleting a tag does not delete an image, and an image referenced only by digest is perfectly normal — that is exactly what a pinned pod spec produces.
    • The repository name has a strict grammar. Lowercase only, and the spec's regex forbids the uppercase letters people reach for first. An unexpected 400 on push is often a capital letter in a repository name.

    This asymmetry is the real argument for image: app@sha256:… over image: app:v2 in a deployment. A tag is a mutable pointer that someone else controls; a digest is not. It is the same distinction W3.6 makes when a rollout's identity has to be pinned to something that cannot shift underneath it, and it is why W6.17's "but it worked yesterday" pulls are so often a moved tag rather than a broken registry.

    Docs: spec.md § Definitions and § Pulling manifests for the grammar of <name> and <reference>. On the Kubernetes side, search for "image pull policy" — the tag/digest distinction drives its whole behaviour.

    I5.3

    HEAD: how a node asks "has this tag moved?"

    Why it matters

    imagePullPolicy: Always has a reputation for being expensive, and the reputation is wrong. Understanding the one HTTP request behind it fixes that misconception, explains why the policy nonetheless breaks disconnected clusters, and — as a bonus you can measure — shows you which registry requests cost you rate-limit budget and which are free.

    The concept

    A HEAD request returns a response's headers with no body. On a manifest URL, the header that matters is Docker-Content-Digest: the digest the reference currently resolves to. So a node holding a cached image can ask the only question it actually has — has this tag moved since I pulled it? — by comparing one string, having transferred nothing.

    That reframes the policy. Always does not mean "always re-download". It means "always re-resolve". The kubelet HEADs the manifest, compares the returned digest against what its content store already holds, and if they match it pulls not one byte. The cost of the policy is one cheap round trip per container start, not a transfer.

    Which also explains the failure that makes it painful in the wrong environment. If the registry is unreachable, the resolve fails — and the pod fails with it, even though a perfectly good image is sitting on local disk. Nothing was needed from the network except a string comparison, and the pod dies anyway. That is why disconnected and air-gapped clusters run IfNotPresent, and it is the single most common reason a cluster that survived a Docker Hub outage sat next to one that did not.

    The spec gives HEAD its own section, and — importantly — makes the digest header a SHOULD, not a MUST. A client cannot assume it is there.

    In order to verify that a repository contains a given manifest or blob, make a HEAD request to a URL in the following form: […]

    A HEAD request to an existing blob or manifest URL MUST return 200 OK.
    A successful response SHOULD contain the digest of the uploaded blob in the header Docker-Content-Digest.
    A successful response SHOULD contain the size in bytes of the uploaded blob in the header Content-Length.
    OCI distribution-spec v1.1.1 — spec.md § Checking if content exists in the registry

    Gotchas

    • The digest depends on your Accept header. HEAD the same tag asking for different media types and you can get different digests back, because you are asking about different documents. I5.4 is entirely about this.
    • "Re-resolve" still needs the registry. The cheapness of Always is about bytes, not about availability. One unreachable registry and every Always pod on the node stops starting.

    This is the mechanism under W1.20's account of who does the pulling on a node, and the reason W6.17 recommends IfNotPresent for clusters that must survive a registry outage. Note the Kubernetes default that catches people: a pod whose image has no tag, or the tag :latest, gets Always whether you asked for it or not.

    Docs: search the Kubernetes docs for "image pull policy" — the defaulting rule for :latest is the exam-relevant part. Spec side: spec.md § Checking if content exists.

    I5.4

    Content negotiation, and the 404 that is really a wrong header

    Why it matters

    One tag can be several different documents depending on what you say you accept, and a registry is entitled to answer "I have nothing that matches" with a 404. That is how you get MANIFEST_UNKNOWN for an image you are looking at in the web UI — the fourth fault in this module's drill, and a genuinely nasty half-hour if you have never met it.

    The concept

    The Accept header lists the media types your client can parse. Four matter here, in two matched pairs: the OCI image index and the Docker manifest list (multi-platform, a list of manifests); and the OCI image manifest and the Docker v2 schema 2 manifest (one platform, config plus layers). I4.6 established that OCI and Docker forms differ in three media-type strings and an annotations block, and in nothing else that moves bytes.

    What a registry does with your Accept header, however, is not uniform, and this is where the lesson has to be careful. The spec says the client SHOULD send one and the server indicates what it returned in Content-Type. It does not require conversion, and it does not require an error. Measured on the two registries in front of us in 2026, the behaviours are strikingly different:

    • Docker Hub ignores it. Ask for the single-platform Docker v2s2 type and you still get the OCI index back. It returns what is stored, and lets your client cope.
    • registry:2 honours it strictly. Ask for a type it does not hold and you get 404 MANIFEST_UNKNOWN — for an image that is definitely there. Send no Accept at all and you get the same 404, because the default is the ancient schema 1 type and modern images are not stored that way.

    There is a third behaviour, and it is the strangest: asked for a type it does not hold, registry:2 may down-convert to Docker schema 1 — a signed legacy format — and hand you a document with a completely different digest from the image you asked about. You did not get an error, you got a different image identity. If anything downstream compares that digest against a pinned one, it will disagree, and nothing in the exchange says why.

    The practical upshot is a rule: always send an explicit Accept listing all four types. Never rely on a server default. Every curl in the rest of this module does exactly that.

    Note how much room the spec leaves here — SHOULD throughout, and no requirement to convert or to refuse.

    The client SHOULD include an Accept header indicating which manifest content types it supports.
    In a successful response, the Content-Type header will indicate the type of the returned manifest.
    […]
    If the manifest has a mediaType field, clients SHOULD reject unless the mediaType field's value matches the type specified by the Content-Type header.

    Pulling by hand

    I5.5

    The token dance: the registry does not authenticate you

    Why it matters

    A public image needs a token. That single fact confuses more people than anything else in this API, and it explains a whole class of failure — including why an imagePullSecret holding perfectly valid credentials can still fail, and why a long pull can die of a 401 halfway through.

    The concept

    The registry does not check your identity. It delegates that to a separate authorization service, and the WWW-Authenticate header from I5.1 is the registry telling you where that service lives and precisely what to ask it for. Three fields matter:

    • realm — the URL of the token endpoint.
    • service — which registry the token should be valid for.
    • scope — what you want to do, as repository:<name>:<actions>, e.g. repository:library/alpine:pull.

    You request a token from the realm with that scope, and use it as an Authorization: Bearer header on the real request. For a public image you send no credentials at all and get an anonymous token — which is why the answer to "why does a public pull need a token?" is that the token is not about who you are, it is about what you asked to do. The auth service is quite happy to grant "pull from library/alpine" to nobody in particular.

    Four consequences, all practical:

    • Tokens are per-scope. A client pulling from two repositories does two dances. A pod with images from three repositories triggers three.
    • Tokens expire, and quickly — Docker Hub's live in five minutes. A large pull can outlast its token and take a sudden 401 partway through; well-behaved clients simply re-fetch and continue, which is why you rarely see it and why a client that does not handle it fails only on big images.
    • docker login stores credentials, not tokens. The token is re-fetched per operation. So a Kubernetes imagePullSecret containing entirely valid credentials still fails if the auth service is unreachable, even when the registry itself is fine — two hostnames, two failure modes, one error message.
    • The token is a JWT, and you can read it. Its payload states the access it grants, in the clear.

    The distribution spec deliberately says almost nothing about authentication — it defines the endpoint and steps back. That silence is why registries differ so much here, and why the challenge header is the only thing you can rely on.

    Gotchas

    I5.6

    Rate limits, and the twenty nodes behind one address

    Why it matters

    This is the failure that wastes the most time in real clusters, because it is intermittent, it strikes under load, and by the time it reaches a human it has been rewritten into a message that mentions neither rate limits nor HTTP. Ten minutes here saves an afternoon later.

    The concept

    Docker Hub meters anonymous pulls, and for anonymous requests the meter is attached to your source IP address. The registry tells you where you stand in the response headers of every request, so the budget is never a mystery — if you look.

    Now apply that to a cluster. Twenty nodes behind one NAT gateway present one address to Docker Hub, so they share one budget. The result is a failure with an unpleasant shape: pods start fine all morning, then a deploy at 14:00 half-succeeds, with a different subset of pods affected each time you retry. Nothing is broken, nothing has changed, and the pods that fail move around — which is exactly the signature people misread as a flaky network.

    The status code is 429. What reaches the person looking at kubectl get pods is ImagePullBackOff, with the real reason buried in the pod's events and often truncated. This is why "go and check the actual HTTP status" is such a high-value first move: the answer is unambiguous the moment you see the number, and unrecoverable guesswork until you do.

    The fixes are all in I5.13, and there are three: authenticate (a bigger budget), mirror (fetch from somewhere else), or run a pull-through cache (fetch once, serve many).

    Rate limiting is not in the distribution spec at all — it is registry policy, and the spec's only hook for it is the general error mechanism. The TOOMANYREQUESTS code is defined in the error-code table.

    The client MAY encounter error codes targeting Docker schema1 manifests […] These error codes are OPTIONAL and clients SHOULD NOT depend on them.
    OCI distribution-spec v1.1.1 — spec.md § Error Codes (and § Legacy Docker support error codes, quoted, for why the code strings are not a contract)

A backoff that resolves itself after an hour with no change is this, and nothing else.

    Docs: nothing in the Kubernetes docs covers registry rate limits; the registry operator's own documentation is the reference. For the exam, the useful search is "ImagePullBackOff" in the debugging pages — know that the reason lives in the events, not in the pod status.

    I5.7

    A complete pull with curl, jq and sha256sum

    Why it matters

    This is the checkpoint the module exists for. Once you have pulled an image by hand, "the registry is broken" stops being a sentence you can say — you can name which of six requests failed and what its status code was. It also surfaces a firewall trap that catches restricted networks every time.

    The concept

    A pull is six steps, and you have already done four of them separately:

    token→index→manifest→config→layers→verify

    Resolve the tag to an index; pick the manifest for your platform; fetch the config blob and each layer blob; verify every digest as it lands. Nothing else happens. There is no session, no negotiation beyond the Accept header, and no state on the server between requests.

    One thing does happen that the diagram hides, and it matters more than anything else in this checkpoint. A blob request is almost never answered with bytes. It is answered with 307 Temporary Redirect to a signed, time-limited URL on object storage — for Docker Hub, a CloudFront hostname that has nothing in common with registry-1.docker.io. The registry does the authorisation; a CDN does the transfer.

    So a pull touches three hosts: the registry, its auth service, and a content host you never configured and cannot guess. Allowlist only the registry hostname and manifests resolve perfectly while every layer download hangs or fails — which presents as "pulls work from my laptop but not from the cluster", the number one cause of that symptom in restricted networks.

    And this is where I4.1's insistence on verifying digests stops being pedantry. You are downloading bytes from a CDN that the registry does not control, over a URL signed hours ago. You verify the hash yourself, so the CDN never has to be trusted with integrity at all. The redirect is safe because the client checks.

    The spec makes the client's verification duty explicit, and — note the wording — puts the requirement on the client rather than trusting the server to be honest.

    A GET request to an existing blob URL MUST provide the expected blob, with a response code that MUST be 200 OK.
    […]
    Most clients MAY ignore the value, but if it is used, the client MUST verify the value matches the returned response body.
    Clients SHOULD verify that the response body matches the requested digest.

    I5.8

    Closing the loop: URL to running container, no container tooling

    Why it matters

    Worth pausing on, because this is the point the whole track has been building towards. Between I2, I4 and the last checkpoint you have implemented every step of "run an image" yourself. Seeing them join up changes what you believe the rest of the stack is for.

    The concept

    Six steps make an image run: resolve, download, verify, unpack, configure, execute. You have now done all six with tools that predate containers entirely — curl, sha256sum, a Python script that untars, and runc.

    So what does everything above this line actually add? Caching, concurrency, lifecycle management, and API surface — not new capability. containerd adds a content store so two pods sharing a base layer download it once, snapshots so a rootfs is prepared without copying (I7), and a lifecycle you can talk to over gRPC. CRI adds a stable interface so the kubelet does not need to know which runtime is installed (I8). The kubelet adds reconciliation, restart policy and reporting. Every one of those is valuable; none of them is a new mechanism.

    That is the intermediate track's thesis at its most concrete — the container ecosystem added almost no mechanism, it added contracts — and it is the mental model that makes node debugging tractable. When a pod will not start, you are no longer asking the unanswerable question "why is Kubernetes unhappy?". You are asking which of six steps failed, and every one of them has a command you can run by hand.

    Pushing

    I5.9

    The push order is the consistency model

    Why it matters

    A registry has no transactions. There is no "begin", no "commit", nothing that makes several uploads atomic — and yet an interrupted push never leaves a broken image. The mechanism that achieves that is one ordering rule, and understanding it tells you exactly what a half-replicated mirror will look like when you meet one.

    The concept

    A push is a pull run backwards: every blob first, the manifest last.

    each layer→config→manifest

    That ordering is the consistency model, and it needs no coordination to work. A manifest is the only thing that makes an image resolvable — nothing can be pulled until one exists. So as long as the manifest is written last, no client can ever fetch a manifest whose content is not already fully present. The failure modes are therefore asymmetric in a very convenient way:

    • An interrupted push leaves orphaned blobs. Wasted space, cleaned up by garbage collection (I5.12), and invisible to every client, because nothing points at them.
    • A broken image — a manifest resolving to content that is not there — cannot happen from an interrupted push at all. It requires something to write the manifest out of order, which is precisely what a mirror replicating naively does, and precisely I5.15's second fault.

    The other thing to notice in the trace below is that a well-behaved client asks before it uploads. Blobs are content-addressed, so "do you already have sha256:…?" is answerable with a HEAD, and the answer is usually yes. Most of a push is finding out how little needs pushing.

    The spec states the ordering in one sentence, and then — in the paragraphs that follow — carves out the single exception, for the subject field used by attestations and signatures.

    Pushing an object typically works in the opposite order as a pull: the blobs making up the object are uploaded first, and the manifest last.

    A registry MUST initially accept an otherwise valid manifest with a subject field that references a manifest that does not exist in the repository, allowing clients to push a manifest and referrers to that manifest in either order.
    A registry MAY reject a manifest uploaded to the manifest endpoint with descriptors in other fields that reference a manifest or blob that does not exist in the registry.

    I5.10

    Pushing a blob by hand: sessions, chunks and resumption

    Why it matters

    The upload half of the API is the part people never look at, and it is where registries differ most in practice. It is also where the integrity guarantee gets its server-side half: you verified digests on the way down in I5.7, and the registry verifies them on the way up.

    The concept

    An upload is a session. You POST to /v2/<name>/blobs/uploads/, the registry answers 202 Accepted with a Location header containing a URL with an upload identifier in it, and you send the bytes to that URL. Two ways to finish:

    • Monolithic — one PUT with the whole blob and ?digest= appended.
    • Chunked — a PATCH per chunk, each with a Content-Range, then a PUT with ?digest= and no body to finalise.

    The session exists so an upload can be resumed rather than restarted. That matters when the blob is 900 MB and the connection is a train's wifi; each PATCH response tells you the byte range the registry now holds, so a client that reconnects knows exactly where to continue.

    The subtle and rather elegant part is when you supply the digest: at finalisation, not at the start. The registry hashes the bytes as they arrive and compares at the end, so a mismatch is caught by the server without it ever having to trust the client's claim about what it was sending. Combined with I5.7's client-side check, the content is verified independently at both ends of the wire, and neither side has to trust the other.

    Note the two-stage shape, and that the Location header is where the session identity lives — the spec never specifies its format, which is why clients must treat it as opaque.

    Upon success, the response MUST have a code of 202 Accepted, and MUST include the following header:
    Location: <location>

    […] The Docker-Content-Digest header returns the canonical digest of the uploaded blob, and MUST be equal to the client provided digest.
    OCI distribution-spec v1.1.1 — spec.md § Pushing blobs

    Gotchas

    • Sessions expire and can be cancelled. An abandoned upload holds space until the registry cleans it up; a client that means to abandon one should DELETE the Location.

    Nothing in a cluster pushes blobs, so this checkpoint has no direct Kubernetes analogue — and saying so is more useful than inventing one. What does transfer is the shape of the guarantee: the receiver validates, so the sender's claim never has to be believed. That is the same reasoning that lets a node accept layers from a CDN it does not trust (W6.17), and it is worth carrying into I11, where the thing being validated stops being integrity and starts being provenance.

    I5.11

    Cross-repository mount: the 30 MB upload that moves no bytes

    Why it matters

    Promoting an image from staging/app to prod/app ought to be free — the bytes are already on the registry. There is an endpoint that makes it free, a permission subtlety that silently disables it, and a symptom so mild that nobody investigates: the pipeline just got slower.

    The concept

    Blobs are content-addressed, so a registry stores each one once and lets repositories reference it. "Uploading" a blob the registry already holds is therefore not a transfer at all — it is a permission check and a new reference. The spec gives it a dedicated form: instead of the usual POST to open an upload session, you POST with two query parameters naming the blob and the repository to take it from.

    A successful mount answers 201 Created — note, not 202 Accepted, which is what opening an upload session returns. That difference is the whole protocol: 201 means "done, it is yours", and 202 means "I could not do that, here is an upload session instead". A client does not need to ask whether the registry supports mounting; it tries, and reads the status code.

    The subtlety is the permission check, and it is where the bug lives. You must be able to pull from the source repository. A CI account scoped narrowly to the repository it publishes to cannot mount from anywhere, so every mount degrades to a full upload — correctly, silently, and with no error anywhere. The only symptom is that pushes take minutes instead of seconds, which is exactly the kind of regression that gets absorbed into "CI is slow lately".

    The spec spells out the fallback explicitly, which is why the try-and-read-the-code approach is safe.

    If a necessary blob exists already in another repository within the same registry, it can be mounted into a different repository via a POST request in the following format:
    /v2/<name>/blobs/uploads/?mount=<digest>&from=<other_name>

    The response to a successful mount MUST be 201 Created […]

    Alternatively, if a registry does not support cross-repository mounting or is unable to mount the requested blob, it SHOULD return a 202. This indicates that the upload session has begun and that the client MAY proceed with the upload.

    Gotchas

Cross-repo mount is the mechanism that makes doing it properly free.

    I5.12

    skopeo: the everyday tool, now that you know what it does

    Why it matters

    You have spent four checkpoints doing by hand what one command does. That was not wasted: you can now read skopeo's output knowing exactly which HTTP requests produced it, and — more usefully — you know which of its conveniences are hiding something you might need to see.

    The concept

    skopeo works on images where they live. No daemon, no root, no local runtime, and nothing is unpacked unless you ask for it. That is why it earns a place in a runtime-internals track: it belongs in CI, in an air-gapped transfer, and — most valuably — in the middle of an incident when the local runtime is exactly what you suspect.

    Four verbs carry the load:

    • inspect — the cooked view: platform, layers, environment. With --raw, the manifest byte for byte as stored, with no interpretation at all. Reach for --raw the moment you care which manifest a registry is handing you, because that is where I5.4's negotiation surprises become visible.
    • copy — between any two transports: docker:// (a registry), oci: (a layout on disk, exactly what I4 read), dir: (a flat directory) and containers-storage:. Registry-to-registry is a streaming operation — nothing is unpacked, so it is fast and needs no disk for a rootfs.
    • list-tags — the tag listing endpoint, which is the only way to discover what is in a repository.
    • delete — and here is the honest caveat, which matters more than the verb does.

    Deleting is where expectations break. On most registries delete removes the manifest, not the blobs. The tag stops resolving immediately; the disk does not move at all. Reclaiming the space needs a separate garbage-collection pass, which for registry:2 means running the registry read-only while it walks the store. And on a default registry:2, deletion is disabled outright — the verb returns unsupported until you enable it.

    This is not a quirk. It follows from I5.9's ordering: blobs are shared between repositories and tags (that is the whole point of I5.11), so nothing can safely delete a blob without proving that nothing else references it. That proof is the garbage-collection pass. Deleting an image and watching disk usage not move is a normal Tuesday.

    The spec allows a registry to refuse deletion entirely, which is why the default you meet is a refusal rather than an error you can fix in the client.

    Content management refers to the deletion of blobs, tags, and manifests.
    Registries MAY implement deletion or they MAY disable it.
    Similarly, a registry MAY implement tag deletion, while others MAY allow deletion only by manifest.

    • skopeo copy without --all copies one platform. I4's finding stands: the result is a layout reached by tag with no index behind it, so a later --platform selection is silently a lie. If you mean to copy a multi-platform image, say --all.

    This is the tool for the air-gapped-cluster question the exam likes: how do images get in? skopeo copy from Docker Hub to a layout on removable media, carry it across, skopeo copy from the layout into the internal registry — no runtime, no root, no daemon at either end. Combined with I5.13's hosts.toml, that is a complete air-gap story that never rewrites an image reference in a single manifest, which is what makes it survivable at scale (W6.17).

    Docs: skopeo(1) and skopeo-copy(1) for the transport syntax — the transport prefixes are the part worth memorising. Spec side: spec.md § Content Management.

    I5.13

    hosts.toml: pointing containerd somewhere else

    Why it matters

    This is the fix for I5.6, and it is one file. It is also the file that makes an air-gapped cluster work without rewriting every image reference in every manifest — which is the difference between a migration you can do and one you cannot.

    The concept

    containerd reads per-registry configuration from a directory tree — one subdirectory per registry host, each holding a hosts.toml. Because it lives outside the main config file, configuration management can drop it in without templating config.toml, and it is read per pull rather than only at start-up.

    Two things that get conflated and should not be:

    • A mirror is a host consulted first, with fall-back to the upstream on a miss. It fixes rate limiting and reduces egress. It does not help when upstream is unreachable, because a miss still has to go somewhere.
    • A pull-through cache is itself a registry that fetches from upstream on a miss and stores the result. It fixes rate limiting, reduces egress, and keeps serving what it has already cached when upstream is down.

    The hosts.toml looks identical for both; the difference is entirely in what you point it at. In the lab below it is a pull-through cache, because that is the configuration worth knowing.

    The last piece is the one that catches people, and it is a version-sensitive detail worth getting exactly right. ctr takes --hosts-dir on the command line, which is convenient for testing and proves nothing about your cluster — the kubelet does not use ctr. It pulls through CRI, and CRI reads the directory only if config_path is set in containerd's configuration. On containerd 2.3.3 that setting lives in [plugins.'io.containerd.cri.v1.images'.registry], and it is empty by default.

    Mirroring is not in the distribution spec at all — it is a client concern, and the spec's content-agnostic framing is precisely what makes a mirror possible: a blob is a blob wherever it comes from, because the client verifies it.

    The specification is designed to be agnostic of content types.

    Blob: the binary form of content that is stored by a registry, addressable by a digest

    I5.14

    Mini project — pull.py, a real registry client

    Why it matters

    Doing the pull once with curl proves you understand the requests. Writing the client proves you understand the decisions — when to verify, when to cache, what to do when the answer is a status code instead of a manifest. And at the end, two programs you wrote a module apart meet at a standard format without either knowing about the other.

    The concept

    pull.py is about 260 lines, half of them comment and diagnosis, and does four things:

    • Authenticates — try /v2/, and if the answer is a 401 with a Bearer challenge, parse realm, service and scope out of it and fetch a token. If the answer is 200, use no token at all. Both paths are exercised in the lab below.
    • Resolves tag → index → manifest, selecting a platform and skipping attestation manifests.
    • Verifies and caches every blob by digest in a content store laid out the way containerd's is: <store>/blobs/sha256/<hex>. That path is not a coincidence — it is also where an OCI layout keeps its blobs, so the layout this writes is the store plus two small files.
    • Diagnoses. Every HTTP error is turned into a sentence naming the status, what the registry said, and what that combination usually means. This is the module's thesis in one function: every common pull failure is a status code that already says what went wrong, and the only reason it reaches people as ImagePullBackOff is that nothing along the way said it out loud.

    Two implementation details are worth arguing about, because both are places a naive client is wrong. Blobs are written to a .partial name and renamed only after the digest matches — so a half-written or altered blob can never be mistaken for a cached one. And the config's architecture is checked against what was requested, because resolving a tag is not selecting a platform: if the tag resolved straight to a single manifest with no index, nothing has chosen anything, and --platform is a lie you told yourself. I4 found that nothing in the real pull path makes that check. This client makes it.

    Quiz

    1. A registry answers 401 at /v2/. Is it healthy?
      Answer

      Almost certainly yes — that is the normal answer from any registry requiring a token, and the WWW-Authenticate header tells you where to get one. The answer that means trouble is 404, which usually means a proxy is fronting the host and does not know it should be routing to a registry. A plain-text body rather than the spec's {"errors":[…]} envelope is the same signal.

    2. Why can a blob be cached forever with no invalidation logic, while a manifest cannot?
      Answer

      Because a blob is named by the hash of its own bytes, so the same URL can never legitimately return different content — there is nothing to invalidate. A manifest may be referenced by a tag, and a tag is a name someone assigned and can move. The tag→digest mapping is the only mutable surface in the entire API, which is why it is also the only thing worth attacking or worth protecting with authorisation.

    3. imagePullPolicy: Always is often described as expensive. What does it actually cost, and when is it genuinely dangerous?
      Answer

      One HEAD per container start. The kubelet re-resolves rather than re-downloading: it compares the returned Docker-Content-Digest with what the content store holds and pulls nothing if they match. Measured against Docker Hub, HEADs did not decrement the rate-limit counter at all. It is dangerous in disconnected environments, because an unreachable registry fails the pod even though a perfectly good image is on local disk — which is why those clusters run IfNotPresent.

    4. A registry returns 404 MANIFEST_UNKNOWN for an image you can see in its web UI. Give two causes.
      Answer

      An Accept header that does not list the media type the manifest is stored as — measured on registry:2, an OCI-stored image asked for as Docker v2s2 404s, and so does a request with no Accept at all. The other cause is a genuinely absent tag, so check by digest too. Note that Docker Hub behaves differently: it ignored every Accept header tested and returned the OCI index regardless. Both are conformant — the spec says SHOULD.

    5. You get a 200 back from a manifest request, but the digest does not match the one you pinned. What happened?
      Answer

      Most likely the registry down-converted to Docker schema 1 (application/vnd.docker.distribution.manifest.v1+prettyjws) because you asked for a type it does not hold. You did not get an error; you got a different document for the same tag, with its own digest. Anything comparing against a pinned digest will now disagree and nothing in the exchange explains why. Send an explicit four-type Accept and check Content-Type on the response.

    6. Why does a public image need a token?
      Answer

      Because the token is not about who you are, it is about what you asked to do. The registry delegates authorisation to a separate service and tells you the scope to request; you send no credentials and receive an anonymous token whose sub is empty. The practical consequence is that a pull depends on two hosts — the registry and its auth service — and a firewall allowing only the first produces failures that look exactly like bad credentials.

    7. Twenty nodes sit behind one NAT gateway. Predict the failure and its shape.
      Answer

      They share one anonymous rate-limit budget, because Docker Hub charges anonymous pulls to the source IP — provable by comparing docker-ratelimit-source with the machine's own public address. The failure is 429, and its shape is what makes it hard: pods start fine until load rises, then a deploy half-fails with a different subset of pods affected each time. By the time it reaches a human it is ImagePullBackOff with the number nowhere in sight.

    8. A push is interrupted halfway. What state is the registry in?
      Answer

      It holds some orphaned blobs and no new manifest, so no client can see anything at all — the image simply does not exist yet. That is the point of uploading blobs first and the manifest last: the manifest is the only thing that makes content resolvable, so writing it last makes the whole push atomic without any transaction. The orphans are wasted space until garbage collection, and are never visible.

    9. A manifest resolves but one of its blobs 404s. Whose bug is it, and why do only some nodes fail?
      Answer

      A replication path — a mirror or a sync job — that copied the manifest before its blobs, breaking the ordering invariant the push protocol maintains. The upstream registry is fine. Only some nodes fail because a node whose content store already holds that layer never asks for it: containerd found ours locally and the pull succeeded, while skopeo copying to a fresh destination reported blob unknown to registry. Test on a node that has never held the image.

    10. Pushing a 900 MB image to a second repository on the same registry takes two seconds. Then, after a permissions tidy-up, it takes nine minutes again. What changed?
      Answer

      Cross-repository blob mount stopped working. It requires pull rights on the source repository, so a CI account scoped narrowly to its destination silently degrades to a full upload — correctly, with no error anywhere. The tell is in the registry's access log: 202 where there used to be 201 on POST …/blobs/uploads/?mount=…&from=….

    11. You deleted several large images from a registry and the disk did not move. Why not, and what would a garbage collector have to prove before removing one blob?
      Answer

      delete removes the manifest, not the blobs — measured: 28.5M before, 28.5M after, and 96K only once garbage-collect ran. A collector must prove no remaining manifest anywhere in the registry references that blob, because blobs are shared between tags and repositories. That is a whole-store walk, which is why it is a separate pass and why it wants the registry read-only.

    12. You configure a mirror in hosts.toml, test it with ctr --hosts-dir, and it works perfectly — but pods on the node still pull from Docker Hub. What did you miss?
      Answer

      config_path. The kubelet pulls through CRI, which reads certs.d only if config_path is set — on containerd 2.3.3 that is [plugins.'io.containerd.cri.v1.images'.registry], and it is empty by default. ctr takes a command-line flag and goes through the transfer service instead, so testing that way proves nothing about pods. Guides written for containerd 1.7 name io.containerd.grpc.v1.cri, which no longer applies.

    13. A pull of a single-platform image succeeds on an amd64 node and the container later dies with exec format error. Where should the pull have failed?
      Answer

      Nowhere, in the real pull path — which is the point. Resolving a tag is not selecting a platform: if the tag resolves straight to one manifest with no index, nothing has chosen anything, and --platform is silently ignored. The only place the truth is stated as a fact rather than a promise is the image config's own architecture field, and nothing in the standard path checks it. pull.py does.

    • You can read any registry URL and say which of the two endpoint families it belongs to, whether what it names can change, and therefore whether it is safe to cache.
    • You can complete the token dance by hand and pull a complete image with curl, jq and sha256sum — then unpack it and run it, with no container tooling in the path at any point.
    • You can push blobs monolithically and in chunks, explain why the manifest is written last, and make a 30 MB upload transfer no bytes at all.
    • You can point containerd at a mirror and prove it is being used, including the config_path setting that decides whether pods see it.
    • ImagePullBackOff is now a diagnosable HTTP problem rather than a Kubernetes mystery — five failure modes, each identified by a status code you can reach in under a minute from the affected node.
