    B9 — Networking II: virtual networking & packet filtering

    This is the module the whole beginner track has been climbing toward. By the end of it you will have built, with your own hands and out of nothing but namespaces, virtual cables, a switch and a handful of firewall rules, the two things people find most mysterious about Kubernetes: a pod network (private machines that all reach each other and the outside world) and a load-balanced Service (one address that fans traffic out across several backends). You will build both before either word is used — so that when Kubernetes later says "pod network" and "ClusterIP," you recognise machinery you already assembled rather than magic you have to trust. Nothing in a cluster's data path is more advanced than what is in this module; there is just more of it, automated.

    We build bottom-up, in four movements. Virtual wiring: a network namespace as a private network stack, the veth pair as a patch cable, the bridge as a switch, and proving two namespaces can talk by watching one packet at two points. Getting out: turning the host into a router, the three flavours of NAT, giving the private subnet real internet access, and why NAT needs a memory (conntrack). Netfilter: where in the kernel a packet can be caught, the tables/chains/rules/targets vocabulary under every Linux firewall, the filter-vs-nat split that explains "ping works but curl doesn't," and reading rules by their packet counters. Load balancing and sockets: DNAT plus a statistics match as a round-robin balancer (this is kube-proxy), publishing a host port (this is a NodePort), and unix domain sockets — the filesystem-based endpoints that explain why access to the runtime socket is root. Then you assemble it all into a hand-built CNI and diagnose three faults by rule and by state.

    Checkpoints20 Hours~8 PrerequisitesB6, B8
    • Create a network namespace and explain what it gets its own of — interfaces, routing table, netfilter rules, port space and loopback — and why that means a pod gets a whole IP.
    • Build a veth pair as a virtual patch cable and a bridge as a virtual switch, and move one end of a veth into a namespace.
    • Address a private subnet deliberately — bridge as gateway, an address per namespace, a default route — the way a CNI's IPAM does for every pod.
    • Connect two namespaces and prove the path by capturing the same packet at two points with tcpdump.
    • Turn the host into a router with ip_forward, and explain SNAT, MASQUERADE and DNAT by what each rewrites.
    • Give a private subnet masqueraded egress to the internet, and explain why removing the rule stops replies while requests still leave.
    • Explain conntrack — why NAT needs state — and read the table with conntrack -L, including the "rule changed mid-flow does nothing" consequence.
    • Draw the netfilter hooks (prerouting, input, forward, output, postrouting) and the to-host vs through-host paths, and say why DNAT lives in prerouting.
    • Name the tables/chains/rules/targets vocabulary and write one rule of each target kind by hand.
    • Reproduce "ping works but curl doesn't" from a filter DROP, and read DROP (hang) vs REJECT (instant) from the timing.
    • Know that the backend on 24.04 is nftables and iptables is iptables-nft, and view the same ruleset both ways.
    • Debug by rule order and packet counters — find which rule traffic actually hits, and prove a later rule is dead.

    • Publish a host port into a private namespace with DNAT in prerouting — a NodePort, by hand.
    • Explain unix domain sockets — stream vs datagram, filesystem permissions, the abstract namespace — and why access to containerd.sock is equivalent to root.
    • Assemble a CNI v0.1 in two scripts, and diagnose filter-vs-nat, a DNAT rule that never matches, and a stale conntrack entry.

    B6 gave you namespaces as an isolation primitive; B8 gave you addresses, routes, ARP, TCP and tcpdump. This module fuses the two: it wires namespaces together into real networks and watches packets cross them. Everything runs on the throwaway sandbox VM (B0.1), never on the cluster. This module deliberately breaks its own connectivity — you will add and delete addresses, flip ip_forward, install firewall rules that drop traffic, and masquerade egress — so take a snapshot first (B0.9) and you can always roll back to a clean machine. Install the tools once up front: sudo apt-get install -y tcpdump conntrack nftables socat netcat-openbsd (iproute2 and iptables are already present on 24.04). Almost every command here needs root, so most labs use sudo; your uplink interface is ens3 on a typical Multipass VM (substitute the name ip -br link shows if it differs).

    Virtual wiring

    B9.1

    A network namespace is a private, empty network stack

    Why it matters

    B6 introduced namespaces as an isolation trick in the abstract. Now that B8 has given you the vocabulary — interfaces, addresses, routes, ports — you can see what a network namespace actually hands you: a whole second network stack, conjured from nothing, that shares not one thing with the machine's real one. This is the single atom every container network is built from. A pod is, at bottom, exactly one of these namespaces with some containers living inside it — which is why the containers in a pod reach each other on localhost but a pod gets its own IP. Build one by hand and the rest of Kubernetes networking stops being magic.

    The concept

    A network namespace is the kernel keeping a separate, private copy of "everything network" for a group of processes. Run ip netns add red and you get a namespace called red that has its own: set of network interfaces, routing table, netfilter rules, port space, and loopback device. Nothing in red can see or collide with anything in the host's network stack or any other namespace. This is the hotel room's own everything — same building, but its own wiring, its own phone list, its own locks.

    Two facts fall straight out of "its own," and both matter for the rest of your career:

    • Its own port space. Two processes in two different network namespaces can both bind port 80 with no conflict, because the port numbers live in separate universes. This is precisely why every pod gets a whole IP address of its own rather than a share of the node's ports — the namespace is the reason ports don't clash between pods.
    • It starts with nothing — not even loopback. A fresh namespace has exactly one interface, lo, and it is down. So the first surprise is that even ping 127.0.0.1 fails until you explicitly bring loopback up with ip link set lo up. A namespace is genuinely empty; every wire you want, you add.

    You run a command inside a namespace with ip netns exec red <command> — the command executes with red's network stack as its world. That one verb, exec, is how you'll do everything from here on: address interfaces, add routes, run ping and tcpdump, all inside the namespace you're building.

    ip netns add red→own interfaces · routes · netfilter · ports · lo· reaches nothing until you wire it
    Lab
    1. Create a namespace and look inside it. It has only a down loopback and can reach nothing — the empty room before you run any wire to it. 
      multipass shell sandbox
sudo ip netns add red
sudo ip netns exec red ip addr show        # what interfaces does red have?
      1: lo: <LOOPBACK> mtu 65536 state DOWN ...    ← one interface, and it is down
    # no inet line: loopback has no address yet either
    2. Prove it is genuinely empty: even pinging its own loopback fails, because lo is down. Then bring lo up and watch the same ping succeed — you just added the first working wire. 
      sudo ip netns exec red ping -c1 -W1 127.0.0.1 2>&1 | tail -1
sudo ip netns exec red ip link set lo up          # bring loopback up
sudo ip netns exec red ping -c1 127.0.0.1 | tail -2
      ping: connect: Network is unreachable        ← lo down: not even localhost works
64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.03 ms   ← lo up: localhost works now
1 packets transmitted, 1 received, 0% packet loss
    3. See the "own port space" fact directly: list the namespace's listening sockets — a separate, empty set from the host's. 
      sudo ip netns exec red ss -ltn        # red's listeners (none)
ss -ltn | head -3                      # the host's listeners (its own, separate set)
      State  Recv-Q Send-Q Local Address:Port      ← red: header only, nothing listening
LISTEN 0      4096   127.0.0.53%lo:53         ← host: its own listeners, a different universe
    Verify

    Name at least four things a network namespace has its own copy of, and state the consequence of "its own port space." (Its own interfaces, routing table, netfilter rules, port space and loopback; because the port space is separate, two processes in different namespaces can both bind the same port — which is why each pod gets a whole IP.) Then: why does ping 127.0.0.1 fail in a brand-new namespace? (Because a fresh namespace's only interface is lo and it starts down — loopback must be brought up with ip link set lo up before even localhost works.)

    Gotchas

    The ip netns command makes named namespaces, which persist as files under /var/run/netns/ and outlive the process that made them — handy for labs. A container runtime instead makes an anonymous per-pod namespace tied to the pod's lifetime, so you won't see pod namespaces in ip netns list by default. The mechanism is identical; only the bookkeeping differs. (You can make a runtime's namespace visible to ip netns by bind-mounting its /proc/<pid>/ns/net, which is exactly what debugging tools do.)

    Deleting a namespace (ip netns del red) destroys every interface that lived only inside it, and moves any interface that had a physical backing back to the default namespace. So a veth end left inside a deleted namespace vanishes with it — which is the tidy way to clean up a whole experiment, but also a way to lose an interface you meant to keep. Delete deliberately.

    A pod is a network namespace. The "pause" (sandbox) container a runtime starts first exists mainly to hold that namespace open; every real container in the pod is then placed into the same namespace, which is why containers in one pod share an IP and reach each other over localhost, while different pods are fully isolated with their own port spaces. The "each pod gets its own IP" rule that all of Kubernetes networking assumes is nothing more than "each pod gets its own network namespace," which you just created by hand.

    Building a pod's namespace, veth and bridge by hand is W4.2; the runtime's pod-sandbox and CRI flow are W1.20.

    Docs

    man 8 ip-netns is the whole toolset — add, del, list, exec, and how named namespaces map to /var/run/netns. man 7 network_namespaces explains what is and isn't isolated. For the syscall underneath, man 2 unshare and man 2 setns (the CLONE_NEWNET flag from B6). In the exam docs, this is assumed under "Cluster Networking" — no page teaches it directly, which is exactly why you learn it here.

    B9.2

    A veth pair is a virtual patch cable

    Why it matters

    A namespace that reaches nothing is useless; to connect it to anything you need a wire, and the wire is a veth pair. It is the single most important virtual device in all of container networking — every pod on every node in every Kubernetes cluster is attached to the world by one of these. Understand it as an ordinary patch cable with a plug at each end and the rest of the module has a physical intuition to hang on.

    The concept

    A veth pair (virtual Ethernet) is two linked interfaces that behave like the two ends of a single cable: whatever goes in one end comes out the other, and nowhere else. You create both ends at once — there is no such thing as half a veth pair — with ip link add veth0 type veth peer name veth1. That gives you veth0 and veth1, both currently in the host namespace, both down and unaddressed. This is the hotel phone wire from the analogy: one end is the handset in the room, the other is a plug in the wiring closet.

    The move that makes it useful is relocating one end into a namespace: ip link set veth1 netns red. Now the cable straddles a boundary — veth0 hangs in the host, veth1 lives inside red — and it is the only path in or out of the namespace. Send a packet into veth1 from inside red and it emerges from veth0 on the host, ready to be handed to a bridge, a route, or another namespace. This is precisely what a container runtime builds for every pod: one end named eth0 inside the pod's namespace, the other hanging on the node with an auto-generated name like vethb3f1a2.

    veth0 (host)⟷ one cable, two plugs ⟷veth1 → moved into red
    Lab
    1. Create a veth pair and confirm both ends exist on the host, linked to each other. The @ notation names each end's peer. 
      multipass shell sandbox
sudo ip link add veth0 type veth peer name veth1
ip -br link show type veth
      veth1@veth0  DOWN  ...        ← veth1, whose peer is veth0
veth0@veth1  DOWN  ...        ← veth0, whose peer is veth1  (a linked pair)
    2. Move one end into the red namespace and watch it disappear from the host and reappear inside. The cable now straddles the boundary. 
      sudo ip link set veth1 netns red
ip -br link show type veth                       # host now shows only veth0
sudo ip netns exec red ip -br link show          # red now has veth1
      # host:
veth0@if5  DOWN  ...          ← only one end left here; its peer is now "if5" (inside red)
# inside red:
lo           DOWN ...
veth1@if6    DOWN ...         ← the other end arrived in the namespace
    3. Prove they are inseparable: delete the host end and the namespace end vanishes too. (Re-create it afterwards for the next lesson.) 
      sudo ip link del veth0                            # delete one end...
sudo ip netns exec red ip -br link show          # ...the other is gone from red too
sudo ip link add veth0 type veth peer name veth1 && sudo ip link set veth1 netns red   # rebuild
      lo  DOWN ...                 ← veth1 is gone: deleting either end destroys both
    Verify

    Where does a packet sent into one end of a veth pair come out, and what happens to one end if you delete the other? (It comes out the paired end and nowhere else — a veth is a point-to-point cable; deleting either end destroys both, because there is no such thing as half a pair.) Then: after ip link set veth1 netns red, where does each end live? (veth0 stays in the host namespace; veth1 is now inside red — the cable straddles the boundary and is the namespace's only link to the outside.)

    Gotchas

    Both ends start DOWN and without an address — creating and moving a veth wires nothing up by itself. You must ip link set … up each end and assign addresses before a single packet flows, which is the next lesson's job. A very common "my namespace can't reach anything" is simply an end left down.

    The @ifN suffix in ip link output is the kernel telling you the peer's interface index, and once the peer is in another namespace it shows as a bare index (@if5) because the name isn't resolvable from here. That's normal, not a fault — it's how you match the two ends of a cable that spans a namespace boundary, and it's exactly how you'll later pair a node-side vethXXXX with the eth0 inside a specific pod.

    Every pod is joined to its node by exactly one veth pair: eth0 inside the pod's namespace, and a host-side end (named vethXXXX) enslaved to the node's bridge or handed to a routing CNI. Finding which host veth belongs to a given pod — by matching the peer interface index you just saw — is a routine node-debugging step, and capturing on that specific veth is how you watch one pod's traffic in isolation. The "delete one end, both die" property is why a crashed pod's veth cleans itself up.

    Locating a real pod's veth peer on a live node is W4.3; the veth is built into the by-hand pod network in W4.2.

    Docs

    man 4 veth for the device itself, man 8 ip-link for add … type veth, set … netns, and reading the @peer notation. The peer-index trick (matching ends across namespaces) uses ip -br link and ethtool -S or reading /sys/class/net/*/iflink. No exam-docs page covers veth directly — it lives under the CNI implementation you'll meet in W4.

    B9.3

    A bridge is a virtual switch

    Why it matters

    A veth pair joins exactly two points, but a network needs many machines able to reach each other — and a cable can't do that. The device that connects many wires and forwards between them is a switch, and Linux has one in software: the bridge. It is what every pod on a bridge-style node plugs into, so building one by hand is building the centre of a node's network.

    The concept

    A bridge is a switch implemented in the kernel. You create one with ip link add br0 type bridge, then enslave interfaces to it with ip link set veth0 master br0 — "master" meaning the bridge is now in charge of that port. Once two or more veth host-ends are enslaved to the same bridge, it does exactly what the metal switch box under a desk does: it learns which MAC address (B8.2) it has seen on which port, records that in a forwarding table, and forwards each frame only out the port where its destination lives (flooding to all ports only when it hasn't learned the destination yet). This is the switchboard the room wires plug into.

    One extra move turns the switch into something more: give the bridge itself an IP address, and it stops being only a switch and becomes the gateway the attached namespaces route through. A bridge is allowed to have its own address because it is a real interface on the host as well as a switch for its ports; that dual role — switch for the pods, router-facing address for the host — is exactly how a node's pod bridge works. On a Kubernetes node with a bridge-style CNI this device really exists, usually named cni0 or docker0, and bridge link lists one port per running pod.

    veth0↘br0 (learns MAC→port, forwards)↙veth-blue
    Lab
    1. Create the bridge, bring it up, and enslave the host end of the veth from B9.2. bridge link then shows the veth as a port of the bridge. 
      multipass shell sandbox
sudo ip link add br0 type bridge
sudo ip link set br0 up
sudo ip link set veth0 up
sudo ip link set veth0 master br0        # enslave veth0 to br0
bridge link
      6: veth0@if6: ... master br0 state forwarding ...   ← veth0 is now a bridge port
    2. Read the bridge's learned forwarding database — the MAC-to-port table it builds automatically as frames arrive. It may be sparse until traffic flows (next lessons). 
      bridge fdb show br br0 | head -4          # forwarding database: which MAC on which port
ip -br link show master br0                 # every interface enslaved to br0
      52:54:00:aa:bb:cc dev veth0 ...           ← a learned MAC and the port it lives behind
veth0@if6  UP  ...                          ← ports enslaved to br0
    3. Confirm the bridge is itself an addressable interface on the host (it appears in ip addr), which is what lets it also be a gateway once you give it an IP in the next lesson. 
      ip -br addr show br0
      br0  UP     ← up, no address yet; B9.4 gives it 10.10.0.1/24 to make it the gateway
    Verify

    What does a bridge learn, and what does it do with what it learns? (It learns which MAC address is reachable on which port and records that in a forwarding database, then forwards each frame only out the port where its destination lives — flooding to all ports only for destinations it hasn't learned yet; it is a learning switch.) Then: what changes when you give the bridge an IP address? (It stops being only a switch and becomes a gateway — an interface the attached namespaces can route through — because a bridge is simultaneously a switch for its ports and a real, addressable interface on the host.)

    Gotchas

    An enslaved port's own IP address is ignored for bridging — the bridge switches at the MAC (link) layer, so addresses belong either on the bridge itself or on the far end of each veth, not on the host-side veth you enslaved. Putting an address on a bridged port is a classic confusion that appears to do nothing; move it to the bridge or the namespace end.

    Both the bridge and every enslaved port must be UP, and the port must be enslaved before traffic will forward through it. A bridge that is down, or a veth end left down, silently drops everything — and because there's no error, it reads as a higher-layer problem until you check bridge link and the interface flags. When a "pod" can't reach its neighbour, "is every port up and enslaved?" is the bridge-layer version of B8's link rung.

    On a node running a bridge-mode CNI (flannel's default, Docker's docker0, kindnet), this exact device is the heart of pod networking: every pod's host-side veth is enslaved to it, the bridge holds the gateway address the pods route through, and bridge link on the node lists one port per pod. When you later debug "pods on this node can't reach each other," you'll check the very things you just built — is the bridge up, are the veths enslaved, is the forwarding database learning the pods' MACs.

    The node's pod bridge is inspected in flannel's moving parts (W4.6) and built by hand in W4.2.

    Docs

    man 8 ip-link for add … type bridge and set … master; man 8 bridge for bridge link (ports), bridge fdb (the learned MAC table) and per-port options. Kernel bridging behaviour and options live under Documentation/networking/bridge.rst. In the exam docs this is assumed under cluster networking; the concept surfaces as "the CNI bridge" in flannel/kindnet discussions.

    B9.4

    Address the private network: subnet, gateway, route

    Why it matters

    You have wires and a switch, which move frames — but nothing can be reached until it has an address to aim at and a route to choose an exit. Assigning those is where a network stops being cabling and becomes usable. And the three decisions you make here — which subnet this network owns, which address each namespace gets, and which gateway it points at — are exactly the three a CNI plugin's IPAM makes for every pod it ever creates. Do it once by hand and "IP address management" loses its mystique.

    The concept

    Pick a subnet for the private network — say 10.10.0.0/24 (the CIDR math from B8.3: 256 addresses, .1–.254 usable). Then make three assignments:

    • The bridge gets the gateway address: 10.10.0.1/24. By convention the first usable address is the gateway; giving it to the bridge makes the bridge the door out of this subnet.
    • Each namespace end gets an address in the subnet: red gets 10.10.0.2/24 on its veth1. This is the namespace's identity on the network.
    • Each namespace gets a default route via the gateway: ip route add default via 10.10.0.1 inside red. An address says "this is me"; a route says "to reach anything not on my own subnet, hand it to 10.10.0.1." Without the route, red can reach neighbours on 10.10.0.0/24 but has no idea how to reach anything else.

    Don't forget to bring every interface up — both veth ends and loopback inside the namespace. IPAM — the "IP address management" half of any CNI plugin — is nothing grander than keeping a record of which addresses in the chosen subnet are already handed out, so it never gives two pods the same one. You are being the IPAM here, by choosing .2 for red and remembering it's taken.

    br0 = 10.10.0.1/24 (gateway)·red veth1 = 10.10.0.2/24·red default route via .1
    Lab
    1. Give the bridge the gateway address and bring it up — the door out of the subnet now has an address. 
      multipass shell sandbox
sudo ip addr add 10.10.0.1/24 dev br0
sudo ip link set br0 up
ip -br addr show br0
      br0  UP  10.10.0.1/24        ← the bridge is now the gateway for 10.10.0.0/24
    2. Inside red: bring loopback and the veth end up, give the veth an address, and add the default route via the gateway. These four commands turn an empty namespace into a reachable host. 
      sudo ip netns exec red ip link set lo up
sudo ip netns exec red ip link set veth1 up
sudo ip netns exec red ip addr add 10.10.0.2/24 dev veth1
sudo ip netns exec red ip route add default via 10.10.0.1
      # no output on success — verify in the next step
    3. Prove red can now reach its gateway: ping the bridge address from inside the namespace. This confirms address + route + the veth-to-bridge path all work. 
      sudo ip netns exec red ip route            # red's routing table: local subnet + default
sudo ip netns exec red ping -c2 10.10.0.1  # can red reach the gateway?
      default via 10.10.0.1 dev veth1               ← the default route
10.10.0.0/24 dev veth1 proto kernel scope link src 10.10.0.2   ← the on-link subnet
64 bytes from 10.10.0.1: icmp_seq=1 ttl=64 time=0.05 ms        ← red reaches the gateway ✓
    Verify

    What three assignments turn the wired-up namespace into a reachable host, and which CNI job do they mirror? (Give the bridge the gateway address, give the namespace an address in the subnet, and give the namespace a default route via the gateway — the three IPAM decisions a CNI makes per pod: which subnet, which address, which gateway.) Then: with an address but no default route, what can the namespace reach and what can't it? (Only hosts on its own subnet — those are directly on-link; anything off the subnet has no route, so it fails with "Network is unreachable" until a default route points at the gateway.)

    Gotchas

    Forgetting ip link set lo up inside the namespace is the quiet killer: local-only services and anything that talks to 127.0.0.1 break even though your external addressing is perfect. Loopback is per-namespace and starts down (B9.1) — bring it up as reflexively as you bring up the veth.

    Put the address on the bridge, not on the host-side veth you enslaved to it — a bridged port's address is ignored (B9.3). And the mask must match on both ends: give the bridge a /24 and the namespace a /25 and you've recreated B8's wrong-netmask fault, where one side thinks the other is on a different subnet and won't ARP for it. Keep the prefix length identical across everything on the same subnet.

    These three assignments are literally what a CNI plugin does when a pod is created: it picks the node's pod-CIDR slice, allocates the next free address in it for this pod (IPAM), sets the pod's eth0 to that address, and installs a default route pointing at the node's bridge or gateway. The "which addresses are taken" bookkeeping you did in your head is the IPAM state a CNI persists on disk. When a pod comes up with no IP or no route, this is the step that failed.

    The three CIDRs a cluster juggles (pod, service, node) and where each is set are W4.4; the CNI contract that automates this addressing is W4.5.

    Docs

    man 8 ip-address (add/del, prefix lengths), man 8 ip-route (add default via, reading the table), man 8 ip-link (set … up). For the CIDR arithmetic behind your subnet choice, re-read B8.3. In the exam docs, pod/service CIDRs appear in the kubeadm ClusterConfiguration and the CNI's own config.

    B9.5

    Connect two namespaces and prove the path at two points

    Why it matters

    A single namespace on a bridge is inert. The payoff is two namespaces that can talk — the smallest real network — and, more valuable still, the technique you use to prove it: capturing the same packet at two points on its path. That "watch it at hop 1, then at hop 2" habit is the one the rest of this module leans on entirely. When a packet appears at one point and not the next, you have localised the fault to a single device without a single guess — which is exactly how you'll later discover whether a pod's traffic died inside the pod, on the bridge, or in a NAT rule.

    The concept

    Add a second namespace, blue, the same way you built red: a veth pair, one end moved into blue, the host end enslaved to br0, an address (10.10.0.3/24) and a default route inside. Now both namespaces hang off the same bridge, on the same subnet, so blue can ping red: the ICMP echo leaves blue's veth, crosses the bridge (which forwards it to red's port after ARP resolves red's MAC), and arrives at red's veth. A reply retraces the path.

    The skill to build is capturing at two points at once. Run one tcpdump on the bridge (br0, on the host) and another on the veth inside red, then ping from blue. The same echo request should appear in both captures — proof the packet reached the bridge and was delivered into red. If it showed up on the bridge but never inside red, the fault is between them (a down port, an unenslaved veth); if it never reached the bridge, the fault is on blue's side. Two capture points turn "it doesn't work" into "it fails here."

    blue veth→br0 (capture 1)→red veth (capture 2)· same packet at both = path proven
    Lab
    1. Build blue exactly as you built red: namespace, veth pair, one end inside, host end on the bridge, address, routes, everything up. 
      multipass shell sandbox
sudo ip netns add blue
sudo ip link add vethb0 type veth peer name vethb1
sudo ip link set vethb1 netns blue
sudo ip link set vethb0 up && sudo ip link set vethb0 master br0
sudo ip netns exec blue sh -c '
  ip link set lo up; ip link set vethb1 up
  ip addr add 10.10.0.3/24 dev vethb1
  ip route add default via 10.10.0.1'
      # no output on success
    2. Prove the two namespaces can talk: ping red (10.10.0.2) from inside blue. The reply confirms the bridge forwarded frames both ways. 
      sudo ip netns exec blue ping -c2 10.10.0.2
      64 bytes from 10.10.0.2: icmp_seq=1 ttl=64 time=0.06 ms   ← blue → bridge → red → back ✓
2 packets transmitted, 2 received, 0% packet loss

    Why capture the same packet at two points instead of one? (Because the point where the packet is present and the next point where it's absent bracket the failing device — it localises a fault to one hop with evidence instead of a guess.) Then: an echo request appears on br0 but never inside red — what does that tell you, and where is the fault? (The bridge received it but didn't deliver it into red, so the fault is between them — red's host-side veth not enslaved or down, or the wrong port — not on blue's side and not addressing.)

    Gotchas

    The very first ping between the namespaces may show a brief delay or a single dropped packet while ARP resolves the peer's MAC (B8.2) — that's the neighbour lookup happening, not a fault.     Capturing inside a namespace needs the capture to run in that namespace: ip netns exec red tcpdump …, not a plain tcpdump on the host, which can't see the namespace's private interfaces. This is the same "where does this traffic actually flow, and from which vantage point can I see it?" discipline from B8's interface-choice lesson — in a namespaced world you must also choose the right namespace to watch from.

    Two pods on one node talking to each other is exactly this: two namespaces, two veths, one bridge, ARP then ICMP/TCP across it. And the two-point-capture technique is the CNI-debugging method — when pod-to-pod traffic vanishes, you capture on the source pod's veth, then the node bridge, then the destination pod's veth, and the first hop where the packet stops appearing is the broken device. You just practised the single most useful skill for diagnosing a cluster's data plane, on a network small enough to hold in your head.

    Breaking the CNI and reading the signatures by capturing at each hop is W4.8; the by-hand pod network these two namespaces model is W4.2.

    B9.6

    Turn the host into a router: ip_forward

    Why it matters

    Your two namespaces reach each other and the bridge, but not the internet — and the reason is one switch that is off by default. An ordinary computer is a host: it deals with traffic addressed to itself and refuses to be a middleman. Anything running containers must instead be a router, passing traffic between its pods and the outside world. Flipping that one setting is why it appears in every Kubernetes install guide, and forgetting it produces one of the most common "pods can talk to each other but not to anything beyond the node" mysteries.

    The concept

    By default the Linux kernel treats itself as a host, controlled by the sysctl net.ipv4.ip_forward, which starts at 0. With forwarding off, the kernel accepts packets whose destination is one of its own addresses and silently drops any packet that arrived for somewhere else — it will not pass a packet from one interface out another. That is the right default for a laptop and the wrong one for anything hosting namespaces, because forwarding between a private veth and the uplink is the whole job.

    Set net.ipv4.ip_forward=1 and the kernel becomes a router: a packet arriving on one interface, addressed to somewhere the kernel has a route to, gets forwarded out the appropriate interface toward its destination. In plain terms, "this packet isn't for me, but I know a next hop, so I'll pass it along" — the defining behaviour of a router. This alone still isn't enough for the private subnet to reach the internet (the replies have nowhere to come back to until you add NAT in B9.8), but it is the necessary first half: without forwarding, the packet never even leaves the box.

    ip_forward=0· packet not for me → dropped ·ip_forward=1· packet not for me → forwarded on
    Lab
    1. Read the current setting — 0 on a stock VM — and watch what happens with forwarding off: a ping from red to the internet produces nothing leaving the uplink, because the host drops the forwarded packet. 
      multipass shell sandbox

    What does the kernel do, by default, with a packet whose destination is not one of its own addresses, and what does ip_forward=1 change? (By default it silently drops such a packet — it is a host, not a router; setting ip_forward=1 makes it forward the packet out the interface toward the destination, i.e. behave as a router.) Then: after enabling forwarding, a ping from the private namespace to 1.1.1.1 now leaves the uplink but still gets no reply — why? (The packet still carries its private source address 10.10.0.2, which the internet has no route back to; forwarding delivers it outward, but only NAT — next lessons — rewrites the source so a reply can return.)

    Gotchas

    sysctl -w changes are lost at reboot; the durable form is a file in /etc/sysctl.d/ (or an entry in /etc/sysctl.conf) applied by sysctl --system. On real nodes the CNI or the install steps drop exactly such a file, which is why the setting "just persists" on a working cluster — but a hand-set node that reverts after a reboot and stops routing pod traffic is a real incident. Set it the durable way anywhere it matters.

    There are also per-interface forwarding knobs (net.ipv4.conf.<iface>.forwarding) and the global one interacts with them; for IPv6 the equivalent is net.ipv6.conf.all.forwarding. And forwarding being on doesn't override a restrictive FORWARD firewall chain — on a hardened host you also need a rule permitting the forwarded traffic (B9.11). On the stock sandbox the FORWARD policy is ACCEPT, so forwarding alone is enough here.

    net.ipv4.ip_forward=1 is set on every Kubernetes node, by the same reasoning: a node forwards traffic between pod veths and between pods and the outside world, so it is a router whether or not anyone calls it one. The CNI plugins and kubeadm preflight expect it; when it's missing the signature is unmistakable — pods reach other pods on the same node's bridge (that's switching, not routing) but nothing off-node and nothing on the internet. It's one of the first things a node-networking checklist verifies.

    The datapath families that all assume a forwarding node are W4.7; broken-CNI signatures (including forwarding/routing faults) are W4.8.

    B9.7

    The three NAT flavours, by what they rewrite

    Why it matters

    Forwarding gets a packet toward the internet, but a packet whose source is a private address (10.10.0.2) can never receive a reply — no one out there has a route back to private space. The fix is address translation, and there are exactly three flavours of it. They sound interchangeable until you learn them by the one thing that distinguishes them: what each rewrites and when. Once you can name which rewrite is supposed to be happening, "the packet arrived carrying an address I didn't expect" stops being a mystery and becomes a specific question about a specific rule — which is most of NAT debugging.

    The concept

    NAT (Network Address Translation) is a router rewriting addresses in a packet as it passes through. The three flavours, by what and when they rewrite:

    • SNAT (source NAT) — rewrite the source address on the way out, to a fixed IP you name. Use it when your router has a known, stable public address. The reply comes back to that address and the router reverses the swap.
    • MASQUERADE — SNAT that uses whatever address the outgoing interface currently has, looked up automatically, instead of a hardcoded one. Slightly more work per packet, but it "just works" on links whose address is dynamic (DHCP, a cloud VM). It's the source-NAT you reach for when you don't want to name the IP.
    • DNAT (destination NAT) — rewrite the destination address (and often port) on the way in. Use it to publish an internal service on an external address/port (port forwarding), or to make a single virtual address stand in for a real backend.

    These map onto where they can run, which you'll formalise in B9.10: source rewriting happens last, in the POSTROUTING hook (after the routing decision, on the way out); destination rewriting happens first, in the PREROUTING hook (before routing, so the kernel routes on the new destination). The single most useful thing to hold onto: everything in a cluster's data path is one of these three. Pods reaching the internet is MASQUERADE; a Service's ClusterIP becoming a real pod IP is DNAT; a NodePort turning an inbound host-port hit into a pod is DNAT. Name the rewrite and you've named the mechanism.

    SNAT — src, out, fixed IP·MASQUERADE — src, out, iface's IP·DNAT — dst, in

    Gotchas

    MASQUERADE vs SNAT is a real trade-off, not a style choice: MASQUERADE looks up the interface's address for every new flow (cheap enough, but non-zero) and, usefully, drops its conntrack entries when the interface goes down so stale translations to an old address don't linger — which is exactly why it suits dynamic uplinks. Plain SNAT to a fixed address is marginally faster and correct when the address never changes. Prefer MASQUERADE when the uplink IP can change; prefer SNAT when it's pinned and you want the tiny efficiency.

    DNAT has to happen before the routing decision, which is why it lives in PREROUTING: the kernel must see the rewritten destination in order to route the packet to the right place. A DNAT rule placed in the wrong chain (say POSTROUTING, after routing) simply never does anything useful, and the counter stays at zero — a mistake you'll deliberately reproduce in the B9.20 drill. The direction/chain pairing isn't arbitrary; it's forced by when the rewrite has to take effect.

    kube-proxy's entire job is writing these three rewrites. Pod-to-external traffic is MASQUERADE'd (so the reply returns to the node, which un-NATs it back to the pod). A Service's ClusterIP — an address that exists on no interface anywhere — is made real purely by DNAT rules that rewrite it to a chosen pod IP. A NodePort is DNAT applied to an inbound host port. When you read the KUBE- chains in W4, every line is one of the three flavours you just named, and knowing which rewrite should occur is how you spot the one that isn't.

    The ClusterIP-as-DNAT idea is W4.9; walking the actual kube-proxy chains is W4.10.

    B9.8

    Give the private subnet real internet access

    Why it matters

    This is the moment the hand-built network stops being a toy: one rule, and namespaces you conjured from nothing can reach the actual internet. It's also the clearest possible demonstration of what NAT does, because removing that single rule produces an unforgettable signature — requests still leave the box, but replies never come back. Watching that happen fuses "forwarding" and "translation" into one working mental model.

    The concept

    You already have the two prerequisites: forwarding on (B9.6) so the host passes the packet along, and the vocabulary of MASQUERADE (B9.7). Now add exactly one rule to the nat table's POSTROUTING chain: for traffic from 10.10.0.0/24 leaving via the uplink ens3, masquerade the source. With it in place, a ping from red to 1.1.1.1 leaves the box with the host's public source address; the reply comes back to the host; and conntrack (B9.9) reverses the translation, delivering the reply back to 10.10.0.2. From inside the namespace it simply looks like the internet works.

    Remove the rule and the failure is precise and instructive: forwarding is still on, so the request still leaves ens3 — but now carrying its private source 10.10.0.2, an address no router on the internet has a route back to, so the reply is dropped somewhere out there and never returns. "Requests leave, replies never arrive" is the exact signature of missing (or wrong) source NAT, and you'll recognise it for the rest of your career. The rule doesn't help the packet get out — forwarding does that — it makes the packet's source answerable.

    red 10.10.0.2 → 1.1.1.1→ MASQUERADE →src rewritten to host's public IP→ reply returns, conntrack un-NATs it
    Lab
    1. Add the masquerade rule and confirm the private namespace now reaches the internet. (Ensure ip_forward=1 from B9.6 is still set.) 
      multipass shell sandbox

    What does the masquerade rule rewrite, and on which packets? (The source address of traffic from 10.10.0.0/24 leaving via ens3 — it swaps the private source for the uplink interface's own address, so replies can find their way back.) Then: with the rule removed but forwarding still on, why do requests still leave while replies stop arriving? (Forwarding delivers the request out the uplink, but it now carries the private source 10.10.0.2, which no internet router can route a reply back to — so the request goes and the reply is lost: the exact signature of missing source NAT.)

    Gotchas

    The rule works on sandbox because the FORWARD chain's policy is ACCEPT — the packet is both forwarded and NAT'd. On a host with a restrictive FORWARD policy (common on anything hardened) you'd also need explicit filter rules permitting the forwarded traffic in both directions, or the NAT rule appears not to work even though it's correct. NAT and filtering are separate tables doing separate jobs (B9.12); a masquerade rule never grants passage a filter rule denies.

    Scope the rule with both -s (the private subnet) and -o (the uplink) so you masquerade only the traffic you mean to. A too-broad MASQUERADE (no source or interface match) will also rewrite traffic that shouldn't be touched — including, on a real node, traffic between pods that needs to keep its real source for NetworkPolicy and logging. "Masquerade only what's actually leaving to somewhere that needs it" is the same principle behind a cluster's carefully-scoped masq rules.

    This one rule is pod egress. When a pod talks to something outside the cluster, its packet is MASQUERADE'd to the node's address so the external service can reply to the node, which un-NATs it back to the pod — exactly what you just built. CNIs and the optional ip-masq-agent install precisely-scoped masquerade rules that rewrite pod-to-external traffic but deliberately skip pod-to-pod and pod-to-service traffic (which must keep real addresses). The "requests leave, replies don't" signature you produced is a real cluster symptom of a missing or misscoped egress masquerade.

    Pod egress masquerade and the ClusterIP datapath are W4.9; the datapath families that shape where masquerade is needed are W4.7.

    B9.9

    Why NAT needs a memory: conntrack

    Why it matters

    The masquerade rule in B9.8 rewrote the outgoing source — but something had to remember that rewrite in order to reverse it on the reply, or the answer would arrive at the host addressed to the host and never find its way back to red. That memory is conntrack, and it's not a background detail: two of its properties cause real, confusing outages in clusters, and both become obvious once you've watched the table fill and empty by hand.

    The concept

    conntrack (connection tracking) is the kernel keeping a record of every flow passing through it — identified by the 4-tuple from B8.10 (source IP, source port, dest IP, dest port), together with any NAT translation applied. When the masqueraded request goes out, conntrack logs "flow from 10.10.0.2:x to 1.1.1.1, source rewritten to 10.191.62.10:y"; when the reply arrives for 10.191.62.10:y, conntrack finds that record and reverses the translation, delivering it back to 10.10.0.2:x. This is the switchboard's log of calls currently in progress — without it, NAT could translate outgoing packets but could never match the returns. You watch it with conntrack -L.

    Two consequences bite for real, and both are worth committing to memory:

    • A rule changed mid-flow does nothing to flows already in the table. Once a connection is tracked, its packets follow the recorded state, not the current rules. So a NAT/DNAT rule you fix appears not to work — until you retry with a fresh connection, which creates a new conntrack entry that sees the new rule. (This is a whole debugging drill in B9.20.)
    • The table is finite. It has a maximum size (net.netfilter.nf_conntrack_max); a machine under heavy connection churn can fill it and then logs nf_conntrack: table full, dropping packet and drops traffic that every rule says should pass. A NAT box that mysteriously drops connections under load is very often a full conntrack table.
    request out: log flow + NAT→conntrack table (the switchboard log)→reply in: match & un-NAT

    Verify

    What does conntrack store, and why can NAT not work without it? (It stores every flow's 4-tuple plus any NAT translation applied, so that when a reply arrives the kernel can match it to the outgoing flow and reverse the translation; without that memory the router could rewrite outbound packets but never map the replies back to the private origin.) Then: you fix a broken DNAT rule but the connection you already had open still misbehaves — why, and what makes it work? (The existing flow is pinned to its recorded conntrack state and ignores the new rule; a fresh connection creates a new entry that sees the corrected rule — so you retry, you don't wait.)

    Gotchas

    conntrack tracks UDP and even ICMP too, despite those being "connectionless" — it uses timeouts rather than handshake state to decide when a "flow" is over, which is why a DNS-heavy or ICMP-heavy load can still fill the table. Each protocol has its own idle timeout (short for UDP, long for established TCP), tunable via the nf_conntrack_*_timeout_* sysctls. So "connectionless" at the protocol layer doesn't mean "untracked" at the NAT layer.

    The "table full" failure is nasty precisely because it's load-dependent and rule-independent: every firewall rule says the traffic should pass, packets are being dropped anyway, and the only evidence is the kernel log line and a count pinned near max. When a busy NAT box or node drops a fraction of connections under load with no rule explaining it, check nf_conntrack_count against nf_conntrack_max before anything else — it's a five-second check that saves hours.

    conntrack is load-bearing for kube-proxy: every Service connection is a DNAT'd flow whose return path depends on a conntrack entry, and the entry is what pins a given client connection to the one backend pod it was first balanced to (so a long-lived connection keeps hitting the same pod). Two famous cluster incidents follow directly: nodes under heavy connection churn hitting nf_conntrack: table full and dropping traffic (the fix is raising nf_conntrack_max), and a stale conntrack entry still steering traffic to a pod that has already been deleted — which is why kube-proxy actively deletes conntrack entries when endpoints change, and why "flush conntrack" is a real remediation. You reproduce that stale-entry fault in B9.20.

    The conntrack-backed ClusterIP datapath is W4.9; endpoint readiness deciding which backends conntrack may pin to is W4.11.

    Netfilter

    B9.10

    Where a packet can be caught: the netfilter hooks

    Why it matters

    Nearly every "my firewall rule does nothing" is the same mistake: the rule is placed where the packet never goes. The Linux packet-filtering framework, netfilter, intercepts packets at exactly five points in the kernel, and each rule is attached to one of them. Learn the five points and the two paths a packet can take through them, and rules stop being voodoo you tweak until something works — you place each rule where its packets actually pass, deliberately.

    The concept

    netfilter is a set of hooks — fixed points in the kernel's packet path where rules can inspect or modify a packet. There are five:

    • prerouting — the packet has just arrived, before the kernel decides where it's going.
    • input — the routing decision said "this is for me," on its way up to a local process.
    • forward — the routing decision said "this is for somewhere else," passing through this box.
    • output — a locally-generated packet, on its way down and out.
    • postrouting — any packet about to leave on the wire, after routing.

    The crucial thing is where the routing decision sits: right after prerouting. That single fork produces the two paths you must be able to draw:

    • To this host: prerouting → (routing: for me) → input → local process.
    • Through this host: prerouting → (routing: for elsewhere) → forward → postrouting → out.

    Two payoffs follow. First, it explains the NAT placement from B9.7: DNAT must run in prerouting because it changes the destination, and the change has to happen before the routing decision so the kernel routes on the new address; SNAT runs in postrouting, after routing, on the way out. Second, and the one that fixes most mistakes: traffic destined for a container is forwarded, so it traverses forward and never touches input. A rule you put in the input chain to affect pod traffic is inspected by no packet you care about — the packets took the through-this-host path and skipped input entirely.

    prerouting→ route? →input (for me)/forward (through me)→ postrouting → out
    Lab
    1. See the base chains and which hook each is attached to. In nftables a chain names its hook directly, which makes the mapping explicit.

    Draw the two paths a packet can take through the hooks. (To this host: prerouting → input → local process. (DNAT changes the destination, which must happen before routing so the kernel routes on the new address; forwarded traffic goes prerouting → forward → postrouting and never enters input, so an input rule inspects none of it.)

    Gotchas

    The single most common wasted hour in firewalling is a correct-looking rule in the wrong chain — usually input when the traffic is forwarded, or forward when the traffic is actually terminating locally. Before writing any rule, ask "is this packet for this host, or passing through it?" and pick the chain from the answer. The counters trick in the lab (add a bare counter to a chain, generate traffic, see if it moves) is the fastest way to confirm which chain a given packet actually traverses.

    Priorities matter when multiple base chains share a hook: NAT, filter and mangle can all attach to prerouting, and they run in priority order (DNAT at a negative priority runs before filtering, for instance). You rarely set priorities by hand, but it's why several tools' rules coexist on one hook without a fight — and why kube-proxy, a CNI, and your own rules can all live on prerouting at once.

    This is why a rule meant to affect pod traffic must live in forward, prerouting or postrouting, never input — pod traffic is routed through the node, not to it. kube-proxy hangs its Service machinery off prerouting (and output, for traffic a pod sends to a Service on its own node) precisely because DNAT must precede routing; NetworkPolicy enforcement lives in forward. When you later read where the KUBE- chains attach, the hook each uses is dictated by exactly the routing-decision placement you just drew.

    B9.11

    The vocabulary under every Linux firewall: tables, chains, rules, targets

    Why it matters

    Every firewall command on Linux — every iptables line, every nft statement, every one of the thousands of rules kube-proxy writes — is built from four nested pieces. Learn those four words precisely and a wall of rules that looked like line noise resolves into "which job, at which hook, matching what, doing what." It's the grammar; once you have it, you can read anyone's ruleset, including Kubernetes'.

    The concept

    From outside in:

    • Table — which job. filter decides pass-or-drop; nat rewrites addresses; mangle edits other packet fields; raw opts flows out of connection tracking. A rule lives in exactly one table, chosen by what it's for.
    • Chain — which hook. A chain is a list of rules attached to one of the five hooks from B9.10 (a built-in chain like PREROUTING), or a user-defined chain you jump to (a labelled subroutine).
    • Rule — the match criteria. The conditions a packet must meet: -p tcp --dport 80, -s 10.10.0.0/24, -i ens3, and so on. A rule with no match conditions matches every packet.
    • Target — what to do when the rule matches: ACCEPT (let it pass), DROP (discard silently), REJECT (discard with an error back to the sender), MASQUERADE/DNAT/SNAT (the rewrites from B9.7), or a jump to another chain (hand the packet to a subroutine of more rules).

    So a rule reads as: in this table, on this chain, packets matching this get this target. iptables -t nat -A POSTROUTING -s 10.10.0.0/24 -o ens3 -j MASQUERADE is table nat, chain POSTROUTING, match "from that subnet leaving that interface," target MASQUERADE — the exact rule from B9.8, now fully parsed. Targets that terminate (ACCEPT/DROP/REJECT) stop the packet's traversal of the chain; a jump is non-terminating in the sense that if the jumped-to chain doesn't decide the packet's fate, traversal returns to the next rule after the jump. This jump-to-a-chain mechanism is how big rulesets stay organised — and how kube-proxy builds its per-Service and per-endpoint chains.

    table (job)→chain (hook)→rule (match)→target (action)

    Define table, chain, rule and target in one phrase each. (Table = which job — filter/nat/mangle/raw; chain = which hook, or a user subroutine; rule = the match criteria; target = the action on a match — ACCEPT/DROP/REJECT/a rewrite/or a jump to another chain.) Then: which table decides whether a packet is allowed through, and which rewrites its addresses? (The filter table decides pass-or-drop; the nat table rewrites addresses — they are separate jobs, which is the whole point of B9.12.)

    Gotchas

    Every built-in chain has a default policy (ACCEPT or DROP) that applies to any packet no rule in the chain decided — the implicit last word. On many hosts the filter INPUT/FORWARD policy is DROP, so "I added an ACCEPT and it still doesn't work" can be a different chain's policy dropping the return traffic, or the packet never reaching your ACCEPT. Always check the policy (shown in the Chain … (policy DROP) header) alongside the rules.

    -A appends a rule to the end of a chain and -I inserts at the top (or a chosen position). Because order decides which rule matches first (B9.14), appending a rule after an existing terminating rule can leave it permanently unreached. When a freshly-added rule seems to do nothing, its position — not its correctness — is the first suspect.

    kube-proxy's iptables output is nothing but this vocabulary at scale: a top-level KUBE-SERVICES chain (in the nat table) that jumps to a per-Service KUBE-SVC-xxxx chain, which jumps to per-endpoint KUBE-SEP-xxxx chains that carry the DNAT targets. Every line is table + chain + match + target, and the jump-to-a-chain mechanism you just used by hand is exactly how it organises hundreds of Services without one unreadable flat list. Reading those chains is just applying this grammar.

    Walking the real KUBE-SERVICES → KUBE-SVC → KUBE-SEP chain structure is W4.10; the ClusterIP DNAT those chains carry is W4.9.

    B9.12

    filter vs nat: "ping works but curl doesn't"

    Why it matters

    This is the single most useful firewall symptom to recognise on sight, and it trips people constantly: a host answers ping but a curl to it hangs. It looks like a contradiction — how can the machine be reachable and unreachable at once? — but it's the ordinary behaviour of a filter rule that drops TCP while leaving ICMP alone. Reproduce it once, deliberately, and you'll never again mistake "ping works" for "the service is reachable." As a bonus you'll learn to read the timing of a failure to know which kind of block you're behind before you've read a single rule.

    The concept

    The filter table's job is pass-or-drop; the nat table's job is rewrite. They're independent, and a filter rule can target one protocol while ignoring another. ping uses ICMP; curl to a web server uses TCP to port 80. So a single rule — drop TCP to port 80 — silently eats the TCP SYN while ICMP echo sails through untouched. The host is genuinely reachable at the network layer (ping proves it) and genuinely blocked at the transport layer for that one service. "Ping works but curl doesn't" isn't a paradox; it's a precise statement that the network layer is fine and something is filtering that TCP port — exactly the layered thinking from B8.

    There's a second, equally useful reading in how the block refuses:

    • DROP discards the packet with no reply. The client hears nothing, so it waits out its full timeout and eventually gives up — the connection hangs, then fails after seconds.
    • REJECT discards but sends back an ICMP error (or a TCP reset). The client is told "no" immediately, so it fails instantly.

    The timing therefore diagnoses the block before you read any rule: a hang means a DROP (or a black hole) is silently eating packets; an instant failure means something actively refused. And this exact reading carries into Kubernetes: a NetworkPolicy denies by dropping, so blocked traffic hangs; a Service with no ready endpoints (or a closed port) refuses with a reset, so it fails instantly. Same two signatures, one level up.

    DROP → client hears nothing → hangs, then times out·REJECT → error returned → fails instantly
    Lab
    1. Stand up a web server and confirm both ping and curl to it work — the healthy baseline. 
      multipass shell sandbox

curl -s -o /dev/null -w 'curl: %{http_code}\n' -m3 http://127.0.0.1
      ping: ok
curl: 200            ← both work: network layer and the TCP service are fine
    2. Add a filter rule that DROPs TCP to port 80. Now ping still works, but curl hangs until its timeout — the classic split, with the tell-tale delay. 
      sudo iptables -I INPUT -p tcp --dport 80 -j DROP
ping -c1 127.0.0.1 >/dev/null && echo 'ping: still ok'
time curl -s -o /dev/null -m3 http://127.0.0.1; echo "curl exit=$?"
      ping: still ok                          ← ICMP untouched: network layer fine
curl exit=28                            ← exit 28 = timeout; and 'time' shows it took ~3s: a DROP
real  0m3.0s                            ← it HUNG for the full timeout — the DROP signature
    3. Swap DROP for REJECT and watch the same curl now fail instantly — the timing alone tells you the block changed from silent to active. Then remove the rule. 
      sudo iptables -D INPUT -p tcp --dport 80 -j DROP
sudo iptables -I INPUT -p tcp --dport 80 -j REJECT
time curl -s -o /dev/null -m3 http://127.0.0.1; echo "curl exit=$?"
sudo iptables -D INPUT -p tcp --dport 80 -j REJECT      # remove; kill the server: kill %1
      curl exit=7                             ← exit 7 = connection refused, returned immediately
real  0m0.0s                            ← instant: the REJECT signature (contrast the 3s DROP)
    Verify

    Why can ping succeed to a host while curl to it fails? (ping is ICMP and curl is TCP to a port; a filter rule dropping that TCP port blocks the service while leaving ICMP untouched — the network layer is fine, one transport-layer service is filtered.) Then: a connection hangs for several seconds and then fails, versus one that fails instantly — which block is each, and what are the Kubernetes analogues? (Hang = DROP/black hole silently eating packets ≈ a NetworkPolicy deny; instant = REJECT/reset actively refusing ≈ a Service with no ready endpoints or a closed port.)

    Gotchas

    Because "ping works" only proves the network layer, never conclude a service is reachable from a successful ping — it's the most common false-positive in network debugging. Test the actual port with curl, nc -vz host port, or ss, not with ping. Conversely, ping failing is weak evidence too, since many hosts drop ICMP by policy while serving TCP fine. Ping tells you about ICMP and the network layer, and nothing more — that's the whole B8 lesson, and this symptom is its sharpest edge.

    The DROP-hangs / REJECT-instant timing is reliable but has one caveat: a hang can also be a routing black hole or an MTU problem (B8.18), not only a DROP — so "it hangs" narrows it to "something is silently eating packets," of which a filter DROP is the most common but not the only cause. Pair the timing read with a quick rule check (iptables -L -n -v, next lesson) to confirm which silent eater you've got.

    This timing read is a daily Kubernetes diagnostic. A pod-to-Service call that hangs and then times out points at a NetworkPolicy dropping the traffic (deny = DROP) or a black-holed route; a call that's refused instantly points at a Service with no ready endpoints, the wrong targetPort, or an app that isn't listening (all of which yield a reset). Before reading a single YAML, the failure's timing has already halved your search space — the exact habit you just built with DROP vs REJECT.

    The default-deny/additive-allow NetworkPolicy model (which drops, hence hangs) is W4.23; the classic policies proven by observing this behaviour are W4.24.

    B9.13

    What's really running: nftables and iptables-nft

    Why it matters

    You've been typing iptables, but on Ubuntu 24.04 iptables is not the thing actually enforcing your rules — it's a compatibility front-end over a newer engine, nftables. That gap matters the moment something looks missing: rules can be present in one tool's view and invisible in another's, and a half-view will convince you a rule is absent when it's merely written in the other dialect. Knowing which tool is really running, and how to see the whole truth, saves you from chasing rules that were there all along.

    The concept

    Linux has two firewall engines. The old one, iptables-legacy, had its own in-kernel machinery. The modern one is nftables, a single unified engine. On 24.04 the iptables command is actually iptables-nft: it accepts the familiar iptables syntax but translates it into nftables rules underneath. So when you ran all the iptables commands in this module, nftables did the enforcing. You can confirm it: iptables -V prints (nf_tables), not (legacy).

    The practical consequence is that the same ruleset can be viewed two ways — the iptables-shaped view (iptables -t nat -L -n -v) and the native nftables view (nft list ruleset) — and they show the same underlying rules in different dialects. The nft view is the ground truth: it shows everything in the unified engine, including rules added by either front-end. This is why, when a rule seems to have vanished, nft list ruleset is the command that ends the argument — it can't be fooled by a front-end that only shows its own additions.

    iptables … (familiar syntax)→ iptables-nft translates →nftables engine (the real enforcer)· see the truth: nft list ruleset

    On Ubuntu 24.04, what is the iptables command really, and how do you confirm it?     Gotchas

    Both iptables-legacy and iptables-nft can exist on a system, selected via update-alternatives. If some tool wrote rules through the legacy path while you're viewing through nft (or vice-versa), each sees only its own — the textbook "the rule is definitely there / no it isn't" standoff. On a mixed host, check both (iptables-legacy -L and nft list ruleset) before concluding anything is missing. Modern distros standardise on nft, but you'll still meet legacy in older images and some appliances.

    Editing kube-proxy-style rulesets by hand is risky precisely because a front-end can't always represent everything the engine holds — a rule written natively in nft may show only partially through the iptables view, so an iptables-save/restore round-trip can silently lose it. For anything you'll modify, read and write in the same dialect, and treat nft list ruleset as the authoritative dump.

    Kubernetes lives in exactly this transition. kube-proxy's default mode still writes iptables-style rules, which — on a modern node — land in nftables underneath, which is why nft list ruleset on a Kubernetes node prints thousands of KUBE- chains even though kube-proxy "uses iptables." (There's also a newer native nftables mode for kube-proxy, GA since Kubernetes 1.33, but iptables remains the default mode, so most clusters you meet are the translated-through-nft case.) When you go hunting for a Service's rules on a node, knowing they may be visible only through the right dialect is what keeps you from concluding they're missing.

    Reading the actual KUBE- chains on a node — through whichever dialect shows them — is W4.10.

    B9.14

    Debug by rule order: first match wins, read the counters

    Why it matters

    Within a chain, rules are tried in order and the first match wins — so a perfectly correct rule can do nothing simply because an earlier rule already decided the packet's fate. This is the most common "but my rule is right!" failure, and it has a definitive cure: every rule carries packet counters, so you can stop arguing about which rule should match and measure which one actually does. Turning firewall debugging from theory into measurement is a skill that pays off the same way whether the chain has three rules or three thousand.

    The concept

    A chain is an ordered list. For each packet the kernel walks the rules top to bottom and applies the first whose match conditions fit; if that rule's target is terminating (ACCEPT/DROP/REJECT), traversal stops there and later rules never see the packet. So a later rule can be shadowed — permanently unreached — by a broader rule above it. Because -A appends to the end, a rule you add can easily land after a terminating rule that already catches its traffic, which is why "I added it and nothing changed" is so often an ordering problem, not a correctness one.

    The tool that ends the guessing is iptables -L -n -v (or -L -v --line-numbers): the -v adds two columns, packets and bytes, counting how many packets have hit each rule. Now you can see reality: generate traffic and watch which rule's counter climbs. A rule whose counter stays at zero while matching traffic is flowing is either shadowed by something above it or sitting in a chain that traffic never enters — a dead rule, proven dead by measurement. (iptables -Z zeroes the counters so you can attribute a fresh burst of traffic cleanly.)

    walk top→bottom· first match wins ·counter stays 0 = shadowed or wrong chain
    Lab
    1. Build a shadowing situation on a custom chain: a broad ACCEPT above a specific DROP, so the DROP can never be reached. 
      multipass shell sandbox
sudo iptables -N ORDER 2>/dev/null; sudo iptables -F ORDER
sudo iptables -A ORDER -p tcp -j ACCEPT               # broad: accept ALL tcp (rule 1)
sudo iptables -A ORDER -p tcp --dport 80 -j DROP      # specific: drop tcp/80 (rule 2, shadowed)
sudo iptables -A INPUT -p tcp --dport 80 -j ORDER     # send tcp/80 into ORDER
sudo iptables -Z ORDER                                 # zero counters for a clean read
      # rule 2 (DROP dport 80) sits BELOW rule 1 (ACCEPT all tcp): it can never match
    2. Generate traffic to port 80, then read the counters: the broad ACCEPT climbs, the specific DROP stays at zero — proof it's dead, not merely inactive. 
      python3 -m http.server 80 &>/dev/null & sleep 1
for i in 1 2 3; do curl -s -o /dev/null -m2 http://127.0.0.1; done
sudo iptables -L ORDER -n -v --line-numbers; kill %1 2>/dev/null
      num  pkts bytes target  ...
1    6    360   ACCEPT  tcp  --  ... 0.0.0.0/0                 ← this rule claimed every packet
2    0    0     DROP    tcp  --  ... tcp dpt:80                ← counter zero: shadowed, dead rule
    3. Fix it by order — insert the specific DROP above the broad ACCEPT — and watch the counters flip, confirming the DROP now claims the traffic. 
      sudo iptables -I ORDER 1 -p tcp --dport 80 -j DROP    # insert at the TOP now
sudo iptables -Z ORDER
python3 -m http.server 80 &>/dev/null & sleep 1
curl -s -o /dev/null -m2 http://127.0.0.1; echo "exit=$?"
sudo iptables -L ORDER -n -v --line-numbers | head -3; kill %1 2>/dev/null
sudo iptables -D INPUT -p tcp --dport 80 -j ORDER; sudo iptables -F ORDER; sudo iptables -X ORDER
      exit=28                                              ← now the DROP takes effect (curl times out)
1    1  60  DROP  tcp  --  ... tcp dpt:80             ← the DROP's counter now moves: it's live
    Verify

    Within a chain, which rule decides a packet's fate, and what does that imply about a rule added with -A? (The first rule whose match fits, walking top to bottom — so a rule appended after an existing terminating rule that already catches the traffic is shadowed and never reached; order, not just correctness, decides.) Then: how do you prove a specific rule is dead rather than merely guessing? (List with counters — iptables -L -n -v — generate matching traffic, and if the rule's packet counter stays at zero while traffic flows, it's shadowed or in a chain the traffic never enters: dead, by measurement.)

    Gotchas

    Not every target is terminating: LOG and a bare counter (and returning from a jumped-to user chain without a verdict) let traversal continue to the next rule, so a packet can hit several non-terminating rules before a terminating one decides it. When reading counters, remember that a climbing counter on a LOG rule doesn't mean the packet stopped there — it logged and moved on. Only ACCEPT/DROP/REJECT (and a jump whose chain decides) end the walk.

    Counters are cumulative since the last zero (-Z) or since boot, so a non-zero counter might be old traffic. For a clean experiment, -Z the chain, generate a known burst, and read — attributing exactly that burst to the rule that caught it. This zero-then-measure discipline is what makes counter-reading trustworthy instead of "well, it's non-zero, so probably."

    Reading a kube-proxy chain is this skill at scale: the KUBE-SERVICES chain is walked top-down, and the rule that claims your packet is the first whose match (a Service's ClusterIP and port) fits — anything below it for that packet is irrelevant. When a Service isn't behaving, listing the relevant chain with counters shows whether packets are even reaching its rule or being claimed by something earlier, turning "why doesn't this Service work" into a measured walk down the chain. The first-match-wins instinct and the read-the-counters habit are exactly what that investigation needs.

    Walking the kube-proxy chains top-down (and reading which rule claims a packet) is W4.10.

    Load balancing and sockets

    B9.15

    A load balancer from two rules: DNAT + statistic

    Why it matters

    Here is the checkpoint where the module's payoff becomes undeniable: with two firewall rules you build a working round-robin load balancer, and it is not a model of how Kubernetes Services work — it is how they work, rule for rule. Understanding this once dissolves the mystery of the ClusterIP, an address that exists on no machine yet somehow answers. When you later see KUBE-SVC-* chains full of probability rules, you'll recognise the exact construction you built by hand.

    The concept

    A ClusterIP is a virtual address — it exists nowhere. No interface holds it, nothing answers ARP for it, no machine "is" it. The only thing that makes traffic to it work is a DNAT rule that rewrites its destination to a real backend address before the packet is routed. Load-balancing across several backends is just making that DNAT probabilistic: send a fraction of connections to backend A, the rest to backend B.

    You express the fraction with iptables' statistic match: -m statistic --mode random --probability 0.5 matches a random half of packets. So two rules balance two backends — "with probability 0.5, DNAT to A; otherwise (the fallthrough) DNAT to B." For more backends the probabilities are chained, not equal: with three backends the first rule uses 0.333 (1/3), the second 0.5 (half of the remaining two-thirds = 1/3), and the third catches the rest (1/3) — so the split comes out even. That chained-probability structure is exactly what you'll read inside a Kubernetes Service chain, because kube-proxy's iptables mode generates precisely these rules. Build it here and you've built kube-proxy's data path.

    virtual IP (exists nowhere)→ DNAT p=0.5 → backend A/else → backend B· conntrack pins each flow
    Lab

    What actually makes a ClusterIP work, given that no machine holds the address? (A DNAT rule that rewrites the virtual destination to a real backend address before routing — the address exists only as rewrite rules; nothing answers ARP for it.) Then: why are the probabilities chained (1/3, 1/2, 1) rather than equal for three backends? (Each rule's probability is applied only to the packets that fell through the rules above it, so 1/3 then 1/2-of-the-remaining-2/3 then all-the-rest yields an even one-third split — the exact structure in a KUBE-SVC chain.)

    Gotchas

    Once a connection is balanced to a backend, conntrack (B9.9) pins every subsequent packet of that connection to the same backend — the random choice happens once, at connection start, not per packet. That's essential (you can't have a single TCP connection's packets split across two servers) and it's why long-lived connections don't rebalance when backends change. It's also why testing with many separate curl calls shows the split, while one persistent connection would stick to one backend.

    Order and fallthrough matter: the last backend rule has no probability match — it's the unconditional catch-all for whatever the probabilistic rules didn't claim. Get the probabilities wrong (e.g. two rules both at 0.5 with no plain fallthrough) and the split skews or some connections match nothing. The chained-probability arithmetic is fiddly by hand, which is precisely why kube-proxy generates it for you — but knowing the pattern is what lets you read and trust the generated rules.

    This is kube-proxy's iptables mode, not an analogy for it. A Service's ClusterIP is an address on no interface; kube-proxy makes it work by writing a KUBE-SVC-xxxx chain whose rules use -m statistic --mode random --probability with exactly the chained fractions you just saw, each jumping to a KUBE-SEP-xxxx chain that DNATs to one pod's IP. conntrack pins each connection to its chosen pod. When you read those chains in W4, you're reading the two-rule construction from this lab, multiplied by the number of endpoints.

    The ClusterIP-as-rewrite-rules idea is W4.9; walking the real KUBE-SVC/KUBE-SEP chains that contain these probability rules is W4.10.

    B9.16

    Publish a private service on a host port

    Why it matters

    So far the private namespaces can reach out; now you make one reachable from outside the machine entirely — a real end-to-end publication, not a loopback trick. This one rule is a NodePort built by hand, and doing it yourself explains a fact that puzzles newcomers: why a NodePort works when you hit any node's IP, even a node that runs none of the Service's pods.

    The concept

    Publishing means: traffic arriving at the host's own address on some port should be redirected to a backend inside a private namespace. That's a DNAT in the PREROUTING chain — for TCP arriving on the host's port 8080, rewrite the destination to 10.10.0.2:80 — placed in prerouting (B9.10) because the rewrite must happen before routing so the kernel then forwards the packet to red. Because it's in prerouting rather than output, it catches traffic coming from other machines, which is what makes it a genuine external publication. The reply retraces the path: red answers toward the host (its gateway), conntrack un-DNATs it, and it returns to the external client looking as if the host itself served port 8080.

    Test it from outside the VM — from the machine running Multipass, hitting the VM's address on 8080 — so you prove the whole forward-and-rewrite path, not just a same-host shortcut. This is precisely a Kubernetes NodePort: the same rule shape, with the host port drawn from the 30000–32767 range and the DNAT jumping into the Service's balancing chain. And because the rule lives on every node (kube-proxy writes it everywhere), hitting any node's IP works even if that node hosts none of the pods — the DNAT there simply forwards the packet on to a node that does.

    external client → host:8080→ DNAT in prerouting →10.10.0.2:80 (inside red)→ forwarded, reply un-NAT'd back

    Which chain does the publish DNAT go in, and why there rather than OUTPUT?     Gotchas

    Publishing external traffic needs the rule in PREROUTING; publishing traffic the host itself originates (a curl from the VM to its own :8080) needs a matching rule in OUTPUT, because locally-generated packets skip prerouting (B9.10). This is exactly why kube-proxy installs its Service jumps in both chains — so a pod reaching a Service on its own node works the same as external traffic. If your publish works from outside but not from the host itself, the missing OUTPUT rule is why.

    Forwarding must be on (B9.6) and, on a hardened host, the FORWARD filter policy must permit the forwarded traffic — a correct DNAT with a blocking FORWARD policy publishes nothing. And "hairpin" cases (a backend reaching the service IP that maps back to itself) need source NAT too, or the reply's addresses won't match the request's flow — the same masquerade-on-the-way-in subtlety kube-proxy handles with its hairpin rules.

    This rule is a NodePort. type: NodePort makes kube-proxy write, on every node, a DNAT from a high port (30000–32767) into the Service's balancing chain — identical in shape to what you just built, just with the load-balancing step from B9.15 in the middle. The "any node's IP works" property, the both-chains (PREROUTING and OUTPUT) placement, and the forwarding requirement are all things you can now explain from first principles rather than accept as configuration.

    B9.17

    Unix domain sockets: endpoints in the filesystem

    Why it matters

    Not every conversation between programs goes over the network. When two processes on the same machine talk — a client to containerd, the kubelet to a CSI driver, almost anything to systemd — they usually use a unix domain socket: an endpoint that lives in the filesystem instead of on a port. Understanding these explains a large fraction of the plumbing on a Linux node, and it sets up the security fact in the next lesson — that access to the right socket file is equivalent to root.

    The concept

    A unix domain socket (UDS) is a communication endpoint identified by a filesystem path (like /run/containerd/containerd.sock) rather than by an IP address and port. No IP stack is involved at all: the kernel simply copies bytes between two processes on the same host. That makes it faster than a loopback TCP connection and — crucially — governed by ordinary file permissions on the socket path, not by firewall rules. If you can't read/write the socket file, you can't connect; the access model is the filesystem's, which you already know from B4.

    Three details complete the picture:

    • Stream vs datagram. A stream socket (SOCK_STREAM) is reliable and ordered, like TCP; a datagram socket (SOCK_DGRAM) is message-based, like UDP — the same two shapes as the network transports in B8, minus the network.
    • The abstract namespace. A UDS name can instead start with a NUL byte, giving it no file on disk at all — it's shown with a leading @ in tools. Abstract sockets have no filesystem permissions; their visibility is scoped to the network namespace instead (which matters for containers — an abstract socket doesn't cross a netns boundary).
    • Finding them. ss -lx lists listening unix sockets — you'll see the node's real machinery: systemd, D-Bus, journald, and any runtime.
    path-based UDS → file permissions gate it·@abstract UDS → no file, scoped to netns

Then: how does an abstract unix socket differ, and why does that matter for containers? (It has no file on disk — its name starts with a NUL byte (shown as @) — so it has no filesystem permissions and is instead scoped to the network namespace, which means it doesn't cross a container's netns boundary.)

    Gotchas

    Because a path socket is a file, a stale one left behind by a crashed server can block the next start with "address already in use" until it's removed — which is why daemons often unlink the path before binding. And the path has a surprisingly short length limit (~108 bytes on Linux), so deeply-nested socket paths can fail to bind for a reason that has nothing to do with permissions. Both are "it's a file" consequences that surprise people expecting network-socket behaviour.

    A server can go beyond file permissions and ask the kernel who is connected via SO_PEERCRED, which reveals the peer's uid/gid/pid — this is how privileged daemons authorise clients precisely (e.g. "only uid 0 may call this method"). So the security of a UDS is file permissions plus, optionally, peer-credential checks — but the file permissions are the first and most important gate, and the one you can see with ls -l.

    A huge amount of a node's control plane talks over unix sockets in /run precisely because they're local and file-permission-gated rather than network-exposed: the kubelet talks to the container runtime over /run/containerd/containerd.sock (the CRI socket), CSI drivers expose sockets the kubelet dials, and device plugins register the same way. "Where does the kubelet actually connect to containerd?" is answered by ss -lx, not ss -ltn — there's no port, just a socket file whose permissions are the entire access policy, which is the setup for the next lesson's security point.

    The kubelet → containerd → shim → runc path over the CRI socket is W1.20.

    B9.18

    Talk over a socket, and why containerd.sock is root

    Why it matters

    Send a message over a unix socket by hand, look at the socket's permissions, and one of the most important security facts in all of container infrastructure falls out on its own: access to the container runtime's socket is equivalent to root on the node. This isn't a rule to memorise — it's a conclusion you can derive, and deriving it is what makes "just mount the docker socket into the pod" recognisable as a full compromise rather than a convenience.

    The concept

    A unix socket is just an endpoint you can read from and write to, which you can prove with socat: one invocation listens on a socket path, another connects to it, and bytes flow between them. The socket file's mode — visible with ls -l as a leading s plus the usual rwx bits — is exactly what decides who may connect, no differently from any other file (B4).

    Now apply that reasoning to /run/containerd/containerd.sock. That socket is the container runtime's control interface: whoever can write to it can tell containerd to start a container — and they can ask for a container with the host's filesystem mounted inside it, running as root, with every capability granted and every namespace shared. In other words, anyone who can connect to that socket can obtain a fully-privileged shell on the host. Therefore write access to the runtime socket is equivalent to root on the node — the socket's permissions are the node's security boundary. This is the concrete reason that mounting the Docker/containerd socket into a pod (a depressingly common "just let CI build images" shortcut) hands that pod the entire node, and through it, frequently the whole cluster. It's also why B12 spends real time on trust boundaries: many of them come down to which processes can reach which socket.

    write to containerd.sock→ "run a container, host FS, privileged" →root on the node

    How does a unix socket decide who may connect, and how did you inspect it? Then: why is write access to containerd.sock equivalent to root on the node? (Because whoever can write to it can instruct the runtime to start a container with the host filesystem mounted, running privileged with all capabilities — i.e. obtain a root shell on the host — so the socket's permissions are the node's security boundary, and mounting it into a pod hands that pod the node.)

    Gotchas

    The danger isn't the socket file's path, it's write access to it — group membership counts. A socket that is root root mode 0660 is safe from ordinary users, but adding a user to the runtime's group (or the classic docker group) silently grants that user node-root-equivalent power without ever typing sudo. "Add me to the docker group so I don't need sudo" and "give me root" are, on a node, the same request — a fact worth stating plainly to anyone who asks for the former.

    The same logic extends to any privileged socket: the kubelet's own socket, a CSI driver's socket, D-Bus system methods. Before exposing or bind-mounting any socket, ask "what can the daemon on the other end be told to do, and does that amount to more authority than the caller should have?" For the runtime socket the answer is always "everything," which is why it's the canonical example — but the question is the transferable skill.

    This is the reasoning behind a whole category of Kubernetes hardening rules. A pod that bind-mounts the host's containerd.sock (or docker.sock) via a hostPath volume can start privileged containers on the node and escape to the host — so it's effectively cluster-admin, and admission controllers and Pod Security Standards exist partly to stop exactly this. "Access to the runtime socket = root on the node" is the single sentence behind why the kubelet↔runtime channel is a trust boundary and why CI-in-cluster image builds moved to rootless builders. B12 builds the trust-boundary model on top of this.

    Mini project — CNI v0.1, in two scripts

    Why it matters

    Every mechanism in this module was a piece; this project assembles them into the two things a cluster's data plane is actually made of.     Debugging drill — filter-vs-nat, a dead DNAT rule, a stale conntrack entry

    Why it matters

    Three faults, each diagnosed to a specific rule or a specific table entry rather than guessed — and each is a real cluster incident in miniature. Reproduce all three and the module's machinery becomes a diagnostic reflex: when a virtual network breaks, you localise it to a rule or a flow, you don't thrash.

    Symptom 1 — ping works but curl doesn't (filter vs nat)
    1. A backend answers ping but its port hangs. Read the timing and the ruleset to place the fault in the filter table, not the addressing. 
      multipass shell sandbox
sudo ip netns exec pod1 bash -c 'cd /tmp/pod1 && python3 -m http.server 80 &>/dev/null &'; sleep 1
sudo iptables -I FORWARD -p tcp -d 10.20.0.2 --dport 80 -j DROP   # plant the fault
ping -c1 10.20.0.2 >/dev/null && echo 'ping: ok'
time curl -s -o /dev/null -m3 http://10.20.0.2; echo "curl exit=$?"
      ping: ok                       ← ICMP passes: network layer + wiring are fine
curl exit=28  (real ~3s)       ← TCP/80 hangs to timeout: a silent DROP in filter, not a nat/route fault
    Cause & fix

    A filter-table DROP on the backend's TCP port, while ICMP is untouched. "Ping works but curl doesn't" localises the fault above the network layer, and the hang (rather than an instant refusal) says it's a silent DROP, not a REJECT or a missing listener. Confirm by reading the chain — iptables -L FORWARD -n -v shows a DROP rule whose counter climbs as you retry — and fix by removing it: sudo iptables -D FORWARD -p tcp -d 10.20.0.2 --dport 80 -j DROP. The reflex: filter decides pass/drop and nat rewrites — they're different tables, and "reachable by ping, dead on a port" is always a filter question. In a cluster this exact signature (hang, not refuse) is a NetworkPolicy dropping the traffic; the diagnosis is identical one layer up.

    Symptom 2 — a DNAT rule that never matches
    1. A published port returns nothing, yet a DNAT rule is clearly present. Don't argue about whether it "should" match — read its counter and find it dead, shadowed by a rule above it. 
      sudo iptables -t nat -F PREROUTING
sudo iptables -t nat -A PREROUTING -p tcp --dport 9090 -j DNAT --to-destination 10.20.0.99:80  # wrong/dead backend, added first
sudo iptables -t nat -A PREROUTING -p tcp --dport 9090 -j DNAT --to-destination 10.20.0.2:80   # the correct rule, shadowed below
sudo iptables -t nat -Z PREROUTING
curl -s -o /dev/null -m2 http://127.0.0.1:9090; echo "exit=$?"     # via OUTPUT it won't even match; test path below
sudo iptables -t nat -L PREROUTING -n -v --line-numbers | grep 9090
      1  N pkts  DNAT ... tcp dpt:9090 to:10.20.0.99:80    ← FIRST match wins: every packet claimed here
2  0 pkts  DNAT ... tcp dpt:9090 to:10.20.0.2:80     ← counter 0: the correct rule is dead/shadowed
    Cause & fix

    The correct DNAT is shadowed by an earlier rule that claims the same packets first. Within a chain the first match wins (B9.14), so the rule pointing at the wrong backend (10.20.0.99, which nothing answers) catches every packet and the correct rule below it never fires — proven by its zero counter while traffic flows. (A sibling of this fault is a DNAT placed in the wrong chain entirely — e.g. in POSTROUTING, after routing — where it also never matches; the counter is the same tell.) Fix by removing or reordering: delete the shadowing rule (iptables -t nat -D PREROUTING 1) so the good rule becomes first. The reflex: a DNAT that "does nothing" is a counter question — read -L -n -v, find the rule whose counter moves, and check whether it's the one you meant. This is exactly how you find why a Service sends traffic to the wrong (or a dead) endpoint by reading its KUBE- chain top-down.

    Symptom 3 — a stale conntrack entry pinning a dead backend
    1. You fix a rule mid-flow, but an existing connection keeps hitting the old, now-wrong backend. The rules are correct; the fault is state. Reproduce by establishing a flow, changing the rule, and watching the old flow ignore the change. 
      sudo iptables -t nat -F
sudo iptables -t nat -A OUTPUT -p tcp -d 127.0.0.1 --dport 7070 -j DNAT --to-destination 10.20.0.2:80
( while :; do curl -s -o /dev/null http://127.0.0.1:7070; sleep 0.3; done ) &   # a steady flow
sleep 1; sudo conntrack -L -p tcp 2>/dev/null | grep 7070 | head -1        # entry pins the mapping
# now "fix" the rule to point at pod2 — but the tracked flow won't follow:
sudo iptables -t nat -R OUTPUT 1 -p tcp -d 127.0.0.1 --dport 7070 -j DNAT --to-destination 10.20.0.3:80
sleep 1; echo '--- flush conntrack so new state is created: ---'
sudo conntrack -D -p tcp --dport 80 2>/dev/null | tail -1; kill %1 2>/dev/null
      tcp 6 ... dport=80 ... dst=10.20.0.2 [ASSURED]    ← the flow is pinned to the OLD backend, 10.20.0.2
--- flush conntrack so new state is created: ---
conntrack v1.4.7: 1 flow entries have been deleted.   ← after flush, new connections see the fixed rule
    Cause & fix

    A conntrack entry pins an existing flow to its original translation, so a corrected rule appears to do nothing. Once a connection is tracked (B9.9), its packets follow the recorded state, not the current ruleset — so a DNAT you fix mid-flow doesn't move traffic already mapped to the old backend, even when the backend is gone. The tells: the rule is provably correct (its counter moves, it points at the right place) yet traffic still lands on the wrong/dead endpoint, and conntrack -L shows an entry with the stale mapping. The fix is to force new state: retry with a fresh connection, or flush the stale entries with conntrack -D/conntrack -F. The reflex: when the rules are right but traffic still goes to the wrong place, suspect state, not configuration. This is precisely why kube-proxy deletes conntrack entries when endpoints change, and why "a Service still hits a deleted pod" is remediated by flushing conntrack.

    Gotchas

    The three faults escalate in kind on purpose. The first lives in the wrong table (filter, not nat) and is read from the symptom. The second lives in the wrong order (shadowed) and is read from a counter. The third lives in state, not rules at all, and is read from the conntrack table — the hardest to see because every rule is correct. Together they map the three places a virtual-network fault can hide: which table, which position, or which cached flow. A clean ruleset that still misbehaves is the signature that pushes you from rules to state.

    The stale-conntrack fault is the one that humbles people, because the instinct "the config is right, so it must be working" is exactly wrong: NAT has a memory, and the memory can outlive the truth. Keep conntrack -L in your kit next to iptables -L -v — one shows the rules, the other shows the flows currently ignoring any rule change. When they disagree, the flow wins until it's flushed or expires, and knowing that saves the hour you'd otherwise spend re-checking correct rules.

    All three are everyday cluster incidents. Filter-vs-nat (hang vs refuse) is the NetworkPolicy-vs-missing-endpoint distinction you'll make constantly. A shadowed/mis-chained DNAT is how a Service routes to the wrong or a dead endpoint, found by reading its KUBE- chain with counters. And a stale conntrack entry pinning traffic to a deleted pod is a known kube-proxy edge case — the reason kube-proxy actively clears conntrack on endpoint changes and the reason "flush conntrack" is a real remediation step. You now have the by-hand version of all three, which is the version you actually understand.

    B9 recall quiz

    Answer out loud before revealing. If you can explain how a ClusterIP works — an address that exists nowhere — and how a packet leaves a private namespace for the internet and finds its way back, this module has done its job.

    1. A brand-new network namespace can reach nothing at all. Name at least four things it has its own of, and say why that means each pod gets a whole IP.
      Answer

      Its own interfaces, routing table, netfilter rules, port space and loopback. Because the port space is private, two processes in different namespaces can both bind the same port without conflict — so giving each pod its own namespace (hence its own IP) is what lets pods not fight over the node's ports. A fresh namespace even starts with loopback down, so ping 127.0.0.1 fails until ip link set lo up.

    2. What is a veth pair, and what happens to one end if you delete the other?
      Answer

      A virtual patch cable — two linked interfaces where whatever enters one end exits the other and nowhere else. It's always created and destroyed as a pair: deleting either end destroys both, because there's no such thing as half a veth. A container runtime makes one per pod — eth0 inside the pod, a vethXXXX on the node.

    3. You give a bridge an IP address. What does that change about its role?
      Answer

      A bridge is a learning switch — it learns which MAC is on which port and forwards frames accordingly. Give it an IP and it also becomes the gateway the attached namespaces route through, because a bridge is simultaneously a switch for its ports and a real, addressable interface on the host. On a node this is cni0/docker0.

    4. Name the three NAT flavours by what and when each rewrites, and match each to a Kubernetes feature.
      Answer

      SNAT — source address, outbound, to a fixed IP (POSTROUTING); MASQUERADE — source address, outbound, to the outgoing interface's current IP (POSTROUTING); DNAT — destination address, inbound (PREROUTING). Pod egress = MASQUERADE; a ClusterIP → pod = DNAT; a NodePort inbound = DNAT.

    5. You remove a masquerade rule and pings from a private namespace stop getting replies — but the requests still leave the box. Why?
      Answer

      Forwarding is still on, so the request is delivered out the uplink — but now with its private source address (e.g. 10.10.0.2), which no internet router has a route back to, so the reply is dropped out there. "Requests leave, replies never arrive" is the exact signature of missing/broken source NAT. The masquerade rule doesn't help the packet leave; it makes its source answerable.

    6. What does conntrack store, and name the two consequences that bite in production.
      Answer

      It stores every flow's 4-tuple plus any NAT translation, so replies can be matched and un-translated. (1) A rule changed mid-flow does nothing to flows already tracked — the flow follows recorded state, so you must retry with a fresh connection. (2) The table is finite (nf_conntrack_max); fill it under load and the kernel logs table full, dropping packet and drops traffic every rule says should pass.

    7. Why must DNAT run in the prerouting hook, and why is a rule in the input chain useless for affecting pod traffic?
      Answer

      DNAT changes the destination, and the change must happen before the routing decision so the kernel routes on the new address — that's prerouting. Pod traffic is forwarded through the node (prerouting → forward → postrouting), so it never traverses input (which is only for traffic addressed to this host); a rule in input is inspected by none of it.

    8. "Ping works but curl doesn't," and the curl hangs before failing. What's happening, and what would an instant failure have meant instead?
      Answer

      A filter-table DROP is silently eating the TCP SYN while ICMP passes untouched — the network layer is fine, one TCP port is filtered. The hang is the DROP signature (client waits out its timeout). An instant failure would be a REJECT or a reset — an active refusal (a closed port / no listener). In Kubernetes: hang ≈ NetworkPolicy deny; instant ≈ Service with no ready endpoints.

    9. On Ubuntu 24.04, what is the iptables command really, and why is nft list ruleset the command that settles "is this rule there?"
      Answer

      iptables is iptables-nft — a compatibility front-end that translates iptables syntax into rules enforced by the nftables engine (confirmed by iptables -V printing nf_tables). nft list ruleset shows the whole unified engine regardless of which front-end wrote a rule, so it can't be fooled by a partial, dialect-specific view. kube-proxy's iptables-mode rules land in nftables underneath — hence thousands of KUBE- chains in nft list ruleset.

    10. Within a chain, which rule decides a packet's fate, and how do you prove a specific rule is dead?
      Answer

      The first rule whose match fits, walking top to bottom (first match wins) — so a rule appended after a terminating rule that already catches the traffic is shadowed. Prove a rule dead by reading counters (iptables -L -n -v): generate matching traffic and if the rule's packet counter stays at zero, it's shadowed or in a chain the traffic never enters — dead by measurement, not by argument.

    11. A ClusterIP is an address no machine holds. What actually makes it work, and why are the load-balancing probabilities chained rather than equal?
      Answer

      A DNAT rule rewrites the virtual destination to a real backend IP before routing — nothing answers ARP for the ClusterIP; it exists only as rewrite rules. For N backends the probabilities are chained (e.g. 1/3, then 1/2, then 1) because each rule's probability applies only to packets that fell through the rules above it, which yields an even split. This is kube-proxy's iptables mode exactly, and conntrack pins each connection to its chosen backend.

    12. Why is write access to /run/containerd/containerd.sock equivalent to root on the node?
      Answer

      Whoever can write to it can tell the runtime to start a container with the host filesystem mounted, running privileged with all capabilities — i.e. obtain a root shell on the host. A unix socket's access control is just its file permissions, so the socket's mode is the node's security boundary. That's why bind-mounting the runtime socket into a pod (or adding a user to the runtime/docker group) hands over the node, and why it's the canonical trust-boundary example for B12.
