    B9 — Networking II: virtual networking & packet filtering

    This is the module the whole beginner track has been climbing toward. By the end of it you will have built, with your own hands and out of nothing but namespaces, virtual cables, a switch and a handful of firewall rules, the two things people find most mysterious about Kubernetes: a pod network (private machines that all reach each other and the outside world) and a load-balanced Service (one address that fans traffic out across several backends). You will build both before either word is used — so that when Kubernetes later says "pod network" and "ClusterIP," you recognise machinery you already assembled rather than magic you have to trust. Nothing in a cluster's data path is more advanced than what is in this module; there is just more of it, automated.

    We build bottom-up, in four movements. Virtual wiring: a network namespace as a private network stack, the veth pair as a patch cable, the bridge as a switch, and proving two namespaces can talk by watching one packet at two points. Getting out: turning the host into a router, the three flavours of NAT, giving the private subnet real internet access, and why NAT needs a memory (conntrack). Netfilter: where in the kernel a packet can be caught, the tables/chains/rules/targets vocabulary under every Linux firewall, the filter-vs-nat split that explains "ping works but curl doesn't," and reading rules by their packet counters. Load balancing and sockets: DNAT plus a statistics match as a round-robin balancer (this is kube-proxy), publishing a host port (this is a NodePort), and unix domain sockets — the filesystem-based endpoints that explain why access to the runtime socket is root. Then you assemble it all into a hand-built CNI and diagnose three faults by rule and by state.

    Checkpoints20 Hours~8 PrerequisitesB6, B8
    • Create a network namespace and explain what it gets its own of — interfaces, routing table, netfilter rules, port space and loopback — and why that means a pod gets a whole IP.
    • Build a veth pair as a virtual patch cable and a bridge as a virtual switch, and move one end of a veth into a namespace.
    • Address a private subnet deliberately — bridge as gateway, an address per namespace, a default route — the way a CNI's IPAM does for every pod.
    • Connect two namespaces and prove the path by capturing the same packet at two points with tcpdump.
    • Turn the host into a router with ip_forward, and explain SNAT, MASQUERADE and DNAT by what each rewrites.
    • Give a private subnet masqueraded egress to the internet, and explain why removing the rule stops replies while requests still leave.
    • Explain conntrack — why NAT needs state — and read the table with conntrack -L, including the "rule changed mid-flow does nothing" consequence.
    • Draw the netfilter hooks (prerouting, input, forward, output, postrouting) and the to-host vs through-host paths, and say why DNAT lives in prerouting.
    • Name the tables/chains/rules/targets vocabulary and write one rule of each target kind by hand.
    • Reproduce "ping works but curl doesn't" from a filter DROP, and read DROP (hang) vs REJECT (instant) from the timing.
    • Know that the backend on 24.04 is nftables and iptables is iptables-nft, and view the same ruleset both ways.
    • Debug by rule order and packet counters — find which rule traffic actually hits, and prove a later rule is dead.
    • Build a round-robin load balancer from DNAT + -m statistic --mode random — kube-proxy's iptables mode, not an analogy for it.
    • Publish a host port into a private namespace with DNAT in prerouting — a NodePort, by hand.
    • Explain unix domain sockets — stream vs datagram, filesystem permissions, the abstract namespace — and why access to containerd.sock is equivalent to root.
    • Assemble a CNI v0.1 in two scripts, and diagnose filter-vs-nat, a DNAT rule that never matches, and a stale conntrack entry.

    B6 gave you namespaces as an isolation primitive; B8 gave you addresses, routes, ARP, TCP and tcpdump. This module fuses the two: it wires namespaces together into real networks and watches packets cross them. Everything runs on the throwaway sandbox VM (B0.1), never on the cluster. This module deliberately breaks its own connectivity — you will add and delete addresses, flip ip_forward, install firewall rules that drop traffic, and masquerade egress — so take a snapshot first (B0.9) and you can always roll back to a clean machine. Install the tools once up front: sudo apt-get install -y tcpdump conntrack nftables socat netcat-openbsd (iproute2 and iptables are already present on 24.04). Almost every command here needs root, so most labs use sudo; your uplink interface is ens3 on a typical Multipass VM (substitute the name ip -br link shows if it differs).

    Virtual wiring

    B9.1

    A network namespace is a private, empty network stack

    Why it matters

    B6 introduced namespaces as an isolation trick in the abstract. Now that B8 has given you the vocabulary — interfaces, addresses, routes, ports — you can see what a network namespace actually hands you: a whole second network stack, conjured from nothing, that shares not one thing with the machine's real one. This is the single atom every container network is built from. A pod is, at bottom, exactly one of these namespaces with some containers living inside it — which is why the containers in a pod reach each other on localhost but a pod gets its own IP. Build one by hand and the rest of Kubernetes networking stops being magic.

    The concept

    A network namespace is the kernel keeping a separate, private copy of "everything network" for a group of processes. Run ip netns add red and you get a namespace called red that has its own: set of network interfaces, routing table, netfilter rules, port space, and loopback device. Nothing in red can see or collide with anything in the host's network stack or any other namespace. This is the hotel room's own everything — same building, but its own wiring, its own phone list, its own locks.

    Two facts fall straight out of "its own," and both matter for the rest of your career:

    • Its own port space. Two processes in two different network namespaces can both bind port 80 with no conflict, because the port numbers live in separate universes. This is precisely why every pod gets a whole IP address of its own rather than a share of the node's ports — the namespace is the reason ports don't clash between pods.
    • It starts with nothing — not even loopback. A fresh namespace has exactly one interface, lo, and it is down. So the first surprise is that even ping 127.0.0.1 fails until you explicitly bring loopback up with ip link set lo up. A namespace is genuinely empty; every wire you want, you add.

    You run a command inside a namespace with ip netns exec red <command> — the command executes with red's network stack as its world. That one verb, exec, is how you'll do everything from here on: address interfaces, add routes, run ping and tcpdump, all inside the namespace you're building.

    ip netns add red→own interfaces · routes · netfilter · ports · lo· reaches nothing until you wire it
    Lab
    1. Create a namespace and look inside it. It has only a down loopback and can reach nothing — the empty room before you run any wire to it. 
      multipass shell sandbox
sudo ip netns add red
sudo ip netns exec red ip addr show        # what interfaces does red have?
      1: lo: <LOOPBACK> mtu 65536 state DOWN ...    ← one interface, and it is down
    # no inet line: loopback has no address yet either
    2. Prove it is genuinely empty: even pinging its own loopback fails, because lo is down. Then bring lo up and watch the same ping succeed — you just added the first working wire. 
      sudo ip netns exec red ping -c1 -W1 127.0.0.1 2>&1 | tail -1
sudo ip netns exec red ip link set lo up          # bring loopback up
sudo ip netns exec red ping -c1 127.0.0.1 | tail -2
      ping: connect: Network is unreachable        ← lo down: not even localhost works
64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.03 ms   ← lo up: localhost works now
1 packets transmitted, 1 received, 0% packet loss
    3. See the "own port space" fact directly: list the namespace's listening sockets — a separate, empty set from the host's. 
      sudo ip netns exec red ss -ltn        # red's listeners (none)
ss -ltn | head -3                      # the host's listeners (its own, separate set)
      State  Recv-Q Send-Q Local Address:Port      ← red: header only, nothing listening
LISTEN 0      4096   127.0.0.53%lo:53         ← host: its own listeners, a different universe
    Verify

    Name at least four things a network namespace has its own copy of, and state the consequence of "its own port space." (Its own interfaces, routing table, netfilter rules, port space and loopback; because the port space is separate, two processes in different namespaces can both bind the same port — which is why each pod gets a whole IP.) Then: why does ping 127.0.0.1 fail in a brand-new namespace? (Because a fresh namespace's only interface is lo and it starts down — loopback must be brought up with ip link set lo up before even localhost works.)

    Gotchas

    The ip netns command makes named namespaces, which persist as files under /var/run/netns/ and outlive the process that made them — handy for labs. A container runtime instead makes an anonymous per-pod namespace tied to the pod's lifetime, so you won't see pod namespaces in ip netns list by default. The mechanism is identical; only the bookkeeping differs. (You can make a runtime's namespace visible to ip netns by bind-mounting its /proc/<pid>/ns/net, which is exactly what debugging tools do.)

    Deleting a namespace (ip netns del red) destroys every interface that lived only inside it, and moves any interface that had a physical backing back to the default namespace. So a veth end left inside a deleted namespace vanishes with it — which is the tidy way to clean up a whole experiment, but also a way to lose an interface you meant to keep. Delete deliberately.

    A pod is a network namespace. The "pause" (sandbox) container a runtime starts first exists mainly to hold that namespace open; every real container in the pod is then placed into the same namespace, which is why containers in one pod share an IP and reach each other over localhost, while different pods are fully isolated with their own port spaces. The "each pod gets its own IP" rule that all of Kubernetes networking assumes is nothing more than "each pod gets its own network namespace," which you just created by hand.

    Building a pod's namespace, veth and bridge by hand is W4.2; the runtime's pod-sandbox and CRI flow are W1.20.

    Docs

    man 8 ip-netns is the whole toolset — add, del, list, exec, and how named namespaces map to /var/run/netns. man 7 network_namespaces explains what is and isn't isolated. For the syscall underneath, man 2 unshare and man 2 setns (the CLONE_NEWNET flag from B6). In the exam docs, this is assumed under "Cluster Networking" — no page teaches it directly, which is exactly why you learn it here.

    B9.2

    A veth pair is a virtual patch cable

    Why it matters

    A namespace that reaches nothing is useless; to connect it to anything you need a wire, and the wire is a veth pair. It is the single most important virtual device in all of container networking — every pod on every node in every Kubernetes cluster is attached to the world by one of these. Understand it as an ordinary patch cable with a plug at each end and the rest of the module has a physical intuition to hang on.

    The concept

    A veth pair (virtual Ethernet) is two linked interfaces that behave like the two ends of a single cable: whatever goes in one end comes out the other, and nowhere else. You create both ends at once — there is no such thing as half a veth pair — with ip link add veth0 type veth peer name veth1. That gives you veth0 and veth1, both currently in the host namespace, both down and unaddressed. This is the hotel phone wire from the analogy: one end is the handset in the room, the other is a plug in the wiring closet.

    The move that makes it useful is relocating one end into a namespace: ip link set veth1 netns red. Now the cable straddles a boundary — veth0 hangs in the host, veth1 lives inside red — and it is the only path in or out of the namespace. Send a packet into veth1 from inside red and it emerges from veth0 on the host, ready to be handed to a bridge, a route, or another namespace. This is precisely what a container runtime builds for every pod: one end named eth0 inside the pod's namespace, the other hanging on the node with an auto-generated name like vethb3f1a2.

    veth0 (host)⟷ one cable, two plugs ⟷veth1 → moved into red
    Lab
    1. Create a veth pair and confirm both ends exist on the host, linked to each other. The @ notation names each end's peer. 
      multipass shell sandbox
sudo ip link add veth0 type veth peer name veth1
ip -br link show type veth
      veth1@veth0  DOWN  ...        ← veth1, whose peer is veth0
veth0@veth1  DOWN  ...        ← veth0, whose peer is veth1  (a linked pair)
    2. Move one end into the red namespace and watch it disappear from the host and reappear inside. The cable now straddles the boundary. 
      sudo ip link set veth1 netns red
ip -br link show type veth                       # host now shows only veth0
sudo ip netns exec red ip -br link show          # red now has veth1
      # host:
veth0@if5  DOWN  ...          ← only one end left here; its peer is now "if5" (inside red)
# inside red:
lo           DOWN ...
veth1@if6    DOWN ...         ← the other end arrived in the namespace
    3. Prove they are inseparable: delete the host end and the namespace end vanishes too. (Re-create it afterwards for the next lesson.) 
      sudo ip link del veth0                            # delete one end...
sudo ip netns exec red ip -br link show          # ...the other is gone from red too
sudo ip link add veth0 type veth peer name veth1 && sudo ip link set veth1 netns red   # rebuild
      lo  DOWN ...                 ← veth1 is gone: deleting either end destroys both
    Verify

    Where does a packet sent into one end of a veth pair come out, and what happens to one end if you delete the other? (It comes out the paired end and nowhere else — a veth is a point-to-point cable; deleting either end destroys both, because there is no such thing as half a pair.) Then: after ip link set veth1 netns red, where does each end live? (veth0 stays in the host namespace; veth1 is now inside red — the cable straddles the boundary and is the namespace's only link to the outside.)

    Gotchas

    Both ends start DOWN and without an address — creating and moving a veth wires nothing up by itself. You must ip link set … up each end and assign addresses before a single packet flows, which is the next lesson's job. A very common "my namespace can't reach anything" is simply an end left down.

    The @ifN suffix in ip link output is the kernel telling you the peer's interface index, and once the peer is in another namespace it shows as a bare index (@if5) because the name isn't resolvable from here. That's normal, not a fault — it's how you match the two ends of a cable that spans a namespace boundary, and it's exactly how you'll later pair a node-side vethXXXX with the eth0 inside a specific pod.

    Every pod is joined to its node by exactly one veth pair: eth0 inside the pod's namespace, and a host-side end (named vethXXXX) enslaved to the node's bridge or handed to a routing CNI. Finding which host veth belongs to a given pod — by matching the peer interface index you just saw — is a routine node-debugging step, and capturing on that specific veth is how you watch one pod's traffic in isolation. The "delete one end, both die" property is why a crashed pod's veth cleans itself up.

    Locating a real pod's veth peer on a live node is W4.3; the veth is built into the by-hand pod network in W4.2.

    Docs

    man 4 veth for the device itself, man 8 ip-link for add … type veth, set … netns, and reading the @peer notation. The peer-index trick (matching ends across namespaces) uses ip -br link and ethtool -S or reading /sys/class/net/*/iflink. No exam-docs page covers veth directly — it lives under the CNI implementation you'll meet in W4.

    B9.3

    A bridge is a virtual switch

    Why it matters

    A veth pair joins exactly two points, but a network needs many machines able to reach each other — and a cable can't do that. The device that connects many wires and forwards between them is a switch, and Linux has one in software: the bridge. It is what every pod on a bridge-style node plugs into, so building one by hand is building the centre of a node's network.

    The concept

    A bridge is a switch implemented in the kernel. You create one with ip link add br0 type bridge, then enslave interfaces to it with ip link set veth0 master br0 — "master" meaning the bridge is now in charge of that port. Once two or more veth host-ends are enslaved to the same bridge, it does exactly what the metal switch box under a desk does: it learns which MAC address (B8.2) it has seen on which port, records that in a forwarding table, and forwards each frame only out the port where its destination lives (flooding to all ports only when it hasn't learned the destination yet). This is the switchboard the room wires plug into.

    One extra move turns the switch into something more: give the bridge itself an IP address, and it stops being only a switch and becomes the gateway the attached namespaces route through. A bridge is allowed to have its own address because it is a real interface on the host as well as a switch for its ports; that dual role — switch for the pods, router-facing address for the host — is exactly how a node's pod bridge works. On a Kubernetes node with a bridge-style CNI this device really exists, usually named cni0 or docker0, and bridge link lists one port per running pod.

    veth0↘br0 (learns MAC→port, forwards)↙veth-blue
    Lab
    1. Create the bridge, bring it up, and enslave the host end of the veth from B9.2. bridge link then shows the veth as a port of the bridge. 
      multipass shell sandbox
sudo ip link add br0 type bridge
sudo ip link set br0 up
sudo ip link set veth0 up
sudo ip link set veth0 master br0        # enslave veth0 to br0
bridge link
      6: veth0@if6: ... master br0 state forwarding ...   ← veth0 is now a bridge port
    2. Read the bridge's learned forwarding database — the MAC-to-port table it builds automatically as frames arrive. It may be sparse until traffic flows (next lessons). 
      bridge fdb show br br0 | head -4          # forwarding database: which MAC on which port
ip -br link show master br0                 # every interface enslaved to br0
      52:54:00:aa:bb:cc dev veth0 ...           ← a learned MAC and the port it lives behind
veth0@if6  UP  ...                          ← ports enslaved to br0
    3. Confirm the bridge is itself an addressable interface on the host (it appears in ip addr), which is what lets it also be a gateway once you give it an IP in the next lesson. 
      ip -br addr show br0
      br0  UP     ← up, no address yet; B9.4 gives it 10.10.0.1/24 to make it the gateway
    Verify

    What does a bridge learn, and what does it do with what it learns? (It learns which MAC address is reachable on which port and records that in a forwarding database, then forwards each frame only out the port where its destination lives — flooding to all ports only for destinations it hasn't learned yet; it is a learning switch.) Then: what changes when you give the bridge an IP address? (It stops being only a switch and becomes a gateway — an interface the attached namespaces can route through — because a bridge is simultaneously a switch for its ports and a real, addressable interface on the host.)

    Gotchas

    An enslaved port's own IP address is ignored for bridging — the bridge switches at the MAC (link) layer, so addresses belong either on the bridge itself or on the far end of each veth, not on the host-side veth you enslaved. Putting an address on a bridged port is a classic confusion that appears to do nothing; move it to the bridge or the namespace end.

    Both the bridge and every enslaved port must be UP, and the port must be enslaved before traffic will forward through it. A bridge that is down, or a veth end left down, silently drops everything — and because there's no error, it reads as a higher-layer problem until you check bridge link and the interface flags. When a "pod" can't reach its neighbour, "is every port up and enslaved?" is the bridge-layer version of B8's link rung.

    On a node running a bridge-mode CNI (flannel's default, Docker's docker0, kindnet), this exact device is the heart of pod networking: every pod's host-side veth is enslaved to it, the bridge holds the gateway address the pods route through, and bridge link on the node lists one port per pod. When you later debug "pods on this node can't reach each other," you'll check the very things you just built — is the bridge up, are the veths enslaved, is the forwarding database learning the pods' MACs.

    The node's pod bridge is inspected in flannel's moving parts (W4.6) and built by hand in W4.2.

    Docs

    man 8 ip-link for add … type bridge and set … master; man 8 bridge for bridge link (ports), bridge fdb (the learned MAC table) and per-port options. Kernel bridging behaviour and options live under Documentation/networking/bridge.rst. In the exam docs this is assumed under cluster networking; the concept surfaces as "the CNI bridge" in flannel/kindnet discussions.

    B9.4

    Address the private network: subnet, gateway, route

    Why it matters

    You have wires and a switch, which move frames — but nothing can be reached until it has an address to aim at and a route to choose an exit. Assigning those is where a network stops being cabling and becomes usable. And the three decisions you make here — which subnet this network owns, which address each namespace gets, and which gateway it points at — are exactly the three a CNI plugin's IPAM makes for every pod it ever creates. Do it once by hand and "IP address management" loses its mystique.

    The concept

    Pick a subnet for the private network — say 10.10.0.0/24 (the CIDR math from B8.3: 256 addresses, .1–.254 usable). Then make three assignments:

    • The bridge gets the gateway address: 10.10.0.1/24. By convention the first usable address is the gateway; giving it to the bridge makes the bridge the door out of this subnet.
    • Each namespace end gets an address in the subnet: red gets 10.10.0.2/24 on its veth1. This is the namespace's identity on the network.
    • Each namespace gets a default route via the gateway: ip route add default via 10.10.0.1 inside red. An address says "this is me"; a route says "to reach anything not on my own subnet, hand it to 10.10.0.1." Without the route, red can reach neighbours on 10.10.0.0/24 but has no idea how to reach anything else.

    Don't forget to bring every interface up — both veth ends and loopback inside the namespace. IPAM — the "IP address management" half of any CNI plugin — is nothing grander than keeping a record of which addresses in the chosen subnet are already handed out, so it never gives two pods the same one. You are being the IPAM here, by choosing .2 for red and remembering it's taken.

    br0 = 10.10.0.1/24 (gateway)·red veth1 = 10.10.0.2/24·red default route via .1
    Lab
    1. Give the bridge the gateway address and bring it up — the door out of the subnet now has an address. 
      multipass shell sandbox
sudo ip addr add 10.10.0.1/24 dev br0
sudo ip link set br0 up
ip -br addr show br0
      br0  UP  10.10.0.1/24        ← the bridge is now the gateway for 10.10.0.0/24
    2. Inside red: bring loopback and the veth end up, give the veth an address, and add the default route via the gateway. These four commands turn an empty namespace into a reachable host. 
      sudo ip netns exec red ip link set lo up
sudo ip netns exec red ip link set veth1 up
sudo ip netns exec red ip addr add 10.10.0.2/24 dev veth1
sudo ip netns exec red ip route add default via 10.10.0.1
      # no output on success — verify in the next step
    3. Prove red can now reach its gateway: ping the bridge address from inside the namespace. This confirms address + route + the veth-to-bridge path all work. 
      sudo ip netns exec red ip route            # red's routing table: local subnet + default
sudo ip netns exec red ping -c2 10.10.0.1  # can red reach the gateway?
      default via 10.10.0.1 dev veth1               ← the default route
10.10.0.0/24 dev veth1 proto kernel scope link src 10.10.0.2   ← the on-link subnet
64 bytes from 10.10.0.1: icmp_seq=1 ttl=64 time=0.05 ms        ← red reaches the gateway ✓
    Verify

    What three assignments turn the wired-up namespace into a reachable host, and which CNI job do they mirror? (Give the bridge the gateway address, give the namespace an address in the subnet, and give the namespace a default route via the gateway — the three IPAM decisions a CNI makes per pod: which subnet, which address, which gateway.) Then: with an address but no default route, what can the namespace reach and what can't it? (Only hosts on its own subnet — those are directly on-link; anything off the subnet has no route, so it fails with "Network is unreachable" until a default route points at the gateway.)

    Gotchas

    Forgetting ip link set lo up inside the namespace is the quiet killer: local-only services and anything that talks to 127.0.0.1 break even though your external addressing is perfect. Loopback is per-namespace and starts down (B9.1) — bring it up as reflexively as you bring up the veth.

    Put the address on the bridge, not on the host-side veth you enslaved to it — a bridged port's address is ignored (B9.3). And the mask must match on both ends: give the bridge a /24 and the namespace a /25 and you've recreated B8's wrong-netmask fault, where one side thinks the other is on a different subnet and won't ARP for it. Keep the prefix length identical across everything on the same subnet.

    These three assignments are literally what a CNI plugin does when a pod is created: it picks the node's pod-CIDR slice, allocates the next free address in it for this pod (IPAM), sets the pod's eth0 to that address, and installs a default route pointing at the node's bridge or gateway. The "which addresses are taken" bookkeeping you did in your head is the IPAM state a CNI persists on disk. When a pod comes up with no IP or no route, this is the step that failed.

    The three CIDRs a cluster juggles (pod, service, node) and where each is set are W4.4; the CNI contract that automates this addressing is W4.5.

    Docs

    man 8 ip-address (add/del, prefix lengths), man 8 ip-route (add default via, reading the table), man 8 ip-link (set … up). For the CIDR arithmetic behind your subnet choice, re-read B8.3. In the exam docs, pod/service CIDRs appear in the kubeadm ClusterConfiguration and the CNI's own config.

    B9.5

    Connect two namespaces and prove the path at two points

    Why it matters

    A single namespace on a bridge is inert. The payoff is two namespaces that can talk — the smallest real network — and, more valuable still, the technique you use to prove it: capturing the same packet at two points on its path. That "watch it at hop 1, then at hop 2" habit is the one the rest of this module leans on entirely. When a packet appears at one point and not the next, you have localised the fault to a single device without a single guess — which is exactly how you'll later discover whether a pod's traffic died inside the pod, on the bridge, or in a NAT rule.

    The concept

    Add a second namespace, blue, the same way you built red: a veth pair, one end moved into blue, the host end enslaved to br0, an address (10.10.0.3/24) and a default route inside. Now both namespaces hang off the same bridge, on the same subnet, so blue can ping red: the ICMP echo leaves blue's veth, crosses the bridge (which forwards it to red's port after ARP resolves red's MAC), and arrives at red's veth. A reply retraces the path.

    The skill to build is capturing at two points at once. Run one tcpdump on the bridge (br0, on the host) and another on the veth inside red, then ping from blue. The same echo request should appear in both captures — proof the packet reached the bridge and was delivered into red. If it showed up on the bridge but never inside red, the fault is between them (a down port, an unenslaved veth); if it never reached the bridge, the fault is on blue's side. Two capture points turn "it doesn't work" into "it fails here."

    blue veth→br0 (capture 1)→red veth (capture 2)· same packet at both = path proven
    Lab
    1. Build blue exactly as you built red: namespace, veth pair, one end inside, host end on the bridge, address, routes, everything up. 
      multipass shell sandbox
sudo ip netns add blue
sudo ip link add vethb0 type veth peer name vethb1
sudo ip link set vethb1 netns blue
sudo ip link set vethb0 up && sudo ip link set vethb0 master br0
sudo ip netns exec blue sh -c '
  ip link set lo up; ip link set vethb1 up
  ip addr add 10.10.0.3/24 dev vethb1
  ip route add default via 10.10.0.1'
      # no output on success
    2. Prove the two namespaces can talk: ping red (10.10.0.2) from inside blue. The reply confirms the bridge forwarded frames both ways. 
      sudo ip netns exec blue ping -c2 10.10.0.2
      64 bytes from 10.10.0.2: icmp_seq=1 ttl=64 time=0.06 ms   ← blue → bridge → red → back ✓
2 packets transmitted, 2 received, 0% packet loss
    3. Now the two-point capture. In one terminal capture on the bridge; in another, capture on the veth inside red; then ping from blue and watch the same echo appear at both hops. 
      # terminal A — capture on the bridge (host side):
sudo tcpdump -nn -i br0 icmp -c 2 &
# terminal B — capture inside red, on its veth end:
sudo ip netns exec red tcpdump -nn -i veth1 icmp -c 2 &
sleep 1; sudo ip netns exec blue ping -c1 10.10.0.2 >/dev/null; wait
      # on br0:   IP 10.10.0.3 > 10.10.0.2: ICMP echo request ...   ← packet reached the bridge
# in red:   IP 10.10.0.3 > 10.10.0.2: ICMP echo request ...   ← same packet delivered into red ✓
    Verify

    Why capture the same packet at two points instead of one? (Because the point where the packet is present and the next point where it's absent bracket the failing device — it localises a fault to one hop with evidence instead of a guess.) Then: an echo request appears on br0 but never inside red — what does that tell you, and where is the fault? (The bridge received it but didn't deliver it into red, so the fault is between them — red's host-side veth not enslaved or down, or the wrong port — not on blue's side and not addressing.)

    Gotchas

    The very first ping between the namespaces may show a brief delay or a single dropped packet while ARP resolves the peer's MAC (B8.2) — that's the neighbour lookup happening, not a fault. Add arp or icmp to a tcpdump filter and you can watch the who-has/is-at exchange precede the first echo. After that the MAC is cached and pings are instant.

    Capturing inside a namespace needs the capture to run in that namespace: ip netns exec red tcpdump …, not a plain tcpdump on the host, which can't see the namespace's private interfaces. This is the same "where does this traffic actually flow, and from which vantage point can I see it?" discipline from B8's interface-choice lesson — in a namespaced world you must also choose the right namespace to watch from.

    Two pods on one node talking to each other is exactly this: two namespaces, two veths, one bridge, ARP then ICMP/TCP across it. And the two-point-capture technique is the CNI-debugging method — when pod-to-pod traffic vanishes, you capture on the source pod's veth, then the node bridge, then the destination pod's veth, and the first hop where the packet stops appearing is the broken device. You just practised the single most useful skill for diagnosing a cluster's data plane, on a network small enough to hold in your head.

    Breaking the CNI and reading the signatures by capturing at each hop is W4.8; the by-hand pod network these two namespaces model is W4.2.

    Docs

No exam-docs page — this is the manual version of "kubectl exec into a pod and tcpdump the datapath," a standard cluster-debugging move.

    B9.6

    Turn the host into a router: ip_forward

    Why it matters

    Your two namespaces reach each other and the bridge, but not the internet — and the reason is one switch that is off by default. An ordinary computer is a host: it deals with traffic addressed to itself and refuses to be a middleman. Anything running containers must instead be a router, passing traffic between its pods and the outside world. Flipping that one setting is why it appears in every Kubernetes install guide, and forgetting it produces one of the most common "pods can talk to each other but not to anything beyond the node" mysteries.

    The concept

    By default the Linux kernel treats itself as a host, controlled by the sysctl net.ipv4.ip_forward, which starts at 0. With forwarding off, the kernel accepts packets whose destination is one of its own addresses and silently drops any packet that arrived for somewhere else — it will not pass a packet from one interface out another. That is the right default for a laptop and the wrong one for anything hosting namespaces, because forwarding between a private veth and the uplink is the whole job.

    Set net.ipv4.ip_forward=1 and the kernel becomes a router: a packet arriving on one interface, addressed to somewhere the kernel has a route to, gets forwarded out the appropriate interface toward its destination. In plain terms, "this packet isn't for me, but I know a next hop, so I'll pass it along" — the defining behaviour of a router. This alone still isn't enough for the private subnet to reach the internet (the replies have nowhere to come back to until you add NAT in B9.8), but it is the necessary first half: without forwarding, the packet never even leaves the box.

    ip_forward=0· packet not for me → dropped ·ip_forward=1· packet not for me → forwarded on
    Lab
    1. Read the current setting — 0 on a stock VM — and watch what happens with forwarding off: a ping from red to the internet produces nothing leaving the uplink, because the host drops the forwarded packet. 
      multipass shell sandbox
sysctl net.ipv4.ip_forward
sudo tcpdump -nn -i ens3 icmp -c1 -w /dev/null & sleep 1
sudo ip netns exec red ping -c1 -W2 1.1.1.1 >/dev/null; sleep 1; sudo pkill -f 'tcpdump.*ens3' 2>/dev/null
      net.ipv4.ip_forward = 0              ← forwarding off: host is a plain host
# tcpdump on ens3 captured 0 packets — the forwarded ping never left the box
    2. Turn forwarding on and repeat the capture: now the request leaves the uplink (you'll still get no reply until B9.8 adds NAT, because the source is a private address — that's the cliffhanger). 
      sudo sysctl -w net.ipv4.ip_forward=1
sudo tcpdump -nn -i ens3 icmp -c1 & sleep 1
sudo ip netns exec red ping -c1 -W2 1.1.1.1 >/dev/null; wait 2>/dev/null
      net.ipv4.ip_forward = 1
IP 10.10.0.2 > 1.1.1.1: ICMP echo request ...   ← now it leaves — but with a private source
    3. Note the change is not persistent — sysctl -w lasts until reboot. See where you'd make it permanent (you don't need to on the throwaway VM). 
      echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-forward.conf   # the permanent way
sudo sysctl --system >/dev/null 2>&1; sysctl net.ipv4.ip_forward
      net.ipv4.ip_forward = 1        ← now survives reboot via /etc/sysctl.d/
    Verify

    What does the kernel do, by default, with a packet whose destination is not one of its own addresses, and what does ip_forward=1 change? (By default it silently drops such a packet — it is a host, not a router; setting ip_forward=1 makes it forward the packet out the interface toward the destination, i.e. behave as a router.) Then: after enabling forwarding, a ping from the private namespace to 1.1.1.1 now leaves the uplink but still gets no reply — why? (The packet still carries its private source address 10.10.0.2, which the internet has no route back to; forwarding delivers it outward, but only NAT — next lessons — rewrites the source so a reply can return.)

    Gotchas

    sysctl -w changes are lost at reboot; the durable form is a file in /etc/sysctl.d/ (or an entry in /etc/sysctl.conf) applied by sysctl --system. On real nodes the CNI or the install steps drop exactly such a file, which is why the setting "just persists" on a working cluster — but a hand-set node that reverts after a reboot and stops routing pod traffic is a real incident. Set it the durable way anywhere it matters.

    There are also per-interface forwarding knobs (net.ipv4.conf.<iface>.forwarding) and the global one interacts with them; for IPv6 the equivalent is net.ipv6.conf.all.forwarding. And forwarding being on doesn't override a restrictive FORWARD firewall chain — on a hardened host you also need a rule permitting the forwarded traffic (B9.11). On the stock sandbox the FORWARD policy is ACCEPT, so forwarding alone is enough here.

    net.ipv4.ip_forward=1 is set on every Kubernetes node, by the same reasoning: a node forwards traffic between pod veths and between pods and the outside world, so it is a router whether or not anyone calls it one. The CNI plugins and kubeadm preflight expect it; when it's missing the signature is unmistakable — pods reach other pods on the same node's bridge (that's switching, not routing) but nothing off-node and nothing on the internet. It's one of the first things a node-networking checklist verifies.

    The datapath families that all assume a forwarding node are W4.7; broken-CNI signatures (including forwarding/routing faults) are W4.8.

    B9.7

    The three NAT flavours, by what they rewrite

    Why it matters

    Forwarding gets a packet toward the internet, but a packet whose source is a private address (10.10.0.2) can never receive a reply — no one out there has a route back to private space. The fix is address translation, and there are exactly three flavours of it. They sound interchangeable until you learn them by the one thing that distinguishes them: what each rewrites and when. Once you can name which rewrite is supposed to be happening, "the packet arrived carrying an address I didn't expect" stops being a mystery and becomes a specific question about a specific rule — which is most of NAT debugging.

    The concept

    NAT (Network Address Translation) is a router rewriting addresses in a packet as it passes through. The three flavours, by what and when they rewrite:

    • SNAT (source NAT) — rewrite the source address on the way out, to a fixed IP you name. Use it when your router has a known, stable public address. The reply comes back to that address and the router reverses the swap.
    • MASQUERADE — SNAT that uses whatever address the outgoing interface currently has, looked up automatically, instead of a hardcoded one. Slightly more work per packet, but it "just works" on links whose address is dynamic (DHCP, a cloud VM). It's the source-NAT you reach for when you don't want to name the IP.
    • DNAT (destination NAT) — rewrite the destination address (and often port) on the way in. Use it to publish an internal service on an external address/port (port forwarding), or to make a single virtual address stand in for a real backend.

    These map onto where they can run, which you'll formalise in B9.10: source rewriting happens last, in the POSTROUTING hook (after the routing decision, on the way out); destination rewriting happens first, in the PREROUTING hook (before routing, so the kernel routes on the new destination). The single most useful thing to hold onto: everything in a cluster's data path is one of these three. Pods reaching the internet is MASQUERADE; a Service's ClusterIP becoming a real pod IP is DNAT; a NodePort turning an inbound host-port hit into a pod is DNAT. Name the rewrite and you've named the mechanism.

    SNAT — src, out, fixed IP·MASQUERADE — src, out, iface's IP·DNAT — dst, in
    Lab
    1. Look at the nat table's structure — the built-in chains that correspond to the hooks where NAT runs. It's empty now; you'll fill POSTROUTING in B9.8 and PREROUTING in B9.16. 
      multipass shell sandbox
sudo iptables -t nat -L -n | grep -E 'Chain (PRE|POST|OUTPUT)'
      Chain PREROUTING (policy ACCEPT)     ← where DNAT lives (rewrite destination, before routing)
Chain POSTROUTING (policy ACCEPT)    ← where SNAT/MASQUERADE live (rewrite source, after routing)
Chain OUTPUT (policy ACCEPT)             ← locally-generated packets
    2. See the rule shapes for each flavour without committing them yet (-C checks whether a rule exists; the point is to read the syntax and where each target goes). 
      # the three shapes you'll use — note the table, chain, and target for each:
echo 'SNAT:      iptables -t nat -A POSTROUTING -s 10.10.0.0/24 -o ens3 -j SNAT   --to-source 10.191.62.10'
echo 'MASQUERADE: iptables -t nat -A POSTROUTING -s 10.10.0.0/24 -o ens3 -j MASQUERADE'
echo 'DNAT:      iptables -t nat -A PREROUTING  -p tcp --dport 8080 -j DNAT       --to-destination 10.10.0.2:80'
      SNAT:      ... POSTROUTING ... -j SNAT  --to-source ...        ← source, fixed, on the way out
MASQUERADE: ... POSTROUTING ... -j MASQUERADE                   ← source, dynamic, on the way out
DNAT:      ... PREROUTING ... -j DNAT --to-destination ...      ← destination, on the way in
    Verify

    For each of SNAT, MASQUERADE and DNAT, say what it rewrites, in which direction, and which chain it runs in. (SNAT — source address, outbound, to a fixed IP, in POSTROUTING; MASQUERADE — source address, outbound, to the outgoing interface's current IP, in POSTROUTING; DNAT — destination address, inbound, in PREROUTING.) Then: match each cluster feature to its flavour — pods reaching the internet, a ClusterIP, a NodePort. (Pod egress = MASQUERADE; ClusterIP → pod = DNAT; NodePort inbound = DNAT.)

    Gotchas

    MASQUERADE vs SNAT is a real trade-off, not a style choice: MASQUERADE looks up the interface's address for every new flow (cheap enough, but non-zero) and, usefully, drops its conntrack entries when the interface goes down so stale translations to an old address don't linger — which is exactly why it suits dynamic uplinks. Plain SNAT to a fixed address is marginally faster and correct when the address never changes. Prefer MASQUERADE when the uplink IP can change; prefer SNAT when it's pinned and you want the tiny efficiency.

    DNAT has to happen before the routing decision, which is why it lives in PREROUTING: the kernel must see the rewritten destination in order to route the packet to the right place. A DNAT rule placed in the wrong chain (say POSTROUTING, after routing) simply never does anything useful, and the counter stays at zero — a mistake you'll deliberately reproduce in the B9.20 drill. The direction/chain pairing isn't arbitrary; it's forced by when the rewrite has to take effect.

    kube-proxy's entire job is writing these three rewrites. Pod-to-external traffic is MASQUERADE'd (so the reply returns to the node, which un-NATs it back to the pod). A Service's ClusterIP — an address that exists on no interface anywhere — is made real purely by DNAT rules that rewrite it to a chosen pod IP. A NodePort is DNAT applied to an inbound host port. When you read the KUBE- chains in W4, every line is one of the three flavours you just named, and knowing which rewrite should occur is how you spot the one that isn't.

    The ClusterIP-as-DNAT idea is W4.9; walking the actual kube-proxy chains is W4.10.

    Docs

The nftables equivalents (snat, dnat, masquerade statements) are in man 8 nft. In the exam docs, this underlies every Service-type explanation.

    B9.8

    Give the private subnet real internet access

    Why it matters

    This is the moment the hand-built network stops being a toy: one rule, and namespaces you conjured from nothing can reach the actual internet. It's also the clearest possible demonstration of what NAT does, because removing that single rule produces an unforgettable signature — requests still leave the box, but replies never come back. Watching that happen fuses "forwarding" and "translation" into one working mental model.

    The concept

    You already have the two prerequisites: forwarding on (B9.6) so the host passes the packet along, and the vocabulary of MASQUERADE (B9.7). Now add exactly one rule to the nat table's POSTROUTING chain: for traffic from 10.10.0.0/24 leaving via the uplink ens3, masquerade the source. With it in place, a ping from red to 1.1.1.1 leaves the box with the host's public source address; the reply comes back to the host; and conntrack (B9.9) reverses the translation, delivering the reply back to 10.10.0.2. From inside the namespace it simply looks like the internet works.

    Remove the rule and the failure is precise and instructive: forwarding is still on, so the request still leaves ens3 — but now carrying its private source 10.10.0.2, an address no router on the internet has a route back to, so the reply is dropped somewhere out there and never returns. "Requests leave, replies never arrive" is the exact signature of missing (or wrong) source NAT, and you'll recognise it for the rest of your career. The rule doesn't help the packet get out — forwarding does that — it makes the packet's source answerable.

    red 10.10.0.2 → 1.1.1.1→ MASQUERADE →src rewritten to host's public IP→ reply returns, conntrack un-NATs it
    Lab
    1. Add the masquerade rule and confirm the private namespace now reaches the internet. (Ensure ip_forward=1 from B9.6 is still set.) 
      multipass shell sandbox
sudo iptables -t nat -A POSTROUTING -s 10.10.0.0/24 -o ens3 -j MASQUERADE
sudo ip netns exec red ping -c2 1.1.1.1
      64 bytes from 1.1.1.1: icmp_seq=1 ttl=57 time=12.3 ms   ← the private namespace reached the internet ✓
2 packets transmitted, 2 received, 0% packet loss
    2. Watch the rewrite happen: capture on the uplink while red pings, and see the source address is the host's, not 10.10.0.2 — that's the masquerade at work. 
      sudo tcpdump -nn -i ens3 icmp -c1 & sleep 1
sudo ip netns exec red ping -c1 1.1.1.1 >/dev/null; wait 2>/dev/null
ip -br addr show ens3    # compare: this host's address is the source you saw
      IP 10.191.62.10 > 1.1.1.1: ICMP echo request ...   ← source is the HOST, not 10.10.0.2
ens3  UP  10.191.62.10/24                              ← ...which is this interface's address
    3. Now the signature: delete the rule and ping again. The request still leaves (forwarding is on) but with the private source, so no reply returns — a clean demonstration of what NAT was doing. 
      sudo iptables -t nat -D POSTROUTING -s 10.10.0.0/24 -o ens3 -j MASQUERADE
sudo ip netns exec red ping -c2 -W2 1.1.1.1; echo "exit=$?"
sudo iptables -t nat -A POSTROUTING -s 10.10.0.0/24 -o ens3 -j MASQUERADE   # restore
      2 packets transmitted, 0 received, 100% packet loss     ← replies never return
exit=1                                                       ← requests left; no answer came back
    Verify

    What does the masquerade rule rewrite, and on which packets? (The source address of traffic from 10.10.0.0/24 leaving via ens3 — it swaps the private source for the uplink interface's own address, so replies can find their way back.) Then: with the rule removed but forwarding still on, why do requests still leave while replies stop arriving? (Forwarding delivers the request out the uplink, but it now carries the private source 10.10.0.2, which no internet router can route a reply back to — so the request goes and the reply is lost: the exact signature of missing source NAT.)

    Gotchas

    The rule works on sandbox because the FORWARD chain's policy is ACCEPT — the packet is both forwarded and NAT'd. On a host with a restrictive FORWARD policy (common on anything hardened) you'd also need explicit filter rules permitting the forwarded traffic in both directions, or the NAT rule appears not to work even though it's correct. NAT and filtering are separate tables doing separate jobs (B9.12); a masquerade rule never grants passage a filter rule denies.

    Scope the rule with both -s (the private subnet) and -o (the uplink) so you masquerade only the traffic you mean to. A too-broad MASQUERADE (no source or interface match) will also rewrite traffic that shouldn't be touched — including, on a real node, traffic between pods that needs to keep its real source for NetworkPolicy and logging. "Masquerade only what's actually leaving to somewhere that needs it" is the same principle behind a cluster's carefully-scoped masq rules.

    This one rule is pod egress. When a pod talks to something outside the cluster, its packet is MASQUERADE'd to the node's address so the external service can reply to the node, which un-NATs it back to the pod — exactly what you just built. CNIs and the optional ip-masq-agent install precisely-scoped masquerade rules that rewrite pod-to-external traffic but deliberately skip pod-to-pod and pod-to-service traffic (which must keep real addresses). The "requests leave, replies don't" signature you produced is a real cluster symptom of a missing or misscoped egress masquerade.

    Pod egress masquerade and the ClusterIP datapath are W4.9; the datapath families that shape where masquerade is needed are W4.7.

    Docs

    man 8 iptables (-t nat, -A/-D, -s, -o) and man 8 iptables-extensions (the MASQUERADE and SNAT targets). To see the reverse-mapping that makes it work, jump to conntrack -L in the next lesson. In the exam docs, egress/masquerade behaviour is discussed under the CNI and ip-masq-agent pages.

    B9.9

    Why NAT needs a memory: conntrack

    Why it matters

    The masquerade rule in B9.8 rewrote the outgoing source — but something had to remember that rewrite in order to reverse it on the reply, or the answer would arrive at the host addressed to the host and never find its way back to red. That memory is conntrack, and it's not a background detail: two of its properties cause real, confusing outages in clusters, and both become obvious once you've watched the table fill and empty by hand.

    The concept

    conntrack (connection tracking) is the kernel keeping a record of every flow passing through it — identified by the 4-tuple from B8.10 (source IP, source port, dest IP, dest port), together with any NAT translation applied. When the masqueraded request goes out, conntrack logs "flow from 10.10.0.2:x to 1.1.1.1, source rewritten to 10.191.62.10:y"; when the reply arrives for 10.191.62.10:y, conntrack finds that record and reverses the translation, delivering it back to 10.10.0.2:x. This is the switchboard's log of calls currently in progress — without it, NAT could translate outgoing packets but could never match the returns. You watch it with conntrack -L.

    Two consequences bite for real, and both are worth committing to memory:

    • A rule changed mid-flow does nothing to flows already in the table. Once a connection is tracked, its packets follow the recorded state, not the current rules. So a NAT/DNAT rule you fix appears not to work — until you retry with a fresh connection, which creates a new conntrack entry that sees the new rule. (This is a whole debugging drill in B9.20.)
    • The table is finite. It has a maximum size (net.netfilter.nf_conntrack_max); a machine under heavy connection churn can fill it and then logs nf_conntrack: table full, dropping packet and drops traffic that every rule says should pass. A NAT box that mysteriously drops connections under load is very often a full conntrack table.
    request out: log flow + NAT→conntrack table (the switchboard log)→reply in: match & un-NAT
    Lab
    1. Watch a tracked, NAT'd flow appear. Start a slow ping from red in the background, then list the conntrack entry for it — you'll see the original tuple and the masqueraded reply tuple side by side. 
      multipass shell sandbox
sudo ip netns exec red ping -i0.5 1.1.1.1 >/dev/null &
sleep 1; sudo conntrack -L 2>/dev/null | grep '1.1.1.1' | head -1
sudo pkill -f 'ping -i0.5' 2>/dev/null
      icmp 1 29 src=10.10.0.2 dst=1.1.1.1 ... src=1.1.1.1 dst=10.191.62.10 ... mark=0
#          ↑ original (private)              ↑ reply tuple: how the answer comes back, then un-NAT'd
    2. See the table's size and its ceiling — the numbers behind the "table full" failure. On a busy NAT box these climb toward the max. 
      sudo sysctl net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_count
      net.netfilter.nf_conntrack_max = 262144      ← the ceiling
net.netfilter.nf_conntrack_count = 41        ← current flows; "table full" happens when count hits max
    3. Watch an entry expire. Open a short TCP connection, see it as ESTABLISHED/ASSURED, then watch it age out of the table after it closes. 
      sudo ip netns exec red sh -c 'curl -s -o /dev/null http://1.1.1.1 & sleep 1; :'
sudo conntrack -L -p tcp 2>/dev/null | grep -m1 'dport=80' || echo '(flow already expired)'
      tcp 6 110 ESTABLISHED src=10.10.0.2 ... dport=80 ... [ASSURED] ...   ← a live tracked TCP flow
# moments after close it transitions to TIME_WAIT and is then removed — the memory is temporary
    Verify

    What does conntrack store, and why can NAT not work without it? (It stores every flow's 4-tuple plus any NAT translation applied, so that when a reply arrives the kernel can match it to the outgoing flow and reverse the translation; without that memory the router could rewrite outbound packets but never map the replies back to the private origin.) Then: you fix a broken DNAT rule but the connection you already had open still misbehaves — why, and what makes it work? (The existing flow is pinned to its recorded conntrack state and ignores the new rule; a fresh connection creates a new entry that sees the corrected rule — so you retry, you don't wait.)

    Gotchas

    conntrack tracks UDP and even ICMP too, despite those being "connectionless" — it uses timeouts rather than handshake state to decide when a "flow" is over, which is why a DNS-heavy or ICMP-heavy load can still fill the table. Each protocol has its own idle timeout (short for UDP, long for established TCP), tunable via the nf_conntrack_*_timeout_* sysctls. So "connectionless" at the protocol layer doesn't mean "untracked" at the NAT layer.

    The "table full" failure is nasty precisely because it's load-dependent and rule-independent: every firewall rule says the traffic should pass, packets are being dropped anyway, and the only evidence is the kernel log line and a count pinned near max. When a busy NAT box or node drops a fraction of connections under load with no rule explaining it, check nf_conntrack_count against nf_conntrack_max before anything else — it's a five-second check that saves hours.

    conntrack is load-bearing for kube-proxy: every Service connection is a DNAT'd flow whose return path depends on a conntrack entry, and the entry is what pins a given client connection to the one backend pod it was first balanced to (so a long-lived connection keeps hitting the same pod). Two famous cluster incidents follow directly: nodes under heavy connection churn hitting nf_conntrack: table full and dropping traffic (the fix is raising nf_conntrack_max), and a stale conntrack entry still steering traffic to a pod that has already been deleted — which is why kube-proxy actively deletes conntrack entries when endpoints change, and why "flush conntrack" is a real remediation. You reproduce that stale-entry fault in B9.20.

    The conntrack-backed ClusterIP datapath is W4.9; endpoint readiness deciding which backends conntrack may pin to is W4.11.
