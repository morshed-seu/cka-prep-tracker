    B11 — Service management: systemd, logs, boot

    Something has to be in charge. When a machine boots, the kernel starts exactly one process and hands it the entire job of turning a bare kernel into a working system: start the things that should run, in an order that works, restart them when they die, collect what they printed, and keep doing all of that until someone turns the power off. On a modern Linux box that process is systemd, and the units it manages are the vocabulary in which every service on every server you will ever touch is described. This is the building superintendent: they get the boiler running and the lights on before any tenant office can open its doors.

    The reason this module sits here, after processes and cgroups, is that a systemd unit turns out to be made entirely of things you already understand. A unit's status is a process, an exit code and a signal (B2.8) formatted into a paragraph. Its restart policy is the supervisor loop you wrote by hand in B2.17. Its resource limits are the cgroup files from B7, written by systemd on your behalf. Its logs are the stdout and stderr of a program that never learned what a log file is. Nothing here is new machinery; it is a management layer over machinery you have already built, and once you see that, the entire systemctl/journalctl surface stops being a set of incantations.

    We go in three movements. Units: what init is for, the unit types you actually meet, writing one from scratch, the keys that decide behaviour, and the ordering-versus-requirement distinction behind most "works on reboot, fails at boot" bugs. Operating: the verbs that matter, overriding without editing, keeping configuration out of the unit, and reading a failure from systemctl status alone. Logs and boot: journalctl fluency, making sure your logs survive the crash you need them for, and the boot-target and cgroup-slice picture that turns out to be the whole layout of a Kubernetes node on one screen. By the end, systemctl status kubelet and journalctl -u kubelet — the two commands you will run on every broken node for the rest of your career — read as ordinary prose.

B7 matters because systemd is what puts every service into a cgroup: the slices and scopes you met in B7.12 are systemd's doing, and the resource keys you can set on a unit are the cgroup files from that module with friendlier names.     B11.1

    What an init system is for, and why PID 1 is special

    Why it matters

    A booted Linux machine is not a natural state; it is a state something worked to produce. The kernel finishes initialising hardware and then starts exactly one program, and from that moment everything else on the machine — every daemon, every login, every network interface being configured — exists because that one program, or something it started, made it exist. Knowing what that program is responsible for is what lets you answer questions like "why did this start before that?", "who restarted my service?" and, eventually, "why is the kubelet the only Kubernetes component that systemd knows about?"

    The concept

    The kernel starts one userspace process, gives it PID 1, and gets out of the way. That process is the init system, and it has three duties that nothing else can do:

    • Bring the machine up. Start the services that should run, in an order that works, and keep going until the system has reached a defined working state. "Working state" is a real, named thing here, not a feeling — B11.12 shows you the target that defines it.
    • Keep it up. Supervise: notice when something dies, decide whether that was expected, and restart it if not. This is the loop from B2.17, running for every service on the machine at once.
    • Adopt the orphans. When a process's parent dies before it does, the kernel reparents the child to PID 1 (B2.9). PID 1 therefore inherits strangers continuously, and must wait() on them so they don't accumulate as zombies. This is not optional politeness; it is a structural duty that comes with the PID.

    PID 1 is also special to the kernel in a way worth knowing: signals with a default action are not delivered to it unless it has installed a handler. Send SIGTERM to a normal process with no handler and it dies; send it to PID 1 with no handler and nothing happens at all. The kernel is protecting itself — a machine whose PID 1 dies panics — but the consequence bites elsewhere, as you will see in a moment.

    systemd is the init system on Ubuntu and on essentially every distribution a Kubernetes node runs. It took on a great deal beyond the three duties above, which is both why it is powerful and why it is argued about: it is simultaneously the supervisor, the logger (B11.10), the cgroup manager (B11.12), a socket activator, a timer daemon and a mount manager. For our purposes that consolidation is good news, because it means one vocabulary — the unit — describes all of it.

    Now the part that pays off later. A container also has a PID 1: the process you told it to run, which lands as PID 1 inside its own PID namespace (B6.5). That process inherits both duties above and usually implements neither. It does not reap orphans, so a container that spawns subprocesses can slowly fill with zombies; and it typically has no SIGTERM handler, so the kernel refuses to deliver the polite stop signal at all and the process only dies when the grace period expires and SIGKILL arrives. That is the entire explanation for why some containers take exactly ten seconds to stop, and why small init programs like tini exist.

    kernel boots→PID 1 = systemd→start units·supervise·reap orphans

    One process is started by the kernel; everything else on the machine descends from it.

    Verify

    Answer three things without looking. What starts PID 1, and what happens to the machine if PID 1 exits? (The kernel starts it; if it exits the kernel panics, which is why the kernel protects it from unhandled default-action signals.) Why must PID 1 reap orphans? (Because the kernel reparents every orphan to it, so it accumulates children it never started and must wait() on them or leak zombies.) And why does a container process that ignores SIGTERM take the full grace period to stop? (It is PID 1 in its own PID namespace with no handler installed, so the kernel does not deliver the signal at all; only the later SIGKILL ends it.)

    Gotchas

    The PID-1 signal rule catches people precisely because it is invisible when it works and baffling when it does not. A program that handles SIGTERM perfectly well as an ordinary process becomes unstoppable-by-TERM the moment it is PID 1 without a handler, because the kernel silently declines to deliver the signal rather than reporting an error. If a process is ignoring a signal you are certain you sent, check whether it is PID 1 in some namespace before you doubt your kill command.

    The second trap is treating "init system" as a synonym for systemd. It is one implementation of the role; others exist (sysvinit, OpenRC, runit, and inside containers, tini or dumb-init). What is universal is the role — PID 1, adoption, supervision — and that is what transfers when you meet a system that does not run systemd. Learn the role first and the specific tool second.

    On a Kubernetes node, systemd runs exactly one Kubernetes component: the kubelet. Everything else — the API server, the scheduler, the controller manager, etcd on a control-plane node — runs as a static pod, started by the kubelet from YAML files on disk rather than by systemd. That arrangement exists because of a chicken-and-egg problem: the API server cannot be scheduled by the machinery that only exists once the API server is running. So the boot order on a control-plane node is systemd → kubelet → everything else, which is why "restart the API server" means moving a file, not running systemctl restart. This single fact reshapes how you troubleshoot a node, and it is the reason this module exists.

    How each component actually runs on the node, static pods and mirror pods included, is W1.2; the kubelet's own supervision loop and its three pod sources is W1.19.

    B11.2

    The unit types you will actually meet

    Why it matters

    systemd manages eleven kinds of thing, which sounds like a lot until you notice that five of them cover almost everything you will ever touch. Knowing which is which saves you from the two most common confusions: looking for a service that is actually a timer, and wondering why multi-user.target has no process attached to it. It also explains why a filesystem, a scheduled job and a daemon are managed with the same three commands.

    The concept

    A unit is systemd's word for "a thing I manage." The file's extension declares its type, and the type determines what the file may contain. The five that matter:

    • .service — a process to run and supervise. This is the overwhelming majority of what you will write and read: a daemon, a one-shot script, a database, the kubelet.
    • .socket — a listening socket that systemd holds open on a service's behalf, starting the service on the first connection. This is socket activation: the port is bound at boot, but the program only starts when someone actually connects, and connections that arrive during start-up wait rather than being refused.
    • .timer — a schedule that starts another unit. This is systemd's replacement for cron, and its advantages are concrete: the job's output goes to the journal automatically, a missed run can be caught up after downtime, and the job is a unit like any other, so it gets status, logs and resource limits for free.
    • .target — a named group of units, with no process of its own. A target is a synchronisation point and a goal: multi-user.target means "the set of units that constitutes a working multi-user system." Targets replaced the old numbered runlevels with something you can actually read.
    • .mount — a filesystem mount, managed as a unit. Every line in /etc/fstab (B5.4) is silently turned into one of these at boot, which is why a failed mount shows up in systemctl at all.

    The remaining types exist and are worth recognising rather than learning: .path (act when a file appears or changes), .slice (a cgroup branch for resource management — B11.12), .scope (a cgroup for processes systemd did not start, like a login session), .device, .swap and .automount.

    Two naming conventions will otherwise confuse you. A templated unit has an @ in its name: getty@tty1.service is an instance of the template getty@.service, with tty1 passed in as the instance name — one file, many instances. And a .timer by default starts the .service with the same base name, which is why timers and services come in pairs: sysreport.timer starts sysreport.service unless told otherwise.

    Gotchas

    The commonest confusion is looking in the wrong place for a scheduled job. If someone says "the nightly backup runs at 2am," systemctl status backup.service will usually show it as inactive — which is correct and not a fault, because the service only runs when the timer starts it. Check systemctl list-timers for when it last ran and when it will run next; the service being idle between runs is the design.

    The second is assuming a socket unit's service must be running for the port to be open. With socket activation the socket unit holds the port while the service is stopped, so ss -ltnp shows something listening and systemctl status shows the service inactive, and both are telling the truth. This is exactly how systemd-journald and, on many systems, sshd are arranged.

    On a Kubernetes node you will meet only two of these types in anger, but you will meet them constantly: kubelet.service and containerd.service, both ordinary .service units. Everything else Kubernetes-shaped on that node is not a systemd unit at all — pods are managed by the kubelet, and the containers inside them are managed by containerd, neither of which registers anything with systemd. The one place the other types show up is the cgroup tree: kubepods.slice is a .slice unit, which is how a node's pod resources are carved out of the machine's (B11.12 and B7.12).

    What actually runs as a systemd unit on a node versus as a static pod is W1.2; the kubelet's relationship with containerd over CRI is W1.20.

    B11.3

    Write a unit file from scratch — three sections, nothing more

    Why it matters

    A unit file looks intimidating in the wild because real ones are long. Written from scratch it is about six lines, and writing those six lines yourself is what converts systemctl from a set of memorised commands into something you understand. It is also a genuinely useful skill: turning "this script needs to keep running" into a supervised, logged, boot-surviving service is a ten-minute job once you have done it once.

    The concept

    A .service file has three sections, and each answers one question:

    • [Unit] — what is this and how does it relate to other units? A Description= (which is what systemctl status prints), plus the ordering and dependency keys covered in B11.5.
    • [Service] — what do I run and how do I supervise it? ExecStart= and the behaviour keys covered in B11.4. This section only exists for .service units.
    • [Install] — what should happen when someone enables this? Almost always a single WantedBy=multi-user.target, meaning "when the machine boots to a working multi-user state, want me too." If you omit this section the unit can still be started by hand but cannot be enabled, which is a confusing failure the first time it happens.

    Where you put the file decides who wins. systemd reads unit files from several directories in a fixed precedence order, and a file in a higher-priority directory completely replaces the same-named file in a lower one:

    • /etc/systemd/system/ — yours, the administrator's. Highest priority. This is where you write new units and where package upgrades never touch.
    • /run/systemd/system/ — runtime, generated, lives in memory, vanishes at reboot.
    • /usr/lib/systemd/system/ — the vendor's, installed by packages. Lowest priority. On Ubuntu 24.04 /lib is a symlink to /usr, so /lib/systemd/system/ is the same directory under an older name.

    That ordering is the whole reason for the classic mistake: editing a unit in /usr/lib/systemd/system/ works perfectly until the next apt upgrade replaces the file and silently reverts your change. Write to /etc/systemd/system/, or better, use a drop-in (B11.7) so you override one key instead of owning the whole file.

    One rule catches everyone once: after creating or editing a unit file, systemd does not notice by itself. You must run systemctl daemon-reload to make it re-read the files from disk. Forget it and you will restart a service repeatedly, watch nothing change, and doubt your own file.

    write /etc/systemd/system/hello.service→systemctl daemon-reload→systemctl start hello→systemctl status hello

    The four-step cycle you will repeat for every unit you ever write; skipping step two is the classic first mistake.

    Lab
    1. Write something for the unit to run. A script that prints and sleeps is enough to be supervised, and printing to stdout means you get logging for free (B11.10). 
      multipass shell sandbox

[Service]

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
                             # daemon-reload is silent when it succeeds

Leave hello.service running; the next few lessons modify it.

    Gotchas

    Forgetting daemon-reload is the mistake everyone makes, and its symptom is uniquely misleading: the restart succeeds, systemd reports no error, and the old behaviour continues. If a change to a unit file appears to have no effect, run daemon-reload before investigating anything else. (systemd will usually warn you with "Warning: The unit file … changed on disk" on the next systemctl command, but only after you have already been confused once.)

    The second is expecting a shell. ExecStart= is not a shell command line: there is no PATH search (use an absolute path), no ~ expansion, no pipes, no redirection, no globbing and no &&. If you genuinely need shell features, be explicit about it — ExecStart=/bin/sh -c 'foo | bar > /tmp/out' — rather than writing something that looks like shell and silently is not. A unit whose ExecStart contains a pipe character will start a program with a literal | as an argument.

    Third, do not edit files in /usr/lib/systemd/system/. It works, which is what makes it dangerous — the next package upgrade overwrites your change with no warning and the service quietly reverts to vendor behaviour, often weeks later when nobody connects the two events. Put your own units in /etc/systemd/system/ and override vendor units with drop-ins (B11.7).

    kubelet.service is a unit file exactly like the one you just wrote — a [Unit] with a description and ordering, a [Service] with an ExecStart pointing at /usr/bin/kubelet, and an [Install] with WantedBy=multi-user.target. When you eventually run systemctl cat kubelet on a node, you will be reading the same three sections, with the interesting part being how kubeadm adds its flags — through a drop-in rather than by editing the file, for exactly the precedence reason above.

    Reading how the node's components are actually launched, kubelet unit included, is W1.2; the kubelet's own directory of state and configuration is W1.23.

    man 5 systemd.unit covers the [Unit] and [Install] sections and — importantly — the "Unit File Load Path" section that lists the precedence order above. man 5 systemd.service covers [Service]. man 5 systemd.syntax explains the file format itself (sections, comments, line continuation). man 1 systemctl for daemon-reload, enable, show -p and cat.

    B11.4

    The [Service] keys that decide behaviour — Restart, RestartSec and Type

    Why it matters

    Your unit currently runs a program. These keys turn it into a supervised program: one that comes back when it dies, waits sensibly before retrying, runs as the right user, and — the one that produces genuinely baffling failures — is correctly understood by systemd to be "up." Type= in particular is the key that, set wrong, makes systemd supervise a process that has already exited and restart the wrong thing forever.

    The concept

    The keys worth knowing, in rough order of how often they matter:

    • ExecStart= — the command, absolute path, no shell (B11.3). Siblings: ExecStartPre= and ExecStartPost= run before and after, and ExecStop=/ExecReload= define what stop and reload mean if the defaults won't do.
    • Restart= — when to bring it back. no (the default — nothing is restarted unless you ask for it), on-failure (a non-zero exit, a signal, a timeout — the sane choice for most services), always (even a clean exit 0), plus the narrower on-abnormal, on-abort and on-watchdog. This is the decision your B2.17 supervisor made in its own code; here it is one word.
    • RestartSec= — how long to wait before restarting. The default is 100ms, which is fast enough that a program crashing on start-up will spin. Set it to something human (2s, 5s) whenever a restart involves reconnecting to anything.
    • User= / Group= — run as somebody other than root. Free, and the single cheapest security improvement available to a unit; this is exactly what system users exist for (B4.3).
    • WorkingDirectory= — the directory the process starts in. Without it you inherit /, which is why relative paths inside a script behave differently under systemd than in your shell.
    • Type= — how systemd decides the service is up. This one deserves its own paragraph.

    Type= answers "when may I consider start-up finished and move on to units ordered after me?" The values you will meet:

    • simple (the default) — the process systemd started is the service; consider it up immediately.
    • exec — like simple, but wait until the exec() has actually succeeded, so a typo'd binary path is reported as a start failure rather than a silent later death. A better default than simple when you have the choice.
    • forking — the program forks a background child and the original exits; treat the child as the service. Old-style daemons do this. Usually paired with PIDFile= so systemd knows which process to watch.
    • oneshot — the process is expected to run and exit; the service is "up" once it has finished successfully. Right for scripts that do a job rather than stay resident, and the type a .timer's service almost always uses. Pair with RemainAfterExit=yes if "done" should count as "active."
    • notify — the program tells systemd when it is ready, over a socket. The most accurate option, and only available if the program was written to support it.

    The failure mode to remember: declare Type=simple for a daemon that forks, and systemd will supervise the original process, which exits immediately after forking. systemd sees the service die a fraction of a second after start, restarts it per your policy, and the real daemon accumulates in the background, unmanaged, one copy per restart. The symptom — "systemd keeps restarting it but it is clearly running" — is unmistakable once you have seen it, and the fix is Type=forking.

    One more key belongs here because it saves the drill in B11.14 from being infinite: systemd rate-limits restarts. StartLimitIntervalSec= (default 10s) and StartLimitBurst= (default 5) live in [Unit], and if a unit starts more than burst times within the interval, systemd gives up and puts it in the failed state with the message "start request repeated too quickly." That message means the restart loop was stopped by the rate limiter, not that the last start failed differently — a distinction people misread constantly.

    Gotchas

    Restart=always is not the safe default it looks like. It hides failures: a service that cannot possibly work — bad config, missing file, wrong permissions — will restart forever, presenting as "active" for a fraction of every second and never producing an alert, while the journal fills with the same error at whatever rate the rate limiter allows. That is precisely the second fault in B11.14. Prefer Restart=on-failure, which restarts real crashes and respects a clean exit as a decision rather than a problem.

    The default RestartSec=100ms is too fast for almost anything real. A service that reconnects to a database or waits for the network will retry ten times a second, hammer whatever it depends on, and hit the start limiter within a second or two — turning a transient dependency problem into a hard failure. Set an explicit RestartSec whenever a restart does more than re-exec a trivial process.

    Finally, User= changes more than the uid. The process gets that user's privileges, and anything the unit touches — working directory, files it writes, sockets it binds — must be reachable by that user. A unit that works as root and fails with User=someone is almost always a permission problem on a path (B4.6 — remember that traversing a directory needs x on every component), and the journal will say so plainly if you look.

    Restart= is the node-level ancestor of a pod's restartPolicy, and the resemblance is not superficial: Always, OnFailure and Never mean here what they mean there, and both use exponential backoff so a crash loop cannot become a busy loop. When you later meet CrashLoopBackOff, you are looking at exactly this mechanism one layer up — a supervisor restarting a failing process with a growing delay — and the debugging move is the same one you just did: get the exit status, then read the logs of the previous attempt rather than the current one. systemd's NRestarts counter is the direct analogue of a pod's restart count.

    Container states and the three status vocabularies are W3.1; CrashLoopBackOff, --previous and the exit-code alphabet are W6.16.

    B11.5

    Ordering is not requirement: After, Requires and Wants

    Why it matters

    These three keys look like variations on one idea and are in fact two completely independent ideas that happen to be written next to each other. Merging them is the direct cause of nearly every "it works when I restart it by hand, but fails at boot" bug — the kind that reproduces only on a cold machine, at the worst possible time, and vanishes the moment you try to investigate it interactively.

    The concept

    systemd separates two questions that most people ask as one:

    • Requirement — must that other unit be running? Answered by Requires= (yes: if it fails or is stopped, I am stopped too) and Wants= (preferably: try to start it, but carry on regardless if it fails). This is about dependency.
    • Ordering — in what sequence? Answered by After= ("do not start me before that unit has finished starting") and Before= (the mirror image). This is about time.

    Crucially, neither implies the other. A unit with Requires=postgresql.service and no After= is telling systemd "start Postgres too" — and systemd, being a parallel starter, will happily start both at the same instant. Your service then races Postgres and loses roughly whenever the machine is cold and slow, which is to say at boot. Add After=postgresql.service and the race disappears. The pairing you almost always want is both:

    [Unit]
Wants=postgresql.service
After=postgresql.service

    Wants= + After= is the workhorse combination: pull the dependency in, and wait for it, but do not make my service collapse if it has a bad day. Reserve Requires= for genuine "there is no point in me existing without it" cases, and know its sharp edge — Requires= propagates stops as well as failures, so stopping the dependency stops you too, which is occasionally a nasty surprise during maintenance.

    Two more mechanisms complete the picture. BindsTo= is Requires= with teeth: it also stops you if the other unit stops for any reason, including the device behind it disappearing. And targets act as ordering landmarks — After=network-online.target is how you say "once the network is genuinely usable," which is subtly different from network.target (meaning "networking has been configured," which can be true before any address is reachable). If a service needs to make an outbound connection at start-up, network-online.target is the one you want, and it needs a corresponding Wants= to actually be pulled in.

    Wants= (pull it in)+After= (wait for it)=the combination that survives a cold boot

    Dependency and sequence are separate switches; almost every boot race is one of them being set without the other.

    Gotchas

    The reason this bug is so expensive is that it does not reproduce interactively. When you restart the service by hand, its dependency has been running for hours, so the race is won trivially every time and everything looks correct. It only fails on a cold boot, when both units start together and the slow one loses — which means the failure appears at reboot, in production, usually at 3am, and cannot be reproduced by the person investigating. If a service works on restart but fails on boot, look at After= before anything else.

    Requires= propagating stops is the second surprise. Stop the dependency for maintenance and everything that Requires= it stops too, immediately and without asking. That is correct behaviour and rarely what the person typing systemctl stop expected. Use Wants= unless you truly mean "I cannot exist without this," and know that BindsTo= is stricter still.

    Finally, network-online.target is not free: it is only reached if something pulls it in, so After=network-online.target alone can order you after a target that never activates. The idiom is Wants=network-online.target together with After=network-online.target — the same pairing as everything else in this lesson, which is a good sign you have understood the rule.

    The kubelet unit is the working example of this pairing on a node: it needs the container runtime to be reachable before it can do anything useful, and getting the ordering right is the difference between a node that comes up cleanly and one that logs runtime-connection errors for the first minute after every reboot. Those errors are harmless-but-alarming and turn up in real incident reviews constantly — now you know they are an ordering artefact rather than a fault. Kubernetes has no equivalent of these keys for pods, incidentally: pod start-up ordering is expressed with init containers and readiness probes instead, which is a deliberate design choice worth noticing.

    How the kubelet and containerd relate on a node is W1.20; the NotReady ladder you will walk when that relationship breaks is W6.10.

    B11.6

    The systemctl verbs that matter — and two pairs people merge

    Why it matters

    systemctl has around eighty subcommands and you need about ten of them. Two pairs within those ten are routinely confused, and each confusion produces a specific, common, embarrassing outcome: a service that vanishes after a reboot, and a service that "was enabled" but never actually started. Getting these straight takes five minutes and removes a whole category of self-inflicted incident.

    The concept

    The first pair is about now versus at boot, and they are completely independent switches:

    • start / stop — act on the running system, right now. They have no memory: nothing about them survives a reboot.
    • enable / disable — act on the next boot, by creating or removing the symlink you saw in B11.3. They do not touch the running system at all.

    So "I started it and it was gone after the reboot" is start without enable, and "I enabled it and nothing happened" is enable without start. Both are correct behaviour. The shorthand for "do both" is enable --now (and disable --now for the reverse), which is what you almost always mean.

    The second pair is about how violently to apply a change:

    • restart — stop the process and start a new one. Always works; always drops whatever the service was doing, including open connections.
    • reload — ask the running process to re-read its configuration without restarting, by sending it a signal (B2.12) or running ExecReload=. Preserves connections — but only works if the unit defines it, and only reloads what that program chose to make reloadable.
    • reload-or-restart — reload if the unit supports it, otherwise restart. The pragmatic middle.

    Then the reading verbs, which are where the real value is:

    • status — the human summary: state, main PID, cgroup tree, and the last few journal lines. Your default.
    • cat — the effective unit file, including every drop-in, printed with the source path above each fragment. This is the only honest answer to "what is this service actually configured to do," and it is the most underrated command in the set.
    • show — every property systemd holds for the unit, machine-readable. show -p Restart --value answers one precise question without prose.
    • list-units / list-unit-files — what is loaded now versus what exists on disk and its enablement state. The second is how you find a unit you have not started yet.
    • is-active / is-enabled / is-failed — one word out, useful exit codes, made for scripts.
    • --failed — systemctl --failed lists everything currently in a failed state. First command to run on a machine somebody says is "acting strange."

    Two more worth having: daemon-reload (re-read unit files from disk — B11.3) and reset-failed (clear the failed state and the restart counter, which you need after fixing a unit that hit the start limiter).

    Gotchas

    reload is not a gentler restart — it is a different operation with different coverage. Note what is not here: there is no systemctl restart kube-apiserver, because that is a static pod and not a unit — restarting it means moving its manifest file.

    B11.7

    Override without editing: drop-ins

    Why it matters

    Sooner or later you need to change one setting on a unit that a package installed — give it more memory, change a flag, add a dependency. Editing the vendor file works and is wrong, because the next upgrade silently reverts it (B11.3). A drop-in changes one key, survives upgrades, is self-documenting, and is exactly the mechanism kubeadm uses to configure the kubelet — so learning it here means reading a real node's configuration later without surprise.

    The concept

    For any unit foo.service, systemd also reads every *.conf file in a directory named foo.service.d/ — under /etc/systemd/system/ for your overrides, and under /usr/lib/systemd/system/ for the vendor's own. Those files are merged over the main unit file rather than replacing it: you write only the sections and keys you want to change, and everything else stays as the vendor wrote it. Files are applied in alphabetical order, which is why the convention is to prefix them with numbers (10-, 20-) so the order is visible and controllable.

    The mechanism has one sharp edge that catches everyone exactly once. Most keys are last-one-wins: set Restart=on-failure in a drop-in and it replaces the vendor's Restart=always. But some keys are list-valued and accumulate — ExecStart=, ExecStartPre=, Environment=, After= and friends. Adding ExecStart=/usr/bin/mine in a drop-in does not replace the vendor's ExecStart; it appends a second one, and systemd refuses the unit with an error about multiple commands. The fix is to clear the list first with an empty assignment, then set your value:

    [Service]
ExecStart=
ExecStart=/usr/bin/mine --with --my --flags

    That first bare ExecStart= means "empty the list." It looks like a typo and is load-bearing. The same trick applies to any accumulating key.

    You can create drop-ins two ways. By hand: mkdir /etc/systemd/system/foo.service.d/, write a .conf file, daemon-reload. Or with systemctl edit foo, which opens an editor on a drop-in called override.conf, creates the directory for you, and runs daemon-reload on save. systemctl edit --full foo instead copies the whole vendor unit into /etc/ for you to edit — occasionally what you want, but it opts you out of future vendor improvements, so prefer the drop-in. Either way, systemctl cat foo afterwards shows the merged result with each fragment's path, which is how you confirm your value actually won.

    vendor unit+10-a.conf+20-b.conf=systemctl cat shows the merge

    Drop-ins layer over the vendor file in alphabetical order; nothing is replaced except the keys you name.

    The ExecStart= trap is worth internalising because its error message names the symptom rather than the cause: "Service has more than one ExecStart= setting" sounds like you wrote the same key twice in one file, when in fact you wrote it once in a drop-in and the vendor wrote it once in the unit. Any time you are replacing rather than adding, clear the list first. The same applies to Environment=, ExecStartPre=, and the dependency keys.

    Alphabetical order means 20-foo.conf beats 10-foo.conf for last-one-wins keys, and that override.conf (from systemctl edit) sorts after any numbered file. Mixing hand-written drop-ins with systemctl edit on the same unit is therefore a good way to confuse yourself later. Pick one convention per unit, and use systemctl cat whenever the effective value surprises you — it prints fragments in application order, so the last occurrence of a key is the winner.

    And drop-ins still need daemon-reload. systemctl edit does it for you; writing the file by hand does not. A drop-in that "has no effect" is, nine times out of ten, a drop-in systemd has not read yet.

    This is precisely how a kubeadm-built node configures its kubelet. The kubelet package ships a plain unit, and kubeadm adds /etc/systemd/system/kubelet.service.d/10-kubeadm.conf — a drop-in that clears ExecStart= with an empty assignment and sets its own, pulling flags from environment files. When you run systemctl cat kubelet on a real node, that two-fragment output is exactly what you just built by hand, down to the 10- prefix and the empty-assignment trick. It is also why changing a kubelet flag means editing a drop-in and running daemon-reload, never editing the shipped unit. (Kubernetes has been moving the same idea into the kubelet itself: as of v1.35 the kubelet's own configuration drop-in directory, --config-dir, is generally available — the same layering principle applied to its YAML config rather than its unit file.)

    Reading the node's real kubelet configuration is part of W1.2; the kubelet's config and state directory is W1.23.

    B11.8

    Keep configuration out of the unit: EnvironmentFile

    Why it matters

    A unit file describes how to run a service; it should not also hold every knob the service happens to need. Separating the two means an operator can change behaviour by editing an obvious file of KEY=value lines and restarting, without touching systemd configuration, without daemon-reload, and without the risk of breaking the unit itself. This is how nearly every packaged service on a Linux machine is arranged, and it is the pattern kubeadm uses to pass flags to the kubelet.

    The concept

    EnvironmentFile=/path/to/file in [Service] tells systemd to read that file before starting the process and put its contents into the process's environment. The file is a list of KEY=value lines — no export, no shell, comments with #. You then reference the values in ExecStart= with $NAME or ${NAME}. A leading dash — EnvironmentFile=-/etc/default/hello — means "ignore this if the file does not exist," which is what packaged units use so a missing optional config is not a start failure.

    For one or two fixed values, Environment="KEY=value" inline in the unit does the same job without a separate file. Use the file when the values are things an operator should edit; use the inline form for things that belong to the unit's definition.

    Now the part that produces real confusion, and it is worth getting exactly right because it looks like shell and is not. systemd performs variable substitution, not shell expansion, and the two forms differ in one specific way:

    • $NAME — the value is substituted and then split on whitespace into separate arguments. This is what you want for a variable holding a list of flags.
    • ${NAME} — the value is substituted as a single argument, whitespace included. This is what you want for a path or a value that might contain spaces.

    The systemd manual's own example makes it concrete: with ONE=one and TWO=two two, the line ExecStart=/bin/echo $ONE $TWO ${TWO} passes four arguments — one, two, two, and two two. Nothing else shell-like works: no command substitution, no globbing, no $(...), no &&, and an undefined variable becomes an empty string rather than an error.

    The consequence people trip over is timing. The environment file is read when the service starts, so editing it changes nothing at all until you restart the service — the running process has its copy of the environment and nothing can push a new one into it. That is not a systemd quirk; it is how process environments work everywhere, and it is exactly why a Kubernetes pod's environment variables never update when their ConfigMap changes while mounted volumes do.

    Lab
    1. Make the script take its behaviour from the environment rather than from hard-coded values.

#!/usr/bin/env bash
GREETING="${GREETING:-hello}"

while true; do

    Your service should be printing values that came from /etc/default/hello, and you should have watched an edit to that file have no effect until a restart.     Gotchas

    The environment file is not a shell script, however much it looks like one. KEY=$(hostname) sets the literal string $(hostname); export KEY=value sets a variable whose name is export KEY or fails outright; quoting rules are systemd's, not bash's. If you need a value computed at start-up, compute it in an ExecStartPre= script that writes the file, or accept a wrapper script as your ExecStart.

    Undefined variables silently become empty. A typo in ExecStart=/usr/bin/foo --port=$PROT does not fail — it runs foo --port=, which the program may accept, reject confusingly, or interpret as a default. When a service starts but behaves as though a setting is missing, print the effective command with systemctl show <unit> -p ExecStart before suspecting the program.

    Finally, be careful about what you put in these files. Everything in a process's environment is readable via /proc/PID/environ by the owning user and by root, and it is shown in systemctl show output. An environment file is a fine place for a port number and a poor place for a password — which is the same lesson Kubernetes teaches when it distinguishes ConfigMaps from Secrets, and then admits Secrets are only base64.

    Two direct parallels. First, this is how kubeadm passes flags to the kubelet: its drop-in reads /var/lib/kubelet/kubeadm-flags.env and /etc/default/kubelet, then references those variables in ExecStart — the exact pattern you just built, which is why changing a kubelet flag is "edit the env file, restart the service." Second, the timing rule is identical to a pod's: environment variables taken from a ConfigMap are copied in at container start and never update when the ConfigMap changes, while a mounted ConfigMap volume does update. Same mechanism, same reason, one layer up — a process's environment is fixed at exec time.

    The four ways to consume a ConfigMap are W3.21; the update-propagation rules that make env the exception are W3.22.

    B11.9

    Read a failure from systemctl status: exit code versus signal

    Why it matters

    This is the single highest-value skill in the module. A service has failed, and systemctl status is telling you why in a format most people skim. Buried in it is one distinction that decides where you look next: did the program decide to exit, or was it killed? Those point in opposite directions — one says read the application's logs, the other says stop reading them and look at what else is on the machine — and getting it right saves the twenty minutes people routinely spend reading logs that were never going to contain the answer.

    The concept

    systemctl status has a fixed shape, and four lines carry almost all the information:

    • Loaded: — which file it came from, and whether it is enabled. A unit that is not-found or bad-setting never got as far as running.
    • Active: — the state and how long it has held it. active (running), inactive (dead), failed (Result: …), or activating (auto-restart) — that last one meaning "currently in a restart loop," which is the fault in B11.14.
    • Main PID: / Process: — the process, and in parentheses how it ended. This is the load-bearing part.
    • The last few journal lines, which are the application's own account of events (and truncated — see B11.6).

    The parenthesised ending takes one of two shapes, and they mean completely different things — this is B2.8's exit-status distinction, surfaced by systemd:

    • (code=exited, status=1/FAILURE) — the program ran, decided it could not continue, and chose to exit with that code. The program knows why. Read its logs. The status number is the program's own vocabulary: 1 is generic failure, 2 is often a usage error, 78 might mean bad configuration; the meaning is the program's to define.
    • (code=killed, signal=KILL) — the program did not decide anything; something ended it from outside. The program's logs will contain nothing about it, because it had no chance to write anything. Look outside the program. Who killed it? The OOM killer (B7.9), an operator, a timeout systemd itself enforced, or a supervisor higher up.

    The Result: field on the Active: line summarises the same thing in one word and is often faster to read: exit-code, signal, oom-kill, timeout, core-dump, start-limit-hit. Result: oom-kill in particular tells you in one glance what would otherwise take a dmesg hunt.

    A special case worth recognising: status=203/EXEC means systemd could not even execute the command — a wrong path, a missing interpreter, or a file without the execute bit. The program never ran, so its logs do not exist, and no amount of reading them will help. Its siblings 200/CHDIR (bad WorkingDirectory=) and 217/USER (unknown User=) are the same class of failure: systemd failed during set-up, before your code existed.

    code=exited→ the program chose to stop →read its logs·code=killed→ something ended it →look outside it

    One line of status decides which half of the machine you investigate next.

    Given only a status line, say where you would look next. (code=exited, status=1) → the program chose to stop, so read its logs.     Gotchas

    The failure that wastes the most time is reading application logs after a signal death. The logs are silent, so people read further back, then read more carefully, then start doubting the logging configuration — when the correct conclusion was available in the first line of status: the program did not fail, it was killed. Train yourself to look at the parenthesised ending before you look at any log line at all.

    Exit code numbers are the program's vocabulary, not a standard. status=1 tells you the program failed and nothing about why; status=78 means whatever that program's documentation says it means. The two exceptions are systemd's own set-up codes (203/EXEC, 200/CHDIR, 217/USER and friends, which are systemd's and are documented in man 5 systemd.exec) and the shell convention that a process killed by signal N reports as 128 + N when a shell reports it (B2.8) — which is why 137 means SIGKILL and 143 means SIGTERM.

    Finally, status shows the most recent attempt. During a restart loop that is the least informative one, because you are looking at attempt forty of an identical sequence. Use journalctl -u <unit> to see the whole history, and check NRestarts to find out how many attempts you are actually looking at the tail of.

    This is the same fork in the road as a pod's Error versus OOMKilled, and Kubernetes derives its version from exactly the same underlying information. A container that exits non-zero gives you lastState.terminated.exitCode — the program's own decision, so read the container logs. A container killed for exceeding its memory limit gives you reason: OOMKilled and exit code 137 (128 + 9), and its logs will be empty for the same reason yours were: SIGKILL cannot be caught, so nothing was written. When you meet the exit-code alphabet in the advanced track, you will already know why 137 is special and why reading the app's logs after it is a waste of time.

    Logs and boot

    B11.10

    journalctl with intent: one unit, follow, since, priority, boot

    Why it matters

    Half of debugging is finding the relevant lines quickly, and on a modern Linux machine those lines are not in a text file you can grep. They are in the journal, and the difference between someone who knows five journalctl flags and someone who does not is the difference between answering a question in ten seconds and scrolling through thousands of unrelated lines. This is also the exact command you will run on every unhealthy Kubernetes node, so the fluency transfers directly.

    The concept

    journald is systemd's logging service, and it collects far more than a log file ever did. Every unit's stdout and stderr are captured automatically — a program that simply prints to the screen is already logging correctly, with no configuration and no log file of its own. It also collects the kernel's messages, everything sent to the classic syslog socket, and audit records, into one merged, time-ordered store.

    The store is structured and binary, not text. Every entry carries fields — which unit produced it, the PID, the uid, the priority, the boot it belongs to — alongside the message. That is why grep /var/log/… finds nothing on a modern box, and it is a feature: you can select by field rather than hoping a regex matches. The cost is that you must go through journalctl to read it.

    The flags worth committing to memory:

    • -u <unit> — only this unit. The single most useful flag; repeatable to merge several units in time order, which is how you correlate a service with its dependency.
    • -f — follow, like tail -f. Combine with -u and restart the service in another window to watch a start-up live.
    • -n N — the last N lines (default 10).
    • --since / --until — time windows in plain language: --since "10 min ago", --since today, --since "2026-07-25 09:00".
    • -p <priority> — severity, using syslog's eight levels: emerg 0, alert 1, crit 2, err 3, warning 4, notice 5, info 6, debug 7. -p err means "err and worse," which is the fastest way to skim a noisy machine.
    • -b — this boot only. -b -1 — the previous boot, which is where the evidence lives after a crash and reboot (and requires persistence, B11.11).
    • -k — kernel messages only, the equivalent of dmesg (B3.11) but with the journal's time filters available.
    • -o <format> — output shape. short-precise adds milliseconds (essential for ordering races, as B11.5 used); cat prints the bare message with no metadata; json-pretty shows every field an entry actually carries.
    • -x — add explanatory text from the message catalogue where one exists.

    You can also select by any field directly, which is where the structured store pays off: journalctl _PID=1234, journalctl _UID=1000, journalctl _COMM=sshd. And priorities are worth understanding rather than memorising by number — a program writing to stderr gets err by default under systemd, which is why perfectly ordinary diagnostic chatter sometimes shows up red.

    The commonest waste of time is reading the journal without -u. The same is true of journalctl -u containerd one layer down. Note also the parallel: a container's stdout is collected by the kubelet exactly as a unit's stdout is collected by journald, which is why "log to stdout" is the correct advice in both worlds.

    B11.11

    Will your logs survive the crash? Journal persistence

    Why it matters

    There is exactly one moment when you need the logs from before a reboot, and it is after an unplanned reboot, when the machine came back and nobody knows why it went away. If the journal was volatile, those logs were in memory and are gone — permanently, with no recovery — and the incident becomes unexplainable. This is a five-minute check you do before you need it, and it is worth being slightly pedantic about because "we don't know why it rebooted" is a genuinely bad sentence to have to say.

    The concept

    journald stores the journal in one of two places, and which one is decided by the Storage= setting in /etc/systemd/journald.conf:

    • /run/log/journal/ — volatile. /run is a tmpfs (B5.9), which means memory: fast, self-cleaning, and erased completely at every boot.
    • /var/log/journal/ — persistent. On disk, survives reboots, and is what makes journalctl -b -1 possible.

    The default is Storage=auto, and this is the part worth reading carefully because it is unusual: auto means "persistent if /var/log/journal/ exists, volatile otherwise" — and it will not create the directory. So the existence of a directory, not a configuration value, is what decides whether your logs survive. Distributions differ on whether they ship it, which is why the honest instruction is "check on your machine" rather than "it is on by default."

    That gives you two ways to enable persistence, and they are equivalent in effect:

    • Create the directory and restart journald — sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald. This works because auto then finds it. (systemd-tmpfiles --create --prefix /var/log/journal creates it with the right ownership and permissions, which is the tidier form.)
    • Set it explicitly with a drop-in — Storage=persistent in /etc/systemd/journald.conf.d/ — which also creates the directory, and states the intent in a file rather than leaving it implicit in a directory's existence. Preferable on anything you care about.

    Persistence brings a disk-space question with it, which journald answers with limits you can set: SystemMaxUse= (total cap, default 10% of the filesystem), SystemKeepFree= (leave this much free), MaxRetentionSec= (discard entries older than this) and MaxFileSec= (rotate at this age). journald enforces these itself — there is no logrotate involved — and you can clean up on demand with journalctl --vacuum-size=200M or --vacuum-time=7d. Checking journalctl --disk-usage occasionally is a reasonable habit; an unbounded journal on a small root filesystem is a real way to fill a disk.

    B11.12

    The boot picture: targets, what took so long, and the cgroup tree

    Why it matters

    Two questions come up on every real machine: "what is this box supposed to be running?" and "why does it take four minutes to boot?" Both are answered by tools you already have and probably have not used. And the third command in this lesson, systemd-cgls, prints something worth more than either: the whole machine's process tree organised by who is accounting for what — which on a Kubernetes node is the entire layout of the node in one screen.

    The concept

    Targets replaced the old numbered runlevels with something you can read. A target is a named group of units (B11.2), and the default target is the goal systemd works toward at boot: reach it, and the machine is considered up. On a server that is multi-user.target — networking, logins, services, no graphical session. On a desktop it is graphical.target, which itself pulls in multi-user.target. Others you will meet: rescue.target (single-user, minimal), emergency.target (barely anything, a shell on the console), and the synchronisation points network.target, network-online.target (B11.5) and timers.target.

    Boot analysis is two commands. systemd-analyze prints how long the phases took (firmware, loader, kernel, userspace). systemd-analyze blame ranks units by how long each took to start — useful, but read it with the caveat below. systemd-analyze critical-chain is the more honest one: it follows the ordering chain that actually delayed reaching the target, which is what you want, because a slow unit that nothing waits for delays nothing.

    The cgroup tree is the part that connects this module back to B7.12. systemd does not merely start processes; it places every one of them in a cgroup, and it organises those cgroups into a deliberate hierarchy:

    • system.slice — the machine's services. Every unit you have written in this module lives here.
    • user.slice — logged-in users, one user-<uid>.slice each, containing a .scope per session. A scope is a cgroup for processes systemd did not start but has adopted for accounting — your SSH session is one.
    • init.scope — PID 1 itself.

    Because every unit is a cgroup, every unit can carry resource limits without any of B7's file editing: MemoryMax=, CPUQuota=, TasksMax= and friends in the unit file (or via systemctl set-property) are written straight into cpu.max, memory.max and pids.max for you. You used one already — MemoryMax=32M in B11.9 — and it produced a genuine cgroup OOM kill.

    That is why systemd-cgls on a Kubernetes node is such a good picture: you see system.slice holding kubelet.service and containerd.service, and right next to it kubepods.slice holding one cgroup per pod, with the pods' containers nested inside. The node's whole resource story — what is the platform, what is the workload, and who is accounted where — in one tree.

    Gotchas

    systemd-analyze blame is the most misused command in this lesson. People "optimise" boots by disabling the top entry and are then puzzled that nothing improved. Use critical-chain to find what was actually on the path, and treat blame as a curiosity.

    Do not hand-edit the cgroup files systemd owns. Writing to /sys/fs/cgroup/system.slice/foo.service/memory.max works for a moment and is then reasserted by systemd at the next reload or restart, silently reverting your change (the same lesson as B7.12). Set the property on the unit — in the file, in a drop-in, or with systemctl set-property — and let systemd write the file.

    Finally, systemctl set-property is persistent by default: it writes a drop-in under /etc/systemd/system/<unit>.d/ and the setting survives reboots. If you want a temporary change, pass --runtime. Discovering months later that a limit you set "just to test" is still in force, in a file you did not write by hand, is an avoidable kind of confusion — and systemctl cat is how you find it.

    Run systemd-cgls on a Kubernetes node and the whole node is on one screen: system.slice holding kubelet.service and containerd.service — the platform — and kubepods.slice beside it holding one cgroup per pod, subdivided by QoS class, with each container's processes nested inside. That layout is not decoration: it is how a node reserves resources for itself so that a runaway pod cannot starve the kubelet, and it is where a pod's requests and limits physically land as cpu.weight and memory.max. Everything you set here with MemoryMax= on a unit, Kubernetes sets on a container's cgroup for the same reason and with the same result at OOM time.

    B11.13

    Mini project — promote your supervisor into a real service, and schedule a job

    Why it matters

    In B2.17 you wrote a supervisor: fork a child, wait for it, decide from the exit status whether to restart, back off, forward SIGTERM. It was about fifty lines and it worked. Now you retire most of it — because everything it does by hand, systemd does by declaration — and keep the part that is genuinely yours. That trade is the whole point of this module, and doing it deliberately is what makes the abstraction stick: you are not learning a tool, you are recognising which of your own code a tool replaces. Then you add a scheduled job, because the second half of "keeping a machine running" is doing things on time.

    The concept

    Two deliverables, each a few lines of configuration:

    1. supervisor.service — your B2.17 script, run as a proper unit: Restart=on-failure with a real RestartSec backoff (B11.4), its command supplied by an EnvironmentFile so an operator can change what it supervises without touching the unit (B11.8), running as an unprivileged user, logging to the journal by doing nothing at all (B11.10), and enabled so it survives a reboot (B11.6).
    2. sysreport.timer + sysreport.service — B1.15's sysreport.sh run hourly. The service is Type=oneshot (it does a job and exits, B11.4); the timer says when. OnCalendar=hourly sets the schedule and Persistent=true means "if the machine was off when a run was due, run it once at the next boot" — the thing cron never did.

    Notice what your script no longer needs to do. The restart loop, the backoff, the signal forwarding on shutdown, the "did it exit or was it killed" decision — all of it is now three lines of unit configuration, applied uniformly to every service on the machine, with logging and resource accounting attached for free. What remains yours is the part that was always the interesting bit: the policy about this particular child. That is exactly the trade Kubernetes offers one layer up, and recognising it here is why the cluster's version will feel familiar rather than magical.

    Gotchas

    The commonest failure here is status=203/EXEC (B11.9) on first start, and it is almost always one of three things: a relative path in ExecStart, a script without the execute bit, or a missing shebang. systemd is not running a shell, so it cannot find things on PATH and cannot guess an interpreter.     The second is User=ubuntu combined with root-owned paths. Note also that you enable the timer, never the service: enabling the service would run it at every boot, which is not what a schedule means. And Persistent=true is what makes a missed run catch up after downtime; without it, a machine that was off at noon simply skips noon.

    You have just built, at node scale, the two things Kubernetes offers at cluster scale — and the correspondence is exact. supervisor.service with Restart=on-failure is a Deployment's pod with restartPolicy: OnFailure: a declared intent to keep something running, with backoff, restart counting and logs collected. sysreport.timer is a CronJob: OnCalendar is the schedule, Type=oneshot is the Job that runs to completion, and Persistent=true is the missed-run behaviour that startingDeadlineSeconds governs in the cluster version. The difference is scope, not concept — systemd supervises one machine's processes, Kubernetes supervises a cluster's containers — and every question you can ask here (did it run, why did it fail, what did it print, when is it next due) has a direct counterpart there.

    The workload zoo including Job and CronJob is W3.10; how the kubelet, itself a unit exactly like the one you wrote, supervises everything else on a node is W1.19.

Its siblings 200/CHDIR (bad WorkingDirectory=) and 217/USER (unknown User=) belong to the same class: systemd failed during set-up, before your code existed, so reading application logs is guaranteed to be wasted effort. Fix by making the command executable and correct: ls -l the path, check the shebang, use an absolute path. Variant B is status=78: the program ran, decided it could not continue, and said why on stderr — which journald captured, so the answer is in journalctl -u broken. Fix the thing it complained about. Had you instead seen (code=killed, signal=KILL) you would be in the third case entirely: nothing the program logged will help, because it was ended from outside — look for the OOM killer (Result: oom-kill, B7.9), a timeout, or an operator. The reflex: read the parenthesised ending before you read a single log line — it tells you whether the logs are worth reading at all.

    Symptom 2 — the service looks busy, and is actually failing forty times a minute
    1. A service with Restart=always and a broken configuration. Watch how it presents: not as failed, but as activating (auto-restart) — which reads like "starting up" and is in fact "dying repeatedly." The tell is not in status's state line but in its counters and its journal. 
      sudo tee /etc/systemd/system/looper.service >/dev/null <<'EOF'
[Unit]
Description=Fault 2
StartLimitIntervalSec=0
[Service]
ExecStart=/bin/sh -c 'echo "FATAL: no such database host: db.invalid" >&2; exit 1'
Restart=always
RestartSec=1s
EOF
sudo systemctl daemon-reload; sudo systemctl start looper; sleep 8
systemctl status looper --no-pager | grep -E 'Active:|Main PID:'
systemctl show looper -p NRestarts --value
journalctl -u looper --since '20 sec ago' --no-pager -o cat | sort | uniq -c
      Active: activating (auto-restart) (Result: exit-code) since ...     ← not "failed"
NRestarts=7                                    ← seven attempts in eight seconds
      7 FATAL: no such database host: db.invalid   ← the same error, over and over
    Cause & fix

    Restart=always is converting a permanent configuration error into an endless loop, and the loop is disguising itself as start-up activity. The service can never work — the host it needs does not exist — but because it is restarted every second, it spends most of its life in activating (auto-restart), which does not read as a failure and does not necessarily alert. Three tells identify it, and any one is enough: the state is activating (auto-restart) rather than active or failed; systemctl show -p NRestarts is a number that keeps climbing; and the journal contains the same message repeating, which sort | uniq -c makes obvious in one command. Note what defeats the naive approach: systemctl status shows only the last ten journal lines, so during a loop you see three copies of one error and may conclude it happened three times — always go to journalctl -u <unit> for the count. (This unit sets StartLimitIntervalSec=0 to disable the rate limiter and keep the loop running; a real unit with default settings would instead hit the limiter after five attempts and stop with "start request repeated too quickly" — B11.4 — which is systemd doing you the favour of turning an infinite loop into a visible failure.) Fix the configuration, then systemctl reset-failed looper to clear the state and counter, and consider whether Restart=on-failure with a longer RestartSec would have made the fault visible an hour earlier. The reflex: a service that is always "starting" is a service that is always dying — check NRestarts and count the repeats in the journal before you believe the state line.

    Gotchas

    The two faults fail in opposite directions, which is why they are paired. The first is loud and immediate — the unit is failed, nothing is running, someone notices in seconds — and its entire difficulty is choosing the right place to look, which one word of status decides for you. The second is quiet and durable: it can run for weeks, because "restarting" does not look like "broken", the process really does exist for a fraction of every second, and a health check that only asks "is the unit loaded" will say yes. Ranked by how much time they waste, the quiet one wins easily.

    Both have a one-command discriminator worth keeping together. Failed to start → read the parenthesised ending: 203/EXEC means the program never ran, status=N means it chose to stop and its logs will say why, signal=KILL means look outside it. Suspiciously busy → systemctl show <unit> -p NRestarts, then journalctl -u <unit> | sort | uniq -c to see whether one error is repeating. Two commands, and between them they cover most of what goes wrong with services on a Linux machine.

  sudo systemctl disable --now $u 2>/dev/null; sudo systemctl reset-failed $u 2>/dev/null
done
sudo rm -rf /etc/systemd/system/{broken,looper,hello,supervisor,sysreport}.service \
            /etc/systemd/system/sysreport.timer /etc/systemd/system/hello.service.d \

sudo systemctl daemon-reload; systemctl --failed --no-pager | tail -1
    0 loaded units listed.        ← a clean machine again

    Both faults have exact counterparts one layer up, and you will meet them constantly. The first is a pod whose container exits immediately: 203/EXEC corresponds to a bad command or entrypoint (the container never ran, so kubectl logs is empty and the answer is in the pod's events); a non-zero exit code corresponds to an application that started and gave up, where the logs do hold the answer; and a signal death corresponds to OOMKilled with exit 137, where the logs are silent for the same reason as here. The second fault is CrashLoopBackOff in every particular: a container restarting endlessly because of a permanent error, where the restart count is the tell, the current attempt's logs are the least useful ones, and kubectl logs --previous exists precisely because of the problem you just solved with journalctl and uniq -c.

    B11 recall quiz

    Answer out loud before revealing. If you can read a failed unit's status and say in one sentence where you would look next — and explain why the kubelet is the only Kubernetes component systemd knows about — this module has done its job.

    1. What are PID 1's three duties, and what does the kernel do differently for it?
      Answer

      Bring the machine to a working state, supervise what is running, and adopt-and-reap every orphan the kernel reparents to it. The kernel treats it specially by not delivering signals with a default action unless PID 1 has installed a handler — which protects the machine (a dead PID 1 panics the kernel) and explains why a container process with no SIGTERM handler ignores the polite stop and dies only to the later SIGKILL.

    2. Name the five unit types you will actually meet and what each manages.
      Answer

      .service (a process to run and supervise), .socket (a listening socket that starts the service on first connection), .timer (a schedule that starts another unit — cron's replacement), .target (a named group of units and a synchronisation point, with no process of its own), .mount (a filesystem; every fstab line becomes one). Bonus: .slice and .scope are the cgroup types from B11.12.

    3. Where do unit files live, in what precedence order, and why does that matter?
      Answer

      /etc/systemd/system/ (yours, highest) → /run/systemd/system/ (runtime) → /usr/lib/systemd/system/ (the vendor's, lowest). It matters because editing the vendor copy works right up until the next package upgrade silently replaces the file and reverts your change. Write your own units in /etc/, and override vendor units with drop-ins.

    4. You wrote a unit file and nothing you change has any effect. What did you forget?
      Answer

      systemctl daemon-reload. systemd caches unit files and does not notice edits by itself, so restarts keep applying the version it read last — with no error, which is what makes it so confusing. The rhythm is: edit → daemon-reload → restart → status.

    5. What does Type= decide, and what goes wrong if you declare simple for a daemon that forks?
      Answer

      It decides when systemd may consider start-up finished — and therefore which process it supervises. Declare simple for a forking daemon and systemd watches the original process, which exits immediately after forking; it sees the service die instantly, restarts it per policy, and the real daemons pile up in the background unmanaged. The symptom is "systemd keeps restarting it but it is clearly running"; the fix is Type=forking (usually with PIDFile=).

    6. A unit has Requires=db.service and no After=. What can go wrong, and when?
      Answer

      It can start before the thing it requires, because requirement and ordering are independent and systemd starts units in parallel. It fails only on a cold boot, when both start at once and the dependency loses the race — never when you restart by hand, because then the dependency has been up for hours. That is the classic "works on reboot, fails at boot" bug. The fix is one line: add After=db.service; the default pairing to reach for is Wants= plus After=.

    7. What is the difference between start and enable, and what single command does both?
      Answer

      start acts on the running system now and is forgotten at reboot; enable creates a symlink so the unit is wanted at the next boot and does nothing to the running system. "Gone after the reboot" is start without enable; "enabled but nothing happened" is the reverse. systemctl enable --now <unit> does both.

    8. You want to change one setting on a package-installed unit. What do you do, and what is the trap when the setting is ExecStart?
      Answer

      Write a drop-in: /etc/systemd/system/<unit>.d/10-something.conf with only the keys you want, then daemon-reload (or use systemctl edit, which does both). The trap is that ExecStart= is list-valued and accumulates, so your line is appended to the vendor's and systemd refuses the unit with "more than one ExecStart= setting." Clear the list first with a bare ExecStart=, then set yours. Confirm the result with systemctl cat.

    9. You edited a service's EnvironmentFile and nothing changed. Why, and what is the Kubernetes parallel?
      Answer

      The environment is read and copied into the process when it starts; nothing can change a running process's environment from outside, so the file takes effect only on restart. The exact parallel is a pod's environment variables sourced from a ConfigMap: they are set at container start and never update when the ConfigMap changes, while a mounted ConfigMap volume does update. Same mechanism, same reason.

    10. Process: 1234 ExecStart=… (code=exited, status=1) versus (code=killed, signal=KILL). Where do you look in each case?
      Answer

      code=exited means the program ran and chose to stop, so it knows why — read its logs. code=killed means something ended it from outside, so its logs contain nothing about it — look outside the program: the OOM killer (Result: oom-kill), an operator, or a timeout. A third case, status=203/EXEC, means systemd could not execute the command at all, so no program logs exist: check the path, the execute bit and the interpreter.

    11. What does Storage=auto actually do, and why should you care before an incident rather than after one?
      Answer

      It stores the journal persistently in /var/log/journal/ if that directory exists, and volatilely in /run/log/journal/ otherwise — and it will not create the directory. So a directory's existence, not a setting, decides whether logs survive a reboot. You care in advance because a volatile journal looks completely normal until the machine reboots unexpectedly, at which point journalctl -b -1 has nothing and the incident is permanently unexplainable.

    12. Why is systemd-analyze critical-chain a better answer than blame to "why was the boot slow"?
      Answer

      blame ranks units by how long each took to start, regardless of whether anything was waiting for them — a slow unit that nothing depends on delays nothing, so the top entry is frequently irrelevant. critical-chain follows the ordering dependencies that actually delayed reaching the target, which is the question you meant to ask.

    13. What does systemd-cgls show on a Kubernetes node, and why is that one screen worth so much?
      Answer

      system.slice holding kubelet.service and containerd.service — the platform — beside kubepods.slice holding one cgroup per pod, subdivided by QoS class, with each container's processes nested inside. It is the node's entire resource story in one tree: what is platform, what is workload, and who is accounted where. It is also where a pod's requests and limits physically land, as cpu.weight and memory.max.

    14. Why is the kubelet the only Kubernetes component systemd manages?
      Answer

      Because of a chicken-and-egg problem: the API server cannot be scheduled by machinery that only exists once the API server is running. The escape hatch is the static pod — the kubelet reads pod YAML from a directory on disk and runs it with no API server involved. So the boot order is systemd → kubelet → everything else, and "restart the API server" means moving a manifest file, not running systemctl restart.
