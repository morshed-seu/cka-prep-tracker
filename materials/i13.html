    I13 — Capstone: build minidock, then the gauntlet

    No new concepts — assembly and proof. Every module's mini project becomes one layer of a single tool that pulls, unpacks, runs, networks, mounts, logs and supervises containers. Then eight planted faults, against a clock.

    This is the module where the track stops explaining and starts asking. Thirteen modules have each handed you one working piece; nothing so far has made you hold all of them at once. The value is not the program — the program is about eleven hundred lines and you could read someone else's in an afternoon. The value is that every design decision you have been told about arrives at your desk as a decision you have to make, in the order the machine forces, and you discover that you already know the answer. That is a different kind of knowing than passing a quiz about it.

    Checkpoints12 Hours~8 PrerequisitesI0–I12
    • Capstone — build minidock in six layers: a content store, a snapshotter, a runtime bundle plus shim, a CNI attachment, volumes and CRI-format logs, and a platform layer with a metadata store, a CLI and a restart reconciler.
    • Gauntlet — eight planted faults, one per layer, against a clock; then a written post-mortem of your own triage order; then the same run again to watch a routine beat improvisation.
    • Assessment — a written self-test across I0–I12, a practical task set with a rubric, and an explicit readiness checklist for the advanced track.

    All of I0–I12, and the artefacts they produced: pull.py, oci-inspect.py, microshim.py, tinybuild.py, cni-minibridge and volman.py. If a module still has unticked checkpoints, finish it first — debugging two unfamiliar layers at once is how people conclude they are bad at this.

    Which machine. The same sandbox VM every intermediate module has used: Ubuntu 24.04, kernel 6.8.0, cgroup v2, with containerd 2.3.3, runc 1.5.1, CNI plugins v1.9.1 plus your cni-minibridge installed as /opt/cni/bin/minibridge, BuildKit v0.32.0, a local registry:2 on 127.0.0.1:5000, and Python 3.12.3. Everything below runs as root, and honestly so — every layer needs a capability an ordinary user does not have: mknod for whiteouts, mount for overlayfs, clone for the namespaces, netlink for the bridge. I11's rootless stack is the alternative and it needs a helper for every one of them.

    The finished program ships with this track as labs/intermediate/minidock.py. Write your own first and read that afterwards — every checkpoint below is worth more attempted than copied. Where the two differ, yours is not wrong; there are several defensible answers to most of these and the lessons say which decision is which.

    Capstone — minidock, one layer at a time

    I13.1

    Layer 1 — pull and store

    Why it matters

    A container starts as bytes you do not have. Before anything can run, something has to fetch those bytes over HTTP, decide whether to believe them, and file them somewhere it can find them again. That "file them somewhere" is a content store, and it is the first thing every runtime in this ecosystem builds — because once you have one, half the hard problems in image distribution turn into lookups.

    The concept

    You already wrote the network half of this in I5: pull.py does the token dance, resolves a tag to an index, picks a platform out of the index, and fetches a manifest, a config and some layers. What it did not do is decide where those bytes live afterwards. That decision is the layer.

    Two stores, and the argument for splitting them writes itself the moment you try. Blobs are content-addressed: the file's name is the SHA-256 of its own contents, so the name is a checksum and any blob can always be fetched again from a registry. Names — the mapping from alpine:3.21 to a manifest digest — cannot be recomputed from anything. They are the only fact in the store with no upstream. I7.11 found containerd making exactly this split, with the content store holding 472 files and meta.db being the one store with nothing to rebuild it from; here you arrive at the same shape from first principles, and you should keep the two in separate directories for the same reason. When the gauntlet plants a corrupted blob, being able to delete one store and keep the other is the difference between a one-line fix and re-pulling everything.

    Verify on write. As each blob streams in, hash it; compare against the digest the manifest claimed; and only then rename it into place. The rename is the whole atomicity story — a partial download is called .partial until its bytes have been proved, so an interrupted pull can never leave a file a later run will trust. This is the one class of error content addressing hands you for free, and it costs a hash of bytes you are already reading.

    Deduplication is a side effect, not a feature. If the blob's path is its digest, then "have I got this already?" is os.path.exists, and two images sharing a base layer share it automatically because they name it identically. You do not write a deduplication algorithm; you write a file path.

    The registry protocol has an opinion on verification, and it is weaker than you might expect:

    Clients SHOULD verify that the response body matches the requested digest.
    OCI distribution-spec v1.1.1, §"Pulling blobs" — spec.md

    SHOULD, not MUST — and the same section says of the Docker-Content-Digest header that "Most clients MAY ignore the value". So a conformant client is allowed to trust whatever the registry sends. That is worth knowing before you decide your own tool's behaviour: verifying is a choice the format makes cheap and the specification does not force.

    Verify

    minidock pull of an image you already have fetches zero payload bytes and prints cached for every blob. Two images sharing a base store that base once. A blob whose bytes you corrupt produces an error naming the digest, and minidock verify finds it without being told where to look.

    Gotchas
    • Verify-on-write is not verify-on-read. Every registry client in this ecosystem, yours included, hashes a blob once — as it arrives — and then trusts the filename forever. That is a defensible trade (a full re-hash costs a read of the whole store) right up until a bit rots, which is why a verify subcommand belongs in the tool even though nothing calls it automatically.
    • Do not put the name index inside the blob directory. It is tempting — one directory, fewer paths — and it destroys the property that makes the blob store safe to delete wholesale.
    • The digest in the manifest and the digest of the manifest are different things. The manifest's own digest is computed over its exact bytes, so re-serialising the JSON before storing it changes the digest and breaks every reference to it. Store the bytes you received, never the object you parsed.

    This layer is what fails when a pod reports ErrImagePull or ImagePullBackOff, and knowing it is two stores explains why the two states differ from "the image is corrupt on one node and fine on the others" — see 6.17 — Image failures: ErrImagePull, ImagePullBackOff, and the three real causes. The kubelet never talks to a registry itself; it asks the CRI's image service, which owns exactly the store you just built.

    Docs: distribution-spec §"Pulling blobs" and §"Content Digests"; image-spec §"Image Layout" for why blobs/sha256/ is the path it is.

    I13.2

    Layer 2 — unpack and snapshot

    Why it matters

    A layer in the store is a gzipped tar file. A container needs a directory tree it can be chrooted into. Turning the first into the second is the job of a snapshotter, and it is where "images are layers" stops being a diagram and becomes a mount command with a very particular argument order.

    The concept

    Three decisions, in increasing order of how easy they are to get wrong.

    What to key the cache on. Not the layer digest — the chain ID. I4.12 argued this and the reason only lands once you build it: two images sharing a base must share unpacked directories up to the exact point their chains diverge, and not one layer further. A layer's digest identifies the layer; the chain ID identifies "this layer applied on top of exactly those layers", which is what a directory on disk actually represents. The recursion is containerd's, not the spec's — sha256("<parent> <diff_id>"), one space, both operands keeping their sha256: prefixes — and the base case is that a one-layer image's chain ID is its diff_id.

    How to represent a deletion. This is the fiddly part and the one worth writing by hand. The image format marks a deleted file with a zero-length file named .wh.<name>. The kernel's overlayfs marks one with a character device numbered 0:0. No kernel has ever heard of the first convention, so somebody has to translate — and in your program, that somebody is about eight lines in the middle of the extract loop. Getting it wrong produces containers with ghost files that no amount of image inspection will explain, because the image is fine.

    How to stack them. One mount -t overlay with lowerdir= listing every snapshot directory topmost first — the reverse of the order the layers are applied in. B5 built this by hand; the only new thing here is that the list is computed from a manifest.

    The whiteout rules are spelled out precisely, and two of them are easy to miss:

    A whiteout file is an empty file with a special filename that signifies a path should be deleted.
    A whiteout filename consists of the prefix .wh. plus the basename of the path to be deleted.
    Once a whiteout is applied, the whiteout itself MUST also be hidden.
    Whiteout files MUST only apply to resources in lower/parent layers.
    OCI image-spec v1.1.1, §"Whiteouts" — layer.md

    "The whiteout itself MUST also be hidden" is the rule your extractor obeys by never creating the .wh. file at all. And the spec defines a second form — .wh..wh..opq, "indicating that all siblings are hidden in the lower layer" — which maps to the trusted.overlay.opaque=y xattr rather than to a device node. Both encodings are legal, so handle both and never infer which producer made an image from which one it used.

    Lab
    1. Prove the cache exists by removing it. Run the same image twice with the unpack timer on. 
      sudo rm -rf /var/lib/minidock/snapshots

MINIDOCK_DEBUG=1 sudo -E minidock run --rm --network none alpine:3.21 true

  unpack: 0.000s for 1 layers

      Fifty milliseconds for three and a half megabytes, then nothing. On a 300 MB image the first number is seconds and the second is still nothing, which is the entire reason a node that has run a pod once starts the next one so much faster.

      Identical. For a single-layer image there is no parent to hash in, so the chain ID is the diff_id — and I7.12 found containerd's snapshot key doing exactly the same thing for the same reason.

      for d in /var/lib/minidock/snapshots/*/; do sudo cat "$d/.committed"; echo; done
      {"chainID": "sha256:438ca0cd...", "layer": "sha256:c383e1fe...", "whiteouts": 0, "opaques": 0}

      Three whiteouts, zero opaques — for a step that deleted an entire directory. BuildKit emitted one .wh. entry per former child (one, two) plus one for /etc/motd, rather than a single .wh..wh..opq. I4.7 found containerd's walking differ making the same choice. Both are conformant; your unpacker must handle either and must not assume which it will get.

    5. The translation, on disk. Look at the same four paths across the three snapshot directories. 
      sudo find /var/lib/minidock/snapshots -name motd -o -name one -o -name two -o -name new \
  | sort | xargs -r sudo ls -l

crw------- 1 root root 0, 0 .../78c42788.../fs/opt/app/two

      That listing is the whole idea in seven lines. /etc/motd still exists, 284 bytes of it, in the base snapshot — nothing was deleted. What the top layer holds instead is crw------- 0, 0, a character device with major 0 and minor 0, which is overlayfs's way of saying "whatever is underneath this name, pretend it is not there". The .wh. files never reached the disk.

    6. Finally, the mount that makes it one tree. Start something and read the mount options back. 
      sudo minidock run -d --network none --name stack 127.0.0.1:5000/i13/wh:v1 sleep 30

      Read the lowerdir list against the .committed files above: 78c42788 is the top layer and it is listed first. Get that order backwards and the container boots into its own base image with every later change invisible — which looks exactly like having pulled the wrong tag.

    Verify

    The second container from an image starts with a zero-second unpack. Your snapshot directories are named by chain ID, and for a single-layer image that name equals the config's diff_id. An image that deletes a file produces a 0, 0 character device in the upper snapshot and the original file, untouched, in the lower one — and the container sees neither.

    Gotchas
    • lowerdir is topmost-first. Every other list in this pipeline — manifest layers, diff_ids, history — is base-first. This one is reversed, and the failure is silent.
    • Handle both whiteout encodings. A producer may emit per-child .wh. entries or one .wh..wh..opq; the same rm -rf can legally produce either.
    • Extract each layer into its own directory. The tempting alternative — extract every layer into one tree and hand that to chroot — works, and throws away the entire cache: nothing is shared between two images, and every container costs a full unpack.
    • Unpacked size is not image size. I7.11 measured a 691 MB content store against a 2.2 GB snapshotter. It is the second number that fills a node.

    This is the layer behind DiskPressure and the evictions that follow it — see 6.12 — Read node Conditions fluently: MemoryPressure, DiskPressure, PIDPressure. When a node runs out of disk it is almost never the image list that did it; it is this directory, at roughly three times the compressed size, times every image ever run there.

    Docs: image-spec §"Whiteouts" and §"Applying Changesets"; man 5 overlayfs (kernel docs filesystems/overlayfs.rst) for lowerdir ordering and the 0:0 whiteout convention.

    I13.3

    Layer 3 — run

    Why it matters

    Here is where the track's thesis becomes forty lines of your own code. "Running an image" turns out to mean one thing: translating an image config into a runtime config. Everything else — the namespaces, the cgroup, the mounts — is boilerplate you copy once. The translation is the whole job, and it is why the two specifications are separate documents.

    The concept

    The image config says what the author wanted: an entrypoint, some default arguments, environment variables, a working directory, a user. The runtime config says what the kernel is told: an args array, a namespace list, a cgroup path, resource limits. Your function reads the first and writes the second, and every interesting behaviour of every container tool lives in the small decisions it makes on the way.

    Three of those decisions are worth naming, because you have already met all three as bugs.

    • Overriding the entrypoint discards the image's Cmd unless arguments are also given (I4.14). This is exactly a pod spec with command: and no args:, and the run then prints an empty line and exits 0. The spec is silent on it; the behaviour is convention.
    • A numeric user always works; a named user has to be looked up inside the image. I2.11 found a uid absent from the rootfs starting fine and failing later with a permission error, while ctr run --user appuser answers no users found — because resolving a name means reading /etc/passwd from a filesystem the tool has not mounted. Your version has mounted it, so you can do better.
    • Resource flags are a unit conversion. --cpus 0.2 becomes quota 20000 / period 100000; --memory 64m becomes a byte count. No cleverness — but note that OCI memory.swap is memory plus swap (I2.9), so equal values mean no swap at all rather than "the same amount of swap".

    Then something has to stay alive. runc will not: it sets up the container, execs away and leaves (I3.2). If nothing holds the container's stdout, the output goes nowhere; if nothing waits on it, the exit status is lost to the kernel. That is what a shim is for, and I3.13's microshim.py is already the answer — a process that owns the pipes and collects the status. Detaching is then just fork(): the parent deliberately does not wait, so the shim re-parents to PID 1 and the CLI's exit means nothing to the container.

    The image specification says outright that its config is a starting point, not an instruction:

    The execution parameters which SHOULD be used as a base when running a container using the image. This field can be null, in which case any execution parameters should be specified at creation of the container.
    OCI image-spec v1.1.1, .config property — config.md

    "As a base" is the licence for every override flag your tool has, and "can be null" is why an image with no config at all is legal — the caller is then required to supply everything. Read that sentence as the formal statement of what this layer does.

      SHIM=$(sudo ps -eo pid,args | awk '/[m]inidock run -d --name lim/{print $1}' | head -1)

      The workload is still running. Its supervisor re-parented to PID 1 and nothing collected anything. minidock ps will say running forever, because the only process that was ever going to update that record is the one you just killed — and the exit code, whenever it comes, has nowhere to go.

      This is the honest answer to "what does containerd actually add?". I7.14 measured the same experiment against the real thing: containerd monitors the shim's ttrpc socket, logs shim disconnected and cleaning up dead shim, and reaps the orphan within about two seconds. Your version has no monitor, so the orphan is permanent. Writing that gap yourself is a better explanation of containerd's value than any diagram.

    Verify

    You can point at the specific lines that turn an image config into a runtime config, and say what each override flag does to the result. --memory and --cpus appear in /sys/fs/cgroup with the values you expect. A detached container survives its CLI, and you can state precisely what happens when its shim dies and why the real runtime behaves differently.

    Gotchas
    • runc will not stay. If you skip the shim and let the CLI run runc run directly, your tool works perfectly until the first time somebody closes the terminal.
    • An empty args array is a runtime error, not a default. If the image declares neither Entrypoint nor Cmd and the user gave no command, fail loudly at translation time — the alternative is a confusing failure from runc about an executable it cannot find.
    • runc warns and continues on unknown capability names. I2.14 found this: the spec says it MUST error, runc says ignoring unknown or unavailable capabilities, and a typo in a hardening config silently produces an empty capability set.
    • Do not hardcode overrides on exec. As above — it makes a correct runtime look broken, and you will chase it in the wrong layer.

    The chain you have just built by hand is drawn end to end in 1.20 — Understand CRI: kubelet → containerd → shim → runc, and the flags you translated are the subject of 3.16 — Requests vs limits: scheduler bookkeeping vs cgroup enforcement. That lesson's central point — that a request never reaches the kernel while a limit becomes exactly the two files you just read — is much harder to forget once you have written the function that does or does not write them.

    Docs: runtime-spec config.md (process, root, linux.resources, linux.namespaces); image-spec config.md for the .config properties you are translating.

    I13.4

    Layer 4 — network

    Why it matters

    This is the layer where you write the least code and learn the most. minidock contains no networking code at all — not one ip link, not one iptables rule. It creates an empty network namespace, executes a binary, writes JSON to that binary's stdin, and reads JSON back from its stdout. Everything else is somebody else's program. That is the entire CNI contract, and implementing it is the cleanest demonstration in this track of what "a contract rather than a special case" buys you.

    The concept

    B9 built a pod network by hand: a namespace, a veth pair, a bridge, an address, a route, a masquerade rule. I9 took that same script and rewrote it as cni-minibridge — identical mechanism, wrapped in a contract. Now you are on the other side of that contract, writing the runtime.

    The runtime's half is four things:

    1. Create the namespace first, before anything runs in it. ip netns add makes a bind mount under /run/netns/, which keeps the namespace alive with no process inside it. I8.5 measured real containerd doing exactly this — the pod's network namespace is pinned by a bind mount before the pause container exists, and the sandbox's own config then joins it by path. The namespace is not made by the process; the process is put into the namespace.
    2. Call loopback first. A fresh namespace answers ping 127.0.0.1 with "Network is unreachable" (I9.10). Every real runtime attaches loopback, and the reference plugin for it exists precisely because everyone needs it.
    3. Pass parameters in the environment and configuration on stdin, then parse the result. CNI_COMMAND, CNI_CONTAINERID, CNI_NETNS, CNI_IFNAME, CNI_PATH — and CNI_ARGS carrying IgnoreUnknown=1, without which the reference bridge plugin rejects unknown arguments outright with code 999 (I9.6).
    4. Call DEL on teardown, and make teardown survive being run twice. This is not politeness; it is the contract, and it is where leaks come from.

    Because you have implemented the runtime side, you can now perform the test that proves the contract is real: change one string — "type": "minibridge" to "type": "bridge" — and the reference plugin takes over with no change to your program. If that works, you built an interface. If it does not, you built a special case with a JSON accent.

    The whole of the runtime's obligation, in two sentences:

    The runtime passes parameters to the plugin via environment variables and configuration. It supplies configuration via stdin. The plugin returns a result on stdout on success, or an error on stderr if the operation fails. Configuration and results are encoded in JSON.
    CNI spec v1.1.0, §2 "Executing plugins" — SPEC.md at library tag v1.3.0

    Note where that text lives: the file describing spec 1.1.0 sits at library tag v1.3.0, because the CNI repository's tags are library releases and not spec versions (I9.1). Note also what the specification never says: it contains no mention of /etc/cni/net.d, /opt/cni/bin, or lexical file ordering. Those are your runtime's policy — and in minidock the "policy" is a Python dict, which is a perfectly conformant way to configure one network.

    • Delete the namespace after DEL, never before. A plugin that reads the container's address out of the namespace returns success on a namespace that is already gone — correctly, per the idempotency MUST — and silently leaks whatever it could not find.
    • Capability arguments must be replayed on DEL. Port mappings passed as CAP_ARGS on ADD have to be passed again on DEL or the DNAT rules survive. cnitool does not do this; containerd does (I9.11).
    • The bridge outlives every container, sitting there NO-CARRIER,DOWN with nothing attached. That is normal and the reference plugin does the same; do not "fix" it.

    I13.5

    Layer 5 — volumes and logs

    Why it matters

    Two features that look unrelated and are the same feature: both are about data that has to outlive the process producing it. A volume outlives the container; a log outlives the moment the line was printed. And both force the same unpleasant question, which is what to do when there is more of it than you have room for.

    The concept

    Volumes are the easy half. A named volume is a directory on the host and a bind mount in config.json — that is all. volman.py from I10 added a real size limit by putting an ext4 filesystem on a loop device, which is the only way to get quota semantics for a directory and the reason ordinary bind mounts cannot be size-limited. minidock deliberately keeps the simpler version, and you should know exactly what that costs: nothing enforces the size, so one container can fill the host's disk through a volume. That is the same trade Kubernetes makes with emptyDir without sizeLimit.

    Logs are the interesting half, because you are now the producer of a format you have only ever consumed. The CRI log format is one line per record:

    timestamp→stdout|stderr→P|F→the text

    The P tag means partial: the line was longer than the maximum and continues in the next record. Producing that tag is easy. The half that most log shippers get wrong is consuming it — reassembling partial records back into one line, per stream, without interleaving the two streams — and implementing minidock logs forces you onto that side of the problem.

    Then rotation, which is where the real decision lives. Rotate and you lose history, permanently. Do not rotate and a chatty container fills the disk — I12.10 measured a 300 MB log file that rm could not reclaim a single byte of, because the runtime still held the descriptor. There is no third option. That is precisely why the kubelet has containerLogMaxSize and containerLogMaxFiles, and why kubectl logs cannot show you last Tuesday.

    The CRI does not define the log format in the proto — it defines where the file goes and leaves the rest to convention:

    // Path relative to PodSandboxConfig.LogDirectory for container to store
    // the log (STDOUT and STDERR) on the host.
    // E.g.,
    // PodSandboxConfig.LogDirectory = `/var/log/pods/<NAMESPACE>_<NAME>_<UID>/`
    // ContainerConfig.LogPath = `containerName/Instance#.log`
    CRI api.proto, ContainerConfig.log_path — kubernetes/cri-api

    Two things worth reading out of that. Instance#.log is the restart attempt — the same number as kubectl's RESTARTS column, which is why a restarted container gets 1.log and its previous life stays readable at 0.log. And the whole path is the kubelet's convention: I12.2 found no /var/log/containers/ on a node with no kubelet, because that symlink farm is not the runtime's.

    Verify

    Data written to a named volume is readable from a second container after the first is gone.     Gotchas
    • Buffer per stream, not globally. One shared partial-line buffer will interleave stdout and stderr mid-line under load, and the corruption only appears when both are busy.
    • Split at the byte limit, not at the character. The limit is bytes; splitting a multi-byte UTF-8 sequence across two records is legal and every consumer has to cope, which is a reason to reassemble before decoding.
    • A directory-backed volume has no size limit. Say so in your own tool's help, or somebody will assume otherwise and fill the node.
    • Deleting a log file the runtime still has open frees nothing. I12.10 measured exactly 0 KB reclaimed from a 300 MB deletion, with the inode still growing. Rotation has to happen through the writer, which is why the CRI has ReopenContainerLog at all.

    I13.6

    Layer 6 — the platform layer

    Why it matters

    Five layers make a container run once. This one makes it a system: state that survives the process that created it, a CLI somebody else could use, several containers coexisting without stepping on each other, and something that notices when one dies and starts it again. That last item is a reconciliation loop, and writing it is the moment B13 stops being theory.

    The concept

    The metadata store is a JSON file and a lock, and the lock is not decoration — two minidock run processes really do race on it, and behind them their CNI plugins race on the IPAM store. What goes in it is the set of facts that cannot be recomputed: the name a human chose, the image reference, the address that was allocated, the restart policy, the exit code. Everything else — is it running, what is its PID — you could rediscover, and the interesting failure of your own tool is what happens when the store and reality disagree.

    The reconciler is four lines of logic and a great deal of consequence. Desired state: every container with restart=always is running. Observed state: the metadata store. The loop compares them and acts on the difference. The instant you write it, you inherit every problem the real ones have:

    • Crash loops need backoff, or the loop is a fork bomb. Exponential, capped — 1s, 2s, 4s, 8s.
    • "Exited cleanly" and "was killed" are different facts, and restart=always is the policy that deliberately ignores the difference. Kubernetes offers OnFailure for the other choice, and now you know why it is a separate policy rather than a smarter default.
    • What should happen to a container whose node rebooted? Your store still says running. Nothing is. Deciding whether the reconciler trusts the store or the machine is the same question a kubelet answers on every startup.

    And one design decision falls out that the tracker's own text does not mention, because you only meet it by building it: a container being restarted must not be torn down. If the exit path deletes the network namespace, every restart gets a new address and the reconciler churns the IPAM pool. Keep the namespace and the container comes back at the same address — which is the pod model, arrived at from below. The sandbox outlives the container.

    The CRI is explicit that teardown is idempotent and eager, which is the same discipline your rm path needs:

    // This call is idempotent, and must not return an error if all relevant
    // resources have already been reclaimed. kubelet will call StopPodSandbox
    // at least once before calling RemovePodSandbox. It will also attempt to
    // reclaim resources eagerly, as soon as a sandbox is not needed. Hence,
    // multiple StopPodSandbox calls are expected.
    CRI api.proto, StopPodSandbox — kubernetes/cri-api

    "Multiple calls are expected" is a design statement, not a warning: the caller is a control loop that may act on stale information at any time, so every operation it can issue has to be safe to issue twice. Your reconciler is that caller. Build the teardown path accordingly and the awkward cases stop being awkward.

    Gotchas

    • Backoff must be capped. Uncapped doubling reaches hours quickly, and then a container that recovers stays down.
    • Decide what a reboot means. Your store will say running for containers that no longer exist. Trusting it silently is the bug; the fix is a reconcile-on-startup pass that checks the machine, which is exactly what the kubelet does with its three pod sources.

    Quiz

    1. Your content store keys blobs by digest. Why does the name index have to live somewhere else, and what property is lost if it does not?
      Answer

      Blobs are recomputable — any blob can be fetched again from a registry, so the blob store is safe to delete wholesale. Names cannot be recomputed from anything; the mapping from alpine:3.21 to a manifest digest is the only fact in the store with no upstream. Putting them together means you can no longer throw away the recoverable half without also losing the irrecoverable one.

    2. Why is the snapshot cache keyed on chain ID rather than layer digest?
      Answer

      A directory on disk represents "this layer applied on top of exactly those layers", which is what a chain ID names. A layer digest names only the layer, so two images that share a base but diverge earlier would wrongly share a directory. For a single-layer image the chain ID equals the diff_id, because there is no parent to hash in.

    3. An image layer contains ./etc/.wh.motd. What does your unpacker write to disk, and what does it deliberately not write?
      Answer

      It writes a character device numbered 0:0 at etc/motd — overlayfs's whiteout convention. It does not write the .wh.motd file itself; the spec requires that once applied, the whiteout is hidden. The original /etc/motd in the lower layer is untouched and simply becomes invisible.

    4. Give the lowerdir ordering rule, and describe the symptom of getting it backwards.
      Answer

      Topmost layer first — the reverse of the order layers are applied in. Reversed, the container sees its base image with every subsequent change invisible, which presents as though the wrong tag was pulled.

    5. What single sentence describes what "running an image" means, and which two specifications does it sit between?
      Answer

      Translating an image config into a runtime config. It sits between image-spec (which says its .config is a base "which SHOULD be used ... when running a container") and runtime-spec (which defines the config.json the runtime is actually handed).

    6. You override a container's entrypoint and pass no arguments. What happens to the image's Cmd?
      Answer

      It is discarded. The container runs the new entrypoint with no arguments — exactly a pod spec with command: and no args:. The specification does not cover this; it is convention, and it usually presents as a container that exits 0 immediately having printed nothing.

    7. A detached container's shim is SIGKILLed. What is the state of the workload, and what does your metadata store say?
      Answer

      The workload keeps running, re-parented to PID 1. The metadata store says running forever, because the process responsible for updating it is gone and the exit status has nowhere to be recorded. Real containerd avoids this by monitoring the shim's ttrpc socket and reaping the orphan within a couple of seconds.

    8. Your store verified every blob on the way in. Why is a verify subcommand still worth having?
      Answer

      Because verification happens on write and then never again — the filename is trusted forever afterwards. That is a reasonable trade until bits rot, at which point the only symptom is an unreadable tar from inside the unpacker. verify re-hashes the store and turns that into a named blob and a one-line repair.
