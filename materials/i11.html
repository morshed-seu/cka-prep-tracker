    I11 — Container security & supply chain

    Two halves that are usually taught apart: hardening the container that runs here, and knowing that the image you are running is the one you meant. Every control below gets proved by attempting the thing it is supposed to forbid.

    The reason to do this by hand is that almost every control here is a single JSON field, and almost every one of them behaves differently from how it reads. A capability listed in effective is ignored for a root container and silently dropped for a non-root one. A seccomp rule listing three syscall names applies the same argument index to all three, and the index is not the same for all three. An AppArmor deny rule blocks the write and logs nothing. Each of those is one measured line below, and each one is the difference between a control you have and a control you think you have.

    • Rootless. Run runc and then the whole containerd stack as an unprivileged user, and measure what that buys and what it costs.
    • Supply chain.     Runtime hardening

    I11.1

    Five capability sets, three of which are usually lies

    Why it matters

    "Root" on Linux is not one switch. It is a bag of about forty separate permits — bind a low port, change a file's owner, open a raw socket, load a kernel module — and B4.10 took that bag apart by hand. A container config declares which permits the process gets, in five arrays. The trap is that only one of those five arrays reliably does what its name suggests, and which one that is depends on whether the container runs as root. Get this wrong and you write a config that reads like least privilege and grants everything, or one that grants a capability the process never receives.

    The concept

    I2.4 read these five arrays out of the spec and watched one of them override another. This lesson asks the next question: for a given container, which of the five does the kernel actually honour? The answer is rarely more than two.

    Every Linux process carries five capability sets, and the kernel recomputes four of them on every execve. That recomputation is the whole story:

    • bounding is a ceiling. Nothing in the container can ever raise a capability that is not in it, including a process that later becomes uid 0. It is the only set that is a real containment boundary.
    • permitted is what the process may switch on. For a process running as uid 0, execve recomputes permitted from the bounding set — so listing a capability here is redundant. For a process running as any other uid, execve recomputes it to empty unless the capability is also ambient.
    • effective is what is switched on right now. For uid 0 the kernel sets it equal to permitted at execve. So for a root container the effective array in config.json is ignored — you can leave a capability out of it and the process still has it.
    • inheritable survives execve only in combination with a file's own inheritable set, which container images essentially never use. On its own it does nothing.
    • ambient is the one that makes a non-root process keep a capability across execve. The kernel refuses to raise an ambient capability that is not also in both permitted and inheritable, so ambient is really a three-field setting.

    Put plainly: for a root container, only bounding matters. For a non-root container, only bounding (as a ceiling) and ambient (plus its two prerequisites) matter. The other arrays are documentation.

    The second surprise is the default. A bare runc spec bundle grants three capabilities, not the dozen-and-a-half that Docker made famous — and CAP_NET_RAW, CAP_CHOWN and CAP_DAC_OVERRIDE are all absent. That is why several perfectly ordinary commands fail in the labs below with errors that never mention capabilities.

    The runtime spec defines the object and its five arrays, and — importantly for a gotcha further down — tells runtimes to warn rather than fail on a capability they cannot grant.

    capabilities (object, OPTIONAL) is an object containing arrays that specifies the sets of capabilities for the process. Valid values are defined in the capabilities(7) man page, such as CAP_CHOWN. Any value which cannot be mapped to a relevant kernel interface, or cannot be granted otherwise MUST be logged as a warning by the runtime. Runtimes SHOULD NOT fail if the container configuration requests capabilities that cannot be granted […]

    effective […] the effective field is an array of effective capabilities that are kept for the process.
    bounding […] the bounding field is an array of bounding capabilities that are kept for the process.
    inheritable […] the inheritable field is an array of inheritable capabilities that are kept for the process.
    permitted […] the permitted field is an array of permitted capabilities that are kept for the process.
    ambient […] the ambient field is an array of ambient capabilities that are kept for the process.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    Notice what the spec does not say: it describes each array as capabilities "kept for the process" and says nothing about the kernel's execve rules. Everything in the concept section above is kernel behaviour that the spec leaves entirely implicit — which is exactly why the arrays mislead.

    Lab
    1. Build a bundle and read the default. Use the alpine rootfs from I2; the only edits are turning off the TTY (so the container runs unattended) and dropping the network namespace (so ping 127.0.0.1 has a working loopback — a fresh netns has none, as I9.11 showed). 
      mkdir -p ~/i11 && cd ~/i11        # rootfs/ already unpacked here
runc spec
jq '.process.capabilities' config.json
      {
  "bounding":  [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "effective": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "permitted": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ]
}

      Three sets, not five — inheritable and ambient are simply absent — and three capabilities in each.

    2. Define a small helper so each experiment is one line. It rewrites config.json from scratch every time, applies one jq filter, and runs the result. 
      run() {   # run <name> <jq-filter> <args-json>
  rm -f config.json; runc spec

      .linux.namespaces |= map(select(.type!=\"network\")) |

    4. Prove a missing capability by using it. ping needs CAP_NET_RAW to open a raw ICMP socket. 
      run B '.' '["/bin/ping","-c1","-W1","127.0.0.1"]'

      It is root. The message is busybox guessing, and it is guessing wrong — the single most common way this failure gets misdiagnosed. Add the capability to all three sets and it works:

       .process.capabilities.permitted += ["CAP_NET_RAW"]' \

      64 bytes from 127.0.0.1: seq=0 ttl=64 time=0.044 ms
1 packets transmitted, 1 packets received, 0% packet loss

      CH='["/bin/sh","-c","touch /f && echo touch=ok; chown 99:99 /f; echo chown_rc=$?"]'

      Two capability failures, two different messages — permission denied and operation not permitted. Neither says "capability".

    6. Now the first lie. Add CAP_CHOWN to bounding and permitted but deliberately leave it out of effective. 
      run F '.process.capabilities.bounding  += ["CAP_CHOWN"] |
       .process.capabilities.permitted += ["CAP_CHOWN"]' "$CH"

CapEff:	0000000020000421     ← the config said 0x…420
CapBnd:	0000000020000421
touch=ok
chown_rc=0

      The capability is effective anyway, and the chown succeeds. The kernel's rule for a uid-0 execve is effective′ = permitted′, so whatever config.json said about effective was overwritten before the first instruction ran.

    7. The second lie, and it fails the other way. Same three-set grant, but run as uid 1000. 
      run F2 '.process.user.uid=1000 | .process.user.gid=1000 |

        .process.capabilities.permitted += ["CAP_CHOWN"] |
        .process.capabilities.effective += ["CAP_CHOWN"]' \

CapEff:	0000000000000000
CapBnd:	0000000020000421     ← the ceiling survived

      Permitted and effective were both wiped. This is the exact shape of a Kubernetes pod that sets runAsNonRoot alongside capabilities.add — the add is silently void.

    8. Fix it the only way that works: ambient, with its two prerequisites. 
      run J '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.capabilities.bounding    += ["CAP_CHOWN"] |
       .process.capabilities.permitted   += ["CAP_CHOWN"] |
       .process.capabilities.effective   += ["CAP_CHOWN"] |
       .process.capabilities.inheritable  = ["CAP_CHOWN"] |
       .process.capabilities.ambient      = ["CAP_CHOWN"]' \
      '["/bin/sh","-c","id; grep -E \"^Cap(Prm|Eff|Amb|Inh)\" /proc/self/status; chown 99:99 /data/owned; echo chown_rc=$?"]'

CapPrm:	0000000000000001
CapEff:	0000000000000001

      Drop just the inheritable line and runc tells you, before the container starts:

      level=warning msg="can't raise ambient capability CAP_CHOWN: operation not permitted"

chown: /data/owned: Operation not permitted
    9. Finally, the ceiling. Empty the bounding set and nothing can climb back. 
      run G '.process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status; id -u"]'
      CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000

      uid 0 with an empty bounding set: root by name, with no permits at all. That is what drop: ["ALL"] compiles to.

    Verify

    You can look at a config.json capability block and say which arrays will actually take effect, given the process.user.uid beside them — and you can name the one array (bounding) that is a containment boundary rather than a request.

    Gotchas
    • The effective array is dead weight for a root container. The kernel recomputes it from permitted at execve. Reviewers who check that a capability was left out of effective are checking nothing.
    • permitted is dead weight for a non-root container. Measured above: uid 1000 came out with CapPrm 0 despite the config listing CAP_CHOWN in all three arrays. Non-root plus capabilities.add needs ambient, and Kubernetes has no field for it.
    • A misspelled capability is a warning, not an error. Adding CAP_NOT_A_REAL_CAP produced level=warning msg="ignoring unknown or unavailable capabilities: [CAP_NOT_A_REAL_CAP]" and a container with the unchanged default set. The spec explicitly asks for exactly this ("Runtimes SHOULD NOT fail"), so a typo in a hardening config fails open and the container starts.
    • CAP_DAC_OVERRIDE is not in the default set, and its absence looks like a storage bug. Container root could not create a file in a directory owned by uid 1000 — touch: /data/x: Permission denied — until CAP_DAC_OVERRIDE was added. Nothing in that message suggests capabilities; see I10.12, where the same absence surfaces as a volume-permissions fault.

    securityContext.capabilities.drop: ["ALL"] becomes exactly the empty-bounding-set container from step 9, and add: ["NET_BIND_SERVICE"] becomes the three-array grant from step 4 — note the CAP_ prefix is stripped in Kubernetes and required in the OCI config. The runAsNonRoot + add combination in step 7 is the trap worth remembering, because the pod starts and the capability simply is not there. The advanced track has no securityContext lesson to link — the nearest relatives are least privilege as a principle in W7.6's RBAC matrix, and W1.2, where you look at what actually runs privileged on a node.

    Docs: man 7 capabilities — the "Transformation of capabilities during execve()" section is the rulebook for everything above; the runtime spec's config.md § User; and B4.12, where you read these same sets out of /proc/self/status without a container.

    I11.2

    noNewPrivileges, and the escape hatch it welds shut

    Why it matters

    You have carefully set the container to run as an unprivileged user. Then the image ships a single file with the setuid bit on it — /usr/bin/passwd, ping, an old mount helper, or something a base image dragged in — and any process in the container can exec that file and come out as root. noNewPrivileges is a one-bit promise to the kernel that closes this, permanently, for the process and every descendant. It is one of the very few security fields that has no downside worth discussing, and one of the few that runc spec already turns on for you.

    The concept

    B4.9 covered the setuid bit: a file marked u+s and owned by root runs with the effective uid of its owner, not its caller. That is how an ordinary user changes their own password. Inside a container it is a privilege-escalation primitive sitting in the filesystem, and it needs no bug to use — it is the documented behaviour of execve.

    noNewPrivileges maps to the kernel's no_new_privs bit, set with prctl(PR_SET_NO_NEW_PRIVS, 1). Once set, the kernel guarantees that no execve from this process onward can raise privilege: setuid and setgid bits are ignored, file capabilities are ignored, and an AppArmor or SELinux transition to a more-privileged profile is refused. The bit is one-way — nothing can clear it — and it is inherited by every child. That one-wayness is what makes it trustworthy: a compromised process cannot turn it off before exploiting the setuid file.

    Two things it is often confused with. It is not a capability control — the escalating process gains uid 0, not capabilities, and those are separate mechanisms (you will see both outcomes side by side below). And it is not the only lever: the nosuid mount option does the same job per-filesystem rather than per-process, which is why it appears on almost every mount in a default bundle.

    The spec gives it two sentences and points at the kernel, which is honest — the semantics are entirely the kernel's.

    noNewPrivileges (bool, OPTIONAL) setting noNewPrivileges to true prevents the process from gaining additional privileges. As an example, the no_new_privs article in the kernel documentation has information on how this is achieved using a prctl system call on Linux.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    OPTIONAL, and defaulting to false when absent. runc spec writes "noNewPrivileges": true into the bundle it generates, so the generated default is safe and the specified default is not. A hand-built config that simply omits the field gets the unsafe one.

    Lab
    1. You need a setuid-root binary that reports what the kernel gave it. Busybox will not do — it dispatches on argv[0], so a renamed copy is inert — so compile four lines of C. Statically linked, because the rootfs is musl and the host is glibc. 
      cat > ~/whoareyou.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("ruid=%d euid=%d rgid=%d egid=%d\n",
           getuid(), geteuid(), getgid(), getegid());
    return 0;
}
EOF
cd ~/i11
gcc -static -O2 -o whoareyou ~/whoareyou.c
sudo install -o root -g root -m 4755 whoareyou rootfs/bin/whoareyou
sudo ls -l rootfs/bin/whoareyou
      -rwsr-xr-x 1 root root 785536 Jul 31 14:49 rootfs/bin/whoareyou

      The s in -rwsr-xr-x is the whole experiment.

    2. Run as uid 1000 with the flag off, using the run helper from I11.1. The shell reports its own uid, then the no_new_privs bit, then execs the setuid binary. 
      A='["/bin/sh","-c","echo shell: $(id -u); grep NoNewPrivs /proc/self/status; /bin/whoareyou"]'
run A '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false' "$A"
      shell: 1000
NoNewPrivs:	0
ruid=1000 euid=0 rgid=1000 egid=1000

      The container was configured to run as an unprivileged user, and one execve later the effective uid is 0.

    3. Change exactly one boolean. 
      run B '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=true' "$A"
      shell: 1000
NoNewPrivs:	1
ruid=1000 euid=1000 rgid=1000 egid=1000

      The binary still runs — it is not blocked, it simply does not get the uid. That distinction matters when you are reading a bug report: the symptom is a permission error deep inside a tool, not a refusal to start.

    4. Show that this is orthogonal to capabilities. Flag off, but every capability stripped from the bounding set. 
      run C '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","/bin/whoareyou; grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status"]'
      ruid=1000 euid=0 rgid=1000 egid=1000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000

      uid 0 with an empty bounding set. The escalation happened; it just arrived with nothing in its hands. Dropping capabilities does not close the setuid hole, and closing the setuid hole does not drop capabilities — you want both.

    5. The other lever, for comparison: nosuid on the mount rather than the process. Bind-mount the same directory a second time with nosuid and run the same binary through both paths, with the flag still off. 
      run D '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .mounts += [{"destination":"/mnt","source":"/home/ubuntu/i11/rootfs/bin",
                    "type":"bind","options":["rbind","nosuid","ro"]}]' \
      '["/bin/sh","-c","echo via-rootfs:; /bin/whoareyou; echo via-nosuid-bind:; /mnt/whoareyou"]'
      via-rootfs:
ruid=1000 euid=0
via-nosuid-bind:
ruid=1000 euid=1000

      One binary, one inode, two mount paths, two outcomes. This is why nosuid is on nearly every mount in the default bundle, and why a hand-written mount entry that omits it quietly re-opens the door on that path.

    Verify

    You can state what noNewPrivileges stops (a uid change at execve) and what it does not (anything to do with capabilities the process already holds), and you can name the second, mount-level control that produces the same result for one filesystem.

    Gotchas
    • Absent is false. The field is OPTIONAL and the spec's default is off. runc spec happens to write true; a config assembled by hand or by a tool that only sets the fields it cares about will not. Check for the field's presence, not just its value.
    • It breaks tools that legitimately escalate. Anything relying on a setuid helper — ping on some distributions, sudo, newuidmap, some FUSE mounts — stops working with an error from inside the tool. If a container works without the flag and fails with it, look for a setuid bit before looking anywhere else: find / -perm -4000 -type f.
    • It cannot be turned off, including by you. There is no way to run a privileged helper "just once" after the bit is set. If a container genuinely needs one, that is an argument for a different container, not for clearing the bit.
    • It does not stop a container that is already root. Everything above assumed a non-root uid. A root container has nothing to escalate to; the flag is close to a no-op there, which is why it belongs with a non-root uid rather than instead of one.

    securityContext.allowPrivilegeEscalation: false is this exact field, and the Pod Security Standards' Restricted profile requires it. Note it is a separate field from runAsNonRoot and is not implied by it — step 2 is what a pod with runAsNonRoot: true and the default allowPrivilegeEscalation looks like. The advanced track has no Pod Security Standards lesson to link into; the closest existing material is W1.2, where you inspect what the control-plane containers on a node actually run as.

    Docs: the kernel's no_new_privs.rst; man 2 prctl under PR_SET_NO_NEW_PRIVS; man 8 mount for nosuid; and B4.15, whose debugging drill is a copied setuid binary.

    I11.3

    A seccomp profile, written by hand, and the SIGSYS it produces

    Why it matters

    Capabilities decide which privileged operations a process may perform. Seccomp decides which system calls it may make at all — a finer instrument in one sense and a blunter one in another. It is the control that stops a container reaching a kernel bug in a syscall it never needed, and it is the control most likely to break a workload in a way whose error message names nothing useful. Both halves of that sentence are things you should see happen rather than read about, which is what this lesson does.

    The concept

    A seccomp filter is a small program the kernel runs before every system call the process makes. It looks at the syscall number and, optionally, at the raw integer arguments, and returns an action: allow it, fail it with an errno, log it, or kill something. The filter is installed once and is irreversible and inherited — the same one-way property as no_new_privs, and in fact installing a filter requires either CAP_SYS_ADMIN or the no_new_privs bit, so the two travel together.

    B12.14 installed one of these by hand, and I1.9 got killed by one on purpose. The OCI config expresses the same thing as JSON under linux.seccomp: a defaultAction that applies to every syscall not otherwise mentioned, then an array of syscalls entries, each with a list of names, an action, and optionally args to match on argument values.

    That gives you two ways to write a profile, and they fail very differently:

    • A deny-list — defaultAction: SCMP_ACT_ALLOW plus entries blocking specific syscalls. Easy to write, impossible to make complete, and the right shape when you want to remove one known-dangerous call.
    • An allow-list — defaultAction: SCMP_ACT_ERRNO plus an enumeration of everything permitted. Genuinely restrictive, and much harder than it looks: the enumeration must cover the syscalls the runtime makes while setting the container up, not just the ones your program makes. You will watch that fail four times below before it works.

    One structural detail that decides whether a profile does what you meant: args matches on the raw register values, and it cannot follow pointers. So you can filter chmod by mode but never by path — the path is a pointer, and the filter sees only the address. This is not a limitation of the OCI schema, it is a limitation of the kernel's filter, and it is why "block writes to /etc" is not a thing seccomp can do.

    The schema is small enough to hold in your head. Note that defaultAction is the only REQUIRED field, and note the warning the spec itself attaches to an empty allow-list.

    defaultAction (string, REQUIRED) - the default action for seccomp. Allowed values are the same as syscalls[].action.
    defaultErrnoRet (uint, OPTIONAL) - the errno return code to use. […] The default is EPERM.
    architectures (array of strings, OPTIONAL) - the architecture used for system calls.
    syscalls (array of objects, OPTIONAL) - match a syscall in seccomp. While this property is OPTIONAL, some values of defaultAction are not useful without syscalls entries. For example, if defaultAction is SCMP_ACT_KILL and syscalls is empty or unset, the kernel will kill the container process on its first syscall.
    · names (array of strings, REQUIRED) - the names of the syscalls. names MUST contain at least one entry.
    · action (string, REQUIRED) - the action for seccomp rules.
    · args (array of objects, OPTIONAL) — with index, value, valueTwo and op.
    OCI Runtime Specification v1.3.0, Linux Configuration § Seccomp — config-linux.md
    Lab
    1. First, establish that there is nothing here by default. 
      cd ~/i11 && rm -f config.json && runc spec
jq '.linux | has("seccomp")' config.json
      false

      A bare bundle has no seccomp filter at all. The "runtime default profile" people talk about belongs to containerd and Docker, not to runc — which is why a container started by runc directly is less confined than the same image under ctr.

    2. Write the smallest real profile: allow everything, refuse to make directories. 
      cat > seccomp-errno.json <<'EOF'
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_X32"],
  "syscalls": [
    { "names": ["mkdir", "mkdirat"], "action": "SCMP_ACT_ERRNO" }
  ]
}
EOF

      Extend the run helper to splice a profile file into the config:

      runsec() {   # runsec <name> <profile.json> <args-json>
  rm -f config.json; runc spec
  jq --slurpfile s "$2" ".process.terminal=false | .process.args=$3 |
      .linux.namespaces |= map(select(.type!=\"network\")) |
      .root.readonly=false | .linux.seccomp = \$s[0]" config.json > c.tmp && mv c.tmp config.json
  sudo dmesg -C
  sudo runc --root /run/runc-i11 run "i11$1"
  sudo runc --root /run/runc-i11 delete -f "i11$1" 2>/dev/null
  sudo dmesg | tail -3
}

      mkdir: can't create directory '/d': Operation not permitted
rc=1
    3. Change the errno the filter returns. 38 is ENOSYS. 
      jq '.syscalls[0].errnoRet = 38' seccomp-errno.json > seccomp-enosys.json

    Gotchas
    • One args block, many names, different argument positions. Measured above: grouping chmod with fchmodat under index: 2 produced a rule that silently did not fire. Group syscalls by argument layout, not by what they are called.

    • The filter covers the runtime's setup, not just your program. An allow-list that omits fcntl, openat2 or statfs fails with an error about file descriptors or a Rust panic, never about seccomp.

    I11.4

    Two fields that delegate to something outside the container

    Why it matters

    Seccomp cannot see file paths. Capabilities cannot express "this program, and only this program, may write to that directory". Mandatory access control can do both, and the OCI config reaches it through two one-line string fields — process.apparmorProfile and linux.selinuxLabel. What makes them different from every other field in this module is that the string is a name, and the thing it names lives on the host, outside the bundle entirely. Ship the config without shipping the profile and the container does not start.

    The concept

    Discretionary access control — the owner/group/other bits from B4.5 — is called discretionary because the owner of a file decides who may touch it. Mandatory access control sits above that: an administrator writes a policy, the kernel enforces it on every access, and no file owner and no root process can override it. The two checks are independent and both must pass, so MAC can only ever remove permissions the DAC bits would have granted.

    Linux ships two implementations, and which one you get is decided by your distribution rather than by you. AppArmor (Debian, Ubuntu, SUSE) attaches policy to executables by path and is written as readable rules over paths and capabilities. SELinux (RHEL, Fedora, CentOS) attaches a label to every process and every file and consults a compiled policy about which label may touch which. For containers, SELinux's category mechanism (the c124,c675 at the end of a label) is what keeps two containers on one host from reading each other's files even when the uid is the same.

    The OCI config sets one string each way. Both are OPTIONAL, both default to unset, and a bare runc spec bundle sets neither — which means the honest default for a hand-built container is no mandatory access control at all.

    Two bullets, one for each, and both defer entirely to the host system.

    apparmorProfile (string, OPTIONAL) specifies the name of the AppArmor profile for the process. For more information about AppArmor, see AppArmor documentation.

    selinuxLabel (string, OPTIONAL) specifies the SELinux label for the process. For more information about SELinux, see SELinux documentation.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    The spec's own example config uses "apparmorProfile": "acme_secure_profile" and "selinuxLabel": "system_u:system_r:svirt_lxc_net_t:s0:c124,c675". Neither string means anything without a host that already knows it.

    Lab

    Gotchas
    • deny logs nothing; audit deny logs. Measured above with two otherwise identical profiles. Any runbook that says "check the audit log to confirm the denial" is assuming the second form.
    • The profile is not in the bundle. Both fields are names resolved on the host. A bundle, an image and a pod spec are all fully portable; the policy they name is not. Treat profile installation as part of node provisioning.
    • An AppArmor profile is an allow-list with deny overrides. The bare rules file, and capability, in the lab grant everything of that kind. Omit them and the container fails in ways that look like a corrupt image — start permissive, add denials, and use complain mode plus aa-logprof to tighten.
    • noNewPrivileges and MAC interact. With no_new_privs set, the kernel refuses an execve that would transition to a more privileged profile. Profiles that rely on a transition at exec stop transitioning, silently, once you turn the flag on.
    • SELinux labels are not optional decoration. On a SELinux host, a volume mounted without the right category label is unreadable by the container even though every uid and mode is correct — the same class of confusing failure as I10.12's uid mismatch, with a different cause.

    I11.5

    A read-only rootfs, the workloads it cures and the one it cannot

    Why it matters

    Most attacks that get a foothold in a container want to write something to it — a webshell into the document root, a modified binary on PATH, a cron entry. One boolean removes the whole category, and it costs nothing for a well-behaved application. The interesting part is what "well-behaved" turns out to mean, because the standard fix — a tmpfs over /tmp — cures one class of application completely and does nothing at all for another.

    The concept

    root.readonly asks the runtime to remount the container's own root filesystem read-only after it has finished setting it up. What it covers is exactly the rootfs and nothing else: every other mount in mounts keeps whatever options it was given, so a writable bind mount or volume stays writable. That separation is the design — the container's code becomes immutable while its data does not.

    I2.5 read this field out of the spec; the point here is what happens to real programs. Three sources of writes have to be dealt with, and only the first two have a good answer:

    • Scratch space — temp files, a pid file, a unix socket, a lock. Cure: a tmpfs over the directory. The data was never meant to survive the process anyway, and putting it in RAM is usually an improvement.
    • State that must persist — a database, uploaded files, a cache you actually want warm. Cure: a volume. That was always the right answer; the read-only rootfs just forces the question.
    • Writes into the program's own install tree — a package manager, a plugin installer, a framework that compiles templates next to the source. There is no cure. You cannot tmpfs over /usr without deleting the program. These workloads have to be rebuilt, not reconfigured, and recognising one early saves a long afternoon.

    There is a second, quieter piece of read-only protection in every default bundle: linux.readonlyPaths and linux.maskedPaths. The first remounts specific paths read-only; the second hides them entirely by bind-mounting /dev/null over them. They exist because /proc and /sys have to be mounted read-write for the container to work at all, and a handful of files under them are dangerous.

    One sentence, and a default that catches people out.

    readonly (bool, OPTIONAL) If true then the root filesystem MUST be read-only inside the container, defaults to false.
    OCI Runtime Specification v1.3.0, Configuration § Root — config.md

    Defaults to false — but runc spec writes "readonly": true into the bundle it generates. As with noNewPrivileges, the generated default and the specified default disagree, and the labs below have been turning it off all module to get anything done.

    Given a workload that fails on a read-only rootfs, you can tell within a minute which of the three categories it is in — by reading where the failed writes point — and therefore whether the fix is a tmpfs, a volume, or a rebuild.

    Gotchas
    • A package manager reports success it did not have. Measured: apk printed "8 MiB in 17 packages" and exited 17, with none of the binaries installed. Anything that runs apk/apt/pip install at container start is incompatible with a read-only rootfs, and its own exit code is the only honest signal.
    • /dev/shm and /dev stay writable. They are separate tmpfs mounts. Useful for you, and equally useful to anyone else who ends up in the container.
    • Writable mounts are unaffected, by design. The flag covers the rootfs only; a rw bind mount writes through to the host. Turning on the boolean while leaving a broad hostPath mounted changes very little.
    • maskedPaths is /dev/null bind-mounted over the file. So the path still exists, ls shows a character device, and a program that checks for the file's presence rather than its content will happily proceed and read nothing.
    • Sizing a tmpfs is sizing memory. A tmpfs with no size= advertises half of RAM and is charged to the container's memory cgroup as it fills — which is I10.2's pod that fills the node, arriving through a different door.

    securityContext.readOnlyRootFilesystem: true is this field, and the emptyDir: {medium: Memory} volume you pair it with is the tmpfs from step 6 — see W5.1 for emptyDir in the advanced track. Kubernetes exposes maskedPaths/readonlyPaths only through procMount, whose non-default value requires a user namespace; the /proc/kcore masking in step 3 is what you lose by changing it.

    Rootless

    I11.6

    Rootless runc, and why its default mapping is exactly one id

    Why it matters

    Every control so far has been about limiting what a container can do given that the runtime runs as root. Rootless changes the premise: the container's uid 0 is an ordinary unprivileged uid on the host, so an escape lands you as a normal user rather than as root. It is the single largest change in blast radius available, and it is also the one with the most surprising list of things that stop working. This lesson gets it running and finds the boundary; the next one takes the whole stack down.

    The concept

    I1.1 and I1.2 built the mechanism: a user namespace holds a uid_map saying "container uid 0 is host uid N", the mapping may be written exactly once, and writing a mapping with more than one entry requires the setuid helper newuidmap backed by a range in /etc/subuid. A rootless container is that, with a rootfs on top.

    The OCI config expresses it with linux.uidMappings and linux.gidMappings, plus a user namespace in linux.namespaces. runc spec --rootless generates a bundle that will run as you, and comparing it with the ordinary one is the fastest way to see what an unprivileged runtime cannot do — cgroup limits disappear, the network namespace disappears, and /sys stops being a fresh sysfs mount and becomes a bind of the host's.

    The important structural fact, and the one that catches everyone: the generated mapping has size: 1. It maps container uid 0 to your uid and nothing else. That is not conservatism — it is the only mapping runc can install on its own, because installing a wider one means writing subuid ranges into uid_map, and doing that requires a privilege runc does not have. Wider mappings are the job of a helper that sets the namespace up first, which is what rootlesskit does in the next checkpoint.

    Three fields, and one line at the end that is the whole reason step 6 below fails.

    uidMappings (array of objects, OPTIONAL) describes the user namespace uid mappings from the host to the container.
    gidMappings (array of objects, OPTIONAL) describes the user namespace gid mappings from the host to the container.

    Each entry has the following structure:
    · containerID (uint32, REQUIRED) - is the starting uid/gid in the container.
    · hostID (uint32, REQUIRED) - is the starting uid/gid on the host to be mapped to containerID.
    · size (uint32, REQUIRED) - is the number of ids to be mapped.

    The runtime SHOULD NOT modify the ownership of referenced filesystems to realize the mapping. Note that the number of mapping entries MAY be limited by the kernel.
    OCI Runtime Specification v1.3.0, Linux Configuration § User namespace mappings — config-linux.md

    "SHOULD NOT modify the ownership of referenced filesystems" is the spec telling the runtime not to chown your rootfs into the mapped range — which leaves the question of who does, and that is the question step 6 runs into.

    I11.7

    The whole stack under your uid, and the five things that change

    Why it matters

    I11.6 ran one container as you. Running the daemon as you is a different exercise, because containerd wants to write to /var/lib/containerd, listen on /run/containerd/containerd.sock, create network namespaces and set cgroup limits — and an unprivileged process may do none of those things. Watching how rootlesskit arranges for all four to appear to work anyway is the most instructive half hour in this module, and it produces a precise list of what you give up.

    The concept

    The trick is a single user namespace with a mount namespace inside it, created once at startup by rootlesskit using newuidmap. Inside that namespace you are uid 0, so /run/containerd and /var/lib/containerd are writable — but they are different directories from the host's, because rootlesskit "copies up" each one onto a fresh tmpfs before containerd looks. Every path containerd knows is the path it always was; only the namespace changed.

    Networking is the part that cannot be faked with mounts. A user namespace lets you create a network namespace, but it does not let you attach a veth to a host bridge or write a NAT rule in the host's tables — those need CAP_NET_ADMIN on the host. So rootless stacks run a userspace network stack: slirp4netns holds one end of a TAP device inside the namespace and translates the container's packets into ordinary sockets opened as your user. That is why the container's addresses come from a private range that exists nowhere on the host, and why published ports are proxied rather than DNAT'd.

    Cgroups are the one thing that works properly, and only because systemd already solved it: user@1000.service gets a delegated subtree, so limits set inside it are real kernel limits. This is the same delegation I1.6 ran into, and what is delegated has grown — measure it rather than assuming.

    I11.8

    The honest table: what each control actually stops

    Why it matters

    Seven checkpoints have each turned on one control and proved it works. That is not the same as knowing what your container is protected from, because the interesting question is never "does this control work" — it is "given this attack, which of my controls is the one that stops it, and is there one?" This checkpoint builds the grid, and the discipline it demands is being willing to write nothing in a cell. A control matrix with no empty cells is a control matrix nobody checked.

    The concept

    B12.1 gave the method: name the assets, name the actors, draw the trust boundaries, and only then talk about mechanisms. Applied to a container the assets are the node's filesystem and credentials, the other containers on it, the node's capacity, and the cluster API. The actor to assume is code running inside the container, because that is what an application vulnerability gets you and it requires no container bug at all.

    That framing is what makes the table below uncomfortable. Most container controls constrain a process that is already inside, and most of them constrain it in exactly one dimension. The three that change the shape of the problem rather than trimming it are the user namespace, the absence of a host mount, and the absence of the container socket — and only the first is a control you turn on rather than a thing you refrain from doing.

    One term to keep straight, because the rest of the table depends on it. Escape to host means obtaining host-root code execution. Read host secrets means getting at a file like /etc/shadow or a kubelet credential, which usually does not require an escape — it requires a mount. Conflating the two is the most common error in these discussions, and it is why "we dropped all capabilities" is offered as an answer to a question about a hostPath.

    Verify

    Given a proposed hardening change, you can say which column of the table it moves and which it does not — and you can name the one control in the list that, if present, makes every other row irrelevant.

    Gotchas
    • The container socket dominates everything. A pod with the containerd or Docker socket mounted is node root, whatever else is set. Every other row in the table is conditional on that one being absent.
    • "Not privileged" is not a control. It is the absence of one particular disaster. A default container still has three capabilities, a writable rootfs unless you say otherwise, no seccomp profile under bare runc, and whatever mounts you gave it.
    • Controls that look adjacent do not compose the way you expect. Dropping capabilities does not close the setuid route; noNewPrivileges does not drop capabilities; a read-only rootfs does not affect volumes. Each was measured separately in this module precisely because the intuition is wrong.
    • Defence in depth is not "turn on everything". It is a claim that each layer stops a different thing. If two controls fill the same cell and none fills another, you have redundancy where you did not need it and a gap where you did — which is what the empty columns above are for.

    In Kubernetes these rows become Pod Security Standards profiles: Baseline removes the host namespaces, hostPath, privileged mode and most hostPort use — i.e. the "no host mounts" and "no container socket" rows; Restricted adds non-root, allowPrivilegeEscalation: false, drop: ["ALL"] and a seccomp profile. The advanced track has no lesson on either, so the mapping is worth writing down yourself. The two columns Kubernetes answers elsewhere are "exhaust the node" — W3.16's requests and limits — and "reach the API server", which is entirely W7.6's RBAC and the ServiceAccount token every pod gets by default.
