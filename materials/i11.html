    I11 — Container security & supply chain

    Two halves that are usually taught apart: hardening the container that runs here, and knowing that the image you are running is the one you meant. Every control below gets proved by attempting the thing it is supposed to forbid.

    The reason to do this by hand is that almost every control here is a single JSON field, and almost every one of them behaves differently from how it reads. A capability listed in effective is ignored for a root container and silently dropped for a non-root one. A seccomp rule listing three syscall names applies the same argument index to all three, and the index is not the same for all three. An AppArmor deny rule blocks the write and logs nothing. Each of those is one measured line below, and each one is the difference between a control you have and a control you think you have.

    Checkpoints15 Hours~6 PrerequisitesI1 · I2 · I4 · I5 · B12
    • Runtime hardening. Read and write the five capability sets, noNewPrivileges, a real seccomp profile, the AppArmor and SELinux fields, and root.readonly — and prove each one by attempting exactly what it forbids.
    • Rootless. Run runc and then the whole containerd stack as an unprivileged user, and measure what that buys and what it costs.
    • Supply chain. Sign an image with cosign and find where the signature is stored, attach and read back an attestation, generate an SBOM and use it to answer a question, scan for vulnerabilities and do the arithmetic that changes a base-image decision, and prove why a digest is the only immutable reference.
    • Project & drill. Build run-verified.sh — refuse to run what does not verify, then run it locked down — and diagnose two faults whose error messages name nothing useful.

    I2 (the spec fields these controls are written in), I4 and I5 (digests and registries), I1 (user namespaces, seccomp for real) and B12 (threat modelling, signatures, PKI). Nothing here is a new mechanism — it is B4's and B12's mechanisms, now declarative.

    Which machine. Everything below ran on the same sandbox VM the rest of this track uses — Ubuntu 24.04, kernel 6.8.0, runc 1.5.1, containerd 2.3.3, nerdctl 2.3.5 — plus four tools installed for this module: cosign v3.1.2, syft v1.50.0, trivy v0.72.0 and grype v0.116.1, with rootlesskit v3.0.2 and slirp4netns 1.2.1 for the rootless half. The registry is the local registry:2 from I5.

    Runtime hardening

    I11.1

    Five capability sets, three of which are usually lies

    Why it matters

    "Root" on Linux is not one switch. It is a bag of about forty separate permits — bind a low port, change a file's owner, open a raw socket, load a kernel module — and B4.10 took that bag apart by hand. A container config declares which permits the process gets, in five arrays. The trap is that only one of those five arrays reliably does what its name suggests, and which one that is depends on whether the container runs as root. Get this wrong and you write a config that reads like least privilege and grants everything, or one that grants a capability the process never receives.

    The concept

    I2.4 read these five arrays out of the spec and watched one of them override another. This lesson asks the next question: for a given container, which of the five does the kernel actually honour? The answer is rarely more than two.

    Every Linux process carries five capability sets, and the kernel recomputes four of them on every execve. That recomputation is the whole story:

    • bounding is a ceiling. Nothing in the container can ever raise a capability that is not in it, including a process that later becomes uid 0. It is the only set that is a real containment boundary.
    • permitted is what the process may switch on. For a process running as uid 0, execve recomputes permitted from the bounding set — so listing a capability here is redundant. For a process running as any other uid, execve recomputes it to empty unless the capability is also ambient.
    • effective is what is switched on right now. For uid 0 the kernel sets it equal to permitted at execve. So for a root container the effective array in config.json is ignored — you can leave a capability out of it and the process still has it.
    • inheritable survives execve only in combination with a file's own inheritable set, which container images essentially never use. On its own it does nothing.
    • ambient is the one that makes a non-root process keep a capability across execve. The kernel refuses to raise an ambient capability that is not also in both permitted and inheritable, so ambient is really a three-field setting.

    Put plainly: for a root container, only bounding matters. For a non-root container, only bounding (as a ceiling) and ambient (plus its two prerequisites) matter. The other arrays are documentation.

    The second surprise is the default. A bare runc spec bundle grants three capabilities, not the dozen-and-a-half that Docker made famous — and CAP_NET_RAW, CAP_CHOWN and CAP_DAC_OVERRIDE are all absent. That is why several perfectly ordinary commands fail in the labs below with errors that never mention capabilities.

    The runtime spec defines the object and its five arrays, and — importantly for a gotcha further down — tells runtimes to warn rather than fail on a capability they cannot grant.

    capabilities (object, OPTIONAL) is an object containing arrays that specifies the sets of capabilities for the process. Valid values are defined in the capabilities(7) man page, such as CAP_CHOWN. Any value which cannot be mapped to a relevant kernel interface, or cannot be granted otherwise MUST be logged as a warning by the runtime. Runtimes SHOULD NOT fail if the container configuration requests capabilities that cannot be granted […]

    effective […] the effective field is an array of effective capabilities that are kept for the process.
    bounding […] the bounding field is an array of bounding capabilities that are kept for the process.
    inheritable […] the inheritable field is an array of inheritable capabilities that are kept for the process.
    permitted […] the permitted field is an array of permitted capabilities that are kept for the process.
    ambient […] the ambient field is an array of ambient capabilities that are kept for the process.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    Notice what the spec does not say: it describes each array as capabilities "kept for the process" and says nothing about the kernel's execve rules. Everything in the concept section above is kernel behaviour that the spec leaves entirely implicit — which is exactly why the arrays mislead.

    Lab
    1. Build a bundle and read the default. Use the alpine rootfs from I2; the only edits are turning off the TTY (so the container runs unattended) and dropping the network namespace (so ping 127.0.0.1 has a working loopback — a fresh netns has none, as I9.11 showed). 
      mkdir -p ~/i11 && cd ~/i11        # rootfs/ already unpacked here
runc spec
jq '.process.capabilities' config.json
      {
  "bounding":  [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "effective": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "permitted": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ]
}

      Three sets, not five — inheritable and ambient are simply absent — and three capabilities in each.

    2. Define a small helper so each experiment is one line. It rewrites config.json from scratch every time, applies one jq filter, and runs the result. 
      run() {   # run <name> <jq-filter> <args-json>
  rm -f config.json; runc spec
  jq "$2 | .process.terminal=false | .process.args=$3 |
      .linux.namespaces |= map(select(.type!=\"network\")) |
      .root.readonly=false" config.json > c.tmp && mv c.tmp config.json
  sudo runc --root /run/runc-i11 run "i11$1"
  sudo runc --root /run/runc-i11 delete -f "i11$1" 2>/dev/null
}
    3. Read the sets from inside, as the process actually holds them. 
      run A '.' '["/bin/sh","-c","grep -E \"^Cap(Prm|Eff|Bnd|Amb|Inh)\" /proc/self/status; id"]'
      CapInh:	0000000000000000
CapPrm:	0000000020000420
CapEff:	0000000020000420
CapBnd:	0000000020000420
CapAmb:	0000000000000000
uid=0(root) gid=0(root)

      0x20000420 is bits 29, 10 and 5 — CAP_AUDIT_WRITE, CAP_NET_BIND_SERVICE, CAP_KILL. Root, with three of forty permits.

    4. Prove a missing capability by using it. ping needs CAP_NET_RAW to open a raw ICMP socket. 
      run B '.' '["/bin/ping","-c1","-W1","127.0.0.1"]'
      PING 127.0.0.1 (127.0.0.1): 56 data bytes
ping: permission denied (are you root?)

      It is root. The message is busybox guessing, and it is guessing wrong — the single most common way this failure gets misdiagnosed. Add the capability to all three sets and it works:

      run C '.process.capabilities.bounding  += ["CAP_NET_RAW"] |
       .process.capabilities.effective += ["CAP_NET_RAW"] |
       .process.capabilities.permitted += ["CAP_NET_RAW"]' \
      '["/bin/ping","-c1","-W1","127.0.0.1"]'
      64 bytes from 127.0.0.1: seq=0 ttl=64 time=0.044 ms
1 packets transmitted, 1 packets received, 0% packet loss
    5. Same shape, different capability, different error text. chown needs CAP_CHOWN. 
      CH='["/bin/sh","-c","touch /f && echo touch=ok; chown 99:99 /f; echo chown_rc=$?"]'
run D '.' "$CH"
run E '.process.capabilities.bounding  += ["CAP_CHOWN"] |
       .process.capabilities.effective += ["CAP_CHOWN"] |
       .process.capabilities.permitted += ["CAP_CHOWN"]' "$CH"
      ### D            ### E
touch=ok         touch=ok
chown: /f: Operation not permitted
chown_rc=1       chown_rc=0

      Two capability failures, two different messages — permission denied and operation not permitted. Neither says "capability".

    6. Now the first lie. Add CAP_CHOWN to bounding and permitted but deliberately leave it out of effective. 
      run F '.process.capabilities.bounding  += ["CAP_CHOWN"] |
       .process.capabilities.permitted += ["CAP_CHOWN"]' "$CH"
      CapPrm:	0000000020000421
CapEff:	0000000020000421     ← the config said 0x…420
CapBnd:	0000000020000421
touch=ok
chown_rc=0

      The capability is effective anyway, and the chown succeeds. The kernel's rule for a uid-0 execve is effective′ = permitted′, so whatever config.json said about effective was overwritten before the first instruction ran.

    7. The second lie, and it fails the other way. Same three-set grant, but run as uid 1000. 
      run F2 '.process.user.uid=1000 | .process.user.gid=1000 |
        .process.capabilities.bounding  += ["CAP_CHOWN"] |
        .process.capabilities.permitted += ["CAP_CHOWN"] |
        .process.capabilities.effective += ["CAP_CHOWN"]' \
       '["/bin/sh","-c","id; grep -E \"^Cap(Prm|Eff|Bnd|Amb)\" /proc/self/status; chown 99:99 /data/owned; echo chown_rc=$?"]'
      uid=1000 gid=1000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000020000421     ← the ceiling survived
CapAmb:	0000000000000000
chown: /data/owned: Operation not permitted
chown_rc=1

      Permitted and effective were both wiped. This is the exact shape of a Kubernetes pod that sets runAsNonRoot alongside capabilities.add — the add is silently void.

    8. Fix it the only way that works: ambient, with its two prerequisites. 
      run J '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.capabilities.bounding    += ["CAP_CHOWN"] |
       .process.capabilities.permitted   += ["CAP_CHOWN"] |
       .process.capabilities.effective   += ["CAP_CHOWN"] |
       .process.capabilities.inheritable  = ["CAP_CHOWN"] |
       .process.capabilities.ambient      = ["CAP_CHOWN"]' \
      '["/bin/sh","-c","id; grep -E \"^Cap(Prm|Eff|Amb|Inh)\" /proc/self/status; chown 99:99 /data/owned; echo chown_rc=$?"]'
      uid=1000 gid=1000
CapInh:	0000000000000001
CapPrm:	0000000000000001
CapEff:	0000000000000001
CapAmb:	0000000000000001
chown_rc=0

      Drop just the inheritable line and runc tells you, before the container starts:

      level=warning msg="can't raise ambient capability CAP_CHOWN: operation not permitted"
CapAmb:	0000000000000000
chown: /data/owned: Operation not permitted
    9. Finally, the ceiling. Empty the bounding set and nothing can climb back. 
      run G '.process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status; id -u"]'
      CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000
0

      uid 0 with an empty bounding set: root by name, with no permits at all. That is what drop: ["ALL"] compiles to.

    Verify

    You can look at a config.json capability block and say which arrays will actually take effect, given the process.user.uid beside them — and you can name the one array (bounding) that is a containment boundary rather than a request.

    Gotchas
    • The effective array is dead weight for a root container. The kernel recomputes it from permitted at execve. Reviewers who check that a capability was left out of effective are checking nothing.
    • permitted is dead weight for a non-root container. Measured above: uid 1000 came out with CapPrm 0 despite the config listing CAP_CHOWN in all three arrays. Non-root plus capabilities.add needs ambient, and Kubernetes has no field for it.
    • A misspelled capability is a warning, not an error. Adding CAP_NOT_A_REAL_CAP produced level=warning msg="ignoring unknown or unavailable capabilities: [CAP_NOT_A_REAL_CAP]" and a container with the unchanged default set. The spec explicitly asks for exactly this ("Runtimes SHOULD NOT fail"), so a typo in a hardening config fails open and the container starts.
    • CAP_DAC_OVERRIDE is not in the default set, and its absence looks like a storage bug. Container root could not create a file in a directory owned by uid 1000 — touch: /data/x: Permission denied — until CAP_DAC_OVERRIDE was added. Nothing in that message suggests capabilities; see I10.12, where the same absence surfaces as a volume-permissions fault.

    securityContext.capabilities.drop: ["ALL"] becomes exactly the empty-bounding-set container from step 9, and add: ["NET_BIND_SERVICE"] becomes the three-array grant from step 4 — note the CAP_ prefix is stripped in Kubernetes and required in the OCI config. The runAsNonRoot + add combination in step 7 is the trap worth remembering, because the pod starts and the capability simply is not there. The advanced track has no securityContext lesson to link — the nearest relatives are least privilege as a principle in W7.6's RBAC matrix, and W1.2, where you look at what actually runs privileged on a node.

    Docs: man 7 capabilities — the "Transformation of capabilities during execve()" section is the rulebook for everything above; the runtime spec's config.md § User; and B4.12, where you read these same sets out of /proc/self/status without a container.

    I11.2

    noNewPrivileges, and the escape hatch it welds shut

    Why it matters

    You have carefully set the container to run as an unprivileged user. Then the image ships a single file with the setuid bit on it — /usr/bin/passwd, ping, an old mount helper, or something a base image dragged in — and any process in the container can exec that file and come out as root. noNewPrivileges is a one-bit promise to the kernel that closes this, permanently, for the process and every descendant. It is one of the very few security fields that has no downside worth discussing, and one of the few that runc spec already turns on for you.

    The concept

    B4.9 covered the setuid bit: a file marked u+s and owned by root runs with the effective uid of its owner, not its caller. That is how an ordinary user changes their own password. Inside a container it is a privilege-escalation primitive sitting in the filesystem, and it needs no bug to use — it is the documented behaviour of execve.

    noNewPrivileges maps to the kernel's no_new_privs bit, set with prctl(PR_SET_NO_NEW_PRIVS, 1). Once set, the kernel guarantees that no execve from this process onward can raise privilege: setuid and setgid bits are ignored, file capabilities are ignored, and an AppArmor or SELinux transition to a more-privileged profile is refused. The bit is one-way — nothing can clear it — and it is inherited by every child. That one-wayness is what makes it trustworthy: a compromised process cannot turn it off before exploiting the setuid file.

    Two things it is often confused with. It is not a capability control — the escalating process gains uid 0, not capabilities, and those are separate mechanisms (you will see both outcomes side by side below). And it is not the only lever: the nosuid mount option does the same job per-filesystem rather than per-process, which is why it appears on almost every mount in a default bundle.

    The spec gives it two sentences and points at the kernel, which is honest — the semantics are entirely the kernel's.

    noNewPrivileges (bool, OPTIONAL) setting noNewPrivileges to true prevents the process from gaining additional privileges. As an example, the no_new_privs article in the kernel documentation has information on how this is achieved using a prctl system call on Linux.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    OPTIONAL, and defaulting to false when absent. runc spec writes "noNewPrivileges": true into the bundle it generates, so the generated default is safe and the specified default is not. A hand-built config that simply omits the field gets the unsafe one.

    Lab
    1. You need a setuid-root binary that reports what the kernel gave it. Busybox will not do — it dispatches on argv[0], so a renamed copy is inert — so compile four lines of C. Statically linked, because the rootfs is musl and the host is glibc. 
      cat > ~/whoareyou.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("ruid=%d euid=%d rgid=%d egid=%d\n",
           getuid(), geteuid(), getgid(), getegid());
    return 0;
}
EOF
cd ~/i11
gcc -static -O2 -o whoareyou ~/whoareyou.c
sudo install -o root -g root -m 4755 whoareyou rootfs/bin/whoareyou
sudo ls -l rootfs/bin/whoareyou
      -rwsr-xr-x 1 root root 785536 Jul 31 14:49 rootfs/bin/whoareyou

      The s in -rwsr-xr-x is the whole experiment.

    2. Run as uid 1000 with the flag off, using the run helper from I11.1. The shell reports its own uid, then the no_new_privs bit, then execs the setuid binary. 
      A='["/bin/sh","-c","echo shell: $(id -u); grep NoNewPrivs /proc/self/status; /bin/whoareyou"]'
run A '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false' "$A"
      shell: 1000
NoNewPrivs:	0
ruid=1000 euid=0 rgid=1000 egid=1000

      The container was configured to run as an unprivileged user, and one execve later the effective uid is 0.

    3. Change exactly one boolean. 
      run B '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=true' "$A"
      shell: 1000
NoNewPrivs:	1
ruid=1000 euid=1000 rgid=1000 egid=1000

      The binary still runs — it is not blocked, it simply does not get the uid. That distinction matters when you are reading a bug report: the symptom is a permission error deep inside a tool, not a refusal to start.

    4. Show that this is orthogonal to capabilities. Flag off, but every capability stripped from the bounding set. 
      run C '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","/bin/whoareyou; grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status"]'
      ruid=1000 euid=0 rgid=1000 egid=1000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000

      uid 0 with an empty bounding set. The escalation happened; it just arrived with nothing in its hands. Dropping capabilities does not close the setuid hole, and closing the setuid hole does not drop capabilities — you want both.

    5. The other lever, for comparison: nosuid on the mount rather than the process. Bind-mount the same directory a second time with nosuid and run the same binary through both paths, with the flag still off. 
      run D '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .mounts += [{"destination":"/mnt","source":"/home/ubuntu/i11/rootfs/bin",
                    "type":"bind","options":["rbind","nosuid","ro"]}]' \
      '["/bin/sh","-c","echo via-rootfs:; /bin/whoareyou; echo via-nosuid-bind:; /mnt/whoareyou"]'
      via-rootfs:
ruid=1000 euid=0
via-nosuid-bind:
ruid=1000 euid=1000

      One binary, one inode, two mount paths, two outcomes. This is why nosuid is on nearly every mount in the default bundle, and why a hand-written mount entry that omits it quietly re-opens the door on that path.

    Verify

    You can state what noNewPrivileges stops (a uid change at execve) and what it does not (anything to do with capabilities the process already holds), and you can name the second, mount-level control that produces the same result for one filesystem.

    Gotchas
    • Absent is false. The field is OPTIONAL and the spec's default is off. runc spec happens to write true; a config assembled by hand or by a tool that only sets the fields it cares about will not. Check for the field's presence, not just its value.
    • It breaks tools that legitimately escalate. Anything relying on a setuid helper — ping on some distributions, sudo, newuidmap, some FUSE mounts — stops working with an error from inside the tool. If a container works without the flag and fails with it, look for a setuid bit before looking anywhere else: find / -perm -4000 -type f.
    • It cannot be turned off, including by you. There is no way to run a privileged helper "just once" after the bit is set. If a container genuinely needs one, that is an argument for a different container, not for clearing the bit.
    • It does not stop a container that is already root. Everything above assumed a non-root uid. A root container has nothing to escalate to; the flag is close to a no-op there, which is why it belongs with a non-root uid rather than instead of one.

    securityContext.allowPrivilegeEscalation: false is this exact field, and the Pod Security Standards' Restricted profile requires it. Note it is a separate field from runAsNonRoot and is not implied by it — step 2 is what a pod with runAsNonRoot: true and the default allowPrivilegeEscalation looks like. The advanced track has no Pod Security Standards lesson to link into; the closest existing material is W1.2, where you inspect what the control-plane containers on a node actually run as.

    Docs: the kernel's no_new_privs.rst; man 2 prctl under PR_SET_NO_NEW_PRIVS; man 8 mount for nosuid; and B4.15, whose debugging drill is a copied setuid binary.
