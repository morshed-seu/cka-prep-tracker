    I11 — Container security & supply chain

    Two halves that are usually taught apart: hardening the container that runs here, and knowing that the image you are running is the one you meant. Every control below gets proved by attempting the thing it is supposed to forbid.

    The reason to do this by hand is that almost every control here is a single JSON field, and almost every one of them behaves differently from how it reads. A capability listed in effective is ignored for a root container and silently dropped for a non-root one. A seccomp rule listing three syscall names applies the same argument index to all three, and the index is not the same for all three. An AppArmor deny rule blocks the write and logs nothing. Each of those is one measured line below, and each one is the difference between a control you have and a control you think you have.

    • Rootless. Run runc and then the whole containerd stack as an unprivileged user, and measure what that buys and what it costs.
    • Supply chain. Sign an image with cosign and find where the signature is stored, attach and read back an attestation, generate an SBOM and use it to answer a question, scan for vulnerabilities and do the arithmetic that changes a base-image decision, and prove why a digest is the only immutable reference.
    • Project & drill. Build run-verified.sh — refuse to run what does not verify, then run it locked down — and diagnose two faults whose error messages name nothing useful.

    Runtime hardening

    I11.1

    Five capability sets, three of which are usually lies

    Why it matters

    "Root" on Linux is not one switch. It is a bag of about forty separate permits — bind a low port, change a file's owner, open a raw socket, load a kernel module — and B4.10 took that bag apart by hand. A container config declares which permits the process gets, in five arrays. The trap is that only one of those five arrays reliably does what its name suggests, and which one that is depends on whether the container runs as root. Get this wrong and you write a config that reads like least privilege and grants everything, or one that grants a capability the process never receives.

    The concept

    I2.4 read these five arrays out of the spec and watched one of them override another. This lesson asks the next question: for a given container, which of the five does the kernel actually honour? The answer is rarely more than two.

    Every Linux process carries five capability sets, and the kernel recomputes four of them on every execve. That recomputation is the whole story:

    • bounding is a ceiling. Nothing in the container can ever raise a capability that is not in it, including a process that later becomes uid 0. It is the only set that is a real containment boundary.
    • permitted is what the process may switch on. For a process running as uid 0, execve recomputes permitted from the bounding set — so listing a capability here is redundant. For a process running as any other uid, execve recomputes it to empty unless the capability is also ambient.
    • effective is what is switched on right now. For uid 0 the kernel sets it equal to permitted at execve. So for a root container the effective array in config.json is ignored — you can leave a capability out of it and the process still has it.
    • inheritable survives execve only in combination with a file's own inheritable set, which container images essentially never use. On its own it does nothing.
    • ambient is the one that makes a non-root process keep a capability across execve. The kernel refuses to raise an ambient capability that is not also in both permitted and inheritable, so ambient is really a three-field setting.

    Put plainly: for a root container, only bounding matters. For a non-root container, only bounding (as a ceiling) and ambient (plus its two prerequisites) matter. The other arrays are documentation.

    The second surprise is the default. A bare runc spec bundle grants three capabilities, not the dozen-and-a-half that Docker made famous — and CAP_NET_RAW, CAP_CHOWN and CAP_DAC_OVERRIDE are all absent. That is why several perfectly ordinary commands fail in the labs below with errors that never mention capabilities.

    The runtime spec defines the object and its five arrays, and — importantly for a gotcha further down — tells runtimes to warn rather than fail on a capability they cannot grant.

    capabilities (object, OPTIONAL) is an object containing arrays that specifies the sets of capabilities for the process. Valid values are defined in the capabilities(7) man page, such as CAP_CHOWN. Any value which cannot be mapped to a relevant kernel interface, or cannot be granted otherwise MUST be logged as a warning by the runtime. Runtimes SHOULD NOT fail if the container configuration requests capabilities that cannot be granted […]

    effective […] the effective field is an array of effective capabilities that are kept for the process.
    bounding […] the bounding field is an array of bounding capabilities that are kept for the process.
    inheritable […] the inheritable field is an array of inheritable capabilities that are kept for the process.
    permitted […] the permitted field is an array of permitted capabilities that are kept for the process.
    ambient […] the ambient field is an array of ambient capabilities that are kept for the process.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    Notice what the spec does not say: it describes each array as capabilities "kept for the process" and says nothing about the kernel's execve rules. Everything in the concept section above is kernel behaviour that the spec leaves entirely implicit — which is exactly why the arrays mislead.

    Lab
    1. Build a bundle and read the default. Use the alpine rootfs from I2; the only edits are turning off the TTY (so the container runs unattended) and dropping the network namespace (so ping 127.0.0.1 has a working loopback — a fresh netns has none, as I9.11 showed). 
      mkdir -p ~/i11 && cd ~/i11        # rootfs/ already unpacked here
runc spec
jq '.process.capabilities' config.json
      {
  "bounding":  [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "effective": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ],
  "permitted": [ "CAP_AUDIT_WRITE", "CAP_KILL", "CAP_NET_BIND_SERVICE" ]
}

      Three sets, not five — inheritable and ambient are simply absent — and three capabilities in each.

    2. Define a small helper so each experiment is one line. It rewrites config.json from scratch every time, applies one jq filter, and runs the result. 
      run() {   # run <name> <jq-filter> <args-json>
  rm -f config.json; runc spec
  jq "$2 | .process.terminal=false | .process.args=$3 |
      .linux.namespaces |= map(select(.type!=\"network\")) |
      .root.readonly=false" config.json > c.tmp && mv c.tmp config.json
  sudo runc --root /run/runc-i11 run "i11$1"
  sudo runc --root /run/runc-i11 delete -f "i11$1" 2>/dev/null

      0x20000420 is bits 29, 10 and 5 — CAP_AUDIT_WRITE, CAP_NET_BIND_SERVICE, CAP_KILL. Root, with three of forty permits.

    4. Prove a missing capability by using it. ping needs CAP_NET_RAW to open a raw ICMP socket. 
      run B '.' '["/bin/ping","-c1","-W1","127.0.0.1"]'
      PING 127.0.0.1 (127.0.0.1): 56 data bytes

      It is root. The message is busybox guessing, and it is guessing wrong — the single most common way this failure gets misdiagnosed. Add the capability to all three sets and it works:

      run C '.process.capabilities.bounding  += ["CAP_NET_RAW"] |
       .process.capabilities.effective += ["CAP_NET_RAW"] |
       .process.capabilities.permitted += ["CAP_NET_RAW"]' \
      '["/bin/ping","-c1","-W1","127.0.0.1"]'
      64 bytes from 127.0.0.1: seq=0 ttl=64 time=0.044 ms
1 packets transmitted, 1 packets received, 0% packet loss

      CH='["/bin/sh","-c","touch /f && echo touch=ok; chown 99:99 /f; echo chown_rc=$?"]'

chown_rc=1       chown_rc=0

      Two capability failures, two different messages — permission denied and operation not permitted. Neither says "capability".

    6. Now the first lie. Add CAP_CHOWN to bounding and permitted but deliberately leave it out of effective. 
      run F '.process.capabilities.bounding  += ["CAP_CHOWN"] |
       .process.capabilities.permitted += ["CAP_CHOWN"]' "$CH"
      CapPrm:	0000000020000421
CapEff:	0000000020000421     ← the config said 0x…420
CapBnd:	0000000020000421
touch=ok
chown_rc=0

      The capability is effective anyway, and the chown succeeds. The kernel's rule for a uid-0 execve is effective′ = permitted′, so whatever config.json said about effective was overwritten before the first instruction ran.

    7. The second lie, and it fails the other way. Same three-set grant, but run as uid 1000. 
      run F2 '.process.user.uid=1000 | .process.user.gid=1000 |
        .process.capabilities.bounding  += ["CAP_CHOWN"] |
        .process.capabilities.permitted += ["CAP_CHOWN"] |
        .process.capabilities.effective += ["CAP_CHOWN"]' \

      uid=1000 gid=1000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000020000421     ← the ceiling survived
CapAmb:	0000000000000000
chown: /data/owned: Operation not permitted
chown_rc=1

      Permitted and effective were both wiped. This is the exact shape of a Kubernetes pod that sets runAsNonRoot alongside capabilities.add — the add is silently void.

    8. Fix it the only way that works: ambient, with its two prerequisites. 
      run J '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.capabilities.bounding    += ["CAP_CHOWN"] |
       .process.capabilities.permitted   += ["CAP_CHOWN"] |
       .process.capabilities.effective   += ["CAP_CHOWN"] |
       .process.capabilities.inheritable  = ["CAP_CHOWN"] |
       .process.capabilities.ambient      = ["CAP_CHOWN"]' \
      '["/bin/sh","-c","id; grep -E \"^Cap(Prm|Eff|Amb|Inh)\" /proc/self/status; chown 99:99 /data/owned; echo chown_rc=$?"]'

CapPrm:	0000000000000001
CapEff:	0000000000000001
CapAmb:	0000000000000001

      Drop just the inheritable line and runc tells you, before the container starts:

      level=warning msg="can't raise ambient capability CAP_CHOWN: operation not permitted"
CapAmb:	0000000000000000
chown: /data/owned: Operation not permitted
    9. Finally, the ceiling. Empty the bounding set and nothing can climb back. 
      run G '.process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status; id -u"]'
      CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000
0

      uid 0 with an empty bounding set: root by name, with no permits at all. That is what drop: ["ALL"] compiles to.

    Verify

    You can look at a config.json capability block and say which arrays will actually take effect, given the process.user.uid beside them — and you can name the one array (bounding) that is a containment boundary rather than a request.

    Gotchas
    • The effective array is dead weight for a root container. The kernel recomputes it from permitted at execve. Reviewers who check that a capability was left out of effective are checking nothing.
    • permitted is dead weight for a non-root container. Measured above: uid 1000 came out with CapPrm 0 despite the config listing CAP_CHOWN in all three arrays. Non-root plus capabilities.add needs ambient, and Kubernetes has no field for it.
    • A misspelled capability is a warning, not an error. Adding CAP_NOT_A_REAL_CAP produced level=warning msg="ignoring unknown or unavailable capabilities: [CAP_NOT_A_REAL_CAP]" and a container with the unchanged default set. The spec explicitly asks for exactly this ("Runtimes SHOULD NOT fail"), so a typo in a hardening config fails open and the container starts.
    • CAP_DAC_OVERRIDE is not in the default set, and its absence looks like a storage bug. Container root could not create a file in a directory owned by uid 1000 — touch: /data/x: Permission denied — until CAP_DAC_OVERRIDE was added. Nothing in that message suggests capabilities; see I10.12, where the same absence surfaces as a volume-permissions fault.

    securityContext.capabilities.drop: ["ALL"] becomes exactly the empty-bounding-set container from step 9, and add: ["NET_BIND_SERVICE"] becomes the three-array grant from step 4 — note the CAP_ prefix is stripped in Kubernetes and required in the OCI config. The runAsNonRoot + add combination in step 7 is the trap worth remembering, because the pod starts and the capability simply is not there. The advanced track has no securityContext lesson to link — the nearest relatives are least privilege as a principle in W7.6's RBAC matrix, and W1.2, where you look at what actually runs privileged on a node.

    Docs: man 7 capabilities — the "Transformation of capabilities during execve()" section is the rulebook for everything above; the runtime spec's config.md § User; and B4.12, where you read these same sets out of /proc/self/status without a container.

    I11.2

    noNewPrivileges, and the escape hatch it welds shut

    Why it matters

    You have carefully set the container to run as an unprivileged user. Then the image ships a single file with the setuid bit on it — /usr/bin/passwd, ping, an old mount helper, or something a base image dragged in — and any process in the container can exec that file and come out as root. noNewPrivileges is a one-bit promise to the kernel that closes this, permanently, for the process and every descendant. It is one of the very few security fields that has no downside worth discussing, and one of the few that runc spec already turns on for you.

    The concept

    B4.9 covered the setuid bit: a file marked u+s and owned by root runs with the effective uid of its owner, not its caller. That is how an ordinary user changes their own password. Inside a container it is a privilege-escalation primitive sitting in the filesystem, and it needs no bug to use — it is the documented behaviour of execve.

    noNewPrivileges maps to the kernel's no_new_privs bit, set with prctl(PR_SET_NO_NEW_PRIVS, 1). Once set, the kernel guarantees that no execve from this process onward can raise privilege: setuid and setgid bits are ignored, file capabilities are ignored, and an AppArmor or SELinux transition to a more-privileged profile is refused. The bit is one-way — nothing can clear it — and it is inherited by every child. That one-wayness is what makes it trustworthy: a compromised process cannot turn it off before exploiting the setuid file.

    Two things it is often confused with. It is not a capability control — the escalating process gains uid 0, not capabilities, and those are separate mechanisms (you will see both outcomes side by side below). And it is not the only lever: the nosuid mount option does the same job per-filesystem rather than per-process, which is why it appears on almost every mount in a default bundle.

    The spec gives it two sentences and points at the kernel, which is honest — the semantics are entirely the kernel's.

    noNewPrivileges (bool, OPTIONAL) setting noNewPrivileges to true prevents the process from gaining additional privileges. As an example, the no_new_privs article in the kernel documentation has information on how this is achieved using a prctl system call on Linux.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    OPTIONAL, and defaulting to false when absent. runc spec writes "noNewPrivileges": true into the bundle it generates, so the generated default is safe and the specified default is not. A hand-built config that simply omits the field gets the unsafe one.

    Lab
    1. You need a setuid-root binary that reports what the kernel gave it. Busybox will not do — it dispatches on argv[0], so a renamed copy is inert — so compile four lines of C. Statically linked, because the rootfs is musl and the host is glibc. 
      cat > ~/whoareyou.c <<'EOF'
#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("ruid=%d euid=%d rgid=%d egid=%d\n",
           getuid(), geteuid(), getgid(), getegid());
    return 0;
}
EOF
cd ~/i11
gcc -static -O2 -o whoareyou ~/whoareyou.c
sudo install -o root -g root -m 4755 whoareyou rootfs/bin/whoareyou
sudo ls -l rootfs/bin/whoareyou
      -rwsr-xr-x 1 root root 785536 Jul 31 14:49 rootfs/bin/whoareyou

      The s in -rwsr-xr-x is the whole experiment.

    2. Run as uid 1000 with the flag off, using the run helper from I11.1. The shell reports its own uid, then the no_new_privs bit, then execs the setuid binary. 
      A='["/bin/sh","-c","echo shell: $(id -u); grep NoNewPrivs /proc/self/status; /bin/whoareyou"]'
run A '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false' "$A"
      shell: 1000
NoNewPrivs:	0
ruid=1000 euid=0 rgid=1000 egid=1000

      The container was configured to run as an unprivileged user, and one execve later the effective uid is 0.

    3. Change exactly one boolean. 
      run B '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=true' "$A"
      shell: 1000
NoNewPrivs:	1
ruid=1000 euid=1000 rgid=1000 egid=1000

      The binary still runs — it is not blocked, it simply does not get the uid. That distinction matters when you are reading a bug report: the symptom is a permission error deep inside a tool, not a refusal to start.

    4. Show that this is orthogonal to capabilities. Flag off, but every capability stripped from the bounding set. 
      run C '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .process.capabilities.bounding=[] | .process.capabilities.effective=[] |
       .process.capabilities.permitted=[]' \
      '["/bin/sh","-c","/bin/whoareyou; grep -E \"^Cap(Prm|Eff|Bnd)\" /proc/self/status"]'
      ruid=1000 euid=0 rgid=1000 egid=1000
CapPrm:	0000000000000000
CapEff:	0000000000000000
CapBnd:	0000000000000000

      uid 0 with an empty bounding set. The escalation happened; it just arrived with nothing in its hands. Dropping capabilities does not close the setuid hole, and closing the setuid hole does not drop capabilities — you want both.

    5. The other lever, for comparison: nosuid on the mount rather than the process. Bind-mount the same directory a second time with nosuid and run the same binary through both paths, with the flag still off. 
      run D '.process.user.uid=1000 | .process.user.gid=1000 |
       .process.noNewPrivileges=false |
       .mounts += [{"destination":"/mnt","source":"/home/ubuntu/i11/rootfs/bin",
                    "type":"bind","options":["rbind","nosuid","ro"]}]' \
      '["/bin/sh","-c","echo via-rootfs:; /bin/whoareyou; echo via-nosuid-bind:; /mnt/whoareyou"]'
      via-rootfs:
ruid=1000 euid=0
via-nosuid-bind:
ruid=1000 euid=1000

      One binary, one inode, two mount paths, two outcomes. This is why nosuid is on nearly every mount in the default bundle, and why a hand-written mount entry that omits it quietly re-opens the door on that path.

    Verify

    You can state what noNewPrivileges stops (a uid change at execve) and what it does not (anything to do with capabilities the process already holds), and you can name the second, mount-level control that produces the same result for one filesystem.

    Gotchas
    • Absent is false. The field is OPTIONAL and the spec's default is off. runc spec happens to write true; a config assembled by hand or by a tool that only sets the fields it cares about will not. Check for the field's presence, not just its value.
    • It breaks tools that legitimately escalate. Anything relying on a setuid helper — ping on some distributions, sudo, newuidmap, some FUSE mounts — stops working with an error from inside the tool. If a container works without the flag and fails with it, look for a setuid bit before looking anywhere else: find / -perm -4000 -type f.
    • It cannot be turned off, including by you. There is no way to run a privileged helper "just once" after the bit is set. If a container genuinely needs one, that is an argument for a different container, not for clearing the bit.
    • It does not stop a container that is already root. Everything above assumed a non-root uid. A root container has nothing to escalate to; the flag is close to a no-op there, which is why it belongs with a non-root uid rather than instead of one.

    securityContext.allowPrivilegeEscalation: false is this exact field, and the Pod Security Standards' Restricted profile requires it. Note it is a separate field from runAsNonRoot and is not implied by it — step 2 is what a pod with runAsNonRoot: true and the default allowPrivilegeEscalation looks like. The advanced track has no Pod Security Standards lesson to link into; the closest existing material is W1.2, where you inspect what the control-plane containers on a node actually run as.

    Docs: the kernel's no_new_privs.rst; man 2 prctl under PR_SET_NO_NEW_PRIVS; man 8 mount for nosuid; and B4.15, whose debugging drill is a copied setuid binary.

    I11.3

    A seccomp profile, written by hand, and the SIGSYS it produces

    Why it matters

    Capabilities decide which privileged operations a process may perform. Seccomp decides which system calls it may make at all — a finer instrument in one sense and a blunter one in another. It is the control that stops a container reaching a kernel bug in a syscall it never needed, and it is the control most likely to break a workload in a way whose error message names nothing useful. Both halves of that sentence are things you should see happen rather than read about, which is what this lesson does.

    The concept

    A seccomp filter is a small program the kernel runs before every system call the process makes. It looks at the syscall number and, optionally, at the raw integer arguments, and returns an action: allow it, fail it with an errno, log it, or kill something. The filter is installed once and is irreversible and inherited — the same one-way property as no_new_privs, and in fact installing a filter requires either CAP_SYS_ADMIN or the no_new_privs bit, so the two travel together.

    B12.14 installed one of these by hand, and I1.9 got killed by one on purpose. The OCI config expresses the same thing as JSON under linux.seccomp: a defaultAction that applies to every syscall not otherwise mentioned, then an array of syscalls entries, each with a list of names, an action, and optionally args to match on argument values.

    That gives you two ways to write a profile, and they fail very differently:

    • A deny-list — defaultAction: SCMP_ACT_ALLOW plus entries blocking specific syscalls. Easy to write, impossible to make complete, and the right shape when you want to remove one known-dangerous call.
    • An allow-list — defaultAction: SCMP_ACT_ERRNO plus an enumeration of everything permitted. Genuinely restrictive, and much harder than it looks: the enumeration must cover the syscalls the runtime makes while setting the container up, not just the ones your program makes. You will watch that fail four times below before it works.

    One structural detail that decides whether a profile does what you meant: args matches on the raw register values, and it cannot follow pointers. So you can filter chmod by mode but never by path — the path is a pointer, and the filter sees only the address. This is not a limitation of the OCI schema, it is a limitation of the kernel's filter, and it is why "block writes to /etc" is not a thing seccomp can do.

    The schema is small enough to hold in your head. Note that defaultAction is the only REQUIRED field, and note the warning the spec itself attaches to an empty allow-list.

    defaultAction (string, REQUIRED) - the default action for seccomp. Allowed values are the same as syscalls[].action.
    defaultErrnoRet (uint, OPTIONAL) - the errno return code to use. […] The default is EPERM.
    architectures (array of strings, OPTIONAL) - the architecture used for system calls.
    syscalls (array of objects, OPTIONAL) - match a syscall in seccomp. While this property is OPTIONAL, some values of defaultAction are not useful without syscalls entries. For example, if defaultAction is SCMP_ACT_KILL and syscalls is empty or unset, the kernel will kill the container process on its first syscall.
    · names (array of strings, REQUIRED) - the names of the syscalls. names MUST contain at least one entry.
    · action (string, REQUIRED) - the action for seccomp rules.
    · args (array of objects, OPTIONAL) — with index, value, valueTwo and op.
    OCI Runtime Specification v1.3.0, Linux Configuration § Seccomp — config-linux.md
    Lab
    1. First, establish that there is nothing here by default. 
      cd ~/i11 && rm -f config.json && runc spec
jq '.linux | has("seccomp")' config.json
      false

      A bare bundle has no seccomp filter at all. The "runtime default profile" people talk about belongs to containerd and Docker, not to runc — which is why a container started by runc directly is less confined than the same image under ctr.

    2. Write the smallest real profile: allow everything, refuse to make directories. 
      cat > seccomp-errno.json <<'EOF'
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64", "SCMP_ARCH_X86", "SCMP_ARCH_X32"],
  "syscalls": [
    { "names": ["mkdir", "mkdirat"], "action": "SCMP_ACT_ERRNO" }
  ]
}
EOF

      Extend the run helper to splice a profile file into the config:

      runsec() {   # runsec <name> <profile.json> <args-json>
  rm -f config.json; runc spec
  jq --slurpfile s "$2" ".process.terminal=false | .process.args=$3 |
      .linux.namespaces |= map(select(.type!=\"network\")) |
      .root.readonly=false | .linux.seccomp = \$s[0]" config.json > c.tmp && mv c.tmp config.json
  sudo dmesg -C
  sudo runc --root /run/runc-i11 run "i11$1"
  sudo runc --root /run/runc-i11 delete -f "i11$1" 2>/dev/null
  sudo dmesg | tail -3
}

      mkdir: can't create directory '/d': Operation not permitted
rc=1
    3. Change the errno the filter returns. 38 is ENOSYS. 
      jq '.syscalls[0].errnoRet = 38' seccomp-errno.json > seccomp-enosys.json

      This is not a curiosity. ENOSYS is what a kernel returns for a syscall it does not have, so libraries treat it as "try the older way" rather than "you are not allowed".     Gotchas
    • One args block, many names, different argument positions. Measured above: grouping chmod with fchmodat under index: 2 produced a rule that silently did not fire. Group syscalls by argument layout, not by what they are called.
    • architectures adds, it does not select. A profile listing only ARM still filters on x86-64.
    • The filter covers the runtime's setup, not just your program. An allow-list that omits fcntl, openat2 or statfs fails with an error about file descriptors or a Rust panic, never about seccomp.
    • A killing action kills the calling process, which is often not the container. The shell survived its mkdir child and the container exited 0 — so a seccomp violation can leave a "successful" container that silently did not do its job.

    I11.4

    Two fields that delegate to something outside the container

    Why it matters

    Seccomp cannot see file paths. Capabilities cannot express "this program, and only this program, may write to that directory". Mandatory access control can do both, and the OCI config reaches it through two one-line string fields — process.apparmorProfile and linux.selinuxLabel. What makes them different from every other field in this module is that the string is a name, and the thing it names lives on the host, outside the bundle entirely. Ship the config without shipping the profile and the container does not start.

    The concept

    Discretionary access control — the owner/group/other bits from B4.5 — is called discretionary because the owner of a file decides who may touch it. Mandatory access control sits above that: an administrator writes a policy, the kernel enforces it on every access, and no file owner and no root process can override it. The two checks are independent and both must pass, so MAC can only ever remove permissions the DAC bits would have granted.

    Linux ships two implementations, and which one you get is decided by your distribution rather than by you. AppArmor (Debian, Ubuntu, SUSE) attaches policy to executables by path and is written as readable rules over paths and capabilities. SELinux (RHEL, Fedora, CentOS) attaches a label to every process and every file and consults a compiled policy about which label may touch which. For containers, SELinux's category mechanism (the c124,c675 at the end of a label) is what keeps two containers on one host from reading each other's files even when the uid is the same.

    The OCI config sets one string each way. Both are OPTIONAL, both default to unset, and a bare runc spec bundle sets neither — which means the honest default for a hand-built container is no mandatory access control at all.

    Two bullets, one for each, and both defer entirely to the host system.

    apparmorProfile (string, OPTIONAL) specifies the name of the AppArmor profile for the process. For more information about AppArmor, see AppArmor documentation.

    selinuxLabel (string, OPTIONAL) specifies the SELinux label for the process. For more information about SELinux, see SELinux documentation.
    OCI Runtime Specification v1.3.0, Configuration § User — config.md

    The spec's own example config uses "apparmorProfile": "acme_secure_profile" and "selinuxLabel": "system_u:system_r:svirt_lxc_net_t:s0:c124,c675". Neither string means anything without a host that already knows it.

    Lab
    1. Write a profile. This one permits everything a container normally does and then denies exactly one path — which is the shape you want, because an AppArmor profile is an allow-list and omitting a permission you need breaks the container in a way that looks like a filesystem bug.

    Gotchas
    • deny logs nothing; audit deny logs. Measured above with two otherwise identical profiles. Any runbook that says "check the audit log to confirm the denial" is assuming the second form.
    • The profile is not in the bundle. Both fields are names resolved on the host. A bundle, an image and a pod spec are all fully portable; the policy they name is not. Treat profile installation as part of node provisioning.
    • An AppArmor profile is an allow-list with deny overrides. The bare rules file, and capability, in the lab grant everything of that kind. Omit them and the container fails in ways that look like a corrupt image — start permissive, add denials, and use complain mode plus aa-logprof to tighten.
    • noNewPrivileges and MAC interact. With no_new_privs set, the kernel refuses an execve that would transition to a more privileged profile. Profiles that rely on a transition at exec stop transitioning, silently, once you turn the flag on.
    • SELinux labels are not optional decoration. On a SELinux host, a volume mounted without the right category label is unreadable by the container even though every uid and mode is correct — the same class of confusing failure as I10.12's uid mismatch, with a different cause.

    I11.5

    A read-only rootfs, the workloads it cures and the one it cannot

    Why it matters

    Most attacks that get a foothold in a container want to write something to it — a webshell into the document root, a modified binary on PATH, a cron entry. One boolean removes the whole category, and it costs nothing for a well-behaved application. The interesting part is what "well-behaved" turns out to mean, because the standard fix — a tmpfs over /tmp — cures one class of application completely and does nothing at all for another.

    The concept

    root.readonly asks the runtime to remount the container's own root filesystem read-only after it has finished setting it up. What it covers is exactly the rootfs and nothing else: every other mount in mounts keeps whatever options it was given, so a writable bind mount or volume stays writable. That separation is the design — the container's code becomes immutable while its data does not.

    I2.5 read this field out of the spec; the point here is what happens to real programs. Three sources of writes have to be dealt with, and only the first two have a good answer:

    • Scratch space — temp files, a pid file, a unix socket, a lock. Cure: a tmpfs over the directory. The data was never meant to survive the process anyway, and putting it in RAM is usually an improvement.
    • State that must persist — a database, uploaded files, a cache you actually want warm. Cure: a volume. That was always the right answer; the read-only rootfs just forces the question.
    • Writes into the program's own install tree — a package manager, a plugin installer, a framework that compiles templates next to the source. There is no cure. You cannot tmpfs over /usr without deleting the program. These workloads have to be rebuilt, not reconfigured, and recognising one early saves a long afternoon.

    There is a second, quieter piece of read-only protection in every default bundle: linux.readonlyPaths and linux.maskedPaths. The first remounts specific paths read-only; the second hides them entirely by bind-mounting /dev/null over them. They exist because /proc and /sys have to be mounted read-write for the container to work at all, and a handful of files under them are dangerous.

    One sentence, and a default that catches people out.

    readonly (bool, OPTIONAL) If true then the root filesystem MUST be read-only inside the container, defaults to false.
    OCI Runtime Specification v1.3.0, Configuration § Root — config.md

    Defaults to false — but runc spec writes "readonly": true into the bundle it generates. As with noNewPrivileges, the generated default and the specified default disagree, and the labs below have been turning it off all module to get anything done.

    Given a workload that fails on a read-only rootfs, you can tell within a minute which of the three categories it is in — by reading where the failed writes point — and therefore whether the fix is a tmpfs, a volume, or a rebuild.

    Gotchas
    • A package manager reports success it did not have. Measured: apk printed "8 MiB in 17 packages" and exited 17, with none of the binaries installed. Anything that runs apk/apt/pip install at container start is incompatible with a read-only rootfs, and its own exit code is the only honest signal.
    • /dev/shm and /dev stay writable. They are separate tmpfs mounts. Useful for you, and equally useful to anyone else who ends up in the container.
    • Writable mounts are unaffected, by design. The flag covers the rootfs only; a rw bind mount writes through to the host. Turning on the boolean while leaving a broad hostPath mounted changes very little.
    • maskedPaths is /dev/null bind-mounted over the file. So the path still exists, ls shows a character device, and a program that checks for the file's presence rather than its content will happily proceed and read nothing.
    • Sizing a tmpfs is sizing memory. A tmpfs with no size= advertises half of RAM and is charged to the container's memory cgroup as it fills — which is I10.2's pod that fills the node, arriving through a different door.

    securityContext.readOnlyRootFilesystem: true is this field, and the emptyDir: {medium: Memory} volume you pair it with is the tmpfs from step 6 — see W5.1 for emptyDir in the advanced track. Kubernetes exposes maskedPaths/readonlyPaths only through procMount, whose non-default value requires a user namespace; the /proc/kcore masking in step 3 is what you lose by changing it.

    Docs: the runtime spec's config.md § Root and config-linux.md § Masked Paths / Readonly Paths; man 5 tmpfs for the size= and mode= options; and I2.5, where the same field was read rather than exercised.

    Rootless

    I11.6

    Rootless runc, and why its default mapping is exactly one id

    Why it matters

    Every control so far has been about limiting what a container can do given that the runtime runs as root. Rootless changes the premise: the container's uid 0 is an ordinary unprivileged uid on the host, so an escape lands you as a normal user rather than as root. It is the single largest change in blast radius available, and it is also the one with the most surprising list of things that stop working. This lesson gets it running and finds the boundary; the next one takes the whole stack down.

    The concept

    I1.1 and I1.2 built the mechanism: a user namespace holds a uid_map saying "container uid 0 is host uid N", the mapping may be written exactly once, and writing a mapping with more than one entry requires the setuid helper newuidmap backed by a range in /etc/subuid. A rootless container is that, with a rootfs on top.

    The OCI config expresses it with linux.uidMappings and linux.gidMappings, plus a user namespace in linux.namespaces. runc spec --rootless generates a bundle that will run as you, and comparing it with the ordinary one is the fastest way to see what an unprivileged runtime cannot do — cgroup limits disappear, the network namespace disappears, and /sys stops being a fresh sysfs mount and becomes a bind of the host's.

    The important structural fact, and the one that catches everyone: the generated mapping has size: 1. It maps container uid 0 to your uid and nothing else. That is not conservatism — it is the only mapping runc can install on its own, because installing a wider one means writing subuid ranges into uid_map, and doing that requires a privilege runc does not have. Wider mappings are the job of a helper that sets the namespace up first, which is what rootlesskit does in the next checkpoint.

    Three fields, and one line at the end that is the whole reason step 6 below fails.

    uidMappings (array of objects, OPTIONAL) describes the user namespace uid mappings from the host to the container.
    gidMappings (array of objects, OPTIONAL) describes the user namespace gid mappings from the host to the container.

    Each entry has the following structure:
    · containerID (uint32, REQUIRED) - is the starting uid/gid in the container.
    · hostID (uint32, REQUIRED) - is the starting uid/gid on the host to be mapped to containerID.
    · size (uint32, REQUIRED) - is the number of ids to be mapped.

    The runtime SHOULD NOT modify the ownership of referenced filesystems to realize the mapping. Note that the number of mapping entries MAY be limited by the kernel.
    OCI Runtime Specification v1.3.0, Linux Configuration § User namespace mappings — config-linux.md

    "SHOULD NOT modify the ownership of referenced filesystems" is the spec telling the runtime not to chown your rootfs into the mapped range — which leaves the question of who does, and that is the question step 6 runs into.

    Gotchas
    • On Ubuntu 24.04 the first failure is AppArmor, and says so nowhere. failed to unshare remaining namespaces: Operation not permitted and write failed /proc/self/uid_map are both downstream of audit deny capability in the stock unprivileged_userns profile.     I11.7

    The whole stack under your uid, and the five things that change

    Why it matters

    I11.6 ran one container as you. Running the daemon as you is a different exercise, because containerd wants to write to /var/lib/containerd, listen on /run/containerd/containerd.sock, create network namespaces and set cgroup limits — and an unprivileged process may do none of those things. Watching how rootlesskit arranges for all four to appear to work anyway is the most instructive half hour in this module, and it produces a precise list of what you give up.

    The concept

    The trick is a single user namespace with a mount namespace inside it, created once at startup by rootlesskit using newuidmap. Inside that namespace you are uid 0, so /run/containerd and /var/lib/containerd are writable — but they are different directories from the host's, because rootlesskit "copies up" each one onto a fresh tmpfs before containerd looks. Every path containerd knows is the path it always was; only the namespace changed.

    Networking is the part that cannot be faked with mounts. A user namespace lets you create a network namespace, but it does not let you attach a veth to a host bridge or write a NAT rule in the host's tables — those need CAP_NET_ADMIN on the host. So rootless stacks run a userspace network stack: slirp4netns holds one end of a TAP device inside the namespace and translates the container's packets into ordinary sockets opened as your user. That is why the container's addresses come from a private range that exists nowhere on the host, and why published ports are proxied rather than DNAT'd.

    Cgroups are the one thing that works properly, and only because systemd already solved it: user@1000.service gets a delegated subtree, so limits set inside it are real kernel limits. This is the same delegation I1.6 ran into, and what is delegated has grown — measure it rather than assuming.

    There is no "rootless" section in any OCI document, and the runtime spec's abstract does not mention privilege at all. What it does say about cgroups is the one line that lets a rootless runtime be conformant while setting no limits: the path is OPTIONAL, and the runtime decides what happens when it is absent.

    cgroupsPath (string, OPTIONAL) path to the cgroups. It can be used to either control the cgroups hierarchy for containers or to run a new process in an existing container.

    […] If the value is not specified, the runtime MAY define the default cgroups path. Runtimes MAY consider certain cgroupsPath values to be invalid, and MUST generate an error if this is the case.

    Implementations of the Spec can choose to name cgroups in any manner. The Spec does not include naming schema for cgroups.
    OCI Runtime Specification v1.3.0, Linux Configuration § Control groups — config-linux.md

    Everything that makes rootless actually work — the copy-up mounts, the userspace network, the systemd cgroup delegation — lives below the specification, in rootlesskit and the distribution. That is why rootless behaves differently on different machines in ways config.json never explains.

    I11.8

    The honest table: what each control actually stops

    Why it matters

    Seven checkpoints have each turned on one control and proved it works. That is not the same as knowing what your container is protected from, because the interesting question is never "does this control work" — it is "given this attack, which of my controls is the one that stops it, and is there one?" This checkpoint builds the grid, and the discipline it demands is being willing to write nothing in a cell. A control matrix with no empty cells is a control matrix nobody checked.

    The concept

    B12.1 gave the method: name the assets, name the actors, draw the trust boundaries, and only then talk about mechanisms. Applied to a container the assets are the node's filesystem and credentials, the other containers on it, the node's capacity, and the cluster API. The actor to assume is code running inside the container, because that is what an application vulnerability gets you and it requires no container bug at all.

    That framing is what makes the table below uncomfortable. Most container controls constrain a process that is already inside, and most of them constrain it in exactly one dimension. The three that change the shape of the problem rather than trimming it are the user namespace, the absence of a host mount, and the absence of the container socket — and only the first is a control you turn on rather than a thing you refrain from doing.

    One term to keep straight, because the rest of the table depends on it. Escape to host means obtaining host-root code execution. Read host secrets means getting at a file like /etc/shadow or a kubelet credential, which usually does not require an escape — it requires a mount. Conflating the two is the most common error in these discussions, and it is why "we dropped all capabilities" is offered as an answer to a question about a hostPath.

    Read the runtime specification's own abstract and notice what is not in it. There is no mention of security, isolation, trust or threat — the document is about configuration and lifecycle, and it never claims a container is a boundary.

    The Open Container Initiative Runtime Specification aims to specify the configuration, execution environment, and lifecycle of a container.

    A container's configuration is specified as the config.json for the supported platforms and details the fields that enable the creation of a container. The execution environment is specified to ensure that applications running inside a container have a consistent environment between runtimes along with common actions defined for the container's lifecycle.
    OCI Runtime Specification v1.3.0, Abstract — spec.md

    I11.9

    Signing an image, and finding where the signature went

    Why it matters

    I4.2 established that a digest is a fingerprint of the bytes: change anything and the digest changes. What a digest cannot tell you is who made those bytes — it is an integrity check with nobody's name on it. A signature adds the name. The mechanically interesting part, and the part that surprises people, is that the signature is not inside the image at all: it is a second artifact sitting beside it in the same registry, and finding it teaches you more about the registry API than about cryptography.

    The concept

    B12.6 built the primitive: sign a hash with a private key, and anyone holding the public key can check it. Here the thing being hashed is a small JSON payload naming the image's digest, and the result is stored back in the registry.

    There are two ways to hold the key, and the difference is operational rather than cryptographic:

    • Key-based. You generate a keypair, keep the private half secret, and distribute the public half. Simple, and it inherits every key-management problem you have ever had — rotation, revocation, and the fact that a leaked key is indistinguishable from a legitimate one.
    • Keyless. You authenticate to an OIDC provider (a CI system's workload identity, a Google or GitHub account), a certificate authority called Fulcio issues a certificate binding a short-lived key to that identity, you sign, and the certificate expires in ten minutes. Because the certificate is dead by the time anyone verifies, the signature is only meaningful if there is proof it existed while the certificate was valid — which is what the Rekor transparency log provides: an append-only, publicly auditable record of the signature and its timestamp. Verification then asks "was this signed by identity X from issuer Y", not "does this match key K".

    "Keyless" is therefore a misnomer — there is a key, it just lives for ten minutes and its identity is an OIDC subject. The reason it dominates in CI is that there is no secret to store, so there is no secret to leak.

    Where the signature is stored has changed. Older cosign pushed it to a tag derived from the image digest, sha256-<hex>.sig. Current cosign uses the OCI referrers mechanism: an artifact whose manifest has a subject field pointing at the image, discovered through the registry's /v2/<name>/referrers/<digest> endpoint — with a fallback tag schema, sha256-<hex> holding an index, for registries that do not implement it. Both mechanisms are in play in the lab below, and one very familiar tool now lies about which.

    The mechanism cosign now uses is the distribution spec's referrers API, and the fallback the lab meets is specified beside it — including the exact tag name.

    To fetch the list of referrers, perform a GET request to a path in the following format: /v2/<name>/referrers/<digest>

    If the referrers API returns a 404, the client MUST fallback to pulling the referrers tag schema. The response SHOULD be an image index with the same content that would be expected from the referrers API.

    Referrers Tag Schema
    <alg>-<ref>
    · <alg>: the digest algorithm (e.g. sha256 or sha512)
    · <ref>: the digest from the subject field (limit of 64 characters)

    This tag should return an image index matching the expected response of the referrers API. Maintaining the content of this tag is the responsibility of clients pushing and deleting image manifests that contain a subject field.
    OCI Distribution Specification v1.1.1, Listing Referrers and Referrers Tag Schema — spec.md

    Three things to carry into the lab. The fallback is a MUST, not a nicety — a conformant client has to try both. The tag is <alg>-<ref>, which is why sha256-f27cad91… appears in the tag list. And it "should return an image index" — which is precisely why one Accept header gets 200 and another gets 404.

    I11.10

    Attestations: a signed statement about the image, not of it

    Why it matters

    A signature answers one question: did somebody holding this key vouch for these bytes? It cannot tell you where the bytes came from, what source commit produced them, which builder ran, or whether a human could have interfered. Those are separate claims, and an attestation is the mechanism for making one and signing it. The practical difference shows up the moment you have a real incident: "this image is signed" narrows nothing, while "this image was built by pipeline P from commit C" tells you exactly which code to read.

    The concept

    An attestation is three nested things, and separating them makes the whole ecosystem legible:

    • A predicate — the claim itself, in whatever schema fits: build provenance, an SBOM, a test result, a vulnerability scan, a manual review sign-off.
    • An in-toto Statement wrapping it — a tiny envelope with a subject (name plus digest), a predicateType URI saying how to read the predicate, and the predicate. This is what makes the claim about something.
    • A DSSE envelope around that — the signature layer, carrying the base64 payload plus one or more signatures.

    The most important of the predicate types is SLSA provenance, which answers "what built this": a buildDefinition naming the build type and its external parameters (source repository, commit), and a runDetails naming the builder and the invocation. SLSA's levels are essentially statements about how trustworthy that provenance is — whether it exists at all, whether the builder generated it rather than the build script, and whether the build was isolated enough that the provenance cannot have been forged by the thing being built.

    The storage mechanism is the one you already dissected in I11.9: another referrer artifact with a subject pointing at the image. Signature and attestation are the same shape; only the payload differs.

    The layering is specified by in-toto rather than by the OCI, and the Statement's four fields are the whole of it. Note the sentence about immutability, and the one about matching purely by digest.

    _type string (TypeURI), required — Identifier for the schema of the Statement. Always https://in-toto.io/Statement/v1 for this version of the spec.

    subject array of ResourceDescriptor objects, required — Set of software artifacts that the attestation applies to. Each element represents a single software artifact. Each element MUST have digest set.
    Subjects are assumed to be immutable, i.e. the artifacts identified by the subject SHOULD NOT change.
    […] IMPORTANT: Subject artifacts are matched purely by digest, regardless of content type.

    predicateType string (TypeURI), required — URI identifying the type of the Predicate.
    in-toto Attestation Framework, Statement — spec/v1/statement.md. Note that cosign v3.1.2 still emits _type: https://in-toto.io/Statement/v0.1, the previous version, as the lab shows.

    "Matched purely by digest" is the sentence that connects this checkpoint to I11.13: an attestation is bound to bytes, and a tag that moves leaves it attached to bytes nobody is running.

      Which is what you want, and the error is unusually helpful: it lists what is attached. Note that the signature itself shows up in that list as https://sigstore.dev/cosign/sign/v1 — signature and attestation really are the same mechanism. A policy that says "must have provenance" has to name the predicate type, or it accepts an image whose only attestation is a test report.

    Verify

    You can state the difference between a signature and an attestation in one sentence each, decode a DSSE payload by hand, and name the field a policy must check so that "has an attestation" does not silently mean "has any attestation at all".

    Gotchas
    • An attestation is only as trustworthy as who generated it. Provenance written by the build script it describes is a claim the build makes about itself. SLSA's levels are graded almost entirely on whether the platform produced it out of the build's reach.
    • Signature and attestation look identical in the registry. Same artifactType, same referrers index, same subject. Tools tell them apart by the payload's media type, so cosign tree showing "two artifacts" tells you nothing about what they claim.
    • --type is a filter on verification, not just a label on signing. Omit it and you are asking "is there anything signed attached to this image".
    • The subject is a digest. An attestation attached to :v1 follows the digest, not the tag — so a re-pushed tag orphans it exactly the way I11.13 orphans a signature.
    • Attestations grow. An SBOM attestation for a large image is megabytes, stored in the registry, pulled by every verifier. Attaching SBOMs to every build of every image is a real storage and bandwidth decision, not a free win.

    Attestation verification is admission-time work, the same as signature verification — Sigstore's Policy Controller and Kyverno both express policies like "the image must carry SLSA provenance whose builder.id is our pipeline and whose source is our repository". That is a much stronger statement than "signed by our key", and it is expressible only because the predicate is structured data rather than an opaque blob. Kubernetes itself checks none of this; the advanced track's closest material is W7.5's walk through the request path, which stops before admission.

    Docs: the in-toto Attestation specification (Statement and predicate layers); SLSA v1.0's Provenance schema and its levels; the DSSE envelope specification; and cosign attest --help for the built-in predicate types.

    I11.11

    An SBOM, and the question it exists to answer in minutes

    Why it matters

    A serious vulnerability lands in a widely-used library on a Friday afternoon. The only question that matters for the next hour is do we ship it, and where. Without an inventory that question is answered by pulling every image and grepping, which takes a day and misses things. With one it is a jq filter over files you already have. That is the entire value proposition of a software bill of materials, and it is worth building the reflex on five images before you need it on five hundred.

    The concept

    An SBOM is a list of the components in an artifact, with versions and enough identity to match against a vulnerability database. Generating one from an image is not guesswork: the tool unpacks the layers and reads the package managers' own databases — /lib/apk/db/installed for Alpine, /var/lib/dpkg/status for Debian, plus language-level manifests like *.dist-info for Python and go.mod data embedded in Go binaries. Each finding records which cataloger found it and at which path, so a surprising entry can always be traced back.

    The identity that makes the whole thing work is the purl (package URL): pkg:apk/alpine/zlib@1.3.2-r0?arch=x86_64&distro=alpine-3.21.7. It encodes ecosystem, namespace, name, version and qualifiers in one string, so matching against an advisory does not depend on string-comparing human-written package names.

    Three formats are in circulation and you will meet all of them. SPDX is the ISO-standardised one, licensing-oriented in origin. CycloneDX comes from OWASP and is security-oriented. syft-json is the tool's native format and is the most detailed. They describe the same image and — as the lab shows — report different counts, which is the first thing to understand before anyone builds a metric on top of one.

    No OCI document defines an SBOM. The load-bearing specification here is the package-URL format, because a purl is what makes an inventory joinable to an advisory database — the same string in your SBOM and in somebody else's vulnerability feed.

    A purl is a URL composed of seven components:
    scheme:type/namespace/name@version?qualifiers#subpath
    Components are separated by a specific character for unambiguous parsing.

    · scheme — Required — The URL scheme with the constant value of "pkg".
    · type — Required — The package "type" or package "protocol" such as maven, npm, nuget, gem, pypi, etc.
    · namespace — Optional — A name prefix such as a Maven groupid, a Docker image owner, a GitHub user or organization. Namespace is type-specific.
    · name — Required — The name of the package.
    · version — Optional — The version of the package.
    · qualifiers — Optional — Qualifier data for a package such as OS, architecture, repository, etc.
    · subpath — Optional — Subpath within a package, relative to the package root.
    Package-URL Specification (ECMA-427), Specification § Table 1 — package-url/purl-spec

    Map that onto the entry the lab produces — pkg:apk/alpine/alpine-baselayout@3.6.8-r1?arch=x86_64&distro=alpine-3.21.7 — and every component is accounted for. The distro qualifier is what lets a matcher distinguish "Alpine's build of zlib" from "Debian's build of zlib", which is the difference the two scanners argue about in the next checkpoint.

    Gotchas
    • Counts are not comparable across formats. 15 / 16 / 98 for one image, measured above. The difference is what counts as a component, not what is installed.

    I11.12

    Scanning, the arithmetic that changes behaviour, and two tools that disagree

    Why it matters

    A vulnerability scanner is the most-deployed and least-understood tool in this whole area. It is treated as a measurement — "the image has four criticals" — when it is really a join between an inventory you generated and a database somebody else curates, with severity opinions attached. This checkpoint runs two scanners over the same five images and shows both what the numbers are good for (choosing a base image; the effect is enormous) and what they are not (a gate on a count).

    The concept

    A scan is three steps. Build an SBOM. Match each purl against advisories. Report. Everything interesting happens in the second and third steps, because the databases and the severity opinions differ:

    • The advisory source. A CVE has an upstream NVD record with a CVSS score. Distributions also publish their own assessment — Debian's security tracker, Ubuntu's CVE database, Alpine's secdb — which may say "does not affect our build", "fixed in this version", or "minor issue, will not fix". A scanner that prefers the vendor's view and one that prefers NVD's will report the same package very differently.
    • Fixed versus unfixed. Many findings have no fix available. Counting them makes the number bigger and the action smaller.
    • Reachability. A package being installed is not the same as its vulnerable code being on any path your process executes. Scanners at this level do not know the difference, and the gap is where most of the noise lives.

    Which leaves one thing a scan measures reliably: how much software is in the image. That is a decision you control completely, and it is where the leverage is.

    Nothing standardises what a scanner must report, which is why two of them disagree below. The nearest authority is CVSS, and its own introduction is careful about what a score is for — the Base score describes the vulnerability, and everything about your exposure is explicitly out of scope.

    Consumers may use CVSS information as input to an organizational vulnerability management process that also considers factors that are not part of CVSS in order to rank the threats to their technology infrastructure and make informed remediation decisions. Such factors may include: number of customers on a product line, monetary losses due to a breach, life or property threatened, or public sentiment on highly publicized vulnerabilities. These are outside the scope of CVSS.
    FIRST, Common Vulnerability Scoring System v3.1: Specification Document, § 1 Introduction — first.org/cvss/v3.1

    So a policy of "fail the build on any CRITICAL" is a policy about a number computed by somebody who knew nothing about your deployment — and, as the lab shows, computed differently by different tools from the same input.

    I11.13

    A tag is a mutable pointer, and everything above assumed it was not

    Why it matters

    Everything in the last four checkpoints binds to a digest. The signature's payload names a digest. The attestation's subject is a digest. The SBOM and the scan describe the bytes behind a digest. Meanwhile every deployment you have ever written names a tag — and a tag is a name a registry lets anyone with push access repoint at any moment. This checkpoint closes that gap by moving one, and watching four things quietly stop being true.

    The concept

    I5.2 established the two ways to name a manifest in the distribution API: <name>:<tag> and <name>@<digest>. They are different in kind, not in style. The digest form is a content address: the registry computes the SHA-256 of the manifest bytes and compares, so the reference either resolves to exactly those bytes or fails. The tag form is a lookup in a mutable table.

    Nothing in the specification prevents re-pushing a tag; it is an ordinary PUT, and the registry answers 201 Created with a new Docker-Content-Digest. Some registries offer immutability as a policy feature, but it is a policy, not a property of the format, and it is off by default in the reference implementation.

    So a digest-pinned reference gives you three things a tag cannot: the bytes cannot change under you, a mirror or proxy cannot substitute different content, and any signature, attestation, SBOM or scan result about that digest stays about the thing you are running. That last one is the point — the supply-chain machinery is only load-bearing at the digest level, and a tag re-push silently unhooks all of it.

    The spec defines both reference forms in a single sentence. What is more interesting is what it does not say: there is no statement anywhere in the document about whether a tag may be repointed at different content.

    <reference> MUST be either (a) the digest of the manifest or (b) a tag.
    OCI Distribution Specification v1.1.1, Pulling manifests — spec.md

    Grep the whole specification for "immutable" or "overwrite" in connection with tags and you get nothing. Tag immutability is therefore not a property of the format and not a guarantee any conformant registry owes you — it is an optional feature some registries offer, and the reference implementation leaves it off. That silence is what makes the lab below possible.

    Gotchas
    • The failure message names the wrong problem. no signatures found sends people to check their key, their signing job and their registry credentials. The check that actually finds it is comparing the digest the tag resolves to now against the digest in the signature payload.
    • Digest pinning does not stop deletion. It guarantees "these bytes or an error", not "these bytes forever". A garbage collection that drops the old manifest turns the pinned reference into a pull failure — which is loud, and therefore fine.
    • A digest does not pin a multi-platform image to a platform. Pinning an index digest still selects by platform at pull time. I4.8 is where that distinction bit.
    • Registry immutability settings are per-registry and mostly off. registry:2 allows re-push by default, as measured. Turning immutability on where your registry supports it is a better control than any convention about not re-pushing.
    • Nothing stops :latest from moving twice during one rollout. That is why a verifying admission webhook must rewrite the reference to the digest it verified, rather than admitting the tag and letting the kubelet resolve it again later.

    A pod's image: field accepts the digest form, and kubectl get pod -o jsonpath='{.status.containerStatuses[*].imageID}' shows the digest a running container was actually started from — which is how you check whether two pods of one Deployment are running the same bytes. This is also the mechanism behind W3.23's point that what is in the cluster is not always what you think you put there. The tag-versus-digest distinction is why every serious admission policy mutates the reference rather than merely approving it.

    Project & drill

    I11.14

    Mini project — run-verified.sh, and proving every control by breaking it

    Why it matters

    Thirteen checkpoints, thirteen controls, each demonstrated on its own. This one puts them in a single script that refuses to run an image whose signature does not verify and otherwise runs it locked down — and then, critically, attempts exactly the thing each control forbids and records the error. Those five error strings are the deliverable. They are what you will recognise in a bug report six months from now, when somebody says "the container just says permission denied".

    The concept

    Three design decisions in the script are worth stating before the code, because each is a place where a naive version is wrong:

    • Verify before unpacking. An unverified image is untrusted data. Unpacking it — even into a scratch directory — runs tar over attacker-controlled bytes before anything has vouched for them. Resolve, verify, then fetch layers.
    • Resolve the tag once, then never mention it again. Everything downstream uses the digest. This is I11.13 made into control flow: the thing verified and the thing run cannot be different if only one reference exists.
    • Make each control's failure distinguishable. If every blocked action returns EPERM, the proof proves nothing — you cannot tell which control fired. Setting the seccomp profile's defaultErrnoRet to ENOSYS gives seccomp its own errno, and leaving chown in the allow-list forces the capability check to be the thing that blocks it.

    You have a script that will not run an unverified image, and a five-row table mapping each control to the exact error it produces. Given any one of those five errors in isolation, you can name the control that produced it.

    Gotchas
    • Verify before you unpack, not after. The order in the script is the security property. A version that fetches layers first has already processed untrusted input.
    • Distinguishable errnos are a design choice, not a default. Left at the default EPERM, seccomp and capability failures are indistinguishable in a log. defaultErrnoRet costs one field.
    • Extract with sudo, delete with sudo. A rootfs unpacked by sudo tar cannot be removed by the next run without it — this failed the first time and produced sixty lines of rm: Permission denied before anything security-related happened.
    • Signing a repository, not an image. i11/unsigned holds byte-identical content at the identical digest and still fails verification, because the signature artifact lives in the repository beside the image. Copying an image between registries does not bring its signature — use cosign copy.
    • A hardened container needs its /tmp. Every one of the five proofs depends on the tmpfs being there; without it the probe cannot even create the file it then fails to chown, and you get one confusing failure instead of four clear ones.

    The pod spec that corresponds to this script is short, and worth writing out beside it: securityContext with runAsNonRoot: true, runAsUser: 1000, allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities.drop: ["ALL"] and seccompProfile.type: RuntimeDefault, plus an emptyDir mounted at /tmp and an image reference pinned by digest. The signature gate is the one part Kubernetes cannot express — it is an admission webhook. That list is also, exactly, the Pod Security Standards Restricted profile, which the advanced track has no lesson on; the nearest live material is W1.2, where you look at what the control-plane pods on a node actually run as, and can now read their securityContext with some idea of which fields matter.

    Docs: the Kubernetes Pod Security Standards page for the Restricted profile's field list; cosign copy --help for moving signatures with images; and the four checkpoints this script assembles — I11.1, I11.2, I11.3 and I11.5.

    I11.15

    Debugging drill — the container that dies before it starts, and the signature about other bytes

    Why it matters

    Both faults below are ones you will meet the week after somebody turns on hardening, and both produce an error message that names the wrong thing. The first fails inside the runtime, before your program's first instruction, with a message about file descriptors. The second fails a signature check on an image that is signed, with a key that is right. Neither is guessable; both are readable, from evidence this module has already taught you to collect.

    Fault 1 — the container dies before its first instruction
    1. The setup: a workload has been given a seccomp allow-list, hand-written from the syscalls the application was observed to make. It ran fine under strace during development. 
      runsec F allow-29.json '["/bin/sh","-c","echo hello from inside"]'
      reopen exec fifo: duplicate handle fd: fcntl(F_DUPFD_CLOEXEC): operation not permitted
level=error msg="runc run failed: container process is already dead"

      Nothing here says "seccomp". "Operation not permitted" is the errno a capability check produces, so the first instinct is to go and look at the capability set — which is fine, and wrong.

    2. Rule that out, because it is cheap. The capabilities are whatever they were, and the container ran before the profile was attached. 
      jq -c '.process.capabilities.bounding' config.json
jq 'del(.linux.seccomp)' config.json > c.tmp && mv c.tmp config.json
sudo runc --root /run/runc-i11 run i11probe
      ["CAP_AUDIT_WRITE","CAP_KILL","CAP_NET_BIND_SERVICE"]
hello from inside

      So it is the profile. That still leaves "which syscall", and an allow-list has no list of what it denied.

    3. Collect the evidence. The technique is to change the profile's action, not its contents: an SCMP_ACT_ERRNO default makes the kernel lie quietly to whoever asked, while a killing default makes it write an audit record naming the process and the syscall number. 
      sudo dmesg -C
jq '.defaultAction = "SCMP_ACT_KILL_PROCESS"' allow-29.json > allow-29-kill.json
runsec G allow-29-kill.json '["/bin/sh","-c","echo hello from inside"]'
sudo dmesg | tail -1
      level=error msg="runc run failed: container process is already dead"

  comm="runc:[2:INIT]" exe="/runc" sig=31 arch=c000003e syscall=72 compat=0
  ip=0x7a18954fabee code=0x80000000
      Diagnosis

      Two facts in that one line settle it. comm="runc:[2:INIT]" says the process that was killed is the runtime's own init process, not the workload — so the profile is being applied before the workload exists, and the syscalls that matter are the ones runc makes while finishing the container setup, not the ones the application makes. syscall=72 on x86-64 is fcntl, which matches the original error text exactly once you know where to look.

      The general shape: a seccomp allow-list must cover the runtime's setup, not just your program. Observing an application under strace and allow-listing what you see produces a profile that cannot start a container, and the failure is attributed to the profile only if you already know that the filter is installed by runc init before execve.

    4. Confirm the diagnosis by fixing exactly the named syscall — and watch it fail again, one syscall further along. 
      jq '.syscalls[0].names += ["fcntl"]' allow-29.json > allow-30.json

      A Rust panic from libpathrs, the library runc uses for safe path resolution — it is missing openat2 and statfs. This is the second half of the lesson: fixing the named syscall is not the fix, it is one step of a walk. Repeat the KILL_PROCESS technique after each round.

      Four rounds to run echo. The durable repair is not a longer hand-written list — it is to start from the runtime's default profile and subtract, which is why every shipped profile is that shape.

    Fault 2 — the image is fine, the signature is fine, and verification fails
    1. The setup: a release was signed at build time, carefully, by digest. A deployment now refuses to start it. 
      cosign verify --key cosign.pub --allow-http-registry --insecure-ignore-tlog=true $R/i11/mutable:v1

      Read what that sentence suggests: signing never ran, or ran against a different repository, or the signature was garbage-collected. All three are worth ten minutes each, and all three are wrong.

      Two tools now agree there is nothing here, and both are resolving the same tag before they look. This is the moment the investigation goes wrong if you stop.

      curl -s http://$R/v2/i11/mutable/tags/list | jq -c .tags
      ["sha256-f27cad9117495d32d067133afff942cb2dc745dfe9163e949f6bfe8a6a245339","v1"]

      There is a signature artifact, sitting under the referrers fallback tag from I11.9 — and that tag name is a digest. Compare it with the digest :v1 resolves to now.

    4. The one command that names the fault. 
      skopeo inspect --tls-verify=false docker://$R/i11/mutable:v1 | jq -r .Digest
      sha256:67cba4faf3b5730d90988d09ec638c7c36defd859dec41960790927a13317575

      Diagnosis

      The tag was re-pushed. Signature verification by tag resolves the tag first and then looks for a signature attached to that digest, finds none, and reports the literal truth: no signatures found for what you asked about. Nothing is broken — the signing worked, the key is right, and the signature is still in the registry attached to the digest it was always about. It is the tag that stopped pointing at the signed bytes.

      Verify by digest and it passes:

      cosign verify … i11/mutable@sha256:f27cad91…
  Verification for 127.0.0.1:5000/i11/mutable@sha256:f27cad91… --
    - The signatures were verified against the specified public key

      Which also tells you what else is now wrong, without further investigation: the attestation, the SBOM and the last clean scan are all attached to f27cad91… too, and every node that has not re-pulled is still running it.

    5. The repair is not "re-sign the new digest". Decide first which bytes were supposed to be there.
      If the re-push was…then…
      intentional (a rebuild published to the same tag)sign the new digest, regenerate the SBOM and scan, and fix the process — a tag that moves is a release you cannot audit
      unintentional (a pipeline pushed a stale build, a mirror sync)re-push the correct manifest, and confirm the digest matches the signature again

      And the durable repair, in all three rows: deploy by digest, and have the verifying admission webhook rewrite the reference to the digest it verified, so that the thing that was checked and the thing that runs cannot diverge.

    Verify

    Given a container that dies with an error about file descriptors, your first move is to swap the seccomp defaultAction for a killing one and read dmesg. Given no signatures found, your first move is to compare the digest the tag resolves to against the digest the signature is attached to.

    Gotchas
    • An SCMP_ACT_ERRNO default hides the evidence. It is the safer production choice and the worse debugging one. Reproducing with SCMP_ACT_KILL_PROCESS is the diagnostic technique; do not ship it.
    • dmesg -C before, not after. A busy node's ring buffer will have rotated the record away by the time you look, and type=1326 records are easy to miss among everything else. Clear, reproduce, read.
    • The seccomp fault moves. Each fix reveals the next missing syscall. Budget for several rounds, and note that the second one presented as a Rust panic rather than an errno.
    • "No signatures found" is not "not signed". Measured above on an image with a valid signature sitting in the same repository.
    • A moved tag breaks four things and reports one. Signature, attestation, SBOM and scan are all digest-bound; only the signature check is loud about it.

    Both faults have direct Kubernetes shapes. The first is a pod stuck in CreateContainerError after somebody set seccompProfile.type: Localhost, where kubectl describe shows the runtime's message and the syscall is only in the node's dmesg — W6.2 is the general ladder down to the node for when kubectl stops explaining things. The second is an admission webhook rejecting a Deployment whose image tag was rebuilt, and it is the reason those webhooks mutate the reference to a digest.

    Quiz

    1. A config.json lists CAP_CHOWN in bounding, permitted and effective, and sets process.user.uid to 1000. Does the container get CAP_CHOWN?
      Answer

      No. Measured: CapPrm and CapEff both came out zero. On execve as a non-root uid the kernel recomputes permitted from the file's capabilities and the ambient set, and container images have neither — so the arrays are discarded. Only bounding survives, as a ceiling. Granting it needs ambient, which in turn requires the capability to be in inheritable and permitted too; ambient alone makes runc warn "can't raise ambient capability". This is exactly a pod with runAsNonRoot: true and capabilities.add.

    2. The same capability is listed in bounding and permitted but deliberately left out of effective, and the container runs as root. Is it effective?
      Answer

      Yes — CapEff came back 0x…421 and the chown succeeded. For a uid-0 execve the kernel sets effective′ = permitted′, so the effective array is overwritten before the first instruction. For a root container it is documentation, not configuration.

    3. A seccomp profile blocks chmod, fchmodat and fchmodat2 in one syscalls[] entry with args: [{index: 2, …}]. What is wrong with it?
      Answer

      The argument positions differ. chmod(path, mode) has the mode at index 1; fchmodat(dirfd, path, mode, flags) has it at index 2. One args block applies to every name in its entry, so the rule silently never fires for chmod — which is what musl calls. Group syscalls by argument layout, not by what they are named.

    4. A container dies with fcntl(F_DUPFD_CLOEXEC): operation not permitted and container process is already dead, before running anything. What is the fastest way to find out which syscall a seccomp allow-list is missing?
      Answer

      Change defaultAction from SCMP_ACT_ERRNO to SCMP_ACT_KILL_PROCESS, clear dmesg, reproduce, and read the type=1326 audit record. It names the process (comm="runc:[2:INIT]" — the runtime's own init, not your workload) and the syscall number (syscall=72, fcntl). Expect several rounds: 29 → 30 → 71 → 74 names before echo ran.

    5. An AppArmor profile denies writes to a path. The write is blocked and the audit log is empty. Is the profile working?
      Answer

      Yes. A bare deny rule suppresses the audit message as well as the access. Write it as audit deny and the apparmor="DENIED" record appears. Measured with two otherwise identical profiles — so "check the audit log to confirm" is only advice for the second form.

    6. A pod sets readOnlyRootFilesystem: true and mounts a writable hostPath. What can a compromised process still write?
      Answer

      Everything under the hostPath, straight through to the host filesystem — measured. root.readonly covers the rootfs only; every entry in mounts keeps the options it was given. Also still writable: /dev and /dev/shm, which the runtime creates as separate tmpfs mounts.

    7. Why does runc spec --rootless map exactly one id rather than your whole /etc/subuid range?
      Answer

      Because installing a wider mapping means chowning into the subuid range, and an unprivileged user cannot do that — chown 100000:100000 is EPERM, and runc fails with fchown fd 7: operation not permitted. A subuid-backed container needs a helper that creates the user namespace with the setuid newuidmap first, then runs runc inside it. That is rootlesskit's entire job, and it is why the rootless containerd stack's uid_map has two lines.

    8. A rootless container and a root container both bind-mount / and read /etc/shadow. What happens?
      Answer

      The root one prints root:*:20639:0:99999:7:::. The rootless one gets Permission denied, because its uid 0 is host uid 1000. That single pair is the argument for the user namespace, and it is why mounting the container socket into a pod is equivalent to granting node root.

    9. You sign an image by digest, carefully. A deployment that references it by tag now reports no signatures found. What happened, and what else broke?
      Answer

      The tag was re-pushed and now resolves to a different digest. Verification by tag resolves first, then looks for a signature attached to that digest — and reports the literal truth. The attestation, the SBOM and the last clean scan are all bound to the old digest too, and nodes that have not re-pulled are still running it. cosign tree does not help: it resolves the tag as well and reports "No Supply Chain Security Related Artifacts found". The tag list does — the referrers fallback tag is the old digest.

    10. One image, scanned by two tools, gives the same total of 13 findings. Why might one fail a "no criticals" gate and the other pass it?
      Answer

      Because they source severity differently. The same three CVEs in the same libc6@2.36-9+deb12u14 were Critical/High/High under grype (NVD's CVSS) and MEDIUM/MEDIUM/MEDIUM under trivy (Debian's own assessment of those bugs in Debian's build). Neither is wrong. A threshold policy inherits whichever opinion the tool bought.

    11. A scanner reports a CRITICAL in your image. How do you decide whether the vulnerable code is reachable?
      Answer

      Read the SBOM's locations for that package and see what they point at. For python:3.13's first critical the four locations were all dpkg bookkeeping — the status file, a copyright file, .md5sums, .list — and the package name ended in -dev. ldd on the interpreter linked four libraries, none of them the vulnerable one. The finding is true and the code is on no executed path; the fix is deleting the package, which is the same conclusion the package-count arithmetic already gave.

    12. Five controls, five outcomes. Match each to what produced it: errno=30, errno=1, errno=38, an unchanged euid, and a write that succeeded.
      Answer

      errno=30 (EROFS) writing to / — root.readonly. errno=1 (EPERM) on chown — the empty capability bounding set. errno=38 (ENOSYS) on mkdir — the seccomp allow-list, given its own errno by defaultErrnoRet. Unchanged euid after exec'ing a setuid-root binary — noNewPrivileges. The write that succeeded is /tmp, the tmpfs that makes a read-only rootfs survivable. With the controls off, the same write to / failed with errno=13 instead — a different mechanism entirely (no CAP_DAC_OVERRIDE on a uid-1000 directory), which is why the project records errnos rather than prose.
