    I2 — What a container is, formally

    This is the hinge of the track. Up to now "a container" has been a thing you did: in B14 you unshared some namespaces, pivoted into a root filesystem, wrote three numbers into a cgroup, and hung a veth off a bridge — and whatever came out the other end, you called a container. That definition is a procedure. It lives in one shell script and it cannot be handed to anybody.

    The OCI runtime specification replaces the procedure with a document. It says: put a directory somewhere with two things in it — a JSON file called config.json and a root filesystem — and any compliant runtime on earth will produce the same container from it. That is the entire contract. No new kernel mechanism appears in this module; every namespace, cgroup and capability below is one you already drove by hand. What appears is agreement, and agreement is what let a scheduler written by one company drive a runtime written by another.

    So the work here is reading. You will generate the reference document with runc spec, take it apart field by field, change one field at a time and prove the change in /proc, walk a container through all four of its states by hand, and finish by writing a program that turns minibox.sh's environment variables into a config.json — and produces, from a different runtime, byte-identical observable output.

    Checkpoints16 Hours~6 PrerequisitesI0, I1, B6, B7, B14
    • State the two-file contract that defines a filesystem bundle, and build one from a distro tarball.
    • Read a whole config.json and say what each top-level key does — and which line of minibox.sh it replaces.
    • Explain where bundles come from in a real stack, and find a live one on your own machine.
    • Configure process — all five capability sets included — and verify every field in /proc/<pid>/status.
    • Run with a read-only root, find what breaks, and repair it with mounts rather than with privilege.
    • Share a namespace by path, which is the whole mechanism behind a Kubernetes pod.
    • Map linux.resources onto the cgroup v2 files you wrote by hand in B7, including the names that changed.
    • Recite the state machine, drive every transition, and say why create and start are two operations.
    • Place all five hooks and determine, from evidence, which side of the isolation boundary each ran on.
    • List what the runtime specification refuses to standardise, and name the module of this track that fills each gap.
    • Run one byte-identical bundle under two independent runtimes and account for every difference.

    B6 (namespaces, pivot_root), B7 (cgroups v2), B14 (minibox), and I0 + I1 from this track. None of it is re-taught. When a lesson opens with "you already built this", follow the link, skim, come back.

    Which machine. Any throwaway Ubuntu 24.04 VM with runc and containerd on it, which is what buildbox was for. The output on this page was captured on a 2-vCPU / 4 GB box with runc 1.5.1, crun 1.14.1 and containerd 2.3.3. One lesson pulls an image and one installs a package, so the machine needs internet. Everything runs as root.

    Set up a scratch directory first — every lesson below builds bundles in it, and the debugging drill deliberately breaks them.

    The bundle

    I2.1

    The whole contract in one sentence: a directory with two things in it

    Why it matters

    Before anything else, you need to know how little a runtime is actually given. Ask most engineers what Docker hands to runc and you will hear something about images, layers, registries, maybe a daemon socket. The truth is smaller and far more useful: a directory path. Inside that directory are exactly two things — a file called config.json and a root filesystem. That is everything. Once you have seen it, an enormous amount of container tooling stops being mysterious and starts being obviously replaceable.

    The concept

    The specification calls this directory a filesystem bundle. In the track's analogy, config.json is the written work order and the runtime is the contractor: the order says what to build, and any contractor who can read it produces the same building. Nothing in the order refers back to the company that wrote it.

    A bundle is self-contained by design. It does not reference an image, because the runtime specification has never heard of images. It does not reference a registry, a daemon, a network, or a name. Everything the runtime needs is either in that JSON file or in that directory tree.

    bundle/→config.json+rootfs/→runc→a container

    The root filesystem is an ordinary directory. There is nothing layered or magical about it at this level — an unpacked distro tarball is a perfectly legal one, which is exactly what you are about to prove. Layers, overlays and snapshots are how images get turned into one of these directories, and that is I4 and I7's business, not the runtime's.

    Lab
    1. Get a root filesystem that owes nothing to any container tooling. Alpine publishes theirs as a plain tarball; it is 3.6 MB and contains a complete userland. 
      cd ~/i2
curl -sSLO https://dl-cdn.alpinelinux.org/alpine/v3.22/releases/x86_64/alpine-minirootfs-3.22.5-x86_64.tar.gz
sha256sum alpine-minirootfs-3.22.5-x86_64.tar.gz
      4b4daa9fe2fc696c4919c4412a4c3d3e770d8fb70292a004a2c72f5096175282  alpine-minirootfs-3.22.5-x86_64.tar.gz

      Record that digest. Alpine moves patch releases, so a reader on a later day who gets a different number knows the tarball moved rather than that they typed something wrong.

    2. Make the bundle. Two commands, and one of them is mkdir. 
      mkdir -p hello/rootfs
sudo tar -C hello/rootfs -xzf alpine-minirootfs-3.22.5-x86_64.tar.gz
ls hello/rootfs
du -sh hello/rootfs
      bin  dev  etc  home  lib  media  mnt  opt  proc  root  run  sbin  srv  sys  tmp  usr  var
8.6M	hello/rootfs

      sudo because the tarball carries ownership and device nodes that only root can recreate. The directory it produces is a filesystem tree and nothing else — grep it, edit it, delete a file in it; there is no metadata anywhere else that will disagree with you.

    3. Add the other half. runc spec writes a default config.json into the current directory; I2.2 reads it properly, and for now you only need it to exist. 
      cd hello
sudo runc spec
ls -la
      -rw-r--r--  1 root   root   2500 Jul 27 15:54 config.json
drwxr-xr-x 19 root   root   4096 Jun 22 01:05 rootfs
    4. Run it. The default spec asks for a terminal, and you have not given it one, so the first attempt fails — usefully. 
      sudo runc run hello
      level=error msg="runc run failed: open /dev/tty: no such device or address"

      process.terminal: true means "allocate me a pseudo-terminal", which needs a controlling terminal to attach to. Turn it off and give the container something to say:

      sudo jq '.process.args = ["/bin/echo","a bundle is a directory"] | .process.terminal = false' \
  config.json > /tmp/c.json && sudo cp /tmp/c.json config.json
sudo runc run hello
      a bundle is a directory

      That jq … > /tmp/c.json && cp dance appears throughout this module. jq cannot edit in place, and writing straight back into config.json truncates it before jq reads it — which produces an empty file and a very confusing error.

    Verify

    find ~/i2/hello -maxdepth 1 lists exactly two entries besides the directory itself. Nothing outside ~/i2/hello was consulted: sudo runc run -b ~/i2/hello hello works from any working directory, and moving the whole directory to another path and running it there works too.

    Gotchas
    • The name is not negotiable. config.json, in the root of the bundle, exactly. runc reports JSON specification file config.json not found and readers routinely lose ten minutes to having run runc run from the parent directory rather than from inside the bundle. -b <dir> is the fix.
    • The bundle is not the container. The container is state that the runtime keeps elsewhere (I2.9). Two containers can be created from one bundle, and deleting the bundle out from under a running container does not stop it.
    • Untar as root or the tree is wrong. Unpacked as an ordinary user, every file is owned by you, the setuid bits are gone, and /dev has no device nodes. Things will half-work, which is worse than failing.

    The specification's own definition, which is shorter than most people expect:

    A set of files organized in a certain way, and containing all the necessary data and metadata for any compliant runtime to perform all standard operations against it.

    And on the two artefacts:

    This REQUIRED file MUST reside in the root of the bundle directory and MUST be named config.json. […] The directory referenced by root.path, if that property is set in config.json.
    OCI Runtime Specification v1.3.0 — bundle.md

    Note the second quote's hedge: the root filesystem is required only if root.path is set, because a VM-based runtime may not use a host directory at all. The two-file rule is the common case, not a universal law.

    When a pod starts, the kubelet never sees a bundle — it sends a CRI request and containerd assembles one. But the bundle is what actually exists on the node, and when you are staring at a container that will not start, it is the artefact worth reading. W1.20 walks the kubelet → CRI → containerd → runc path; everything on that path exists to produce the directory you just made by hand.

    Docs

    The whole of runtime-spec bundle.md is 14 lines long — read it now, in full, because you will never have a cheaper opportunity. Then man 8 runc-spec and man 8 runc-run.

    I2.2

    Read the generated default, top to bottom

    Why it matters

    There is a version of learning this material where you look up fields one at a time, forever, and never form a picture of the whole. Reading the default document once, end to end, costs twenty minutes and prevents that. It is also small — 2500 bytes — which is worth knowing, because the mental image most people carry of "container configuration" is much bigger than the thing itself.

    The concept

    runc spec emits a minimal-but-real configuration, and it is a genuinely good reference document: every field in it is a field runtimes actually honour, with defaults chosen to be safe. Six top-level keys appear:

    • ociVersion — which edition of the standard this file claims to conform to. Not the runtime's version. I0.5 laboured this point; it is about to matter again in I2.14.
    • process — what to run and who to run it as. Replaces minibox.sh's final exec capsh … --shell=/bin/sh line and its whole capability argument.
    • root — where the root filesystem is, and whether it is writable. Replaces pivot_root.
    • hostname — replaces hostname "$NAME".
    • mounts — replaces every mount -t proc proc /proc-style line.
    • linux — the platform-specific everything: namespaces, cgroup limits, seccomp, devices, masked paths. Replaces the unshare flags and the whole setup_cgroup function.

    Two more keys are legal and simply absent from the default: hooks (I2.12) and annotations (free-form key/value metadata that the runtime ignores and higher layers — containerd, the CRI, Kubernetes — use heavily). Their absence is itself informative: neither is needed to run a container.

    Lab
    1. List the top-level keys, so you know the shape before reading the contents. 
      cd ~/i2/hello
jq 'keys' config.json
      [
  "hostname",
  "linux",
  "mounts",
  "ociVersion",
  "process",
  "root"
]

      Six. Not hooks, not annotations — runc spec does not emit them because a container does not need them.

    2. Read the thing. Do not skim it; this is the exercise. 
      jq . config.json | less

      As you go, keep a single question in your head for every field: which line of minibox.sh does this replace? Say the answer out loud. The ones with no answer — maskedPaths, readonlyPaths, the devices deny-rule, noNewPrivileges — are the places where the standard is stricter than the thing you wrote, and each is a lesson later in this module.

    3. Get a shape summary you can hold in your head, rather than 130 lines of JSON. 
      jq '{ociVersion, args: .process.args, user: .process.user,
     caps: (.process.capabilities | to_entries | map("\(.key)=\(.value|length)")),
     root, hostname,
     mounts: [.mounts[].destination],
     ns: [.linux.namespaces[].type],
     masked: (.linux.maskedPaths|length), ro: (.linux.readonlyPaths|length)}' config.json
      {
  "ociVersion": "1.3.0",
  "args": [ "/bin/echo", "a bundle is a directory" ],
  "user": { "uid": 0, "gid": 0 },
  "caps": [ "bounding=3", "effective=3", "permitted=3" ],
  "root": { "path": "rootfs", "readonly": true },
  "hostname": "runc",
  "mounts": [ "/proc", "/dev", "/dev/pts", "/dev/shm", "/dev/mqueue", "/sys", "/sys/fs/cgroup" ],
  "ns": [ "pid", "network", "ipc", "uts", "mount", "cgroup" ],
  "masked": 10, "ro": 5
}

      Three notes worth pausing on. Only three capabilities by default, against the 37 minibox leaves in place. The root is read-only by default. And six namespaces are unshared — minibox unshares five, having no cgroup namespace.

    4. Confirm the version number means what I0.5 said it means. 
      jq -r .ociVersion config.json
runc --version | head -3
      1.3.0
runc version 1.5.1
commit: v1.5.1-0-g8f2685a47
spec: 1.3.0

      Two versions, both real: runc is at 1.5.1 and implements edition 1.3.0 of the specification. The spec: line is a runtime declaring its conformance, and I2.14 turns that declaration into a failure you can watch.

    Verify

    Without looking, name all six top-level keys and one field inside each. Then name the two legal keys the default omits. If you can do that, the rest of this module is annotation on a structure you already hold.

    Gotchas
    • The default is runc's opinion, not the specification's. Almost everything in it is OPTIONAL in the standard. Another runtime's spec subcommand may emit something different and both are conformant. Never argue from "but the default says".
    • Absent is not the same as empty. "seccomp" missing means "apply no filter"; "seccomp": {"defaultAction":"SCMP_ACT_ERRNO","syscalls":[]} means "block everything", which is a container that dies instantly. The distinction bites hardest with capabilities, where an absent set inherits and an empty set drops.
    • 2500 bytes is the floor, not the norm. A configuration generated for a Kubernetes pod runs to tens of kilobytes, most of it a seccomp profile. Do not be surprised by the size; be surprised if the structure differs, because it will not.

    On what is actually mandatory:

    ociVersion (string, REQUIRED) MUST be in SemVer v2.0.0 format and specifies the version of the Open Container Initiative Runtime Specification with which the bundle complies.

    Every other top-level key is OPTIONAL, with one conditional:

    process (object, OPTIONAL) specifies the container process. This property is REQUIRED when start is called.
    OCI Runtime Specification v1.3.0 — config.md

    That conditional is the specification quietly telling you that create and start are separate operations with separate requirements — a fact I2.11 spends a whole lesson on.

    Everything you just read is what a PodSpec is eventually compiled into. command/args become process.args; env becomes process.env; resources.limits become linux.resources; volumeMounts become entries in mounts. The pod API is a much larger document because it also describes scheduling, identity and lifecycle policy — none of which the runtime has any opinion about. W3.1 is the same document from the other end.

    Docs

    runtime-spec config.md for the platform-neutral fields and config-linux.md for everything under linux. Together they are about 2000 lines and are the reference for the rest of this module. man 1 jq for the query syntax used above.

    I2.3

    Where bundles come from, since nobody ships one

    Why it matters

    You have now made a bundle by hand, and you will never do that again outside this module. Nobody publishes bundles; there is no registry of them, no docker pull that produces one. So the obvious question — if the runtime only accepts bundles and nobody distributes bundles, who makes them? — has an answer worth knowing precisely, because the answer is the architecture of the rest of the container stack.

    The concept

    A bundle is assembled on the node, moments before use, and destroyed after. Two different components each produce half of it:

    • The snapshotter produces rootfs/. It takes the image's layers — which it already has on disk, unpacked — and mounts them as one directory using overlayfs, exactly the stack of transparent sheets from B5.14. Nothing is copied. The mount is created for this container and torn down when it dies.
    • The runtime layer (containerd, via its CRI plugin) produces config.json. It merges two sources: the image config — the entrypoint, environment and working directory baked in when the image was built — and the caller's request, which for Kubernetes is the pod spec. I4 covers the first, I8 covers the second.
    image layers→snapshotter→rootfs/+image config & pod spec→containerd→config.json

    In the analogy: the room-prep crew (snapshotter) stacks the sheets to make the room, and the building-services company (containerd) writes the work order. The contractor (runc) arrives, reads the order, and leaves.

    The consequence to hold on to: the bundle is ephemeral, but it is on disk while the container runs, and you can read it. That makes it one of the best debugging artefacts on a node — it is the exact, final, fully-merged answer to "what did we actually ask for", after every default, every admission controller and every runtime option has had its say.

    Lab
    1. Start a container with containerd's own client, so nothing here depends on Kubernetes. 
      sudo ctr images pull docker.io/library/alpine:3.22
sudo ctr run -d docker.io/library/alpine:3.22 demo sleep 300

      Record the digest the tag resolved to, so a later run can tell a moved tag from a broken command:

      application/vnd.oci.image.index.v1+json sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce
Completed pull from OCI Registry (docker.io/library/alpine:3.22)	elapsed: 9.5 s	total: 3.6 Mi
    2. Find the bundle. It is under /run, which is a tmpfs — more evidence that it is scaffolding rather than storage. 
      sudo ls /run/containerd/io.containerd.runtime.v2.task/default/demo/
      bootstrap.json  config.json  init.pid  log  log.json  options.json  rootfs  runtime  s  shim-binary-path  work

      There are your two required entries, plus a handful of files that belong to the shim rather than to the runtime — the foreman's paperwork, which I7 reads properly.

    3. Confirm that rootfs is a mount and not a copy. 
      mount | grep demo
      overlay on /run/containerd/io.containerd.runtime.v2.task/default/demo/rootfs type overlay
  (rw,relatime,lowerdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/1/fs,
   upperdir=…/snapshots/2/fs,workdir=…/snapshots/2/work,uuid=on,nouserxattr)

      One lowerdir because Alpine is a single-layer image; a multi-layer image produces a colon-separated list. The upperdir is this container's writable layer, and it is what disappears when the container is removed.

    4. Read the generated config.json and compare it with your hand-written one. 
      B=/run/containerd/io.containerd.runtime.v2.task/default/demo/config.json
sudo jq '{ociVersion, root, hostname, mounts: (.mounts|length),
          ns: [.linux.namespaces[].type], cgroupsPath: .linux.cgroupsPath,
          seccomp: (.linux.seccomp.syscalls|length), args: .process.args,
          caps: (.process.capabilities.bounding|length)}' $B
      {
  "ociVersion": "1.3.0",
  "root": { "path": "rootfs" },
  "hostname": null,
  "mounts": 7,
  "ns": [ "pid", "ipc", "uts", "mount", "network" ],
  "cgroupsPath": "/default/demo",
  "seccomp": null,
  "args": [ "sleep", "300" ],
  "caps": 14
}

      Four things to notice. cgroupsPath is derived from the namespace and container name — that is where containerd's naming ends up, since the runtime spec has no name field. There is no cgroup namespace and no seccomp profile: ctr is a debugging client and applies neither. hostname is unset. And the capability set is 14, which is Docker's historic default list, inherited by containerd. Under the CRI (I8) every one of these answers changes.

    5. Prove that containerd's containers are just runc containers, by asking runc directly. The trick is that containerd keeps runc's state under its own root directory. 
      sudo runc --root /run/containerd/runc/default list
sudo runc --root /run/containerd/runc/default state demo | jq '{id,pid,status,bundle}'
      ID     PID     STATUS    BUNDLE                                                       OWNER
demo   26604   running   /run/containerd/io.containerd.runtime.v2.task/default/demo   root

{
  "id": "demo",
  "pid": 26604,
  "status": "running",
  "bundle": "/run/containerd/io.containerd.runtime.v2.task/default/demo"
}

      That is the whole point of the module in one command. There is no separate "containerd container" concept; there is a bundle, and there is runc, and you can drive it with the same binary and the same subcommands you used on hello.

    6. Clean up. 
      sudo ctr task kill -s KILL demo; sudo ctr c rm demo
    Verify

    After ctr c rm demo, the directory under /run/containerd/io.containerd.runtime.v2.task/default/ is gone and mount | grep demo is silent — the bundle really was scaffolding. The snapshot under /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/ is not gone, because that belongs to the image, not to the container.

    Gotchas
    • Do not edit a live bundle expecting anything to happen. config.json is read once, at create. Editing it afterwards changes nothing about the running container and will confuse whoever reads it next. It is a record, not a control surface.
    • runc list with the wrong --root lies by omission. Plain runc list uses /run/runc and will cheerfully report an empty list on a node running fifty containers. Every runc command containerd's containers respond to needs --root /run/containerd/runc/<namespace>.
    • The path encodes the containerd namespace, not the Kubernetes namespace. default above is containerd's own tenancy concept; Kubernetes uses the containerd namespace k8s.io for everything, regardless of which Kubernetes namespace the pod is in.

    The specification never says where bundles come from, and that silence is deliberate:

    The Open Container Initiative Runtime Specification aims to specify the configuration, execution environment, and lifecycle of a container.
    OCI Runtime Specification v1.3.0 — spec.md § Abstract

    Configuration, execution, lifecycle. Not acquisition, not distribution, not assembly. Everything you watched containerd do above lives in the gap that sentence leaves open — which is why it took three more specifications and this whole track to fill it.

    On a Kubernetes node this directory is the fastest way to answer "what did the kubelet actually ask for", when the pod spec and the observed behaviour disagree. The path is the same with k8s.io in place of default, and the container id is the long hash from crictl ps. W6.6 triages a container that will not start; reading its generated config.json belongs in that toolkit, and by I8 you will be able to explain every field in it.

    Docs

    containerd docs/PLUGINS.md for what a snapshotter is and which one is in use; ctr --help and ctr snapshots --help. The runtime specification is silent here by design, which is itself the thing to remember.

    config.json, field by field

    I2.4

    process — and the five capability sets

    Why it matters

    process is the part of the document that decides what the container can do, and it is where the majority of real-world container security failures are configured. It also contains the single most misunderstood structure in the whole specification — the five capability sets — which people routinely copy from a blog post without knowing that setting one of them silently overrides another. This lesson changes one field at a time and checks each one in /proc, because that is the only way the relationships become visible.

    The concept

    The straightforward fields first. args is the argv the runtime will exec — element zero is the program, and it is resolved inside the container's root filesystem using the container's PATH. env is the complete environment; nothing from your shell leaks in. cwd must exist inside the rootfs or creation fails. terminal asks the runtime for a pseudo-terminal. rlimits are the same per-process limits ulimit sets. oomScoreAdj tunes which process the kernel kills first when the machine runs out of memory.

    user carries uid, gid and additionalGids, all numeric. There is no username field anywhere in the specification — resolving appuser to a number by reading /etc/passwd inside the rootfs is a job for the layer above, and I2.16 shows you exactly the error it produces when it fails.

    noNewPrivileges sets the no_new_privs bit from I1.10: a one-way promise that no exec from here can ever gain privilege, which is what makes setuid binaries inside the container inert.

    Then capabilities, with all five sets from B4.12, each an explicit list of CAP_ names:

    • bounding — the ceiling. Nothing in this process or any of its descendants can ever hold a capability outside this set. This is the one that matters.
    • permitted — what this process may raise into effective.
    • effective — what is being checked right now, for this process.
    • inheritable — what survives exec into a file that has the matching inheritable bits. Nearly always useless and nearly always wrong to set.
    • ambient — what survives exec into an ordinary unprivileged binary. This is the one that makes non-root containers able to bind port 80.

    They are not five independent lists. The kernel enforces relationships between them at exec, and the important one is: a capability in ambient is forced into permitted and effective. So a configuration that lists a capability as ambient but omits it from effective does not get what it asked for — it gets the capability anyway. You are about to watch that happen.

    Lab
    1. Build a fresh bundle whose workload sticks around long enough to inspect. 
      cd ~/i2
sudo rm -rf caps && sudo mkdir -p caps/rootfs
sudo tar -C caps/rootfs -xzf alpine-minirootfs-3.22.5-x86_64.tar.gz
cd caps && sudo runc spec
    2. Set every field in one edit, so each can be checked independently afterwards. Note the deliberately inconsistent capability sets — CAP_CHOWN is ambient and inheritable but not effective. 
      sudo jq '
   .process.terminal = false
 | .process.args = ["/bin/sleep","600"]
 | .process.cwd = "/tmp"
 | .process.env += ["GREETING=from the spec"]
 | .process.user = {uid:0, gid:0, additionalGids:[10,20]}
 | .process.oomScoreAdj = -500
 | .process.rlimits = [{type:"RLIMIT_NOFILE", hard:4096, soft:2048}]

     bounding:    ["CAP_NET_RAW","CAP_CHOWN"],
     permitted:   ["CAP_NET_RAW","CAP_CHOWN"],
     effective:   ["CAP_NET_RAW"],

      --pid-file writes the host-side PID of the container's first process, which is how you inspect a container from outside without guessing.

Max open files            2048                 4096                 files
-500

      Two things the specification did not say. HOME appeared from nowhere — runc synthesises it from process.user.uid when the environment does not set it. And soft and hard map onto the two columns in exactly the order you would hope.

    5. Clean up. 
      sudo runc delete -f caps
    Verify

    Re-run with ambient removed and nothing else changed. CapEff becomes 0000000000002000 — cap_net_raw alone, exactly as configured. That single difference is the proof that ambient was the cause and not a runc quirk.

    Gotchas
    • An absent capabilities object is not an empty one. Omit process.capabilities entirely and runc gives the container the caps it inherited, which as root is everything. Write {} and the container gets none. This is the difference between a container that is fine and a container that owns the node, expressed as two characters.
    • bounding is the only set with teeth. Trimming effective while leaving bounding wide open buys nothing: the process can raise anything permitted at any time, and permitted is capped by bounding. If you are auditing a configuration, read bounding first and treat the rest as commentary.
    • Misspelled capability names are a warning, not an error. runc prints ignoring unknown or unavailable capabilities: [...] and carries on. Get every name wrong and you get an empty set and a container that fails in some unrelated-looking way ten minutes later. I2.15 has this bug on purpose so you meet it once, deliberately.
    • cwd must exist. There is no "create it if missing" — a non-existent cwd fails at create with a message about chdir, which is easy to misread as a permissions problem.

    On the five sets, and on the fact that they are lists of names rather than a bitmask:

    capabilities (object, OPTIONAL) is an object containing arrays that specifies the sets of capabilities for the process. Valid values are defined in the man page. […] Any value which cannot be mapped to a relevant kernel interface MUST cause an error.
    OCI Runtime Specification v1.3.0 — config.md § Linux Process

    Worth reading twice: the specification says an unmappable value MUST cause an error, and runc 1.5.1 emits a warning and continues. That is a real conformance gap, and it is the mechanism behind the gotcha above. Where a spec and an implementation disagree, the implementation is what runs your production workload.

    A pod's securityContext.capabilities.add/drop compiles down to exactly these arrays; runAsUser/runAsGroup/fsGroup become process.user; allowPrivilegeEscalation: false becomes noNewPrivileges: true. The advanced track has no dedicated securityContext lesson, so the nearest anchor is W3.16 on the pod spec fields that reach the runtime — and this lesson is the honest description of what happens after they get there.

    Docs

    man 7 capabilities — specifically the "Transformation of capabilities during execve()" section, which is the rulebook the kernel applied above. man 1 capsh for --decode. config.md § POSIX Process for rlimits.

    I2.5

    root — path, and the read-only container

    Why it matters

    root is two fields and both of them cause outages. path is resolved relative to the bundle directory, which is not where anybody expects, and gets a whole third of the debugging drill to itself. readonly is the single highest-value security setting in the document — and turning it on breaks almost every real image in a way that people then "fix" by turning it off again. This lesson breaks it and repairs it properly.

    The concept

    root.path names the directory that becomes /. A relative path is relative to the bundle directory — not the current directory, not the runtime's directory. An absolute path is also legal and works, and is what a snapshotter-driven stack does not use, because it wants the bundle to be relocatable.

    root.readonly: true makes the root mount read-only. This is not the same as making the container's whole filesystem read-only: any mounts entry can still be writable, and that is the intended design. The container's image is immutable; the container's working data lives on mounts you chose deliberately. A container that cannot write to its own image cannot be persistently backdoored by anything that gets in, and it cannot slowly fill the node's disk with logs nobody reads.

    The two things that break, in every image, are always the same: somewhere to write temporary files, and a package manager's lock file. The wrong fix is readonly: false. The right fix is a writable tmpfs mounted where writes belong, which is one line and which also puts a size limit on them.

    Lab
    1. Start from the read-only default and try three ordinary things. 
      cd ~/i2/hello
sudo jq '.root.readonly = true | .process.terminal = false
 | .process.args = ["/bin/sh","-c","echo hi > /tmp/x || true; touch /etc/probe || true"]' \
  config.json > /tmp/c && sudo cp /tmp/c config.json
sudo runc run ro
      /bin/sh: can't create /tmp/x: Read-only file system
touch: /etc/probe: Read-only file system
    2. Now try what a real program does, which is where the failure stops being obvious. 
      sudo jq '.process.args = ["/sbin/apk","add","--no-cache","curl"]' config.json > /tmp/c && sudo cp /tmp/c config.json
sudo runc run ro
      ERROR: Unable to lock database: Read-only file system
ERROR: Failed to open apk database: Read-only file system

      Note what this looks like in a log aggregator with no context: a database error. Reported by a user, it becomes "the container can't reach the database", and half an hour disappears. The signature to memorise is the phrase Read-only file system appearing anywhere in an error whose subject is something else entirely.

    3. Fix it the right way — add a writable mount, keep the root read-only. 
      sudo jq '.process.args = ["/bin/sh","-c","echo hi > /tmp/x && cat /tmp/x && mount | grep \" /tmp \""]
 | .mounts += [{destination:"/tmp", type:"tmpfs", source:"tmpfs",
                options:["nosuid","nodev","mode=1777","size=16m"]}]' \
  config.json > /tmp/c && sudo cp /tmp/c config.json
sudo runc run ro
      hi
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,relatime,size=16384k,inode64)

      The root is still read-only. /tmp is writable, capped at 16 MB, and vanishes with the container. That combination is strictly better than a writable root: the blast radius is bounded in both space and time.

    4. Now the path. An absolute root.path works: 
      sudo jq '.root.path = "/home/ubuntu/i2/hello/rootfs"' config.json > /tmp/c && sudo cp /tmp/c config.json
sudo runc run ro
      hi
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,relatime,size=16384k,inode64)

      And a relative one is resolved against the bundle, which the error message tells you exactly if you read it:

      sudo jq '.root.path = "nope"' config.json > /tmp/c && sudo cp /tmp/c config.json
sudo runc run ro
      level=error msg="runc run failed: invalid rootfs: stat /home/ubuntu/i2/hello/nope: no such file or directory"

      The path in the message is bundle + root.path. Whenever this error appears, read the path it prints rather than the path you wrote — the difference between them is the bug.

    5. Put it back before moving on. 
      sudo jq '.root.path = "rootfs"' config.json > /tmp/c && sudo cp /tmp/c config.json
    Verify

    With the tmpfs mount in place and readonly: true, mount inside the container shows / as ro and /tmp as rw simultaneously. Writing 20 MB into /tmp fails with No space left on device rather than filling the host — that is the size limit doing its job.

    Gotchas
    • A read-only root does not mean an immutable container. Every writable mount you add is writable, and a hostPath mount is writable on the node. Read-only root removes one attack surface; it is not a containment boundary on its own.
    • The rootfs must be a directory on the same machine. A symlink for root.path is resolved, an NFS mount works but will hang the container if the server goes away, and a path that crosses a mount point behaves differently under different rootfsPropagation settings (I2.8).
    • Images that log to their own directory fail late. Everything starts, traffic is served, and forty minutes later the first log rotation fails. Test with the root read-only from the start rather than switching it on before a release.
    path (string, REQUIRED) Specifies the path to the root filesystem for the container. […] The value SHOULD be the conventional rootfs. A directory MUST exist at the path declared by the field.
    readonly (bool, OPTIONAL) If true then the root filesystem MUST be read-only inside the container, defaults to false.
    OCI Runtime Specification v1.3.0 — config.md § Root

    SHOULD be rootfs: a convention with the force of a strong recommendation, which is why every bundle you will ever meet uses that exact name, and why a bundle that does not is worth a second look.

    securityContext.readOnlyRootFilesystem: true is this field, and the standard companion pattern — an emptyDir volume mounted at /tmp — is the writable-mount fix you just performed by hand. W5.2 covers emptyDir; it is a tmpfs or a node directory depending on its medium, and either way it becomes an entry in the mounts array.

    Docs

    config.md § Root, and man 8 mount for the tmpfs options used above (mode=1777 is the sticky world-writable mode /tmp must have).
