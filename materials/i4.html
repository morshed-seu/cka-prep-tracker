    I4 — Images

    An image is not a file and not a filesystem — it is a content-addressed graph of JSON documents and tar archives, held together by SHA-256. Walk one by hand from index.json down to a layer tar, then assemble a runnable rootfs out of it with no container tooling at all.

    The thesis of this track is that the container ecosystem added contracts rather than mechanism, and images are the cleanest case of it. There is no new kernel feature here and nothing to install — an image is JSON documents pointing at tarballs, held together by SHA-256. By the end you will have taken one apart with jq, recomputed every hash in it, rebuilt its filesystem yourself, and handed the result to the runc bundle you built in I2.

    Checkpoints16 Hours~6 PrerequisitesI2 · B5 · B12
    • The model — content addressing, the descriptor as the format's only pointer, the index → manifest → config + layers graph, and why a tag is the one mutable thing in it.
    • Walking a real image — get one onto disk in the spec's own layout with no daemon, follow it hop by hop with jq, tell OCI and Docker media types apart, and do multi-platform selection by hand.
    • Layers — a layer is a tar; digest versus diff_id and why both exist; whiteouts as tar entries rather than the device nodes B5 found on disk; and the chain ID a snapshotter actually caches on.
    • The config — the image config as the subset of a config.json an image may pre-declare, and the precedence rule that explains Kubernetes' command/args.
    • Project & drill — oci-inspect.py: verify every digest, apply whiteouts correctly, produce a rootfs runc will run. Then three faults that each look like something else.

    I2 (you need somewhere to put the rootfs you build) and B5 (overlayfs, copy-up, whiteouts on disk), plus B12.4 for hashing. Authored against OCI image-spec v1.1.1 (the current release; v1.1.0 was February 2025, v1.1.1 the March 2025 patch).

    Which machine. Everything here ran on the sandbox VM — Ubuntu 24.04, kernel 6.8.0 — with skopeo 1.13.3 (apt), containerd 2.3.3, runc 1.5.1, nerdctl, jq and stock python3. No image building and no local registry yet, so the larger buildbox is not needed until I6; internet access is, because we pull from Docker Hub. The image is alpine:3.21, which resolved to sha256:48b0309c…abc07d (Alpine 3.21.7, built 2026-04-16) on the day this was written — see I4.4 for why that sentence is phrased so carefully.

    The model

    I4.1

    Content addressing: a name you can check

    Why it matters

    Almost everything people find confusing about images — why two images can "share" a layer without anyone arranging it, why a mirror in another country is trustworthy, why :latest ruins afternoons — comes from a single design decision made before any of the rest of the format existed. Everything is named by the hash of its own bytes. Get that one idea properly settled and the remaining fifteen checkpoints are consequences.

    The concept

    You already know how to hash a file: you did it in B12.4, where hashing, encoding and encryption were separated once and for all. A digest is just that — SHA-256 run over some bytes, written as sha256: followed by 64 hex characters.

    Content addressing is the decision to use that digest as the thing's name. Not a name you assign, and not a name that says where the thing lives — a name computed from what the thing is. Two consequences follow, and the whole format is built on them.

    The first: identical content always has the identical name, everywhere, forever, with no coordination. Two teams who have never spoken, building on the same Alpine base, produce byte-identical base layers and therefore the same digest. Storage deduplication is not a feature anyone implemented; it falls out of the naming.

    The second, and the one that matters more: a name can be verified rather than trusted. Normally a name is a promise — you ask for /etc/passwd and you trust the filesystem handed you the right file. A digest is different: you fetch the bytes from anywhere at all, hash them yourself, and compare. If it matches, the content is right, and it does not matter one bit whether it came from Docker Hub, a corporate mirror, a pull-through cache, or a USB stick carried into an air-gapped datacentre. This is why a digest is an identity, not a location.

    Hold on to that phrase, because it explains things that otherwise look arbitrary. A registry is only a convenient place to keep blobs, not an authority about them — which is why I5 can pull an image with nothing but curl, and why I11's supply-chain tooling can make meaningful guarantees at all. If content could only be identified by where it came from, none of that would work.

    The spec states the property and, in the same breath, the reason for it — note that verification is framed as defending against an insecure source, not against a broken disk.

    The digest property of a Descriptor acts as a content identifier, enabling content addressability. It uniquely identifies content by taking a collision-resistant hash of the bytes.

    If the digest can be communicated in a secure manner, one can verify content from an insecure source by recalculating the digest independently, ensuring the content has not been modified.
    OCI image-spec v1.1.1 — descriptor.md § Digests
    Lab
    1. Prove the first consequence: the same bytes in two unrelated places get the same name. Nothing coordinates this — the name is computed, not assigned. 
      echo "the same bytes" > a.txt
cp a.txt /var/tmp/b.txt
sha256sum a.txt /var/tmp/b.txt

    2. Now change a single character — one lowercase s becomes S — and watch the name become unrecognisably different. There is no "close": digests do not degrade gracefully, which is exactly what makes comparison a yes/no test. 
      echo "the same byteS" > c.txt
sha256sum c.txt
      51bef788bff6b5c72dce1199e1cd09dcea66cc37e7d96f6f2b2a047301b72346  c.txt

    Verify

    You can state, without hedging, why an image pulled from an untrusted mirror is safe to run when you know its digest — and why knowing only its tag gives you no such assurance. If that distinction is still fuzzy, I4.4 is where it bites.

    Gotchas
    • A digest proves integrity, not provenance. It tells you the bytes were not altered in transit. It says nothing about whether the person who built them should be trusted — that requires a signature over the digest, which is I11's subject. "It matched the digest" and "it is safe" are different claims.
    • The hash covers the exact bytes, not the meaning. Reformat a JSON manifest — same fields, different whitespace — and the digest changes completely. This is why manifests are stored and transferred verbatim and why tooling must never re-serialise one it intends to reference.
    • sha256: is part of the name. The prefix names the algorithm, so the format can migrate later without ambiguity. Strip it when using the value as a path under blobs/, keep it everywhere else.

    This is why image: app@sha256:… exists as an alternative to image: app:v2 in a pod spec, and it is the same reasoning as W3.23's point that base64 in a Secret is encoding, not encryption — a hash is not a secret and not a lock, it is a checkable name. When you meet ErrImagePull in W6.17, one of the three root causes is a digest that no longer resolves.

    Docs: the exam will not ask you to hash anything, but it will ask you to pin an image. Search the Kubernetes docs for "images" and read the section on image names and digests; the OCI side is descriptor.md § Digests.

    I4.2

    The descriptor: the only pointer in the format

    Why it matters

    Most file formats accumulate half a dozen ways to refer to something — an offset here, a filename there, an ID somewhere else. The image spec has exactly one, used at every level without exception. Once you can recognise it, an image manifest stops being a wall of JSON and becomes a handful of pointers you can follow.

    The concept

    A descriptor is a small JSON object with three required fields:

    • mediaType — what the thing you are about to fetch is, as a MIME-style string.
    • digest — its content-addressed name, from I4.1.
    • size — its length in bytes.

    Optionally it may also carry urls (other places the blob can be fetched from), annotations (arbitrary metadata), data (the content inlined, for tiny blobs) and — in an index — platform.

    Each required field earns its place, and the third is the one people overlook. digest is the identity. mediaType tells a client how to parse the bytes before it fetches them, so nothing ever has to sniff content or guess from a file extension — the parser is chosen from the pointer, not from the payload. And size lets a client allocate exactly once and, more importantly, refuse: if a descriptor says 611 bytes and the server keeps sending, the client can cut the connection instead of streaming a decompression bomb into memory.

    So every pointer in the format is simultaneously self-describing (you know the type), self-verifying (you can check the digest) and self-limiting (you know when to stop). A format whose only reference type has all three properties is a large part of why this specification has aged as well as it has. It is also why the whole thing is walkable with curl and jq — there is nothing to decode, just pointers to follow.

    The spec introduces descriptors as the mechanism for all references, and the word to notice in the first sentence is Merkle — a tree (here a graph) in which every node names its children by hash, so verifying the root transitively commits to everything beneath it.

    An OCI image consists of several different components, arranged in a Merkle Directed Acyclic Graph (DAG). References between components in the graph are expressed through Content Descriptors.

    A Content Descriptor (or simply Descriptor) describes the disposition of the targeted content. A Content Descriptor includes the type of the content, a content identifier (digest), and the byte-size of the raw content.
    OCI image-spec v1.1.1 — descriptor.md
    Lab
    1. Pull out every reference in a real image and see that they are all the same shape. The first lives in index.json and points at a manifest; the other two live inside that manifest and point at a config and a layer. 
      cd ~/i4/alpine-oci
MAN=$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
jq -c '.manifests[] | {mediaType, digest, size}' index.json
jq -c '.config | {mediaType, digest, size}' blobs/sha256/$MAN
jq -c '.layers[] | {mediaType, digest, size}' blobs/sha256/$MAN
      {"mediaType":"application/vnd.oci.image.manifest.v1+json","digest":"sha256:f27cad9117495d32d067133afff942cb2dc745dfe9163e949f6bfe8a6a245339","size":1022}
{"mediaType":"application/vnd.oci.image.config.v1+json","digest":"sha256:2607caa9805847fac4de202017bb1b830deb09f4c07dc9964a0157abbc604577","size":611}
{"mediaType":"application/vnd.oci.image.layer.v1.tar+gzip","digest":"sha256:897d797d2723cf0e318402f4d6f37d51b011517e5cf09246b22155f0fa90dc81","size":3646875}

      Three different kinds of thing — a JSON manifest, a JSON config, a gzipped tarball — and one pointer shape for all of them. The mediaType is what tells them apart, and it arrives before the content does.

    2. Count them mechanically, so it is not a claim you are taking on faith. This walks both JSON documents and picks out every object carrying the three required fields. 
      cat index.json blobs/sha256/$MAN \
  | jq -c '[.. | objects | select(has("digest") and has("size") and has("mediaType"))] | length'
      1
2

      jq reports per document: one descriptor in index.json, two in the manifest. Three pointers, and that is the entire reference graph of this image. A multi-layer image differs only in the length of the layers array.

    Verify

    Shown any JSON document from this format, you can point at each descriptor and say what it targets without following it — because mediaType already told you.

    Gotchas
    • size is a security control, not a hint. A client that ignores it and streams until EOF has no defence against a hostile registry returning an endless response. Your I4.15 project checks it for exactly this reason.
    • Annotations on a descriptor and annotations inside the target are different places. The manifest descriptor in an index can be annotated by whoever assembled the index; the manifest itself carries its own. They are not merged, and tooling that shows you "the annotations" rarely says which set it means.
    • A descriptor does not say where the blob is. Apart from the optional urls, there is no location anywhere — resolution is entirely the client's problem. That is deliberate, and it is what I4.1 meant by identity rather than location.

    You will not type a descriptor into Kubernetes, but the kubelet's image handling is descriptors all the way down: when W1.20's kubelet → containerd → shim → runc chain pulls an image, every hop between containerd and the registry is a descriptor being resolved and verified. The size field is why a partially-transferred layer is detected rather than silently used.

    Docs: descriptor.md in the image spec is two pages and worth reading start to finish — it is the only part of the format you must know by heart. The media-type registry is in media-types.md.

    I4.3

    The graph: index → manifest → config + layers

    Why it matters

    "An image" sounds like one object, and every tool encourages that impression by printing a single name and a single size. It is actually four kinds of node in a small graph, and nearly every confusing thing about images — why docker images shows an ID that appears nowhere in the registry, why an image has no honest single size — dissolves the moment you can draw the graph.

    The concept

    Draw it before you touch a real one. There are four node types, and only two of them are JSON you can read:

    • An index (sometimes called a manifest list) — a list of manifests, normally one per platform. JSON. Optional: single-platform images may have none.
    • A manifest — one image, for one platform. JSON. It holds exactly two things: a descriptor for the config, and an ordered list of descriptors for the layers.
    • A config — JSON describing how to run the thing: environment, entrypoint, user, plus the layer bookkeeping of I4.13.
    • The layers — opaque binary. Tarballs, usually compressed. These are the leaves, and they are all of the bytes that matter.

    Every arrow is a descriptor from I4.2. Everything above the layer blobs is small, readable JSON; the layers are the only opaque bytes — and, as the shared box shows, two images can point at the very same layer.

    Two properties of this shape matter more than the shape itself.

    First, everything above the layers is JSON small enough to read in a terminal. The manifest in your lab is 1,022 bytes. This is a format you can debug with curl and jq, which is precisely why I5 will be able to pull an image by hand over HTTP with no client library.

    Second, it is a graph, not a tree, and it is acyclic because references are digests — you cannot point at something whose content is not yet fixed, so a cycle is unconstructible. Because names are computed from content, two images built from the same base do not merely have similar layers, they point at the same blob. The sharing is automatic and needs no coordination between the people who built them.

    Which leads to a question worth retiring: how big is this image? There is no honest single answer. The sum of its layer sizes is one number; what a given node must actually download is usually far smaller, because it already has most of the leaves. The useful question is always "how much of this do I not already have?"

    The spec is explicit that the arrangement is a Merkle DAG, which is what makes verifying the top descriptor meaningful: each node commits, by hash, to every node below it.

    An OCI image consists of several different components, arranged in a Merkle Directed Acyclic Graph (DAG).
    OCI image-spec v1.1.1 — descriptor.md
    Lab
    1. Before walking a real one in I4.6, sketch this on paper: one index box, two manifest boxes beneath it, and a config plus a layer stack under each — then draw the layer arrows from both manifests to one shared blob. Label each arrow "descriptor". The drawing takes ninety seconds and is the thing you will actually recall under exam pressure.
    2. Confirm the node types are what you think by asking a real image what shape it is. This is the layout you build in I4.5; the point here is only that the top-level entry is a list. 
      cd ~/i4/alpine-oci
jq '{schemaVersion, entries: (.manifests | length), type: .manifests[0].mediaType}' index.json
      {
  "schemaVersion": 2,
  "entries": 1,
  "type": "application/vnd.oci.image.manifest.v1+json"
}

      One entry, and it is a manifest rather than an index — because this copy was fetched for a single platform. I4.8 fetches the whole thing and finds sixteen.

    Verify

    You can draw the four node types from memory, say which are JSON and which are opaque, and explain to someone why two different images can share storage without either build knowing about the other.

    Gotchas
    • "Image ID" usually means the config digest, not the manifest digest. The registry indexes by manifest digest; local tooling has historically shown the config digest. That is why the ID in docker images or nerdctl images matches nothing you saw in the registry — they are two different nodes of the same graph, both legitimately called "the image".
    • An index is optional. Plenty of images are a bare manifest with no index above them. Code that assumes the top node is always an index breaks on them — your I4.15 project has to handle both, which is why it checks the mediaType before descending.
    • Layer order is significant and is carried only by the array. Nothing inside a layer says where it belongs in the stack. Lose the ordering and you get I4.16's third fault: a rootfs that looks fine and is quietly wrong.

    This graph is why a node that already runs six images built on the same base pulls almost nothing for the seventh, and why W6.17's image failures are so often about one missing leaf rather than "the image" being broken. It is also the structure B5.16 arrived at from the other direction — layers plus a thin writable one — except that here the layers have names you can verify.

    Docs: manifest.md and image-index.md in the image spec; both are short. For the mental model, the phrase to search is "Merkle DAG".

    I4.4

    Tags are mutable labels on immutable content

    Why it matters

    This is the single most expensive misunderstanding in the whole format, and it produces incidents that are maddening precisely because nothing is broken: two nodes run different code, both pulled the same image name, both did exactly what they were told. Everyone blames caching. The actual cause is that a tag was never a name for content in the first place.

    The concept

    Everything in I4.1 through I4.3 is immutable: a digest names fixed bytes and always will. A tag is the one mutable thing in the system — a human-readable label the registry maps to a digest, and that mapping can be reassigned at any time by anyone with push access.

    So alpine:3.21 is not the name of an image. It is a name for whatever the registry currently says 3.21 means. Resolve it today and you get one digest; resolve it next month and you may legitimately get another, because the maintainers rebuilt 3.21 with a patched OpenSSL. Nothing has gone wrong. The tag did its job.

    People file this under "the :latest problem", which badly understates it. latest is not special in any way — it is just a tag with a misleading name, and it has no defined meaning at all. Any tag can move, including ones that look like immutable version numbers. v2.1.0 moves more often than you would like.

    Two nodes pulling app:v2 a week apart can therefore run different code, and every layer of the system will report success. The fix is to pin by digest — app@sha256:… — which names content and cannot drift. The reason people resist is honest: digests are unreadable, and updating them is work that has to be automated. So the compromise most teams reach, and the habit this track enforces, is name a tag and record the digest it resolved to. That will not prevent drift, but it makes drift detectable, which is most of the battle.

    The lab below shows the mechanism plainly: the tag's digest is nothing more than the SHA-256 of the manifest bytes the registry hands you. Resolution is a lookup; verification is arithmetic you can do yourself.

    The layout spec is careful to separate the two kinds of naming, and the phrasing is worth keeping: blobs are content-addressable, references are location-addressable. A tag is the second kind.

    The OCI Image Layout is the directory structure for OCI content-addressable blobs and location-addressable references (refs).
    OCI image-spec v1.1.1 — image-layout.md
    Lab
    1. Ask the registry for the raw bytes it serves for a tag, and save them exactly as received. Do not re-format them — the whole point is that the digest is over these precise bytes. 
      cd ~/i4
skopeo inspect --raw docker://alpine:3.21 > raw-index.json
    2. Now compute the tag's digest yourself, then ask the registry what it thinks the digest is. They are the same number, because "the digest of a tag" means nothing more than the hash of the document the tag resolves to. 
      sha256sum raw-index.json
skopeo inspect docker://alpine:3.21 | jq -r '.Digest, .Name'
      48b0309ca019d89d40f670aa1bc06e426dc0931948452e8491e3d65087abc07d  raw-index.json

sha256:48b0309ca019d89d40f670aa1bc06e426dc0931948452e8491e3d65087abc07d
docker.io/library/alpine

      Nothing privileged happened. You independently derived the registry's own answer with a command that ships in coreutils — which is exactly the property I4.1 promised.

    3. Record the pair. From here on, every pull in this track names a tag and writes down what it resolved to, so that a reader running these commands on a different day can immediately tell "the tag moved" from "my command is wrong". 
      echo "alpine:3.21 -> sha256:48b0309ca019d89d40f670aa1bc06e426dc0931948452e8491e3d65087abc07d  ($(date -I))" >> ~/i4/pinned.txt

      The image this page was authored against is alpine:3.21 at sha256:48b0309c…abc07d, which was Alpine 3.21.7, built 2026-04-16. If your digest differs, 3.21 has been rebuilt since — that is the lesson working, not a mistake.

    Verify

    You can explain why "we deployed the same image to both clusters" is not a claim anyone can make from a tag alone, and you can produce the digest a tag currently resolves to without trusting any tool's summary of it.

    Gotchas
    • imagePullPolicy: IfNotPresent plus a moving tag is a booby trap. A node that already has something cached under that tag never asks the registry again, so it never learns the tag moved — while a freshly-joined node pulls the new content. The cluster now runs two versions of "the same" image, and nothing reports an error.
    • Re-formatting a manifest changes its digest. If you pipe a manifest through jq . and hash the result, you will get a different number and conclude the registry is lying. Hash the raw bytes; that is why the lab uses --raw and redirects straight to a file.
    • Deleting and re-pushing a tag is invisible after the fact. There is no history: the registry has no record that the tag pointed anywhere else. Your recorded digest is the only evidence, which is the whole argument for recording it.

    In a pod spec, image: app:v2 is a tag and image: app@sha256:… is a digest, and the difference is exactly this lesson. The tag-moved scenario is one of the three root causes behind W6.17's ErrImagePull/ImagePullBackOff — a tag that resolved fine yesterday now points at a manifest the node cannot fetch. This is also why a rollout that "did nothing" can change behaviour: same spec, same tag, different bytes.

    Docs: search the Kubernetes docs for "image pull policy" and read the whole table — the defaulting rule (a tag of latest silently changes the default) is the part people get wrong. On the OCI side, tags are a registry concern, so the detail is in the distribution spec you meet in I5.
