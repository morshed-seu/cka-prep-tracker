    I1 — The primitives the beginner track left out

    This is a bridge module, and it is the only one in the track that teaches raw kernel machinery rather than a contract. Everything here is a delta: each lesson names the beginner lesson that built the thing, and then adds the one part that was deliberately left out because it only earns its keep once containers are the subject.

    There are six such parts, and every one of them turns up later as a symptom you would otherwise misdiagnose. User namespaces are how a container can have a root that is not the machine's root. PSI is how you tell "starved" from "idle" when a load average cannot. cpuset is how Kubernetes hands a pod exclusive cores — and how it accidentally starves one. The device controller moved to eBPF in cgroup v2 and stopped being readable with cat. seccomp is the single most common cause of a container that dies with no log line at all. And VXLAN is what your cluster's pod network is actually made of, MTU arithmetic included.

    Checkpoints14 Hours~5 PrerequisitesB2, B5, B6, B7, B9
    • Explain user namespaces and ID mapping well enough to reason about rootless containers — including the single-write rule and why it exists.
    • Install a mapped range with newuidmap from an unprivileged process, and say where the range came from.
    • Enter a namespace by file descriptor with setns(2), and name the three ways a namespaced process comes into existence.
    • Diagnose Ubuntu 24.04's AppArmor restriction on unprivileged user namespaces, and choose between the three responses knowingly.
    • Read PSI to distinguish a starved workload from an idle one, and say what load average cannot tell you.
    • Pin a workload with cpuset.cpus, and explain how that differs from cpu.max.
    • Find a cgroup's device policy when there is no file to read, using bpftool.
    • Write a seccomp filter by hand, get killed by it, and recognise the signature without being told.
    • Build a TUN device held open by your own program, and a VXLAN overlay between two namespaces — then compute its MTU and prove the arithmetic.

    B2 (processes and signals), B5 (overlayfs), B6 (namespaces), B7 (cgroups v2) and B9 (veth, bridges, NAT). None of that is re-taught here. If a lesson below opens with "you already did this", it means it — follow the link, skim, come back.

    Which machine. I1 is the one module in this track that touches no container tooling at all: no containerd, no registry, no internet. Any throwaway Ubuntu 24.04 VM with at least 2 vCPU works, so the beginner track's sandbox is as good a home as buildbox, and you may prefer to keep buildbox's clean snapshot untouched. Everything below runs as root on that VM unless a lesson says otherwise, and several labs deliberately leave the machine in a strange state — take a snapshot first.

    The output on this page was captured on a 2-vCPU box, so CPU numbers like cpuset.cpus = 0 reflect that. On a 4-vCPU buildbox, the same lessons work with a range such as 2-3; the file takes either.

    Isolation, the parts we skipped

    I1.1

    The eighth namespace: uid_map, and the rule that you may write it once

    Why it matters

    Every container you have ever run had a process claiming to be root. On a normal node, that claim is true — the process really is uid 0, and the only things standing between it and the machine are capabilities, seccomp and luck. A user namespace is the mechanism that makes the claim false in a useful way: root inside, an ordinary unprivileged account outside. It is the difference between a container escape that hands the attacker the node and one that hands them a user with no permissions at all.

    B6 walked through the other seven namespace types and stopped short of this one on purpose, because on its own it does very little. It is only interesting once you can read the translation table, and that table is a file.

    The concept

    A user namespace does one thing: it installs a translation table for user and group IDs. Inside the namespace, a process sees one set of numbers; outside, the kernel sees another. Nothing about the kernel's permission checks changes — a file owned by uid 100000 is still owned by uid 100000 — only which number a given process reads and writes.

    The table lives in /proc/<pid>/uid_map and /proc/<pid>/gid_map, and each line has exactly three columns:

    first ID inside→first ID outside→how many IDs

    So the line 0 100000 65536 reads: "uid 0 in here is uid 100000 out there, and the next 65,535 follow in order." A process that is uid 0 inside that namespace writes a file, and on the host that file belongs to 100000. That single sentence is the whole of rootless containers.

    Two properties make the feature safe enough to hand to unprivileged users, and both are worth internalising now because both produce confusing errors later:

    • Each map file may be written exactly once. The second write fails with EPERM, always, no matter who you are. This is what stops a process from widening its own mapping after the fact — you get the table you were given at birth, and you are stuck with it.
    • Until the map is written, everything is nobody. A fresh user namespace starts with an empty map, and every unmapped ID renders as 65534 (nobody/nogroup). That is not an error state; it is the pre-configuration state, and it is exactly what you see when something forgot to write the map.

    One more thing to have straight before the lab: /proc/<pid>/status shows a process's IDs as the reader's namespace sees them, not as the process sees itself. Reading it from the host will tell you the outside numbers. This trips people up constantly.

    Lab
    1. Start with the command every tutorial opens with, so you meet Ubuntu 24.04's answer to it immediately rather than in an hour. Run it as your ordinary user. 
      unshare --user --map-root-user bash -c id
      unshare: write failed /proc/self/uid_map: Operation not permitted

      That is not a broken machine and not a typo — it is a deliberate Ubuntu mitigation, and I1.4 takes it apart and fixes it properly. For the next three lessons, put sudo in front and carry on.

    2. Now the same thing with privilege, and look at what you actually got. 
      sudo unshare --user --map-root-user bash -c \
  'id; cat /proc/self/uid_map; grep -E "^Cap(Eff|Bnd)" /proc/self/status'
      uid=0(root) gid=0(root) groups=0(root),65534(nogroup)
         0          0          1
CapEff:	000001ffffffffff
CapBnd:	000001ffffffffff

      A one-line map — inside 0 is outside 0, for one ID — and a full capability set. Full capabilities in this namespace, which is a much smaller claim than it looks; the rest of the machine is unaffected.

    3. Watch the pre-configuration state, which is the one you will actually meet in the wild. Create a namespace and write nothing. 
      sudo unshare --user bash -c 'id; echo "map: [$(cat /proc/self/uid_map)]"'
      uid=65534(nobody) gid=65534(nogroup) groups=65534(nogroup)
map: []

      Empty map, everything is nobody. If a container ever shows you nobody where you expected a real user, this is the reason: an ID that no line covers.

    4. Write a map from outside, the way a real runtime does. Start a process in a fresh, unmapped namespace and leave it running. 
      sudo unshare --user sleep 60 &
sleep 1; P=$(pgrep -x sleep | tail -1); echo "child = $P"
      child = 21081
    5. Install the map, then try to change your mind. This is the single-write rule, demonstrated. 
      sudo sh -c "echo '0 100000 65536' > /proc/$P/uid_map"
cat /proc/$P/uid_map
sudo sh -c "echo '0 200000 65536' > /proc/$P/uid_map"
               0     100000      65536
sh: 1: echo: echo: I/O error

      The shell reports that unhelpfully. Ask for the errno directly and it is unambiguous:

      sudo python3 -c '
import os
for i, line in enumerate([b"0 100000 65536\n", b"0 200000 65536\n"], 1):
    try:
        fd = os.open("/proc/'$P'/uid_map", os.O_WRONLY); os.write(fd, line); os.close(fd)
        print(f"write {i}: OK")
    except OSError as e:
        print(f"write {i}: errno={e.errno} ({os.strerror(e.errno)})")'
      write 1: OK
write 2: errno=1 (Operation not permitted)

      (The first write succeeds because that python3 is a new process in a new namespace; re-running against the same still-mapped child would fail both times.)

    Verify

    You can state, without looking: what the three columns of uid_map mean; what a process's id shows before the map is written; and what happens on the second write. If you can also say why the second write is forbidden — so a process cannot widen the mapping it was born with — you have the security argument as well as the mechanism.

    Gotchas

    gid_map has a companion you will forget exactly once. Before an unprivileged process may write gid_map, it must usually write the string deny into /proc/<pid>/setgroups, which permanently disables setgroups(2) for that namespace. The reason is a real historical escalation: without it, a process could drop a group that was being used to deny access to a file and thereby gain access. If a gid_map write fails with EPERM and the uid_map write succeeded, this is almost always why.

    Reading /proc/<pid>/status from the host shows host-side IDs, so a container's "root" appears there as Uid: 100000. That is correct and is the point of the feature — but it means ps on the node and ps inside the container legitimately disagree about who is running, and neither is lying.

    Kubernetes exposes exactly this as spec.hostUsers: false on a Pod — user namespaces reached GA in v1.33, and setting it makes the pod's uid 0 an unprivileged host uid drawn from a per-pod range the kubelet allocates. It is the strongest single mitigation available against a container escape, and it is off by default because it interacts badly with volumes whose files are owned by real host uids.

    The advanced track has no securityContext or Pod Security Standards coverage — that is CKS territory, not CKA — so there is no anchor here to send you to, and you should be suspicious of anything that claims otherwise. What the advanced track does cover is the layer this sits under: W1.2 — what runs privileged on a node, and W3.2 — the pod spec fields the exam actually asks for.

    Docs

    man 7 user_namespaces is the authoritative reference and is unusually readable — the User and group ID mappings section is the one to know. Then man 2 setns, man 7 capabilities for what "full capabilities in a namespace" does and does not buy, and man 5 subuid for where the ranges in I1.2 come from.

    I1.2

    newuidmap, /etc/subuid, and what "root inside, nobody outside" costs

    Why it matters

    I1.1 wrote a mapping as root. That is what a privileged runtime does, and it explains nothing about how rootless containers work — because there, nobody has root to spare. This lesson is the allocation model that makes it possible, and it is genuinely simple once you see it: the distribution hands every user a block of 65,536 ID numbers at account-creation time, and the container's "root" is the first one.

    The concept

    An unprivileged process may write its own single ID into a map — one line, one ID, the one it already is. That is all the kernel will let it do without CAP_SETUID in the parent namespace. A useful container needs a whole range, because the software inside expects uid 0 and uid 33 and uid 1000 to be distinct.

    The gap is bridged by two small setuid-root helpers, newuidmap and newgidmap. They have CAP_SETUID because they are setuid-root, so they can write a multi-range map — and they refuse to write anything outside the range an administrator granted you in /etc/subuid and /etc/subgid. Those two files are the entire policy surface:

    /etc/subuid→newuidmap (setuid)→/proc/PID/uid_map→root inside

    The consequence is worth sitting with, because it is the security argument for rootless containers in one sentence. A process that breaks out of a rootless container arrives on the host as uid 100000 — an account that owns nothing, is in no groups, and has no entry in /etc/passwd. Compare that with breaking out of a conventional container, where the process arrives as uid 0.

    The price is the mirror image, and it is why rootless is not simply better: files created by the container are owned by host uids nobody else can read or write. Sharing a directory between a rootless container and a normal user requires either matching ID mapping on both sides or an ID-shifting mount, and "why can't I read the file my container just wrote" is the single most common rootless support question.

    Lab
    1. Install the helpers and read your allocation. On Ubuntu they are in the uidmap package, which is not installed by default on a server image. 
      sudo apt-get install -y uidmap
grep "^$USER:" /etc/subuid /etc/subgid
ls -l /usr/bin/newuidmap
      /etc/subuid:ubuntu:100000:65536
/etc/subgid:ubuntu:100000:65536
-rwsr-xr-x 1 root root 41864 May 30  2024 /usr/bin/newuidmap

      The s in the permission bits is the whole trick: it runs as root regardless of who invoked it, and it is small and audited precisely because of that.

    2. Start an unmapped namespace and hand its pid to newuidmap — as your ordinary user, no sudo anywhere. 
      unshare --user sleep 90 & C=$!
sleep 1
echo "uid_map is empty: [$(cat /proc/$C/uid_map)]"
newuidmap $C 0 100000 65536
newgidmap $C 0 100000 65536
cat /proc/$C/uid_map
      uid_map is empty: []
         0     100000      65536

      The three arguments after the pid are the same three columns as the file: inside, outside, count. newuidmap accepts several triples in a row if you want a non-contiguous map.

    3. Try to map a range you were not granted, so you see the policy enforce itself rather than taking its existence on faith. 
      unshare --user sleep 30 & C2=$!
sleep 1
newuidmap $C2 0 500000 65536
      newuidmap: uid range [0-65536) -> [500000-565536) not allowed
    4. Look at the mapped child from inside and from outside at the same time. This is the "root inside, nobody outside" claim, made concrete. 
      nsenter -t $C -U --preserve-credentials -- id
grep -E '^(Uid|Gid)' /proc/$C/status
      uid=65534(nobody) gid=65534(nogroup) groups=65534(nogroup)
Uid:	1000	1000	1000	1000

      Both lines are surprising and both are correct. --preserve-credentials keeps your uid 1000 as you enter, and 1000 is not in the map (the map covers 100000–165535), so inside you are nobody. And /proc/<pid>/status is rendered for the reader — you are on the host, so you see host numbers.

    5. Now do it properly, with the child becoming root once the map exists. The synchronisation matters: the child must wait, because it cannot map itself. 
      mkfifo /tmp/go
unshare --user bash -c 'read _ < /tmp/go; exec setpriv --reuid 0 --regid 0 \
   --clear-groups sh -c "id; touch /tmp/rf; ls -ln /tmp/rf"' &
C=$!; sleep 1
newuidmap $C 0 100000 65536 && newgidmap $C 0 100000 65536
echo go > /tmp/go
      setpriv: setresuid failed: Operation not permitted

      It fails, on Ubuntu 24.04, and the reason is not the mapping — the map installed fine. It is the AppArmor restriction from I1.4, which leaves the process with an empty effective capability set, and setuid(2) to another user needs CAP_SETUID. Confirm that diagnosis rather than guessing at it:

      unshare --user bash -c 'read _ < /tmp/go; grep -E "^Cap(Eff|Bnd)" /proc/self/status
   cat /proc/self/attr/current' &
C=$!; sleep 1; newuidmap $C 0 100000 65536; echo go > /tmp/go
      CapEff:	0000000000000000
CapBnd:	000001ffffffffff
unprivileged_userns (enforce)

      Bounding set full, effective set empty, and an AppArmor profile named in the third line. Hold that thought for two lessons — I1.4 makes this exact command work.

    Verify

    newuidmap $C 0 100000 65536 succeeds as an unprivileged user and /proc/$C/uid_map shows the range; the same command with an out-of-range base is refused by name. You can say where the number 100000 came from without looking at the file.

    Gotchas

    Ranges are per-user and must not overlap, and nothing enforces that for you if you edit /etc/subuid by hand. Two users sharing a range means two users' containers share host identities — which quietly undoes the entire isolation argument, since one user's escaped container lands as the other user's container files' owner. Use usermod --add-subuids rather than an editor.

    65,536 IDs is a lot until you nest. A rootless container that itself runs a user namespace can only sub-allocate from its own range, so the inner container's "root" is drawn from the outer container's block. Nesting three deep with software that expects a fresh 65,536 each time is where rootless setups run out of numbers, and the error message is never about numbers.

    These helpers are frequently absent. Ubuntu server images do not ship uidmap, and Podman or Buildah installed without it fail with a message about newuidmap not being found that reads like a bug in the container tool. It is not; it is one apt install.

    The kubelet does this allocation itself when a pod sets hostUsers: false — it hands each pod a distinct 65,536-ID block from a node-wide pool, for exactly the non-overlap reason above, and writes the map into the OCI config that I2 takes apart. The /etc/subuid mechanism is the single-machine version of the same idea, done by the distribution instead of by a scheduler.

    The volume-ownership pain has an exact Kubernetes counterpart in fsGroup and the fsGroupChangePolicy field, which exist because a pod and a volume can disagree about which numeric group may read a file. W5.4 — PersistentVolumeClaims and access modes is where volume ownership first bites in the advanced track.

    Docs

    man 5 subuid and man 5 subgid for the files; man 1 newuidmap for the helper's exact argument shape; man 8 usermod for --add-subuids. man 7 user_namespaces again, this time the Defining the mappings section, which spells out precisely which writes are permitted to whom.

    I1.3

    setns(2) by file descriptor — and the three ways a process gets a namespace

    Why it matters

    You have used nsenter. This lesson is what nsenter does, which turns out to be two system calls in a loop — and once you have seen them, kubectl exec stops being magic. Nothing "enters the pod". A process already on the node opens some files and calls setns.

    The concept

    A namespace has no name. It is not a path, not a string, not an entry in a table you can list. It is an object in the kernel, and the only handle you get on it is a file descriptor — obtained by opening /proc/<pid>/ns/<type>, which is a magic symlink whose text is <type>:[<inode>]. That inode number is the namespace's identity: two processes are in the same network namespace if and only if /proc/A/ns/net and /proc/B/ns/net read the same inode.

    Referencing namespaces by descriptor rather than by name explains several things at once that otherwise look like unrelated trivia:

    • Lifetime. A namespace lives as long as something refers to it — a process inside it, or an open fd. That is why ip netns add works by bind-mounting the fd onto /run/netns/<name>: the mount is a reference, so the namespace survives with no processes in it. "Pinning" is nothing more exotic than that.
    • Transferability. A file descriptor can be passed to another process over a unix socket. So one program can create a namespace and hand it to another, which is how a runtime and its network plugin can cooperate without either being the other's child.
    • Granularity. setns takes one namespace at a time, so a process can join a pod's network namespace while keeping its own mount namespace. That is not a curiosity — it is precisely how a debug container sees the pod's network but its own filesystem.

    Three ways exist to get a process into a namespace, and it is worth having the distinction crisp because the error signatures differ:

    MechanismWhat it doesWho uses it
    fork/clone with no flagsinherit the parent's namespaceseverything, all the time
    unshare(2)leave the current namespaces and make new ones, in placethe unshare tool; shell-script runtimes
    clone3 with CLONE_NEW*create a process that is already inside new namespacesreal runtimes: runc, crun
    setns(2)join namespaces that already existnsenter, kubectl exec, CNI plugins

    The reason clone3 matters to a runtime is subtle but real: unshare-then-configure leaves a window in which a half-configured process exists, briefly, with new namespaces and old everything-else. clone3 closes that window by creating the process already inside. A shell-script runtime cannot do this, which is one of several honest reasons minibox.sh is a teaching tool and not a product.

    Lab
    1. Make a target: a process with its own UTS and network namespaces, so there is something distinguishable to enter. 
      sudo unshare --uts --net bash -c 'hostname minibox; sleep 90' &
sleep 1; T=$(pgrep -f "sleep 90" | head -1); echo "target = $T"
      target = 23625
    2. Read the identities. Compare the target's inode numbers with your own — the ones that differ are the namespaces it left. 
      sudo readlink /proc/$T/ns/uts /proc/$T/ns/net /proc/$T/ns/mnt

mnt:[4026531841]

      Two differ, one matches — it unshared uts and net and kept the host's mount namespace, which is exactly what the command asked for.

    3. Enter by fd from a program of your own. Write this file; it is about fifteen lines and it is the entire mechanism. 
      cat > ~/enter.py <<'PY'
import ctypes, os, sys
TYPES = {"mnt": 0x00020000, "uts": 0x04000000, "pid": 0x20000000, "net": 0x40000000}
libc = ctypes.CDLL("libc.so.6", use_errno=True)
target, wanted = sys.argv[1], sys.argv[2].split(",")
for t in wanted:
    path = f"/proc/{target}/ns/{t}"
    fd = os.open(path, os.O_RDONLY)
    print(f"  open({path}) = fd {fd}  -> {os.readlink(path)}")
    if libc.setns(fd, TYPES[t]) != 0:
        raise OSError(ctypes.get_errno(), os.strerror(ctypes.get_errno()), path)
    print(f"  setns(fd {fd}, CLONE_NEW{t.upper()}) = 0")
    os.close(fd)
print("--- now running inside those namespaces ---")
os.execvp(sys.argv[3], sys.argv[3:])
PY

  setns(fd 3, CLONE_NEWNET) = 0

    readlink /proc/<pid>/ns/net prints matching inode numbers for two processes you believe share a network namespace, and different ones for two you believe do not. Your enter.py prints a hostname belonging to the target, not to the host.

    Gotchas

    setns into a PID namespace does not move the calling process — it only affects the children it forks afterwards. That is why /proc/<pid>/ns/pid_for_children exists as a separate link, and why nsenter -p without -f sometimes appears to do nothing. A process's own pid cannot change underneath it, so the kernel does not try.

    Order matters when you join several at once. Join the mount namespace first and the /proc you were about to read from is a different /proc; join the user namespace last and you may no longer have the capability to join the rest. nsenter has a fixed, carefully chosen order — if you write your own, copy it rather than inventing one.

    The fd must be opened by a process that can see the target's /proc entry. Inside a PID namespace where the target is invisible, there is no path to open, and the failure is ENOENT rather than EPERM — which sends people looking for a permissions problem that is not there.

    This is the mechanism under kubectl exec, end to end. The apiserver streams to the kubelet, the kubelet asks the runtime over CRI (I8) for an exec, and the runtime creates a process that setnses into the target container's namespaces — one open and one setns per type, exactly as above. Nothing crosses a machine boundary except the stream.

    It is also what an ephemeral debug container does with shareProcessNamespace or kubectl debug --target: join the target's PID and network namespaces, keep your own mount namespace, and you have your tools plus their view. See W6.6 — debugging a pod that has no shell, which is the practical form of everything on this page.

    Docs

    man 2 setns — the Description section lists which namespace types have which restrictions. man 2 unshare and man 2 clone (search for clone3) for the other two mechanisms. man 1 nsenter, whose options map one-to-one onto the CLONE_NEW* flags. man 7 namespaces for the /proc/<pid>/ns/ layout including pid_for_children.

    I1.4

    Ubuntu 24.04's AppArmor wall, and the three honest ways past it

    Why it matters

    Two lessons ago a command failed, and the fix was "use sudo". That was a stopgap. This restriction is the single biggest obstacle to running rootless containers on a modern Ubuntu box, it is deliberate, it is a good idea, and the internet's standard advice about it — flip a sysctl — is the worst of the three available answers. It deserves an explanation rather than a workaround.

    The concept

    Unprivileged user namespaces have been an unusually rich source of kernel privilege escalations. The reason is structural rather than accidental: creating one hands an ordinary user CAP_SYS_ADMIN inside the namespace, and a great deal of kernel code that was written on the assumption "only root reaches this" is suddenly reachable — mount option parsing, netfilter, filesystem drivers, and every obscure ioctl behind them. The isolation boundary holds; the bugs are in the newly-exposed surface behind it.

    Ubuntu's answer was not to disable the feature. It was to gate the capabilities, using AppArmor. When an unconfined process creates a user namespace, the kernel transitions it into a stock profile called unprivileged_userns, and that profile's first line is the whole mitigation:

    profile unprivileged_userns {
     audit deny capability,
     audit deny change_profile,
     allow network,
     allow signal,
     ...
     allow userns,
}

    Read that carefully, because it is not what most write-ups describe. The namespace is created successfully — allow userns is right there. What is denied is capability: the process inside gets an empty effective set. So the classic claim "you get full capabilities inside your own user namespace" is simply not true on stock 24.04, and the symptoms are downstream of that: unshare --map-root-user fails at the uid_map write, setpriv --reuid 0 fails at setresuid, mounting fails, and none of the error messages mention AppArmor.

    Three responses exist, and they are genuinely different in what they cost:

    ResponseWhat it changesCost
    A named AppArmor profile with userns,one program, by path, gets real capabilities in its own namespacesa file in /etc/apparmor.d/ and a reload; this is the right answer
    sysctl kernel.apparmor_restrict_unprivileged_userns=0removes the mitigation for every process on the machinefine on a VM you will throw away; never on a node
    Accept it and use sudonothingyou are no longer studying rootless containers, you are studying containers

    The profile route wins because it is the one that scales: it is what a packaged application ships, it names a single binary, and everything else on the box stays denied. The sysctl route is the one to understand precisely so you can recognise it in someone else's install script and object.

  pid=20943 comm="unshare" capability=21  capname="sys_admin"

      Two lines: the transition, then the denial. If you remember one diagnostic from this lesson, make it "dmesg | grep apparmor after a permission error that makes no sense".

    3. Response A — the good one. Write a profile for a single wrapper script, so exactly one path is exempt. 
      mkdir -p ~/bin
printf '#!/bin/bash\nexec unshare --user --map-root-user "$@"\n' > ~/bin/rootless-lab

  userns,
  include if exists <local/rootless-lab>

      The profile is flags=(unconfined) — it confines nothing — and grants exactly one permission, userns. That is the minimum that undoes the restriction for this binary and nothing else.

    4. Prove it works, and prove it is narrow.

      One binary exempted, the machine-wide mitigation untouched. Confirm that last part:

      sysctl -n kernel.apparmor_restrict_unprivileged_userns

      sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0

      Identical result to the profile — for every process on the machine, including anything that has just been downloaded and run. That is the difference, and it does not show up in the output.

    Verify

    ~/bin/rootless-lab id prints uid=0(root) with a full CapEff, while a bare unshare --user --map-root-user still fails, and sysctl -n kernel.apparmor_restrict_unprivileged_userns still prints 1. All three at once is the state you want for I1.13.

    Gotchas

    The profile matches by absolute path, so it must name the real location of the binary, and moving or reinstalling the file silently un-exempts it. That is a feature — a path-based rule cannot be inherited by an attacker's copy — but it means "it worked yesterday" after a package upgrade is a real failure mode. aa-status | grep rootless tells you whether the profile is loaded; cat /proc/self/attr/current from inside tells you whether it applied.

    Do not carry the sysctl to a Kubernetes node. Nodes run arbitrary workloads by definition, which is precisely the population the mitigation exists for; turning it off there is a straightforward reduction in the node's defence against container escapes, made globally, to fix one program's problem.

    Other distributions differ, and the difference is not cosmetic. Debian and Fedora do not ship this restriction, so the same lab needs no profile there; older Ubuntu used kernel.unprivileged_userns_clone, a different sysctl that blocks namespace creation outright rather than gating capabilities. Reading advice for one and applying it to the other produces a fix that does nothing.

    Kubernetes has the same argument at a different altitude: whether a workload may do privileged things, and how narrowly you can grant it. The kubelet does not use AppArmor to gate user namespaces — it allocates ID ranges itself and asks the runtime — but a node running rootless-capable workloads has to make exactly this decision about which processes may create namespaces with real capabilities.

    The advanced track has no securityContext, Pod Security Standards or AppArmor-annotation coverage, because none of it is on the CKA. Do not go looking for an anchor. What is there is the node-level view: W1.2 — what runs privileged on a node and W6.12 — node Conditions, which is where a node whose security posture you have just changed starts telling you about it.

    Docs

    man 5 apparmor.d for the profile syntax, particularly the Rules section covering userns; man 8 apparmor_parser for -r. Ubuntu's own write-up lives at ubuntu.com — restricted unprivileged user namespaces and is worth reading once for the threat model. Then man 7 user_namespaces, Security section, for why anyone thought this was necessary.

    Resource control, the parts we skipped

    I1.5

    PSI — the question load average cannot answer

    Why it matters

    "Is this thing slow because it is overloaded, or because it is waiting on something, or is it just idle?" is the first question in every performance investigation, and load average answers it badly. Pressure stall information — PSI — answers it directly, it has been in the kernel since 4.20, it is four files, and almost nobody reads it. It is the highest-value-per-minute thing in this module.

    The concept

    B7 taught you cpu.stat, which counts how much CPU a cgroup used and how often it was throttled. That tells you what happened to the resource. PSI tells you what happened to the work: how much wall-clock time was lost because something that wanted to run could not.

    Load average cannot do this, and the reason is worth stating precisely rather than as a slogan. Load average counts runnable tasks. A machine with 40 threads on 40 CPUs and a machine with 40 threads on 4 CPUs both report a load around 40; one is perfectly healthy and the other is dying. The number has no denominator.

    PSI has one — wall-clock time — and reports two different percentages:

    LinePercentage of time in which…What it means
    someat least one task was stalled waiting for the resourcethere is contention; work is being delayed
    fullevery runnable task was stalled, so nothing useful happened at allreal damage; the machine is losing throughput outright

    Each line carries decaying averages over 10, 60 and 300 seconds, plus a monotonic total in microseconds — which is the one to use if you are recording it, because the averages are for humans looking at a terminal and the total is for anything that subtracts two samples.

    System-wide values live in /proc/pressure/{cpu,memory,io}. Every cgroup v2 directory also carries cpu.pressure, memory.pressure and io.pressure with the same format, scoped to that cgroup and its descendants — which is what makes PSI useful per-workload rather than per-machine.

    Lab
    1. Read the system-wide files on an idle box first, so you know what "nothing wrong" looks like. 
      head -20 /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io
      ==> /proc/pressure/cpu <==
some avg10=0.18 avg60=0.03 avg300=0.00 total=31733351
full avg10=0.00 avg60=0.00 avg300=0.00 total=0

==> /proc/pressure/memory <==
some avg10=0.00 avg60=0.00 avg300=0.00 total=288
full avg10=0.00 avg60=0.00 avg300=0.00 total=288

==> /proc/pressure/io <==
some avg10=1.34 avg60=0.25 avg300=0.05 total=34870652
full avg10=1.16 avg60=0.22 avg300=0.04 total=26089773

      Note the bolded line: system-wide cpu full is always zero, by definition. If every task on the machine were stalled on CPU there would be no task to run, which is not a state the CPU can be in. It is meaningful at the cgroup level — where "every task in this cgroup" is a much smaller claim — and that is where you will use it.

      The io numbers being non-zero on an idle VM is also normal: journald and the cloud-init machinery do enough writing to register.

    2. Make a cgroup with a hard CPU limit, and put two busy loops in it. This is the throttled case — the one B7 taught you to recognise. 
      sudo -i

sleep 12
    3. Read both stories at once — what happened to the resource, and what happened to the work. 
      cat $CG/cpu.stat; echo '---'; cat $CG/cpu.pressure
      usage_usec 1211659

      Throttled in all 120 periods, 22.7 seconds of enforced idling, and roughly 60% of wall time lost to waiting. The two files agree, and that agreement is the signature of a genuine CPU-limit problem: the limit is the cause, so raising it is the fix.

      Here some and full are equal because both tasks are throttled simultaneously — the bandwidth controller stops the whole cgroup at once. Remember that; I1.6 produces a case where they are very different.

      kill %1 %2; rmdir $CG
    Verify

    You can say what some avg10=59 means without hedging (59% of the last ten seconds had at least one task stalled), why system-wide cpu full is structurally zero, and which field to record if you are graphing this rather than reading it (total).

    Gotchas

    The averages are exponentially decaying, so a burst that ended 30 seconds ago still colours avg60 and a burst that started two seconds ago barely moves avg10. Sampling PSI once, immediately after a complaint, tends to show you nothing. Sample total twice a few seconds apart and divide by the elapsed time if you need a number you can defend.

    memory.pressure going up is not the same as approaching memory.max. It measures time lost to reclaim, refaults and swap — so a cgroup nowhere near its limit but thrashing its page cache shows high memory pressure and a comfortable memory.current. That combination is a real and commonly-missed diagnosis: the workload's working set no longer fits, and the limit is not the thing to change.

    A cgroup's pressure includes its descendants. Reading pressure at a slice and concluding a particular service is stalled is a mistake if the slice has other children — walk down to the leaf.

    The kubelet uses eviction signals rather than PSI for its own decisions — memory.available, nodefs.available and friends, thresholds you set with --eviction-hard. PSI is what you reach for when the kubelet's signals say the node is fine and the pods on it are visibly not, which is exactly the case eviction thresholds cannot see: nothing is out of memory, everything is waiting.

    See W3.18 — node-pressure eviction and the QoS classes for what the kubelet does act on, and W6.12 — node Conditions for how a node reports pressure upward. Reading a node's /proc/pressure/io during a DiskPressure investigation will very often tell you in one line what a long describe will not.

    Docs

    The authoritative document is the kernel's own Documentation/accounting/psi.rst — search "kernel psi.rst" — which is two pages and defines some/full exactly. Then Documentation/admin-guide/cgroup-v2.rst, the PSI section, for the per-cgroup files and the poll interface that OOM daemons use. man 5 proc covers /proc/pressure only briefly.

    I1.6

    cpuset — restricting where, not how much

    Why it matters

    There are two entirely different ways to limit a workload's CPU, they produce nearly identical symptoms, and only one of them shows up in the file everyone checks. cpu.max caps how much CPU time you get. cpuset.cpus caps which cores you may use. A workload starved by the second looks throttled and has zero throttling recorded — and that disagreement is the diagnosis this module's drill is built on.

    The concept

    B7 covered cpu.max: a quota and a period, enforced by stopping the cgroup when it has spent its allowance. cpuset is a different controller entirely. cpuset.cpus takes a list or range of CPU numbers — 0, 2-3, 0,4-7 — and every task in the cgroup is confined to those cores. There is no quota, no period and no accounting; the scheduler simply never considers the other CPUs.

    cpu.max = how much·cpuset.cpus = where·only the first is counted in cpu.stat

    Two details about the v2 interface catch people out. Like every controller, cpuset must be enabled in the parent's cgroup.subtree_control before the files appear in a child. And an empty cpuset.cpus means "inherit from the parent", not "no CPUs" — so a cgroup you have created but not written to is unrestricted, and cpuset.cpus.effective is the file that tells you what is actually in force.

    cpuset.mems is the same idea for memory: it restricts which NUMA nodes a task's pages may be allocated from. On a multi-socket machine, memory attached to another socket is reachable but meaningfully slower, so a latency-sensitive workload wants its threads and its pages on the same node — pinning one without the other buys you very little. On a single-socket machine or a VM there is one node, 0, and the file is a formality you should still know exists.

    Lab
    1. Enable the controller and make a cgroup pinned to a single CPU. On a 4-vCPU box use 2-3; the captures below are from a 2-vCPU box, so they use 0. 
      sudo -i
echo "+cpu +cpuset" > /sys/fs/cgroup/cgroup.subtree_control
CG=/sys/fs/cgroup/pinned; mkdir -p $CG
echo 0 > $CG/cpuset.cpus
echo "cpu.max     = $(cat $CG/cpu.max)"
echo "cpuset.cpus = $(cat $CG/cpuset.cpus)  effective = $(cat $CG/cpuset.cpus.effective)"
echo "cpuset.mems.effective = $(cat $CG/cpuset.mems.effective)"
      cpu.max     = max 100000
cpuset.cpus = 0  effective = 0
cpuset.mems.effective = 0

      cpu.max is max — there is deliberately no bandwidth limit here. Everything that follows happens with the limit switched off.

    2. Create contention on that one CPU from outside the cgroup, then put two busy loops inside it. Three runnable tasks, one core. 
      taskset -c 0 bash -c 'while :; do :; done' &

      pid 21581's current affinity list: 0

      taskset -pc reads the affinity mask the cgroup imposed — you never called taskset on that process, but the mask is there. That is the confirmation that cpuset.cpus and taskset are two interfaces onto the same kernel field.

    3. Now the point of the whole lesson. Read the two files a tired engineer would read. 
      head -7 $CG/cpu.stat; echo '---'; cat $CG/cpu.pressure
      usage_usec 7503330

full avg10=37.37 avg60=10.29 avg300=2.32 total=7498732

      Zero throttling — not "a little", zero, and nr_periods 0 because the bandwidth controller is not running at all. And 75% of wall time with at least one task stalled. The workload is being starved and cpu.stat has nothing to say about it.

      Notice too that some and full now differ sharply, unlike I1.5. With two tasks sharing one core, one of them is usually running while the other waits — that is some. Only when a third task (ours from outside) holds the core do both stall at once — that is full. The gap between the two lines is telling you how much of the contention is internal to the cgroup versus imposed from outside.

      kill %1 %2 %3; rmdir $CG

    taskset -pc <pid> on a process you moved into the cgroup reports only the CPUs you wrote, and cpu.stat shows nr_throttled 0 while cpu.pressure is high. State the difference between cpu.max and cpuset.cpus in one sentence each — one is a budget, the other is a seating chart.

    Gotchas

    Writing a CPU number that does not exist, or that the parent cgroup does not have, fails with EINVAL and no explanation. Check cpuset.cpus.effective on the parent before writing a child, because v2 enforces that a child's set is a subset of its parent's — this is the usual cause of "the file rejects a value that is obviously valid".

    An empty cpuset.cpus is inherit, not deny. A cgroup you created and never wrote to imposes no restriction at all, which means "I set up the cpuset and nothing changed" is usually "I created the directory and stopped".

    Pinning without measuring is a common own goal. Confining a workload to two cores on an otherwise-idle 8-core machine makes it slower, not more predictable, unless something else was actually interfering with it. Exclusive cores are a latency optimisation, and they cost throughput; buy them deliberately.

    Kubernetes writes this exact file. The kubelet's CPU Manager, with --cpu-manager-policy=static, gives Guaranteed-QoS pods whose CPU requests are whole numbers a set of exclusive cores by setting cpuset.cpus on the pod's cgroup — and simultaneously removes those cores from every other pod's cpuset. The companion Memory Manager and Topology Manager do the same for cpuset.mems and NUMA alignment.

    The failure this produces on a real node is exactly the drill in I1.14: a pod's CPU usage looks fine, its throttling counters are zero, and it is slow anyway, because the cores it was given are shared with something the CPU Manager does not know about. For the Kubernetes-side view of requests, limits and QoS classes, see W3.17 — requests, limits and the three QoS classes.

    Docs

    Documentation/admin-guide/cgroup-v2.rst, the Cpuset section, is the reference for every file named above including cpuset.cpus.partition, which is how you take cores away from the kernel's general scheduling domain entirely. man 7 cpuset describes the v1 interface and the NUMA reasoning, which has not changed. man 1 taskset and man 2 sched_setaffinity for the per-process equivalent.

    I1.7

    The device controller moved to eBPF, and stopped being readable

    Why it matters

    "Which device nodes may this container open?" is a security question with a concrete answer, and in cgroup v2 that answer is not in a file. This is the biggest single v1→v2 surprise, it invalidates a decade of blog posts, and the practical consequence is that you cannot audit device policy with cat — you need a different tool, and knowing which one is most of the lesson.

    The concept

    In cgroup v1 the device controller was an ordinary interface file. You wrote rules like c 1:3 rwm into devices.allow or devices.deny, and you read the current policy back out of devices.list. It was inspectable, greppable and scriptable.

    Cgroup v2 has no such file. The kernel dropped the controller and replaced it with an eBPF program — a small verified program, loaded into the kernel, attached to the cgroup with type BPF_PROG_TYPE_CGROUP_DEVICE, invoked on every attempt to open a device node, returning allow or deny. eBPF ("extended Berkeley Packet Filter") is the kernel's general mechanism for running user-supplied, verified-safe code at fixed hook points; you will meet it again in I1.9 as seccomp and in the advanced track as the datapath under some CNI plugins.

    Two consequences follow, and both are operational rather than theoretical:

    • Policy is invisible to the filesystem. There is nothing to cat. bpftool cgroup show <path> tells you a program is attached and what it is called; it does not decompile it into rules. To know what a container may open, you read the runtime's config.json — which is why I2's linux.resources.devices is the practical source of truth, not the kernel.
    • The denial has no diagnostic. The open(2) returns EPERM. There is no log line, no audit record by default, and no file to consult. A container that "cannot see the GPU" and a container that has been denied the GPU are indistinguishable from inside.

    The failure signature to memorise is therefore just this: Operation not permitted when opening something under /dev, from a process that appears to have the right file permissions. If the mode bits say you may and the kernel says you may not, a cgroup device program is the reason.

    Lab
    1. Confirm the absence first. This is one of those facts that is easier to believe after you have failed to find the file. 
      ls /sys/fs/cgroup/ | grep -i device || echo "(no device* file anywhere in the root cgroup)"
      (no device* file anywhere in the root cgroup)
    2. Now make a cgroup that does have a device policy. The quickest source of one is systemd, which sets device policy on any unit that asks — and does it by attaching exactly the kind of program described above. 
      sudo systemd-run --unit=i1dev --property=DevicePolicy=strict \
  --property=DeviceAllow='/dev/null rw' /bin/bash -c 'sleep 45'
sleep 2
CG=/sys/fs/cgroup/system.slice/i1dev.service

        (still no devices.* file — the policy is not in the filesystem)
    3. Find it with the right tool. 
      sudo bpftool cgroup show $CG

244      cgroup_device   multi           sd_devices

	loaded_at 2026-07-27T09:11:25+0600  uid 0
	xlated 472B  jited 296B  memlock 4096B

      sd_devices is systemd's name for it — a runtime would attach its own. 472 bytes of bytecode is the entire device policy for that unit, and bpftool will not tell you which devices it permits. That is the point being made.

    4. Feel the denial from inside. Move a shell into that cgroup and try to open something the policy does not list. 
      sudo bash -c 'echo $BASHPID > '"$CG"'/cgroup.procs
  echo hi > /dev/null      && echo "write /dev/null    -> OK"

      /dev/null was allowed by name; everything else was refused at open. Check the mode bits on /dev/zero — crw-rw-rw-, world-readable — and note that they had no bearing on the outcome.

      sudo systemctl stop i1dev; sudo systemctl reset-failed

    bpftool cgroup show on the unit's cgroup lists a cgroup_device program, and reading /dev/zero from inside that cgroup fails with EPERM despite world-readable permissions. You can name the tool you would reach for on a node where a container cannot open a device.

    Gotchas

    systemd's DevicePolicy=closed — the more common setting — still permits a default list including /dev/null, /dev/zero, /dev/full, /dev/random, /dev/urandom and the tty devices. If you are trying to demonstrate a denial and everything keeps working, that is why; strict is the one that allows only what you list.

    bpftool lives in linux-tools-common plus a kernel-specific package on Ubuntu, and the generic bpftool binary sometimes warns about a version mismatch with the running kernel. It still lists attached programs correctly. It also needs root — an unprivileged bpftool cgroup show silently returns nothing rather than an error, which looks exactly like "no policy attached".

    Device policy is inherited down the cgroup tree, and a child cannot grant itself something an ancestor denied. So the program you find on a container's own cgroup may not be the one doing the denying — walk up toward the root and check each level.

    Device access is how GPUs, FUSE mounts and raw block volumes reach a pod, and it is mediated by exactly this mechanism: the kubelet asks the runtime, the runtime writes linux.resources.devices into the OCI config, and runc compiles that into the BPF program you just found. A device plugin's entire job is to get the right entries into that list.

    The advanced track meets the consequence rather than the mechanism, in storage: W5.9 — volume types and what the kubelet actually mounts. When a raw-block PVC produces "permission denied" on a device node that plainly has the right mode bits, this lesson is the explanation.

    Docs

    Documentation/admin-guide/cgroup-v2.rst — the Device controller section is four sentences and says exactly this. man 8 bpftool-cgroup and man 8 bpftool-prog for the tool. man 5 systemd.resource-control for DeviceAllow and the DevicePolicy values, which is also the clearest written description of the default lists.

    I1.8

    hugetlb, and recognising a cgroup v1 node in three seconds

    Why it matters

    Two loose ends, both of which you will meet on somebody else's machine rather than your own. Huge pages are the clearest example of a resource that cannot be throttled — you get them or you fail — and cgroup v1 is the layout half of what you learned in B7 does not apply to. Neither is deep; both are expensive to not know.

    The concept

    Huge pages are memory mapped in 2 MB or 1 GB units instead of the usual 4 KB. The benefit is not the size but the TLB: a database with a 64 GB buffer pool needs sixteen million 4 KB translations and only thirty-two thousand 2 MB ones, and the difference in cache misses is measurable. This is why real database deployments ask for them.

    The controller — hugetlb.2MB.max, hugetlb.1GB.max and their .current counterparts — limits how many a cgroup may hold. What makes it pedagogically useful is that huge pages are a countable, non-compressible resource. You cannot be throttled into having fewer of them the way you can be throttled into less CPU. The pool is reserved at boot or by a sysctl, it is either big enough or it is not, and a workload that asks for huge pages and cannot get them fails at startup with an allocation error rather than degrading under load. That failure timing is the whole reason to know the file exists.

    Cgroup v1 is the other loose end. You will not meet it on 24.04, and you will meet it on a long-lived node someone stood up years ago. The differences that matter:

     v2 (unified)v1 (legacy)
    Hierarchyone tree, all controllersone tree per controller, mounted separately
    A process's cgroupone patha different path per controller
    Enabling controllerscgroup.subtree_controlno equivalent — mount it or don't
    Memory limit filememory.maxmemory.limit_in_bytes
    Filesystem typecgroup2fstmpfs with cgroup mounts beneath

    The three-second test is stat -fc %T /sys/fs/cgroup, and the confirming detail is the shape of /proc/self/cgroup: a single 0::/path line means unified v2; several numbered lines naming controllers means v1 or hybrid.

    Lab
    1. Look for the hugetlb files and find them missing, which is the ordinary state. The controller exists but is not enabled in the root's subtree.

      Two page sizes, because x86-64 supports both. A limit of max is unlimited — but see the next step for why that is not the same as "available".

cat /proc/self/cgroup
      cgroup2fs
cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime,nsdelegate,memory_recursiveprot)
0::/user.slice/user-1000.slice/session-191.scope

      On a v1 or hybrid host the first line reads tmpfs, and /proc/self/cgroup has one numbered line per controller — 12:memory:/…, 11:cpu,cpuacct:/… and so on. Once you have seen both, you will never need to look twice.

    Verify

    stat -fc %T /sys/fs/cgroup prints cgroup2fs and /proc/self/cgroup is a single 0:: line. You enabled hugetlb in the root subtree and the files appeared, and you can say why a hugetlb limit of max does not mean a workload will get any.

    Gotchas

    Do not leave +hugetlb enabled if you did not need it — writing to cgroup.subtree_control on the root affects every service on the machine, and although enabling a controller is harmless, the habit of casually editing the root cgroup is not. Remove it with echo "-hugetlb" > /sys/fs/cgroup/cgroup.subtree_control.

    A cgroup directory cannot be removed while any process is in it, and rmdir reports EBUSY rather than saying so. cat <cg>/cgroup.procs lists the holdouts. Every lab in this group ends with a rmdir that will fail if you skipped a kill.

    Do not spend long on v1. Learn the two tells, learn that memory.limit_in_bytes is v1's memory.max, and move on. The reason to recognise it is so that when someone's runbook does not work on your machine you know instantly that it was written for a different layout, rather than concluding the runbook is wrong.

    Huge pages are a first-class Kubernetes resource — a pod requests hugepages-2Mi alongside cpu and memory, and the scheduler treats it as countable, exactly like the kernel does. There is no "huge page throttling" because there cannot be. If the node's pool is exhausted, the pod stays Pending.

    The cgroup version matters to Kubernetes too: the kubelet's cgroupDriver must match the one the container runtime uses (systemd on any modern install), and a mismatch produces pods that start and then behave strangely under memory pressure. See W1.4 — the kubelet, containerd and the cgroup driver, which is the single most common kubeadm-era misconfiguration this module gives you the background to understand.
