Intermediate track final — 30 questions + 8 tasks · 90 minutes · pass ≥ 66/100

Part A is 30 recall questions worth one point each; Part B is 8 hands-on tasks worth 70 points, all run on the throwaway sandbox VM. Every recall question names the module that taught it, so a wrong answer points at a page rather than at a fact — and the instruction that matters is to re-read that module, not the answer. Do not open the solutions page until the timer rings.

90:00 The countdown survives page reloads — start it once and work.
Before you start
  1. Work on a clean sandbox VM — the same one every module in this track has used. Several tasks change system state; a snapshot is cheap insurance if you have one.
  2. Answer files go exactly where each task says, under ~/final/ on the sandbox. A correct result in the wrong path scores zero — the same rule the CKA applies.
  3. Part A first, from memory, writing answers into ~/final/partA.txt as numbered lines. No looking anything up; a blank is worth the same as a wrong answer and takes less time.
  4. Then Part B. First pass ≤8 minutes per task; flag and skip anything sticky, second pass by points. Verify every task with its own verification line before calling it done.
  5. When the timer rings: hands off, then grade honestly against the solutions page, which carries a per-task rubric. 66 points passes.

Part A — recall (30 × 1 pt)

  1. Name the toolchain difference between this track and the beginner track: which two Multipass VMs does the intermediate track use, and why did I1 and I2 not need the second one? I0
  2. A container's user namespace maps uid 0 inside to a non-zero uid outside. What kernel record makes that mapping possible, and why does the container's own ps still report uid 0? I1
  3. Name the eBPF-based mechanism that replaced the old whitelist-style device cgroup controller, and what capability it checks per access rather than per rule. I1
  4. List the six top-level keys a bare runc spec bundle's config.json has, and name the one directory a bundle absolutely cannot run without. I2
  5. What does ociVersion actually pin, and what happened when the same bundle was run under runc 1.5.1 versus crun 1.14.1 at spec version 1.1.0? I2
  6. State the OCI runtime spec's own three lifecycle operations in order, and which of them a runc run actually performs internally. I2
  7. runc's nsexec does its work in three stages, not two. Why does creating a PID namespace force the extra stage? I3
  8. Where does runc re-exec itself from before entering the new namespaces, and what CVE does that defend against? I3
  9. runc update changes a running container's limits. Where does that change get written, and what happens to it the next time the container is recreated from its bundle? I3
  10. Name the three parts of an OCI image and say, in one sentence each, what identifies and what verifies each one. I4
  11. What is a chain ID, how is it computed from a layer's diff IDs, and in which specification is it actually defined? I4
  12. An image's manifest is converted from OCI to Docker v2 schema 2. Which bytes move, and what happens to the manifest's own digest and any annotations it carried? I4
  13. Name the three hosts a single blob pull touches on Docker Hub, and what a HEAD versus a GET on the same manifest costs against the rate limit. I5
  14. Two registries are asked for a manifest type they don't hold. Name one real thing each is allowed to do instead, per the distribution spec's own wording. I5
  15. What is cross-repository blob mounting, and what did it measure as, compared to a full re-upload of the same layer? I5
  16. Explain why a Dockerfile comment does not invalidate the build cache but a chmod does. What is actually being hashed? I6
  17. What does --no-cache do to a BuildKit type=cache mount, and what happens on the very next ordinary build afterward? I6
  18. Draw the process lineage from containerd to a running workload. Whose child is the shim really, and why does that answer explain why a containerd restart doesn't kill anything? I7
  19. What replaced the old per-task address file under a 2.x task directory, and what protocol does the shim actually speak over that socket? I7
  20. A container's snapshot is deleted while its content blob remains. Which of the three storage layers (content, snapshot, an active mount) has no upstream to rebuild from if lost, and which two do? I7
  21. Name the four CRI calls, in order, that create and start a single container inside a pod, and say which of them the network attachment happens inside. I8
  22. What holds a pod's network, IPC and UTS namespaces open, and is that the same thing the pod's app containers actually join by path? I8
  23. A memory limit update through UpdateContainerResources shrinks a container below its current usage. What does the call return, and what happens two seconds later? I8
  24. Recite the CNI contract's five (or six, counting GC) operations, and say which channel — stdin, environment, or stdout — each of a plugin's inputs and its result travel over. I9
  25. A CNI ADD fails partway through. What state can it leave behind, and what error does the very next ADD attempt report because of it? I9
  26. Of the ten reference CNI plugins, how many implement the GC operation, and what does that mean for a stale IPAM reservation from a container that no longer exists? I9
  27. What is the default mount propagation for a bare runc bundle, and how does that differ from what a pod gets by default in Kubernetes? I10
  28. In CSI's call ordering, what happens if a client calls NodePublishVolume before NodeStageVolume, and is NodeUnstageVolume reference-counted the same way? I10
  29. A container root process without CAP_DAC_OVERRIDE tries to create a file in a uid-1000 directory. What happens, and which array in the OCI spec's capability sets is the one that actually matters for a root process? I11
  30. The container-to-log path is four hops. Name them in order, and say which hop's descriptor is the one that must be closed to actually free a deleted log's disk space. I12

Part B — practical (8 tasks · 70 pts)

Task 1 Write a bundle by hand and run it with runc

OCI runtime spec & runc · I2, I38 pts

Under ~/final/bundle/, build a runnable OCI bundle from scratch — no runc spec shortcut for the parts being tested:

  • A minimal rootfs of your own assembly (busybox or an unpacked image layer), a hand-edited config.json with a working directory of /final, one environment variable, and a memory limit of 64 MiB.
  • Run it with runc run, prove the working directory, environment variable and memory limit all took effect from inside.
  • Save runc state <id>'s output to ~/final/t1-state.json.
Verify:  jq -r '.status' ~/final/t1-state.json   # running, before you stop it

Task 2 Pull a manifest with curl and select a platform out of an index

OCI image & distribution specs · I4, I59 pts

Using nothing but curl and jq (no docker, ctr or skopeo for the pull itself) against Docker Hub:

  • Get an anonymous pull token, fetch the index for alpine:3.21, and select the linux/arm64 manifest — skipping any attestation manifests in the index.
  • From that manifest, fetch the config blob and print its architecture field to confirm it really is arm64.
  • Save the index to ~/final/t2-index.json and the selected manifest's digest to ~/final/t2-digest.txt.
Verify:  cat ~/final/t2-digest.txt   # a sha256:... digest that appears in t2-index.json

Task 3 Build a multi-stage image and explain its layers

Building images · I4, I68 pts

Write a multi-stage Dockerfile in ~/final/build/ — a build stage that produces one file of your own content, and a minimal final stage that copies only that file in:

  • Build it, then show that the final image's layer count is smaller than the build stage's own layer count would have been alone.
  • Identify which layer in the final image is the copied file, by inspecting history against the layers list.
  • Save the final image's history (with empty_layer flags visible) to ~/final/t3-history.json.
Verify:  jq '[.[] | select(.empty_layer!=true)] | length' ~/final/t3-history.json

Task 4 Drive a pod sandbox and container through crictl

containerd & CRI · I7, I89 pts

Using crictl directly (no Kubernetes, no kubelet):

  • Start a pod sandbox and one container inside it with shareProcessNamespace behaviour — the container's own ps must show the sandbox process, not just itself.
  • Prove the container joins the sandbox's network namespace by path, not by an independent namespace of its own.
  • Save the container's generated OCI config's linux.namespaces array to ~/final/t4-namespaces.json.
Verify:  jq -r '.[] | select(.type=="network") | .path' ~/final/t4-namespaces.json

Task 5 Drive a CNI plugin by hand and prove the teardown left nothing

CNI · I910 pts

Using cnitool and the reference bridge + host-local plugins against a network namespace you create yourself:

  • ADD a namespace onto the network, capturing the result JSON.
  • DEL it cleanly, then prove nothing was left behind: no leftover veth on the host, no IPAM reservation file for the address that was freed, and no NAT rule still referencing it.
  • Save the three verification commands' output to ~/final/t5-teardown.txt.
Verify:  grep -c . ~/final/t5-teardown.txt   # three non-empty proofs, all clean

Task 6 Attach and release a volume, CSI-style

Container storage & CSI · I108 pts

Build a named volume on a loop-mounted filesystem under ~/final/vol/, and attach it into a running container by rewriting its bundle's mount list — mirroring the stage/publish split CSI itself uses:

  • "Stage" the volume (make the device ready on the node) as a step separate from "publish" (bind it into the container), and show that a second container can also publish the same staged volume.
  • Prove the volume refuses to be removed while any container still references it.
  • Save the mount table entry proving the bind is live to ~/final/t6-mount.txt.
Verify:  grep -c final/vol ~/final/t6-mount.txt   # at least 1

Task 7 Produce and verify a signature

Supply chain security · I119 pts

Sign an image you control with cosign (keyless is fine, or a local key pair) and push it to a registry you can reach:

  • Verify the signature succeeds against the correct image digest.
  • Re-push the same tag pointing at different content, then show that verifying by tag now behaves differently from verifying by digest — and say in one sentence why.
  • Save both verification attempts' output to ~/final/t7-verify.txt.
Verify:  grep -c 'Verified OK\|no signatures found\|no matching signatures' ~/final/t7-verify.txt

Task 8 Read a container's resource usage from the cgroup files

Observability · I129 pts

Start a container that allocates a known amount of memory and burns a bounded amount of CPU under a quota:

  • Read its CPU and memory usage straight from the cgroup v2 files (cpu.stat, memory.current, memory.stat), computing a CPU percentage by hand from two samples.
  • Reconcile your hand-computed numbers against crictl stats for the same container and explain any difference you find, in particular between page-cache-inflated memory.current and what a monitoring tool actually reports.
  • Save both the raw cgroup readings and the reconciliation to ~/final/t8-metrics.txt.
Verify:  grep -c 'memory.current\|workingSet\|cpu.stat' ~/final/t8-metrics.txt   # at least 3
When the timer rings
  1. Stop. Grade Part A one point per correct answer — partial credit only where the question asks for a list and you got most of it.
  2. Grade Part B with the per-task rubric on the solutions page; each task's points are all-or-most-or-nothing, and the verification command decides.
  3. 66/100 passes. Below that, the useful move is not to retake it — it is to re-read the modules behind the specific things you missed, then retake it a week later.
