Intermediate final — solutions & grading

Grade yourself honestly: the score is only useful as a comparison against the same rubric later. Where an answer is wrong, the module tag beside it is the instruction — re-read that module's lesson, not this answer. An answer you have memorised from this page is worth nothing on a real machine.

Part A — answers (30 × 1 pt)

  1. The intermediate track's spec calls for a second VM, buildbox, for image-building work — but I1 needs no container tooling at all and I2 needs only runc/crun and one image pull, so neither justified standing it up. Both were authored on sandbox alone, which already carries the full toolchain. I0
  2. /proc/<pid>/uid_map (and gid_map) record the mapping from in-namespace ids to host ids. A process's credentials are stored in the namespace's own numbering, so a process that is uid 100000 on the host genuinely is uid 0 inside its own user namespace — ps is reporting the truth from where it's asked, not translating anything. I1
  3. The eBPF device cgroup controller (a BPF_CGROUP_DEVICE program attached to the cgroup). It checks the major/minor/type/access-mode of each device access at the point of the syscall, rather than matching against a static allow/deny list the old whitelist controller used. I1
  4. ociVersion, process, root, hostname, mounts, linux — six keys, no hooks, no annotations. The bundle cannot run without rootfs (the directory root.path points at). I2
  5. It pins the schema version of config.json itself — nothing about runtime behaviour. At spec version 1.1.0 the same bundle under runc 1.5.1 and crun 1.14.1 differed only in two namespace inode numbers (an implementation detail); crun additionally refuses any bundle declaring ociVersion ≥ 1.2.0 outright, where runc does not. I2
  6. create, start, kill, delete (plus a query, state). runc run performs create and start internally in one call. I2
  7. unshare(CLONE_NEWPID) does not move the calling process into the new PID namespace — only children forked after the call land in it. Getting a process running as PID 1 inside the new namespace therefore needs an extra clone(), which is the third stage. I3
  8. From /proc/self/fd/N, a sealed clone of its own binary made by libcontainer's exeseal (overlayfs preferred, then memfd_create, then O_TMPFILE). It defends against CVE-2019-5736, a container-breakout via overwriting /proc/self/exe. I3
  9. To the kernel only — neither the bundle's config.json nor state.json records the change. Recreating the container from its bundle silently reverts it. I3
  10. Manifest: content-addressed by its own digest, references the config and every layer by digest — it is the composition. Config: runtime metadata (env, entrypoint, rootfs.diff_ids) whose own digest is what the manifest's config.digest verifies against. Layers: tar+gzip diffs, each verified on fetch against its own compressed digest. I4
  11. chainID[0] = diff_ids[0]; chainID[i] = sha256("<chainID[i-1]> <diff_ids[i]>") — one space, both operands keeping their sha256: prefix. It is not in the OCI image spec at all; it is a containerd construction built on top of the spec's ordering guarantee. I4
  12. No layer or config bytes move — the same blobs back both manifests. Exactly three media-type strings and the annotations block change; the manifest's own digest changes because its content changed, and annotations are dropped entirely, since Docker v2 schema 2 has nowhere to put them. I4
  13. The registry, the auth/token service, and a CDN edge for blobs (Docker Hub's is CloudFront). A HEAD does not move the pull-rate-limit counter; a GET does — which is why re-resolving a tag (imagePullPolicy: Always when the image is already local) is effectively free. I5
  14. registry:2 answers a mismatched request with a plain 404 MANIFEST_UNKNOWN, or — if it holds the content in a different schema — silently down-converts and returns 200 with a different Docker-Content-Digest for the same tag. Docker Hub instead just ignores the requested type and returns what it has (often an OCI index) regardless of what was asked for. I5
  15. Cross-repository blob mounting: the registry links an existing blob into a new repository by reference instead of re-uploading it. Measured: a 30 MB layer went from 5.552 s (full push) to 0.092 s (mount). I5
  16. BuildKit hashes file content, not comments and not mtime — a comment never becomes an LLB vertex at all, and an unchanged-content touch doesn't invalidate the cache either. chmod changes the file's own metadata, which is part of what gets hashed, so it does invalidate. I6
  17. It empties the type=cache mount's contents permanently — not simulated. Four accumulated lines collapsed to one on the --no-cache build, and the very next ordinary build then saw only two lines, starting fresh from the emptied cache rather than the five that had actually accumulated. I6
  18. kubelet → containerd → shim → (transient) runc → workload. The shim's parent is PID 1, not containerd — containerd starts it detached so it reparents to systemd immediately. That detachment is exactly why restarting containerd kills nothing: it reconnects to already-running shims over their sockets rather than owning the processes. I7
  19. bootstrap.json ({version, address, protocol}, with address a real path under /run/containerd/s/, not an abstract socket). The shim speaks ttrpc over it. I7
  20. A running container's active snapshot has no upstream — if lost, it is simply gone. The content store does (it is re-fetchable from the registry), and a committed snapshot does too (it is re-derivable by unpacking the content store again). I7
  21. RunPodSandbox, PullImage, CreateContainer, StartContainer. Network attachment (the CNI ADD) happens inside RunPodSandbox, before any container exists. I8
  22. A bind mount at /var/run/netns/cni-<uuid>, pinned before pause even starts (CNI ADD runs first) — not the pause process itself. IPC and UTS genuinely are held via /proc/<pause-pid>/ns/…. App containers join the network namespace by that same path, and IPC/UTS by pause's /proc path. I8
  23. It returns success. About two seconds later the container is OOMKilled (exit 137) — the runtime's contract is only not to restart it artificially; it says nothing about the kernel's own OOM killer. I9
  24. ADD, DEL, CHECK, GC, VERSION — the spec's own text says "CNI defines 5 operations", with STATUS defined alongside them. Configuration arrives on stdin; per-invocation parameters (container ID, netns, interface name, capability args) arrive via environment variables (CNI_*); the result is printed as JSON to stdout. I9
  25. It can leave eth0 already created inside the namespace and the bridge already wired. The retry then fails with "container veth name (\"eth0\") … already exists" — a message that names neither the original failure nor the fact that this is a retry. I9
  26. None of the ten reference plugins implement GC — host-local's own source wires up only cmdAdd/cmdDel/cmdCheck. GC is a well-formed no-op, so a stale reservation from a vanished container is never reclaimed automatically — the field repair really is deleting the reservation file by hand. I9
  27. A bare bundle's default is master:1 (slave) — host-to-container propagation works out of the box. Kubernetes' default mountPropagation: None asks explicitly for rprivate instead, so a pod does not get that same visibility unless it opts in with HostToContainer or Bidirectional. I10
  28. NodePublishVolume before NodeStageVolume is refused with FAILED_PRECONDITION and creates zero mounts. NodeUnstageVolume is refcounted — it returns INTERNAL and names the still-live publish paths while any publication remains. DeleteVolume, by contrast, does not check for live mounts at all. I10
  29. Creating a new file in a directory owned by uid 1000 fails without CAP_DAC_OVERRIDE — but appending to an existing root-owned file still works, since root already satisfies the owner check there and needs no override. The array that actually matters for a root process is the bounding set: the kernel recomputes effective′ = permitted′ = bounding at execve, so only bounding is load-bearing. I11
  30. Workload's fd 1 (a pipe) → the shim (reads the pipe, writes into a <id>-stdout FIFO) → containerd (reads that FIFO, writes the log file). Containerd's own descriptor on the log file is the one that must close before a deleted log's disk space is actually freed — the shim holds no descriptor on the log file at all. I12

Part B — solutions & rubric (70 pts)

Task 1 Write a bundle by hand and run it with runc

OCI runtime spec & runc · I2, I38 pts
mkdir -p ~/final/bundle/rootfs/bin ~/final/bundle/rootfs/final
cp /usr/bin/busybox ~/final/bundle/rootfs/bin/busybox
ln -sf busybox ~/final/bundle/rootfs/bin/sh
cd ~/final/bundle && runc spec
python3 - config.json <<'PY'
import json
c = json.load(open("config.json"))
c["process"]["args"] = ["/bin/sh", "-c", "pwd; echo $GREETING; cat /sys/fs/cgroup/memory.max"]
c["process"]["cwd"] = "/final"
c["process"]["env"].append("GREETING=hello-final")
c["process"]["terminal"] = False
c["linux"]["resources"] = {"memory": {"limit": 67108864}}
json.dump(c, open("config.json", "w"))
PY
sudo runc run t1 | tee ~/final/t1-output.txt
sudo runc state t1 > ~/final/t1-state.json 2>/dev/null || true
Verify
cat ~/final/t1-output.txt   # /final, hello-final, 67108864
CriterionPts
Bundle built by hand (own rootfs, edited config.json — not left at defaults)2
Working directory /final confirmed from inside2
Environment variable confirmed from inside2
64 MiB memory limit confirmed via memory.max1
t1-state.json captured while running1

Common miss: capturing runc state after the container has already exited — a one-shot command exits the moment its process does, so the state must be captured from a second terminal or a command that sleeps.

Task 2 Pull a manifest with curl and select a platform out of an index

OCI image & distribution specs · I4, I59 pts
mkdir -p ~/final && cd ~/final
TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/alpine:pull" | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/vnd.oci.image.index.v1+json,application/vnd.docker.distribution.manifest.list.v2+json" \
  https://registry-1.docker.io/v2/library/alpine/manifests/3.21 | tee t2-index.json | \
  jq -r '.manifests[] | select(.platform.architecture=="arm64" and .platform.os=="linux" and (.annotations["vnd.docker.reference.type"]==null)) | .digest' \
  | tee t2-digest.txt
DIGEST=$(cat t2-digest.txt)
curl -s -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/vnd.oci.image.manifest.v1+json" \
  https://registry-1.docker.io/v2/library/alpine/manifests/$DIGEST | jq -r .config.digest > t2-config-digest.txt
CFGDIGEST=$(cat t2-config-digest.txt)
curl -s -H "Authorization: Bearer $TOKEN" \
  https://registry-1.docker.io/v2/library/alpine/blobs/$CFGDIGEST | jq -r .architecture
Verify
cat t2-digest.txt                    # sha256:...
grep -c "$(cat t2-digest.txt)" t2-index.json   # 1
CriterionPts
Anonymous token obtained and used, no docker/skopeo/ctr in the pull path2
Index fetched and saved2
Correct linux/arm64 manifest selected, skipping attestation entries3
Config blob's architecture confirmed as arm642

Common miss: not filtering out attestation manifests — a modern index carries one platform: unknown/unknown attestation entry per real platform, and a selector that only matches on architecture without also excluding those picks up nothing useful.

Task 3 Build a multi-stage image and explain its layers

Building images · I4, I68 pts
mkdir -p ~/final/build && cd ~/final/build
echo "built at $(date +%s)" > source.txt
cat > Dockerfile <<'EOF'
FROM alpine:3.21 AS builder
WORKDIR /work
COPY source.txt .
RUN sha256sum source.txt > source.sha256

FROM alpine:3.21
COPY --from=builder /work/source.sha256 /source.sha256
EOF
sudo nerdctl build -t final-multistage:v1 .
sudo nerdctl image history --format json final-multistage:v1 | jq -s . > ~/final/t3-history.json
jq '[.[] | select(.empty_layer!=true)] | length' ~/final/t3-history.json
Verify
jq '.[] | select(.created_by|test("source.sha256")?)' ~/final/t3-history.json
CriterionPts
Genuine multi-stage Dockerfile, build stage produces its own content3
Final image's real layer count smaller than a single-stage equivalent would be2
The copied file's layer correctly identified in history2
t3-history.json written and readable1

Common miss: assuming every Dockerfile instruction produces a layer — WORKDIR does (it goes through the filesystem-snapshot path even when the directory already exists), but a build-stage-only RUN whose output is never copied into the final stage contributes nothing to the final image's history at all.

Task 4 Drive a pod sandbox and container through crictl

containerd & CRI · I7, I89 pts
cat > ~/final/t4-pod.json <<'EOF'
{"metadata":{"name":"final-pod","namespace":"default","uid":"final-pod"},"linux":{}}
EOF
cat > ~/final/t4-ctr.json <<'EOF'
{"metadata":{"name":"final-ctr"},"image":{"image":"alpine:3.21"},
"command":["sleep","3600"],
"linux":{"namespaces":{"options":{"pid":0}}}}
EOF
sudo crictl pull alpine:3.21
POD=$(sudo crictl runp ~/final/t4-pod.json)
CTR=$(sudo crictl create $POD ~/final/t4-ctr.json ~/final/t4-pod.json)
sudo crictl start $CTR
sudo crictl exec $CTR ps
sudo crictl inspect $CTR | jq '.info.runtimeSpec.linux.namespaces' | tee ~/final/t4-namespaces.json
Verify
jq -r '.[] | select(.type=="network") | .path' ~/final/t4-namespaces.json   # /proc/<pause-pid>/ns/net
CriterionPts
Pod sandbox and container both created and started via crictl2
pid: 0 (POD-level) namespace option used — container's ps shows pause too3
Network namespace shown to be joined by path, not independent3
t4-namespaces.json written1

Common miss: setting namespace_options.pid on the wrong object — it belongs on the container config, not the pod config; the same field on the sandbox config parses but does nothing.

Task 5 Drive a CNI plugin by hand and prove the teardown left nothing

CNI · I910 pts
sudo mkdir -p /etc/final-cni/net.d
cat <<'EOF' | sudo tee /etc/final-cni/net.d/10-final.conflist
{"cniVersion":"1.0.0","name":"finalnet","plugins":[
  {"type":"bridge","bridge":"finalbr0","isGateway":true,"ipMasq":true,
   "ipam":{"type":"host-local","subnet":"10.77.0.0/24","dataDir":"/var/lib/final-ipam"}}
]}
EOF
sudo ip netns add finalns
export CNI_PATH=/opt/cni/bin NETCONFPATH=/etc/final-cni/net.d
sudo -E cnitool add finalnet /var/run/netns/finalns | tee ~/final/t5-add.json
sudo -E cnitool del finalnet /var/run/netns/finalns
{ echo "=== veth on host ==="; ip link show | grep -c veth || echo 0
  echo "=== ipam reservations ==="; ls /var/lib/final-ipam/finalnet/ 2>/dev/null | grep -v last_reserved || echo none
  echo "=== nat rules ==="; sudo iptables -t nat -S | grep -c 10.77.0 || echo 0
} | tee ~/final/t5-teardown.txt
sudo ip netns del finalns
Verify
cat ~/final/t5-teardown.txt
CriterionPts
ADD succeeds, returns an address2
DEL run before the namespace is destroyed (correct order)2
No leftover veth on the host2
No stale IPAM reservation file2
No stale NAT rule; file written2

Common miss: destroying the namespace before calling DEL — the bridge plugin reads the container's own address out of the namespace to release it, so once the namespace is gone DEL returns success while reclaiming nothing, and both the IPAM reservation and the NAT rule leak silently.

Task 6 Attach and release a volume, CSI-style

Container storage & CSI · I108 pts
sudo mkdir -p ~/final/vol
sudo dd if=/dev/zero of=~/final/vol.img bs=1M count=200
sudo mkfs.ext4 -q ~/final/vol.img
STAGEDIR=~/final/vol/staged
sudo mkdir -p "$STAGEDIR"
sudo mount -o loop ~/final/vol.img "$STAGEDIR"     # "NodeStageVolume": ready on the node
findmnt -no SOURCE,TARGET "$STAGEDIR" > ~/final/t6-mount.txt
# "NodePublishVolume" x2: bind the staged volume into two different containers
sudo mkdir -p /run/containers/c1/final /run/containers/c2/final
sudo mount --bind "$STAGEDIR" /run/containers/c1/final
sudo mount --bind "$STAGEDIR" /run/containers/c2/final
findmnt -no SOURCE,TARGET /run/containers/c1/final >> ~/final/t6-mount.txt
# refuse to remove while referenced
sudo umount "$STAGEDIR" 2>&1 | tee -a ~/final/t6-mount.txt   # busy: still bind-mounted elsewhere
sudo umount /run/containers/c1/final /run/containers/c2/final
sudo umount "$STAGEDIR"
Verify
grep -c final/vol ~/final/t6-mount.txt
CriterionPts
Stage step (loop mount) separate from publish step (bind mount)3
Volume published into two separate targets from the one staged source2
Unstage refused while a publish reference remains2
t6-mount.txt written1

Common miss: unmounting the staged loop device directly instead of each bind mount first — the kernel refuses with "target is busy" precisely because a publish reference still exists, which is the whole point CSI's separate calls exist to make explicit.

Task 7 Produce and verify a signature

Supply chain security · I119 pts
sudo nerdctl tag alpine:3.21 localhost:5000/final/signed:v1
sudo nerdctl push localhost:5000/final/signed:v1
cosign generate-key-pair
cosign sign --key cosign.key localhost:5000/final/signed:v1
cosign verify --key cosign.pub localhost:5000/final/signed:v1 | tee ~/final/t7-verify.txt
DIGEST=$(sudo nerdctl image inspect localhost:5000/final/signed:v1 --format '{{.RepoDigests}}')
# Move the tag to point at different content
sudo nerdctl tag busybox:1.36 localhost:5000/final/signed:v1
sudo nerdctl push localhost:5000/final/signed:v1
echo "--- verify by TAG (now wrong content) ---" | tee -a ~/final/t7-verify.txt
cosign verify --key cosign.pub localhost:5000/final/signed:v1 2>&1 | tee -a ~/final/t7-verify.txt
echo "--- verify by DIGEST (still the signed content) ---" | tee -a ~/final/t7-verify.txt
cosign verify --key cosign.pub "localhost:5000/final/signed@$DIGEST" 2>&1 | tee -a ~/final/t7-verify.txt
Verify
grep -c 'Verified OK\|no matching signatures\|no signatures found' ~/final/t7-verify.txt
CriterionPts
Image signed and a first verification succeeds3
Tag re-pushed against different content2
Verify-by-tag now fails or reports no matching signature2
Verify-by-digest still succeeds, and the one-sentence reason is correct (a digest is immutable content addressing; a tag is a mutable pointer the registry is free to move)2

Common miss: using cosign triangulate to find the signature — it is deprecated and prints a stale .sig-suffixed tag path; modern cosign stores signatures as OCI referrers under a sha256-<hex> tag with no .sig suffix, and cosign verify/cosign tree resolve it correctly on their own.

Task 8 Read a container's resource usage from the cgroup files

Observability · I129 pts
sudo crictl runp ~/final/t4-pod.json > ~/final/t8-pod-id.txt   # or reuse an existing pod
POD=$(cat ~/final/t8-pod-id.txt)
cat > ~/final/t8-ctr.json <<'EOF'
{"metadata":{"name":"final-metrics"},"image":{"image":"alpine:3.21"},
"command":["sh","-c","head -c 33554432 /dev/urandom > /tmp/x; while :; do :; done"],
"linux":{"resources":{"cpu_quota":20000,"cpu_period":100000}}}
EOF
CTR=$(sudo crictl create $POD ~/final/t8-ctr.json ~/final/t4-pod.json)
sudo crictl start $CTR
CGPATH=$(sudo crictl inspect $CTR | jq -r '.info.runtimeSpec.linux.cgroupsPath')
{
  echo "=== sample 1 ==="; cat "/sys/fs/cgroup${CGPATH}/cpu.stat"; date +%s%N
  sleep 5
  echo "=== sample 2 ==="; cat "/sys/fs/cgroup${CGPATH}/cpu.stat"; date +%s%N
  echo "=== memory ==="; cat "/sys/fs/cgroup${CGPATH}/memory.current"
  grep -E '^(anon|file)' "/sys/fs/cgroup${CGPATH}/memory.stat"
  echo "=== crictl stats ==="; sudo crictl stats $CTR
} | tee ~/final/t8-metrics.txt
Verify
grep -c 'memory.current\|workingSet\|cpu.stat' ~/final/t8-metrics.txt
CriterionPts
Two cpu.stat samples taken with a known interval between them2
CPU percentage computed by hand from usage_usec delta ÷ wall-clock delta3
Reconciled against crictl stats, difference explained (windowed vs point-in-time, or working set vs raw usage)3
t8-metrics.txt written1

Common miss: reading memory.current and reporting it directly as "the container's memory usage" — page cache from files the container wrote (like the 32 MiB write above) inflates memory.current far past actual working memory; crictl stats' figure is workingSetBytes, computed as usage minus inactive_file, and the two numbers can differ by two orders of magnitude on the same container.

Scoring

Total10066 to pass

A pass here means the intermediate track has done its job: you can build and run an OCI bundle by hand, explain and pull an image without a client, drive containerd through the CRI, write and tear down a CNI attachment cleanly, stage and publish storage the way CSI does, sign and verify supply-chain provenance, and read a container's true resource usage from the same files the kernel itself keeps. That is the entry condition for the Advanced track, which assumes every one of those things is now familiar rather than new.

Below 66, the useful move is not an immediate retake. Re-read the modules behind the specific misses, redo those modules' mini projects, and come back to this page in a week — a second score against the same rubric is the only comparison that means anything.
