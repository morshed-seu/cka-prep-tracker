      Containers & runtimes

      The Beginner track ends with minibox — about eighty lines of bash that runs a process on an overlay filesystem, in five namespaces, inside a cgroup, with dropped capabilities, on a bridge with NAT and DNS, supervised by systemd. That is, honestly, a container runtime. The Advanced track begins with a cluster where containerd, runc, CNI plugins and images already exist, and teaches Kubernetes on top of them. This track is the decade in between.

      Its thesis is the sequel to the beginner track's. That one argued that Kubernetes invented very little; it composes decades-old operating-system technology. This one argues that the container ecosystem added almost no mechanism — it added contracts. runc does what your minibox already did; what it adds is config.json, a schema anyone can generate. containerd's snapshotter mounts the same overlayfs you mounted by hand; what it adds is a content-addressed store and an API. CNI does nothing your networking script didn't; what it adds is "exec a binary, JSON on stdin, JSON on stdout."

      So every module runs the same arc: you already built this → here is the spec that says how everyone agrees to build it → here is the real implementation obeying that spec → now break it. Every conceptual lesson carries a “What the spec actually says” block quoting the normative text, and the beginner track's “Where this shows up in Kubernetes” block linking forward. Checkboxes save automatically in this browser, in the same store as the other two trackers.

      • Under the hood

        Try pip install requests without the venv on 24.04 and you get error: externally-managed-environment. That is PEP 668: the distro marks its Python as owned by apt, because a pip that overwrites a system library can brick tools written in Python — on Ubuntu, that includes parts of the installer and cloud-init. The escape hatch --break-system-packages exists and is named honestly; use the venv instead. This track writes real programs (an image parser, a registry client, a shim), so you will be in it a lot.

      • Under the hood

      The toolchain

      • Under the hood

        Noble's own containerd package is the 1.7 line, which predates almost everything this track teaches about configuration: 2.0 moved to config version = 3, renamed the CRI plugin's path to io.containerd.cri.v1.runtime (plus a separate …images plugin), and dropped several 1.x compatibility shims outright. Learning 1.7's layout and then meeting 2.x on a real node is the worst of both. Pinning also buys reproducibility in the other direction: containerd now ships minor releases on a roughly four-month cadence, so "latest" means something different depending on the month you read this.

      • Under the hood

        The map, in one line: kubelet → (CRI) → containerd → (shim) → runc → your process, with images arriving from a registry over HTTP and the network attached by a CNI plugin. The clients you just installed each cut into that chain at a different height, and confusing them is the classic beginner error. ctr is containerd's own low-level debug tool and speaks its native API. crictl speaks CRI — the same interface the kubelet uses, so it sees pods and sandboxes. nerdctl is a Docker-compatible face on the same daemon. runc is below all of them and knows nothing about images or networks at all. Three of them can be pointed at the same containerd and show you three different worlds.

      • Under the hood

        ctr version printing a client and a server version separately is your first sight of the architecture: ctr is a thin client over a unix socket, and the thing that actually holds your containers is a long-lived daemon. That split is the entire subject of I7 — including the surprise that killing the daemon does not kill the containers. Meanwhile runc has no server at all, which is why I3 can operate containers with no daemon in the picture whatsoever.

      How to read a spec

      • Under the hood

        These are short documents — the runtime spec is a handful of Markdown files you could read on a train — and they are the primary source for arguments that otherwise get settled by folklore. Two habits pay off immediately. First, MAY is where portability bugs live: if a spec says a runtime MAY do something, code that assumes it will is broken on the runtime that doesn't. Second, "the spec is silent on this" is a real and frequent answer — the runtime spec says nothing about images, networking, logging or naming, and every one of those silences is a later module of this track. Knowing that a behaviour is unspecified is more useful than guessing which implementation's behaviour is the standard one.

      Isolation, the parts we skipped

      • Under the hood

        The second write fails with EPERM, always: each map file may be written exactly once, and that single-write rule is what makes the whole feature safe to hand to unprivileged users — a process cannot widen its own mapping after the fact. The file is three columns: the first ID inside the namespace, the ID it corresponds to outside, and how many consecutive IDs the range covers. So 0 100000 65536 means "uid 0 in here is uid 100000 out there". Nothing about the kernel's permission checks changes; only the translation does.

      • Under the hood

        An unprivileged process can only ever map its own uid, one line, one ID. Mapping a whole range needs CAP_SETUID in the parent namespace, which is why newuidmap is setuid-root — and why it refuses to map anything outside the range the administrator granted you in /etc/subuid. That is the entire allocation model behind rootless containers: the distro hands each user 65,536 IDs at install time, and the container's "root" is one of them. The file you just created is owned by uid 100000 (or wherever your range starts) on the host, which is precisely what "root inside, nobody outside" means — and precisely why an escaped rootless container lands as a user with no privileges rather than as uid 0.

      • Under the hood

        Namespaces are referenced by file descriptor, not by name, and that single design decision explains several things at once. A namespace stays alive as long as some fd or process refers to it, which is what "pinning" with a bind mount does. It can be passed between processes over a unix socket. And it is the actual mechanic under kubectl exec: nothing "enters the pod" — a process on the node opens the sandbox's namespace fds and setnses into them, one type at a time. clone3 matters here because creating a process already inside its namespaces avoids a window where a half-configured process exists in the parent's — a window that unshare-then-fork genuinely has.

      • Under the hood

        This is the single biggest obstacle to the rootless labs, and it deserves an explanation rather than a sudo. Unprivileged user namespaces have been a rich source of kernel privilege escalations, because they hand ordinary users CAP_SYS_ADMIN inside the namespace and thereby reachable surface (mounts, netfilter, filesystem drivers) that unprivileged code could never touch before. Ubuntu's answer was not to disable the feature but to gate it behind AppArmor, so a packaged application that legitimately needs it ships a profile and everything else is denied by default. Flipping the sysctl globally "to make the lab work" removes that mitigation for every process on the box — fine on a throwaway VM, absolutely not a recommendation to carry to a node.

      Resource control, the parts we skipped

      • Under the hood

        PSI answers a question load average cannot: how much time was lost to waiting? Load average counts runnable tasks, so a box with 40 threads on 40 CPUs and a box with 40 threads on 4 CPUs can report similar-looking numbers while one is healthy and the other is dying. PSI instead reports the percentage of wall time in which at least one task was stalled on a resource (some) and in which every runnable task was stalled, so nothing useful happened at all (full). full is the number that means real damage. This is also the mechanism behind modern OOM-avoidance daemons and the honest way to answer "is this pod slow because it is throttled, or because it is idle?".

      • Under the hood

        Under cgroup v2, cpuset requires +cpuset in the parent's cgroup.subtree_control like any other controller, and an empty cpuset.cpus means "inherit", not "none". The reason it exists alongside CPU bandwidth limiting is NUMA: on a multi-socket machine, memory attached to another socket costs meaningfully more to reach, so a latency-sensitive workload wants its threads and its pages on the same node — that is what cpuset.mems is for. Kubernetes exposes this as the CPU Manager's static policy, which hands Guaranteed pods with whole-number CPU requests exclusive cores by writing exactly this file. The failure mode is memorable and lands in this module's drill: a workload pinned to a busy core looks throttled but has no throttling in cpu.stat.

      • Under the hood

        This is the biggest v1→v2 surprise, and it breaks a lot of old scripts and old blog posts. In v1 the device controller was an interface file you wrote rules into; in v2 the kernel dropped it entirely and the equivalent is an eBPF program attached to the cgroup, invoked on every device-node open, returning allow or deny. The consequence to internalise: device policy is no longer readable by cat. You cannot inspect it with the filesystem — you need bpftool, or you have to read the runtime's config.json, which is why I2's linux.devices and linux.resources.devices fields are the practical source of truth for what a container may open.

      • Under the hood

        The three-second test: stat -fc %T /sys/fs/cgroup prints cgroup2fs on a pure v2 host and tmpfs on v1 or hybrid. It matters because v1 has no unified hierarchy — each controller mounts separately, a process has a different path per controller, and there is no cgroup.subtree_control, so half of what B7 taught you has a different shape there. You will not meet v1 on 24.04, but you will meet it on a long-lived node someone stood up years ago, and the tell is that memory.max does not exist while memory.limit_in_bytes does. Huge pages are worth knowing for a different reason: they are the clearest example of a resource Kubernetes treats as a countable resource rather than a compressible one — you cannot be throttled into fewer huge pages, you simply fail to get them.

      Filtering syscalls for real

      • Under the hood

        Recognising this signature is the whole point of the checkpoint, because in the wild it arrives with no explanation attached. A process dies instantly, the logs say nothing, and the only evidence is a strange exit code and the fact that strace shows the syscall never returning. no_new_privs is mandatory before an unprivileged process may install a filter, and for a good reason: without it you could attach a filter that neuters a security-relevant syscall and then exec a setuid binary into the trap. Note also that a filter is inherited across fork and exec and can never be removed — one-way, like the uid_map rule, and for the same reason.

      • Under the hood

        Every profile worth deploying is an allow-list, for the same reason firewalls default-deny: a deny-list protects you only against the attacks someone already thought of, and the kernel adds syscalls every release. The subtlety is the action. Returning ENOSYS or EPERM (SCMP_ACT_ERRNO) is usually kinder than killing, because well-written software falls back — this is exactly how the default profile blocks newer syscalls without breaking a libc that probes for them. But it also produces the confusing bug where a program silently takes a slow path for years. SCMP_ACT_LOG exists so you can build an allow-list empirically: run the workload, log everything, then permit what it actually used.

      Networking, the parts we skipped

      • Under the hood

        A veth pair, from B9, connects two kernel endpoints. TUN/TAP is stranger and more powerful: it is a network interface whose other end is a file descriptor held by an ordinary program. Whatever the kernel routes into tun0, your process reads; whatever your process writes, the kernel treats as having arrived from the network. That is the whole mechanism behind every userspace VPN, every rootless-container network stack (which cannot create veths or bridges, because those need real privilege), and QEMU's networking. It is also the honest answer to "why is rootless networking slow?" — packets cross the user/kernel boundary twice more than they otherwise would.

      • Under the hood

        The arithmetic is 14 (inner Ethernet) + 8 (VXLAN) + 8 (UDP) + 20 (outer IPv4) = 50 bytes, so a 1500-byte underlay yields a 1450-byte overlay — which is exactly why Flannel's VXLAN backend gives pods an MTU of 1450 and why nobody should ever hand-write 1500 there. Get it wrong and you rebuild B8's MTU black hole from the inside: ARP works, ping works, the TLS handshake works, and then the first full-size response silently disappears, because the oversized packet needs fragmenting but carries DF, and the ICMP "fragmentation needed" that should tell the sender gets dropped by somebody's firewall. GRE is the same idea with a smaller header and no UDP encapsulation, which costs it the ability to traverse most load balancers. Hairpin mode is the adjacent trap: a bridge will not by default send a frame back out the port it arrived on, which is why a pod reaching its own Service address used to fail.

      I2 — What a container is, formally

      16 cp · ~6 h

      The hinge of the track. Your bash runtime's command-line flags become a JSON document that anyone's runtime can execute — and the moment that works, "container" stops being a vague word and becomes a two-file directory with a specification behind it.

      I0, I1, and the beginner track's B6 (namespaces), B7 (cgroups v2) and B14 (minibox). Authored against OCI runtime-spec v1.3.0.

      The bundle

      • Under the hood

        The minimalism is the point. Everything you might expect to be part of "a container" — the image it came from, its name, its network, where its logs go, how it is restarted — is outside this contract. The runtime spec deliberately standardises only the last step: given a directory laid out this way, produce a running process with these properties. That narrowness is why the same runc serves Kubernetes, Docker, Podman and CI systems that share no other code, and it is why the rest of this track exists — each later module fills in one of the things a bundle deliberately does not say.

      • Under the hood

        Do this exercise honestly and the track's thesis lands on its own: there is essentially nothing in that file you have not already done with a flag or a shell command. linux.namespaces is your unshare; linux.resources is the cgroup files you wrote; process.capabilities is your capsh --drop; mounts is your mount -t proc line; root is your pivot_root. What the specification adds is not capability but agreement — a declarative document that another team's binary can execute identically, which is a thing eighty lines of bash can never be.

      • Under the hood

        Bundles are ephemeral build products, assembled seconds before use and deleted after — which is exactly why so few people have ever seen one, and why reading a real one is worth doing now. The interesting half is the merge: the image pre-declares some of this document (Env, Entrypoint, User, WorkingDir — I4's lesson), while the caller supplies the rest (namespaces to join, cgroup path, resource limits, mounts). A Kubernetes pod spec is, at the bottom of the stack, an opinionated way of filling in the caller's half of a config.json.

      config.json, field by field

      • Under the hood

        The five capability sets are B4's material arriving with consequences. The one that catches everybody: putting a capability in permitted and effective is not enough for it to survive an exec of a non-setuid binary — that needs ambient (and ambient requires the capability be in both permitted and inheritable). bounding is the ceiling nothing can exceed, and dropping from it is irreversible, so it is the set that actually constrains an attacker. noNewPrivileges is the same PR_SET_NO_NEW_PRIVS that I1's seccomp lesson required: with it set, no exec can ever gain privilege, which neutralises setuid binaries inside the container wholesale.

      • Under the hood

        root.path is resolved relative to the bundle directory, not the process's working directory, and the mismatch is this module's first drill fault — a genuinely confusing error because the path exists, just not from where the runtime looked. Read-only roots are worth the trouble: they turn a whole class of compromise into a no-op, and the standard pattern that makes them survivable is an emptyDir-shaped writable mount over /tmp and whatever state directory the application insists on. In Kubernetes this is readOnlyRootFilesystem, and it maps to precisely this one boolean.

      • Under the hood

        Two of these carry the actual isolation. Mounting a fresh proc is what makes the PID namespace visible — without it the container reads the host's process list through an inherited mount, which is the classic "my container can see every process on the node" misconfiguration. And devpts with newinstance gives the container its own pty numbering, so its /dev/pts/0 is not the host's; that is the mechanism a terminal in a container depends on, and it comes back in I3 when a console socket has to carry the pty master out. Mount order in the array is significant: they are applied in sequence, so a mount whose target lives under a later mount point disappears.

      • Under the hood

        You have just built a pod. That is not an analogy — it is the mechanism: a Kubernetes pod is a set of containers whose config.json files name the same namespace paths, which is why containers in a pod share an IP and can talk over localhost while keeping separate mount namespaces and separate filesystems. It also explains the pause container, which does nothing but exist so that something owns those namespaces and holds them open while application containers restart around it. And it explains this module's second drill fault: name a path whose owner has already exited, and the namespace is gone before you can join it.

      • Under the hood

        maskedPaths is the most educational list in the file. /proc/kcore is the machine's live memory as a file. /proc/sys/kernel/core_pattern is a value the kernel will happily execute on a crash — a famous container-escape primitive whenever it is writable. /sys/firmware exposes host hardware tables. Masking is done by bind-mounting /dev/null over the file (or an empty read-only tmpfs over the directory), which is why a masked path reads as empty rather than as denied. Note the shape of the whole section: resources is a spec-level renaming of files you already wrote by hand, while cgroupsPath is what lets an outside supervisor find the container's cgroup afterwards — the hook that makes per-container metrics possible at all.

      Lifecycle

      • Under the hood

        "Stopped but still existing" is the state that explains a surprising amount of day-to-day Kubernetes. A container's exit code, its final logs and its identity all outlive the process, because the record persists until someone deletes it — which is what makes kubectl logs --previous and the lastState.terminated field possible, and what makes leaked stopped containers a real disk-space incident on busy nodes. The spec is also explicit that these four states are the only ones; anything richer you see in a UI (Created, Paused, Restarting, Exited…) is that tool's invention layered on top.

      • Under the hood

        Notice what is not in the list: no run, no exec, no logs, no pull, no ps. runc run and runc exec exist as conveniences in the implementation, not as spec operations, and that distinction matters when you compare runtimes — a minimal OCI runtime may implement exactly these five. The delete step is the one people forget, and forgetting it is this module's cousin of the "container with that ID already exists" error that I3 dissects: the state directory is what makes an ID taken, and it is removed by delete, not by the process dying.

      • Under the hood

        This split is the single most consequential design decision in the runtime spec, and almost everything above it depends on the gap it opens. In that window a supervisor can attach stdio and a pty, a network plugin can enter the already-created network namespace and configure it (which is exactly how CNI is invoked — I9), metrics collection can find the cgroup, and a shim can take ownership of the process's lifetime before it produces any output that could be lost. Without the split, every one of those would be a race. It is also the reason a container can be "created but not started" in your tooling for a surprisingly long time while a plugin is slow.

      • Under the hood

        The distinction is the whole lesson. createRuntime runs in the runtime's namespaces, so it can see the host — that is where a network plugin belongs, because it needs host privilege to make a veth and then move one end into the container's netns. createContainer runs in the container's namespaces but before pivot_root, and startContainer runs inside, immediately before exec. Hooks receive the container state JSON on stdin — including the PID — which is precisely how a hook finds the namespace it must operate on. A failing hook aborts the container, which makes hooks a real and under-appreciated cause of "the container never started and there is nothing in the logs".

      Boundaries

      • Under the hood

        Images are I4 and I5; building them is I6; naming, logging and lifecycle-above-the-container are I7's containerd objects; networking is I9's CNI; storage is I10. The omissions were not oversights — a specification that also standardised images would have needed every runtime to agree on a registry protocol, and the ecosystem would have forked. Keeping the runtime contract this small is why runc, crun, youki, gVisor and Kata can all be drop-in replacements for one another despite being written in four languages and, in two cases, not even running the workload on the host kernel.

      • Under the hood

        This is the checkpoint that converts "there is a standard" from a claim into an observation. crun is written in C rather than Go, starts measurably faster and uses a fraction of the memory, and shares no code with runc whatsoever — yet the same directory produces the same container. Where you do find differences, they are nearly always in territory the spec left as SHOULD or MAY (error message text, exact cgroup path construction, how quickly the state file appears), which makes this a practical exercise in I0.7's reading skill: for each difference, go and find out whether the spec required anything at all.

      Creation, step by step

      • Under the hood

        Because some namespace changes cannot apply to the calling process. CLONE_NEWPID in particular affects only children — the process that unshares it stays where it was, and its next child becomes PID 1 in the new namespace. So a runtime that wanted to configure everything in place would find itself outside half the isolation it just created. The answer everyone converged on is to fork a fresh, minimal process (runc init), have it place itself inside all the namespaces, and only then exec the workload — and it is a re-exec of the same binary rather than a helper because that guarantees the two halves are exactly the same version.

      • Under the hood

        Configuration reaches runc init over a pipe rather than on its command line for two reasons, both worth internalising. The command line and environment of any process are world-readable at /proc/<pid>/cmdline and /proc/<pid>/environ — B12's secret-leak lesson — so anything sensitive must not go there. And the handshake is bidirectional: the parent has work it can only do after the child exists but before the child proceeds, most importantly writing uid_map/gid_map, which I1 showed can only be written from outside and only once. The netlink framing is just a convenient self-describing binary format; the interesting part is the synchronisation it carries.

      • Under the hood

        Isolation is applied in decreasing order of privilege required, because it is a one-way ratchet. Mounting needs CAP_SYS_ADMIN, so mounts must precede the capability drop. pivot_root needs CAP_SYS_ADMIN too, and it needs the new root already mounted. A seccomp filter that blocks mount — as every real profile does — must therefore be installed after all mounting is finished, and it must be installed before execve so the workload never runs unfiltered for even an instant. Once you see the constraint, the sequence is the only one that satisfies it, which is why every OCI runtime does it identically without the spec having to dictate the order.

      Living with a runtime that exits

      • Under the hood

        Detached, the workload's parent becomes whatever the nearest subreaper is — systemd, or PID 1 — and that is the entire problem a shim exists to solve. When the parent is gone, nobody is waiting on the process, so its exit code is collected by init and discarded, its stdout goes wherever the fds happened to point, and there is no process left that can be asked "is it still running?". Foreground mode has the opposite problem: it works perfectly and ties the supervising process's lifetime to the container's, so restarting your daemon would kill every workload on the node.

      • Under the hood

        --pid-file is written by runc before it exits, and written atomically (to a temporary name, then renamed), so a reader either sees the complete PID or no file at all — never a half-written one. The race it closes is nastier than "the PID is missing": PIDs are reused, so a supervisor that discovers a PID late can end up supervising, and eventually signalling, an entirely unrelated process. This is the same class of bug as a stale PID file in /var/run, and it is why the modern answer is not a PID at all but a pidfd or a cgroup — you will see both in I7.

      • Under the hood

        You cannot pass a terminal by name. A pty master is an open file description, and the only way to hand one to a process that did not create it is SCM_RIGHTS over a unix domain socket — B9's file-descriptor-passing lesson, arriving with a use case. The reason it is needed here is the same re-parenting problem: runc init creates the pty inside the container's devpts instance and then exits the runtime, so the master must be handed to whoever will still be around. This is exactly how kubectl exec -it and docker attach get a terminal into a container started minutes earlier by a process that is long gone.

      • Under the hood

        runc exec is setns from I1, wrapped: it joins the container's namespaces and cgroup and executes a new process there. What it does not do is join the PID namespace as PID 1 or inherit the original process's environment from the image — which is why an execed shell often has a different PATH and no application environment, a confusion that arrives later as "why does kubectl exec not see my variables?". runc update is the honest reminder that cgroup limits are live files: nothing needs restarting to change them, which is the mechanism behind in-place pod resizing.

      State on disk

      • Under the hood

        It is a directory. That is the honest and useful answer: without a daemon, a "container" is a JSON file plus whatever kernel objects (namespaces, cgroup, mounts) are still referenced. The location matters as much as the content — /run is a tmpfs, so it is emptied on reboot, which is exactly right for state describing processes that also do not survive a reboot. This is your first sight of a pattern that repeats all the way up the stack: I7's containerd keeps the same kind of record in a bbolt database, and the kubelet keeps its own above that. Three layers, each with an independent idea of what exists, and reconciling them is most of what node troubleshooting is.

      • Under the hood

        The error is about the directory, not about a process, which is why it persists long after everything has died and why it is so disorienting the first time. rm -rf makes the error go away while leaving the container's mounts and cgroup behind — a leak that shows up hours later as a full disk or a cgroup that cannot be removed. Rootless runc defaults to $XDG_RUNTIME_DIR/runc (typically /run/user/<uid>/runc) for the obvious reason that an unprivileged user cannot write /run/runc — and that split is why a container created as root is invisible to the same command run as your user, which accounts for a great many "but I just created it" conversations.

      Beyond the basics

      • Under the hood

        The reason this works is I2.11's create/start split: at createRuntime time the network namespace exists and is empty, and the workload has not executed, so it cannot observe a half-configured network. The reason it is not how Kubernetes does it is worth noting now — a hook is embedded in the bundle, so the runtime layer would have to synthesise hook entries for every container, and errors surface as opaque runtime failures. CNI keeps the same timing but moves the call out to the caller, where failures can be reported and retried sensibly.

      • Under the hood

        Kubernetes exposes it as the kubelet's container checkpoint API — a forensic tool, not a migration one: it dumps a running container to an archive so an analyst can restore and study a compromised workload offline. That framing tells you why live migration never became mainstream here. Restoring requires the same kernel, the same filesystem state and the same open connections, and the cloud-native answer to "this workload must survive its node" was to make workloads restartable rather than movable. Knowing the shape of CRIU is still worth an hour: it is the clearest demonstration of exactly how much invisible state an ordinary process accumulates.

      I4 — Images

      16 cp · ~6 h

      An image is not a file and not a filesystem — it is a content-addressed graph of JSON documents and tar archives, held together by SHA-256. Walk one by hand from index.json down to a layer tar, then assemble a runnable rootfs out of it with no container tooling at all.

      I2 (you need somewhere to put the rootfs you build) and B5 (overlayfs, copy-up, whiteouts on disk). Authored against OCI image-spec v1.1.1.

      The model

      • Under the hood

        B12's hashing lesson, finally spent. A digest is an identity, not a location: sha256:e1c0… says nothing about which registry holds the blob, which is precisely why a mirror, a pull-through cache and an air-gapped copy can all serve the same bytes and all be provably correct. It is also why deduplication is free — two images sharing a base layer share the storage without anyone coordinating it — and why the entire supply-chain security story of I11 is possible at all. Everything in the image spec is a consequence of this one choice.

      • Under the hood

        Three fields, each earning its place. digest is the identity. mediaType tells you how to parse what you fetch before you fetch it, so a client never has to guess or sniff. And size is the one people overlook: knowing the length in advance means a client can refuse an oversized response rather than streaming a decompression bomb into memory, and can allocate exactly once. A format whose only pointer is self-describing, self-verifying and self-limiting is a large part of why this spec aged so well.

      • Under the hood

        Everything above the layers is JSON small enough to read in a terminal — this is a format you can debug with curl and jq, which is the entire reason I5 can pull an image by hand. Because references are digests, the structure is a directed acyclic graph and not a tree: two images built from the same base literally point at the same layer blobs, so the storage is shared and so is the verification. It also means an image has no single "size" — the honest question is always "how much of it do I not already have?"

      • Under the hood

        This is the whole :latest class of incident, and it is not really about latest — any tag can be moved. Two nodes pulling app:v2 a week apart can legitimately run different code, and nothing anywhere is broken. The habit that fixes it is pinning by digest (image: app@sha256:…), and the reason people resist is that digests are unreadable and updating them is work; the compromise most teams land on is tag-plus-recorded-digest, which at least makes drift detectable. This also explains why imagePullPolicy: IfNotPresent with a moving tag is a booby trap: the node with a cached copy never learns the tag moved.

      Walking a real image

      • Under the hood

        The OCI image layout is the on-disk twin of the registry API: an oci-layout marker file naming the version, an index.json as the single entry point, and a flat blobs/<algorithm>/<hex> content store. It is deliberately boring, and that is its value — it is a directory you can tar, copy onto a USB stick and carry into an air-gapped environment, which is exactly how most disconnected deployments actually move images. Note also what is not here: no filenames from inside the image, no directory structure, nothing human-readable at all below index.json.

      • Under the hood

        Getting comfortable with these two commands is worth more than any tool that pretty-prints images for you, because on a broken node the pretty-printer is often precisely what is failing. The hop that surprises people is that the config is a blob like any other — it lives in the same content store as the layer tarballs, addressed the same way, and its digest is what the wider ecosystem calls the image ID. That is why docker images shows an ID that matches nothing you saw in the registry: the registry indexes by manifest digest, the local tooling by config digest.

      • Under the hood

        The OCI image spec was adopted from Docker's v2 schema 2, so the structures are near-identical and the field names mostly match — which is exactly why the difference is so easy to trip over. Both types are alive in the wild simultaneously, registries store whatever was pushed, and clients ask for what they can handle via the HTTP Accept header. Ask for the wrong set and you get a manifest you did not expect, or a 404 for an image that plainly exists — one of the four failures in I5's drill.

      • Under the hood

        Platform selection is done by the client, not the registry: you fetch the index, pick a manifest whose platform matches the machine you are on, and fetch that. Which is why exec format error is such a persistent incident — pull an image that has no matching entry (or a single-platform image built on an M-series laptop and deployed to amd64 nodes) and the failure surfaces not at pull time but as a binary the kernel refuses to run. Annotations are the other half of I11's supply-chain story: image.source pointing at the repository and image.revision at the commit is how a running container gets traced back to code.

      Layers

      • Under the hood

        A layer is a tar archive of a filesystem diff — the files that this step of the build added or changed, not a whole filesystem. That is the entire representation, and it is why layers stack: extract them in order onto the same directory and the later ones overwrite the earlier ones, which is a slow, disk-hungry version of what overlayfs does instantly with mount options. zstd is the newer option and decompresses several times faster than gzip, which matters more than it sounds when a node is cold-starting fifty pods at once.

      • Under the hood

        One identifies the transfer, the other identifies the content. They must be separate because compression is not deterministic across implementations and versions — recompress the same tar with a different gzip and you get a different blob digest for identical content. So the registry and the download path work in terms of digest, while anything reasoning about what the filesystem actually contains works in diff_id. This is also why re-pushing a rebuilt-but-identical image can transfer bytes that were logically already there.

      • Under the hood

        Two different representations of the same idea, and knowing that they differ is the point. On disk, overlayfs records a deletion as a character device with major:minor 0:0 — a filesystem trick. In the transfer format it must be something a plain tar can carry anywhere, so it is a specially-named regular entry. Converting between them is the snapshotter's job (I7), which is why unpacking layers with plain tar gives you a directory containing visible .wh. files instead of actual deletions — and why doing the conversion correctly is the interesting part of this module's project, and getting the order wrong is its third drill fault.

      • Under the hood

        Because a layer's content does not determine the filesystem it produces — its whole history does. The same "install our app" layer applied on top of Alpine and on top of Ubuntu yields two completely different rootfs states, so caching on diff_id alone would let a snapshotter reuse a prepared filesystem that is silently wrong. A chain ID hashes the entire ordered prefix into one identity, which makes "have I already prepared exactly this stack?" a single lookup. It is why two images sharing the first four layers share four snapshots on the node, and why changing anything early in a Dockerfile invalidates everything after it — the same fact that I6 meets again as build-cache behaviour.

      The config

      • Under the hood

        Seen this way the split is obvious and stops being arbitrary: the image knows things about the software (where its binary is, what environment it needs, which user it should run as), and the caller knows things about the deployment (limits, mounts, namespaces to join, network). The image config carries exactly the first set and nothing from the second — there is no place in it for a memory limit or a namespace, by design. ExposedPorts is the field to be cynical about: it is pure documentation, publishes nothing and is ignored entirely by Kubernetes, exactly like containerPort in a pod spec.

      • Under the hood

        The rule: the final process.args is Entrypoint followed by Cmd; overriding Cmd replaces only the tail, while overriding Entrypoint replaces the head and — in most tooling — clears Cmd unless it too is supplied. Kubernetes renames both fields and renames them confusingly: pod command overrides the image's Entrypoint, and pod args overrides the image's Cmd. Half of all "my container ignores the command I gave it" incidents are this one mapping, and knowing it is worth an exam question and several real outages. Environment merges rather than replaces, with the caller winning per key.

      I5 — Registries

      15 cp · ~6 h

      A registry is an HTTP server with two namespaces — blobs by digest, manifests by tag or digest — and once you have pulled an image using nothing but curl, ImagePullBackOff stops being a Kubernetes mystery and becomes a status code you can read.

      I4 — you must already be able to walk an image graph and verify a digest. Authored against OCI distribution-spec v1.1.1. This module needs working internet.

      The API

      • Under the hood

        Every conformant registry answers at /v2/, and the whole API lives under that prefix — the version is in the path rather than in a header, so a client discovers support with one request and nothing to negotiate. A 401 here is the normal and expected answer from any registry that requires a token, which is the first thing to internalise: on this API, 401 is frequently the start of a successful conversation rather than an error. Getting a 404 instead is the real bad news, and usually means you are talking to a reverse proxy that does not know it is fronting a registry.

      • Under the hood

        That asymmetry is the whole design. Because blobs are immutable and named by their own hash, they can be cached forever, served by any mirror, and verified by the client without trusting the server at all — which is why registry caching is unusually easy to get right. All the mutability in the system is concentrated in the tag→digest mapping, so the tag endpoint is the only thing that needs consistency guarantees, the only thing worth protecting with authorisation, and the only thing an attacker gains anything by tampering with. I11's signing story targets exactly this point.

      • Under the hood

        This one request is the mechanism behind imagePullPolicy: Always, and knowing that reframes it: "Always" does not mean always re-download, it means always re-resolve. The node HEADs the manifest, compares the returned digest with what it has, and pulls nothing if they match — so the policy costs one cheap round trip per container start, not a transfer. It also explains the failure that makes it painful: if the registry is unreachable, Always fails the pod even though a perfectly good image sits in the local content store, which is why disconnected environments run IfNotPresent.

      • Under the hood

        The registry stores what was pushed and hands back the best match for what you said you accept; if you say nothing, you get whatever the server considers its default, which for historical reasons is often a Docker schema-2 manifest even when an OCI index exists. That is how you end up with a single-platform manifest when you asked for a multi-platform image and then wonder where the arm64 variant went. It is also the cause of a genuinely misleading MANIFEST_UNKNOWN for an image you can see in the web UI — the fourth fault in this module's drill.

      Pulling by hand

      • Under the hood

        The registry does not authenticate you itself — it points at a separate authorization service and tells you exactly what to ask for, which is why a public image needs a token even though it needs no credentials: you fetch an anonymous token scoped to repository:library/alpine:pull. The consequences are practical. Tokens are per-scope, so a client pulling from two repositories does two dances. They expire, so a long pull can fail partway through with a sudden 401. And docker login stores your credentials, not a token — the token is re-fetched per operation, which is why a imagePullSecret with valid credentials can still fail if the auth service is unreachable.

      • Under the hood

        It means they share one budget, and the failure is delightfully misleading: pods start fine all morning and then a deploy at 14:00 half-fails, with different pods on different nodes affected each time. The status code is 429, but by the time it reaches a user it has been through the kubelet and become a generic ImagePullBackOff with the reason buried in the events — which is why "check the actual HTTP status" is such a high-value first move. The real fixes are all in I5.13: authenticate (higher limit), mirror, or run a pull-through cache.

      • Under the hood

        Blob requests almost always answer 307 to a signed, time-limited URL on object storage — the registry does the authorisation and hands the transfer to a CDN, which is why the endpoint you must allow through a firewall is frequently not the registry hostname. This is the number one cause of "pulls work from my laptop but not from the cluster" in restricted networks. Note also that you verify the digest yourself and that this is not a formality: it is what makes the redirect safe, since the CDN never has to be trusted with content integrity.

      • Under the hood

        Worth pausing on. Between this and I2, you have implemented the whole of what "run an image" means: resolve, download, verify, unpack, configure, execute. Everything the rest of the stack adds above this line — containerd, CRI, the kubelet — is caching, concurrency, lifecycle management and API surface, not new capability. That is the track's thesis at its most concrete, and it is also the mental model that makes node debugging tractable, because you can now ask which of those six steps failed instead of asking why Kubernetes is unhappy.

      Pushing

      • Under the hood

        That ordering is the consistency model, and it needs no transactions to work. A manifest is the only thing that makes an image resolvable, so as long as it is written last, no client can ever fetch a manifest whose content is not already fully present. An interrupted push leaves orphaned blobs — wasted space, cleaned up by garbage collection — but never a broken image. Contrast with the failure mode you get when a mirror replicates in the wrong order, which is I5.15's second fault: a manifest that resolves and a blob that 404s, and a pull that fails halfway.

      • Under the hood

        The session exists so an upload can be resumed rather than restarted — which matters when the blob is 900 MB and the connection is a train's wifi. The digest is supplied at finalisation, not at the start, so the registry computes the hash as bytes arrive and rejects a mismatch at the end; that is the server-side half of the integrity guarantee whose client-side half you did in I5.7. Chunked uploads are also where registries differ most in practice, since the spec leaves plenty as SHOULD — a good place to practise I0.7's habit of checking what was actually required.

      • Under the hood

        Blobs are content-addressed and stored once per registry, so "uploading" a blob the registry already has is just a permission check and a reference. This is why re-tagging or promoting an image between repositories (staging/app → prod/app) is nearly free, and why a well-behaved client always tries the mount before uploading. The permission check is the subtle part and occasionally the bug: you must have pull rights on the source repository, so cross-repo mount silently degrades to a full upload when a CI account is scoped too narrowly — and the only symptom is that the pipeline got slower.

      In practice

      • Under the hood

        The reason skopeo earns a place in a runtime-internals track is that it needs no daemon and no root, so it belongs in CI, in an air-gapped transfer, and in the middle of an incident when the local runtime is exactly what you suspect. copy is a registry-to-registry streaming operation — nothing is unpacked, so it is fast and needs no disk for a rootfs. One honest caveat about delete: on most registries it removes the manifest, not the blobs, and reclaiming the space needs a separate garbage-collection pass with the registry read-only. Deleting an image and watching disk usage not move is a normal Tuesday.

      • Under the hood

        The certs.d mechanism is per-registry-host configuration that lives outside the main config file, so it can be dropped in by configuration management without templating config.toml — and it is read on each pull rather than at start-up on modern containerd, though the restart habit is cheap insurance. The distinction to keep straight: a mirror is consulted first and falls back to the upstream, while a pull-through cache is a registry that fetches and stores on a miss. Both fix rate limiting; only the second helps when upstream is unreachable. This is also the file that makes an air-gapped cluster work without rewriting every image reference in every manifest.

      I6 — Building images

      13 cp · ~5 h

      A Dockerfile is two things at once: a sequence of layer-producing operations, and a cache-key function. Learn to read it as both — then build an image with no Dockerfile and no Docker, which is the only way to be certain you understood it.

      I4 (layers, digests, chain IDs) and I5 (you need somewhere to push to — the local registry:2 from I5.9).

      Semantics

      • Under the hood

        Everything about image building follows from this split, and I4 already told you why: layer-producing instructions change the filesystem and therefore the chain ID, so they invalidate every cached step after them; config-amending instructions produce a history entry marked empty_layer: true and cost nothing. It is why moving your ENV and LABEL lines around is free while moving a COPY is not, and why an image with thirty instructions may have only five layers.

      • Under the hood

        .dockerignore is usually sold as a performance tweak, and it is, but the more important framing is that it is a secrecy control. The whole context is uploaded to the builder, so a .git directory, a .env file or a stray private key is transferred even when no COPY ever references it — and if anything later does COPY . ., it is now baked into a layer that will be pushed to a registry. This is one of the most common ways real credentials end up in public images, and I6.11 makes you go and find one.

      • Under the hood

        This single fact produces the most valuable ordering rule in the ecosystem: copy your dependency manifest, install dependencies, and only then copy your source. Because the cache key of the install step depends only on the manifest's content, editing application code leaves it hit and skips the slowest step in the build. Do it the other way — COPY . . above the install — and every single-character change reinstalls the world, which is the single most common cause of slow CI and this module's first drill fault. Note that the cache is a chain, not a set: once a step misses, everything after it rebuilds regardless.

      • Under the hood

        I4's whiteout lesson arriving as a bill. A layer is a diff, so the second RUN adds a .wh. entry — it does not and cannot remove bytes from a layer that is already sealed and content-addressed. The file is invisible at runtime and fully present in the registry, downloaded by every node that pulls the image, and extractable by anyone. That last part is why this is not merely a size issue: a secret written and then deleted in a later instruction is still in the image, which is the second half of I6.11 and the reason build secrets need the mechanism in I6.6 rather than discipline.

      Doing it properly

      • Under the hood

        Only the final stage's layers end up in the image, so everything the build needed but the runtime does not — compilers, headers, package caches, source, and any credential used along the way — is discarded rather than whitened out. That is a categorically stronger guarantee than "delete it afterwards", because those bytes were never in a layer of the resulting image at all. --target is the underused half: being able to build and run the builder stage is how you debug a compile failure that only happens inside the build, without a separate Dockerfile.

      • Under the hood

        BuildKit's central idea is that a build is a DAG, not a script: it resolves what actually depends on what, runs independent branches concurrently, and skips branches whose output nothing needs. The mounts follow from the same model — a cache mount is a node the graph can reuse without it being part of any layer's content, which is why pip and apt caches finally became safe to keep. Build args, by contrast, are recorded in the image config's history in plain text, so anyone who pulls the image can read them with jq; that is not a bug, it is what history is for, and it is why the secret mount had to be invented.

      • Under the hood

        Cross-building for a foreign architecture runs the foreign binaries under QEMU user-mode emulation, which is transparent and can be five to twenty times slower — fine for a Go binary copied in from a native builder, painful for a build that compiles a large C dependency inside the foreign stage. The alternative is a real builder per architecture with the results combined into one index, which is what most projects with heavy builds end up doing. Either way the payoff is the same and it is real: one image reference that works on both an M-series laptop and an amd64 node, and no more exec format error.

      Building without Docker

      • Under the hood

        buildctl exposes the seam the convenient tools paper over: BuildKit does not natively understand Dockerfiles. A frontend (dockerfile.v0, itself shipped as an image) parses the Dockerfile into BuildKit's own LLB graph, and an exporter decides where the result goes — an OCI layout, a tarball, the local content store, or straight to a registry. That decomposition is why alternative build definitions exist at all, and why the same builder can emit an image that never touches a local runtime, which is exactly what you want in CI.

      • Under the hood

        This is the checkpoint where images stop being a black box permanently. There is no privileged operation anywhere in that list — no namespaces, no mounts, no daemon — because building an image is not running a container; it is writing tar files and JSON and computing hashes. That realisation is what the unprivileged, daemonless builders (Kaniko, Buildah in rootless mode, ko, apko, Nix) are all built on, and it is why building images inside a Kubernetes cluster without mounting the node's container socket is possible at all. The only step that genuinely needs a container is executing a RUN instruction — which is what the project handles with runc.

      Reading images others built

      • Under the hood

        Each entry carries created, created_by (the instruction text) and empty_layer, and matching non-empty entries against rootfs.diff_ids in order is what lets you attribute bytes to instructions. Two caveats worth carrying: created_by is free-form text written by whichever builder produced the image, so it is a strong hint and not proof; and a squashed or hand-built image may have no useful history at all. Both are reasons this is a starting point for investigation rather than an answer, and both are why I11's SBOMs and provenance attestations exist.

      • Under the hood

        The uncomfortable part is how little access this needs: anyone who can pull the image can do it, with curl and tar. There is no exploit, no privilege and no running workload — the bytes are simply in a public blob. This is why the only correct response to a secret committed into an image is to treat it as disclosed and rotate it, and why "we removed it in the next layer" and "we deleted the tag" are both non-answers: the blob is content-addressed and may still be fetchable by digest, and any mirror that replicated it kept a copy.

      I7 — Runtime architecture: containerd, shims, snapshotters

      18 cp · ~7 h

      The heaviest module on the track — plan two sittings. Everything above runc and below the kubelet, assembled: who runs, who stays running, what survives a daemon restart, and where each of the three on-disk stores physically is.

      I2, I3, I4, I5 — the bundle, the runtime you drive by hand, the image format, and somewhere to pull from. This is the first module that needs all four at once, because containerd is precisely the thing that holds them together.

      The process tree

      • Under the hood

        The tree is not the one most people draw from memory. containerd is a child of systemd; your shell is a child of containerd-shim-runc-v2; and the shim is also a child of systemd, not of containerd. That is deliberate: the shim is started detached and reparented, so containerd is never the parent of anything that matters. And runc is nowhere, because I3 already told you why — runc create and runc start both exit as soon as they have done their work. runc is a contractor who finishes the job and leaves the site; the shim is the foreman who stays.

      • Under the hood

        The shim exists to own the three things a restartable daemon cannot hold: the workload's stdio (someone must be on the other end of the pipe or the pty when containerd is not running), its exit status (only the parent can reap a process and read its code), and the pty itself for interactive containers. Everything else follows. address holds the abstract socket containerd reconnects to; init.pid is the workload's PID, so the state can be rebuilt from disk after a restart; config.json is exactly the bundle spec you hand-wrote in I2, generated for you from the image config. Under CRI (I8) the arithmetic changes slightly — one shim per pod sandbox, with the pod's containers grouped under it — which is why ps on a Kubernetes node shows fewer shims than containers.

      • Under the hood

        This is the single most important architectural fact about containerd, and it is the answer to "can I safely upgrade the runtime on a node with workloads on it?" Because the shim is a separate, reparented process holding the workload, containerd's death is invisible to the container: nothing is reaped, no stdio pipe closes, no cgroup is torn down. On restart, containerd walks /run/containerd/io.containerd.runtime.v2.task/, reads each address, and reconnects over the shim's socket. Contrast Docker before it grew this design, where restarting the daemon killed the containers — the split into daemon + per-container shim is the fix, and it is why the kubelet can be restarted without disturbing pods too.

      • Under the hood

        That last command is worth the whole checkpoint. containerd does not reimplement anything runc does — it invokes the same binary you drove by hand in I3, just with a different state root (--root /run/containerd/runc/<namespace> instead of the default /run/runc). That is exactly the split I3 warned you about when a container "created as root was invisible": state roots are per-caller, and the reason runc list looked empty on a node full of containers was never that runc was not being used. Knowing this flag is a genuine debugging superpower — it lets you inspect and even kill a container from below a containerd that has stopped answering.

      Objects

      • Under the hood

        A containerd namespace is a flat tenancy label over every object in the daemon — images, containers, snapshots, content, leases — so several clients can share one runtime without colliding. The kubelet uses k8s.io; ctr and nerdctl default to default. This produces the single most common false alarm in container debugging: an engineer runs ctr images ls on a node with sixty running pods, sees nothing, and concludes the runtime is broken. Note also that content is not deduplicated across namespaces at the metadata level even though the blobs on disk are shared, so a `pull` in each namespace is bookkeeping, not bytes.

      • Under the hood

        A container in containerd is pure metadata: a spec, an image reference, a snapshot key, labels. A task is a running process created from it. The separation is what lets a container be stopped and restarted without re-resolving its image or re-preparing its snapshot, and it maps one-to-one onto Kubernetes' own distinction between a container's definition in the pod spec and the instance that has a restart count. It also explains a class of leak: deleting a task and forgetting the container leaves the snapshot referenced, so the disk never comes back — which is one of the faults in this module's drill.

      • Under the hood

        That sentence is the whole design. Everything else — layers, config, platform variants — is reachable by walking from that one manifest digest, exactly as pull.py walked it. So "deleting an image" deletes a name; the blobs go only when nothing references them and the garbage collector runs (I7.13), which is why ctr images rm can free zero bytes and why two tags for the same digest cost one copy. It is also why an image can be perfectly present on a node by digest while ctr images ls shows nothing you recognise.

      • Under the hood

        "Plugin" here does not mean a separate file you install — almost all of them are compiled into the single containerd binary and registered at start-up, with the plugin model providing dependency ordering and per-component failure. That is why a broken CRI configuration shows up as one plugin in error state while everything else is fine, and why ctr plugins ls is the fastest triage command on the box. The 2.x config is a real break, not a rename: config version = 3, the CRI plugin split into io.containerd.cri.v1.runtime and …v1.images, and several 1.x compatibility paths removed. Configuration copied from a 1.7-era blog post will be silently ignored rather than rejected, which is exactly why I0 made you pin the version and write it down.

      Storage internals

      • Under the hood

        This directory is pull.py's cache from I5, with an API and a garbage collector bolted on — the layout is not clever, and it does not need to be, because content addressing does the hard work. Corruption is detectable (the name disagrees with the bytes), deduplication is automatic (the same layer in ten images is one file), and there is no cache-invalidation problem at all, because content that differs has a different name. This is also the store the kubelet's disk-pressure eviction is ultimately reacting to on a real node.

      • Under the hood

        The snapshotter is the room-prep crew stacking B5's transparent sheets. Its whole job is: given a parent chain and a layer tar, produce a directory that can be a lower layer, and remember it by chain ID so nobody unpacks it twice. ctr snapshot tree is the visible proof of I4's claim that the chain ID, not the layer digest, is the cache key — two images sharing a base share snapshots up to the point where their chains diverge, and not one byte further. Note also that overlayfs is only the default snapshotter: native, btrfs, zfs, devmapper and the remote/lazy-pulling ones (stargz) plug into the identical interface, which is the whole point of having one.

      • Under the hood

        That mount string is B5's mount -t overlay command, generated for you — the same lowerdir=…:…:…,upperdir=…,workdir=… you assembled by hand, with the lowerdirs in chain order. Committed snapshots are read-only and shared by every container built on them; the active one is the container's writable layer and dies with the container, which is the mechanical reason "data written in a container is lost on restart" and the reason a chatty log-to-disk workload can fill a node without any volume being involved. It is also the source of a nasty production shape: image layers are shared, so ten pods from one image cost one copy, but ten writable layers are ten copies of whatever each pod writes.

      • Under the hood

        bbolt is an embedded key/value store — a B+tree in one memory-mapped file, one writer at a time, no server — and it is the same family of component as etcd's backend, which is why B13's reading pays off here. Its content is tiny and irreplaceable: the content store can be re-fetched from a registry and the snapshotter re-derived from the content store, but nothing on earth can tell you that blob sha256:9b2a… was called myapp:v3 once meta.db is gone. That asymmetry is why the correct repair for "containerd is confused" is almost never rm -rf /var/lib/containerd, and why doing it on a node means every image re-pulls.

      • Under the hood

        containerd's GC is a mark-and-sweep over a reference graph built entirely out of labels: containerd.io/gc.root marks an object as a root, and containerd.io/gc.ref.content.* / gc.ref.snapshot.* are the edges from an object to what it needs. Anything unreachable is deleted. A lease is a temporary root with an expiry — the mechanism that stops the collector from deleting a half-finished pull, and, when you fetch a blob by hand, the reason your blob quietly vanishes about a day later. This is the model behind the entire "my disk filled up / my image disappeared" genre of node incidents, and it is why an orphaned snapshot with a stale label is a leak the GC will never reclaim.

      Talking to it

      • Under the hood

        There is nothing to fix here — it is the design. A runtime's job is to create processes with arbitrary uids, mounts, capabilities and namespaces, so any API that can ask for a container can ask for a container that owns the machine. B12's least-privilege lesson arrives with teeth: this is why mounting the container socket into a workload ("so CI can build images") is a full node compromise waiting to happen, why the same is true of /var/run/docker.sock, and why the rootless and daemonless build tooling in I6 and I11 exists at all. On a Kubernetes node the equivalent sentence is: a pod that can mount the host's socket does not need any RBAC permission to become cluster-admin, because it can read the kubelet's credentials off the disk.

      • Under the hood

        The API is a set of gRPC services over that socket — Containers, Tasks, Images, Content, Snapshots, Leases, Events — and every client you have installed is a face on the same services. The event stream is the runtime's own audit log, and it answers the question node logs usually cannot: did this container exit, or was it never started? On a Kubernetes node the same stream shows you the pause container being created before its app containers, in the exact order I8 will teach, which makes ctr -n k8s.io events one of the more useful things to have running while you reproduce a pod-startup problem.

      • Under the hood

        nerdctl is a Docker-compatible CLI over containerd's own API — same daemon, same content store, same snapshots — so it demonstrates that "Docker commands" were never a runtime feature. What Docker's CLI adds over ctr is convention: default networking, port publishing, volume names, restart policies, logs. Every one of those is a client-side decision layered on primitives you have already handled by hand, and every one is something Kubernetes chooses to do differently. That is precisely why docker run knowledge transfers so unevenly to debugging a cluster.

      I8 — CRI: the interface the kubelet speaks

      16 cp · ~7 h

      The first of the three contracts Kubernetes drives a node through. By the end you can say exactly what the kubelet asks for, in what order, and what comes back — and you will have implemented enough of the server side to make crictl believe you are a container runtime.

      I7 — CRI is a plugin inside the containerd you just took apart, so every call below lands on machinery you can already inspect from underneath.

      Why and what

      • Under the hood

        In-tree runtime support meant every runtime's bugs were kubelet bugs, every runtime's release cycle was Kubernetes' release cycle, and adding a runtime meant persuading the Kubernetes project to merge it. CRI inverts that: the kubelet ships one client, and anyone can write a server. The dockershim removal is worth being precise about because the internet was not — images built by Docker were never affected (they are OCI images, I4's subject), and neither was using Docker on a developer laptop. What broke was nodes whose runtime was the Docker daemon, and the fix was almost always to point the kubelet at containerd, which Docker had been using underneath the whole time.

      • Under the hood

        gRPC means the wire format is protobuf and the API is a .proto file in the cri-api repository — a machine-checkable contract rather than prose, which is why CRI has stayed stable while both sides changed underneath it. A unix socket rather than TCP means the trust boundary is filesystem permissions, so I7.14's warning applies unchanged: the CRI socket is root on the node too. And the compatibility rule is asymmetric in a way worth memorising — a newer kubelet talking to an older runtime is the combination that bites, because the kubelet may request fields the runtime never implemented.

      • Under the hood

        They are separate because they can genuinely be provided by different components, and sometimes are: the kubelet accepts --image-service-endpoint distinct from the runtime endpoint. It also draws a clean line for policy — image pulling is the half that talks to the network, needs registry credentials, and is where pull secrets, digest pinning and admission checks belong (I11), while the runtime half never touches a registry. The practical payoff is diagnostic: "images pull but nothing starts" and "containers start but images fail" are failures of two different services, and knowing which one you are looking at halves the search space.

      The sandbox model

      • Under the hood

        The pause container is the room: rented, numbered and wired before any guest checks in. Its source is a few dozen lines — it sets up signal handling, reaps zombie children, and blocks forever. The reason it must exist is ordering: something has to own the pod's network and IPC namespaces before any app container starts, must keep owning them while containers come and go across restarts, and must be the last thing to die. A namespace with no process in it is destroyed unless it is pinned, so "a process that does nothing" is exactly the right tool.

      • Under the hood

        I2 taught the runtime spec's linux.namespaces array, where an entry with a path means "join this existing namespace" instead of "unshare a new one", and B6 taught that a namespace is a file you can bind-mount and hold open. Put them together and the famous pod semantics stop being magic: app containers join the pause container's net/ipc/uts namespaces by path, so they share an IP, a loopback interface, a port space and a hostname — while keeping their own mount and PID namespaces, which is exactly why sidecars can see each other on localhost but not in each other's filesystems or process lists (unless shareProcessNamespace is set, which simply stops asking for a private PID namespace).

      • Under the hood

        This is where B10's resolver lesson meets Kubernetes and where several classic mysteries get their explanation. The runtime — not the workload, not the container image — writes the sandbox's resolv.conf, which is why every pod on a cluster has the same nameserver regardless of its base image, and why ndots:5 in that generated file makes an external lookup take five failed queries before it succeeds. The log directory field is the other quiet one: it is where the CRI log files I12 dissects will be written, chosen by the kubelet, and the reason kubectl logs works at all.

      • Under the hood

        The ordering explains an entire family of cluster symptoms. Because networking is attached to the sandbox, and the sandbox precedes every app container, a broken CNI produces pods stuck in ContainerCreating with an error mentioning networking and no container logs to read — there is nothing to log, nothing was started. It also explains why a pod keeps its IP across container restarts but not across pod restarts: the IP belongs to the sandbox's network namespace, not to any container. I9 opens exactly this seam and makes you implement the other side of it.

      The call sequence

      • Under the hood

        The kubelet is a reconciler (B13's loop, W1's syncLoop): it compares the pod spec it has been given against what the runtime reports, and issues whichever of these calls closes the gap. That is why the sequence is not a script but a fixpoint — a container that exits gets created and started again by the same code path, and a sandbox that disappears gets a new one along with a new IP. Knowing the order tells you which call failed from the symptom alone: no sandbox means networking or the sandbox image, sandbox but no container means image pull or spec, container but immediate exit means the workload itself.

      • Under the hood

        gRPC is a poor fit for an interactive terminal — long-lived, bidirectional, with window-resize messages — so CRI hands the problem off: Exec returns a URL to a streaming server that the runtime hosts, and the API server is redirected to it. That indirection is why kubectl exec can fail with an error naming a host and port that appear nowhere in your kubeconfig, and why exec/attach/port-forward have their own firewall and authentication considerations distinct from the rest of the API. ExecSync, meanwhile, is the probe path, and its timeout behaviour is the reason a heavyweight liveness probe can wedge a node's runtime.

      • Under the hood

        In-place pod resize went GA in Kubernetes v1.35, the version this track targets, and this call is the whole mechanism: the kubelet writes new values into the container's cgroup v2 files, which is precisely B7's lab, done by an API. That is why growing a memory limit takes effect immediately and shrinking one may not (the pages are already charged), and why CPU changes are smooth while memory changes can meet an OOM kill. PortForward is worth one honest sentence too: it is a tunnel to the sandbox's network namespace, which is why it works for a pod with no Service and tells you nothing about whether Service routing is healthy.

      • Under the hood

        Deletion runs the creation sequence in reverse for a reason: the sandbox owns the network namespace, so tearing it down first would strand containers with a namespace that is going away, and the CNI DEL — which must run to release the pod's IP — is bound to sandbox teardown. Get this wrong and you leak IPAM reservations, which is I9's third fault and a real node-level outage mode: a node that refuses new pods because a subnet full of addresses is held by pods that no longer exist. It is also why a terminating pod's grace period is spent on containers, with the sandbox removed only afterwards.

      Operating it

      • Under the hood

        kubectl shows you the cluster's intent and the kubelet's summary of reality; crictl shows you the node's reality directly, with no API server in the path. That difference is the entire reason it belongs in your CKA toolkit: when the API server is unreachable, when a node is NotReady, or when a pod's status is a summary of something that has already happened three times, crictl still answers. The trap to remember is the reverse: crictl talks to a runtime, so it cannot tell you anything about scheduling, admission or the API objects that produced what you are looking at.

      • Under the hood

        Someone has to invent this format, because the workload just calls write(2) on fd 1 — it has no idea it is being logged. The shim reads the pipe and the runtime writes these lines, which is why the timestamp is the runtime's and not the application's, and why a stream that emits a 40 KB line arrives as several P records followed by one F. Knowing the format lets you read logs on a node where kubectl logs is unavailable, and knowing who writes it explains the rule that a container logging to a file inside itself effectively has no logs at all. I12 traces the whole path from write(2) to your terminal.

      • Under the hood

        The cgroup driver is not a preference, it is a claim about who owns the cgroup tree. With systemd, the runtime asks systemd to create a scope/slice and lets it manage the hierarchy; with cgroupfs, the runtime writes the directories itself. When the kubelet and the runtime disagree, both succeed at their own half and you get two parallel trees: containers run, but the kubelet's accounting looks at cgroups nothing is charged to, so limits are enforced somewhere it is not reading and eviction decisions are made on fiction. Since systemd is PID 1 on essentially every production node, systemd on both sides is the only correct answer — and this remains one of the most common node misconfigurations in the field.

      I9 — CNI: the interface the network speaks

      16 cp · ~6 h

      The smallest contract in the entire ecosystem, and the one that most often gets blamed for outages it merely reported. B9 already built the datapath by hand; this module is the twenty lines of agreement that turned that script into something a runtime can call.

      I8 (the sandbox is what gets wired) and B9 (veth, bridge, ip_forward, NAT, conntrack, netfilter). Keep net-up.sh open on one side of the screen for most of this module — the project is a rewrite of it.

      The contract

      • Under the hood

        There is no daemon, no socket, no library to link, no version negotiation handshake — a CNI plugin is a program, and the calling convention is the one every Unix tool has used since the 1970s. That is why plugins exist in bash, Python, Rust and Go without anyone coordinating, and why you can write one this afternoon. Compare CRI, which needed protobuf and gRPC because it is a long-lived bidirectional API, and note the design lesson: the interface's complexity followed the interaction's, not the subject's. The electrician is handed a room number and a job, does it, and reports back the socket they fitted.

      • Under the hood

        Notice what is not in that list: there is no pod name, no namespace, no labels, no service account — CNI knows nothing about Kubernetes. CNI_NETNS is a path to a namespace file (B6's bind-mounted /proc/<pid>/ns/net), CNI_IFNAME is the name the interface must have inside it (conventionally eth0), and CNI_CONTAINERID is an opaque string the plugin uses as a bookkeeping key — which is why IPAM reservations are filed under it, and why a runtime that passes a different ID on DEL than it did on ADD leaks addresses forever. Anything Kubernetes-specific that a plugin needs, such as the pod's name for policy, arrives smuggled through CNI_ARGS or a per-plugin capability field.

      • Under the hood

        That MUST is the most-violated sentence in the specification, and the reason is a reasonable-sounding instinct: a plugin author writes DEL, tests it once, and returns an error when the interface is missing because "that shouldn't happen." It happens constantly. The runtime retries after a timeout, a node reboots between ADD and DEL, a sandbox is torn down twice — and a DEL that errors makes the runtime believe the teardown failed, so it retries forever, and the pod hangs in Terminating. The spec makes the same point about DEL being best-effort: complete it "to the fullest extent possible, even if some resources or state are missing." Write DEL first, and write it to succeed on an empty world.

      • Under the hood

        Because errors are structured, the runtime can distinguish "this plugin does not support the requested version" from "the network is broken" — but only if the plugin actually produces the object rather than printing a bare message and exiting 1. This is where bash plugins usually go wrong, and it produces one of the most disorienting Kubernetes error messages there is: the kubelet reports a JSON parse failure while creating a sandbox, so the operator investigates the runtime, when the real answer is that a plugin wrote a diagnostic to stdout where the result should have been. The rule for the project: stdout is the result channel; every human-readable word goes to stderr.

      Configuration

      • Under the hood

        The runtime sorts the directory lexically and takes the first file — not the newest, not the highest-numbered, not a merge. That rule is a genuine production footgun: an operator adds 99-mynetwork.conflist expecting it to win and nothing changes, or a CNI daemonset upgrade drops 05-cilium.conflist next to an old 10-flannel.conflist and the whole node quietly changes networks on the next pod. Two conf files in that directory is a bug even when one of them is "just a backup" — 10-flannel.conflist.bak is fine, 10-flannel.conflist.orig is a live configuration file if it still ends in .conflist.

      • Under the hood

        Chaining is a pipeline where each stage receives everything the previous stages built, so the second plugin knows the container's IP without ever having allocated one — which is exactly what portmap needs in order to write a DNAT rule to it. The composition is why the ecosystem's small plugins stay small: bandwidth shapes the interface it is told about, firewall writes rules for the address it is told about, tuning sets sysctls on it. Put portmap first and it has no prevResult to work from, which is not a subtle failure — it is the same class of mistake as piping into a command that expected an argument.

      • Under the hood

        The version in the configuration is a request for a result format, and it is negotiated per plugin, not per cluster — which is why a chain can legitimately mix plugins built against different spec versions as long as each supports the requested one. The differences are small but real (the 1.x result's interfaces/ips structure replaced the older flat ip4/ip6 fields, and CHECK arrived in 0.4.0), and libcni converts between them. This matters for the project: a plugin that prints a 0.3.1-shaped result while claiming 1.1.0 will be parsed, misread, and fail in a way that blames the wrong component.

      • Under the hood

        cnitool is a thin wrapper over libcni, the same library containerd and CRI-O use to find configurations, order chains, marshal stdin and parse results — so "works under cnitool" is a meaningful statement about spec compliance rather than a toy. Developing against it is also enormously faster than the alternative: the feedback loop for a plugin bug found via a Kubernetes pod is a sandbox creation, a kubelet retry backoff and a log hunt, while the loop here is one command and a JSON blob on your terminal. Keep the namespace around between runs and you can test DEL idempotency by simply running it twice.

      The plugins that ship

      • Under the hood

        This is the module's thesis made literal: the reference plugin does nothing your bash script did not, mechanically. What it adds is the contract — a parsed configuration, a structured result, an idempotent DEL, and a CHECK that verifies rather than assumes. The two extras worth finding yourself are usually hairpin/promiscuous handling (so a pod can reach itself through a Service VIP without the bridge dropping the frame) and correct behaviour when the bridge already exists with different settings. Both are the kind of detail you only write after being paged.

      • Under the hood

        An entire genre of node incident lives in this directory. IPAM is a separate concern from wiring — a plugin in its own right, invoked by the network plugin — and host-local's implementation is a directory of files on the node with no coordination, no TTL and no reconciliation. So every DEL that never ran leaves an address allocated forever, and after enough of them the node has a /24 of reservations and three running pods, and rejects new ones with an out-of-range error that mentions nothing about files. The v1.1 GC verb (I9.14) exists precisely to make this reclaimable, and until every plugin implements it, the field repair is still "delete the stale files".

      • Under the hood

        loopback is mandatory because a fresh network namespace has a lo interface that is down, and an enormous amount of software assumes 127.0.0.1 works — a sidecar talking to its app, a health check, a database client connecting to its own machine. Forget it and you get failures that look like anything but networking. macvlan gives each container its own MAC on the physical LAN (fast, no bridge, but many switches and most clouds refuse multiple MACs per port), while ipvlan shares the parent's MAC and splits by IP (survives those restrictions, at the cost of some L2 features). Both put pods directly on the physical network, which is why they show up in bare-metal and telco clusters and almost nowhere else.

      • Under the hood

        Recognising your own B9 rule inside a production networking stack is the moment the black box opens for good: hostPort in a pod spec becomes a portmap capability in the CNI result, which becomes an iptables DNAT rule in the node's nat table, which is the mechanism you already understand line by line. It also explains hostPort's reputation — the rule is per node, so two pods wanting the same host port on one node cannot both run, and the scheduler has to treat the port as a consumable resource. Note the plumbing detail: portmap needs the IP from prevResult, which is why I9.6's ordering rule is not academic.

      In a real stack

      • Under the hood

        "Installing a CNI" is, at bottom, a privileged daemonset that writes a file into /etc/cni/net.d and drops binaries into /opt/cni/bin on every node — which is why a cluster is NotReady until it runs, and why the fix for a broken network so often turns out to be a file. The daemon that stays running afterwards is doing the part CNI deliberately does not specify: learning every node's pod subnet from the API, programming routes or VXLAN FDB entries between nodes (I1's overlay lesson), and enforcing NetworkPolicy. The split is worth stating plainly — CNI attaches one pod on one node; everything about how nodes reach each other is the provider's own business, which is why w4.html#cp-4-7's datapath families differ so wildly while all of them speak the same twenty-line contract.

      • Under the hood

        Each verb replaces a bad inference with a statement. Before GC, nothing could safely clean up leaked IPAM reservations, because no component knew the full set of live attachments — the plugin sees one call at a time and the runtime does not own the IPAM store; GC closes that loop, and libcni additionally synthesises DELs for stale cached attachments so even v1.0 plugins get some of the benefit. Before STATUS, a runtime decided the network was ready by observing that a conf file existed, which is why nodes have gone Ready and accepted pods a fraction of a second before their network agent finished programming routes, producing pods with addresses that could not reach anything. Both are small additions that delete a class of race.

      I10 — Container storage: volumes, snapshots, the CSI shape

      12 cp · ~5 h

      The third contract, and the one with the least mystery in it: a volume at the runtime layer is a bind mount plus some bookkeeping. Get that sentence properly earned and Kubernetes storage becomes a naming and orchestration layer over mechanics you already have.

      I7 (snapshots and where the writable layer lives) and B5 (VFS, mounts, overlayfs, propagation, loop devices — you will reuse that module's disk.img).

      A container's three storages

      • Under the hood

        Almost every storage question in Kubernetes is really the question "which of these three is this?", and the answers differ completely. Image layers are shared, so ten pods from one image cost one copy on the node and are re-fetchable from a registry at any time. The writable layer is private, unshared, counted against the node's ephemeral storage, and destroyed with the container — recoverable from nowhere. Mounts from outside are the only category with a lifetime independent of the container, and everything called a "volume" in a pod spec is one of them.

      • Under the hood

        This is the mechanism behind node disk pressure and one of the most confusing eviction stories in Kubernetes: a pod with no volumes, no PVCs and a modest memory limit can fill a node's disk and get itself — and its innocent neighbours — evicted, because nothing limits how much a container writes into its own root filesystem unless you set ephemeral-storage limits. The most common source is not application data but logs written to a file inside the container, which I12 will also show you have the additional property of being invisible to kubectl logs. The worst of both worlds, from one mistake.

      • Under the hood

        Both containers mount the same read-only lowerdir stack and each gets its own upperdir, so reads fall through to shared bytes while the first write to any file triggers a copy-up into that container's own upper layer. This is why starting a hundred pods from one image is cheap and why modifying a large file inside a container is suddenly expensive — copy-up copies the whole file before changing a byte of it, which is a real and frequently-surprising cost for a container that opens a multi-gigabyte data file for writing.

      Volumes at runtime level

      • Under the hood

        The runtime spec's mounts array is just mount(2) arguments — source, destination, type, options — executed inside the container's mount namespace after pivot_root. Everything the ecosystem calls a volume is built on this one field: a Docker named volume is a directory under /var/lib/docker/volumes plus a name in a database; a Kubernetes emptyDir is a directory under /var/lib/kubelet/pods/<uid>/volumes/ that the kubelet creates and deletes; a PVC-backed volume is the same, with a CSI driver having mounted something there first. The orchestration is elaborate; the runtime-level primitive is one line of JSON.

      • Under the hood

        The tmpfs experiment is the point of this checkpoint: pages in a tmpfs mounted into a container are charged to that container's memory cgroup, so filling /dev/shm or an emptyDir: {medium: Memory} gets your container OOM-killed by its own memory limit — with a log line about memory and no mention of storage anywhere. B7's OOM lesson, arriving from an unexpected direction. The block-device case matters for the opposite reason: it is the only one of the three where the container gets a real filesystem with real quota semantics, which is why size limits on ordinary bind mounts are so awkward and why the project below uses a loop image to get one.

      • Under the hood

        B5 taught propagation as kernel mechanics; here is what it is for. A CSI node plugin running as a pod mounts a volume into a host path, and the workload pod must see that mount appear inside a directory it already has mounted — which is impossible under rprivate, because the mount event does not propagate. That is the entire reason HostToContainer (rslave) exists, and Bidirectional (rshared) is the stronger form that lets a container's mounts escape onto the host, which is why it requires a privileged container and is a genuine escape risk. The symptom when it is wrong is uniquely maddening: an empty directory where a filesystem plainly is mounted, one namespace over.

      The CSI shape

      • Under the hood

        The pattern is now recognisable enough to predict: an interface appears exactly where a project refuses to keep merging vendor code, and the shape it takes follows the interaction it has to support — a long-lived, stateful, error-heavy conversation gets gRPC (CRI, CSI), while a short one-shot action gets an exec'd binary (CNI). Notice too what all three have in common: they are versioned contracts with their own release cycles, and Kubernetes ships a client for each. Once you see that, the answer to "how do I add X to Kubernetes" is almost always "find which of the interfaces already covers it".

      • Under the hood

        The split is where the volume runs, not what it does: Controller calls talk to a storage API somewhere (a cloud provider, a SAN) and can run anywhere in the cluster, while Node calls perform mount(2) and therefore must run on the target node — which is why a CSI driver ships as a Deployment and a DaemonSet. That immediately gives you a diagnostic map: a volume stuck in Pending with no PersistentVolume is a Controller/provisioner problem, while a pod stuck in ContainerCreating with a mount error on one node is a Node-plugin problem, and the two live in different pods with different logs.

      • Under the hood

        The reason is expensive work that must not be repeated: formatting a filesystem, attaching a device, running fsck, or a recursive chown for fsGroup. Do it once per node in staging, then give each pod a cheap bind mount from it — which is exactly how ReadWriteOnce can serve several pods on the same node while refusing a pod on a second node. That last fact surprises people every time and falls straight out of the model. The fsGroup chown is worth its own warning: it is recursive, so a volume with a million small files can add minutes to pod start-up, which is what fsGroupChangePolicy: OnRootMismatch exists to avoid.

      • Under the hood

        This is a genuinely elegant division: the vendor writes only the part that knows their storage system (a gRPC server that speaks CSI), and the Kubernetes-shaped work — watching PVCs, respecting finalizers, retrying with backoff, handling leader election between replicas — is done by generic sidecars maintained by the project, running next to the driver in the same pod. It is B13's reconciliation loop with a translator bolted on, and once you can name the sidecars you can diagnose a stuck volume by asking which loop stopped turning rather than by reading the vendor's driver logs first.

      I11 — Container security & supply chain

      15 cp · ~6 h

      Two halves that are usually taught apart: hardening the container that runs here, and knowing that the image you are running is the one you meant. Every control below gets proved by attempting the thing it is supposed to forbid.

      I2 (the spec fields these controls are written in), I4 and I5 (digests and registries), I1 (user namespaces, seccomp for real) and B12 (threat modelling, signatures, PKI). Nothing here is a new mechanism — it is B4's and B12's mechanisms, now declarative.

      Runtime hardening

      • Under the hood

        B4 taught the keyring; here it is issued declaratively, and the important discovery is that the defaults are not minimal — runtimes grant a list of roughly fourteen capabilities to every container by default, including CAP_CHOWN, CAP_SETUID, CAP_NET_RAW and CAP_MKNOD. "Not privileged" is therefore a long way from "has no power". The set that matters most for containment is bounding: it is a ceiling nothing in the container can raise, so dropping a capability from it removes that power from every process in the container permanently, including one that later becomes root. This is exactly what Kubernetes' securityContext.capabilities.drop: ["ALL"] compiles down to.

      • Under the hood

        Without this flag, running as a non-root uid buys less than it appears to: any setuid binary inside the image — and base images ship several, su, sudo, mount, ping historically — is a path back to uid 0 inside the container, which is then only a kernel bug or a careless mount away from being uid 0 outside. no_new_privs is a one-way process flag inherited by every child, so it cannot be undone after the fact. It is also a hard prerequisite for unprivileged seccomp, which is why the two arrive together in nearly every hardened profile.

      • Under the hood

        seccomp filters are BPF programs the kernel runs on every syscall entry, so the two workable strategies are opposite: SCMP_ACT_ERRNO as the default with an allow-list (strong, and what the runtime-default profile does — it blocks around forty dangerous syscalls) or a deny-list (easy and weak). The reason so many workloads run unconfined is honest and worth stating: getting an allow-list right requires knowing every syscall a program and its libc will ever make, including ones only reached during error handling, and the failure mode is a crash with no useful message. That is precisely this module's first drill fault. Note also that args-based filtering cannot dereference pointers, so filtering on a path is impossible by design.

      • Under the hood

        These are a second, independent layer: discretionary permissions (uid, mode bits, capabilities) say what the process is allowed to ask for, and MAC says what the policy permits regardless — so a root process with every capability can still be denied. AppArmor is path-based and lives on Debian/Ubuntu/SUSE; SELinux is label-based and lives on RHEL-family systems, where a container process is typically container_t and the volume it cannot read is mislabelled. That last sentence explains a large share of "permission denied as root" tickets on Red Hat nodes, and the :z/:Z mount options exist to relabel volumes for exactly this reason.

      • Under the hood

        A read-only rootfs is one of the highest-value-per-effort controls there is, because it removes the attacker's easiest move: writing a tool, a webshell or a modified binary into the container and running it. What breaks is predictable and small — /tmp, PID and lock files, package managers, log files written next to the binary, and language runtimes that compile caches at start-up. Enumerating that list is the work, and the enumeration is itself valuable: an application that needs to write to five scattered paths in its own image is telling you something about how it was designed. In Kubernetes this is securityContext.readOnlyRootFilesystem: true plus emptyDir mounts, and the advanced track has no lesson on Pod Security Standards, so this is where you learn it.

      Rootless

      • Under the hood

        This is the payoff for I1's user-namespace work: uid 0 inside is a mapped, unprivileged uid outside, so a container escape lands the attacker as a user who owns nothing. The mapping comes from your subuid/subgid ranges, and newuidmap/newgidmap — themselves setuid helpers — are what let an unprivileged user establish a mapping wider than one id. Everything else about rootless follows from the fact that the container is genuinely running as you: the files it writes on a bind mount are owned by a mapped uid, which is the cause of the drill fault in I10.12 and of nearly every "permission denied with a uid nobody recognises" report.

      • Under the hood

        Rootless is a real reduction in blast radius and a real reduction in convenience, and both halves deserve honesty. Networking is the biggest change: without CAP_NET_ADMIN on the host you cannot create a veth into the host namespace, so rootless stacks use a userspace network layer (slirp4netns or its faster successors), which costs throughput and complicates anything expecting real host networking. Cgroup limits need systemd's user-level delegation to work at all, and overlayfs in a user namespace only became broadly possible with recent kernels. The correct summary is: excellent for developer machines and CI builders, still uncommon for production nodes.

      • Under the hood

        The table forces the sentence most container security material avoids: a container is a process with restricted views, not a security boundary in the sense a virtual machine is. All of these controls share one kernel, so a kernel vulnerability reachable by syscall defeats them collectively — which is why seccomp, which reduces the reachable syscall surface, is disproportionately valuable, and why genuinely hostile multi-tenancy uses a VM boundary (Kata, Firecracker, gVisor's intercepting kernel) rather than a hardened namespace. Knowing which rows in your table are empty is what lets you argue for that when it is warranted, and not before.

      Supply chain

      • Under the hood

        The mechanism is B12's digital signatures with no new cryptography: sign the image's digest, which is the one identifier that cannot be moved. Two details make it practical. First, the signature is stored in the registry itself under a digest-derived tag (or as a referring artifact), so no separate infrastructure is needed — which also means anyone who can pull the image can verify it. Second, keyless signing exists because key management is where signing programmes die: instead of a long-lived private key, you get a short-lived certificate bound to an OIDC identity ("this GitHub Actions workflow in this repo") and a public transparency log entry proving it existed. The trust statement changes from "someone with the key" to "this build system", which is usually what you actually wanted.

      • Under the hood

        A signature answers who vouches for these bytes; provenance answers where these bytes came from. The distinction became load-bearing after a run of attacks in which the build system itself was compromised — a perfectly valid signature over a maliciously-built artifact is still perfectly valid. Provenance is a signed in-toto statement naming the source repository, commit, build parameters and builder identity, so a policy can demand not merely "signed" but "built by our pipeline from our main branch". In Kubernetes this is enforced at admission (a policy controller verifying before the image is ever pulled), which is the only place it can be enforced usefully.

      • Under the hood

        An SBOM is a parts list, and its value is measured entirely in incident time. When a critical vulnerability in a widely-used library is announced on a Friday evening, the organisations that answer "am I affected?" in minutes are the ones that already have inventories; the ones that answer in days are grepping through Dockerfiles and rebuilding images to look inside them. The formats (SPDX, CycloneDX) matter less than having one at all. The honest caveat: an SBOM lists what the scanner could identify — a vendored C library copied into a source tree, or a binary built from an unpackaged dependency, is invisible to it, so it is a strong inventory and not a proof.

      • Under the hood

        A scanner compares package versions against a vulnerability database, so what it reports is packages present with known advisories — not exploitability. A CVE in libxml2 in an image whose only process is a static Go binary that never loads it is a true statement and an irrelevant one, and drowning teams in those is how scanning programmes lose credibility. The base-image arithmetic is the part that generalises: you cannot have a vulnerability in a package you did not ship, so a minimal base removes whole categories at once — and it also removes the shell, the package manager and the tools an attacker would have used post-compromise. The trade is real debugging friction, which ephemeral debug containers exist to solve.

      • Under the hood

        I4 taught that a tag is a mutable pointer; here is the security consequence, and it is the whole reason the second drill fault below exists. A signature refers to a digest, so re-pushing a tag silently separates the tag from the signature, and every deployment that says :v1 gets unsigned content while every check that used the digest keeps passing. Registry-side immutable tags and pull-through mirror policies exist to blunt this, but the reliable fix is at the consumer: pin digests in production manifests, let a bot propose updates, and let admission verify the signature over the digest you pinned. It is also why imagePullPolicy: Always is not a security control — it fetches whatever the tag means now.

      I12 — Observability of a running runtime

      10 cp · ~4 h

      The short module that makes the other twelve debuggable. One line of application output, traced from write(2) to the file kubectl logs reads; one number, traced from a cgroup file to a dashboard — and the honest limits of both.

      I7 (the shim owns the stdio) and I8 (the CRI log format and who chose the directory). B7's cgroup files return as the source of every container metric there is.

      Logs

      • Under the hood

        The chain matters because every well-known logging surprise is a property of one specific hop. The workload never knows it is being logged — it writes to a file descriptor, which is a pipe, and that is the entire contract. The shim must be the one holding the read end (I7's whole reason for existing), which is why logs survive a containerd restart. And the timestamp on each line is written by the runtime at the moment it read the pipe, not by the application, which is why a buffered application can produce a burst of lines all stamped within the same millisecond, minutes after the events they describe.

      • Under the hood

        The P/F tag exists because a pipe read returns whatever bytes are available, not whole lines, and something downstream must be able to reassemble them — which is a problem log shippers get wrong constantly, producing a JSON application log chopped into three unparseable fragments in your logging backend. The stdout/stderr distinction is preserved all the way from the container, which is why kubectl logs can interleave them but a shipper can separate them, and why "the error only appears in the console, not in our log system" is usually a filter someone wrote years ago.

      • Under the hood

        The kubelet performs the rotation (with containerLogMaxSize and containerLogMaxFiles), not logrotate and not the runtime — so the default of a few files of a few megabytes is a node-level setting that silently defines how much history kubectl logs can ever show, and no amount of scrolling recovers the rest. That is the honest reason log shipping to a real backend exists rather than being an enterprise nicety. The in-container-file case is the harder lesson: those bytes go to the writable layer, so they are invisible to kubectl logs, uncollected by every shipper, counted against ephemeral storage, and deleted with the container — which is the exact combination that fills nodes in I10.2.

      Metrics

      • Under the hood

        B7's files, now being read by an industry. Every layer above — docker stats, cAdvisor, metrics-server, your Grafana dashboard, the HPA's scaling decision — is ultimately reading these same files and doing arithmetic, so "the dashboard disagrees with the container" is nearly always a question about sampling interval or unit conversion rather than about truth. Finding your way to the container's cgroup path is the skill worth drilling: from the container ID via the runtime, or from the workload PID via /proc/<pid>/cgroup, which works even when the runtime is not answering.

      • Under the hood

        Two demystifications for the price of one. cAdvisor is not an agent you install — it is compiled into the kubelet, which is why container metrics exist on a stock cluster with nothing added and why the kubelet's own /metrics/cadvisor endpoint is where metrics-server gets its numbers. And the exposition format is deliberately trivial: a text endpoint anything can produce, pulled on an interval, with no client library required. That combination is exactly why the project below can be fifty lines and still be a real exporter.

      • Under the hood

        Graphing a counter raw produces a rising line that means nothing, and averaging a gauge over a long window hides exactly the spike that killed your pod — both are common enough to be worth naming. The CPU counter also explains why "CPU usage" for a container is always an average over an interval and never an instant, so a container throttled hard in fifty-millisecond bursts can show a comfortable one-minute average while its latency is ruined; cpu.stat's nr_throttled and throttled_usec are the fields that tell you the truth, and they are the first thing to check when a service is slow but "not using its CPU limit".

      Events and deeper

      • Under the hood

        Logs tell you what a workload said, metrics tell you what it consumed, and events tell you what the runtime did — three questions that people routinely try to answer with the wrong signal. The classic case is a pod that never produced a log line: there is nothing to read because nothing ran, and only the event stream (or the exit event's code) distinguishes "image pull failed" from "started and exited instantly" from "sandbox never came up". Note that this is the runtime's own stream, distinct from Kubernetes Events in the API, which are the kubelet's summary of the same reality and are pruned after an hour.

      • Under the hood

        This works because of the fact the whole track has been building toward: a container is a process, so every host tool that takes a PID works on it, and none of them need to be installed inside the image — which is the cleanest answer to "how do I debug a distroless container with no shell". eBPF extends the same idea by letting you attach small verified programs to kernel events and watch syscalls, network flows or file access across every container at once, with no instrumentation in the workloads. The cost is honest and worth stating: it needs elevated privileges and host namespaces, so the observability agent is itself among the most powerful things running on your node.

      I13 — Capstone: build minidock, then the gauntlet

      12 cp · ~8 h

      No new concepts — assembly and proof. Every module's mini project becomes one layer of a single tool that pulls, unpacks, runs, networks, mounts, logs and supervises containers. Then eight planted faults, against a clock.

      All of I0–I12, and the artefacts they produced: pull.py, oci-inspect.py, microshim.py, tinybuild.py, cni-minibridge and volman.py. If a module still has unticked checkpoints, finish it first — debugging two unfamiliar layers at once is how people conclude they are bad at this.

      Capstone — minidock, one layer at a time

      • Under the hood

        You are rebuilding I7's content store and metadata store, and the design decisions arrive on their own: verify-on-write because a name that disagrees with its bytes is the one error content addressing lets you catch for free, and a separate name index because names are the one thing that cannot be recomputed from the data. Keep the two stores in different directories — when you reach the gauntlet's corrupted-blob fault, being able to delete one and keep the other is the difference between a one-line fix and a re-pull of everything.

      • Under the hood

        This is a snapshotter, and the chain-ID keying is the whole of it: I4 argued that the cache key must be the chain rather than the layer, and here you feel why, because two images sharing a base must share directories up to the exact point their chains diverge and not one layer further. Whiteouts are the fiddly part and the one worth testing deliberately — a .wh. entry in a layer tar is a deletion instruction, not a file, and getting it wrong produces containers with ghost files that no image inspection will explain.

      • Under the hood

        Here the track's thesis is fully visible in your own code: translating an image config into a runtime config is essentially all that "running an image" means, and it is why the two specs are separate documents. Your shim is doing containerd's most important job — staying alive to own the stdio and reap the exit status — and if you now kill minidock itself while a container runs and the container survives, you have independently reproduced I7.3's architecture, which is the moment to stop and appreciate it.

      • Under the hood

        Note what you are not doing: minidock contains no networking code at all. It execs a binary and parses JSON, exactly as containerd does, which means any conformant plugin — including the reference bridge — can be dropped in with no change to your tool. That substitution test is the best possible proof that you implemented a contract rather than a special case. The DEL-on-teardown discipline is the same one I9.3 made a rule, and skipping it is how you will produce the gauntlet's IPAM-exhaustion fault yourself, by accident, before you ever run the script that plants it.

      • Under the hood

        Writing the log format yourself is what makes I12's reading of it stick, and the rotation is where you meet the real decision: rotate and lose history, or keep everything and let a chatty container fill the disk. There is no third option, which is precisely why the kubelet has containerLogMaxSize and why kubectl logs cannot show you last Tuesday. Implementing minidock logs also forces the partial-line reassembly problem on you from the reader's side, which is the half most log shippers get wrong.

      • Under the hood

        The restart logic is where B13 finally arrives: restarting a failed container is a reconciliation loop comparing desired state against observed state, and the moment you write it you inherit every problem the real ones have — crash loops needing exponential backoff, the difference between "exited cleanly" and "was killed", and the question of what should happen to a container whose node rebooted. When you can name those three problems in your own code, you can read the kubelet's syncLoop in the advanced track as a more careful version of something you have written, which is exactly the position this track set out to put you in.

      The debugging gauntlet

      • Under the hood

        Speed on a real incident comes from having an order, not from knowing more commands, and this stack has a natural one: is the daemon answering, is the client talking to the right endpoint, does the image exist locally, did the sandbox come up, did the network attach, did the container start, did it exit. Almost every minute you lose in run 1 will turn out to be a rung skipped or a guess made before evidence — and you cannot fix a habit you have not named.
